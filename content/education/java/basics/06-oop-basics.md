지금까지는 값과 문장의 이야기였다. 변수에 값을 담고, 연산하고, 조건과 반복으로 흐름을 만들었다. 이 장부터는 그 문장들을 무엇으로 나눌 것인가의 이야기다. 원리는 셋이다. 첫째, **객체는 데이터와 그 데이터의 규칙을 한 단위에 묶은 책임이다.** 절차지향은 기능으로 나누고 데이터를 그 사이로 흘려보내지만, 객체지향은 채널 값과 채널을 올리는 규칙을 TV 하나에 넣는다. 그래서 변경이 그 단위 안에서 끝나고, 메서드를 부르는 쪽은 안을 몰라도 된다. 둘째, **클래스는 설계도이고, 값은 `new`가 힙에 잡은 인스턴스에 살고, 변수에는 그 주소만 들고, 메서드는 호출 스택의 프레임 위에서 산다.** 사는 곳이 셋이라 변수의 종류가 셋이고, `static`은 클래스 공간에 하나뿐이고, 자바는 언제나 변수에 든 값(참조형이면 주소)을 복사해 넘기고, `this`는 숨겨진 첫 인자다. 셋째, **인스턴스는 "기본값 → 적힌 순서 → 생성자"의 한 사슬로 초기화되고, 컴파일러는 호출 문장만 보고 메서드와 생성자를 고르며 그 사슬이 끊기지 않게 지킨다.** 반환 타입으로는 오버로딩을 못 가르고, 생성자를 하나 쓰면 기본 생성자가 사라지고, `this(...)`는 첫 문장이어야 한다. 왜 `new`가 필요한지, 왜 `static`은 하나뿐인지, 왜 자바는 값만 전달하는지, 왜 생성자를 하나 만들면 기본 생성자가 사라지는지가 이 장의 "왜"다.

## 1. 왜 객체로 나누는가

| 얻는 것 | 어떻게 | 왜 |
|:------|:-----|:---|
| 관리 용이성 | 데이터와 그 규칙이 한 곳에 있다 | 변경이 그 단위 안에서 끝난다 |
| 신뢰성 | 바깥에서 데이터를 직접 만지지 못하게 한다 | 규칙을 우회할 길이 없다 |
| 재사용성 | 단위째로 가져다 쓰거나 확장한다 | 단위가 스스로 완결되어 있다 |

첫째 원리다. 절차지향 프로그램에서 "채널을 올린다"는 기능은 함수 하나이고, 채널 값은 그 함수와 무관한 어딘가의 변수다. 채널 값을 쓰는 함수가 열 개면 그 열 곳이 전부 그 변수의 규칙(0 이상, 최대 채널 이하)을 알아야 하고, 규칙이 바뀌면 열 곳을 고쳐야 한다. 객체지향은 채널 값과 채널을 올리는 기능을 TV라는 하나의 단위에 묶는다. 채널의 규칙은 TV 안에만 있고, 바깥은 "채널을 올려라"고 말할 뿐 값을 직접 만지지 않는다. 규칙이 바뀌면 TV 하나만 고치면 된다. "실제 세계는 사물로 이루어져 있고 모든 사건은 사물의 상호작용"이라는 객체지향의 표어는 이 설계 방침을 현실에 빗댄 것이다. 중요한 것은 비유가 아니라 책임을 어디에 둘 것인가라는 질문이다.

## 2. 클래스와 인스턴스

### 2.1 설계도와 실체

| 용어 | 뜻 | 어디에 있나 | 왜 나뉘나 |
|:-----|:---|:--------|:-------|
| 클래스 | 객체가 어떤 값을 가지고 무엇을 할 수 있는지 정의한 것 | 메서드 영역. 프로그램에 하나 | 모양은 한 번만 적으면 된다 |
| 인스턴스(객체) | 클래스대로 만들어져 실제 값을 가진 것 | 힙. `new`할 때마다 하나씩 | 값은 담을 자리가 있어야 하고, TV마다 채널이 다르다 |

```java
public class Tv {
    // 속성: 인스턴스마다 값을 가진다
    String color;
    boolean power;
    int channel;

    // 기능: 속성을 다룬다
    void power() { power = !power; }
    void channelUp() { ++channel; }
    void channelDown() { --channel; }
}
```

```text
Tv 클래스 (설계도, 메서드 영역)
  color, power, channel  ← 속성
  power(), channelUp()   ← 기능
          │ new Tv()
          ▼
t ──▶ ┌─────────────────┐  힙의
      │ color   = null  │  인스턴스
      │ power   = false │
      │ channel = 0     │
      └─────────────────┘
```

둘째 원리다. 클래스는 "TV에는 채널이 있다"고 말할 뿐 어느 TV의 채널이 몇 번인지는 담지 않는다. 값을 담으려면 그 값이 놓일 메모리가 있어야 하고, 그 메모리를 힙에 잡는 것이 `new`다. `new`가 없으면 아무리 클래스를 잘 만들어도 값을 넣을 자리가 없다. 클래스 하나에서 인스턴스를 얼마든지 만들 수 있고, 각 인스턴스는 자기만의 값을 갖는다. "클래스로부터 인스턴스를 만든다"는 뜻으로 인스턴스화라 하고, 어느 클래스에서 나왔는지를 강조할 때 객체 대신 인스턴스라 부른다.

### 2.2 참조 변수로 다룬다

```java
Tv t;            // 1. 변수만. 아직 없다
t = new Tv();      // 2. 힙에 만든다
t.channel = 7;     // 3. 인스턴스에 쓴다
t.channelDown();   // 4. channel은 6
```

[Chapter 02](../02-java-variable)에서 참조형 변수에는 주소가 들어 있다고 했다. 인스턴스는 힙에 있고 크기도 제각각이라 변수에 직접 담을 수 없으니, 변수에는 주소만 담고 그 주소를 통해 인스턴스를 다룬다. 인스턴스에 이름이 없는 이유도 이것이다. 이름은 참조 변수에 있고, 인스턴스는 주소로만 찾아진다.

```java
Tv t1 = new Tv();
Tv t2 = new Tv();
t1.channel = 7;
t2.channel;        // 0. 별개의 인스턴스

Tv t3 = new Tv();
Tv t4 = t3;        // 주소가 복사된다
t3.channel = 7;
t4.channel;        // 7. 같은 인스턴스
```

```text
t3 ──▶ ┌──────────┐
       │ channel 7│
t4 ──▶ └──────────┘   같은 인스턴스
```

| 문장 | 인스턴스 수 | 왜 |
|:-----|:--------|:---|
| `Tv t2 = new Tv();` | 하나 더 | `new`마다 힙에 새로 잡는다 |
| `Tv t4 = t3;` | 그대로 | 복사되는 것은 변수에 든 주소다 |
| `t3 = null;` | 그대로. 단, 아무도 안 가리키면 회수 대상 | 닿을 수 없는 인스턴스는 가비지 컬렉터가 거둔다 |

`t4 = t3`는 인스턴스를 복사하지 않는다. 주소만 복사되므로 두 변수가 한 인스턴스를 가리키고, 한쪽으로 바꾸면 다른 쪽에서도 보인다. 참조 변수 하나는 한 번에 인스턴스 하나만 가리키지만, 인스턴스 하나를 여러 변수가 가리킬 수는 있다. 아무 변수도 가리키지 않게 된 인스턴스는 더 이상 닿을 수 없으므로 가비지 컬렉터가 회수한다([자동 메모리 관리](../../jvm/memory-management)).

### 2.3 객체 배열

```java
Tv[] tvs = new Tv[3];
// [null, null, null]. 주소 칸 3개
for (int i = 0; i < tvs.length; i++) {
    tvs[i] = new Tv();   // 따로 만든다
    tvs[i].channel = i + 10;
}
```

```text
tvs ──┐
      ▼
    ┌──────┐
    │ [0] ─┼──▶ Tv (ch=10)
    │ [1] ─┼──▶ Tv (ch=11)
    │ [2] ─┼──▶ Tv (ch=12)
    └──────┘
```

[Chapter 05](../05-array)에서 본 참조형 배열 그대로다. `new Tv[3]`은 TV 세 대를 만드는 것이 아니라 TV의 주소를 담을 칸 세 개를 만든다. 칸은 `null`로 시작하고, 인스턴스는 `new Tv()`로 하나씩 만들어 넣어야 한다.

## 3. 변수의 세 종류

```java
class Variables {
    int iv;            // 인스턴스 변수
    static int cv;     // 클래스 변수

    void method() {
        int lv = 0;    // 지역 변수
    }
}
```

| 종류 | 선언 위치 | 어디에 사는가 | 만들어질 때 | 사라질 때 | 왜 |
|:-----|:-------|:---------|:--------|:-------|:---|
| 인스턴스 변수 | 클래스 영역 | 힙의 인스턴스 안 | 인스턴스 생성 시 | 인스턴스가 회수될 때 | 인스턴스마다 값이 다르다 |
| 클래스 변수 (`static`) | 클래스 영역 | 클래스당 하나의 공간 | 클래스가 처음 쓰일 때 | 프로그램 종료 시 | 모든 인스턴스가 같은 값을 본다 |
| 지역 변수 | 메서드, 블록 안 | 호출 스택의 프레임 | 선언문 실행 시 | 블록을 벗어날 때 | 그 호출 동안만 필요하다 |

```text
┌──────────────┬──────────────────────┐
│ 메서드 영역  │ 클래스, static 변수  │
├──────────────┼──────────────────────┤
│ 힙           │ 인스턴스와 그 변수   │
├──────────────┼──────────────────────┤
│ 호출 스택    │ 프레임, 지역 변수    │
└──────────────┴──────────────────────┘
```

둘째 원리다. 변수의 종류가 셋인 이유는 사는 곳이 셋이기 때문이다. 인스턴스 변수는 인스턴스 안에 있으니 인스턴스마다 하나씩이고, 인스턴스와 운명을 같이한다. 지역 변수는 메서드가 호출될 때 만들어지는 스택 프레임 안에 있으니 메서드가 끝나면 사라진다. 클래스 변수는 어디에 있는가. 각 영역이 무엇을 담는지는 [JVM 런타임 데이터 영역 정리](../../../../blog/tech-review/jvm-runtime-data-areas)에서 자세히 본다.

### 3.1 static은 왜 하나뿐인가

```java
public class Card {
    String kind;   // 카드마다 다르다
    int number;

    static int width = 100; // 모두 같다
    static int height = 250;
}

Card.width;   // 100. 인스턴스 없이도

Card c1 = new Card();
Card c2 = new Card();
c1.width = 50;
c2.width;     // 50. 같은 공간이다
```

| 변수 | 인스턴스가 없을 때 | 인스턴스가 백 개일 때 | 왜 |
|:-----|:------------|:-------------|:---|
| `kind`, `number` | 없다 | 백 개 | 카드마다 다른 값이라 인스턴스 안에 산다 |
| `width`, `height` | 있다 | 하나 | 모든 카드가 같은 값. 복사해 두면 낭비이고 바꿀 때 위험하다 |

카드의 종류와 숫자는 카드마다 다르지만 카드의 가로세로 크기는 모든 카드가 같다. 같은 값을 인스턴스마다 복사해 두는 것은 낭비이고, 바꿀 때 전부 바꿔야 하는 위험이기도 하다. `static`을 붙이면 그 변수는 인스턴스가 아니라 클래스에 속한 공간 하나에 놓인다. 인스턴스가 하나도 없어도 존재하고, 인스턴스가 백 개여도 하나다. `c1.width`와 `c2.width`가 같은 값을 보이는 것은 같은 변수이기 때문이다.

{{< callout type="warning" >}}
클래스 변수는 `Card.width`처럼 **클래스 이름으로** 접근한다. `c1.width`도 동작하지만 읽는 사람은 카드마다 다른 값이라고 오해한다. 이름이 곧 "이 값은 클래스 전체의 것"이라는 안내가 된다.
{{< /callout >}}

클래스 변수가 만들어지는 시점은 정확히는 클래스가 처음 사용될 때다. 인스턴스를 만들거나, `static` 메서드를 부르거나, `static` 변수에 접근하는 순간 JVM이 그 클래스를 초기화한다. [Chapter 01](../01-java-intro)에서 본 게으른 로딩과 같은 원리로, 쓰지 않는 클래스의 `static` 변수는 만들어지지도 않는다.

## 4. 메서드

### 4.1 왜 문장을 메서드로 묶는가

```text
반환타입 이름(매개변수) {   // 선언부
    // 구현부
    return 반환값;
}
```

```java
int add(int x, int y) {
    return x + y;
}

void printGugudan(int dan) {
    // 반환값이 없어도 return으로 끝낸다
    if (dan < 2 || dan > 9) return;
    for (int i = 1; i <= 9; i++) {
        System.out.printf(
            "%d * %d = %d%n",
            dan, i, dan * i);
    }
}
```

| 얻는 것 | 뜻 | 왜 |
|:------|:---|:---|
| 재사용 | 같은 일을 여러 곳에서 다시 쓴다 | 문장 묶음에 이름이 있다 |
| 유지보수 | 고칠 때 한 곳만 고친다 | 같은 문장이 한 곳에만 있다 |
| 읽기 | 큰 작업을 이름 붙은 단위로 읽는다 | 부르는 쪽은 선언부만 알면 된다. 안을 몰라도 된다 |

메서드는 문장 여러 개에 이름을 붙인 것이다. 얻는 것은 세 가지이고 세 번째가 가장 중요하다. 메서드를 부르는 쪽은 선언부만 알면 된다. 무엇을 받아 무엇을 돌려주는지는 알아야 하지만 어떻게 하는지는 몰라도 된다. 첫째 원리의 반쪽이다. 이 "안을 몰라도 되는" 성질 위에 [Chapter 07](../07-oop-advanced)의 캡슐화가 세워진다.

| 구성 | 뜻 | 규칙 | 왜 |
|:-----|:---|:-----|:---|
| 반환 타입 | 돌려주는 값의 타입 | 없으면 `void` | 돌려주는 값도 타입이 있어야 받는 쪽이 담는다 |
| 이름 | 메서드의 이름 | 변수 규칙과 같다. 동사로 시작하는 것이 관례 | 하는 일을 이름이 말한다 |
| 매개변수 | 받을 값의 타입과 이름 | 여러 개면 쉼표로 | 호출마다 다른 값으로 같은 문장을 돌린다 |
| 반환값 | 하나 | 여럿이면 배열이나 객체(`record`)에 담는다 | 호출한 쪽 스택에 값을 올려 놓는 자리가 하나다 |

반환값은 하나다. 메서드가 끝날 때 JVM은 값 하나를 호출한 쪽의 스택에 올려 놓고 프레임을 걷어 내는데, 그 자리가 하나이기 때문이다. 여러 값을 돌려주고 싶으면 배열이나 객체에 담아 하나로 만든다. Java 16의 `record`가 이런 용도의 작은 묶음을 한 줄로 정의해 준다.

### 4.2 인자와 매개변수

```java
long add(int a, long b) {
    return a + b;
}

add(3, 5L);   // 된다
add(3, 5);    // 된다. int 5 → long
add(3L, 5);   // 안 된다. long → int
```

| 호출 | 되나 | 왜 |
|:-----|:-----|:---|
| `add(3, 5L)` | 된다 | 타입이 그대로 맞는다 |
| `add(3, 5)` | 된다 | `int` 5가 `long` b로 자동 변환된다 |
| `add(3L, 5)` | 안 된다 | `long` 3L을 `int` a에 넣을 수 없다. "possible lossy conversion" |

호출할 때 넘기는 값이 인자, 선언부에서 받는 변수가 매개변수다. 인자의 개수와 순서가 매개변수와 같아야 하고, 타입은 같거나 [Chapter 03](../03-java-operator)의 자동 형변환으로 맞출 수 있어야 한다. 큰 타입에서 작은 타입으로는 자동 변환이 없으므로 세 번째 호출은 실패한다.

### 4.3 호출 스택: 메서드는 프레임 위에서 산다

```java
static void main(String[] args) {
    first();
}
static void first() { second(); }
static void second() { /* ... */ }
```

```text
1) [main]
2) [main, first]
3) [main, first, second]
4) [main, first]
5) [main]
6) []
```

| 사건 | 스택 | 왜 |
|:-----|:-----|:---|
| 메서드 호출 | 프레임이 쌓인다 | 지역 변수와 매개변수를 담을 자리가 필요하다 |
| 메서드 종료 | 프레임이 걷힌다 | 바로 아래 프레임, 즉 호출한 메서드로 돌아간다 |
| 끝없는 재귀 | `StackOverflowError` | 스택 크기가 정해져 있다 |

둘째 원리의 셋째 집이다. 메서드가 호출되면 그 메서드의 지역 변수와 매개변수를 담을 프레임이 호출 스택에 쌓이고, 메서드가 끝나면 프레임이 걷히면서 바로 아래 프레임, 즉 호출한 메서드로 돌아간다. 맨 위 프레임이 지금 실행 중인 메서드다. [Chapter 02](../02-java-variable)에서 지역 변수가 메서드를 벗어나면 사라진다고 한 것은 이 프레임이 걷히기 때문이다. 스택은 크기가 정해져 있다. 메서드가 자기 자신을 끝없이 부르면 프레임이 쌓이다 한계에 닿아 `StackOverflowError`가 난다. 재귀 호출에 종료 조건이 필요한 이유가 프레임에 있다.

### 4.4 자바는 값만 전달한다

```java
static void change(int x) { x = 100; }

int x = 10;
change(x);   // change의 x는 복사본
x;           // 10
```

```java
class Data { int x; }
static void change(Data d) {
    d.x = 100;
}

Data d = new Data();
d.x = 10;
change(d);   // 주소의 복사본
d.x;         // 100
```

```text
main의 d  ──(주소 복사)──▶  change의 d
     │                            │
     └──▶  ┌─────────┐ ◀─────────┘
           │ x: 100  │
           └─────────┘
```

| 넘기는 변수 | 복사되는 것 | 메서드 안에서 | 호출한 쪽 | 왜 |
|:--------|:--------|:---------|:-------|:---|
| 기본형 `x` | 값 | `x = 100` | 그대로 10 | 복사본을 바꿨다 |
| 참조형 `d` | 주소 | `d.x = 100` | 100으로 보인다 | 같은 인스턴스를 가리킨다 |
| 참조형 `d` | 주소 | `d = new Data()` | 그대로 | 복사된 주소를 다른 주소로 덮어썼을 뿐이다 |

두 결과가 달라 보이지만 규칙은 하나다. 자바는 언제나 변수에 든 값을 복사해서 넘긴다. 둘째 원리다. 기본형 변수에는 값이 들어 있으니 값이 복사되고, 참조형 변수에는 주소가 들어 있으니 주소가 복사된다. 주소의 복사본으로 인스턴스를 고치면 원본 변수도 같은 인스턴스를 보고 있으니 바뀐 것이 보일 뿐이다. 이 규칙의 결과를 하나 더 보면 "참조를 전달한다"와 어떻게 다른지 분명해진다.

```java
static void replace(Data d) {
    d = new Data();   // 복사본만 바뀐다
}

Data d = new Data();
replace(d);
// main의 d는 여전히 원래 인스턴스
```

매개변수 `d`에 새 인스턴스를 넣어도 호출한 쪽의 `d`는 바뀌지 않는다. 복사된 주소를 다른 주소로 덮어쓴 것이지 원본 변수를 만진 것이 아니기 때문이다. 같은 이유로 두 참조를 맞바꾸는 `swap` 메서드는 자바로 쓸 수 없다. 배열도 참조형이므로 메서드 안에서 요소를 바꾸면 원본에 반영되지만, 배열 변수 자체를 새 배열로 바꾸는 것은 호출한 쪽에 영향을 주지 않는다.

## 5. 오버로딩

```java
int add(int a, int b) {
    return a + b;
}
long add(long a, long b) {
    return a + b;
}
int add(int a, int b, int c) {
    return a + b + c;
}
```

같은 이름의 메서드를 매개변수만 다르게 여러 개 두는 것이 오버로딩이다. 정수를 더하든 실수를 더하든 "더한다"는 뜻은 같으니 이름도 같은 것이 자연스럽고, 부르는 쪽은 타입마다 다른 이름을 외울 필요가 없다.

| 항목 | 오버로딩 구분에 쓰이나 | 왜 |
|:-----|:--------------|:---|
| 메서드 이름 | 같아야 한다 | 같은 이름이라서 오버로딩이다 |
| 매개변수의 개수, 타입, 순서 | 하나라도 다르면 구분된다 | 호출 문장에 항상 드러난다 |
| 매개변수의 이름 | 관계없다 | 호출 문장에 안 나온다 |
| 반환 타입 | 관계없다 | `add(1, 2);`처럼 결과를 안 쓰는 호출에는 단서가 없다 |

```java
int add(int a, int b) { return a + b; }
long add(int a, int b) { return a + b; }
// 컴파일 오류. 매개변수가 같다
```

셋째 원리다. 반환 타입으로는 구분하지 못한다. 컴파일러는 호출하는 문장을 보고 어느 메서드인지 정하는데, `add(1, 2);`처럼 결과를 쓰지 않는 호출에서는 반환 타입을 알 단서가 전혀 없기 때문이다. 매개변수는 호출 문장에 항상 드러나므로 구분의 기준이 될 수 있다. 컴파일러의 오류 메시지도 "method add(int,int) is already defined"다.

### 5.1 어느 메서드가 골라지는가

| 단계 | 허용하는 변환 | 예 | 왜 이 순서인가 |
|:-----|:----------|:---|:----------|
| 1 | 없음, 또는 자동 형변환 | `add(int, long)`에 `add(3, 5)` | 가장 싸고 뜻이 안 바뀌는 변환 |
| 2 | 1단계 실패 시, 박싱·언박싱까지 | `add(Integer, Integer)`에 `add(3, 5)` | 객체를 만드는 변환은 그다음 |
| 3 | 2단계 실패 시, 가변 인자까지 | `add(int...)`에 `add(3, 5)` | 배열을 만드는 변환은 마지막 |

인자에 딱 맞는 메서드가 없으면 컴파일러는 정해진 순서로 후보를 찾는다. 앞 단계에서 후보가 나오면 뒤 단계는 보지 않는다. 그래서 `method(int, int)`와 `method(int...)`가 함께 있을 때 `method(1, 2)`는 모호하지 않고 앞의 것이 골라진다. 고정 인자 메서드가 1단계에서 이미 잡히기 때문이다. 모호함은 같은 단계 안에서 어느 쪽이 더 구체적인지 가릴 수 없을 때 생긴다.

```java
void method(int... args) { }
void method(Integer... args) { }

method(1, 2);   // 컴파일 오류. 모호하다
```

### 5.2 가변 인자

```java
String concat(String... args) {
    // args는 String[]이다
    return String.join("", args);
}

concat();                // 0개
concat("a");
concat("a", "b", "c");
// new String[]{"a", "b", "c"}로 바뀐다
```

[Chapter 05](../05-array)에서 본 대로 가변 인자는 배열이다. 컴파일러가 호출 문장의 인자들을 배열로 묶어 넘기고, 메서드 안에서는 그냥 배열이다. 가변 인자가 마지막 매개변수여야 하는 이유는 여기에 있다. `(String... args, int n)`처럼 뒤에 다른 매개변수가 오면, 인자 목록에서 어디까지가 배열이고 어디부터가 `n`인지 정할 수 없다. 컴파일러는 "varargs parameter must be the last parameter"로 거절한다.

## 6. 생성자

### 6.1 인스턴스가 태어나는 세 단계

```java
class Card {
    String kind;
    int number;

    Card() { }   // 매개변수 없는 생성자

    Card(String kind, int number) {
        this.kind = kind;
        this.number = number;
    }
}

Card c = new Card("Heart", 7);
```

| 단계 | 누가 | 하는 일 | 왜 |
|:-----|:-----|:------|:---|
| 1 | `new` | 힙에 `Card` 크기의 메모리를 잡고 0으로 채운다 | 값을 넣을 자리가 먼저 있어야 한다 |
| 2 | 생성자 | 인자에 맞는 생성자가 그 메모리에 값을 채운다 | 초기화는 클래스가 정한 규칙대로 |
| 3 | `new` 식 | 완성된 인스턴스의 주소를 돌려준다 | 그래서 생성자에는 반환 타입이 없다 |

둘째 원리와 셋째 원리가 만나는 자리다. `new Card("Heart", 7)`은 세 단계로 실행된다. 먼저 `new`가 힙에 `Card` 크기의 메모리를 잡고 [Chapter 02](../02-java-variable)에서 본 대로 전부 0으로 채운다. 그다음 인자에 맞는 생성자가 호출되어 그 메모리에 값을 채운다. 마지막으로 완성된 인스턴스의 주소가 `new` 식의 값으로 돌아와 `c`에 들어간다. 생성자는 인스턴스를 만드는 것이 아니라 이미 만들어진 메모리를 초기화하는 메서드다. 생성자에 반환 타입이 없는 이유가 이것이다. 돌려줄 것이 없다. 주소를 돌려주는 것은 `new` 식이다. 이름이 클래스 이름과 같아야 하는 것은 "이 클래스의 인스턴스를 초기화하는 것"임을 이름으로 보이기 위한 약속이다.

### 6.2 기본 생성자는 왜 사라지는가

```java
class Card {        // 생성자가 없으면
    String kind;   // Card()가 생긴다
}
new Card();         // 된다

class Card {
    Card(String kind, int number) { }
    // 생성자를 하나라도 쓰면
}
new Card();         // 컴파일 오류
```

| 클래스에 적은 생성자 | 컴파일러가 넣어 주는 것 | 왜 |
|:--------------|:---------------|:---|
| 없음 | `Card() { }` | 생성자가 하나는 있어야 인스턴스를 만든다 |
| 하나라도 있음 | 없음 | 적은 생성자가 "이렇게만 만들 수 있다"는 선언이다. 컴파일러가 그 선언을 무력화하지 않는다 |

셋째 원리다. 인스턴스를 만들려면 생성자가 반드시 하나는 있어야 한다. 그래서 생성자가 없는 클래스에는 컴파일러가 매개변수 없는 기본 생성자를 넣어 준다. 그런데 개발자가 생성자를 하나라도 쓰면 컴파일러는 물러선다. 이유는 설계 의도를 지키기 위해서다. `Card(String kind, int number)`를 만들었다는 것은 "카드는 종류와 숫자 없이 만들어질 수 없다"는 선언이다. 그런데도 컴파일러가 `Card()`를 넣어 주면 그 선언이 무력해진다. 두 방식이 모두 필요하면 두 생성자를 모두 쓰라는 것이 자바의 입장이다.

### 6.3 this: 인스턴스 자신

```java
class Car {
    String color;

    Car(String color) {
        this.color = color;
        // this.color는 인스턴스 변수
    }
}
```

| 호출 | 컴파일러가 실제로 넘기는 것 | `this` | 왜 |
|:-----|:----------------|:-------|:---|
| `t.channelUp()` | `t`의 주소를 숨겨진 첫 인자로 | 그 주소 | 어느 인스턴스의 `channel`인지 알아야 한다 |
| `Card.width`, `static` 메서드 | 인스턴스 없음 | 없다 | 넘길 주소가 없다. 인스턴스 변수도 못 쓴다 |

매개변수 이름과 인스턴스 변수 이름이 같으면 가까운 쪽인 매개변수가 우선한다. `this`는 "지금 이 메서드가 실행되고 있는 인스턴스"를 가리키는 참조라서, `this.color`라고 쓰면 인스턴스 변수를 지목할 수 있다. `this`가 어디서 오는지 알면 `static` 메서드에서 `this`를 쓸 수 없는 이유가 보인다. 인스턴스 메서드를 `t.channelUp()`처럼 부르면 컴파일러는 `t`의 주소를 숨겨진 첫 번째 인자로 함께 넘긴다. 메서드 안의 `this`는 그 숨겨진 인자다. `static` 메서드는 `Card.width`처럼 인스턴스 없이 불리므로 넘겨줄 주소가 없고, 따라서 `this`도 없다. `static` 메서드가 인스턴스 변수를 쓸 수 없는 것도 같은 이유이고, 오류 메시지가 그대로 말한다. "non-static variable cannot be referenced from a static context".

### 6.4 this(): 생성자가 생성자를 부른다

```java
class Car {
    String color;
    String gearType;
    int door;

    Car() {
        this("white", "auto", 4);
    }
    Car(String color, String gearType) {
        this(color, gearType, 4);
    }
    Car(String color, String gearType,
            int door) {
        this.color = color;
        this.gearType = gearType;
        this.door = door;
    }
}
```

| 규칙 | 내용 | 왜 |
|:-----|:-----|:---|
| `this(...)`로 위임 | 초기화는 한 생성자에 모으고 나머지는 기본값만 채워 넘긴다 | 중복을 없앤다 |
| 첫 문장이어야 한다 | `this(...)` 앞에 다른 문장을 둘 수 없다 | 인스턴스는 하나의 사슬로 처음부터 끝까지 초기화돼야 한다 |
| Java 25의 완화 (JEP 513) | 생성 중인 인스턴스를 참조하지 않는 문장은 앞에 둘 수 있다 | 인자 검증과 계산은 사슬을 끊지 않는다 |

생성자가 여럿이면 초기화 코드가 중복되기 쉽다. `this(...)`로 같은 클래스의 다른 생성자를 부르면 초기화를 한 곳에 모으고 나머지는 기본값만 채워 넘기는 구조가 된다. 위에서는 인자 세 개짜리 생성자만 실제로 값을 채우고, 나머지 둘은 그리로 위임한다. `this(...)`는 생성자의 첫 문장이어야 한다는 규칙이 있다. 셋째 원리다. 인스턴스는 하나의 생성자 사슬로 처음부터 끝까지 초기화되어야 하는데, `this()` 앞에서 인스턴스 변수를 건드리면 뒤이어 실행되는 생성자가 그 값을 덮어쓰거나, 반쯤 초기화된 인스턴스를 다른 코드가 볼 수 있기 때문이다.

{{< callout type="info" >}}
Java 25부터는 이 규칙이 조금 풀렸다(JEP 513). `this(...)`나 `super(...)` 앞에 **생성 중인 인스턴스를 참조하지 않는** 문장은 둘 수 있다. 인자를 검증해 예외를 던지거나 넘길 값을 미리 계산하는 용도다. Java 22부터 24까지는 프리뷰(JEP 447, 482, 492)라 `--enable-preview`가 필요했다. 인스턴스를 반쯤 만든 채로 노출하지 않는다는 원래 의도는 그대로다.
{{< /callout >}}

```java
Car(Car other) {   // 복사 생성자
    this(other.color, other.gearType,
        other.door);
}
```

다른 인스턴스의 값을 그대로 옮겨 새 인스턴스를 만드는 생성자를 복사 생성자라 한다. 2.2절에서 본 `t4 = t3`가 주소를 복사하는 것과 달리, 이쪽은 값이 같은 별개의 인스턴스를 만든다.

## 7. 초기화

### 7.1 무엇이 자동으로 초기화되는가

| 변수 | 초기화 | 왜 |
|:-----|:-----|:---|
| 지역 변수 | 쓰기 전에 반드시 직접 | 스택 프레임은 0으로 채워지지 않는다 ([Chapter 02](../02-java-variable)) |
| 인스턴스 변수, 클래스 변수 | 안 해도 기본값이 들어 있다 | 힙과 클래스 공간은 만들 때 0으로 채워진다 |

| 타입 | 기본값 | 왜 |
|:-----|:-----|:---|
| `boolean` | `false` | 0 비트는 거짓 |
| `char` | `'\u0000'` (널 문자) | 값이 0인 문자 |
| `byte`, `short`, `int`, `long` | `0`, `0L` | |
| `float`, `double` | `0.0` | 비트가 전부 0이면 0.0 |
| 참조형 | `null` | 주소 0은 "가리키는 것 없음" |

### 7.2 멤버 변수를 초기화하는 세 가지 방법

```java
class InitBlock {
    static int cv = 10;   // 1. 명시적
    int iv = 20;

    static { cv = cv * 2; }   // 3. 블록
    { iv = iv * 2; }

    InitBlock() { iv = iv + 1; }   // 2.
}
```

| 방법 | 언제 | 왜 |
|:-----|:-----|:---|
| 1. 명시적 초기화 | 값 하나를 넣는 것으로 끝날 때 | 선언에 바로 적는 것이 가장 읽기 쉽다 |
| 2. 생성자 | 인자에 따라 값이 달라질 때 | 인자를 받는 곳이 생성자뿐이다 |
| 3. 초기화 블록 | 클래스 변수에 계산이나 반복이 필요할 때 (`static` 블록), 모든 생성자가 공통으로 할 일이 있을 때 (인스턴스 블록) | 한 줄로 못 적거나 생성자마다 반복될 코드를 한곳에 |

값 하나를 넣는 것으로 끝나면 선언에 바로 적는 명시적 초기화가 가장 읽기 쉽다. 인자에 따라 달라지면 생성자에서 한다. 초기화 블록은 두 경우에 쓴다. 클래스 변수를 한 줄로 채울 수 없어 계산이나 반복이 필요할 때 `static` 블록을 쓰고, 모든 생성자가 공통으로 해야 할 일이 있을 때 인스턴스 블록을 쓴다.

```java
class Car {
    static int count = 0;
    String color;

    // 어느 생성자로 만들어도 한 번 센다
    { count++; }

    Car() { this("white"); }
    Car(String color) {
        this.color = color;
    }
}
```

인스턴스 초기화 블록은 모든 생성자보다 먼저 실행된다. 그래서 생성자마다 `count++`를 적지 않아도 된다. 다만 위 예처럼 생성자들이 `this()`로 한 곳에 모이는 구조라면 그 한 곳에 적어도 되므로, 블록은 정말 공통 처리가 필요할 때만 쓴다.

### 7.3 순서: 기본값, 적힌 순서, 생성자

```text
클래스 변수 (처음 쓰일 때 한 번)
  기본값
  → 명시적 초기화, static 블록
    (적힌 순서대로)

인스턴스 변수 (만들 때마다)
  기본값
  → 명시적 초기화, 인스턴스 블록
    (적힌 순서대로)
  → 생성자
```

```java
class InitTest {
    static int cv = 1;
    int iv = 1;

    static { cv = 2; }
    { iv = 2; }

    InitTest() { iv = 3; }
}
```

```text
[클래스가 처음 쓰일 때]
1) cv = 0    기본값
2) cv = 1    명시적 초기화
3) cv = 2    static 블록

[new InitTest() 마다]
4) iv = 0    기본값
5) iv = 1    명시적 초기화
6) iv = 2    인스턴스 블록
7) iv = 3    생성자

결과: cv = 2, iv = 3
```

| 순서 | 단계 | 왜 그 자리인가 |
|:-----|:-----|:----------|
| 1 | 기본값 | 초기화가 아니라 메모리 할당의 결과. `new`가 0으로 채운 뒤에야 코드가 돈다 |
| 2 | 명시적 초기화와 초기화 블록 | 우선순위가 아니라 소스에 적힌 순서. 순서를 바꿔 적으면 결과도 바뀐다 |
| 3 | 생성자 | 인자를 받아 하는 초기화가 가장 구체적이라 나머지를 덮어쓸 수 있어야 한다 |

셋째 원리의 사슬이 이것이다. 기본값이 맨 앞인 이유는 그것이 초기화가 아니라 메모리 할당의 결과이기 때문이다. `new`가 0으로 채운 뒤에야 코드가 실행된다. 명시적 초기화와 초기화 블록은 따로 우선순위가 있는 것이 아니라 소스에 적힌 순서대로 실행된다. 위 예에서 블록이 나중인 것은 블록이 아래에 적혀 있기 때문이고, 순서를 바꿔 적으면 결과도 바뀐다. 생성자가 마지막인 것은 인자를 받아 하는 초기화가 가장 구체적이라 나머지를 덮어쓸 수 있어야 하기 때문이다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 객체지향 | 데이터와 기능을 책임 단위로 묶는다 | 변경이 그 단위 안에서 끝난다 |
| 클래스, 인스턴스 | 설계도와 힙의 실체. `new`로 만든다 | 값을 담을 메모리는 `new`가 잡는다 |
| 참조 변수 | 인스턴스의 주소를 담는다 | 인스턴스는 크기가 제각각이라 변수에 못 담는다 |
| 인스턴스 변수 | 인스턴스마다 하나 | 인스턴스 안에 산다 |
| 클래스 변수 | 클래스에 하나. 클래스 이름으로 접근 | 인스턴스가 아닌 클래스 공간에 산다 |
| 지역 변수 | 메서드가 끝나면 사라진다 | 스택 프레임과 함께 걷힌다 |
| 메서드 | 문장 묶음. 반환값은 하나 | 안을 몰라도 쓸 수 있다. 반환 자리가 하나다 |
| 호출 스택 | 호출마다 프레임이 쌓이고 걷힌다 | 끝없는 재귀는 `StackOverflowError` |
| 값 전달 | 언제나 변수의 값을 복사한다 | 참조형은 그 값이 주소라 인스턴스가 공유된다 |
| 오버로딩 | 이름 같고 매개변수 다름. 반환 타입은 무관 | 호출 문장에는 매개변수만 드러난다 |
| 생성자 | 만들어진 메모리를 초기화. 반환 타입 없음 | 주소는 `new` 식이 돌려준다 |
| 기본 생성자 | 생성자를 쓰면 사라진다 | 설계 의도를 컴파일러가 무력화하지 않는다 |
| `this` | 숨겨진 첫 인자. `static`에는 없다 | 인스턴스 없이 불리면 넘길 주소가 없다 |
| `this(...)` | 첫 문장. Java 25부터 인스턴스를 안 건드리는 문장은 앞에 가능 | 초기화 사슬이 끊기면 안 된다 |
| 초기화 순서 | 기본값 → 적힌 순서 → 생성자 | 기본값은 할당의 결과, 생성자가 가장 구체적이다 |

{{< callout type="info" >}}
**용어 정리**
- **클래스 / 인스턴스**: 설계도 / `new`로 힙에 만든 실체. 인스턴스화는 그 만드는 일
- **참조 변수**: 인스턴스의 주소를 담는 변수. 대입하면 주소가 복사된다
- **인스턴스 변수 / 클래스 변수 / 지역 변수**: 힙의 인스턴스 안 / 클래스 공간에 하나 / 스택 프레임 안
- **`static`**: 인스턴스가 아니라 클래스에 속한다는 표시. 인스턴스 없이 쓴다
- **메서드**: 문장 묶음에 이름을 붙인 것. 선언부(무엇을 받아 무엇을 돌려주나)와 구현부
- **인자 / 매개변수**: 호출할 때 넘기는 값 / 선언부에서 받는 변수
- **호출 스택 / 프레임**: 호출 중인 메서드가 쌓이는 곳 / 한 호출의 지역 변수와 매개변수가 사는 칸
- **값 전달 (pass by value)**: 변수에 든 값을 복사해 넘기는 것. 참조형은 주소가 복사된다
- **오버로딩**: 같은 이름, 다른 매개변수. 컴파일러가 호출 문장을 보고 고른다
- **가변 인자**: `타입...`으로 받는 마지막 매개변수. 컴파일러가 배열로 묶는다
- **생성자**: `new`가 잡은 메모리를 초기화하는 메서드. 이름은 클래스 이름, 반환 타입 없음
- **기본 생성자**: 생성자가 하나도 없을 때 컴파일러가 넣어 주는 `클래스이름() { }`
- **`this` / `this(...)`**: 지금 실행 중인 인스턴스의 참조 / 같은 클래스의 다른 생성자 호출
- **초기화 블록**: `static { }`은 클래스가 처음 쓰일 때 한 번, `{ }`는 인스턴스를 만들 때마다 생성자 전에
