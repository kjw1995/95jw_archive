지금까지는 값과 문장의 이야기였다. 변수에 값을 담고, 연산하고, 조건과 반복으로 흐름을 만들었다. 이 장부터는 그 문장들을 **무엇으로 나눌 것인가**의 이야기다. 절차지향은 프로그램을 기능(함수)으로 나누고 데이터를 그 사이로 흘려보낸다. 객체지향은 데이터와 그 데이터를 다루는 기능을 한 덩어리로 묶어 **책임을 가진 것**, 즉 객체로 나눈다. 이 장에서는 그 덩어리를 정의하는 클래스, 그것을 메모리에 실제로 만드는 인스턴스, 그리고 인스턴스가 태어나는 과정인 생성자와 초기화를 본다. 왜 `new`가 필요한지, 왜 `static`은 하나뿐인지, 왜 자바는 값만 전달하는지, 왜 생성자를 하나 만들면 기본 생성자가 사라지는지가 이 장의 "왜"다.

---

## 1. 왜 객체로 나누는가

절차지향 프로그램에서 "채널을 올린다"는 기능은 함수 하나이고, 채널 값은 그 함수와 무관한 어딘가의 변수다. 채널 값을 쓰는 함수가 열 개면 그 열 곳이 전부 그 변수의 규칙(0 이상, 최대 채널 이하)을 알아야 하고, 규칙이 바뀌면 열 곳을 고쳐야 한다.

객체지향은 채널 값과 채널을 올리는 기능을 **TV라는 하나의 단위**에 묶는다. 채널의 규칙은 TV 안에만 있고, 바깥은 "채널을 올려라"고 말할 뿐 값을 직접 만지지 않는다. 규칙이 바뀌면 TV 하나만 고치면 된다.

| 얻는 것 | 어떻게 | 왜 그렇게 되는가 |
|:--------|:-------|:-----------------|
| 관리 용이성 | 데이터와 그 규칙이 한 곳에 있다 | 변경이 그 단위 안에서 끝난다 |
| 신뢰성 | 바깥에서 데이터를 직접 만지지 못하게 한다 | 규칙을 우회할 길이 없다 |
| 재사용성 | 단위째로 가져다 쓰거나 확장한다 | 단위가 스스로 완결되어 있다 |

"실제 세계는 사물로 이루어져 있고 모든 사건은 사물의 상호작용"이라는 객체지향의 표어는 이 설계 방침을 현실에 빗댄 것이다. 중요한 것은 비유가 아니라 **책임을 어디에 둘 것인가**라는 질문이다.

## 2. 클래스와 인스턴스

### 2.1 설계도와 실체

| 용어 | 뜻 | 어디에 있나 |
|:-----|:---|:------------|
| 클래스 | 객체가 어떤 값을 가지고 무엇을 할 수 있는지 정의한 것 | 메서드 영역. 프로그램에 하나 |
| 인스턴스(객체) | 클래스대로 만들어져 실제 값을 가진 것 | 힙. `new`할 때마다 하나씩 |

```java
public class Tv {
    String color;                          // 속성. 인스턴스마다 값을 가진다
    boolean power;
    int channel;

    void power()       { power = !power; } // 기능. 속성을 다룬다
    void channelUp()   { ++channel; }
    void channelDown() { --channel; }
}
```

```
Tv 클래스 (설계도, 메서드 영역)
  color, power, channel  ← 속성
  power(), channelUp()   ← 기능
          │ new Tv()
          ▼
t ──▶ ┌─────────────────┐  힙의
      │ color   = null  │  인스턴스
      │ power   = false │
      │ channel = 0     │
      └─────────────────┘
```

클래스는 "TV에는 채널이 있다"고 말할 뿐 어느 TV의 채널이 몇 번인지는 담지 않는다. 값을 담으려면 그 값이 놓일 메모리가 있어야 하고, 그 메모리를 힙에 잡는 것이 `new`다. `new`가 없으면 아무리 클래스를 잘 만들어도 값을 넣을 자리가 없다. 클래스 하나에서 인스턴스를 얼마든지 만들 수 있고, 각 인스턴스는 자기만의 값을 갖는다. "클래스로부터 인스턴스를 만든다"는 뜻으로 **인스턴스화**라 하고, 어느 클래스에서 나왔는지를 강조할 때 객체 대신 인스턴스라 부른다.

### 2.2 참조 변수로 다룬다

```java
Tv t;              // 1. Tv 인스턴스의 주소를 담을 변수. 아직 인스턴스는 없다
t = new Tv();      // 2. 힙에 인스턴스를 만들고 그 주소를 t에 넣는다
t.channel = 7;     // 3. t가 가리키는 인스턴스의 channel에 쓴다
t.channelDown();   // 4. 그 인스턴스의 메서드를 부른다. channel은 6
```

[Chapter 02](../02-java-variable)에서 참조형 변수에는 주소가 들어 있다고 했다. 인스턴스는 힙에 있고 크기도 제각각이라 변수에 직접 담을 수 없으니, 변수에는 주소만 담고 그 주소를 통해 인스턴스를 다룬다. 인스턴스에 이름이 없는 이유도 이것이다. 이름은 참조 변수에 있고, 인스턴스는 주소로만 찾아진다.

```java
Tv t1 = new Tv();
Tv t2 = new Tv();
t1.channel = 7;
t2.channel;        // 0. 별개의 인스턴스다

Tv t3 = new Tv();
Tv t4 = t3;        // 주소가 복사된다. 인스턴스는 그대로 하나
t3.channel = 7;
t4.channel;        // 7. 같은 인스턴스를 본다
```

```
t3 ──▶ ┌──────────┐
       │ channel 7│
t4 ──▶ └──────────┘   같은 인스턴스
```

`t4 = t3`는 인스턴스를 복사하지 않는다. 주소만 복사되므로 두 변수가 한 인스턴스를 가리키고, 한쪽으로 바꾸면 다른 쪽에서도 보인다. 참조 변수 하나는 한 번에 인스턴스 하나만 가리키지만, 인스턴스 하나를 여러 변수가 가리킬 수는 있다. 아무 변수도 가리키지 않게 된 인스턴스는 더 이상 닿을 수 없으므로 가비지 컬렉터가 회수한다([자동 메모리 관리](../../jvm/memory-management)).

### 2.3 객체 배열

```java
Tv[] tvs = new Tv[3];             // [null, null, null]. 주소를 담을 칸 3개
for (int i = 0; i < tvs.length; i++) {
    tvs[i] = new Tv();            // 인스턴스는 따로 만들어 넣는다
    tvs[i].channel = i + 10;
}
```

```
tvs ──┐
      ▼
    ┌──────┐
    │ [0] ─┼──▶ Tv (ch=10)
    │ [1] ─┼──▶ Tv (ch=11)
    │ [2] ─┼──▶ Tv (ch=12)
    └──────┘
```

[Chapter 05](../05-array)에서 본 참조형 배열 그대로다. `new Tv[3]`은 TV 세 대를 만드는 것이 아니라 TV의 주소를 담을 칸 세 개를 만든다. 칸은 `null`로 시작하고, 인스턴스는 `new Tv()`로 하나씩 만들어 넣어야 한다.

## 3. 변수의 세 종류

```java
class Variables {
    int iv;            // 인스턴스 변수
    static int cv;     // 클래스 변수

    void method() {
        int lv = 0;    // 지역 변수
    }
}
```

| 종류 | 선언 위치 | 어디에 사는가 | 만들어질 때 | 사라질 때 |
|:-----|:----------|:--------------|:------------|:----------|
| 인스턴스 변수 | 클래스 영역 | 힙의 인스턴스 안 | 인스턴스 생성 시 | 인스턴스가 회수될 때 |
| 클래스 변수 (`static`) | 클래스 영역 | 클래스당 하나의 공간 | 클래스가 처음 쓰일 때 | 프로그램 종료 시 |
| 지역 변수 | 메서드, 블록 안 | 호출 스택의 프레임 | 선언문 실행 시 | 블록을 벗어날 때 |

```
┌──────────────┬──────────────────────┐
│ 메서드 영역  │ 클래스, static 변수  │
├──────────────┼──────────────────────┤
│ 힙           │ 인스턴스와 그 변수   │
├──────────────┼──────────────────────┤
│ 호출 스택    │ 프레임, 지역 변수    │
└──────────────┴──────────────────────┘
```

변수의 종류가 셋인 이유는 **사는 곳이 셋**이기 때문이다. 인스턴스 변수는 인스턴스 안에 있으니 인스턴스마다 하나씩이고, 인스턴스와 운명을 같이한다. 지역 변수는 메서드가 호출될 때 만들어지는 스택 프레임 안에 있으니 메서드가 끝나면 사라진다. 클래스 변수는 어디에 있는가. 각 영역이 무엇을 담는지는 [JVM 런타임 데이터 영역 정리](../../../../blog/tech-review/jvm-runtime-data-areas)에서 자세히 본다.

### 3.1 static은 왜 하나뿐인가

```java
public class Card {
    String kind;               // 카드마다 다르다
    int number;

    static int width = 100;    // 모든 카드가 같다
    static int height = 250;
}

Card.width;                    // 100. 인스턴스가 없어도 된다

Card c1 = new Card();
Card c2 = new Card();
c1.width = 50;
c2.width;                      // 50. 같은 공간이다
```

카드의 종류와 숫자는 카드마다 다르지만 카드의 가로세로 크기는 모든 카드가 같다. 같은 값을 인스턴스마다 복사해 두는 것은 낭비이고, 바꿀 때 전부 바꿔야 하는 위험이기도 하다. `static`을 붙이면 그 변수는 인스턴스가 아니라 **클래스에 속한 공간 하나**에 놓인다. 인스턴스가 하나도 없어도 존재하고, 인스턴스가 백 개여도 하나다. `c1.width`와 `c2.width`가 같은 값을 보이는 것은 같은 변수이기 때문이다.

{{< callout type="warning" >}}
클래스 변수는 `Card.width`처럼 **클래스 이름으로** 접근한다. `c1.width`도 동작하지만 읽는 사람은 카드마다 다른 값이라고 오해한다. 이름이 곧 "이 값은 클래스 전체의 것"이라는 안내가 된다.
{{< /callout >}}

클래스 변수가 만들어지는 시점은 정확히는 클래스가 **처음 사용될 때**다. 인스턴스를 만들거나, `static` 메서드를 부르거나, `static` 변수에 접근하는 순간 JVM이 그 클래스를 초기화한다. [Chapter 01](../01-java-intro)에서 본 게으른 로딩과 같은 원리로, 쓰지 않는 클래스의 `static` 변수는 만들어지지도 않는다.

## 4. 메서드

### 4.1 왜 문장을 메서드로 묶는가

```
반환타입 이름(매개변수) {   // 선언부
    // 구현부
    return 반환값;
}
```

```java
int add(int x, int y) {
    return x + y;
}

void printGugudan(int dan) {
    if (dan < 2 || dan > 9) return;      // 반환값이 없어도 return으로 끝낼 수 있다
    for (int i = 1; i <= 9; i++) {
        System.out.printf("%d * %d = %d%n", dan, i, dan * i);
    }
}
```

메서드는 문장 여러 개에 이름을 붙인 것이다. 얻는 것은 세 가지다. 같은 일을 여러 곳에서 **다시 쓸** 수 있고, 고칠 때 **한 곳만** 고치면 되고, 큰 작업을 이름 붙은 작은 단위로 나누어 **읽을** 수 있다. 세 번째가 가장 중요하다. 메서드를 부르는 쪽은 선언부만 알면 된다. 무엇을 받아 무엇을 돌려주는지는 알아야 하지만 어떻게 하는지는 몰라도 된다. 이 "안을 몰라도 되는" 성질 위에 다음 장의 캡슐화가 세워진다.

| 구성 | 뜻 | 규칙 |
|:-----|:---|:-----|
| 반환 타입 | 돌려주는 값의 타입 | 없으면 `void` |
| 이름 | 메서드의 이름 | 변수 규칙과 같다. 동사로 시작하는 것이 관례 |
| 매개변수 | 받을 값의 타입과 이름 | 여러 개면 쉼표로 |

반환값은 **하나**다. 메서드가 끝날 때 JVM은 값 하나를 호출한 쪽의 스택에 올려 놓고 프레임을 걷어 내는데, 그 자리가 하나이기 때문이다. 여러 값을 돌려주고 싶으면 배열이나 객체에 담아 하나로 만든다. Java 16의 `record`가 이런 용도의 작은 묶음을 한 줄로 정의해 준다.

### 4.2 인자와 매개변수

```java
long add(int a, long b) { return a + b; }

add(3, 5L);    // 된다
add(3, 5);     // 된다. int 5가 long으로 자동 변환된다
add(3L, 5);    // 안 된다. long 3L을 int a에 넣을 수 없다
```

호출할 때 넘기는 값이 **인자**, 선언부에서 받는 변수가 **매개변수**다. 인자의 개수와 순서가 매개변수와 같아야 하고, 타입은 같거나 [Chapter 03](../03-java-operator)의 자동 형변환으로 맞출 수 있어야 한다. 큰 타입에서 작은 타입으로는 자동 변환이 없으므로 세 번째 호출은 실패한다.

### 4.3 호출 스택: 메서드는 프레임 위에서 산다

```java
static void main(String[] args) { first(); }
static void first()              { second(); }
static void second()             { /* ... */ }
```

```
1) [main]
2) [main, first]
3) [main, first, second]
4) [main, first]
5) [main]
6) []
```

메서드가 호출되면 그 메서드의 지역 변수와 매개변수를 담을 **프레임**이 호출 스택에 쌓이고, 메서드가 끝나면 프레임이 걷히면서 바로 아래 프레임, 즉 호출한 메서드로 돌아간다. 맨 위 프레임이 지금 실행 중인 메서드다. 2장에서 지역 변수가 메서드를 벗어나면 사라진다고 한 것은 이 프레임이 걷히기 때문이다.

스택은 크기가 정해져 있다. 메서드가 자기 자신을 끝없이 부르면 프레임이 쌓이다 한계에 닿아 `StackOverflowError`가 난다. 재귀 호출에 종료 조건이 필요한 이유가 프레임에 있다.

### 4.4 자바는 값만 전달한다

```java
static void change(int x) { x = 100; }

int x = 10;
change(x);     // change의 x는 10의 복사본. 그것을 100으로 바꿔도
x;             // 10
```

```java
class Data { int x; }
static void change(Data d) { d.x = 100; }

Data d = new Data();
d.x = 10;
change(d);     // change의 d는 주소의 복사본. 같은 인스턴스를 가리킨다
d.x;           // 100
```

```
main의 d  ──(주소 복사)──▶  change의 d
     │                            │
     └──▶  ┌─────────┐ ◀─────────┘
           │ x: 100  │
           └─────────┘
```

두 결과가 달라 보이지만 규칙은 하나다. 자바는 언제나 **변수에 든 값을 복사해서** 넘긴다. 기본형 변수에는 값이 들어 있으니 값이 복사되고, 참조형 변수에는 주소가 들어 있으니 주소가 복사된다. 주소의 복사본으로 인스턴스를 고치면 원본 변수도 같은 인스턴스를 보고 있으니 바뀐 것이 보일 뿐이다.

이 규칙의 결과를 하나 더 보면 "참조를 전달한다"와 어떻게 다른지 분명해진다.

```java
static void replace(Data d) { d = new Data(); }   // 복사본 d가 다른 인스턴스를 가리키게 됐을 뿐

Data d = new Data();
replace(d);
// main의 d는 여전히 원래 인스턴스를 가리킨다
```

매개변수 `d`에 새 인스턴스를 넣어도 호출한 쪽의 `d`는 바뀌지 않는다. 복사된 주소를 다른 주소로 덮어쓴 것이지 원본 변수를 만진 것이 아니기 때문이다. 같은 이유로 두 참조를 맞바꾸는 `swap` 메서드는 자바로 쓸 수 없다. 배열도 참조형이므로 메서드 안에서 요소를 바꾸면 원본에 반영되지만, 배열 변수 자체를 새 배열로 바꾸는 것은 호출한 쪽에 영향을 주지 않는다.

## 5. 오버로딩

```java
int  add(int a, int b)          { return a + b; }
long add(long a, long b)        { return a + b; }
int  add(int a, int b, int c)   { return a + b + c; }
```

같은 이름의 메서드를 매개변수만 다르게 여러 개 두는 것이 **오버로딩**이다. 정수를 더하든 실수를 더하든 "더한다"는 뜻은 같으니 이름도 같은 것이 자연스럽고, 부르는 쪽은 타입마다 다른 이름을 외울 필요가 없다.

| 항목 | 오버로딩 구분에 쓰이나 |
|:-----|:-----------------------|
| 메서드 이름 | 같아야 한다 |
| 매개변수의 개수, 타입, 순서 | 하나라도 다르면 구분된다 |
| 매개변수의 이름 | 관계없다 |
| 반환 타입 | 관계없다 |

```java
int  add(int a, int b) { return a + b; }
long add(int a, int b) { return a + b; }   // 컴파일 오류. 매개변수가 같다
```

반환 타입으로는 구분하지 못한다. 컴파일러는 **호출하는 문장**을 보고 어느 메서드인지 정하는데, `add(1, 2);`처럼 결과를 쓰지 않는 호출에서는 반환 타입을 알 단서가 전혀 없기 때문이다. 매개변수는 호출 문장에 항상 드러나므로 구분의 기준이 될 수 있다.

### 5.1 어느 메서드가 골라지는가

인자에 딱 맞는 메서드가 없으면 컴파일러는 정해진 순서로 후보를 찾는다.

| 단계 | 허용하는 변환 | 예 |
|:-----|:--------------|:---|
| 1 | 없음, 또는 자동 형변환 | `add(int, long)`에 `add(3, 5)` |
| 2 | 1단계 실패 시, 박싱·언박싱까지 | `add(Integer, Integer)`에 `add(3, 5)` |
| 3 | 2단계 실패 시, 가변 인자까지 | `add(int...)`에 `add(3, 5)` |

앞 단계에서 후보가 나오면 뒤 단계는 보지 않는다. 그래서 `method(int, int)`와 `method(int...)`가 함께 있을 때 `method(1, 2)`는 모호하지 않고 앞의 것이 골라진다. 고정 인자 메서드가 1단계에서 이미 잡히기 때문이다. 모호함은 같은 단계 안에서 어느 쪽이 더 구체적인지 가릴 수 없을 때 생긴다.

```java
void method(int... args) { }
void method(Integer... args) { }

method(1, 2);   // 컴파일 오류. 둘 다 3단계이고 int와 Integer는 어느 쪽도 더 구체적이지 않다
```

### 5.2 가변 인자

```java
public String concat(String... args) {   // args는 String[]이다
    return String.join("", args);
}

concat();                 // 0개
concat("a");
concat("a", "b", "c");    // 컴파일러가 new String[]{"a", "b", "c"}로 바꾼다
```

5장에서 본 대로 가변 인자는 배열이다. 컴파일러가 호출 문장의 인자들을 배열로 묶어 넘기고, 메서드 안에서는 그냥 배열이다. 가변 인자가 **마지막 매개변수**여야 하는 이유는 여기에 있다. `(String... args, int n)`처럼 뒤에 다른 매개변수가 오면, 인자 목록에서 어디까지가 배열이고 어디부터가 `n`인지 정할 수 없다.

## 6. 생성자

### 6.1 인스턴스가 태어나는 세 단계

```java
class Card {
    String kind;
    int number;

    Card() { }                                // 매개변수 없는 생성자

    Card(String kind, int number) {           // 값을 받아 초기화하는 생성자
        this.kind = kind;
        this.number = number;
    }
}

Card c = new Card("Heart", 7);
```

`new Card("Heart", 7)`은 세 단계로 실행된다. 먼저 `new`가 힙에 `Card` 크기의 메모리를 잡고 [Chapter 02](../02-java-variable)에서 본 대로 전부 0으로 채운다. 그다음 인자에 맞는 **생성자**가 호출되어 그 메모리에 값을 채운다. 마지막으로 완성된 인스턴스의 주소가 `new` 식의 값으로 돌아와 `c`에 들어간다.

생성자는 인스턴스를 만드는 것이 아니라 **이미 만들어진 메모리를 초기화**하는 메서드다. 생성자에 반환 타입이 없는 이유가 이것이다. 돌려줄 것이 없다. 주소를 돌려주는 것은 `new` 식이다. 이름이 클래스 이름과 같아야 하는 것은 "이 클래스의 인스턴스를 초기화하는 것"임을 이름으로 보이기 위한 약속이다.

### 6.2 기본 생성자는 왜 사라지는가

```java
class Card {           // 생성자를 하나도 쓰지 않으면
    String kind;       // 컴파일러가 Card() { } 를 넣어 준다
}
new Card();            // 된다

class Card {
    Card(String kind, int number) { ... }   // 생성자를 하나라도 쓰면
}
new Card();            // 컴파일 오류. 기본 생성자는 만들어지지 않는다
```

인스턴스를 만들려면 생성자가 반드시 하나는 있어야 한다. 그래서 생성자가 없는 클래스에는 컴파일러가 매개변수 없는 **기본 생성자**를 넣어 준다. 그런데 개발자가 생성자를 하나라도 쓰면 컴파일러는 물러선다. 이유는 설계 의도를 지키기 위해서다. `Card(String kind, int number)`를 만들었다는 것은 "카드는 종류와 숫자 없이 만들어질 수 없다"는 선언이다. 그런데도 컴파일러가 `Card()`를 넣어 주면 그 선언이 무력해진다. 두 방식이 모두 필요하면 두 생성자를 모두 쓰라는 것이 자바의 입장이다.

### 6.3 this: 인스턴스 자신

```java
class Car {
    String color;

    Car(String color) {
        this.color = color;   // this.color는 인스턴스 변수, color는 매개변수
    }
}
```

매개변수 이름과 인스턴스 변수 이름이 같으면 가까운 쪽인 매개변수가 우선한다. `this`는 "지금 이 메서드가 실행되고 있는 인스턴스"를 가리키는 참조라서, `this.color`라고 쓰면 인스턴스 변수를 지목할 수 있다.

`this`가 어디서 오는지 알면 `static` 메서드에서 `this`를 쓸 수 없는 이유가 보인다. 인스턴스 메서드를 `t.channelUp()`처럼 부르면 컴파일러는 `t`의 주소를 **숨겨진 첫 번째 인자**로 함께 넘긴다. 메서드 안의 `this`는 그 숨겨진 인자다. `static` 메서드는 `Card.width`처럼 인스턴스 없이 불리므로 넘겨줄 주소가 없고, 따라서 `this`도 없다. `static` 메서드가 인스턴스 변수를 쓸 수 없는 것도 같은 이유다.

### 6.4 this(): 생성자가 생성자를 부른다

```java
class Car {
    String color;
    String gearType;
    int door;

    Car()                              { this("white", "auto", 4); }
    Car(String color, String gearType) { this(color, gearType, 4); }
    Car(String color, String gearType, int door) {
        this.color = color;
        this.gearType = gearType;
        this.door = door;
    }
}
```

생성자가 여럿이면 초기화 코드가 중복되기 쉽다. `this(...)`로 같은 클래스의 다른 생성자를 부르면 초기화를 한 곳에 모으고 나머지는 기본값만 채워 넘기는 구조가 된다. 위에서는 인자 세 개짜리 생성자만 실제로 값을 채우고, 나머지 둘은 그리로 위임한다.

`this(...)`는 생성자의 **첫 문장**이어야 한다는 규칙이 있다. 인스턴스는 하나의 생성자 사슬로 처음부터 끝까지 초기화되어야 하는데, `this()` 앞에서 인스턴스 변수를 건드리면 뒤이어 실행되는 생성자가 그 값을 덮어쓰거나, 반쯤 초기화된 인스턴스를 다른 코드가 볼 수 있기 때문이다.

{{< callout type="info" >}}
Java 25부터는 이 규칙이 조금 풀렸다(JEP 513). `this(...)`나 `super(...)` 앞에 **생성 중인 인스턴스를 참조하지 않는** 문장은 둘 수 있다. 인자를 검증해 예외를 던지거나 넘길 값을 미리 계산하는 용도다. 인스턴스를 반쯤 만든 채로 노출하지 않는다는 원래 의도는 그대로다.
{{< /callout >}}

```java
Car(Car other) {                                   // 복사 생성자
    this(other.color, other.gearType, other.door);
}
```

다른 인스턴스의 값을 그대로 옮겨 새 인스턴스를 만드는 생성자를 복사 생성자라 한다. 2.2절에서 본 `t4 = t3`가 주소를 복사하는 것과 달리, 이쪽은 값이 같은 **별개의 인스턴스**를 만든다.

## 7. 초기화

### 7.1 무엇이 자동으로 초기화되는가

| 변수 | 초기화 | 왜 |
|:-----|:-------|:---|
| 지역 변수 | 쓰기 전에 반드시 직접 | 스택 프레임은 0으로 채워지지 않는다 (2장) |
| 인스턴스 변수, 클래스 변수 | 안 해도 기본값이 들어 있다 | 힙과 클래스 공간은 만들 때 0으로 채워진다 |

| 타입 | 기본값 |
|:-----|:-------|
| `boolean` | `false` |
| `char` | `'\u0000'` (널 문자) |
| `byte`, `short`, `int` | `0` |
| `long` | `0L` |
| `float`, `double` | `0.0` |
| 참조형 | `null` |

### 7.2 멤버 변수를 초기화하는 세 가지 방법

```java
class InitBlock {
    static int cv = 10;                 // 1. 명시적 초기화: 선언과 함께
    int iv = 20;

    static { cv = cv * 2; }             // 3. 클래스 초기화 블록: 클래스가 처음 쓰일 때 한 번
    { iv = iv * 2; }                    //    인스턴스 초기화 블록: 인스턴스를 만들 때마다

    InitBlock() { iv = iv + 1; }        // 2. 생성자
}
```

값 하나를 넣는 것으로 끝나면 선언에 바로 적는 명시적 초기화가 가장 읽기 쉽다. 인자에 따라 달라지면 생성자에서 한다. 초기화 블록은 두 경우에 쓴다. 클래스 변수를 한 줄로 채울 수 없어 계산이나 반복이 필요할 때 `static` 블록을 쓰고, 모든 생성자가 공통으로 해야 할 일이 있을 때 인스턴스 블록을 쓴다.

```java
class Car {
    static int count = 0;
    String color;

    { count++; }                        // 어느 생성자로 만들어도 한 번씩 센다

    Car()             { this("white"); }
    Car(String color) { this.color = color; }
}
```

인스턴스 초기화 블록은 **모든 생성자보다 먼저** 실행된다. 그래서 생성자마다 `count++`를 적지 않아도 된다. 다만 위 예처럼 생성자들이 `this()`로 한 곳에 모이는 구조라면 그 한 곳에 적어도 되므로, 블록은 정말 공통 처리가 필요할 때만 쓴다.

### 7.3 순서: 기본값, 적힌 순서, 생성자

```
클래스 변수 (처음 쓰일 때 한 번)
  기본값
  → 명시적 초기화, static 블록
    (적힌 순서대로)

인스턴스 변수 (만들 때마다)
  기본값
  → 명시적 초기화, 인스턴스 블록
    (적힌 순서대로)
  → 생성자
```

```java
class InitTest {
    static int cv = 1;
    int iv = 1;

    static { cv = 2; }
    { iv = 2; }

    InitTest() { iv = 3; }
}
```

```
[클래스가 처음 쓰일 때]
1) cv = 0    기본값
2) cv = 1    명시적 초기화
3) cv = 2    static 블록

[new InitTest() 마다]
4) iv = 0    기본값
5) iv = 1    명시적 초기화
6) iv = 2    인스턴스 블록
7) iv = 3    생성자

결과: cv = 2, iv = 3
```

기본값이 맨 앞인 이유는 그것이 초기화가 아니라 메모리 할당의 결과이기 때문이다. `new`가 0으로 채운 뒤에야 코드가 실행된다. 명시적 초기화와 초기화 블록은 따로 우선순위가 있는 것이 아니라 **소스에 적힌 순서대로** 실행된다. 위 예에서 블록이 나중인 것은 블록이 아래에 적혀 있기 때문이고, 순서를 바꿔 적으면 결과도 바뀐다. 생성자가 마지막인 것은 인자를 받아 하는 초기화가 가장 구체적이라 나머지를 덮어쓸 수 있어야 하기 때문이다.

## 8. 요약

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 객체지향 | 데이터와 기능을 책임 단위로 묶는다 | 변경이 그 단위 안에서 끝난다 |
| 클래스, 인스턴스 | 설계도와 힙의 실체. `new`로 만든다 | 값을 담을 메모리는 `new`가 잡는다 |
| 참조 변수 | 인스턴스의 주소를 담는다 | 인스턴스는 크기가 제각각이라 변수에 못 담는다 |
| 인스턴스 변수 | 인스턴스마다 하나 | 인스턴스 안에 산다 |
| 클래스 변수 | 클래스에 하나. 클래스 이름으로 접근 | 인스턴스가 아닌 클래스 공간에 산다 |
| 지역 변수 | 메서드가 끝나면 사라진다 | 스택 프레임과 함께 걷힌다 |
| 메서드 | 문장 묶음. 반환값은 하나 | 안을 몰라도 쓸 수 있다. 반환 자리가 하나다 |
| 값 전달 | 언제나 변수의 값을 복사한다 | 참조형은 그 값이 주소라 인스턴스가 공유된다 |
| 오버로딩 | 이름 같고 매개변수 다름. 반환 타입은 무관 | 호출 문장에는 매개변수만 드러난다 |
| 생성자 | 만들어진 메모리를 초기화. 반환 타입 없음 | 주소는 `new` 식이 돌려준다 |
| 기본 생성자 | 생성자를 쓰면 사라진다 | 설계 의도를 컴파일러가 무력화하지 않는다 |
| `this` | 숨겨진 첫 인자. `static`에는 없다 | 인스턴스 없이 불리면 넘길 주소가 없다 |
| 초기화 순서 | 기본값 → 적힌 순서 → 생성자 | 기본값은 할당의 결과, 생성자가 가장 구체적이다 |
