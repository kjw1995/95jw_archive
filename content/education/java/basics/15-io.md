이 장의 스트림은 [Chapter 14](../14-lambda-stream)의 스트림과 이름만 같다. 14장의 스트림이 컬렉션 위를 흐르는 연산 파이프라인이라면, 여기의 스트림은 프로그램과 파일, 콘솔, 네트워크 사이를 흐르는 **바이트의 통로**다. 앞 장들이 이 장으로 넘긴 것들이 있다. `try-with-resources`로 닫아야 하는 자원이 정확히 무엇인가([Chapter 08](../08-exception-handling)), 문자와 바이트 사이의 인코딩은 어디서 일어나는가([Chapter 02](../02-java-variable)), `Properties.load(InputStream)`은 왜 ISO 8859-1로 읽는가([Chapter 11](../11-collections-framework)), 14장의 `Files.lines()`는 왜 닫아야 하는가. 규칙은 세 원리에서 나온다. 첫째, **입출력 스트림은 바이트의 흐름이자 운영체제의 자원이다.** 단방향이고 순서대로 흐르며 닫아야 한다. 둘째, **바이트와 문자는 다른 층이고, 그 사이가 인코딩이다.** 바이트 스트림과 문자 스트림이 따로 있는 이유이자 한글이 깨지는 모든 경우의 원인이다. 셋째, **기능은 상속이 아니라 포장으로 더한다.** 보조 스트림이 그것이고, 버퍼 하나가 복사 속도를 300배 바꾸는 이유가 운영체제 호출 횟수에 있다. 마지막 절의 직렬화는 이 원리들 위에서 왜 요즘 피하는 기술이 됐는지를 본다.

## 1. 스트림: 바이트의 흐름이자 운영체제의 자원

### 1.1 단방향, 순서대로

```
┌──────────┐  InputStream   ┌──────────┐
│          │ ◀───────────── │          │
│ 프로그램 │                │ 파일 등  │
│          │ ─────────────▶ │          │
└──────────┘  OutputStream  └──────────┘
```

프로그램이 파일, 콘솔, 네트워크, 다른 프로세스와 데이터를 주고받는 방법은 대상마다 다르다. 자바는 그 차이를 **스트림**이라는 하나의 그림으로 덮는다. 데이터가 한 방향으로, 보낸 순서대로, 건너뜀 없이 흐르는 통로다. 읽기와 쓰기를 둘 다 하려면 통로가 둘 필요하고, 중간을 건너뛰려면 앞을 다 읽어 버려야 한다. 이 제약은 불편이 아니라 추상화의 대가다. 파일이든 소켓이든 "다음 바이트를 다오"라는 하나의 질문으로 다룰 수 있게 되었고, [Chapter 16](../16-networking)의 소켓이 파일과 같은 코드로 읽히는 이유가 이것이다.

```
          입출력 스트림
     ┌────────┴────────┐
  바이트 기반        문자 기반
 InputStream        Reader
 OutputStream       Writer
```

스트림은 무엇을 나르느냐로 둘로 나뉜다. 바이트 스트림(`InputStream`, `OutputStream`)은 바이트를 나르고, 문자 스트림(`Reader`, `Writer`)은 문자를 나른다. 이미지나 동영상 같은 이진 데이터는 바이트 스트림이고, 텍스트는 문자 스트림인데, 둘이 왜 따로 있어야 하는지는 4절의 인코딩에서 분명해진다.

### 1.2 왜 닫아야 하나

파일 스트림을 열면 운영체제가 **파일 디스크립터**를 하나 내준다. 프로세스가 동시에 열 수 있는 디스크립터 수에는 한도가 있어서(리눅스 기본 1024개), 닫지 않은 스트림이 쌓이면 어느 순간 파일을 열 수 없게 된다. 닫아야 하는 이유가 하나 더 있다. 3절에서 볼 버퍼가 있는 스트림은 `close()`가 마지막 버퍼를 비우므로, 닫지 않으면 데이터 끝부분이 파일에 도달하지 못한다.

```java
try (FileInputStream fis = new FileInputStream("input.txt")) {   // 8장의 try-with-resources
    int b;
    while ((b = fis.read()) != -1) {
        System.out.print((char) b);        // 4절에서 보듯 한글이면 깨진다
    }
}                                          // 정상이든 예외든 close()
```

8장에서 `try-with-resources`가 닫는 일을 문법에 맡긴다고 했는데, 그 문법이 만들어진 대상이 바로 스트림이다. 예외가 나도 닫히고, 여러 개를 열면 연 순서의 역순으로 닫히며, `close()`의 예외는 억제된 예외로 붙는다. `ByteArrayInputStream`처럼 메모리 위의 스트림은 운영체제 자원이 없어 닫지 않아도 되고, `System.in`과 `System.out`은 JVM이 관리하므로 닫지 않는다.

## 2. 바이트 스트림

### 2.1 read()는 왜 int를 돌려주나

| `InputStream` | `OutputStream` | 뜻 |
|:--------------|:---------------|:---|
| `int read()` | `void write(int b)` | 한 바이트. 읽기는 끝이면 `-1` |
| `int read(byte[] b)` | `void write(byte[] b)` | 배열 단위. 읽은 개수를 돌려준다 |
| `int read(byte[] b, int off, int len)` | `void write(byte[] b, int off, int len)` | 배열의 일부 |
| `long skip(long n)`, `int available()` | `void flush()` | 건너뛰기, 대기 없이 읽을 수 있는 양 / 버퍼 비우기 |
| `void close()` | `void close()` | 자원 반환 |
| `long transferTo(OutputStream)` (Java 9) | | 전부 옮기기 |

`read()`는 한 바이트를 읽는데 반환 타입이 `byte`가 아니라 `int`다. 바이트의 256가지 값을 전부 데이터로 써야 하는데 "끝"도 알려야 하기 때문이다. `byte`로 돌려주면 `-1`이 데이터 `0xFF`와 구별되지 않는다. 그래서 `0`부터 `255`까지를 `int`로 돌려주고 `-1`은 끝의 신호로만 쓴다. `0xFF`를 읽으면 `255`가 오고, 그것을 `(byte)`로 바꾸면 그제야 `-1`이 된다. 반복문의 조건이 늘 `!= -1`인 이유다.

`read()`는 데이터가 올 때까지 **스레드를 세운다.** 파일에서는 잠깐이지만 네트워크에서는 상대가 보낼 때까지 무한정일 수 있다. [Chapter 13](../13-thread)에서 스레드 하나가 대기하는 동안 아무것도 못 한다고 한 것이 이 상황이고, 대기 없이 준비된 데이터만 처리하는 NIO가 그래서 생겼다. 이 장은 블로킹 스트림만 다룬다.

```java
try (FileInputStream in = new FileInputStream("src.bin");
     FileOutputStream out = new FileOutputStream("dst.bin")) {
    int b;
    while ((b = in.read()) != -1) out.write(b);   // 동작은 하지만 3절에서 보듯 아주 느리다
}
new FileOutputStream("log.txt", true);             // 이어 쓰기

byte[] src = {0, 1, 2};
ByteArrayInputStream mem = new ByteArrayInputStream(src);      // 메모리가 대상
ByteArrayOutputStream collect = new ByteArrayOutputStream();
mem.transferTo(collect);
byte[] copied = collect.toByteArray();
```

### 2.2 DataInputStream: 기본형을 바이트로

```java
try (DataOutputStream dos = new DataOutputStream(new FileOutputStream("data.bin"))) {
    dos.writeInt(100);          // 4바이트  00 00 00 64
    dos.writeFloat(3.14f);      // 4바이트  40 48 f5 c3
    dos.writeBoolean(true);     // 1바이트  01
    dos.writeUTF("Hello");      // 2바이트 길이 + 5바이트  00 05 48 65 6c 6c 6f
}                               // 파일 크기 16바이트

try (DataInputStream dis = new DataInputStream(new FileInputStream("data.bin"))) {
    int i = dis.readInt();          // 100
    float f = dis.readFloat();      // 3.14
    boolean b = dis.readBoolean();  // true
    String s = dis.readUTF();       // "Hello"
    dis.readInt();                  // EOFException
}
```

바이트 스트림은 바이트만 안다. `int` 하나를 쓰려면 누군가 4바이트로 쪼개야 하고, 그 일을 `DataOutputStream`이 한다. 2장에서 본 `int`의 4바이트를 큰 자리부터(빅엔디안) 차례로 내보내고, 문자열은 길이 2바이트 뒤에 UTF-8 비슷한 인코딩(수정 UTF-8, 65,535바이트 한도)으로 적는다. 파일에는 타입 정보가 없다. 그래서 **쓴 순서와 타입 그대로** 읽어야 한다. 위 파일을 `readFloat()`부터 읽으면 `00 00 00 64`가 `float`로 해석되어 `1.4E-43`이 나오고, 이어지는 값도 전부 어긋난다. 오류가 아니라 잘못된 값이 조용히 나온다는 점이 이 형식의 위험이고, 6절의 직렬화가 타입 정보를 함께 적는 이유이기도 하다.

### 2.3 PrintStream: System.out의 정체

```java
System.out.printf("이름: %s, 점수: %.1f%n", name, score);
```

| 서식 | 뜻 | `65`의 결과 |
|:-----|:---|:-----------|
| `%d`, `%x`, `%c`, `%s` | 10진, 16진, 문자, 문자열 | `65`, `41`, `A`, `65` |
| `%5d`, `%-5d`, `%05d` | 너비 5, 왼쪽 정렬, 0 채움 | `   65`, `65   `, `00065` |
| `%8.2f` | 너비 8, 소수 둘째 자리 | `   65.00` |
| `%n` | 플랫폼의 줄바꿈 | Windows는 `\r\n` |

`System.out`은 `PrintStream`이다. `print`, `println`, `printf`로 무엇이든 문자열로 바꿔 내보내는 편의 스트림인데, 다른 스트림과 다른 점이 하나 있다. **`IOException`을 던지지 않는다.** 출력에 실패하면 예외 대신 내부 플래그를 세우고, `checkError()`로만 알 수 있다. 콘솔 출력 한 줄마다 `try-catch`를 강요하지 않으려는 결정이고, 그 대가로 `System.out`이 막혀도 프로그램은 모른다.

## 3. 보조 스트림: 기능은 포장으로 더한다

### 3.1 데코레이터

```
DataInputStream        타입 단위 읽기
 └ BufferedInputStream 버퍼링
    └ FileInputStream  파일 접근
```

```java
DataInputStream dis = new DataInputStream(
    new BufferedInputStream(
        new FileInputStream("data.bin")));
```

파일을 버퍼링해서 타입 단위로 읽고 싶다. 상속으로 풀면 `BufferedFileInputStream`, `DataBufferedFileInputStream`처럼 대상과 기능의 모든 조합마다 클래스가 필요하고, 대상이 셋에 기능이 셋이면 클래스는 곱으로 는다. 자바 I/O는 [Chapter 07](../07-oop-advanced)의 "포함이 기본"을 택했다. 기능마다 클래스를 하나씩 만들되 그 클래스가 **다른 스트림을 안에 품고**, 자기 일을 한 뒤 나머지는 품은 스트림에 넘긴다. 이렇게 겹겹이 감싸는 것을 데코레이터 패턴이라 하고, 감싸는 쪽을 보조 스트림이라 부른다. 보조 스트림은 스스로 파일을 열 수 없다. 대상은 언제나 가장 안쪽의 기반 스트림이다. 바깥 스트림을 닫으면 안쪽까지 차례로 닫히므로 `try-with-resources`에는 바깥 것 하나만 두면 된다.

### 3.2 버퍼링: 시스템 콜을 줄인다

```
버퍼 없음: read()마다 시스템 콜
  프로그램 ─▶ OS ─▶ 디스크   × 2천만 번

버퍼 있음: 8KB마다 시스템 콜
  프로그램 ─▶ [8KB 버퍼] ─▶ OS
                            × 2,560번
```

`FileInputStream.read()`는 부를 때마다 운영체제에 읽기를 요청한다. 운영체제 호출(시스템 콜)은 사용자 모드에서 커널 모드로 넘어갔다 오는 일이라 메서드 호출보다 수천 배 비싸다. `BufferedInputStream`은 안에 8KB 배열을 두고, 첫 `read()`에서 8KB를 한꺼번에 가져온 뒤 그다음 8,191번은 배열에서 꺼내 준다. 20MB 파일을 한 바이트씩 복사해 보면 차이가 얼마나 큰지 드러난다.

| 방법 | 20MB 복사 |
|:-----|----------:|
| `read()` 한 바이트씩, 버퍼 없음 | 약 120초 |
| `read()` 한 바이트씩, `Buffered` 포장 | 약 0.45초 |
| `read(byte[8192])` 배열 단위 | 약 0.04초 |
| `Files.copy()` | 약 0.01초 |

버퍼 없이 한 바이트씩 읽고 쓰면 시스템 콜이 4천만 번이고, 필자의 PC에서 2분이 걸렸다. 버퍼를 씌우기만 해도 300배 가까이 빨라지고, 처음부터 배열로 읽으면 다시 10배 빨라진다. 배열로 읽으면 버퍼가 필요 없다. 이미 프로그램이 큰 단위로 읽고 있기 때문이다. 버퍼 스트림이 이득을 주는 것은 한 바이트씩, 한 줄씩 읽는 **코드의 편의**를 유지하면서 시스템 콜만 줄이고 싶을 때다.

```java
BufferedWriter bw = new BufferedWriter(new FileWriter("out.txt"));
bw.write("data");                     // 아직 파일 크기는 0
bw.close();                           // 이제 4바이트. close()가 flush()를 한다
```

쓰기 버퍼는 반대 방향의 함정이 있다. 버퍼가 찰 때까지 파일에는 아무것도 가지 않는다. `close()`가 남은 것을 내보내므로 닫기만 하면 되지만, 닫기 전에 프로세스가 죽으면 마지막 조각은 사라진다. 로그처럼 즉시 남아야 하는 데이터는 `flush()`를 직접 부른다.

## 4. 문자 스트림: 바이트와 문자 사이의 인코딩

### 4.1 왜 따로 있나

```
"안녕" ──인코딩──▶ ec 95 88 eb 85 95
 문자 2개 ◀──디코딩── 바이트 6개
            (UTF-8 규칙)
```

| `"안녕".getBytes(...)` | 바이트 수 |
|:----------------------|---------:|
| UTF-8 | 6 |
| UTF-16 | 6 (순서 표시 2 + 4) |
| MS949 (Windows 한글) | 4 |

2장에서 문자 집합은 글자에 번호를 매기는 것이고 인코딩은 그 번호를 바이트로 적는 규칙이라고 했다. 같은 두 글자가 규칙에 따라 4바이트도 6바이트도 되니, 파일의 바이트를 문자로 되돌리려면 **어느 규칙으로 적었는지** 알아야 한다. 1.2절의 코드처럼 바이트를 하나씩 읽어 `(char)`로 바꾸면 `ec`, `95`, `88`이 각각 한 글자로 해석되어 `ì` 같은 라틴 문자와 제어 문자가 여섯 개 나온다. UTF-8 파일을 MS949로 열면 `�븞�뀞`이 된다. 한글이 깨지는 경우는 전부 이 하나의 원인, **적은 규칙과 읽는 규칙이 다른 것**으로 설명된다.

문자 스트림은 이 변환을 안에서 맡는다. `Reader`는 바이트를 읽어 문자로 디코딩해 주고, `Writer`는 문자를 받아 바이트로 인코딩해 내보낸다. 그래서 문자 스트림에는 반드시 문자셋이 있고, 지정하지 않으면 기본값이 쓰인다.

### 4.2 기본 문자셋: Java 18부터 UTF-8

```java
Charset.defaultCharset();                    // UTF-8. Windows에서도
System.getProperty("native.encoding");       // MS949. 운영체제의 설정
System.getProperty("stdout.encoding");       // MS949. 콘솔의 설정

new FileReader("input.txt");                 // Java 18+: UTF-8로 읽는다
new FileReader("input.txt", StandardCharsets.UTF_8);   // Java 11+. 명시하는 편이 낫다
```

오래된 책과 글은 "`FileReader`는 운영체제 기본 인코딩을 쓰므로 Windows에서는 MS949"라고 적는데, 지금은 틀린 말이다. **Java 18(JEP 400)부터 기본 문자셋은 운영체제와 무관하게 UTF-8**이다. 그 전에는 같은 코드가 Windows에서는 MS949로, 리눅스에서는 UTF-8로 파일을 써서 서로 읽지 못하는 일이 흔했고, 그것이 기본값을 고정한 이유다. 운영체제의 설정은 `native.encoding`으로 따로 알 수 있다.

콘솔은 예외다. 위의 세 번째 줄처럼 `stdout.encoding`은 여전히 콘솔의 문자셋이라, Windows 명령 프롬프트에서 한글이 깨지는 것은 파일 인코딩이 아니라 **콘솔 인코딩** 문제다. `java -Dstdout.encoding=UTF-8`로 바꾸거나 콘솔의 코드 페이지를 맞춘다. 기본값이 UTF-8이 되었어도 파일을 열 때 문자셋을 적는 습관은 남겨 둘 만하다. 코드를 읽는 사람에게 의도가 보이고, 11장의 `Properties.load(InputStream)`처럼 자기만의 규칙(ISO 8859-1)을 가진 API도 아직 있기 때문이다.

### 4.3 Reader와 Writer

| 바이트 스트림 | 문자 스트림 | 대상 |
|:-------------|:-----------|:-----|
| `FileInputStream` / `FileOutputStream` | `FileReader` / `FileWriter` | 파일 |
| `ByteArrayInputStream` / `ByteArrayOutputStream` | `CharArrayReader` / `CharArrayWriter`, `StringReader` / `StringWriter` | 메모리 |
| `BufferedInputStream` / `BufferedOutputStream` | `BufferedReader` / `BufferedWriter` | 버퍼링 |
| `PrintStream` | `PrintWriter` | 서식 출력 |
| | `InputStreamReader` / `OutputStreamWriter` | 바이트와 문자를 잇는 다리 |

`Reader`와 `Writer`의 메서드는 `byte[]` 자리에 `char[]`가 온 것 말고는 바이트 스트림과 같다. 문자 쪽에만 있는 것이 둘이다. `InputStreamReader`와 `OutputStreamWriter`는 바이트 스트림에 문자셋을 붙여 문자 스트림으로 바꾸는 **다리**다. `FileReader`는 사실 `FileInputStream`에 이 다리를 씌운 것이고, 콘솔이나 소켓처럼 바이트 스트림만 주는 대상을 문자로 읽을 때 직접 쓴다. `BufferedReader`의 `readLine()`은 줄 단위 읽기를 준다. 줄 끝의 `\n`이나 `\r\n`은 잘라 내고 돌려주며, 끝이면 `null`이다.

```java
BufferedReader console = new BufferedReader(
    new InputStreamReader(System.in, StandardCharsets.UTF_8));   // 바이트 → 문자 → 줄
String input = console.readLine();

try (BufferedReader br = new BufferedReader(
        new FileReader("input.txt", StandardCharsets.UTF_8))) {
    String line;
    while ((line = br.readLine()) != null) {
        System.out.println(line);
    }
}

try (BufferedWriter bw = new BufferedWriter(
        new FileWriter("output.txt", StandardCharsets.UTF_8))) {
    bw.write("첫 줄");
    bw.newLine();                          // System.lineSeparator(). Windows는 \r\n
    bw.write("둘째 줄");
}
```

## 5. 표준 입출력과 파일

### 5.1 System.in, out, err

JVM이 시작하면서 열어 두는 스트림이 셋이다. `System.in`은 `InputStream`이라 그대로는 바이트만 나오고, 4.3절처럼 다리를 놓아야 문자와 줄이 된다. `System.out`과 `System.err`는 2.3절의 `PrintStream`이며, `err`가 따로 있는 이유는 셸에서 정상 출력과 오류 출력을 다른 곳으로 보낼 수 있게 하기 위해서다. `System.setOut()`으로 대상을 파일로 바꿀 수도 있다. 콘솔 입력은 `Scanner`가 파싱까지 해 주어 편하고, 줄 단위로 빠르게 읽을 때는 `BufferedReader`가 낫다.

### 5.2 RandomAccessFile

```java
try (RandomAccessFile raf = new RandomAccessFile("data.dat", "rw")) {
    raf.writeInt(100);
    raf.writeUTF("Hello");
    raf.seek(0);                 // 파일 포인터를 처음으로
    int n = raf.readInt();       // 100
    raf.seek(4);
    String s = raf.readUTF();    // "Hello"
}
```

스트림은 순서대로만 흐르지만 파일은 원래 아무 위치나 읽을 수 있는 매체다. `RandomAccessFile`은 스트림이 아니라 그 성질을 그대로 드러낸 클래스로, 하나로 읽고 쓰며 `seek()`으로 위치를 옮긴다. 파일의 특정 위치를 고쳐 쓰거나 큰 파일의 일부만 읽을 때 쓴다.

### 5.3 File에서 Files로

```java
File f = new File("data/test.txt");     // 경로일 뿐 파일이 생기지는 않는다
f.exists();  f.isFile();  f.length();  f.lastModified();
f.delete();                              // 실패해도 false를 돌려줄 뿐이다

Path p = Path.of("data/test.txt");
Files.delete(p);                         // NoSuchFileException: data/test.txt
```

`File`은 JDK 1.0의 클래스로 파일과 디렉터리의 메타 정보를 다룬다. 문제는 실패를 알리는 방식이다. `delete()`, `mkdir()`, `renameTo()`가 실패하면 예외 대신 `false`를 돌려주고 이유는 알려 주지 않는다. 8장에서 반환값으로 실패를 알리는 방식의 문제로 꼽은 것이 그대로다. Java 7의 NIO.2(`java.nio.file`)가 `Path`와 `Files`로 이것을 다시 만들었다. 실패는 예외로, 그것도 어느 파일이 왜 안 됐는지가 메시지에 담겨 온다.

```java
Path src = Path.of("a.txt"), dst = Path.of("b.txt");
Files.copy(src, dst, StandardCopyOption.REPLACE_EXISTING);
Files.move(src, dst);
Files.size(src);  Files.isDirectory(src);  Files.exists(src);

String text = Files.readString(src);               // Java 11. UTF-8
Files.writeString(dst, text);
List<String> all = Files.readAllLines(src);         // 전부 메모리에

try (Stream<String> lines = Files.lines(src)) {     // 한 줄씩 지연. 14장
    lines.filter(l -> !l.isBlank()).forEach(System.out::println);
}
try (Stream<Path> walk = Files.walk(Path.of("."))) {
    walk.filter(Files::isRegularFile).forEach(System.out::println);
}
BufferedReader br = Files.newBufferedReader(src);   // UTF-8. 보조 스트림을 직접 쌓지 않아도 된다
```

`Files`의 문자 관련 메서드는 처음부터 UTF-8이 기본이었고, 버퍼도 알아서 씌운다. 3절에서 보조 스트림을 세 겹으로 쌓던 일을 한 줄로 끝내며, `Files.copy()`가 2.1절의 복사 코드보다 수백 배 빠른 것은 운영체제의 복사 기능을 바로 쓰기 때문이다. `Files.lines()`가 돌려주는 스트림은 파일을 한 줄씩 읽으므로 큰 파일도 메모리에 올리지 않지만, 그래서 파일 핸들을 쥐고 있고 닫아야 한다. 새 코드는 `File` 대신 `Path`와 `Files`다.

## 6. 직렬화: 왜 피하는 기술이 됐나

### 6.1 객체를 바이트로

```
   직렬화                 역직렬화
객체 ─▶ 바이트 스트림 ─▶ 파일 ─▶ 객체
```

```java
class UserInfo implements Serializable {
    private static final long serialVersionUID = 1L;
    String name;
    int age;
    transient String password;       // 저장하지 않는다
}

try (ObjectOutputStream oos = new ObjectOutputStream(new FileOutputStream("user.ser"))) {
    oos.writeObject(new UserInfo("홍길동", 25, "secret"));
}
try (ObjectInputStream ois = new ObjectInputStream(new FileInputStream("user.ser"))) {
    UserInfo u = (UserInfo) ois.readObject();   // password는 null
}
```

2절의 `DataOutputStream`은 값만 적어서 읽는 쪽이 타입과 순서를 알아야 했다. 직렬화는 객체의 **클래스 이름, 필드 이름, 타입, 값**을 함께 적어서 읽는 쪽이 그것만 보고 객체를 복원하게 한다. 참조로 이어진 객체들은 따라가며 함께 적고, 같은 객체가 두 번 나오면 두 번째는 앞의 것을 가리키는 표시만 적어 그래프 구조가 유지된다. 대신 크기가 크다. 이름과 나이 하나를 `DataOutputStream`으로 쓰면 15바이트인데 직렬화하면 80바이트 남짓이다.

`Serializable`은 메서드가 없는 마커 인터페이스다. [Chapter 12](../12-generics-enum-annotation)에서 애너테이션 이전에 "이 클래스는 이렇다"를 표시하던 방식이라고 한 것이 이것이다. 규칙은 넷이다. `static` 변수는 클래스의 것이라 적지 않고, `transient`를 붙인 필드는 건너뛰며 복원하면 기본값이 된다. 조상이 `Serializable`이 아니면 조상의 필드는 적히지 않고, 복원할 때 그 조상의 기본 생성자가 불려 초기화된다. 필드 중 하나라도 직렬화할 수 없는 타입이면 `NotSerializableException`이다.

### 6.2 생성자를 거치지 않는다

```java
class UserInfo implements Serializable {
    UserInfo(String name, int age) {
        if (age < 0) throw new IllegalArgumentException();   // 역직렬화는 이 검사를 지나가지 않는다
        ...
    }
}
```

역직렬화는 `new`가 아니다. JVM이 클래스의 생성자를 부르지 않고 객체를 만든 뒤 필드에 값을 채운다. 생성자에 넣어 둔 검사와 불변식이 전부 우회되고, 어떤 클래스의 인스턴스가 만들어질지는 **바이트 스트림이 정한다.** 스트림을 만든 쪽이 악의적이면, 클래스패스에 있는 어떤 클래스든 원하는 필드 값으로 만들어 낼 수 있고, 그 클래스들의 `readObject()`나 `hashCode()`가 연쇄적으로 불리면서 임의 코드 실행에 이르는 공격(가젯 체인)이 2015년 이후 여러 라이브러리에서 실제로 터졌다. Java 9의 `ObjectInputFilter`(JEP 290)로 허용할 클래스를 제한할 수 있게 됐지만, 원칙은 **믿을 수 없는 바이트는 역직렬화하지 않는다**이다. 외부와 주고받는 데이터는 JSON 같은 데이터 형식으로 적고, 파싱한 뒤 생성자를 거쳐 객체를 만든다. Java 16의 `record`는 예외적으로 역직렬화 때도 정규 생성자를 부르므로 검사가 살아 있다.

### 6.3 serialVersionUID

```java
// 필드 name, age로 저장한 뒤, 클래스에 email 필드를 추가하고 읽으면
// InvalidClassException: UserInfo; local class incompatible:
//   stream classdesc serialVersionUID = 2929570838881765252,
//   local class serialVersionUID = 913353644432075533
```

저장할 때의 클래스와 읽을 때의 클래스가 같은지를 `serialVersionUID`로 확인한다. 직접 적지 않으면 클래스 이름, 필드, 메서드 시그니처를 해시해서 계산하는데, 필드 하나를 추가하는 순간 값이 바뀌어 예전 파일을 읽지 못한다. 그래서 JDK 문서는 직접 선언하기를 강하게 권한다. 선언해 두면 필드가 추가돼도 읽을 수 있고, 새 필드는 기본값으로 채워진다. 호환되지 않는 변경을 했을 때만 값을 올려 옛 데이터를 명시적으로 거부한다. `record`는 기본값이 `0L`이라 이 문제가 없다.

직렬화가 쓸 곳이 남아 있기는 하다. 같은 프로그램의 두 프로세스 사이, 세션 정보의 임시 저장, 깊은 복사 같은 **내부 용도**다. 그 밖의 저장과 전송에는 형식이 문서화되고 생성자를 거치는 데이터 포맷이 맞다.

## 7. 요약

| 항목 | 핵심 | 왜 |
|:-----|:-----|:---|
| 스트림 | 단방향, 순서대로 흐르는 바이트 | 파일, 콘솔, 소켓을 하나의 그림으로 |
| 닫기 | `try-with-resources` | 파일 디스크립터는 유한하고 쓰기 버퍼는 닫아야 비워진다 |
| `read()`가 `int` | 0~255와 `-1` | 256가지 값을 다 쓰면서 끝도 알려야 한다 |
| 블로킹 | 데이터가 올 때까지 스레드가 선다 | NIO가 생긴 이유 |
| `DataOutputStream` | 기본형을 바이트로 | 타입 정보가 없어 쓴 순서대로 읽어야 한다 |
| `PrintStream` | `IOException`을 삼킨다 | 출력마다 `try-catch`를 강요하지 않으려고 |
| 보조 스트림 | 포장으로 기능 추가 | 상속이면 대상과 기능의 조합마다 클래스가 는다 |
| 버퍼링 | 시스템 콜을 8KB마다 한 번으로 | 커널 호출은 메서드 호출보다 수천 배 비싸다. 300배 차이 |
| 쓰기 버퍼 | 닫기 전에는 파일에 없다 | `close()`가 `flush()`다. 중요하면 직접 `flush()` |
| 문자 스트림 | 인코딩을 안에서 맡는다 | 바이트와 문자는 다른 층이다 |
| 한글 깨짐 | 적은 규칙과 읽는 규칙이 다르다 | 원인은 언제나 이 하나 |
| 기본 문자셋 | Java 18부터 UTF-8 | 운영체제마다 다르던 기본값이 파일을 깨뜨렸다 |
| 콘솔 | `stdout.encoding`은 여전히 콘솔 설정 | 명령 프롬프트의 한글 깨짐은 콘솔 인코딩 문제 |
| `InputStreamReader` | 바이트와 문자의 다리 | `FileReader`도 이것으로 만들어졌다 |
| `Files` | 예외로 실패를 알린다 | `File`은 `false`만 돌려줬다 |
| `Files.lines()` | 한 줄씩 지연 | 큰 파일도 메모리에 안 올리지만 닫아야 한다 |
| 직렬화 | 클래스와 필드 정보까지 적는다 | 읽는 쪽이 타입을 몰라도 된다. 대신 크다 |
| 생성자 우회 | 역직렬화는 `new`가 아니다 | 검사가 무력화되고 임의 클래스가 만들어진다 |
| `serialVersionUID` | 직접 선언 | 계산값은 필드 하나에도 바뀐다 |

| 할 일 | 도구 |
|:------|:-----|
| 이진 파일 읽고 쓰기 | `FileInputStream` + `Buffered`, 또는 `Files.readAllBytes` |
| 텍스트 파일 전체 | `Files.readString`, `Files.writeString` |
| 큰 텍스트를 줄 단위로 | `Files.lines`, `BufferedReader.readLine` |
| 콘솔 입력 | `Scanner`, 또는 `InputStreamReader` + `BufferedReader` |
| 복사, 이동, 삭제, 속성 | `Files` |
| 파일의 특정 위치 | `RandomAccessFile` |
| 객체 저장과 전송 | JSON 같은 데이터 포맷. 직렬화는 내부 용도만 |
