[Chapter 01](../01-java-intro)에서 자바 프로그램은 실제 컴퓨터가 아니라 JVM이라는 가상의 컴퓨터 위에서 돈다고 했다. 이 장은 그 컴퓨터의 **메모리 칸** 이야기다. 값을 어디에 어떻게 담는가. 자바가 기본 타입을 여덟 개로 못 박고, 각 타입의 크기를 어느 컴퓨터에서나 똑같이 정해 두고, 정수와 실수를 전혀 다른 방식으로 저장하는 것은 전부 "메모리에 값을 어떻게 놓을 것인가"에 대한 결정이다. 그 결정을 이해하면 `long l = 10000000000;`이 왜 컴파일되지 않는지, `0.1 + 0.2`가 왜 `0.3`이 아닌지, `byte`에 1을 더했더니 왜 음수가 되는지가 외울 것이 아니라 당연한 결과가 된다.

## 1. 변수: 이름 붙은 메모리 칸

```java
int age;          // 선언: 칸을 마련한다
age = 25;         // 초기화: 처음 값을 넣는다
int score = 90;   // 선언과 초기화를 한 번에
```

변수는 값을 담는 메모리 공간에 이름을 붙인 것이다. 칸 하나에는 값 하나만 들어가고, 새 값을 넣으면 이전 값은 사라진다.

선언에 반드시 **타입**이 붙는 이유는 메모리에 있는 것이 그저 비트이기 때문이다. `0100 0001`이라는 8비트는 정수 65일 수도, 문자 `'A'`일 수도 있다. JVM은 이 비트를 몇 바이트 단위로 읽고 어떤 뜻으로 해석할지 알아야 하는데, 그것을 알려 주는 것이 타입이다. 자바는 이 정보를 실행 중이 아니라 **컴파일 시점**에 확정한다. 그래서 `int` 변수에 문자열을 넣는 코드는 실행해 보기도 전에 컴파일러가 거른다.

### 1.1 왜 지역 변수만 초기화를 강제하는가

```java
class Member {
    int count;                // 필드: 자동으로 0

    void run() {
        int local;            // 지역 변수: 값이 없다
        System.out.println(local);   // 컴파일 오류
    }
}
```

| 구분 | 어디에 있나 | 초기화 | 이유 |
|:-----|:------------|:-------|:-----|
| 필드 | 힙의 객체 안 | JVM이 자동으로 0, `false`, `null` | 객체를 만들 때 메모리를 통째로 0으로 채운다. 한 번이면 되니 싸다 |
| 지역 변수 | 메서드의 스택 프레임 | 개발자가 반드시 직접 | 프레임은 메서드가 호출될 때마다 재사용되는 공간이라 이전 호출의 값이 남아 있을 수 있다 |

JVM은 객체를 만들 때 그 메모리를 0으로 밀어 놓는다. 그래서 필드는 읽어도 안전하다. 지역 변수가 사는 스택 프레임은 다르다. 메서드가 호출될 때마다 만들어졌다 사라지는 공간이라, 0으로 밀지 않으면 직전에 그 자리를 썼던 값이 그대로 보인다. 호출마다 0으로 미는 비용을 치르는 대신 자바는 **컴파일러가 초기화 여부를 검사**하는 쪽을 택했다. 실행 중 비용은 없고, 실수는 컴파일 시점에 잡힌다.

### 1.2 var: 타입을 쓰지 않아도 타입은 있다

```java
var list = new ArrayList<String>();   // ArrayList<String>으로 추론
var count = 10;                       // int
```

Java 10부터 지역 변수의 타입을 `var`로 대신할 수 있다. 오른쪽 값을 보고 컴파일러가 타입을 정하는 것이지, 타입이 없어지는 것이 아니다. `count`는 여전히 `int`이고 나중에 문자열을 넣을 수 없다. 오른쪽만 봐도 타입이 분명한 자리에서 중복을 줄이는 도구이며, 초기화 없이 `var x;`처럼 쓸 수 없는 이유도 추론할 값이 없기 때문이다.

## 2. 이름 규칙

| 규칙 | 내용 | 예 |
|:-----|:-----|:---|
| 대소문자 구분 | `age`와 `Age`는 다른 변수 | |
| 첫 글자 | 문자, `_`, `$`. 숫자는 안 된다 | `top10` 가능, `7up` 불가 |
| 나머지 글자 | 문자, 숫자, `_`, `$` | `S#arp` 불가 |
| 예약어 | 쓸 수 없다 | `int`, `class`, `for` |
| 길이 | 제한 없음 | |

첫 글자에 숫자가 오면 안 되는 이유는 컴파일러가 `7up`을 읽을 때 숫자 리터럴 `7`로 시작하는지 이름인지 구분할 수 없기 때문이다. `$`는 허용되지만 쓰지 않는 것이 관례다. 컴파일러가 스스로 만드는 이름에 `$`를 쓰기 때문이다. 1장에서 본 `Outer$Inner.class`가 그 예다. `_` 하나만으로 된 이름은 Java 9부터 예약어가 됐고, Java 22부터는 "쓰지 않는 값"을 뜻하는 자리 표시자로 쓰인다.

| 대상 | 관례 | 예 |
|:-----|:-----|:---|
| 클래스 | 첫 글자 대문자 | `StringBuilder` |
| 변수, 메서드 | 첫 글자 소문자, 이후 단어는 대문자 | `lastName`, `getName()` |
| 상수 | 전부 대문자, 단어 사이 `_` | `MAX_VALUE` |
| 패키지 | 전부 소문자 | `java.util` |

관례는 문법이 아니라 약속이지만 지키는 이유가 있다. 이름의 모양만 보고 그것이 클래스인지 변수인지 상수인지 알 수 있어야 코드를 읽는 속도가 빨라진다. `Member`는 클래스, `member`는 변수, `MEMBER`는 상수라는 것을 선언부를 찾아보지 않아도 안다.

## 3. 자료형: 값을 담느냐, 주소를 담느냐

### 3.1 기본형과 참조형

```
[기본형]  int age = 25;
             ┌────┐
      age ──▶│ 25 │   값 자체
             └────┘

[참조형]  String s = "hi";
             ┌────┐     ┌───────────┐
        s ──▶│주소│ ──▶ │ "hi" 객체 │
             └────┘     └───────────┘
```

| 구분 | 변수 칸에 들어 있는 것 | 종류 |
|:-----|:-----------------------|:-----|
| 기본형 (primitive) | 값 그 자체 | `boolean`, `char`, `byte`, `short`, `int`, `long`, `float`, `double` 여덟 개 |
| 참조형 (reference) | 객체가 있는 메모리 주소 | 나머지 전부. 클래스, 배열, 인터페이스 |

왜 두 종류로 나뉘는가. 변수 칸은 크기가 정해진 작은 공간이다. 8바이트 안에 들어가는 숫자와 문자는 칸에 직접 담을 수 있지만, 객체는 크기가 제각각이고 얼마든지 커질 수 있어 칸에 담을 수 없다. 그래서 객체는 힙에 두고 변수에는 그 **주소**만 담는다. 참조형 변수가 `null`을 가질 수 있는 것도 이 때문이다. `null`은 "가리키는 객체가 없다"는 뜻이고, 값 자체를 담는 기본형에는 그런 상태가 없다.

### 3.2 기본형 여덟 가지

```
기본형 (Primitive Type)
┌────────┬────────┬────────┐
│ 논리형 │ 문자형 │ 수치형 │
├────────┼────────┼────────┤
│boolean │  char  │ byte   │
│  (1B)  │  (2B)  │ short  │
│        │        │ int    │
│        │        │ long   │
│        │        │ float  │
│        │        │ double │
└────────┴────────┴────────┘
```

| 타입 | 크기 | 범위 | 비고 |
|:-----|:-----|:-----|:-----|
| `boolean` | 1 byte | `true`, `false` | 명세는 크기를 정하지 않는다. JVM이 보통 1바이트로 다룬다 |
| `char` | 2 byte | 0 ~ 65,535 | 유니코드 문자. 부호가 없는 유일한 타입 (7절) |
| `byte` | 1 byte | -128 ~ 127 | |
| `short` | 2 byte | -32,768 ~ 32,767 | |
| `int` | 4 byte | 약 ±21억 | 정수의 기본 |
| `long` | 8 byte | 약 ±922경 | |
| `float` | 4 byte | 유효 자릿수 약 7 | |
| `double` | 8 byte | 유효 자릿수 약 15 | 실수의 기본 |

n비트 부호 있는 정수의 범위는 -2^(n-1) ~ 2^(n-1)-1이다. 음수 쪽이 하나 더 많은 이유는 6절의 2의 보수에서 나온다.

**왜 크기가 못 박혀 있는가.** C의 `int`는 컴퓨터에 따라 2바이트일 수도 4바이트일 수도 있다. 같은 소스가 기계마다 다른 범위를 갖는 셈이다. 자바는 1장에서 본 "한 번 컴파일하면 어디서나 같은 결과"를 지키려고 모든 기본형의 크기를 명세에 고정했다. `int`는 어느 JVM에서든 4바이트이고, 그래서 어느 JVM에서든 같은 자리에서 넘친다.

**왜 부호 없는 타입이 없는가.** C에는 `unsigned int`가 있지만 자바에는 없다. 부호 있는 값과 없는 값을 섞어 계산할 때 생기는 혼란을 언어에서 없애기 위한 선택이었다. 부호 없는 해석이 꼭 필요한 곳(네트워크 바이트, 해시 값)을 위해 Java 8부터 `Integer.toUnsignedString()`, `Integer.parseUnsignedInt()` 같은 메서드가 있다.

## 4. 상수와 리터럴

```java
final int MAX_SPEED = 100;   // 상수: 한 번 넣으면 바꿀 수 없다
int year = 2024;             // 2024가 리터럴
```

| 용어 | 뜻 |
|:-----|:---|
| 변수 | 값 하나를 담는 칸 |
| 상수 | 값을 한 번만 넣을 수 있는 칸. `final` |
| 리터럴 | 코드에 직접 적은 값 그 자체. `123`, `3.14`, `'A'`, `"hi"` |

### 4.1 리터럴에도 타입이 있다

```java
long big = 10000000000;      // 컴파일 오류
long big = 10000000000L;     // L을 붙여야 한다

float f = 3.14;              // 컴파일 오류
float f = 3.14f;             // f를 붙여야 한다
```

첫 줄이 오류인 이유는 대입 전에 리터럴 자체가 먼저 해석되기 때문이다. 접미사 없는 정수 리터럴은 **`int`**이고, `10000000000`은 `int` 범위를 넘으므로 `long` 변수에 넣기도 전에 리터럴 단계에서 잘못됐다고 판정된다. 실수 리터럴의 기본은 **`double`**이라 `3.14`를 `float`에 넣는 것은 8바이트 값을 4바이트 칸에 넣는 일이 되어 거부된다.

| 타입 | 접미사 | 예 |
|:-----|:-------|:---|
| `long` | `L` (소문자 `l`은 1과 헷갈리니 피한다) | `100L` |
| `float` | `f` | `3.14f` |
| `double` | `d`, 생략 가능 | `3.14`, `3.14d` |

기본이 `int`와 `double`인 이유는 각각 정수와 실수의 "기본 타입"이기 때문이다. JVM은 `byte`, `short` 연산을 따로 갖지 않고 전부 `int`로 계산하며(8절), 실수는 정밀도가 높은 `double`을 기준으로 삼는다.

### 4.2 진법 접두사와 구분자

| 진법 | 접두사 | 예 |
|:-----|:-------|:---|
| 2진수 | `0b` | `0b0101` |
| 8진수 | `0` | `077` |
| 16진수 | `0x` | `0xFF` |

8진수 접두사가 `0`이라는 점은 함정이 될 수 있다. `010`은 십진수 10이 아니라 8진수 `10`, 즉 8이다. 숫자 앞에 0을 붙여 자릿수를 맞추려다 값이 바뀌는 버그가 여기서 난다. Java 7부터는 리터럴 중간에 `_`를 넣어 자릿수를 읽기 쉽게 만들 수 있다.

```java
int million = 1_000_000;
long card = 1234_5678_9012_3456L;
```

## 5. 형식화된 출력: printf

```java
System.out.printf("%-10s | %5d%n", "apple", 3);   // apple      |     3
System.out.printf("%.2f%n", 3.14159);              // 3.14
```

| 지시자 | 뜻 | 예 |
|:-------|:---|:---|
| `%d` | 10진 정수 | `123` |
| `%x`, `%X` | 16진 정수 | `7b`, `7B` |
| `%o` | 8진 정수 | `173` |
| `%f` | 실수 | `3.140000` |
| `%e` | 지수 표기 | `3.14e+00` |
| `%c` | 문자 | `A` |
| `%s` | 문자열 | `Hello` |
| `%b` | 논리값 | `true` |
| `%n` | 줄바꿈 | |

`println`은 값을 있는 그대로 찍지만 `printf`는 자릿수, 정렬, 소수점 이하 자릿수를 정할 수 있다. 줄바꿈에 `\n` 대신 `%n`을 쓰는 이유는 운영체제마다 줄바꿈 문자가 다르기 때문이다. Windows는 `\r\n`, 그 외는 `\n`을 쓰는데, `%n`은 실행되는 곳에 맞는 문자를 골라 준다.

## 6. 진법과 음수 표현

### 6.1 진법 변환

```
10진 → 2진: 2로 나누고 나머지를 역순으로
2진 → 10진: 각 자리 × 2^n 을 합산

2진 → 8진:  3자리씩 묶는다 (2^3 = 8)
2진 → 16진: 4자리씩 묶는다 (2^4 = 16)
```

16진수가 프로그래밍에서 자주 보이는 이유는 2진수와의 변환이 자리별로 딱 떨어지기 때문이다. 4비트가 16진수 한 자리이므로, 1바이트는 언제나 16진수 두 자리다. `0xFF`가 `1111 1111`인 것을 계산 없이 읽을 수 있다.

### 6.2 음수는 2의 보수로

```
양수 5 (4비트): 0101
   ↓ 1의 보수 (비트 반전)
               1010
   ↓ +1
음수 -5:       1011
```

컴퓨터는 음수를 저장할 때 **2의 보수**를 쓴다. 왜 이렇게 번거로운 방식인가. 덧셈 회로 하나로 뺄셈까지 처리하기 위해서다. `5 + (-5)`를 위 표현으로 더하면 `0101 + 1011 = 1 0000`이고, 4비트를 넘친 1을 버리면 `0000`이다. 부호를 따로 처리하는 회로 없이 덧셈만으로 뺄셈이 된다. 최상위 비트(MSB)가 1이면 음수, 0이면 양수로 읽히는 것도 이 방식의 결과다.

이 표현에서 3절의 "음수가 하나 더 많은" 이유가 나온다. 4비트로 표현할 수 있는 16가지 중 `0000`은 0, `0001`~`0111`은 1~7, `1000`~`1111`은 -8~-1이다. 0이 양수 쪽 자리를 하나 차지하므로 양수는 7까지, 음수는 -8까지다.

## 7. 문자형

### 7.1 문자는 숫자다

```java
char ch = 'A';         // 실제로 저장되는 것은 65
char ch2 = 65;         // 위와 같다
int code = ch;         // 65
```

메모리에는 글자를 담을 방법이 없다. 담을 수 있는 것은 숫자뿐이므로, 글자마다 번호를 정해 두고 그 번호를 저장한다. 그 번호표가 문자 집합이고, 자바가 채택한 문자 집합이 **유니코드**다. `char`는 유니코드 번호를 담는 2바이트 정수이며, 그래서 `char`끼리 더하거나 비교할 수 있다. `'B' - 'A'`는 1이다.

**왜 2바이트인가.** 자바가 설계된 1990년대 중반의 유니코드는 16비트, 즉 65,536개의 문자로 세상의 모든 글자를 담을 계획이었다. 자바는 그 계획에 맞춰 `char`를 2바이트로 정했다. 그런데 유니코드는 곧 그 범위를 넘어섰다. 이모지와 일부 한자처럼 65,536번 뒤에 있는 문자는 `char` 하나에 들어가지 않아 두 개를 이어 붙여 표현한다(서로게이트 쌍). 그래서 `"😀".length()`는 1이 아니라 2다. 문자 수를 정확히 세려면 `codePointCount()`를 써야 한다. `char`가 2바이트인 것은 설계 당시의 합리적 결정이 시간이 지나 한계가 된 사례다.

### 7.2 이스케이프 문자

| 표기 | 뜻 |
|:-----|:---|
| `\t` | 탭 |
| `\n` | 줄바꿈 |
| `\\` | 역슬래시 |
| `\'` | 작은따옴표 |
| `\"` | 큰따옴표 |
| `\u0041` | 유니코드 번호로 직접 지정. `'A'`와 같다 |

따옴표 안에 따옴표를 넣을 수 없고 줄바꿈 같은 보이지 않는 문자를 적을 방법이 없으니, 역슬래시 뒤의 글자를 특별한 뜻으로 읽는 약속을 둔 것이다.

### 7.3 인코딩

| 방식 | 특징 |
|:-----|:-----|
| ASCII | 7비트, 128개 문자. 영어와 기호만 |
| UTF-16 | 2바이트, 범위를 넘는 문자는 4바이트. 자바 `char`와 `String`의 내부 표현 |
| UTF-8 | 1~4바이트 가변. 영어는 1바이트라 웹과 파일의 표준 |

문자 집합(유니코드)이 "어떤 글자가 몇 번인가"라면, 인코딩은 "그 번호를 바이트로 어떻게 적는가"다. 같은 유니코드라도 UTF-8과 UTF-16은 바이트가 다르다. 파일을 읽고 쓸 때 인코딩을 잘못 맞추면 글자가 깨지는 이유가 이것이다.

{{< callout type="info" >}}
`String`은 내부적으로 UTF-16을 쓰지만, Java 9의 Compact Strings 최적화 이후로는 모든 문자가 Latin-1 범위(0~255) 안에 있는 문자열을 문자당 1바이트로 저장한다. 영어 문자열이 대부분인 프로그램에서 메모리를 크게 아낀다. 한글이 하나라도 들어가면 그 문자열은 다시 문자당 2바이트다.
{{< /callout >}}

## 8. 정수형 오버플로우

```java
byte b = 127;   // byte의 최대값
b++;            // 128이 되어야 하지만
// b == -128    // 최소값으로 돌아간다
```

```
0111 1111  (127)
+       1
─────────
1000 0000  (-128)
최상위 비트가 1이 되어 음수로 읽힌다
```

타입의 범위를 넘으면 값이 반대쪽 끝으로 돌아간다. 6절의 2의 보수 때문이다. 127에 1을 더한 `1000 0000`은 자릿수로만 보면 128이지만, 최상위 비트가 1이므로 -128로 해석된다. 비트 연산으로는 아무 문제가 없었고, 해석만 바뀐 것이다.

**왜 예외를 던지지 않는가.** 덧셈마다 넘쳤는지 검사하면 모든 산술 연산이 느려진다. 자바는 C와 같은 선택을 했다. 정수 연산은 그냥 돌고, 넘침을 감지하는 것은 개발자 몫이다. 그래서 오버플로우 버그는 오류 없이 틀린 값으로 조용히 진행되다가 뒤늦게 드러난다.

{{< callout type="warning" >}}
큰 값을 다룰 때는 처음부터 `long`을 쓰고, `long`으로도 부족하면 `BigInteger`를 쓴다. 넘침을 반드시 잡아야 하는 계산에는 `Math.addExact()`, `Math.multiplyExact()`처럼 넘치면 예외를 던지는 메서드가 있다. 검사 비용을 치를지는 개발자가 고른다.
{{< /callout >}}

**정수는 기본적으로 `int`를 쓴다.** `byte`나 `short`가 메모리를 덜 쓸 것 같지만 계산에서는 이득이 없다. JVM에는 `byte`나 `short`를 위한 산술 명령이 없어서 계산할 때 전부 `int`로 바꾼 뒤 계산한다. `byte b = 1; b = b + 1;`이 컴파일되지 않는 이유가 이것이다. `b + 1`의 결과는 `int`이고, 그것을 `byte`에 도로 넣으려면 명시적 변환이 필요하다. 이 형 변환 규칙은 [Chapter 03](../03-java-operator)에서 다룬다. `byte`와 `short`는 배열이나 파일 입출력처럼 메모리 크기가 중요한 자리에서만 쓴다.

## 9. 실수형

### 9.1 float와 double

| 항목 | `float` | `double` |
|:-----|:--------|:---------|
| 크기 | 4바이트 | 8바이트 |
| 유효 자릿수 | 약 7 | 약 15 |
| 리터럴 기본 | | O |

실수는 정수와 달리 **자릿수가 아니라 유효 숫자**로 정밀도를 말한다. `float`는 유효 숫자 7자리쯤, `double`은 15자리쯤을 담는다. 특별한 이유가 없으면 `double`을 쓴다. 메모리를 아끼려고 `float`를 고르면 계산 몇 번에 오차가 눈에 보이는 자리까지 올라온다.

### 9.2 IEEE 754: 부호, 지수, 가수

```
float (32bit): S(1) E(8)  M(23)
double(64bit): S(1) E(11) M(52)

S: 부호 (0=양수, 1=음수)
E: 지수 (Exponent)
M: 가수 (Mantissa, 정밀도 결정)
```

실수는 `(-1)^S × 1.M × 2^(E-bias)` 꼴로 저장된다. 과학적 표기법 `1.23 × 10^5`를 2진수로 옮긴 것이다. 정수처럼 비트를 값에 그대로 대응시키지 않는 이유는, 아주 큰 수와 아주 작은 수를 같은 크기의 칸에 담으려면 소수점의 위치가 움직여야(부동, floating) 하기 때문이다. 가수 `M`의 비트 수가 유효 숫자를 정하므로 `double`이 `float`보다 훨씬 정밀하다.

### 9.3 0.1을 정확히 담을 수 없는 이유

```java
double a = 0.1 + 0.2;
System.out.println(a);          // 0.30000000000000004
System.out.println(a == 0.3);   // false
```

10진수에서 1/3은 0.3333…으로 끝나지 않는다. 분모 3이 10의 소인수(2, 5)가 아니기 때문이다. 같은 일이 2진수에서는 1/10에 일어난다. 분모 10에는 소인수 5가 있고, 2진수는 2의 거듭제곱으로만 소수를 표현하므로 0.1은 `0.000110011001100…`처럼 무한히 반복된다. 유한한 가수 비트로 이것을 담으면 어딘가에서 잘라야 하고, 그 순간 이미 0.1이 아니다. 0.1과 0.2가 각각 조금씩 틀린 채 더해지니 결과가 0.3에서 어긋난다.

이것은 자바의 버그가 아니라 2진 부동소수점의 성질이다. 그래서 실수를 `==`로 비교하지 않는다. 두 값의 차이가 허용 오차보다 작은지를 보거나, 아예 실수를 쓰지 않는다.

{{< callout type="warning" >}}
**금액처럼 10진수로 정확해야 하는 값은 `BigDecimal`을 쓴다.** `double`의 오차는 계산이 쌓일수록 커져 금융 계산에서는 치명적이다. 만들 때는 `new BigDecimal(0.1)`이 아니라 `new BigDecimal("0.1")`이나 `BigDecimal.valueOf(0.1)`을 써야 한다. 앞의 것은 이미 오차가 들어간 `double` 0.1을 그대로 옮기기 때문이다.
{{< /callout >}}

### 9.4 넘침과 특수한 값

| 상황 | 결과 |
|:-----|:-----|
| 표현 범위를 넘는 큰 값 | `Infinity`, `-Infinity` |
| 표현 범위보다 작은 값 | `0.0` |
| `0.0 / 0.0` | `NaN` (Not a Number) |

정수는 넘치면 반대쪽으로 돌아가지만 실수는 `Infinity`가 된다. IEEE 754가 무한대와 "숫자 아님"을 위한 비트 패턴을 따로 두었기 때문이다. `NaN`은 자기 자신과도 같지 않아서 `x == x`가 `false`가 되는 유일한 값이다. `NaN`인지 확인하려면 `Double.isNaN(x)`를 써야 한다.
