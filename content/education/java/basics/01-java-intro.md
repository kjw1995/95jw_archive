자바를 처음 배울 때 외우게 되는 것들이 있다. 컴파일하면 기계어가 아니라 `.class` 파일이 나온다, 실행하려면 JVM이 있어야 한다, `main`은 반드시 `public static void`여야 한다, 파일 이름은 클래스 이름과 같아야 한다. 전부 규칙처럼 들리지만 사실은 하나의 설계 결정에서 흘러나온 결과다. **자바는 프로그램을 특정 컴퓨터가 아니라 가상의 컴퓨터를 향해 컴파일한다.** 이 장에서는 그 결정이 왜 내려졌고, 거기서 어떤 규칙들이 따라 나왔는지를 첫 프로그램을 실행하기까지의 흐름을 따라가며 본다.

---

## 1. 자바는 어디서 왔나

자바는 1991년 썬 마이크로시스템즈(Sun Microsystems)의 그린 프로젝트에서 시작됐다. 제임스 고슬링(James Gosling)이 이끈 이 팀의 목표는 웹이 아니라 **가전제품**이었다. 셋톱박스나 리모컨 같은 기기에 들어갈 언어를 만들려 했는데, 기기마다 CPU와 운영체제가 제각각이라는 것이 문제였다. C나 C++로 만든 프로그램은 특정 CPU의 기계어로 컴파일되므로 기기가 바뀔 때마다 다시 빌드해야 했다. 처음 이름이 오크(Oak)였던 이 언어가 "한 번 컴파일하면 어느 기기에서든 실행된다"를 목표로 삼은 이유가 여기에 있다.

가전 시장은 열리지 않았지만 1990년대 중반에 웹이 열렸다. 브라우저를 쓰는 컴퓨터 역시 제각각이었고, 같은 프로그램을 어디서든 돌려야 한다는 요구는 그대로였다. 자바는 1995년에 공개되고 1996년에 JDK 1.0으로 정식 발표되면서 이 요구에 정확히 맞아떨어졌다. **Write Once, Run Anywhere**라는 구호가 그때 만들어졌다.

| 시기 | 사건 |
|:-----|:-----|
| 1991 | 그린 프로젝트 시작. 가전제품용 언어 오크 |
| 1995~1996 | 자바로 개명, 공개, JDK 1.0 |
| 2010 | 오라클이 썬을 인수. 이후 오라클이 관리 |
| 2018 | 6개월마다 새 버전을 내는 방식으로 전환 |
| 현재 | 참조 구현은 오픈소스 OpenJDK. 장기 지원(LTS) 버전은 8, 11, 17, 21, 25 |

## 2. 왜 기계어가 아니라 바이트코드인가

### 2.1 컴파일 결과물이 다르다

```
[C]     소스 ─컴파일▶ 기계어(OS·CPU별)
        Windows·Linux·Mac용 각각 빌드

[Java]  소스 ─javac▶ 바이트코드 하나
        Windows JVM  Linux JVM  Mac JVM
        (JVM만 OS별, .class는 하나)
```

C 컴파일러는 소스를 **특정 CPU의 기계어**로 바꾼다. 그 결과물은 그 CPU와 운영체제에서만 돈다. 자바 컴파일러 `javac`는 소스를 **바이트코드**로 바꾼다. 바이트코드는 실제 CPU의 명령어가 아니라, 자바가 정의한 가상의 컴퓨터인 **JVM**(Java Virtual Machine)의 명령어다. 어느 실제 CPU도 바이트코드를 직접 실행하지 못하므로, 실행하려면 그 운영체제용 JVM이 바이트코드를 읽어 실제 기계어로 바꿔 줘야 한다.

```
 ┌──────────────┐
 │ Java 소스코드 │ Hello.java
 └──────┬───────┘
        │ javac (컴파일)
        ▼
 ┌──────────────┐
 │  바이트코드   │ Hello.class
 └──────┬───────┘
        │ java (실행)
        ▼
 ┌──────────────┐
 │     JVM      │ OS별로 다른 JVM
 └──────┬───────┘
        ▼
 ┌──────────────┐
 │    운영체제   │ Win/Linux/mac
 └──────────────┘
```

여기서 자바의 이식성이 나온다. 개발자는 `.class` 파일 하나를 배포하고, 운영체제마다 다른 것은 JVM뿐이다. 이식성의 짐을 프로그램이 아니라 JVM이 진다.

{{< callout type="info" >}}
**자바 프로그램은 운영체제에 독립적이지만 JVM은 운영체제에 종속적이다.** `.class` 파일은 어디서나 같지만, 그것을 실행할 JVM은 Windows용, Linux용, macOS용이 따로 있고 실행할 컴퓨터에 설치되어 있어야 한다. "어디서나 실행된다"는 말은 "JVM이 있는 곳이라면 어디서나"라는 뜻이다.
{{< /callout >}}

### 2.2 이 결정이 낳은 나머지 특징

가상 머신을 사이에 둔 것은 이식성 때문이었지만, 그 층이 생기자 다른 것들도 가능해졌다.

| 특징 | 내용 | 왜 가능한가 |
|:-----|:-----|:------------|
| 플랫폼 독립성 | `.class` 하나로 어느 OS에서든 실행 | 실제 CPU가 아닌 JVM을 향해 컴파일한다 |
| 자동 메모리 관리 | 쓰지 않는 객체를 가비지 컬렉터가 회수 | JVM이 메모리를 소유하고 관찰한다 |
| 안전성 | 잘못된 바이트코드를 실행 전에 거른다 | JVM이 로딩 시점에 검증한다 (7절) |
| 실행 중 최적화 | 자주 도는 코드를 기계어로 바꿔 빠르게 | JVM이 실행을 지켜보다 최적화한다 (3절) |
| 동적 로딩 | 클래스는 처음 쓰이는 순간에 로드 | 클래스 단위로 파일이 나뉘어 있다 (8절) |
| 객체지향, 멀티스레드, 표준 라이브러리 | 언어와 JDK가 기본 제공 | 언어 설계의 선택 |

이 가운데 자동 메모리 관리는 C와 C++ 개발자를 가장 괴롭히던 문제에 대한 답이었다. 해제한 메모리를 다시 쓰거나(댕글링 포인터), 해제를 잊어 새는 문제(메모리 누수)는 프로그램이 커질수록 잡기 어렵다. JVM이 객체를 관리하니 "더 이상 아무도 참조하지 않는 객체"를 JVM이 알아서 찾아 지울 수 있다. 대신 그 작업이 언제 얼마나 걸릴지 개발자가 통제하기 어렵다는 비용이 따른다. 가비지 컬렉션의 동작은 [자동 메모리 관리](../../jvm/memory-management)에서 따로 다룬다.

## 3. JVM: 바이트코드를 실행하는 가상의 컴퓨터

### 3.1 구성 요소

```
┌──────────────────────────────┐
│            JVM                │
├─────────┬─────────┬──────────┤
│ Class   │ Runtime │Execution │
│ Loader  │ Data    │ Engine   │
│         │ Area    │          │
│ .class  │ 메모리   │바이트코드│
│ 로드    │ 영역    │ 실행     │
└─────────┴─────────┴──────────┘
```

실제 컴퓨터에 디스크, 메모리, CPU가 있듯 JVM에도 세 부분이 있다.

| 구성 요소 | 하는 일 | 실제 컴퓨터에 비유하면 |
|:----------|:--------|:-----------------------|
| 클래스 로더 | `.class` 파일을 찾아 읽고 메모리에 올린다 | 디스크에서 프로그램을 불러오는 로더 |
| 런타임 데이터 영역 | 객체가 사는 힙, 메서드 호출을 쌓는 스택, 클래스 정보를 두는 메서드 영역 | 메모리 |
| 실행 엔진 | 바이트코드를 해석하거나 기계어로 바꿔 실행한다 | CPU |

클래스 로더는 프로그램 시작 때 모든 클래스를 올리지 않는다. 어떤 클래스가 **처음 쓰이는 순간**에 그 클래스만 찾아 올린다. 표준 라이브러리만 해도 클래스가 수천 개인데 전부 올리면 시작이 느려지고 메모리만 차지한다. 8절에서 볼 "클래스마다 `.class` 파일 하나"라는 규칙은 이 게으른 로딩을 위한 것이다. 런타임 데이터 영역의 각 부분이 무엇을 담고 왜 나뉘어 있는지는 [JVM 런타임 데이터 영역 정리](../../../../blog/tech-review/jvm-runtime-data-areas)에서 자세히 본다.

### 3.2 인터프리터와 JIT 컴파일러

```
인터프리터:
  바이트코드 → 한 줄씩 해석·실행 (느림)

JIT 컴파일러:
  자주 실행되는 코드 → 기계어로 컴파일
  → 캐싱 → 재사용 (빠름)
```

초기 JVM은 바이트코드를 한 명령씩 읽어 해석하는 **인터프리터**였다. 구현이 단순하고 바로 시작할 수 있지만, 같은 명령을 만날 때마다 다시 해석하니 느렸다. "자바는 느리다"는 평판이 이때 생겼다.

해법은 **JIT**(Just-In-Time) 컴파일러다. JVM은 처음에는 인터프리터로 실행하면서 어떤 메서드와 반복문이 자주 도는지 센다. 일정 횟수를 넘긴 코드(hot code)는 그 자리에서 기계어로 컴파일해 두고, 이후로는 기계어를 바로 실행한다. 오라클과 OpenJDK의 JVM인 **HotSpot**의 이름이 여기서 왔다.

왜 처음부터 전부 컴파일하지 않을까. 첫째, 전부 컴파일하면 시작이 늦어진다. 대부분의 코드는 한두 번 실행되고 말아서 컴파일할 가치가 없다. 둘째, 실행해 봐야 알 수 있는 정보가 있다. 어느 분기가 주로 타는지, 어떤 메서드가 실제로 어떤 타입으로 호출되는지를 보고 컴파일하면, 소스만 보고 미리 컴파일하는 것보다 더 공격적으로 최적화할 수 있다. JIT는 늦게 시작하는 대신 더 많이 알고 컴파일한다.

{{< callout type="info" >}}
JIT의 대가는 **예열**(warm-up)이다. 시작 직후에는 인터프리터로 돌아 느리고, 최적화가 끝나야 제 속도가 난다. 그래서 오래 켜 두는 서버에서는 유리하고, 잠깐 실행되고 끝나는 프로그램에서는 불리하다. 이 시작 비용을 줄이려고 JDK 24부터는 이전 실행에서 얻은 정보를 저장해 뒀다 다음 시작에 쓰는 AOT 캐시(Project Leyden)가 들어왔고, 아예 실행 파일로 미리 컴파일하는 GraalVM 네이티브 이미지도 쓰인다.
{{< /callout >}}

## 4. JDK, JRE, JVM

```
┌────────────────────────────┐
│           JDK               │
│  ┌──────────────────────┐  │
│  │         JRE           │  │
│  │  ┌────────────────┐  │  │
│  │  │      JVM        │  │  │
│  │  └────────────────┘  │  │
│  │  + Java API          │  │
│  └──────────────────────┘  │
│  + 개발 도구 (javac 등)     │
└────────────────────────────┘
```

| 이름 | 무엇인가 | 누가 필요한가 |
|:-----|:---------|:--------------|
| JVM | 바이트코드를 실행하는 가상 머신 | 실행에 필수 |
| JRE | JVM + 표준 라이브러리(Java API) | 자바 프로그램을 **실행만** 하는 사람 |
| JDK | JRE + `javac` 같은 개발 도구 | 자바 프로그램을 **만드는** 사람 |

셋이 층을 이루는 이유는 사용자가 다르기 때문이다. 프로그램을 실행만 하는 컴퓨터에는 컴파일러가 필요 없다. 그래서 오랫동안 JRE가 따로 배포됐다. **Java 11부터 오라클은 JRE를 따로 배포하지 않는다.** 대신 `jlink`로 애플리케이션이 실제로 쓰는 모듈만 골라 작은 실행 환경을 만드는 방식을 권한다. 모든 프로그램에 같은 크기의 JRE를 깔아 두던 시대에서, 프로그램마다 필요한 만큼만 담는 시대로 바뀐 것이다.

| 도구 | 하는 일 |
|:-----|:--------|
| `javac` | 소스를 바이트코드로 컴파일 |
| `java` | JVM을 띄워 클래스를 실행 |
| `jar` | 여러 `.class`를 하나의 아카이브로 묶기 |
| `javap` | `.class` 안의 바이트코드를 사람이 읽을 수 있게 출력 |
| `javadoc` | 주석에서 API 문서 생성 |
| `jshell` | 한 줄씩 실행해 보는 대화형 셸 (Java 9) |

`javap -c Hello.class`를 한 번 실행해 보면 2절의 설명이 눈으로 확인된다. 기계어가 아니라 `getstatic`, `ldc`, `invokevirtual` 같은 JVM 명령어가 나온다.

## 5. 첫 프로그램

```java
// Hello.java
public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

```bash
javac Hello.java   # Hello.class 생성
java Hello         # 실행. 파일 이름이 아니라 클래스 이름을 준다
```

```
Hello, World!
```

`java` 명령에 `Hello.class`가 아니라 `Hello`를 주는 이유는 3.1절의 클래스 로더에 있다. `java`는 파일을 여는 명령이 아니라 "이 이름의 클래스를 찾아 실행하라"는 명령이고, 클래스 로더가 클래스패스에서 이름에 맞는 `.class` 파일을 찾는다. 클래스 이름을 주는 것이지 파일을 주는 것이 아니다.

{{< callout type="info" >}}
**Java 11부터는 `java Hello.java`처럼 소스를 바로 실행할 수 있다.** 내부적으로 메모리에서 컴파일한 뒤 실행하며, `.class` 파일은 남지 않는다. Java 22부터는 여러 소스 파일로 이루어진 프로그램도 같은 방식으로 실행된다. 한 번 돌려 보는 실험이나 스크립트에 어울리고, 배포할 프로그램은 여전히 컴파일해서 `.jar`로 묶는다.
{{< /callout >}}

## 6. main 메서드는 왜 그렇게 생겼나

```java
public static void main(String[] args)
```

JVM이 프로그램을 시작할 때 가장 먼저 호출하는 메서드다. 시그니처가 이렇게 정해진 데는 각 단어마다 이유가 있다.

| 키워드 | 이유 |
|:-------|:-----|
| `public` | 호출하는 쪽이 클래스 밖, 그것도 패키지 밖의 JVM이다. 접근 제한이 있으면 부를 수 없다 |
| `static` | JVM이 `main`을 부르는 시점에는 아직 아무 객체도 만들어지지 않았다. 객체 없이 부를 수 있어야 한다 |
| `void` | 프로그램의 결과는 반환값이 아니라 운영체제에 주는 종료 코드로 전한다. 정상 종료는 0, 예외로 끝나면 1, 직접 정하려면 `System.exit(n)` |
| `String[] args` | 명령행에서 넘긴 인자를 문자열 배열로 받는다 |

`java Hello` 뒤에 붙인 단어들이 `args`가 된다.

```java
public class ArgsExample {
    public static void main(String[] args) {
        for (int i = 0; i < args.length; i++) {
            System.out.println("args[" + i + "]: " + args[i]);
        }
    }
}
```

```bash
java ArgsExample Hello World Java
```

```
args[0]: Hello
args[1]: World
args[2]: Java
```

JVM이 `main`을 찾는 순서는 다음과 같다. `java Hello`를 실행하면 클래스 로더가 `Hello` 클래스를 찾아 올리고, 그 안에 `public static void main(String[])`이 있는지 확인한다. 없으면 `Main method not found` 오류로 끝나고, 있으면 명령행 인자를 배열로 묶어 넘기며 호출한다. 시그니처가 조금이라도 다르면 JVM은 그것을 진입점으로 인정하지 않는다. `main`이 특별한 것이 아니라, JVM이 약속된 모양의 메서드 하나만 찾도록 정해져 있는 것이다.

{{< callout type="info" >}}
**Java 25부터는 이 약속이 느슨해졌다.** JEP 512로 `void main()`처럼 `public`, `static`, `args`를 뺀 인스턴스 메서드도 진입점으로 인정되고, 클래스 선언 없이 메서드만 있는 소스 파일도 실행된다(컴팩트 소스 파일). Java 21부터 24까지는 같은 기능이 프리뷰라 `--enable-preview` 옵션이 필요했다. 배우는 단계에서는 편하지만, 실무 코드는 여전히 위의 온전한 형태를 쓴다.
{{< /callout >}}

## 7. 실행 과정 전체

```
1. java Hello 실행
       │
       ▼
2. JVM 시작
       │
       ▼
3. Class Loader가
   Hello.class 로드
       │
       ▼
4. 링크: 검증·준비·해석
   (Verifier: 보안 체크)
       │
       ▼
5. 클래스 초기화
   (static 필드, static 블록)
       │
       ▼
6. main 메서드 호출
       │
       ▼
7. main 종료 → JVM 종료
```

로드와 실행 사이에 **링크** 단계가 있다는 점이 중요하다. 클래스 로더가 읽어 온 바이트코드는 실행되기 전에 검증되고, `static` 필드의 자리가 마련되고, 다른 클래스를 가리키는 참조가 실제 위치로 연결된다. 그다음 `static` 초기화가 실행되고 나서야 `main`이 호출된다.

{{< callout type="info" >}}
**검증(Verifier)은 왜 필요한가.** 바이트코드는 파일이라서 `javac`를 거치지 않고 만들거나 고칠 수 있다. 검증기는 실행 전에 타입이 맞는지, 스택이 넘치거나 비지 않는지, 접근 권한을 어기지 않는지를 확인해 잘못된 바이트코드가 JVM을 망가뜨리지 못하게 막는다. 2절의 "가상 머신이 있어서 가능해진 것" 중 하나가 이 안전장치다. 기계어를 직접 실행하는 언어에는 이 단계가 없다.
{{< /callout >}}

## 8. 소스 파일과 클래스의 규칙

| 규칙 | 이유 |
|:-----|:-----|
| 모든 코드는 클래스 안에 있어야 한다 | JVM이 로드하고 실행하는 단위가 클래스다. 클래스 밖의 코드는 올릴 방법이 없다 |
| `public` 클래스 이름과 소스 파일 이름이 대소문자까지 같아야 한다 | 컴파일러와 클래스 로더가 이름으로 파일을 찾는다. `Hello`를 쓰면 `Hello.java`나 `Hello.class`를 찾는다 |
| `public` 클래스는 파일당 하나만 | 파일 이름은 하나인데 `public` 클래스가 둘이면 어느 쪽 이름을 따를지 정할 수 없다 |
| 클래스마다 `.class` 파일이 하나씩 생긴다 | 클래스 로더가 클래스 단위로 찾고 올린다. 3.1절의 게으른 로딩이 이 규칙 위에서 동작한다 |

```java
// Example.java
public class Example {              // 파일 이름과 같다
    public static void main(String[] args) {
        new Helper().help();
    }
}

class Helper {                      // public이 아니므로 파일 이름과 달라도 된다
    void help() {
        System.out.println("Helper class");
    }
}
```

```
Example.class
Helper.class    ← 클래스마다 따로 생긴다
```

`Helper`가 파일 이름과 달라도 되는 이유는 `public`이 아니기 때문이다. 같은 패키지 안에서만 쓰이는 클래스는 그 패키지의 소스를 함께 컴파일하면 컴파일러가 찾을 수 있다. 반면 `public` 클래스는 어디서든 이름만으로 참조되므로 이름으로 파일을 찾을 수 있어야 하고, 그래서 파일 이름이 묶인다. 컴파일 결과가 클래스마다 나뉘는 것도 같은 이유다. `Example`이 실행되다 `Helper`를 처음 쓰는 순간 클래스 로더는 `Helper.class`만 찾아 올리면 된다.

## 9. 요약

| 항목 | 핵심 | 왜 |
|:-----|:-----|:---|
| 출발 | 가전제품용 언어에서 웹으로 | 기기마다 다른 하드웨어에서 같은 프로그램을 돌려야 했다 |
| 바이트코드 | 실제 CPU가 아닌 JVM의 명령어 | 이식성의 짐을 프로그램이 아니라 JVM이 진다 |
| JVM | 클래스 로더, 런타임 데이터 영역, 실행 엔진 | 가상의 컴퓨터에도 로더, 메모리, CPU가 필요하다 |
| JIT | 자주 도는 코드만 실행 중에 기계어로 | 실행해 봐야 아는 정보로 더 잘 최적화한다 |
| JDK, JRE, JVM | 개발, 실행, 실행 엔진의 층 | 사용자가 다르다. Java 11부터 JRE 별도 배포 없음 |
| `java Hello` | 파일이 아니라 클래스 이름 | 클래스 로더가 이름으로 파일을 찾는다 |
| `main` | `public static void main(String[])` | JVM이 객체 없이, 밖에서, 약속된 모양만 찾는다 |
| 실행 과정 | 로드 → 링크(검증) → 초기화 → `main` | 검증은 가상 머신이라서 가능한 안전장치 |
| 파일 규칙 | 파일 이름 = `public` 클래스, 클래스마다 `.class` | 이름으로 찾고 클래스 단위로 올린다 |
