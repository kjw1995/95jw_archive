앞 장의 `em.persist(member)`는 "회원을 저장한다"로 읽힌다. 그런데 이 코드가 실행되는 순간 DB에는 아무 일도 일어나지 않는다. INSERT는 커밋 때 나간다. 그 사이에 회원 객체는 어디에 있는 걸까. 그 "어디"가 바로 **영속성 컨텍스트**다. JPA를 이해한다는 것은 결국 이 보이지 않는 공간이 무엇을 기억하고, 언제 생겼다가 언제 사라지는지를 아는 일이다. 이 장에서는 영속성 컨텍스트가 왜 필요한지, 안에 무엇이 들어 있는지, 그리고 그 수명이 누구에게 묶여 있는지를 본다.

---

## 1. 영속성 컨텍스트는 왜 있는가

JDBC로 개발할 때 애플리케이션과 DB 사이에는 아무것도 없다. SQL을 보내면 그 자리에서 실행되고, 결과 행은 객체로 복사된 뒤 잊힌다. 같은 행을 두 번 조회하면 객체가 두 개 생기고, 값을 바꿨는지는 개발자만 안다.

```
[JDBC]
 애플리케이션 ──── SQL ────▶ DB
              (즉시, 매번)

[JPA]
 애플리케이션 ─▶ 영속성 컨텍스트 ─▶ DB
                  기억하고 모아서
                  필요한 순간에 SQL
```

1장에서 JPA가 약속한 것들을 떠올려 보자. 같은 기본키면 같은 인스턴스를 돌려주고, INSERT를 모았다가 한 번에 보내고, 값이 바뀐 엔티티만 골라 UPDATE하고, 연관 객체는 실제로 쓸 때 가져온다. 이 네 가지에는 공통점이 있다. 전부 **호출과 호출 사이에 무언가를 기억해 두어야** 가능하다는 것이다. 어떤 엔티티를 이미 읽었는지, 읽었을 때 값이 무엇이었는지, 아직 보내지 않은 SQL이 무엇인지. JDBC처럼 매번 DB와 직접 대화하는 구조에서는 이 기억이 있을 자리가 없다.

그래서 JPA는 애플리케이션과 DB 사이에 기억을 담당하는 공간을 하나 둔다. JPA 명세의 정의를 옮기면 이렇다.

> 영속성 컨텍스트는 엔티티 인스턴스의 집합이다. 이 집합 안에서는 하나의 엔티티 식별자에 대해 인스턴스가 정확히 하나만 존재하며, 그 안의 엔티티와 생명주기는 엔티티 매니저가 관리한다.

두 가지가 핵심이다. **식별자당 인스턴스 하나**라는 유일성, 그리고 그 인스턴스들을 **JPA가 관리**한다는 사실. 앞으로 보게 될 모든 기능은 이 두 성질에서 나온다. "엔티티를 영구 저장하는 환경"이라는 흔한 번역은 이 공간이 DB로 가는 길목이라는 뜻이지, 이 공간 자체가 DB라는 뜻이 아니다.

## 2. persist는 "저장"이 아니다

```java
Member member = new Member();
member.setId(1L);
member.setUsername("홍길동");

em.persist(member);      // 영속성 컨텍스트에 등록. SQL 없음
em.contains(member);     // true. JPA가 관리하기 시작했다

tx.commit();             // 이때 INSERT
```

`persist`라는 이름은 "저장하다"가 아니라 "영속 상태로 만들다"에 가깝다. 이 호출이 하는 일은 객체를 영속성 컨텍스트에 넣고 관리 대상으로 삼는 것이다. INSERT SQL은 만들어져 대기열에 들어갈 뿐, DB로 나가는 것은 커밋 때다. 2장에서 `show_sql`을 켜 두라고 한 이유가 여기서 드러난다. `persist()` 다음 줄에 SQL 로그가 없고 `commit()` 다음에야 INSERT가 찍히는 것을 눈으로 보면, 영속성 컨텍스트가 중간에 있다는 사실이 실감 난다.

왜 이름을 이렇게 지었을까. JPA가 관심 있는 것은 "SQL이 나갔는가"가 아니라 "이 객체를 내가 관리하는가"이기 때문이다. 관리 대상이 된 객체는 **영속 상태**라 부르고, 이후 값이 바뀌면 JPA가 알아서 UPDATE를 만들고, 같은 기본키로 다시 찾으면 이 객체를 돌려준다. 관리 밖에 있는 객체에는 아무 일도 해 주지 않는다. 이 상태 변화를 정리한 것이 [Chapter 04. 엔티티 생명주기](../04-entity-lifecycle)다.

{{< callout type="info" >}}
`find()`도 마찬가지로 조회한 엔티티를 영속성 컨텍스트에 넣는다. 그래서 조회한 객체의 값을 바꾸기만 해도 커밋 때 UPDATE가 나간다. "저장한 적이 없는데 왜 UPDATE가 나가지?"라는 의문은, 조회 역시 영속성 컨텍스트에 등록하는 행위라는 것을 알면 풀린다.
{{< /callout >}}

## 3. 안을 들여다보면

영속성 컨텍스트는 클래스 이름이 아니다. `new PersistenceContext()` 같은 코드는 없다. Hibernate 안에서는 엔티티 매니저가 들고 있는 내부 자료구조일 뿐이고, 개발자는 `persist`, `find`, `flush`, `clear` 같은 엔티티 매니저의 메서드를 통해서만 간접적으로 만진다. 그래서 "논리적 개념"이라고 부른다. 하지만 안에 무엇이 있는지는 그려 볼 수 있다.

```
┌─────────────────────────────────┐
│         영속성 컨텍스트         │
│                                 │
│  1차 캐시 (Map)                 │
│  ┌──────┬──────────┬─────────┐  │
│  │ @Id  │ Entity   │ 스냅샷  │  │
│  ├──────┼──────────┼─────────┤  │
│  │ "1"  │ member1  │ 복사본  │  │
│  │ "2"  │ member2  │ 복사본  │  │
│  └──────┴──────────┴─────────┘  │
│                                 │
│  쓰기 지연 SQL 저장소           │
│  ┌───────────────────────────┐  │
│  │ INSERT ... │ UPDATE ...   │  │
│  └───────────────────────────┘  │
└─────────────────────────────────┘
```

### 3.1 1차 캐시: 기본키를 열쇠로 쓰는 맵

첫 번째 구성 요소는 **1차 캐시**다. 실체는 기본키를 키로, 엔티티 인스턴스를 값으로 갖는 맵이다. 1절의 정의에서 말한 "식별자당 인스턴스 하나"를 구현하는 가장 단순한 방법이 바로 맵이다. 같은 키로는 하나의 값만 들어가니까.

왜 하필 기본키인가. DB가 행을 구별하는 유일한 기준이 기본키이기 때문이다. 객체 세계의 `==`와 DB 세계의 기본키를 잇는 다리가 이 맵이고, 그래서 2장에서 `@Id` 없는 엔티티는 있을 수 없다고 했던 것이다. `find(Member.class, 1L)`은 DB보다 이 맵을 먼저 본다. 있으면 그대로 돌려주고, 없을 때만 SELECT를 실행해 결과를 맵에 넣은 뒤 돌려준다.

"1차"라는 이름은 엔티티 매니저 팩토리 수준에서 여러 영속성 컨텍스트가 공유하는 **2차 캐시**와 구분하기 위한 것이다. 1차 캐시는 영속성 컨텍스트 하나에 갇혀 있어서 트랜잭션이 끝나면 사라진다. 성능을 위한 캐시라기보다 작업 중인 엔티티를 올려 두는 작업대에 가깝다.

### 3.2 스냅샷: 변경 감지의 근거

맵에는 엔티티만 들어 있는 것이 아니다. Hibernate는 엔티티가 영속성 컨텍스트에 들어온 순간의 값을 복사한 **스냅샷**을 함께 저장한다. 커밋 시점에 각 엔티티의 현재 값과 스냅샷을 비교해, 달라진 것이 있는 엔티티에 대해서만 UPDATE를 만든다.

이것이 `em.update()`가 없는 이유의 나머지 절반이다. 개발자가 "바꿨다"고 알리지 않아도 되는 것은 JPA가 원본을 따로 기억하고 있기 때문이다. 기억이 없다면 비교할 대상도 없다.

### 3.3 쓰기 지연 SQL 저장소: 커밋까지 모아 두는 대기열

두 번째 구성 요소는 아직 보내지 않은 SQL을 순서대로 쌓아 두는 **쓰기 지연 SQL 저장소**다. `persist()`가 만든 INSERT, 변경 감지가 만든 UPDATE, `remove()`가 만든 DELETE가 여기 모였다가 플러시 때 한꺼번에 DB로 나간다.

왜 바로 보내지 않는가. 트랜잭션 안에서는 커밋 전까지 DB에 반영되든 안 되든 결과가 같기 때문이다. 어차피 커밋 때 반영될 것이라면 모아서 보내는 편이 네트워크 왕복이 적고, 롤백해야 할 때는 대기열을 비우기만 하면 된다. 앞 장에서 본 "트랜잭션이 없으면 SQL이 나갈 시점이 없다"는 말이 성립하는 이유도 이 구조에 있다.

### 3.4 이 구조가 주는 다섯 가지 이점

| 이점 | 근거가 되는 구성 요소 | 자세히 |
|:-----|:----------------------|:-------|
| 1차 캐시 | 기본키 맵 | [Chapter 05](../05-persistence-features) |
| 동일성 보장 | 기본키 맵 (식별자당 인스턴스 하나) | [Chapter 05](../05-persistence-features) |
| 쓰기 지연 | SQL 저장소 | [Chapter 05](../05-persistence-features) |
| 변경 감지 | 스냅샷 | [Chapter 05](../05-persistence-features) |
| 지연 로딩 | 프록시, 그리고 살아 있는 영속성 컨텍스트 | [Chapter 10](../10-proxy-loading) |

이점이라고 나열하면 서로 다른 다섯 기능처럼 보이지만, 위 그림의 두 자료구조에서 파생된 성질들이다. 자료구조를 이해하면 기능은 외울 필요가 없다.

## 4. 누가 만들고 언제 사라지는가

영속성 컨텍스트는 스스로 생기지 않는다. 엔티티 매니저를 만들 때 함께 만들어지고, 엔티티 매니저를 닫을 때 함께 사라진다. 2장에서 "엔티티 매니저는 상태를 갖는다"고 했는데, 그 상태가 바로 영속성 컨텍스트다.

```
EntityManagerFactory
        │  createEntityManager()
        ▼            커넥션 없음
  EntityManager ─── 영속성 컨텍스트
        │
        │  tx.begin()
        ▼            커넥션 획득
  SQL 실행 (플러시, 조회)
        │
        │  tx.commit() / rollback()
        ▼            커넥션 반환
  em.close()  → 영속성 컨텍스트 종료
```

### 4.1 왜 커넥션은 나중에 얻는가

엔티티 매니저를 만드는 순간에는 DB 커넥션을 얻지 않는다. 커넥션은 트랜잭션을 시작할 때 커넥션 풀에서 빌려 오고, 커밋이나 롤백이 끝나면 돌려준다. 커넥션 풀의 크기는 보통 열 개 안팎으로 작다. 요청마다 만드는 엔티티 매니저가 생성 시점부터 커넥션을 붙들면, 아직 DB에 갈 일이 없는 요청까지 풀을 차지해 정작 SQL을 보내야 하는 요청이 기다리게 된다. 값싼 자원인 엔티티 매니저는 미리 만들고, 비싼 자원인 커넥션은 필요한 순간에만 잠깐 빌리는 것이 합리적이다.

| 구분 | 만들어질 때 | 사라질 때 | 개수 |
|:-----|:------------|:----------|:-----|
| EntityManagerFactory | 애플리케이션 시작 | 애플리케이션 종료 | 영속성 유닛당 하나 |
| EntityManager | 작업 단위 시작 | `em.close()` | 작업 단위마다 |
| 영속성 컨텍스트 | 엔티티 매니저와 함께 | 엔티티 매니저와 함께 | 기본은 엔티티 매니저당 하나 |
| DB 커넥션 | 트랜잭션 시작 | 커밋·롤백 | 트랜잭션마다 잠깐 빌림 |

"기본은 엔티티 매니저당 하나"라는 단서가 붙은 이유는 다음 절에서 밝혀진다.

## 5. 스프링에서는: 트랜잭션이 곧 영속성 컨텍스트의 범위

순수 JPA에서는 개발자가 엔티티 매니저를 직접 만들고 닫으므로 영속성 컨텍스트의 수명도 개발자가 정한다. 스프링에서는 이 일을 컨테이너가 대신하는데, 그 기준이 **트랜잭션**이다. 스프링은 트랜잭션이 시작될 때 영속성 컨텍스트를 만들고, 트랜잭션이 끝날 때 플러시하고 닫는다. 이를 **트랜잭션 범위의 영속성 컨텍스트**라 한다.

```
  트랜잭션 시작        트랜잭션 커밋
       │                   │
       ▼                   ▼
  ┌────────────────────────────┐
  │      영속성 컨텍스트       │
  │  find() ─ save() ─ flush   │
  └────────────────────────────┘
       엔티티: 영속         준영속
```

### 5.1 왜 엔티티 매니저가 아니라 트랜잭션인가

스프링에서 `@PersistenceContext`로 주입받는 엔티티 매니저는 진짜가 아니라 프록시다. 이 프록시는 호출이 들어오면 현재 스레드의 트랜잭션을 확인하고, 그 트랜잭션에 묶인 진짜 엔티티 매니저와 영속성 컨텍스트로 요청을 넘긴다. 그래서 다음 두 가지가 성립한다.

- **같은 트랜잭션이면 같은 영속성 컨텍스트다.** 서비스 메서드 하나에서 회원 리포지토리와 주문 리포지토리를 차례로 불러도, 두 리포지토리가 각자 주입받은 엔티티 매니저가 달라도, 영속성 컨텍스트는 하나다. 그래서 회원 리포지토리가 조회한 엔티티를 주문 리포지토리가 같은 인스턴스로 본다.
- **트랜잭션이 다르면 영속성 컨텍스트도 다르다.** 같은 엔티티 매니저 필드를 여러 스레드가 동시에 써도, 스레드마다 트랜잭션이 다르니 영속성 컨텍스트가 섞이지 않는다. 2장에서 "스프링에서는 엔티티 매니저를 공유해도 안전하다"고 한 근거가 이것이다.

즉 스프링에서는 엔티티 매니저 1개가 아니라 **트랜잭션 1개당 영속성 컨텍스트 1개**다. 4절의 표에 "기본은"이라는 단서를 붙인 이유다.

### 5.2 트랜잭션이 끝나면 엔티티는 어떻게 되는가

트랜잭션이 커밋되면 영속성 컨텍스트는 플러시된 뒤 닫힌다. 그 안에 있던 엔티티는 관리에서 벗어나 **준영속 상태**가 된다. 서비스 메서드가 반환한 엔티티를 컨트롤러가 받았을 때, 그 객체는 이미 영속성 컨텍스트 밖에 있다. 값을 바꿔도 UPDATE가 나가지 않고, 아직 로딩되지 않은 연관 객체를 건드리면 `LazyInitializationException`이 난다. 프록시가 SELECT를 실행하려 해도 돌아갈 영속성 컨텍스트가 없기 때문이다.

```java
@Service
public class MemberService {

    @Transactional
    public Member find(Long id) {
        return memberRepository.findById(id).orElseThrow();
    }   // 커밋 → 영속성 컨텍스트 종료 → 반환된 member는 준영속
}

@RestController
public class MemberController {

    @GetMapping("/members/{id}/team")
    public String teamName(@PathVariable Long id) {
        Member member = memberService.find(id);
        return member.getTeam().getName();   // 준영속 상태에서 지연 로딩
    }
}
```

관리 밖으로 나간 엔티티를 다루는 방법인 `detach`, `clear`, `merge`는 [Chapter 06. 플러시](../06-flush-and-detached)에서 정리한다.

{{< callout type="warning" >}}
**위 코드가 실제로 예외를 내는지는 OSIV 설정에 달려 있다.** 스프링 부트는 기본값으로 OSIV(Open Session In View)를 켜 두는데, 이 설정은 영속성 컨텍스트를 트랜잭션이 끝난 뒤에도 HTTP 응답이 나갈 때까지 살려 둔다. 그래서 컨트롤러에서도 지연 로딩이 된다. 대신 그 사이에 얻은 DB 커넥션을 요청이 끝날 때까지 붙들 수 있어, 트래픽이 몰리면 커넥션 풀이 마른다. 이 저장소의 [JPA + MyBatis 혼용 시 OSIV 커넥션 풀 고갈 문제](../../../../blog/troubleshooting/jpa-mybatis-osiv)가 바로 그 사례다. 영속성 컨텍스트의 범위를 정확히 알아야 이 설정을 판단할 수 있다.
{{< /callout >}}

영속성 컨텍스트가 "언제부터 언제까지 살아 있는가"는 JPA에서 생기는 문제의 절반과 직결된다. 값을 바꿨는데 반영이 안 되는 것도, 지연 로딩이 예외를 내는 것도, 커넥션이 모자라는 것도 결국 범위 문제다. 다음 장부터는 이 공간 안에서 엔티티가 어떤 상태를 오가는지, 그리고 각 기능이 정확히 어떻게 동작하는지를 하나씩 본다.

## 요약

| 항목 | 핵심 |
|:-----|:-----|
| 왜 있는가 | 호출 사이에 엔티티·스냅샷·SQL을 기억하는 공간. 1장의 약속들이 여기서 나온다 |
| 정의 | 식별자당 인스턴스 하나. JPA가 관리하는 엔티티의 집합 |
| `persist()` | 저장이 아니라 관리 시작. SQL은 플러시 때 |
| 1차 캐시 | 기본키 → 엔티티 맵. 동일성과 캐시의 근거 |
| 스냅샷 | 들어온 순간의 값. 변경 감지의 근거 |
| SQL 저장소 | 커밋까지 SQL을 모아 두는 대기열 |
| 수명 | 엔티티 매니저와 함께 생기고 사라진다 |
| 커넥션 | 트랜잭션 시작 때 빌리고 끝날 때 반환 |
| 스프링 | 트랜잭션 1개 = 영속성 컨텍스트 1개. 끝나면 준영속 |
| OSIV | 영속성 컨텍스트를 응답까지 연장. 커넥션 점유에 주의 |

### 핵심 코드

```java
EntityManager em = emf.createEntityManager();   // 영속성 컨텍스트 생성
EntityTransaction tx = em.getTransaction();

tx.begin();                                     // 커넥션 획득
em.persist(member);                             // 등록. SQL 없음
em.contains(member);                            // true
Member same = em.find(Member.class, 1L);        // 1차 캐시에서 반환
tx.commit();                                    // 플러시 → INSERT, 커넥션 반환

em.close();                                     // 영속성 컨텍스트 종료
```
