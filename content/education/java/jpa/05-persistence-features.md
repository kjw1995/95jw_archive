[Chapter 03](../03-persistence-context)에서 영속성 컨텍스트 안에 기본키 맵과 스냅샷과 SQL 저장소가 있다고 했고, [Chapter 04](../04-entity-lifecycle)에서 JPA는 영속 상태의 객체에만 일한다고 했다. 이 장은 그 "일"의 내용이다. 1차 캐시, 동일성 보장, 쓰기 지연, 변경 감지, 삭제. 각 기능이 정확히 어떤 순서로 동작하는지, 왜 그렇게 설계됐는지, 그리고 그 설계가 실무에서 어떤 결과를 낳는지를 본다. 앞 장들이 "무엇이 있는가"였다면 이 장은 "그래서 무슨 일이 일어나는가"다.

## 1. 1차 캐시

### 1.1 find()는 이 순서로 움직인다

```
em.find(Member.class, 1L)
        │
        ▼
   1차 캐시 조회
   ┌────┴────┐
  있음      없음
   │         │
   │         ▼
   │     SELECT 실행
   │         │
   │         ▼
   │     캐시에 저장
   │         │
   └────┬────┘
        ▼
  영속 엔티티 반환
```

```java
Member member = new Member();
member.setId(1L);
member.setUsername("회원1");
em.persist(member);                          // 1차 캐시에 들어간다

Member a = em.find(Member.class, 1L);        // 캐시에 있다 → SQL 없음
Member b = em.find(Member.class, 2L);        // 캐시에 없다 → SELECT → 캐시에 저장
Member c = em.find(Member.class, 2L);        // 이제 캐시에 있다 → SQL 없음
```

`find()`는 언제나 1차 캐시를 먼저 본다. 있으면 그 인스턴스를 돌려주고, 없을 때만 SELECT를 실행한 뒤 결과를 캐시에 넣고 돌려준다. 그래서 방금 `persist()`한 회원을 같은 트랜잭션에서 `find()`하면 DB에 INSERT조차 나가지 않은 상태인데도 그 객체가 돌아온다. DB가 아니라 캐시가 대답했기 때문이다.

### 1.2 왜 "캐시"라기보다 작업대인가

1차 캐시라는 이름 때문에 성능 최적화 장치로 오해하기 쉽다. 그런데 이 캐시는 영속성 컨텍스트 하나에 갇혀 있다. 스프링에서는 트랜잭션 하나가 그 범위이므로, 캐시의 수명은 요청 하나를 넘지 못한다. 요청 A가 조회한 회원을 요청 B가 재사용할 방법은 없다. 한 트랜잭션 안에서 같은 엔티티를 두 번 이상 조회하는 일 자체가 그리 흔하지 않으니, DB 조회 횟수를 줄이는 효과는 생각보다 작다.

1차 캐시의 진짜 역할은 성능이 아니라 **일관성**이다. 같은 기본키에 대해 인스턴스를 하나만 유지하고, 그 인스턴스의 원본을 기억하고, 변경을 추적한다. 이 장의 나머지 기능은 전부 1차 캐시가 있기에 가능하다. 여러 요청이 공유하는 진짜 캐시가 필요하다면 엔티티 매니저 팩토리 수준의 **2차 캐시**를 따로 켜야 한다.

### 1.3 JPQL은 1차 캐시를 먼저 보지 않는다

`find()`와 달리 JPQL은 항상 SQL을 실행한다. 이유는 단순하다. "이름이 홍길동인 회원"이 캐시에 몇 명이나 있는지, 캐시에 없는 회원이 DB에 더 있는지는 DB에 물어보지 않고는 알 수 없기 때문이다. 기본키 하나로 찾는 `find()`만이 캐시에서 답을 확정할 수 있다.

그렇다면 JPQL로 조회한 행이 이미 1차 캐시에 있는 엔티티라면 어떻게 될까. 이때는 DB에서 읽어 온 값을 버리고 **캐시에 있던 인스턴스를 돌려준다**. 식별자당 인스턴스 하나라는 규칙이 JPQL에도 적용되는 것이다. 새 객체를 만들어 돌려주면 같은 회원이 두 인스턴스가 되어 버린다.

| 구분 | 1차 캐시를 먼저 보는가 | SQL 실행 | 결과가 이미 캐시에 있으면 |
|:-----|:-----------------------|:---------|:--------------------------|
| `find()` | 본다 | 캐시에 없을 때만 | 캐시 인스턴스 반환 |
| JPQL | 안 본다 | 항상 | DB 값을 버리고 캐시 인스턴스 반환 |

{{< callout type="info" >}}
JPQL이 실행되기 직전에 영속성 컨텍스트가 먼저 **플러시**된다는 점도 같은 맥락이다. 캐시를 거치지 않고 DB에 직접 묻는 이상, 아직 안 나간 INSERT나 UPDATE가 있으면 결과가 틀리기 때문이다. 플러시 시점은 [Chapter 06. 플러시](../06-flush-and-detached)에서 다룬다.
{{< /callout >}}

## 2. 동일성 보장

```java
Member a = em.find(Member.class, 1L);
Member b = em.find(Member.class, 1L);

a == b;   // true
```

1차 캐시가 기본키를 키로 하는 맵이므로, 같은 기본키로 두 번 찾으면 같은 값이 나온다. 동일성 보장은 별도의 기능이 아니라 맵의 성질이다. 1장에서 JDBC는 같은 행을 두 번 읽으면 두 객체가 생긴다고 했는데, JPA는 그 둘을 하나로 묶어 준다.

### 2.1 왜 이것이 격리 수준과 연결되는가

이 성질은 애플리케이션 차원에서 **반복 가능한 읽기**(REPEATABLE READ)를 흉내 낸다. DB의 격리 수준이 READ COMMITTED라면 한 트랜잭션 안에서 같은 행을 두 번 읽었을 때 그 사이 다른 트랜잭션이 커밋한 값이 보일 수 있다. 그런데 JPA를 거치면 두 번째 `find()`는 DB에 가지 않고 캐시의 인스턴스를 돌려주므로, 다른 트랜잭션이 무엇을 했든 처음 읽은 값이 유지된다.

정확히 말하면 이 보장은 **엔티티 하나의 상태**에 대한 것이다. JPQL로 "나이가 20 이상인 회원"을 두 번 조회하면 그 사이 추가된 회원이 결과에 새로 나타날 수 있다. 다만 결과에 포함된 엔티티 중 이미 캐시에 있던 것은 1.3절에서 봤듯 캐시 인스턴스가 돌아오므로, 개별 엔티티의 값은 여전히 처음 읽은 그대로다. 행의 집합은 바뀔 수 있어도 행의 내용은 바뀌지 않는 셈이다.

{{< callout type="info" >}}
동일성은 영속성 컨텍스트 하나 안에서만 성립한다. 트랜잭션이 다르면 같은 회원이라도 `==`는 `false`다. 컨텍스트를 넘어 비교해야 한다면 `equals()`와 `hashCode()`를 식별자 기준으로 정의해야 하고, 컬렉션에 담아 다룰 때 특히 중요하다.
{{< /callout >}}

## 3. 트랜잭션을 지원하는 쓰기 지연

### 3.1 동작

```
tx.begin()
   │
em.persist(A) ─▶ 저장소 [INSERT A]
em.persist(B) ─▶ 저장소 [INSERT A, B]
   │              (DB로는 아직 안 간다)
tx.commit()
   │  flush
   ▼
INSERT A, INSERT B를 한 번에 전송
   │
   ▼
DB 커밋
```

```java
tx.begin();

em.persist(memberA);   // INSERT 생성 → 쓰기 지연 SQL 저장소
em.persist(memberB);   // INSERT 생성 → 쓰기 지연 SQL 저장소
// 여기까지 DB에는 아무것도 가지 않았다

tx.commit();           // 플러시 → 모아 둔 SQL 전송 → DB 커밋
```

`persist()`는 INSERT SQL을 만들어 저장소에 넣는 데서 멈춘다. 저장소의 SQL은 플러시 때 순서대로 DB에 전송되고, 그다음 DB 트랜잭션이 커밋된다. 커밋이 곧 플러시를 부른다는 점이 중요하다. 개발자가 플러시를 따로 부르지 않아도 커밋 직전에 반드시 한 번은 일어난다.

### 3.2 왜 미뤄도 되는가

트랜잭션의 성질 때문이다. 커밋 전까지는 어떤 SQL도 다른 트랜잭션에 보이지 않고, 롤백하면 전부 없던 일이 된다. 그렇다면 INSERT를 `persist()` 시점에 보내든 커밋 직전에 보내든, 트랜잭션 밖에서 관찰되는 결과는 같다. 결과가 같다면 늦게 모아서 보내는 편이 유리하다. DB 왕복 횟수가 줄고, 여러 SQL을 한 묶음으로 전송할 수 있다.

"트랜잭션을 지원하는"이라는 수식어가 붙는 이유가 여기에 있다. 쓰기 지연은 트랜잭션이 있어야만 성립한다. 트랜잭션 없이는 "커밋 직전"이라는 시점이 없고, 모아 둔 SQL을 내보낼 계기도 없다. 롤백이 값싼 것도 같은 이유다. 아직 DB에 나간 것이 없으니 저장소를 비우기만 하면 된다.

### 3.3 실행 순서는 호출 순서가 아니다

여기서 많이들 놀라는 사실이 있다. 플러시 때 SQL이 나가는 순서는 `persist()`, `remove()`를 부른 순서가 아니다. Hibernate는 SQL을 종류별로 묶어서 **INSERT → UPDATE → 컬렉션 변경 → DELETE** 순으로 실행한다. 같은 종류끼리는 호출 순서를 지킨다.

```java
Member old = em.find(Member.class, 1L);   // 로그인 ID "kim"
em.remove(old);                           // DELETE 예약

Member fresh = new Member();
fresh.setId(2L);
fresh.setLoginId("kim");                  // 같은 유니크 값
em.persist(fresh);                        // INSERT 예약

tx.commit();   // INSERT가 DELETE보다 먼저 나간다 → 유니크 제약 위반
```

왜 이렇게 묶는가. 같은 종류의 SQL을 연달아 보내야 JDBC 배치로 묶을 수 있기 때문이다. INSERT와 DELETE가 번갈아 나가면 배치가 매번 끊긴다. 성능을 위한 설계인데, 위처럼 삭제와 등록 사이에 제약 조건이 걸려 있으면 순서가 문제가 된다. 이럴 때는 삭제 직후 `em.flush()`를 호출해 DELETE를 먼저 내보내면 된다. 순서가 중요한 순간에는 플러시로 경계를 긋는다고 기억하면 된다.

{{< callout type="info" >}}
모아 둔 INSERT를 실제로 한 번의 왕복으로 보내려면 `hibernate.jdbc.batch_size`를 설정해야 한다. 설정이 없으면 순서만 미뤄질 뿐 SQL은 한 건씩 나간다. 여러 엔티티 타입을 섞어 저장한다면 `hibernate.order_inserts=true`로 타입별로 다시 묶을 수 있다. 단, 기본키 전략이 IDENTITY인 엔티티는 [Chapter 04](../04-entity-lifecycle)에서 본 이유로 `persist()` 즉시 INSERT가 나가므로 배치에 묶이지 않는다.
{{< /callout >}}

## 4. 변경 감지

### 4.1 동작

```java
tx.begin();

Member member = em.find(Member.class, 1L);   // 스냅샷이 찍힌다
member.setUsername("변경");
member.setAge(20);
// em.update(member) 같은 호출은 없다

tx.commit();   // 플러시 → 스냅샷과 비교 → UPDATE
```

```
 flush 시점
     │
     ▼
 1차 캐시의 모든 영속 엔티티에 대해
 ┌──────────────┬──────────────┐
 │  현재 값     │   스냅샷     │
 │ name = "B"   │ name = "A"   │
 │ age  = 20    │ age  = 20    │
 └──────┬───────┴──────┬───────┘
        └──── 비교 ────┘
               │ 다르다
               ▼
    UPDATE ... SET name=?, age=?
               │
               ▼
        쓰기 지연 SQL 저장소
```

플러시가 일어나면 JPA는 1차 캐시의 영속 엔티티를 하나씩 꺼내 현재 값과 스냅샷을 필드 단위로 비교한다. 다른 곳이 하나라도 있으면 그 엔티티에 대한 UPDATE를 만들어 쓰기 지연 SQL 저장소에 넣고, 저장소의 SQL이 DB로 나간다. 변경 감지는 이렇게 쓰기 지연 위에 얹혀 있다.

### 4.2 왜 setter가 아니라 값을 보는가

JPA는 setter 호출을 가로채지 않는다. 엔티티는 평범한 자바 객체이고, 필드를 직접 바꾸든 setter로 바꾸든 JPA는 알 수 없다. 대신 처음 상태를 복사해 두었다가 나중에 비교한다. 이 방식이 낳는 결과 두 가지를 알아 두면 좋다.

첫째, **같은 값으로 바꾸면 UPDATE가 나가지 않는다.** `member.setUsername(member.getUsername())`처럼 값이 그대로면 스냅샷과 차이가 없으니 변경으로 치지 않는다. 둘째, **엔티티 안의 객체를 제자리에서 바꿔도 감지된다.** 스냅샷은 값의 복사본이라, 컬렉션에 요소를 추가하거나 날짜 객체의 값을 바꾸는 식의 변경도 비교에서 드러난다.

### 4.3 왜 모든 컬럼을 UPDATE하는가

`username` 하나만 바꿨는데 실행되는 SQL은 이렇다.

```sql
UPDATE MEMBER
   SET NAME = ?, AGE = ?
 WHERE ID = ?
```

바꾸지 않은 `AGE`까지 포함된다. 낭비처럼 보이지만 의도된 설계다. 바뀐 컬럼만 넣으면 어떤 필드를 바꿨느냐에 따라 UPDATE 문의 모양이 매번 달라진다. 모든 컬럼을 넣으면 엔티티마다 UPDATE 문이 **하나로 고정**되므로, 애플리케이션이 시작될 때 미리 만들어 두고 재사용할 수 있다. DB 쪽에서도 같은 SQL이 반복되면 파싱 결과와 실행 계획을 캐시에서 꺼내 쓴다. 문장 하나를 조금 길게 보내는 대가로 양쪽의 준비 비용을 없애는 선택이다.

이 설계가 불리해지는 경우도 있다. 컬럼이 수십 개거나 큰 데이터를 담은 컬럼이 있으면 안 바뀐 값까지 매번 보내는 비용이 커진다. 그럴 때는 Hibernate 전용 `@DynamicUpdate`를 붙여 바뀐 컬럼만 UPDATE하게 할 수 있다. 대신 SQL을 플러시 때마다 새로 만들어야 하므로, 작은 엔티티에 붙이면 오히려 손해다.

```java
@Entity
@org.hibernate.annotations.DynamicUpdate
public class Member { ... }
```

### 4.4 변경 감지의 비용

비교는 공짜가 아니다. 플러시 한 번에 **영속 엔티티 수 × 필드 수**만큼의 비교가 일어난다. 엔티티 백 개를 조회한 트랜잭션이라면 커밋 때 백 개를 전부 훑는다. 값을 바꾼 것이 하나도 없어도 마찬가지다. JPA는 무엇이 바뀌었는지 모르니 전부 확인하는 수밖에 없다.

여기서 두 가지 실무 습관이 나온다. 첫째, 조회만 하는 트랜잭션에는 `@Transactional(readOnly = true)`를 붙인다. 스프링은 이 힌트를 받으면 Hibernate에게 읽기 전용 세션임을 알리고, Hibernate는 스냅샷을 만들지 않고 커밋 때 변경 감지도 건너뛴다. 메모리와 CPU를 함께 아낀다. 둘째, 대량 처리에서는 [Chapter 04](../04-entity-lifecycle)에서 본 것처럼 일정 건수마다 `flush()`와 `clear()`로 컨텍스트를 비워 비교 대상을 줄인다.

{{< callout type="warning" >}}
변경 감지는 **영속 상태의 엔티티**에만 일어난다. `detach()`했거나 트랜잭션이 끝나 준영속이 된 객체는 스냅샷도 없고 비교 대상도 아니다. 값을 바꿨는데 UPDATE가 안 나간다면 먼저 그 객체가 아직 영속 상태인지, 그리고 지금 트랜잭션 안에 있는지를 확인해야 한다.
{{< /callout >}}

## 5. 엔티티 삭제

```java
Member member = em.find(Member.class, 1L);   // 삭제할 대상을 먼저 영속 상태로
em.remove(member);                           // DELETE 생성 → 쓰기 지연 SQL 저장소
em.contains(member);                         // false
tx.commit();                                 // 플러시 → DELETE 전송
```

삭제도 쓰기 지연 위에서 동작한다. `remove()`는 DELETE를 만들어 저장소에 넣고 엔티티를 삭제 예약 상태로 표시할 뿐, DB에는 커밋 때 나간다. 삭제할 대상을 먼저 조회해야 하는 이유는 [Chapter 04](../04-entity-lifecycle)에서 봤듯 영속성 컨텍스트가 관리하는 객체만 삭제 예약을 할 수 있기 때문이다.

커밋이 끝난 뒤의 객체는 재사용하지 않는 것이 좋다. 컨텍스트에서 완전히 빠져나간 이 객체는 식별자만 남은 껍데기라서, 다시 `persist()`하면 같은 식별자로 INSERT를 시도하거나 준영속 취급을 받아 예외가 난다. 연관된 엔티티를 함께 지우는 영속성 전이와 고아 객체 제거는 [Chapter 10. 프록시](../10-proxy-loading)에서 다룬다.

## 요약

| 특징 | 동작 | 왜 그렇게 설계됐나 |
|:-----|:-----|:-------------------|
| 1차 캐시 | `find()`는 캐시 먼저, JPQL은 DB 먼저 | 기본키 조회만 캐시에서 답을 확정할 수 있다 |
| 동일성 보장 | 같은 기본키 → 같은 인스턴스 | 기본키 맵의 성질. 애플리케이션 수준 반복 가능 읽기 |
| 쓰기 지연 | SQL을 모아 커밋 직전에 전송 | 커밋 전까지는 언제 보내도 결과가 같다 |
| 실행 순서 | INSERT → UPDATE → DELETE | 같은 종류끼리 묶어야 배치가 된다 |
| 변경 감지 | 플러시 때 스냅샷과 비교 | setter를 가로채지 않고 값을 본다 |
| 전체 컬럼 UPDATE | 바뀌지 않은 컬럼도 포함 | SQL을 고정해 재사용한다 |
| 삭제 | `remove()`는 예약, 커밋 때 DELETE | 쓰기 지연의 일부 |

### 핵심 코드

```java
tx.begin();

Member a = em.find(Member.class, 1L);   // SELECT → 1차 캐시 저장, 스냅샷
Member b = em.find(Member.class, 1L);   // 캐시 반환, SQL 없음
a == b;                                 // true

a.setUsername("변경");                  // 변경 감지 대상

Member c = em.find(Member.class, 2L);
em.remove(c);                           // DELETE 예약

em.persist(newMember);                  // INSERT 예약

tx.commit();   // 플러시: INSERT → UPDATE → DELETE 순으로 전송 → 커밋
```
