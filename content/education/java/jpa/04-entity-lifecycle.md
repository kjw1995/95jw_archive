[Chapter 03. 영속성 컨텍스트](../03-persistence-context)에서 영속성 컨텍스트가 무엇을 기억하는지를 봤다. 그 기억의 관점에서 보면 모든 엔티티 객체는 네 가지 중 하나의 상태에 있다. 컨텍스트가 모르는 객체, 관리하는 객체, 한때 관리했던 객체, 지우기로 한 객체. 같은 `member.setUsername("...")` 한 줄이 어떤 상태에서는 UPDATE가 되고 어떤 상태에서는 아무 일도 일으키지 않는다. JPA에서 "분명히 바꿨는데 반영이 안 된다"는 문제의 대부분은 이 상태를 잘못 짚은 데서 나온다. 이 장에서는 네 상태가 왜 구분되는지, 무엇이 상태를 바꾸는지, 각 상태에서 JPA가 무엇을 해 주고 무엇을 해 주지 않는지를 본다.

---

## 1. 왜 상태가 필요한가

JPA가 해 주는 일은 전부 자동이다. 바뀐 값을 찾아 UPDATE를 만들고, 같은 기본키면 같은 인스턴스를 돌려주고, 커밋 때 SQL을 내보낸다. 그런데 이 자동 처리에는 조건이 하나 있다. **영속성 컨텍스트가 아는 객체여야 한다.** JPA는 애플리케이션의 모든 객체를 감시하지 않는다. 엔티티 매니저를 거쳐 컨텍스트에 들어온 객체만 관리한다.

```
 ┌───── 영속성 컨텍스트 ─────┐
 │    영속    │  삭제 예약   │
 └────────────┴──────────────┘
   → 커밋 때 JPA가 SQL을 만든다

   비영속, 준영속 (컨텍스트 밖)
   → JPA는 아무것도 하지 않는다
```

상태란 결국 "컨텍스트가 이 객체에 대해 커밋 때 무엇을 할 것인가"에 대한 답이다.

| 상태 | 컨텍스트가 아는가 | 커밋 때 하는 일 |
|:-----|:------------------|:----------------|
| 비영속 (new) | 모른다 | 없음 |
| 영속 (managed) | 안다 | 새로 등록됐으면 INSERT, 값이 바뀌었으면 UPDATE |
| 준영속 (detached) | 알았지만 지금은 모른다 | 없음 |
| 삭제 (removed) | 안다. 지우기로 예약 | DELETE |

상태를 바꾸는 것은 엔티티 매니저의 메서드뿐이다. 객체를 만들거나 값을 바꾸는 것만으로는 상태가 변하지 않는다.

```
   new Member()
       │
       ▼
  ┌─────────┐           DB
  │  비영속 │           │
  └────┬────┘           │
       │ persist()      │ find()
       ▼                ▼
   ┌─────────────────────────┐
   │          영속           │
   └───┬──────────────┬──────┘
       │ detach()     │ remove()
       │ clear()      │
       │ close()      ▼
       ▼         ┌─────────┐
  ┌─────────┐    │  삭제   │
  │  준영속 │    └─────────┘
  └────┬────┘
       │ merge()
       ▼
  영속 (새 인스턴스)
```

화살표 하나하나에 이유가 있다. 비영속에서 영속으로 가는 길은 `persist()` 하나뿐이고, 조회(`find()`, JPQL)는 DB에서 곧바로 영속 상태의 객체를 만들어 낸다. 영속에서 준영속으로는 세 가지 방법으로 갈 수 있지만 준영속에서 영속으로 되돌아오는 길은 `merge()` 하나이며, 그마저도 원래 객체가 아니라 **새 인스턴스**가 돌아온다. 삭제 상태에서 나가는 화살표는 그림에 없다. 아래에서 각 상태를 하나씩 보면서 왜 그런지 설명한다.

---

## 2. 비영속: 컨텍스트가 모르는 객체

```java
Member member = new Member();
member.setId(1L);
member.setUsername("회원1");
// 아직 아무 메서드도 거치지 않았다 → 비영속
```

`new`로 만든 객체는 그냥 자바 객체다. `@Entity`가 붙어 있어도 JPA는 이 객체의 존재를 모른다. 여기서 흔한 오해 하나를 짚고 가자. 비영속은 "DB에 없다"는 뜻이 아니라 **영속성 컨텍스트가 모른다**는 뜻이다. 위 객체의 기본키 1번이 DB에 이미 있을 수도 있다. JPA는 확인하지 않는다. 확인할 이유가 없기 때문이다. 이 객체는 아직 JPA에게 넘겨진 적이 없다.

이 구분이 중요한 순간이 있다. DB에 이미 있는 회원과 같은 기본키로 객체를 새로 만들어 `persist()`하면 어떻게 될까. JPA는 이 객체를 모르므로 새 엔티티로 받아들이고 INSERT를 예약한다. 결과는 커밋 시점의 기본키 중복 오류다. 이미 있는 행을 고치고 싶다면 객체를 새로 만드는 것이 아니라 `find()`로 가져와서 고쳐야 한다. 그래야 컨텍스트가 그 객체를 알고, 바뀐 값을 UPDATE로 만들어 준다.

## 3. 영속: 컨텍스트가 관리하는 객체

```java
// 길 1: persist()
em.persist(member);                            // 비영속 → 영속

// 길 2: 조회. 결과는 처음부터 영속이다
Member found = em.find(Member.class, 1L);
List<Member> list = em.createQuery("select m from Member m", Member.class)
                      .getResultList();

// 길 3: merge()의 반환값 (4절에서)
```

영속 상태는 영속성 컨텍스트의 1차 캐시에 들어 있는 상태다. 3장에서 본 두 자료구조가 이 객체에 대해 일하기 시작한다. 스냅샷이 찍히고, 같은 기본키의 `find()`는 이 인스턴스를 돌려주고, 값이 바뀌면 커밋 때 UPDATE가 나가고, 연관 객체는 필요한 순간에 로딩된다. JPA의 모든 기능은 영속 상태를 전제로 한다.

### 3.1 왜 조회 결과도 영속인가

`find()`나 JPQL로 가져온 객체는 `persist()`를 부른 적이 없는데도 영속 상태다. 그래야만 3장의 "식별자당 인스턴스 하나"가 지켜지기 때문이다. 조회한 객체를 컨텍스트에 넣어 두지 않으면 같은 회원을 두 번 조회했을 때 두 인스턴스가 생기고, 값을 고쳤을 때 JPA가 그 사실을 알 방법도 없다. 조회는 "DB에서 읽어 컨텍스트에 등록한다"는 행위이고, 영속은 그 등록의 결과다.

```java
Member a = em.find(Member.class, 1L);   // SELECT, 컨텍스트에 등록
Member b = em.find(Member.class, 1L);   // 컨텍스트에서 반환
a == b;                                 // true

a.setUsername("변경");                  // 스냅샷과 달라졌다
tx.commit();                            // UPDATE
```

### 3.2 왜 영속 상태에는 식별자가 반드시 있는가

1차 캐시는 기본키를 키로 쓰는 맵이다. 키가 없는 값은 맵에 넣을 수 없다. 그래서 영속 상태의 엔티티는 예외 없이 식별자를 갖는다. 개발자가 직접 넣든, `@GeneratedValue`로 JPA가 채우든 마찬가지다.

이 사실이 낳는 유명한 예외가 하나 있다. 기본키를 DB가 만들어 주는 IDENTITY 전략에서는 INSERT를 실행해야 키 값을 알 수 있다. 그런데 영속 상태가 되려면 키가 있어야 하니, JPA는 이 경우에만 `persist()` 시점에 INSERT를 바로 보낸다. 쓰기 지연이 동작하지 않는 이유가 "최적화를 포기해서"가 아니라 "영속 상태의 정의를 지키기 위해서"인 셈이다. 키 전략별 차이는 [Chapter 07. 엔티티 매핑](../07-entity-mapping)에서 다룬다.

{{< callout type="info" >}}
`persist()`는 "INSERT를 실행하라"가 아니라 "이 객체를 관리하라"는 요청이다. 그래서 `persist()` 뒤에 값을 더 바꿔도 된다. persist 시점의 값으로 INSERT가 예약되고, 그 뒤의 변경은 변경 감지가 UPDATE로 뒤따라 보낸다. 결과적으로 DB에는 최종 값이 남는다.
{{< /callout >}}

## 4. 준영속: 한때 관리했던 객체

```java
Member member = em.find(Member.class, 1L);   // 영속
em.detach(member);                           // 준영속
member.setUsername("변경됨");                // 바꿔도
tx.commit();                                 // UPDATE 없음
```

준영속은 영속 상태였던 객체가 컨텍스트에서 떨어져 나간 상태다. 객체 자체는 멀쩡하다. 필드 값도 그대로고 식별자도 있다. 달라진 것은 단 하나, 영속성 컨텍스트가 더 이상 이 객체를 추적하지 않는다는 점이다. 그래서 값을 바꿔도 UPDATE가 나가지 않고, 아직 로딩되지 않은 연관 객체를 건드리면 `LazyInitializationException`이 난다. 프록시가 SELECT를 실행하려면 컨텍스트가 있어야 하는데 이제 없기 때문이다.

### 4.1 준영속이 되는 길

| 방법 | 범위 | 언제 쓰는가 |
|:-----|:-----|:------------|
| `em.detach(e)` | 엔티티 하나 | 특정 엔티티만 변경 감지에서 빼고 싶을 때 |
| `em.clear()` | 컨텍스트 전체 | 대량 처리 중 1차 캐시를 비워 메모리를 지킬 때 |
| `em.close()` | 컨텍스트 종료 | 작업 단위가 끝났을 때 |
| 트랜잭션 종료 | 컨텍스트 전체 | 스프링에서 서비스 메서드가 반환될 때 (3장) |

실무에서 가장 자주 마주치는 것은 표의 마지막 줄이다. 스프링에서는 트랜잭션이 끝나면 컨텍스트가 닫히므로, 서비스 밖으로 나온 엔티티는 전부 준영속이다. 개발자가 `detach()`를 부른 적이 없는데도 그렇다. 컨트롤러에서 엔티티 값을 바꿨는데 반영이 안 되는 이유, 뷰에서 지연 로딩이 터지는 이유가 모두 여기에 있다.

`clear()`가 필요한 이유는 좀 더 실용적이다. 회원 백만 명을 한 트랜잭션에서 등록하면 1차 캐시에 백만 개의 엔티티와 스냅샷이 쌓인다. 커밋 전까지 아무것도 버려지지 않으니 메모리가 바닥난다. 그래서 일정 건수마다 `flush()`로 SQL을 내보내고 `clear()`로 컨텍스트를 비우는 패턴을 쓴다.

```java
for (int i = 0; i < members.size(); i++) {
    em.persist(members.get(i));
    if ((i + 1) % 1000 == 0) {
        em.flush();   // 모아 둔 INSERT 전송
        em.clear();   // 1차 캐시 비움 → 지금까지의 엔티티는 준영속
    }
}
```

### 4.2 왜 준영속과 비영속을 구분하는가

둘 다 "컨텍스트가 모르는 객체"인데 굳이 이름을 나눈 이유가 있다. **준영속 객체에는 식별자가 있고, JPA는 그 식별자를 근거로 이 객체가 DB에 이미 있는 행이라고 가정한다.** 이 가정이 두 상태의 취급을 갈라놓는다.

| 호출 | 비영속 | 준영속 |
|:-----|:-------|:-------|
| `persist()` | 영속이 되고 INSERT 예약 | 예외. "detached entity passed to persist" |
| `merge()` | 복사본을 만들어 영속화, INSERT 예약 | 복사본을 만들어 영속화, 변경이 있으면 UPDATE |
| `remove()` | 무시된다 | 예외. 먼저 `merge()`해서 영속으로 만들어야 한다 |

준영속 객체를 다시 관리 상태로 돌리는 방법이 `merge()`다. 그런데 `merge()`는 넘긴 객체를 영속으로 만드는 것이 아니라 **영속 상태의 새 인스턴스를 돌려준다**. 왜 그럴까. 3장의 규칙, 식별자당 인스턴스 하나 때문이다. 컨텍스트에 같은 식별자의 엔티티가 이미 있을 수 있으므로, JPA는 넘긴 객체를 그대로 넣는 대신 식별자로 영속 인스턴스를 찾거나 만들고, 거기에 넘긴 객체의 값을 복사한다. 넘긴 객체는 여전히 준영속이다. `merge()`의 반환값을 받아서 써야 하는 이유이고, 자세한 동작은 [Chapter 06. 플러시](../06-flush-and-detached)에서 다룬다.

{{< callout type="warning" >}}
**JPA가 비영속과 준영속을 구분하는 기준은 식별자다.** `@GeneratedValue`를 쓰는 엔티티에 식별자가 채워져 있으면 Hibernate는 "한때 영속이었던 객체"로 간주하고, 그 객체를 `persist()`하면 `detached entity passed to persist` 예외를 낸다. 스프링 데이터 JPA의 `save()`가 식별자가 없으면 `persist()`, 있으면 `merge()`를 고르는 것도 같은 기준이다. 식별자를 직접 넣은 새 엔티티를 `save()`했을 때 INSERT 전에 SELECT가 먼저 나가는 이유가 바로 이 `merge()` 분기다.
{{< /callout >}}

## 5. 삭제: 지우기로 예약한 객체

```java
Member member = em.find(Member.class, 1L);   // 영속
em.remove(member);                           // 삭제 상태. DELETE 예약
em.contains(member);                         // false
tx.commit();                                 // 이때 DELETE
```

`remove()`도 `persist()`와 같은 원리로 동작한다. DELETE를 바로 보내는 것이 아니라 쓰기 지연 저장소에 예약하고, 커밋 때 실행한다. 그 사이의 객체를 "삭제 상태"라 부른다. `contains()`는 `false`를 돌려주지만 컨텍스트는 이 객체를 잊은 것이 아니라 "지울 것"으로 기억하고 있다.

### 5.1 왜 삭제가 별도의 상태인가

즉시 DELETE를 보낸다면 상태가 필요 없을 것이다. 그런데 쓰기 지연 때문에 "지우기로 했지만 아직 안 지운" 기간이 생기고, 그 기간 동안 이 객체를 어떻게 취급할지 정해야 한다. 변경 감지 대상에서는 빠져야 하고(어차피 지울 행에 UPDATE를 보낼 이유가 없다), 같은 식별자를 다시 `find()`했을 때 돌려줘서도 안 된다. 그래서 영속과 구분되는 상태가 필요하다.

1절의 그림에서 삭제 상태에는 나가는 화살표가 없었다. 사실 한 가지 예외가 있다. 커밋 전에 같은 객체를 다시 `persist()`하면 삭제 예약이 취소되고 영속 상태로 돌아온다. DELETE가 아직 나가지 않았기에 가능한 일이다. 실무에서 일부러 쓸 일은 드물지만, "삭제는 커밋 때까지 예약일 뿐"이라는 사실을 가장 잘 보여 주는 동작이다.

```java
em.remove(member);    // 삭제 예약
em.persist(member);   // 예약 취소 → 다시 영속
tx.commit();          // DELETE 없음
```

준영속 객체는 바로 지울 수 없다. 컨텍스트가 관리하지 않는 객체에 대해 DELETE를 예약할 수 없기 때문이다. 먼저 `merge()`로 영속 인스턴스를 얻고 그것을 `remove()`해야 한다. 삭제와 관련된 세부 동작은 [Chapter 05. 영속성 특징](../05-persistence-features)에서 다룬다.

## 6. 상태 전이를 한눈에

```java
Member member = new Member();          // 비영속
member.setId(1L);

em.persist(member);                    // 영속. INSERT 예약
em.detach(member);                     // 준영속
Member merged = em.merge(member);      // merged만 영속. member는 여전히 준영속
em.remove(merged);                     // 삭제 예약
```

| 현재 상태 | 호출 | 다음 상태 | 비고 |
|:----------|:-----|:----------|:-----|
| 비영속 | `persist()` | 영속 | INSERT 예약 |
| 비영속 | `merge()` | 반환값이 영속 | 복사본, INSERT 예약 |
| (DB) | `find()`, JPQL | 영속 | 조회 결과는 처음부터 영속 |
| 영속 | `detach()`, `clear()`, `close()` | 준영속 | 트랜잭션 종료도 같은 효과 |
| 영속 | `remove()` | 삭제 | DELETE 예약 |
| 준영속 | `merge()` | 반환값이 영속 | 넘긴 객체는 준영속 그대로 |
| 준영속 | `persist()`, `remove()` | 예외 | 먼저 `merge()` |
| 삭제 | `persist()` | 영속 | 삭제 예약 취소 |
| 삭제 | 커밋 | 사라짐 | DELETE 실행 |

### 상태별로 JPA가 해 주는 것

| 구분 | 비영속 | 영속 | 준영속 | 삭제 |
|:-----|:-------|:-----|:-------|:-----|
| 1차 캐시 | X | O | X | 지울 것으로 기록 |
| 식별자 | 없을 수 있음 | 반드시 있음 | 있음 | 있음 |
| 변경 감지 | X | O | X | X |
| 지연 로딩 | X | O | X (예외 발생) | X |
| 커밋 때 SQL | 없음 | INSERT / UPDATE | 없음 | DELETE |

두 표를 관통하는 원칙은 하나다. **JPA는 영속 상태의 객체에 대해서만 일한다.** 나머지 상태는 "왜 일하지 않는가", 혹은 "어떻게 하면 다시 일하게 만드는가"에 대한 설명일 뿐이다. 다음 장에서는 영속 상태에서 실제로 무슨 일이 일어나는지, 1차 캐시와 변경 감지와 쓰기 지연의 동작을 하나씩 뜯어본다.

## 요약

| 상태 | 뜻 | JPA의 태도 |
|:-----|:---|:-----------|
| 비영속 | 컨텍스트가 모르는 객체. DB에 없다는 뜻이 아니다 | 아무것도 하지 않는다 |
| 영속 | 1차 캐시에 들어 있는 객체. 식별자 필수 | 캐시·변경 감지·쓰기 지연·지연 로딩 전부 제공 |
| 준영속 | 한때 영속이었던 객체. 식별자 있음 | 아무것도 하지 않는다. `merge()`로 복사본을 영속화 |
| 삭제 | DELETE가 예약된 객체 | 커밋 때 DELETE. 그 전에 `persist()`하면 취소 |

### 핵심 메서드

```java
em.persist(entity);    // 비영속 → 영속 (삭제 → 영속: 예약 취소)
em.find(...);          // DB → 영속
em.detach(entity);     // 영속 → 준영속 (하나)
em.clear();            // 영속 → 준영속 (전체)
em.close();            // 영속 → 준영속 (컨텍스트 종료)
em.merge(entity);      // 준영속·비영속 → 반환값이 영속
em.remove(entity);     // 영속 → 삭제
em.contains(entity);   // 영속이면 true
```
