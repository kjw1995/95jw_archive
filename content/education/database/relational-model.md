[데이터 모델링](../data-modeling)의 마지막 표에서 주문 101과 102는 포인터가 아니라 `1`이라는 값으로 고객 1을 가리켰다. 관계를 값으로 표현한다는 이 원칙 하나가 어떻게 모델 하나가 되는지를 이 장에서 정식으로 본다. 1970년 에드거 F. 코드(E. F. Codd)가 제안한 관계 데이터 모델은 데이터를 릴레이션이라는 표 하나의 모양으로만 담는다. 릴레이션을 이루는 용어에서 시작해, 릴레이션이 지켜야 하는 특성, 투플을 구별하는 키, DBMS가 값의 정확성을 지키는 무결성 제약조건을 차례로 본다. 원리는 셋이다. 첫째, **릴레이션은 투플의 집합이다.** 같은 행이 둘 없고, 행과 열에 순서가 없고, 칸마다 값이 하나뿐이라는 릴레이션의 네 가지 특성은 모두 "집합"이라는 한 단어에서 나온다. SQL의 테이블은 이 정의에서 조금씩 비켜나 있어서, 그 틈을 아는 것이 실무에서 중요하다. 둘째, **투플을 가리키는 방법은 값뿐이고, 그 값을 정한 것이 키다.** 집합에는 순서도 주소도 없으니 "세 번째 행"이라고 가리킬 수 없다. 그래서 값이 겹치지 않는 속성을 골라 키로 삼고, 다른 릴레이션의 투플도 그 키 값으로 가리킨다. 이것이 외래 키다. 셋째, **무결성 제약은 값으로 가리키는 일이 믿을 만하도록 DBMS가 지키는 규칙이다.** 기본키가 비어 있으면 그 투플을 가리킬 수 없고, 외래 키가 없는 값을 가리키면 참조가 허공에 뜬다. 개체 무결성과 참조 무결성은 둘째 원리가 성립하기 위한 최소한의 약속이다.

## 1. 관계 데이터 모델의 개념

관계 데이터 모델은 데이터를 2차원 표 모양의 릴레이션(relation)에 담는 논리적 데이터 모델이다. 개체 하나에 관한 데이터를 릴레이션 하나에 담고, 릴레이션 사이의 관계는 외래 키 값으로 잇는다.

"릴레이션"은 원래 수학 용어다. 속성마다 들어갈 수 있는 값의 집합(도메인)이 있을 때, 도메인들의 카티션 곱(가능한 모든 조합) 가운데 실제로 성립하는 조합만 골라 모은 부분집합이 릴레이션이다.

```text
도메인
 이름 = {홍길동, 김영희}
 학년 = {1, 2}

카티션 곱: 가능한 모든 조합
 (홍길동, 1)  (홍길동, 2)
 (김영희, 1)  (김영희, 2)

릴레이션: 성립하는 조합만
 (홍길동, 2)
 (김영희, 1)
```

그래서 투플 하나는 "홍길동은 2학년이다" 같은 참인 사실 하나이고, 릴레이션은 참인 사실의 집합이다. 릴레이션에 없는 조합은 거짓으로 본다. "김영희가 2학년인가"를 물으면 DBMS는 "모른다"가 아니라 빈 결과, 즉 "아니다"로 답한다. 이를 닫힌 세계 가정(closed world assumption)이라 한다. 첫째 원리가 말하는 "집합"이 바로 이 집합이다.

실제로는 표로 그린다. 헤더 행이 속성, 나머지 행 하나하나가 투플이다.

```text
학생 릴레이션
┌───────┬────────┬──────┬──────────┐
│ 학번  │ 이름   │ 학년 │ 전화     │
├───────┼────────┼──────┼──────────┤
│ 23001 │ 홍길동 │ 2    │ 010-1234 │
│ 23002 │ 김영희 │ 1    │ 010-2345 │
│ 23003 │ 이철수 │ 3    │ 010-3456 │
│ 23004 │ 박민수 │ 1    │ NULL     │
└───────┴────────┴──────┴──────────┘
 차수 = 속성 4개
 카디널리티 = 투플 4개
```

{{< callout type="warning" >}}
"관계 데이터 모델"의 관계는 릴레이션(relation), 즉 표 자체다. [데이터 모델링](../data-modeling)에서 본 E-R 모델의 관계(relationship)는 개체 사이의 연관이라 전혀 다른 말이다. E-R의 관계는 관계 데이터 모델에서 외래 키 값으로, M:N이라면 연결 테이블이라는 릴레이션으로 표현된다. 관계형 데이터베이스가 "테이블 사이의 관계를 다뤄서" 붙은 이름이라는 설명은 흔하지만 틀렸다.
{{< /callout >}}

## 2. 기본 용어

| 용어 | 뜻 | 파일 시스템 | SQL | 왜 |
|:---|:---|:---|:---|:---|
| 릴레이션 (Relation) | 투플의 집합 | 파일 | 테이블 | 표는 모양일 뿐이고, 릴레이션은 그 표가 지켜야 할 집합의 성질까지 포함한다 |
| 속성 (Attribute) | 이름이 붙은 값의 자리, 릴레이션의 열 | 필드 | 열 (column) | 열은 위치가 아니라 이름으로 구별된다(4절) |
| 투플 (Tuple) | 속성 값의 묶음, 릴레이션의 행 | 레코드 | 행 (row) | 투플 하나가 참인 사실 하나다 |
| 도메인 (Domain) | 한 속성이 가질 수 있는 원자 값의 집합 | - | 데이터 타입 + 제약조건 | 같은 `INT`라도 학년과 나이는 다른 값의 집합이다 |
| 널 (NULL) | 값이 없다는 표시 | - | `NULL` | 0이나 빈 문자열과 달리 "값이 아니다"를 나타낼 수단이 필요하다 |
| 차수 (Degree) | 속성의 개수 | - | 열 개수 | 스키마가 정하니 거의 바뀌지 않는다 |
| 카디널리티 (Cardinality) | 투플의 개수 | - | 행 개수 | 삽입·삭제마다 바뀐다 |

{{< callout type="info" >}}
차수와 카디널리티는 앞 장에서도 나왔지만 뜻이 다르다. E-R 모델의 차수는 관계에 참여하는 **개체 수**(이항, 삼항)이고, 매핑 카디널리티는 인스턴스끼리 짝이 되는 **비율**(1:N)이다([데이터 모델링](../data-modeling)). 인덱스 이야기에서 "카디널리티가 낮다"고 하면 한 열에 서로 다른 값이 몇 개 있느냐를 말한다([DBMS 개요](../dbms-overview)). 같은 단어가 셋 이상의 뜻으로 쓰이니 문맥을 보고 읽어야 한다.
{{< /callout >}}

### 도메인

도메인은 속성에 들어갈 수 있는 값의 집합이다. 데이터 타입과 비슷해 보이지만 더 좁고, 뜻을 담는다.

```text
속성   도메인
학번   숫자 5자리 문자열
이름   50자 이내 문자열
학년   {1, 2, 3, 4}
전화   전화번호 형식, NULL 허용
```

데이터 타입은 도메인을 거칠게 근사한 것이다. 학년을 `INT`로만 정의하면 -7도 들어가니, `CHECK`로 범위를 좁혀야 비로소 도메인이 된다(6절). 도메인에는 비교의 뜻도 들어 있다. 학번 `'23001'`과 상품번호 `'23001'`은 같은 문자열이지만 다른 도메인의 값이라 둘을 비교할 이유가 없다. SQL은 타입만 보므로 이런 비교를 막지 않는다.

SQL 표준에는 도메인에 이름을 붙여 정의하는 `CREATE DOMAIN`이 있다. 같은 규칙을 여러 테이블에서 쓸 때 한 곳에서 고칠 수 있다. PostgreSQL 같은 일부 제품만 지원하고 MySQL에는 없다.

```sql
-- PostgreSQL
CREATE DOMAIN 학년_t AS INT
  CHECK (VALUE BETWEEN 1 AND 4);

CREATE TABLE 장학생 (
    학번 CHAR(5) PRIMARY KEY,
    학년 학년_t
);
```

{{< callout type="info" >}}
**원자 값(Atomic Value)**: 관계 데이터 모델에서 속성 값은 더 나눌 수 없는 원자 값이어야 한다. 이를 만족하는 릴레이션이 [제1정규형](../normalization)이다. 다만 "나눌 수 없다"는 상대적이다. 날짜도 연·월·일로 나뉘지만 날짜 하나로 다룬다면 원자 값이다. 기준은 DBMS가 그 값의 안을 들여다봐야 하느냐다. 쉼표로 이은 전화번호 목록은 번호 하나를 찾으려면 문자열을 쪼개야 하니 원자 값이 아니다.
{{< /callout >}}

### 널 (NULL)

널은 값이 아니라 "값이 없다"는 표시다. 값이 없는 이유는 두 가지다. 전화번호가 있는지 아직 **모르는** 경우와, 전화가 없어 **해당 없는** 경우다. 관계 데이터 모델은 둘을 구별하지 않고 같은 `NULL`로 적는다. `NULL`은 0이나 빈 문자열 `''`과도 다르다. 다만 Oracle은 빈 문자열을 `NULL`로 저장하므로 그 구별이 사라진다는 점을 알아 두자.

값이 아니니 비교도 되지 않는다. `NULL`과 무엇을 비교해도 결과는 참도 거짓도 아닌 UNKNOWN이고, `WHERE`는 참인 행만 돌려준다. 그래서 1절의 학생 릴레이션에서 전화가 없는 박민수를 `= NULL`로는 찾을 수 없다.

```sql
-- 0건: 전화 = NULL은 UNKNOWN
SELECT 이름 FROM 학생
 WHERE 전화 = NULL;

-- 박민수
SELECT 이름 FROM 학생
 WHERE 전화 IS NULL;

-- 4, 3: COUNT(열)은 NULL을 뺀다
SELECT COUNT(*), COUNT(전화)
  FROM 학생;
```

`NULL = NULL`도 UNKNOWN이다. 모르는 값 둘이 같은지는 알 수 없기 때문이다. 이 성질이 6절에서 두 번 나온다. 기본키에 `NULL`을 허용하지 않는 이유(6.1)와, `CHECK`가 `NULL`을 통과시키는 이유(6.3)다. `NULL` 검색과 집계는 [SQL](../sql)에서 다시 본다.

## 3. 릴레이션 스키마와 인스턴스

릴레이션 스키마는 릴레이션의 이름과 속성의 목록이다. `학생(학번, 이름, 학년, 전화)`처럼 적고, 기본키에는 밑줄을 긋는다. 코드 블록에서는 밑줄을 그을 수 없어 이 장에서는 `_학번_`으로 적는다. 릴레이션 인스턴스는 어느 시점에 릴레이션에 들어 있는 투플 전체다.

```text
릴레이션 스키마: 내포
 학생(_학번_, 이름, 학년, 전화)
 틀. 거의 바뀌지 않는다
        │
        │ 값을 채운다
        ▼
릴레이션 인스턴스: 외연
 (23001, 홍길동, 2, 010-1234)
 (23002, 김영희, 1, 010-2345)
 ...
 값. 삽입·삭제·수정마다 바뀐다
```

스키마를 릴레이션 내포(intension), 인스턴스를 릴레이션 외연(extension)이라고도 부른다. [데이터베이스 시스템](../db-system)에서 본 스키마와 인스턴스의 짝이 릴레이션 하나의 단위로 내려온 것이다. 릴레이션 스키마를 모으면 데이터베이스 스키마, 인스턴스를 모으면 데이터베이스 인스턴스가 된다.

```text
데이터베이스 스키마
├── 학과(_학과코드_, 학과명)
├── 학생(_학번_, 이름, 학년, 학과코드)
├── 과목(_과목번호_, 과목명, 학점)
└── 수강(_학번_, _과목번호_, 성적)

데이터베이스 인스턴스
├── 학과: 투플 12개
├── 학생: 투플 3,000개
├── 과목: 투플 400개
└── 수강: 투플 52,000개
```

이 장에서 기억할 것은 키와 제약조건이 **스키마 쪽**에 있다는 점이다. 지금 들어 있는 값이 우연히 겹치지 않는 것과, 앞으로 들어올 어떤 값도 겹치면 안 된다는 약속은 다르다. 키는 뒤의 것이다(5절).

## 4. 릴레이션의 특성

릴레이션이 지켜야 하는 네 가지 특성은 첫째 원리 하나에서 나온다. 릴레이션은 투플의 집합이고, 투플은 (속성 이름, 값) 쌍의 집합이다.

| 특성 | 뜻 | 집합에서 나오는 이유 | SQL 테이블에서는 |
|:---|:---|:---|:---|
| 투플의 유일성 | 같은 투플이 둘 있을 수 없다 | 집합에는 같은 원소가 두 번 들어가지 않는다 | 키를 선언하지 않으면 같은 행이 여러 번 들어간다 |
| 투플의 무순서 | 행의 순서에 의미가 없다 | 집합 {a, b}와 {b, a}는 같은 집합이다 | `ORDER BY` 없이는 결과의 순서가 보장되지 않는다 |
| 속성의 무순서 | 열의 순서에 의미가 없다 | 투플은 이름으로 구별되는 쌍의 집합이다 | 열에 정의 순서가 있고, `SELECT *`와 열 이름 없는 `INSERT`가 그 순서에 기댄다 |
| 속성의 원자성 | 칸마다 값이 하나다 | 도메인의 원소가 원자 값이다 | 배열이나 JSON 타입을 주는 제품도 있다(관계 모델 밖) |

넷째 열이 실무의 요점이다. SQL의 테이블은 엄밀히 말하면 릴레이션이 아니라 같은 원소가 여러 번 들어갈 수 있는 멀티셋(multiset)이다. 그래서 릴레이션의 성질을 SQL에서 누리려면 몇 가지를 직접 챙겨야 한다.

### 투플의 유일성

```text
[올바름] 모든 투플이 서로 다르다
┌───────┬────────┬──────┐
│ 학번  │ 이름   │ 학년 │
├───────┼────────┼──────┤
│ 23001 │ 홍길동 │ 2    │
│ 23002 │ 김영희 │ 1    │
│ 23003 │ 이철수 │ 3    │
└───────┴────────┴──────┘

[잘못됨] 셋째 투플이 첫째와 같다
┌───────┬────────┬──────┐
│ 학번  │ 이름   │ 학년 │
├───────┼────────┼──────┤
│ 23001 │ 홍길동 │ 2    │
│ 23002 │ 김영희 │ 1    │
│ 23001 │ 홍길동 │ 2    │
└───────┴────────┴──────┘
```

릴레이션에서는 둘째 그림이 성립하지 않는다. 같은 사실을 두 번 적는다고 사실이 둘이 되지는 않기 때문이다. SQL 테이블에서는 성립한다. 기본키를 선언하지 않으면 DBMS는 같은 행을 그대로 받아 준다.

```sql
-- 기본키 없는 테이블
CREATE TABLE 학생_키없음 (
    학번 CHAR(5),
    이름 VARCHAR(50)
);
INSERT INTO 학생_키없음 VALUES
  ('23001', '홍길동'),
  ('23001', '홍길동');

-- 하나만 지우려 해도 2건이 지워진다
DELETE FROM 학생_키없음
 WHERE 학번 = '23001';
```

두 행은 모든 값이 같아 `WHERE`로 구별되지 않는다. 그러니 하나만 고치거나 지울 방법이 없다. 둘째 원리를 거꾸로 확인한 셈이다. 값이 같으면 가리킬 수도 없다. MySQL의 `DELETE ... LIMIT 1`, PostgreSQL의 `ctid`, Oracle의 `ROWID`처럼 제품마다 우회로는 있지만 모두 값이 아니라 저장 위치로 행을 가리키는 장치라 관계 모델 밖이다. 결국 해법은 기본키를 선언해 처음부터 같은 행이 들어오지 못하게 하는 것이다.

질의 결과도 마찬가지다. `SELECT 학년 FROM 학생`은 학생 수만큼 행을 돌려주어 같은 학년이 여러 번 나오고, 집합으로 만들려면 `DISTINCT`를 붙여야 한다. 관계 대수의 프로젝트 연산은 중복을 없애지만 SQL의 `SELECT`는 그러지 않는다는 차이는 [관계 데이터 연산](../relational-operation)에서 다시 본다.

### 투플과 속성의 무순서

투플에 순서가 없으니 "첫 번째 학생"이라는 질문은 릴레이션에서 성립하지 않는다. 투플은 위치가 아니라 내용으로 찾는다. SQL도 같다. `ORDER BY`가 없는 `SELECT`의 결과 순서는 인덱스, 실행 계획, 데이터가 쌓인 모양에 따라 언제든 바뀔 수 있다. 어제와 같은 순서로 나왔다고 내일도 그러리라는 보장은 없다. 페이지를 나눠 조회할 때 `ORDER BY` 없이 `LIMIT`과 `OFFSET`을 쓰면 같은 행이 두 페이지에 나오거나 어느 페이지에도 나오지 않을 수 있다. 정렬 열에 같은 값이 많을 때도(학년) 그 안의 순서는 다시 정해지지 않으니, 끝에 키를 붙여(`ORDER BY 학년, 학번`) 순서를 하나로 고정한다.

속성도 위치가 아니라 이름으로 구별된다. 그런데 SQL의 열에는 정의한 순서가 있고, 열 이름을 적지 않은 `INSERT`는 그 순서에 기댄다.

```sql
-- 열 순서에 기댄다
INSERT INTO 학생
VALUES ('23005', '정다은', 2, NULL);

-- 이름으로 짝을 짓는다
INSERT INTO 학생 (학번, 이름, 학년)
VALUES ('23005', '정다은', 2);
```

첫째 문장은 열이 하나 늘면 값 개수가 맞지 않아 실패하고, 테이블을 다시 만들면서 열 순서가 바뀌면 타입이 맞는 한 값이 엉뚱한 열에 조용히 들어간다. 둘째 문장은 열이 늘거나 순서가 바뀌어도 그대로 동작한다. 응용 프로그램의 `INSERT`와 `SELECT`에 열 이름을 적는 습관은 속성의 무순서를 SQL에서 되살리는 일이다.

### 속성의 원자성

```text
[위반] 한 칸에 값이 둘
┌───────┬────────┬──────────────────┐
│ 학번  │ 이름   │ 전화             │
├───────┼────────┼──────────────────┤
│ 23001 │ 홍길동 │ 010-1234,02-1234 │
└───────┴────────┴──────────────────┘

[원자 값] 전화를 따로 뺀다
학생
┌───────┬────────┐
│ 학번  │ 이름   │
├───────┼────────┤
│ 23001 │ 홍길동 │
└───────┴────────┘
학생전화
┌───────┬────────┬──────────┐
│ 학번  │ 구분   │ 전화     │
├───────┼────────┼──────────┤
│ 23001 │ 휴대폰 │ 010-1234 │
│ 23001 │ 집     │ 02-1234  │
└───────┴────────┴──────────┘
```

학생 릴레이션 안에서 행만 둘로 나누면 원자성은 지켜도 이름이 두 번 저장되고, 이름을 고칠 때 한쪽만 고치는 일이 생긴다. 그래서 값이 여럿인 속성은 별도 릴레이션으로 뺀다. [데이터 모델링](../data-modeling)에서 본 다중 값 속성의 변환 규칙이 바로 이것이다.

## 5. 키 (Key)

둘째 원리대로, 집합에는 순서도 주소도 없으니 투플을 가리킬 수 있는 것은 값뿐이다. 키(key)는 릴레이션에서 투플을 유일하게 구별하는 속성 또는 속성의 집합이다.

### 키의 두 성질

| 성질 | 뜻 | 왜 필요한가 |
|:---|:---|:---|
| 유일성 (Uniqueness) | 키 값이 같은 투플이 둘 없다 | 키 값으로 가리켰을 때 정확히 하나가 나와야 한다 |
| 최소성 (Minimality) | 키에서 어느 속성을 빼도 유일성이 깨진다 | 필요 없는 속성이 섞이면 키가 길어지고, 그 속성 값이 바뀔 때마다 키도 바뀐다 |

예제로 학생 릴레이션을 쓴다.

```text
학생
┌───────┬─────────────┬────────┐
│ 학번  │ 이메일      │ 이름   │
├───────┼─────────────┼────────┤
│ 23001 │ hong@uni.ac │ 홍길동 │
│ 23002 │ kim@uni.ac  │ 김영희 │
│ 23003 │ lee@uni.ac  │ 이철수 │
└───────┴─────────────┴────────┘
```

지금 세 이름은 모두 다르다. 그래도 {이름}은 키가 아니다. 동명이인이 입학하는 순간 깨지기 때문이다. 키인지 아닌지는 지금 들어 있는 값이 아니라 업무 규칙이 정한다. "학번은 학생마다 하나씩 주고 다시 쓰지 않는다", "이메일은 계정마다 하나다" 같은 규칙이 있어야 키가 된다. 3절에서 키가 스키마 쪽에 있다고 한 이유다.

### 5.1 키의 종류

**슈퍼키(Super Key)**: 유일성만 만족하는 속성 집합이다.

```text
{학번}  {이메일}
{학번, 이름}  {이메일, 이름}
{학번, 이메일}
{학번, 이메일, 이름}
```

유일한 속성 집합에 무엇을 더해도 여전히 유일하니, 후보키를 품은 속성 집합은 모두 슈퍼키다.

**후보키(Candidate Key)**: 유일성과 최소성을 모두 만족하는 속성 집합이다.

```text
{학번}        유일, 최소   O
{이메일}      유일, 최소   O
{학번, 이름}  이름을 빼도
              유일하다     X
```

최소성은 "속성 수가 가장 적다"가 아니라 "더 뺄 것이 없다"는 뜻이다. 수강 릴레이션을 보면 차이가 분명하다.

```text
수강
┌───────┬──────────┬──────┐
│ 학번  │ 과목번호 │ 성적 │
├───────┼──────────┼──────┤
│ 23001 │ DB101    │ A    │
│ 23001 │ OS201    │ B    │
│ 23002 │ DB101    │ A    │
└───────┴──────────┴──────┘
 {학번}      23001이 둘   X
 {과목번호}  DB101이 둘   X
 {학번, 과목번호}
             유일, 최소   O
```

학번만으로도, 과목번호만으로도 수강을 구별할 수 없지만 둘을 합치면 구별되고, 어느 쪽을 빼도 다시 겹친다. 그러니 {학번, 과목번호}는 속성 두 개짜리 후보키다.

**기본키(Primary Key)**: 후보키 가운데 투플을 대표로 구별하는 데 쓰려고 고른 하나다. 학번과 이메일 중 무엇을 고를지는 다음 기준으로 정한다.

| 기준 | 학번 | 이메일 | 왜 |
|:---|:---|:---|:---|
| `NULL`이 없는가 | 입학하면 바로 받는다 | 계정을 만들기 전에는 없다 | 기본키는 `NULL`일 수 없다(6.1) |
| 잘 바뀌지 않는가 | 졸업 뒤에도 그대로다 | 메일 주소를 바꿀 수 있다 | 기본키가 바뀌면 그것을 가리키는 모든 외래 키도 바뀌어야 한다 |
| 짧고 단순한가 | 5자 | 수십 자 | 외래 키로 여러 테이블에 복사되고 인덱스에 들어간다 |
| 밖에 드러나도 되는가 | 학생증에 찍힌다 | 개인정보다 | 키는 URL, 로그, 다른 테이블로 퍼져 나간다 |

네 기준 모두 학번이 낫다. 학번이 기본키가 된다.

**대체키(Alternate Key)**: 기본키가 되지 못한 후보키다. 이메일이 대체키다. 기본키가 되지 못했어도 후보키라는 사실은 그대로이니 유일성은 여전히 지켜야 하고, SQL에서는 `UNIQUE`로 선언한다.

{{< callout type="info" >}}
학번처럼 업무에서 쓰이는 값을 그대로 키로 삼으면 **자연 키(natural key)**, 업무와 상관없이 DBMS가 매기는 일련번호(`AUTO_INCREMENT`, `IDENTITY`)를 키로 삼으면 **대리 키(surrogate key)**라 한다. 학번 체계가 개편될 수 있다면 대리 키를 기본키로 두고 학번에는 `UNIQUE`를 거는 편이 안전하다. 다만 대리 키는 기본키 고르기의 고민을 덜어 줄 뿐, 업무 규칙의 유일성을 대신 지켜 주지는 않는다. 학번에 `UNIQUE`를 빠뜨리면 대리 키만 다르고 학번이 같은 학생이 두 번 들어간다.
{{< /callout >}}

{{< callout type="warning" >}}
교재는 주민등록번호를 후보키의 예로 자주 든다. 하지만 실무에서는 키로 쓰지 않는다. 개인정보 보호법이 2014년부터 법령이 허용한 경우 같은 몇 가지 예외가 아니면 주민등록번호를 처리할 수 없게 했기 때문이다. 바뀌지 않을 것 같은 값도 아니다. 2017년부터는 유출 피해 등을 이유로 번호를 바꿀 수 있다. "절대 안 바뀌는 자연 키"는 생각보다 드물다.
{{< /callout >}}

**외래 키(Foreign Key)**: 다른 릴레이션의 기본키를 참조하는 속성이다. 학생의 학과코드는 학과의 기본키를 참조한다.

```text
학생 (참조하는 쪽)
┌───────┬────────┬──────────┐
│ 학번  │ 이름   │ 학과코드 │
├───────┼────────┼──────────┤
│ 23001 │ 홍길동 │ CS       │
│ 23002 │ 김영희 │ BA       │
│ 23003 │ 이철수 │ CS       │
└───────┴────────┴────┬─────┘
                      │ 참조
                      ▼
학과 (참조되는 쪽)
┌──────────┬────────────┐
│ 학과코드 │ 학과명     │
├──────────┼────────────┤
│ CS       │ 컴퓨터공학 │
│ BA       │ 경영학     │
└──────────┴────────────┘
```

외래 키에는 기본키와 다른 성질이 몇 가지 있다.

| 성질 | 예 | 왜 |
|:---|:---|:---|
| 참조하는 기본키와 도메인이 같아야 한다 | 학생.학과코드와 학과.학과코드 | 값을 비교해 짝을 찾으니 같은 종류의 값이어야 한다. 이름은 달라도 된다 |
| 유일하지 않아도 된다 | 홍길동과 이철수가 같은 CS | 여러 투플이 같은 투플을 가리키는 것, 그것이 1:N이다 |
| `NULL`일 수 있다 | 학과를 아직 정하지 않은 학생 | 아무것도 가리키지 않는 상태도 정상일 수 있다(부분 참여) |
| 기본키의 일부가 될 수 있다 | 수강의 학번, 과목번호 | 수강은 학생과 과목을 잇는 연결 테이블이다 |
| 대체키를 참조할 수도 있다 | 학과명에 `UNIQUE`가 있다면 학과명 | 표준은 기본키나 `UNIQUE`가 걸린 후보키를 참조하게 한다 |

### 5.2 키 종류 비교

| 종류 | 유일성 | 최소성 | SQL 선언 | 왜 |
|:---|:---|:---|:---|:---|
| 슈퍼키 | O | X | 선언하지 않음 | 후보키에 속성을 더한 것이라 후보키만 지키면 저절로 지켜진다 |
| 후보키 | O | O | `PRIMARY KEY` 또는 `UNIQUE` | 기본키와 대체키로 나뉘어 선언된다 |
| 기본키 | O | O | `PRIMARY KEY` | 대표 식별자라 `NULL`도 허용하지 않는다 |
| 대체키 | O | O | `UNIQUE` | 기본키가 아니어도 후보키의 유일성은 지켜야 한다 |
| 외래 키 | X | - | `FOREIGN KEY` | 자기 투플을 구별하지 않고 다른 투플을 가리킬 뿐이다 |

### 키의 포함 관계

```text
┌──────────────────────────┐
│ 슈퍼키  {학번, 이름} 등  │
│ ┌──────────────────────┐ │
│ │ 후보키               │ │
│ │ ┌────────┬─────────┐ │ │
│ │ │ 기본키 │ 대체키  │ │ │
│ │ │ {학번} │{이메일} │ │ │
│ │ └────────┴─────────┘ │ │
│ └──────────────────────┘ │
└──────────────────────────┘
 외래 키는 이 그림 밖이다
 다른 릴레이션의 키를 가리킨다
```

### 5.3 자기 참조 외래 키

외래 키가 같은 릴레이션의 기본키를 참조할 수도 있다. [데이터 모델링](../data-modeling)의 순환 관계가 테이블로 옮겨진 모양이다.

```text
사원
┌──────┬────────┬──────────┐
│ 번호 │ 이름   │ 상사번호 │
├──────┼────────┼──────────┤
│ E1   │ 김사장 │ NULL     │
│ E2   │ 이부장 │ E1       │
│ E3   │ 박과장 │ E2       │
│ E4   │ 최대리 │ E3       │
└──────┴────────┴──────────┘
 상사번호 → 같은 테이블의 번호
 E4 → E3 → E2 → E1 → 끝
```

자기 참조 외래 키는 참조가 한 테이블 안에서 이어지기 때문에 따로 챙길 점이 셋 있다.

- **거의 언제나 `NULL`을 허용한다.** 맨 위의 김사장에게는 상사가 없고, 테이블에 첫 행을 넣을 때는 가리킬 행이 아직 없다. 상사번호에 `NOT NULL`을 걸면 김사장의 상사를 김사장 자신으로 적는 식의 억지를 써야 첫 행이 들어간다.
- **넣는 순서와 지우는 순서가 정해진다.** 상사가 먼저 들어가야 부하를 넣을 수 있고, 부하가 남아 있는 상사는 지울 수 없다. 박과장(E3)을 지우려 하면 최대리(E4)가 없는 사원을 가리키게 되니 DBMS가 거부한다. 지워도 되게 하려면 6.2의 삭제 규칙을 쓴다.
- **고리는 막지 못한다.** 김사장의 상사번호를 E4로 바꾸면 E1 → E4 → E3 → E2 → E1로 끝없이 도는 고리가 생기지만, E4는 실제로 있는 사원이니 외래 키는 통과시킨다. 외래 키는 "있는 값을 가리키는가"만 검사한다. 고리를 막으려면 트리거나 응용 프로그램이 검사해야 한다.

외래 키는 바로 위 한 단계만 안다. 최대리의 상사를 끝까지 따라 올라가는 조회는 재귀 질의(`WITH RECURSIVE`)로 한다.

## 6. 무결성 제약조건

무결성(integrity)은 데이터가 정확하고 서로 어긋나지 않는 상태를 말한다. 셋째 원리대로 관계 데이터 모델은 이를 위한 규칙을 스키마에 적어 둔다. 규칙이 스키마에 있으면 DBMS가 모든 삽입·수정·삭제 때 검사하고, 어기는 요청은 들어오는 순간 거부된다. 응용 프로그램마다 검사 코드를 따로 두지 않아도 된다는 것이 [DBMS 개요](../dbms-overview)에서 본 제약조건의 이점이다.

### 무결성과 보안

| 구분 | 막는 것 | 예 | 수단 | 왜 구분하나 |
|:---|:---|:---|:---|:---|
| 무결성 | 권한 있는 사용자의 잘못된 값 | 학년에 5를 넣는다 | 제약조건 | 권한이 있어도 틀린 값은 틀리다 |
| 보안 | 권한 없는 사용자의 접근 | 남의 성적을 본다 | 인증, `GRANT` | 값이 맞더라도 볼 자격이 없으면 막아야 한다 |

보안은 [보안과 권한 관리](../security-authorization)에서 다루고, 이 장은 무결성만 본다.

### 제약조건 종류

| 제약조건 | 대상 | 규칙 | SQL | 왜 |
|:---|:---|:---|:---|:---|
| 도메인 무결성 | 속성 값 | 도메인에 속한 값만 | 데이터 타입, `CHECK`, `NOT NULL` | 도메인 밖의 값은 사실을 나타내지 않는다 |
| 키 무결성 | 후보키 | 키 값이 겹치지 않는다 | `PRIMARY KEY`, `UNIQUE` | 키 값으로 가리켰을 때 하나만 나와야 한다 |
| 개체 무결성 | 기본키 | `NULL`이 아니다 | `PRIMARY KEY` | `NULL`로는 투플을 가리킬 수 없다 |
| 참조 무결성 | 외래 키 | 참조되는 기본키에 있는 값이거나 `NULL` | `FOREIGN KEY` | 없는 투플을 가리키면 참조가 허공에 뜬다 |

위의 셋은 릴레이션 하나 안의 규칙이고, 마지막 참조 무결성만 두 릴레이션 사이의 규칙이다. 교재에 따라 키 무결성을 따로 세지 않기도 하지만, 기본키와 대체키의 유일성을 지키는 일이라 함께 보는 편이 이해하기 쉽다.

### 6.1 개체 무결성

기본키를 이루는 어떤 속성도 `NULL`일 수 없다.

```text
[올바름] 기본키만 채우면 된다
┌───────┬────────┬──────────┐
│ 학번  │ 이름   │ 전화     │
├───────┼────────┼──────────┤
│ 23001 │ 홍길동 │ 010-1234 │
│ 23004 │ 박민수 │ NULL     │
└───────┴────────┴──────────┘

[위반] 기본키가 NULL
┌───────┬────────┬──────────┐
│ 학번  │ 이름   │ 전화     │
├───────┼────────┼──────────┤
│ NULL  │ 이철수 │ 010-3456 │
└───────┴────────┴──────────┘
```

이유는 둘째 원리에 있다. 기본키는 투플을 가리키는 값인데, `NULL`은 값이 없다는 표시이니 `NULL` 기본키로는 그 투플을 가리킬 수 없다. 다른 테이블의 외래 키가 이 학생을 참조할 방법도 사라진다. 유일성도 깨진다. 2절에서 봤듯 `NULL = NULL`은 UNKNOWN이라, 기본키가 `NULL`인 투플이 둘 있으면 둘이 같은 학생인지 다른 학생인지조차 판정할 수 없다.

복합 기본키도 마찬가지로, 일부만 `NULL`이어도 안 된다.

```text
수강(_학번_, _과목번호_, 성적)

OK   (23001, DB101, A)
위반 (23001, NULL,  A)
위반 (NULL,  DB101, A)
```

과목번호를 모르는 수강은 어느 수강인지 모르는 것과 같다. 반면 대체키는 기본키가 아니므로 `NULL`을 허용한다. `UNIQUE` 열에는 `NULL`이 여러 개 들어갈 수 있는데, `NULL`끼리는 같다고 판정되지 않아 겹치는 것으로 보지 않기 때문이다. 이메일이 없는 학생이 여럿이어도 된다. 대체키를 반드시 채워야 한다면 `UNIQUE`에 `NOT NULL`을 함께 건다.

{{< callout type="warning" >}}
제품마다 다른 곳이 있다. SQL Server는 `UNIQUE` 열에 `NULL`을 하나만 허용하고, PostgreSQL은 15부터 `UNIQUE NULLS NOT DISTINCT`로 같은 동작을 고를 수 있다. SQLite는 오래된 버그와의 호환 때문에 `PRIMARY KEY` 열에도 `NULL`을 받아 주고, `NULL` 기본키 행이 여러 개 들어가기까지 한다. `STRICT`나 `WITHOUT ROWID` 테이블, `NOT NULL`을 직접 적은 열에서만 거부하고, `INTEGER PRIMARY KEY` 열은 `NULL`을 넣으면 번호를 자동으로 매긴다. SQLite에서는 기본키 열에 `NOT NULL`을 함께 적어 두자.
{{< /callout >}}

### 6.2 참조 무결성

외래 키 값은 참조되는 릴레이션의 기본키 값 가운데 하나이거나 `NULL`이어야 한다.

```text
학생 (참조하는 쪽)
┌───────┬────────┬──────────┐
│ 학번  │ 이름   │ 학과코드 │
├───────┼────────┼──────────┤
│ 23001 │ 홍길동 │ CS       │
│ 23002 │ 김영희 │ BA       │
│ 23003 │ 이철수 │ NULL     │
│ 23004 │ 박민수 │ EE       │
└───────┴────────┴────┬─────┘
                      │ 참조
                      ▼
학과 (참조되는 쪽)
┌──────────┬────────────┐
│ 학과코드 │ 학과명     │
├──────────┼────────────┤
│ CS       │ 컴퓨터공학 │
│ BA       │ 경영학     │
└──────────┴────────────┘
 CS, BA  학과에 있다    OK
 NULL    가리키지 않음  OK
 EE      학과에 없다    위반
```

`NULL`이 허용되는 이유는 `NULL`이 "아무것도 가리키지 않는다"이지 "없는 것을 가리킨다"가 아니기 때문이다. 학과를 아직 정하지 않은 이철수는 정상이지만, 있지도 않은 EE 학과에 속한 박민수는 사실이 될 수 없다. 모든 학생이 반드시 학과에 속해야 한다면(전체 참여) 학과코드에 `NOT NULL`을 더한다. [데이터 모델링](../data-modeling)의 참여 제약이 테이블에서 드러나는 자리가 여기다.

#### 어떤 연산이 위반하나

참조 무결성은 두 테이블에 걸친 규칙이라, 어느 쪽의 어떤 연산이 그것을 깨뜨릴 수 있는지부터 따져야 한다.

| 연산 | 대상 | 위반할 수 있나 | 왜 |
|:---|:---|:---|:---|
| 삽입 | 학생 (참조하는 쪽) | 예 | 없는 학과코드를 넣을 수 있다 |
| 학과코드 수정 | 학생 | 예 | 없는 학과코드로 바꿀 수 있다 |
| 삭제 | 학생 | 아니오 | 가리키던 쪽이 사라질 뿐이다 |
| 삽입 | 학과 (참조되는 쪽) | 아니오 | 새 학과는 아직 아무도 가리키지 않는다 |
| 학과코드 수정 | 학과 | 예 | 옛 코드를 가리키던 학생이 고아가 된다 |
| 삭제 | 학과 | 예 | 그 학과를 가리키던 학생이 고아가 된다 |

참조하는 쪽의 위반은 거부하면 그만이다. 고민은 참조되는 쪽, 즉 학과를 지우거나 학과코드를 바꿀 때다. 이때 DBMS가 어떻게 할지를 외래 키에 `ON DELETE`, `ON UPDATE`로 정해 둔다.

| 옵션 | 학과 CS를 지우면 | 언제 쓰나 | 왜 |
|:---|:---|:---|:---|
| `NO ACTION` | 거부 (표준 기본값) | 대부분 | 지워도 되는지는 사람이 판단해야 한다 |
| `RESTRICT` | 거부 | `NO ACTION`과 같지만 검사를 미루지 않을 때 | 바로 거부해 원인을 분명히 한다 |
| `CASCADE` | CS 학생도 삭제 | 약한 개체, 다중 값 테이블 | 주인 없이는 존재할 수 없는 행이다 |
| `SET NULL` | CS 학생의 학과코드를 `NULL`로 | 부분 참여인 외래 키 | 관계만 끊고 행은 남긴다 |
| `SET DEFAULT` | 학과코드를 기본값으로 | 드물다 | 기본값에 해당하는 학과가 따로 있어야 한다 |

`NO ACTION`과 `RESTRICT`는 둘 다 거부하지만 검사 시점이 다르다. `RESTRICT`는 행을 지우는 즉시 검사하고, `NO ACTION`은 문장이 끝날 때(지연 제약이라면 커밋할 때) 검사한다. 그래서 고아가 된 행을 같은 문장 안에서, 지연 제약이라면 같은 트랜잭션 안에서 다시 이어 주면 `NO ACTION`만 통과한다. 지연 제약은 [데이터 모델링](../data-modeling)에서 서로를 가리키는 두 테이블을 넣을 때 본 그 장치다.

{{< callout type="warning" >}}
제품마다 지원하는 범위가 다르다. MySQL(InnoDB)은 `NO ACTION`을 `RESTRICT`와 똑같이 즉시 검사하고, `SET DEFAULT`는 문법으로는 알아듣지만 그런 외래 키가 있는 테이블 정의를 거부한다. Oracle은 `ON DELETE CASCADE`와 `ON DELETE SET NULL`만 지원하고 `ON UPDATE` 절이 아예 없다. 기본키를 바꾸지 않도록 설계하라는 5.1의 기준이 여기서도 이득이 된다. SQLite는 외래 키 검사가 **기본으로 꺼져 있다**. 연결마다 `PRAGMA foreign_keys = ON;`을 실행해야 하고, 꺼져 있는 동안에는 `CASCADE`나 `SET NULL` 같은 규칙도 동작하지 않는다. 그동안 들어간 고아 행은 켠 뒤에도 그대로 남으니 `PRAGMA foreign_key_check`로 찾아야 한다.
{{< /callout >}}

{{< callout type="info" >}}
복합 외래 키는 일부 열만 `NULL`이면 검사를 건너뛴다. 성적 이의신청 테이블이 수강(학번, 과목번호)을 참조한다고 하자. 이의신청에 `(99999, NULL)`을 넣으면 99999라는 학생이 없어도 통과한다. 표준의 기본 규칙인 `MATCH SIMPLE`이 "하나라도 `NULL`이면 가리키지 않는 것"으로 보기 때문이다. 전부 채우거나 전부 비워야 한다면 `CHECK`로 따로 막는다. PostgreSQL은 이를 외래 키에서 바로 강제하는 `MATCH FULL`도 지원한다.
{{< /callout >}}

### 6.3 도메인 무결성

속성 값은 그 속성의 도메인에 속해야 한다. 데이터 타입이 첫 번째 거름망이고, `CHECK`와 `NOT NULL`로 더 좁힌다.

```sql
학년 INT CHECK (학년 BETWEEN 1 AND 4)
성별 CHAR(1) CHECK (성별 IN ('M', 'F'))
상태 VARCHAR(10) NOT NULL
  CHECK (상태 IN ('재학', '휴학'))
```

여기에도 `NULL`이 끼어든다. `CHECK`는 조건이 **거짓일 때만** 거부한다. 학년에 `NULL`을 넣으면 `NULL BETWEEN 1 AND 4`가 UNKNOWN이 되고, 거짓은 아니니 통과한다. `WHERE`는 참인 행만 통과시키고 `CHECK`는 거짓인 행만 거부한다. 같은 3값 논리를 반대 방향에서 쓰는 셈이다. 그래서 반드시 있어야 하는 값이라면 `CHECK`만으로는 부족하고 `NOT NULL`을 함께 건다. 위의 상태 열이 그 모양이다.

`CHECK`는 한 행 안의 값만 본다. "학과 정원을 넘을 수 없다"처럼 다른 행이나 다른 테이블을 봐야 하는 규칙은 `CHECK`로 걸 수 없어 트리거나 응용 프로그램이 검사한다. 오래된 MySQL이 `CHECK`를 검사하지 않았던 문제는 [데이터베이스 시스템](../db-system)에서 봤다.

## 7. SQL로 보는 관계 데이터 모델

지금까지의 개념을 SQL로 모으면 다음과 같다. 무결성 제약 넷이 모두 `CREATE TABLE` 안에 들어 있다.

### 릴레이션 생성

```sql
-- 참조되는 쪽
CREATE TABLE 학과 (
    학과코드 CHAR(2) PRIMARY KEY,
    학과명   VARCHAR(50) NOT NULL
);

-- 참조하는 쪽
CREATE TABLE 학생 (
    -- 기본키: 개체·키 무결성
    학번     CHAR(5) PRIMARY KEY,
    -- 대체키: 키 무결성
    이메일   VARCHAR(50) UNIQUE,
    이름     VARCHAR(50) NOT NULL,
    -- 도메인 무결성
    학년     INT NOT NULL
      CHECK (학년 BETWEEN 1 AND 4),
    -- 외래 키: 참조 무결성
    학과코드 CHAR(2),
    FOREIGN KEY (학과코드)
      REFERENCES 학과(학과코드)
      ON DELETE SET NULL
      ON UPDATE CASCADE
);
```

학과코드에 `NOT NULL`이 없는 것은 학과를 정하지 않은 학생을 허용한다는 뜻이고(부분 참여), 그래서 `ON DELETE SET NULL`을 고를 수 있다. 외래 키가 `NOT NULL`이라면 `SET NULL`은 쓸 수 없다. Oracle에서는 `ON UPDATE` 줄을 빼야 한다.

### 무결성 위반 시나리오

```sql
INSERT INTO 학과 VALUES
  ('CS', '컴퓨터공학'),
  ('BA', '경영학');
INSERT INTO 학생
  (학번, 이름, 학년, 학과코드)
VALUES ('23001', '홍길동', 2, 'CS'),
       ('23002', '김영희', 1, 'BA');

-- 개체 무결성: 기본키가 NULL
INSERT INTO 학생 (학번, 이름, 학년)
VALUES (NULL, '이철수', 3);

-- 키 무결성: 학번이 겹친다
INSERT INTO 학생 (학번, 이름, 학년)
VALUES ('23001', '이철수', 3);

-- 참조 무결성: 없는 학과
INSERT INTO 학생
  (학번, 이름, 학년, 학과코드)
VALUES ('23003', '이철수', 3, 'EE');

-- 도메인 무결성: 학년이 5
INSERT INTO 학생 (학번, 이름, 학년)
VALUES ('23003', '이철수', 5);
```

처음 두 문장은 들어가고 아래 넷은 모두 거부된다. 오류 메시지는 제품마다 다르지만, 거부되는 이유는 위 주석의 규칙 그대로다. 응용 프로그램에 검사 코드가 하나도 없어도 잘못된 값은 테이블에 닿지 못한다. 단, SQLite라면 6.1에서 본 대로 첫째 위반이 통과하고, 외래 키 검사를 켜지 않았다면 셋째도 통과한다.

### 삭제·수정 규칙의 동작

참조되는 쪽을 바꾸면 외래 키에 적어 둔 규칙이 참조하는 쪽에 번진다.

```sql
-- BA를 BM으로: 학생이 따라 바뀐다
UPDATE 학과 SET 학과코드 = 'BM'
 WHERE 학과코드 = 'BA';

-- CS 삭제: 학생은 남고 관계만 끊긴다
DELETE FROM 학과
 WHERE 학과코드 = 'CS';

SELECT 학번, 이름, 학과코드
  FROM 학생;
-- 23001  홍길동  NULL
-- 23002  김영희  BM
```

`ON UPDATE CASCADE`가 김영희의 학과코드를 BM으로 따라 바꾸고, `ON DELETE SET NULL`이 홍길동의 학과코드를 비웠다. 규칙이 없었다면(`NO ACTION`) 두 문장 모두 거부됐을 것이다.

{{< callout type="warning" >}}
`CASCADE`는 편리하지만 연쇄된다. 학생의 외래 키가 `ON DELETE CASCADE`였다면 학과 하나를 지울 때 그 학과 학생이 모두 지워지고, 수강이 학생을 `CASCADE`로 참조한다면 그 학생들의 수강 기록까지 지워진다. `DELETE` 한 문장이 테이블 셋에서 행을 지우는 셈이다. 결제나 주문처럼 이력을 남겨야 하는 데이터라면 `RESTRICT`(또는 `NO ACTION`)를 기본으로 두고, 행을 지우는 대신 상태 열로 "삭제됨"을 표시하는 방법(소프트 삭제)을 먼저 고려하자. `CASCADE`는 다중 값 속성이나 약한 개체처럼 주인 없이는 의미가 없는 행에만 쓰는 편이 안전하다.
{{< /callout >}}

{{< callout type="info" >}}
학과를 지우거나 학과코드를 바꿀 때마다 DBMS는 학생 테이블에서 그 학과코드를 가진 행을 찾아야 한다. 외래 키 열에 인덱스가 없으면 그때마다 학생 테이블 전체를 읽는다. MySQL(InnoDB)은 외래 키 열에 인덱스를 자동으로 만들지만, PostgreSQL, Oracle, SQLite는 만들지 않으니 외래 키 열에 인덱스를 직접 두는 편이 좋다.
{{< /callout >}}

이렇게 정의한 릴레이션 위에서 질의를 표현하는 방법이 [관계 데이터 연산](../relational-operation)이고, 그것을 실제 언어로 옮긴 것이 [SQL](../sql)이다. 키와 제약조건을 갖춘 릴레이션에도 같은 사실이 여러 번 저장되는 문제는 남을 수 있는데, 그것을 가리는 기준이 [정규화](../normalization)다.

## 핵심 정리

| 항목 | 핵심 | 왜 |
|:---|:---|:---|
| 릴레이션 | 도메인들의 카티션 곱의 부분집합, 참인 사실의 집합 | 집합이라서 네 가지 특성이 나온다 |
| 투플 / 속성 | 행 / 이름이 붙은 열 | 투플 하나가 사실 하나, 속성은 위치가 아니라 이름으로 구별된다 |
| 차수 / 카디널리티 | 속성 수 / 투플 수 | 스키마가 정하는 것과 인스턴스마다 바뀌는 것이다 |
| 도메인 | 속성이 가질 수 있는 원자 값의 집합 | 데이터 타입만으로는 좁혀지지 않아 `CHECK`가 필요하다 |
| `NULL` | 값이 없다는 표시, 비교하면 UNKNOWN | `= NULL`로는 찾을 수 없고 `IS NULL`을 쓴다 |
| 스키마 / 인스턴스 | 내포 / 외연 | 키와 제약은 스키마 쪽의 약속이다 |
| 릴레이션 4특성 | 투플 유일·무순서, 속성 무순서·원자성 | SQL 테이블은 멀티셋이라 키, `ORDER BY`, 열 이름을 직접 챙긴다 |
| 슈퍼키 / 후보키 | 유일성 / 유일성 + 최소성 | 최소성은 "더 뺄 것이 없다"는 뜻이다 |
| 기본키 / 대체키 | 고른 후보키 / 남은 후보키 | `NULL` 없고 잘 안 바뀌고 짧은 것을 기본키로, 나머지는 `UNIQUE` |
| 외래 키 | 다른 릴레이션의 키 값을 가리킨다 | 관계를 포인터가 아닌 값으로 표현한다 |
| 개체 무결성 | 기본키는 `NULL`이 아니다 | `NULL`로는 투플을 가리킬 수 없다 |
| 참조 무결성 | 외래 키는 있는 값이거나 `NULL` | 없는 투플을 가리키면 참조가 허공에 뜬다 |
| 도메인 무결성 | 값은 도메인 안에 | `CHECK`는 UNKNOWN을 통과시키니 `NOT NULL`을 함께 건다 |
| 삭제·수정 규칙 | `NO ACTION`, `CASCADE`, `SET NULL` 등 | 참조되는 쪽이 바뀔 때 참조하는 쪽을 어떻게 할지 정한다 |

{{< callout type="info" >}}
**용어 정리**
- **관계 데이터 모델**: 데이터를 릴레이션에 담고 릴레이션 사이를 외래 키 값으로 잇는 논리적 데이터 모델 (Codd, 1970)
- **릴레이션 (Relation)**: 투플의 집합. 도메인들의 카티션 곱의 부분집합
- **투플 (Tuple)**: 릴레이션의 행. 참인 사실 하나
- **속성 (Attribute)**: 릴레이션의 열. 이름으로 구별된다
- **도메인 (Domain)**: 속성이 가질 수 있는 원자 값의 집합
- **원자 값 (Atomic Value)**: DBMS가 안을 들여다볼 필요가 없는, 더 나누지 않는 값
- **널 (NULL)**: 값이 없다는 표시. 모름과 해당 없음을 함께 나타낸다
- **3값 논리**: 참, 거짓, UNKNOWN. `NULL`과의 비교는 UNKNOWN이 된다
- **차수 (Degree)**: 속성의 개수
- **카디널리티 (Cardinality)**: 투플의 개수
- **릴레이션 내포 / 외연**: 릴레이션 스키마 / 릴레이션 인스턴스
- **닫힌 세계 가정**: 릴레이션에 없는 사실은 거짓으로 본다
- **멀티셋 (Multiset)**: 같은 원소가 여러 번 들어갈 수 있는 집합. SQL 테이블과 질의 결과
- **슈퍼키 (Super Key)**: 유일성을 만족하는 속성 집합
- **후보키 (Candidate Key)**: 유일성과 최소성을 만족하는 속성 집합
- **기본키 (Primary Key)**: 대표로 고른 후보키. `NULL` 불가
- **대체키 (Alternate Key)**: 기본키가 되지 못한 후보키. `UNIQUE`로 선언한다
- **자연 키 / 대리 키**: 업무에서 쓰는 값을 그대로 쓴 키 / DBMS가 매긴 일련번호 키
- **외래 키 (Foreign Key)**: 다른(또는 같은) 릴레이션의 기본키를 참조하는 속성
- **도메인 / 키 / 개체 / 참조 무결성**: 값은 도메인 안에 / 후보키는 겹치지 않게 / 기본키는 `NULL` 아니게 / 외래 키는 있는 값이나 `NULL`로
- **NO ACTION / RESTRICT**: 참조되는 행의 삭제·수정을 거부한다. 검사 시점이 문장 끝 / 즉시
- **CASCADE / SET NULL / SET DEFAULT**: 참조하는 행도 함께 삭제·수정 / 외래 키를 `NULL`로 / 기본값으로
{{< /callout >}}
