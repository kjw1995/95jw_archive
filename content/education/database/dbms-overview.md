[데이터베이스 기본 개념](../db-fundamentals)에서 데이터베이스가 무엇인지 봤다. 이 장은 그 데이터베이스를 실제로 만들고 지키는 소프트웨어, DBMS를 다룬다. 파일 시스템으로 데이터를 관리하던 시절에 무엇이 문제였는지에서 시작해, DBMS가 그 문제를 어떻게 푸는지, 어떤 기능을 어떤 언어로 제공하는지, 구조를 어떻게 나누어 변화를 견디는지를 본다. 원리는 셋이다. 첫째, **DBMS는 응용 프로그램과 데이터 사이에 들어선 중개자다.** 파일 시스템의 문제는 전부 프로그램이 데이터 파일을 직접 소유했기 때문에 생겼고, 중개자를 하나 두면 통합, 독립성, 동시 공유, 보안과 회복이 그 자리에서 해결된다. 둘째, **DBMS가 하는 일은 정의·조작·제어 셋으로 정리되고, 전부 언어로 요청한다.** 정의가 만든 스키마는 데이터 사전에 저장되고, 조작이 인스턴스를 바꾸며, 제어는 권한과 트랜잭션으로 드러난다. 셋째, **구조를 세 단계로 나누고 단계 사이를 사상으로 이으면 아래가 바뀌어도 위가 흔들리지 않는다.** 3단계 구조와 데이터 독립성이 그것이고, 인덱스를 붙여도 질의가 그대로인 것이 가장 흔한 예다. DBMS의 발전 과정은 이 중개자가 어떤 데이터 모델로 말하는가가 바뀌어 온 역사다.

## 1. 파일 시스템의 한계

초기 응용 프로그램은 데이터를 각자 파일에 저장했다. 프로그램이 파일의 구조를 알고 직접 읽고 쓰는 방식이다. 이 구조에서는 같은 데이터가 여러 파일에 중복되고, 파일 구조가 바뀔 때마다 그 파일을 읽는 프로그램도 전부 수정해야 한다. 아래 네 가지 문제는 전부 "프로그램이 데이터를 소유한다"는 한 가지 사실에서 나온다.

```text
[파일 시스템]
앱 A ─→ 파일 A (고객)
앱 B ─→ 파일 B (고객+주문)   ← 중복
앱 C ─→ 파일 C (고객+배송)   ← 중복

[DBMS]
앱 A ─┐
앱 B ─┼─→ DBMS ─→ 통합 DB
앱 C ─┘
```

| 문제점 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| 데이터 중복성 | 같은 값이 여러 파일에 저장 | 고객 정보가 A·B·C에 각각 존재 | 프로그램마다 자기 파일을 가지니 같은 고객이 세 번 적힌다 |
| 데이터 종속성 | 파일 구조 변경 시 프로그램 수정 | 필드 추가 → 모든 앱 재컴파일 | 프로그램 코드가 파일의 물리 구조를 직접 알고 있다 |
| 동시 공유 불가 | 동시 접근·갱신이 어려움 | 여러 사용자 동시 수정 실패 | 파일은 통째로 잠그는 것 말고는 조정 수단이 없다 |
| 보안/회복 부족 | 파일 단위 권한만 제공 | 레코드 단위 권한 제어 불가 | 운영체제는 파일 안의 내용을 모른다 |

중복은 앞 장에서 본 대로 불일치를 낳고, 종속은 구조 변경을 두렵게 만들고, 동시 공유 불가는 조직이 함께 쓴다는 데이터베이스의 전제를 깨고, 보안과 회복이 없다는 것은 사고가 났을 때 되돌릴 수단이 없다는 뜻이다. 넷 중 하나만 고쳐서는 안 되고, 데이터를 프로그램에서 떼어 내 한 곳에서 관리해야 한다.

## 2. DBMS의 정의

DBMS(Database Management System)는 데이터베이스를 생성·관리하고, 응용 프로그램의 데이터 처리 요청을 중개하는 소프트웨어다. 핵심은 **중개**다. 첫째 원리다. 프로그램은 더 이상 파일을 직접 열지 않고 DBMS에 요청하며, 데이터베이스를 실제로 읽고 쓰는 것은 DBMS뿐이다. 중개자가 하나이므로 통합(중복 통제), 독립성(구조 변경 흡수), 동시 공유(접근 조정), 보안과 회복(권한과 로그)이 전부 그 한 자리에서 처리된다.

```text
      사용자
 (DBA, 개발자, 최종 사용자)
        │ SQL
        ▼
 ┌────────────────┐
 │     DBMS       │
 │ 질의 처리기 +   │
 │ 저장 데이터     │
 │ 관리자         │
 └───────┬────────┘
         ▼
 ┌────────────────┐
 │ 데이터베이스    │
 │ 데이터+메타     │
 └────────────────┘
```

질의 처리기는 사용자의 요청을 해석해 실행 방법을 정하고, 저장 데이터 관리자는 디스크의 데이터와 메타데이터를 실제로 읽고 쓴다. 사용자는 "무엇을" 원하는지만 말하고 "어떻게" 찾을지는 DBMS가 정한다. 이 분업이 이 장의 나머지 전부를 떠받친다.

## 3. DBMS의 3가지 핵심 기능

둘째 원리의 자리다. 중개자가 해 주는 일은 셋으로 정리된다.

| 기능 | 설명 | 대표 SQL | 왜 |
|:---|:---|:---|:---|
| 정의 기능 (DDL) | 구조 정의·수정·삭제 | `CREATE`, `ALTER`, `DROP` | 데이터를 담기 전에 담을 틀(스키마)이 있어야 한다 |
| 조작 기능 (DML) | 데이터 삽입·삭제·수정·검색 | `INSERT`, `DELETE`, `UPDATE`, `SELECT` | 틀 안의 값(인스턴스)을 바꾸고 읽는 일이 일상 업무다 |
| 제어 기능 (DCL) | 보안·무결성·동시성·회복 | `GRANT`, `REVOKE`, `COMMIT`, `ROLLBACK` | 여러 사람이 함께 쓰므로 누가 무엇을 할 수 있고 어디까지가 한 작업인지 정해야 한다 |

세 기능은 전부 SQL이라는 한 언어로 요청된다. 문법은 [SQL](../sql)에서 자세히 다루고, 여기서는 기능마다 어떤 문장이 대응하는지만 본다.

### DDL 예제

```sql
CREATE TABLE customers (
    id INT PRIMARY KEY,
    name VARCHAR(100) NOT NULL,
    email VARCHAR(255) UNIQUE,
    created_at DATETIME
        DEFAULT CURRENT_TIMESTAMP
);

ALTER TABLE customers
  ADD phone VARCHAR(20);
DROP TABLE customers;
```

`NOT NULL`, `UNIQUE`, `PRIMARY KEY`처럼 틀에 적어 둔 규칙을 제약조건이라 한다. 규칙을 틀에 적어 두면 어기는 값은 들어오는 순간 거부되므로, 프로그램마다 검사 코드를 따로 쓰지 않아도 된다.

### DML 예제

```sql
INSERT INTO customers (id, name, email)
VALUES (1, '홍길동',
        'hong@example.com');

SELECT * FROM customers
 WHERE name = '홍길동';
UPDATE customers
   SET email = 'new@example.com'
 WHERE id = 1;
DELETE FROM customers WHERE id = 1;
```

### DCL 예제

```sql
GRANT SELECT, INSERT ON customers
   TO user1;
REVOKE INSERT ON customers
  FROM user1;

BEGIN TRANSACTION;
UPDATE accounts
   SET balance = balance - 10000
 WHERE id = 1;
UPDATE accounts
   SET balance = balance + 10000
 WHERE id = 2;
COMMIT;
```

`GRANT`와 `REVOKE`는 누가 무엇을 할 수 있는지를 정하는 권한 제어이고([보안과 권한 관리](../security-authorization)), `COMMIT`과 `ROLLBACK`은 어디까지를 한 작업으로 볼지 정하는 트랜잭션 제어다(13절). 트랜잭션 제어만 따로 떼어 TCL이라 부르기도 한다.

## 4. 스키마와 인스턴스

스키마는 데이터베이스의 구조와 제약조건 정의이고, 인스턴스는 특정 시점에 실제 저장된 데이터 값이다. 3절의 정의 기능이 만드는 것이 스키마, 조작 기능이 바꾸는 것이 인스턴스다.

```text
[Schema] 구조 정의
CREATE TABLE employees (
  id INT PRIMARY KEY,
  name VARCHAR(50) NOT NULL,
  salary DECIMAL(10,2)
);
        │
        ▼
[Instance] 실제 데이터
 id │ name   │ salary
 1  │ 홍길동 │ 50000
 2  │ 김철수 │ 45000
```

| 구분 | 스키마 | 인스턴스 | 왜 |
|:---|:---|:---|:---|
| 성격 | 정적 (거의 변하지 않음) | 동적 (자주 변함) | 틀은 가끔 바뀌고 내용은 매 순간 바뀐다 |
| 내용 | 구조, 제약조건 | 실제 데이터 값 | 무엇을 담을 수 있는가와 지금 무엇이 담겨 있는가의 차이다 |
| 정의 | DDL | DML | 두 기능이 겨누는 대상이 다르다 |

## 5. 3단계 데이터베이스 구조

ANSI/SPARC가 제안한 3단계 구조는 사용자 뷰, 조직 전체 뷰, 물리적 저장을 분리한다. 나누는 이유가 셋째 원리다. 각 단계는 자기 바로 아래 단계만 알고, 단계 사이는 **사상(mapping)**이 잇는다. 그래서 아래 단계가 바뀌면 사상만 고치면 되고 위 단계는 그대로다.

```text
 ┌──────────────────────────┐
 │ 외부 단계 (사용자 뷰)     │
 │ 외부 스키마 1..N         │
 └────────┬─────────────────┘
          │ 외부/개념 사상
 ┌────────┴─────────────────┐
 │ 개념 단계 (조직 뷰)       │
 │ 개념 스키마 (1개)         │
 └────────┬─────────────────┘
          │ 개념/내부 사상
 ┌────────┴─────────────────┐
 │ 내부 단계 (저장 뷰)       │
 │ 내부 스키마 (1개)         │
 └────────┬─────────────────┘
          ▼
      저장 장치
```

| 단계 | 스키마 | 관점 | 개수 | 설명 | 왜 |
|:---|:---|:---|:---|:---|:---|
| 외부 | 외부 스키마 | 개별 사용자 | 여러 개 | 사용자별 필요 데이터만 노출 | 사용자마다 보는 범위와 모양이 다르다 |
| 개념 | 개념 스키마 | 조직 전체 | 1개 | 전체 DB 논리 구조 정의 | 조직의 데이터는 하나의 통합된 그림이어야 한다 |
| 내부 | 내부 스키마 | 저장 장치 | 1개 | 물리적 저장 방법 정의 | 실제로 어떻게 저장하는지는 하나로 정해져 있어야 한다 |

### 외부 스키마 예제 (View)

```sql
-- 개념 스키마
CREATE TABLE employees (
    id INT, name VARCHAR(50),
    salary DECIMAL, ssn VARCHAR(20)
);

-- 외부 스키마 1: 인사팀용
CREATE VIEW hr_view AS
SELECT id, name, salary, ssn
  FROM employees;

-- 외부 스키마 2: 일반 직원용
CREATE VIEW employee_view AS
SELECT id, name FROM employees;
```

뷰는 데이터를 따로 저장하지 않는 가상 테이블이다. 같은 `employees`를 인사팀은 급여와 주민번호까지 보고, 일반 직원은 이름만 본다. 외부 스키마가 여러 개일 수 있다는 말의 실체가 이것이다. 세 단계가 시스템 안에서 어떻게 관리되는지는 [데이터베이스 시스템](../db-system)에서 더 본다.

## 6. 데이터 독립성

3단계 구조의 목적이 데이터 독립성이다. 하위 단계의 변경이 상위 단계에 영향을 주지 않는 성질이고, 두 단계 사이의 사상이 변경을 흡수한다.

| 구분 | 바뀌는 것 | 지켜지는 것 | 왜 |
|:---|:---|:---|:---|
| 논리적 데이터 독립성 | 개념 스키마 | 외부 스키마, 응용 프로그램 | 외부/개념 사상이 변경을 흡수한다 |
| 물리적 데이터 독립성 | 내부 스키마 | 개념 스키마 | 개념/내부 사상이 변경을 흡수한다 |

### 논리적 데이터 독립성

개념 스키마가 변경되어도 외부 스키마와 응용 프로그램은 영향을 받지 않는다.

```sql
ALTER TABLE employees
  ADD department VARCHAR(50);
SELECT * FROM employee_view;
-- 여전히 동작한다
```

테이블에 열이 추가돼도 뷰의 정의는 바뀌지 않았으니 뷰를 쓰는 프로그램은 그 사실을 모른다. 열을 지우거나 이름을 바꾸는 변경은 사상(뷰 정의)을 함께 고쳐야 하지만, 그래도 고치는 곳은 사상 한 곳이다.

### 물리적 데이터 독립성

내부 스키마가 변경되어도 개념 스키마는 그대로 유지된다.

```text
예) HDD → SSD 교체
    인덱스 추가/삭제
    파티셔닝 방식 변경

→ 논리 구조 그대로
→ 응용 프로그램 수정 불필요
```

저장 매체를 바꾸거나 인덱스를 붙이는 것은 개념/내부 사상만 바꾼다. 같은 질의가 같은 결과를 내고, 달라지는 것은 속도뿐이다. 10절의 인덱스가 바로 이 예다.

## 7. DBMS 장단점

### 장점

| 장점 | 설명 | 왜 |
|:---|:---|:---|
| 데이터 중복 통제 | 통합 관리로 중복 최소화 | 데이터를 한 곳에서 관리한다 |
| 데이터 독립성 | 구조 변경 시 앱 영향 최소화 | 3단계 구조와 사상이 변경을 흡수한다 |
| 동시 공유 | 여러 사용자 동시 접근 지원 | 중개자가 접근을 조정한다 |
| 보안 향상 | 세분화된 접근 제어 가능 | DBMS는 데이터의 내용을 알아 행과 열 단위로 통제한다 |
| 무결성 유지 | 제약조건으로 정확성 보장 | 틀에 적어 둔 규칙을 어기는 값은 들어오지 못한다 |
| 표준화 | SQL로 접근 방법 통일 | 모든 요청이 한 언어로 중개자를 거친다 |
| 장애 회복 | 트랜잭션 로그로 복구 | 중개자가 모든 변경을 기록한다 |

### 단점

| 단점 | 설명 | 왜 |
|:---|:---|:---|
| 높은 비용 | 라이선스, 하드웨어, 운영 비용 | 중개자 자체가 크고 복잡한 소프트웨어다 |
| 복잡한 백업/회복 | 대용량 데이터 관리 복잡 | 모든 데이터가 한 곳에 모여 있다 |
| 단일 장애점 | DBMS 장애 시 전체 영향 | 모든 프로그램이 한 중개자를 거친다 |

장점과 단점이 같은 뿌리에서 나온다는 점을 눈여겨볼 만하다. 데이터와 요청이 한 곳을 지나기 때문에 통제가 가능하고, 같은 이유로 그 한 곳이 비싸고 무거우며 멈추면 전부 멈춘다.

## 8. DBMS 발전 과정

```text
 1세대 (1960s)  네트워크/계층
 2세대 (1970s)  관계형 (RDBMS)
 3세대 (1980s)  객체지향/객체관계
 4세대 (2000s)  NoSQL / NewSQL
```

| 세대 | 유형 | 데이터 모델 | 대표 제품 | 왜 |
|:---|:---|:---|:---|:---|
| 1세대 | 네트워크/계층 | 그래프/트리 | IDS, IMS | 레코드를 포인터로 직접 이었다. 빠르지만 구조가 프로그램에 드러난다 |
| 2세대 | 관계형 | 테이블 | Oracle, MySQL | 포인터 대신 값으로 관계를 표현해 구조와 프로그램을 분리했다 |
| 3세대 | 객체지향/객체관계 | 객체 | ObjectStore | 프로그램의 객체를 그대로 저장하려 했다 |
| 4세대 | NoSQL | 문서·키값·컬럼·그래프 | MongoDB, Redis | 대규모 분산 환경의 확장성을 위해 고정 스키마와 즉시 일관성을 양보했다 |
| 4세대 | NewSQL | 테이블(분산) | CockroachDB, Spanner | 분산 확장성과 관계형의 ACID를 함께 가지려 한다 |

세대가 바뀐 것은 중개자의 역할이 아니라 중개자가 쓰는 **데이터 모델**이다. 관계형이 오래 자리를 지킨 이유는 값으로 관계를 표현한다는 단순한 원칙 덕분이고, 그 원칙은 [관계 데이터 모델](../relational-model)에서 다룬다.

### RDBMS vs NoSQL vs NewSQL

| 구분 | RDBMS | NoSQL | NewSQL | 왜 |
|:---|:---|:---|:---|:---|
| 주 용도 | 정형 데이터 | 비정형/반정형 | 정형 + 분산 | 스키마를 미리 정할 수 있는 데이터인가 |
| 일관성 | ACID | BASE | ACID | 분산 환경에서 즉시 일관성은 비용이 크다 |
| 확장 | 수직 | 수평 | 수평 | 한 대를 키우는가, 여러 대로 나누는가 |
| 언어 | SQL | 제품별 API | SQL | 표준 언어는 관계 모델 위에서 자란 것이다 |

NoSQL의 종류와 쓰임은 [데이터 과학과 빅데이터](../data-science-bigdata)에서 다룬다.

## 9. 주요 RDBMS 비교

실무에서 자주 만나는 4개 RDBMS는 라이선스, 특장점, 주 사용처가 뚜렷하게 다르다.

| 제품 | 라이선스 | 특징 | 주 사용처 | 왜 |
|:---|:---|:---|:---|:---|
| MySQL | GPL / 상용 | 가볍고 빠름, 웹 친화 | 웹 서비스, 스타트업 | 설치가 쉽고 읽기 위주 CRUD에 맞춰져 웹과 함께 자랐다 |
| PostgreSQL | BSD 계열 오픈소스 | 표준 SQL 충실, 확장성 풍부 | 분석·지리정보·복잡 쿼리 | 표준 준수와 확장 기능을 우선한 설계다 |
| Oracle | 상용 | 고성능·고가용성, 풍부한 기능 | 대기업·금융·ERP | 오랜 기간 기업용 기능과 지원을 쌓았다 |
| SQL Server | 상용 | .NET/Windows 친화, BI 통합 | 엔터프라이즈 Windows 환경 | 마이크로소프트 생태계와 통합되어 있다 |

{{< callout type="info" >}}
PostgreSQL은 JSONB, 윈도 함수, CTE, 파티셔닝, 사용자 정의 타입 등 고급 기능이 풍부해 "오픈소스 Oracle"로 불린다. MySQL은 단순 CRUD 위주 워크로드에서 압도적인 채택률을 보인다.
{{< /callout >}}

## 10. 인덱스 기본 원리 (B-Tree)

인덱스는 책의 색인처럼 데이터 위치를 빠르게 찾기 위한 별도의 구조다. 대부분의 RDBMS는 기본 인덱스 구조로 **B-Tree(정확히는 B+Tree)** 를 사용한다.

```text
        [50]
       /    \
    [20]    [80]
    / \     / \
 [10][30][60][90]
```

B-Tree는 각 노드에 정렬된 키를 두고 트리 깊이를 낮게 유지해 탐색·삽입·삭제를 모두 `O(log n)` 시간에 수행한다. 키가 정렬되어 있으므로 같은 값 찾기뿐 아니라 범위 검색, 정렬, 접두사 매칭(`LIKE 'abc%'`)에도 쓰인다. 접두사 매칭이 되는 이유는 `'abc'`로 시작하는 값들이 정렬된 키 안에서 연속한 구간을 차지하기 때문이다.

```sql
CREATE INDEX idx_emp_name
    ON employees(name);
CREATE INDEX idx_emp_salary
    ON employees(salary);

-- B-Tree 인덱스가 사용되는 쿼리
SELECT * FROM employees
 WHERE name = '홍길동';
SELECT * FROM employees
 WHERE name LIKE '홍%';
SELECT * FROM employees
 WHERE salary BETWEEN 30000 AND 50000;
```

인덱스를 만들어도 질의는 한 글자도 바뀌지 않는다. 어느 인덱스를 탈지는 질의 처리기가 데이터 사전의 인덱스 정보를 보고 정한다. 6절의 물리적 데이터 독립성이 가장 자주 쓰이는 모습이다.

{{< callout type="warning" >}}
인덱스는 조회는 빠르게 하지만 삽입·수정·삭제 시 인덱스도 함께 갱신되어 쓰기 비용이 증가한다. 선택도가 낮은(카디널리티가 낮은) 컬럼이나 자주 갱신되는 컬럼에 과도하게 인덱스를 걸면 오히려 성능이 떨어진다.
{{< /callout >}}

## 11. 데이터베이스 사용자

| 사용자 | 역할 | 주요 도구 | 왜 |
|:---|:---|:---|:---|
| DBA | 설계·운영·보안·튜닝·백업 | DDL, DCL | 틀과 규칙, 즉 스키마와 권한을 책임진다 |
| 응용 프로그래머 | 앱 개발, SQL 임베딩 | DML, 호스트 언어 | 틀 안의 데이터를 프로그램에서 다룬다 |
| 최종 사용자 | 조회·수정 (GUI·웹) | 간접 DML | 프로그램을 통해서만 데이터에 닿는다 |

세 사용자가 3절의 세 기능과 대응한다. 사용자의 종류와 DBMS 안의 구성 요소는 [데이터베이스 시스템](../db-system)에서 함께 정리한다.

## 12. 데이터 사전 (시스템 카탈로그)

데이터 사전은 테이블, 컬럼, 제약조건, 사용자, 권한 같은 **메타데이터를 저장하는 시스템 DB**다. 3절의 정의 기능이 만든 결과가 저장되는 곳이고, DBMS 자신이 가장 열심히 읽는 곳이다. 질의를 받으면 테이블과 컬럼이 있는지, 요청한 사용자에게 권한이 있는지, 어떤 인덱스를 탈 수 있는지를 전부 여기서 확인한다.

```sql
-- MySQL
SELECT * FROM information_schema.tables
 WHERE table_schema = 'mydb';

SELECT * FROM information_schema.columns
 WHERE table_name = 'employees';

-- PostgreSQL
SELECT * FROM pg_catalog.pg_tables;

-- Oracle
SELECT * FROM user_tables;
SELECT * FROM user_tab_columns
 WHERE table_name = 'EMPLOYEES';
```

| 정보 유형 | 예시 | 왜 |
|:---|:---|:---|
| 테이블 정보 | 테이블명, 생성일, 소유자 | 어떤 틀이 있는지 |
| 컬럼 정보 | 컬럼명, 데이터타입, 제약조건 | 틀의 모양과 규칙 |
| 인덱스 정보 | 인덱스명, 대상 컬럼 | 질의 처리기가 접근 경로를 고를 근거 |
| 사용자 정보 | 사용자명, 권한 | 제어 기능의 근거 |
| 뷰 정보 | 뷰 이름, 정의 쿼리 | 외부 스키마와 사상의 실체 |

데이터 사전도 테이블이므로 SQL로 조회할 수 있다. 다만 제품마다 이름이 다르다. 표준은 `information_schema`이고, PostgreSQL과 Oracle은 자기 카탈로그 뷰를 따로 둔다.

## 13. 트랜잭션과 ACID

트랜잭션은 하나의 논리 작업 단위를 구성하는 연산들의 집합이다. 계좌 이체는 출금과 입금 두 문장이지만 업무로는 한 작업이다. 둘 중 하나만 반영된 상태는 현실에 없다.

```sql
BEGIN TRANSACTION;

UPDATE accounts
   SET balance = balance - 50000
 WHERE account_id = 'A';

UPDATE accounts
   SET balance = balance + 50000
 WHERE account_id = 'B';

COMMIT;
-- 실패 시: ROLLBACK;
```

| 특성 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| Atomicity (원자성) | 전부 수행 또는 전부 취소 | 이체 중 오류 → 전체 롤백 | 반만 된 작업은 현실에 없는 상태다 |
| Consistency (일관성) | 전후 DB 일관성 유지 | 이체 후 총액 동일 | 제약조건과 업무 규칙을 깨는 상태로 끝나면 안 된다 |
| Isolation (격리성) | 동시 트랜잭션 간 간섭 없음 | 다른 이체와 독립 실행 | 함께 쓰는 저장소에서 중간 상태를 남이 보면 안 된다 |
| Durability (지속성) | 완료 결과 영구 보존 | 장애 후에도 유지 | 커밋했다고 답한 뒤 사라지면 믿을 수 없다 |

출금만 반영되고 장애가 나면 `ROLLBACK`으로 출금을 되돌린다. 커밋 전의 변경은 언제든 취소할 수 있고, 커밋한 뒤에는 장애가 나도 남는다. 이것을 보장하는 로그와 잠금의 구조는 [회복과 병행 제어](../recovery-concurrency)에서 다룬다.

## 핵심 정리

| 항목 | 핵심 | 왜 |
|:---|:---|:---|
| 파일 시스템의 한계 | 중복, 종속, 동시 공유 불가, 보안·회복 부족 | 프로그램이 데이터 파일을 직접 소유했다 |
| DBMS | DB 생성·관리·중개 소프트웨어 | 중개자가 하나면 통합·독립성·공유·보안이 한 자리에서 풀린다 |
| DDL/DML/DCL | 정의/조작/제어 언어 | 틀을 만들고, 값을 바꾸고, 규칙을 정하는 세 가지 일이다 |
| 스키마/인스턴스 | 구조 정의 / 실제 데이터 값 | DDL과 DML이 겨누는 대상이 다르다 |
| 3단계 구조 | 외부·개념·내부, 사상으로 연결 | 각 단계가 바로 아래만 알면 변경이 번지지 않는다 |
| 데이터 독립성 | 상위 영향 없이 하위 변경 가능 | 사상이 변경을 흡수한다 |
| 장단점 | 통제가 되는 대신 비싸고 무겁다 | 모든 요청이 한 곳을 지나기 때문에 둘 다 생긴다 |
| 발전 과정 | 네트워크/계층 → 관계형 → 객체 → NoSQL/NewSQL | 바뀐 것은 중개자가 쓰는 데이터 모델이다 |
| B-Tree 인덱스 | 정렬된 트리 기반 빠른 탐색 구조 | 정렬 덕분에 같은 값, 범위, 접두사를 모두 찾는다 |
| 데이터 사전 | 메타데이터 시스템 카탈로그 | 정의의 결과가 저장되고 DBMS가 스스로 읽는다 |
| ACID | 트랜잭션의 4가지 특성 | 반만 된 작업과 사라지는 결과를 막는다 |

{{< callout type="info" >}}
**용어 정리**
- **DBMS**: 데이터베이스 관리 시스템. 응용 프로그램과 데이터 사이의 중개자
- **DDL / DML / DCL / TCL**: 정의·조작·제어·트랜잭션 제어 언어
- **제약조건**: 스키마에 적어 두는 값의 규칙. `NOT NULL`, `UNIQUE`, `PRIMARY KEY` 등
- **스키마 / 인스턴스**: 구조 정의 / 실제 데이터 값
- **3단계 구조**: 외부·개념·내부 단계 (ANSI/SPARC)
- **사상 (mapping)**: 두 단계의 스키마를 잇는 대응 규칙. 변경을 흡수하는 자리
- **뷰 (view)**: 데이터를 저장하지 않는 가상 테이블. 외부 스키마의 실체
- **데이터 독립성**: 논리적(개념→외부) / 물리적(내부→개념)
- **데이터 사전**: 메타데이터를 담는 시스템 카탈로그
- **ACID**: 원자성·일관성·격리성·지속성
- **B-Tree**: 정렬된 트리 기반 인덱스 자료구조
- **RDBMS / NoSQL / NewSQL**: 관계형 / 비관계형 / 분산 관계형
- **MySQL / PostgreSQL / Oracle / SQL Server**: 대표적 RDBMS 제품
{{< /callout >}}
