[데이터베이스 시스템](../db-system)에서 DBMS가 스키마를 데이터 사전에 적어 두고 모든 요청을 처리할 때 그것부터 읽는다는 것을 봤다. 그렇다면 그 스키마, 즉 어떤 테이블에 어떤 열을 두고 무엇을 무엇과 이을지는 누가 어떻게 정할까. 이 장은 그 일, 데이터 모델링을 다룬다. 현실의 업무를 E-R 모델로 그리는 법에서 시작해, 개체·속성·관계를 어떻게 가려내는지, 관계의 수와 참여 방식을 어떻게 적는지, 다 그린 다이어그램을 어떤 규칙으로 테이블로 옮기는지를 본다. 원리는 셋이다. 첫째, **데이터 모델링은 현실을 두 번 옮긴다.** 현실에서 개념 세계로 옮길 때는 무엇을 저장할지만 정하고, 개념 세계에서 컴퓨터 세계로 옮길 때 그것을 DBMS가 이해하는 모양으로 바꾼다. 두 번에 나누는 이유는 바뀌는 이유가 다르기 때문이다. 업무 규칙이 바뀌면 처음부터 다시 옮기고, DBMS가 바뀌면 두 번째 옮기기만 다시 한다. 둘째, **개체는 따로 구별되는 대상, 속성은 그것을 설명하는 값, 관계는 둘 이상을 잇는 사실이다.** 무엇을 개체로 보고 무엇을 속성으로 볼지가 모델링의 핵심 판단이고, 그 판단이 그대로 테이블과 열이 된다. 같은 연락처도 하나뿐이면 열이고, 여럿이면 테이블이 된다. 셋째, **카디널리티와 참여 제약이 외래 키의 자리와 NULL 허용 여부를 정한다.** 열 하나에는 값 하나만 들어간다는 관계 모델의 규칙 때문에 1:N의 외래 키는 N쪽에, M:N은 연결 테이블에 가고, 전체 참여는 `NOT NULL`이 된다. 7절의 변환 규칙은 전부 이 하나에서 나온다.

## 1. 데이터 모델링 개요

데이터 모델링은 현실 세계의 데이터를 데이터베이스로 옮기는 과정이다. 첫째 원리대로 옮기기는 두 번이다. 현실에서 알아낸 개체와 관계를 개념적 구조로 그리고(개념적 모델링), 그것을 DBMS가 지원하는 논리적 구조로 바꾼다(논리적 모델링). 논리적 구조를 저장 장치에 어떻게 둘지 정하는 물리적 모델링이 그 뒤를 잇는다.

```text
현실 세계
 "고객이 상품을 주문한다"
        │
        │ 개념적 모델링
        │ 무엇을 저장할까
        ▼
개념 세계  E-R 다이어그램
 [고객]──<주문>──[상품]
        │
        │ 논리적 모델링
        │ DBMS가 알아듣게
        ▼
컴퓨터 세계  릴레이션 스키마
 CREATE TABLE 고객 (...)
        │
        │ 물리적 모델링
        │ 어떻게 저장할까
        ▼
 인덱스, 파티션, 저장 공간
```

| 단계 | 하는 일 | 산출물 | 무엇에 종속되나 | 왜 |
|:---|:---|:---|:---|:---|
| 개념적 모델링 | 현실 → 개념 세계 | E-R 다이어그램 | 어디에도 종속되지 않음 | 업무를 아는 사람과 무엇을 저장할지 합의하려면 DBMS 용어가 끼면 안 된다 |
| 논리적 모델링 | 개념 → 논리 구조 | 릴레이션 스키마 (테이블, 키) | 데이터 모델 (관계형 등) | DBMS가 지원하는 데이터 모델의 모양이어야 실행할 수 있다 |
| 물리적 모델링 | 논리 → 저장 구조 | 인덱스, 파티션, 저장 공간 | DBMS 제품 | 같은 테이블도 질의 패턴과 제품에 따라 저장 방식이 달라진다 |

논리적 모델링의 산출물은 "관계형"이라는 데이터 모델에는 묶이지만 MySQL이냐 PostgreSQL이냐에는 거의 묶이지 않는다. 제품이 갈리는 것은 물리적 모델링부터다. DBMS를 바꿀 때 개념 모델은 손대지 않고, 논리 모델은 대부분 그대로 쓰며, 물리 모델만 새로 짜는 이유다.

{{< callout type="warning" >}}
이름이 겹쳐 헷갈리기 쉽다. [3단계 구조](../db-system)의 **개념 스키마**는 `CREATE TABLE`로 만든 테이블과 제약조건, 즉 이 장으로 치면 **논리적 모델링의 산출물**이다. 개념적 모델링의 산출물인 E-R 다이어그램은 DBMS 안이 아니라 설계 문서에 있다. 물리적 모델링의 산출물이 3단계 구조의 내부 스키마에 해당한다.
{{< /callout >}}

### 데이터 모델의 3요소

데이터 모델은 데이터를 표현하는 도구이고, 구조·연산·제약조건 세 요소로 이루어진다.

| 요소 | 특성 | 내용 | 관계 데이터 모델에서 | 왜 |
|:---|:---|:---|:---|:---|
| 데이터 구조 (Structure) | 정적 | 개체 타입과 속성, 개체 사이의 관계 | 릴레이션, 속성, 도메인 | 무엇을 어떤 모양으로 담는지가 먼저 정해져야 나머지가 선다 |
| 연산 (Operation) | 동적 | 구조에 담긴 값을 처리하는 작업 | 관계 대수, SQL | 값은 계속 바뀌니 바꾸고 꺼내는 방법이 함께 있어야 한다 |
| 제약조건 (Constraint) | 규칙 | 구조와 값에 허용되는 범위 | 키, 무결성 제약 | 구조만으로는 막지 못하는 잘못된 값을 걸러야 한다 |

E-R 모델은 구조와 제약조건(카디널리티, 참여)은 표현하지만 표준 연산이 없다. 그래서 업무를 그려 합의하는 데는 좋지만 DBMS가 바로 실행할 수는 없고, 연산까지 갖춘 관계 데이터 모델로 옮겨야 한다. 개념적 모델링 다음에 논리적 모델링이 오는 이유가 여기 있다. 관계 데이터 모델의 연산은 [관계 데이터 연산](../relational-operation)에서 본다.

## 2. E-R 모델과 기본 기호

E-R(Entity-Relationship) 모델은 피터 첸(Peter Chen)이 1976년에 제안한 개념적 데이터 모델이다. 현실 세계를 개체(entity)와 개체 사이의 관계(relationship)로 나누어 보고, 개체와 관계는 저마다 속성(attribute)을 가진다. 이것을 그림으로 나타낸 것이 E-R 다이어그램이다. 둘째 원리의 세 요소가 곧 세 종류의 기호다.

| 대상 | 기호 | 이 장의 표기 | 왜 그렇게 그리나 |
|:---|:---|:---|:---|
| 개체 | 사각형 | 상자, 한 줄일 때는 `[개체]` | 따로 구별되는 대상이고 나중에 테이블이 된다 |
| 약한 개체 | 이중 사각형 | 이중 상자 `╔══╗` | 혼자 식별되지 못하고 다른 개체에 기댄다는 표시다 |
| 관계 | 마름모 | `<관계>` | 개체가 아니라 개체 사이의 사실이라 모양을 달리한다 |
| 식별 관계 | 이중 마름모 | `<<관계>>` | 약한 개체에 식별에 필요한 키를 빌려 준다 |
| 속성 | 타원 | `(속성)` | 개체나 관계에 매달린 값이다 |
| 키 속성 | 밑줄 친 타원 | `(_속성_)` | 인스턴스를 구별하는 값이라 눈에 띄게 한다 |
| 다중 값 속성 | 이중 타원 | `((속성))` | 값이 여럿이라 테이블로 따로 뺄 대상이다 |
| 유도 속성 | 점선 타원 | `(-속성-)` | 다른 값에서 계산되므로 저장하지 않아도 된다 |
| 복합 속성 | 타원에 달린 타원 | 들여 쓴 하위 속성 | 더 작은 값으로 나뉜다는 표시다 |
| 전체 참여 | 이중선 | `══`, `║` | 모든 인스턴스가 빠짐없이 관계에 참여한다 |
| 부분 참여 | 단일선 | `──`, `│` | 일부 인스턴스만 참여한다 |

{{< callout type="info" >}}
코드 블록으로는 타원과 마름모를 그릴 수 없어서 이 장의 다이어그램은 표의 셋째 열 표기를 쓴다. 교재나 모델링 도구에서는 둘째 열의 도형으로 보인다.
{{< /callout >}}

## 3. 개체 (Entity)

개체는 현실 세계에서 다른 것과 구별되는 사람, 사물, 개념이다. 고객이나 상품처럼 눈에 보이는 것뿐 아니라 주문, 수강처럼 일어난 사건도 개체가 될 수 있다. 개체 타입은 어떤 속성으로 개체를 설명할지 정한 틀이고, 개체 인스턴스는 그 틀에 실제 값을 채운 하나다. 어느 시점의 인스턴스 전체를 개체 집합이라 한다.

```text
개체 타입: 틀
┌─────────────────────────────┐
│ 고객(고객ID,이름,주소,등급) │
└──────────────┬──────────────┘
               │ 값을 채운다
               ▼
개체 인스턴스: 값 하나하나
┌─────────────────────────────┐
│ 1, 홍길동, 서울, VIP        │
│ 2, 김철수, 부산, 일반       │
│ 3, 이영희, 대전, VIP        │
└─────────────────────────────┘
  인스턴스 전체 = 개체 집합
```

[데이터베이스 시스템](../db-system)의 스키마와 인스턴스가 여기서도 그대로 나타난다. 개체 타입은 좀처럼 바뀌지 않는 틀(내포)이고, 개체 집합은 고객이 가입하고 탈퇴할 때마다 바뀌는 값의 모음(외연)이다.

### 용어 대응

| E-R 모델 | 파일 시스템 | 관계형 DB | 왜 |
|:---|:---|:---|:---|
| 개체 타입 | 레코드 타입 | 테이블 (릴레이션) | 틀 하나가 `CREATE TABLE` 한 번이 된다 |
| 개체 인스턴스 | 레코드 | 행 (투플) | 인스턴스마다 키 값이 달라 행 하나로 구별된다 |
| 개체 집합 | 파일 | 테이블에 저장된 행 전체 | 테이블을 조회하면 그 시점의 개체 집합이 나온다 |
| 속성 | 필드 | 열 (속성) | 대개 속성 하나가 열 하나가 된다. 다중 값·복합 속성은 예외다(7절) |

### 개체인가, 속성인가

둘째 원리에서 가장 자주 부딪히는 판단이다. 요구사항 문장의 명사가 개체 후보가 된다는 요령([데이터베이스 설계](../database-design))은 출발점일 뿐, 모든 명사가 개체는 아니다. 쇼핑몰의 "배송지"를 예로 들면 다음 질문으로 가린다.

| 질문 | 예라면 | 배송지의 경우 | 왜 |
|:---|:---|:---|:---|
| 따로 구별해 가리켜야 하나 | 개체 | 저장해 둔 배송지 가운데 하나를 골라 주문한다 | 다른 데이터가 가리키려면 그 자체에 식별자가 있어야 한다 |
| 자기만의 속성이 더 있나 | 개체 | 수령인, 연락처, 별칭이 따로 붙는다 | 값 하나가 아니라 값의 묶음이면 별도의 틀이 필요하다 |
| 한 대상에 여러 개 붙나 | 별도 테이블 | 고객마다 배송지가 여럿이다 | 열 하나에는 값 하나만 들어간다 |
| 모두 아니오 | 속성 | 주문할 때 주소 한 줄만 적는다 | 대상을 설명하는 값일 뿐이라 열 하나로 충분하다 |

같은 "배송지"라도 업무가 어떻게 쓰느냐에 따라 개체도 되고 속성도 된다. 정답은 업무 규칙이 정하고, 그래서 개념적 모델링은 업무를 아는 사람과 함께 한다.

## 4. 속성 (Attribute)

속성은 개체가 가지는 고유한 특성이고, 의미 있는 데이터의 가장 작은 논리적 단위다. 속성은 몇 가지 기준으로 나뉘는데, 나누는 이유는 모두 테이블로 옮길 때 다르게 다뤄야 하기 때문이다.

### 속성 유형

| 기준 | 유형 | 예 | 표기 | 왜 나누나 |
|:---|:---|:---|:---|:---|
| 값의 개수 | 단일 값 / 다중 값 | 이름 / 연락처, 취미 | `( )` / `(( ))` | 다중 값은 열 하나에 담을 수 없어 테이블을 따로 만든다 |
| 분해 가능성 | 단순 / 복합 | 성별 / 주소 (시·구·동·상세) | `( )` / 하위 속성 | 부분으로 검색하거나 집계할지에 따라 열을 나눌지 정한다 |
| 계산 여부 | 저장 / 유도 | 생년월일 / 나이 | `( )` / `(- -)` | 유도 속성을 저장하면 원본과 어긋날 수 있다 |
| 값의 유무 | 널 속성 | 탈퇴일, 배우자명 | `( )` | `NULL`을 허용할지 정한다 |
| 식별 여부 | 키 속성 | 고객ID, 이메일 | `(_ _)` | 기본키와 후보키가 된다 |

### 고객 개체의 속성 예시

```text
┌──────┐
│ 고객 │
└──┬───┘
   ├─(_고객ID_)   키
   ├─(이름)       단일 값
   ├─((연락처))   다중 값
   ├─(생년월일)   저장
   ├─(-나이-)     유도
   ├─(탈퇴일)     널 허용
   └─(주소)       복합
       ├─(시)
       ├─(구)
       ├─(동)
       └─(상세)
```

유형마다 테이블에서 다뤄지는 방식이 다르다. 자세한 변환은 7절에서 본다.

- **다중 값 속성**: 연락처는 `고객` 테이블의 열이 될 수 없다. 번호 여럿을 열 하나에 넣으면 번호 하나로 고객을 찾거나 지우기가 어려워지므로, 연락처만 담는 테이블을 따로 만든다.
- **복합 속성**: 주소는 시·구·동·상세로 나눌 수도, 한 열로 둘 수도 있다. "강남구 고객 수"처럼 부분으로 검색하거나 집계한다면 나누고, 화면에 출력만 한다면 한 열로 충분하다. 해외 주소처럼 형식이 다른 값이 섞이면 너무 잘게 나눈 열이 오히려 방해가 된다.
- **유도 속성**: 나이는 생년월일에서 계산된다. 나이를 저장하면 해가 바뀔 때마다 모든 행이 틀린 값이 되므로, 생년월일만 저장하고 나이는 조회할 때 계산한다.
- **널 속성**: 탈퇴일처럼 아직 정해지지 않았거나, 배우자명처럼 해당 없는 값이 있으면 `NULL`을 허용하는 열이 된다. 반대로 반드시 있어야 하는 속성에는 `NOT NULL`을 붙인다.
- **키 속성**: 고객ID는 기본키가 된다. 이메일처럼 역시 유일한 속성이 하나 더 있다면 후보키로 보고 `UNIQUE`를 붙인다. 키의 종류는 [관계 데이터 모델](../relational-model)에서 다룬다.

{{< callout type="info" >}}
유도 속성을 굳이 저장해야 한다면, 예를 들어 수량 × 단가로 구하는 주문 금액을 자주 조회한다면, 응용 프로그램이 계산해 넣지 말고 DBMS가 계산하게 하는 편이 안전하다. 생성 열(`금액 DECIMAL(12,2) GENERATED ALWAYS AS (수량 * 단가)`)은 원본 열이 바뀌면 함께 바뀌어 어긋날 일이 없다. PostgreSQL은 17까지 `STORED`를 붙인 저장형만 지원했고, 18부터 계산형(`VIRTUAL`)을 지원한다. 다만 나이는 생성 열로도 만들 수 없다. 생성 열의 식에는 `CURRENT_DATE`처럼 부를 때마다 결과가 달라지는 함수를 쓸 수 없기 때문이다.
{{< /callout >}}

## 5. 관계 (Relationship)

관계는 개체와 개체 사이의 의미 있는 연관이다. "학생이 과목을 수강한다"의 "수강한다"처럼 요구사항의 동사에서 나온다. 관계를 그릴 때 정할 것은 셋이다. 몇 개의 개체가 참여하는가(차수), 각각 몇 개씩 짝이 되는가(카디널리티), 모든 인스턴스가 빠짐없이 참여하는가(참여 제약). 셋째 원리대로 뒤의 둘이 외래 키의 자리와 `NULL` 허용 여부를 정한다.

### 참여 개체 수 (차수)

```text
이항 관계: 두 개체
┌──────┐          ┌──────┐
│ 학생 │──<수강>──│ 과목 │
└──────┘          └──────┘

삼항 관계: 세 개체
┌──────┐          ┌──────┐
│ 고객 │──<구매>──│ 상품 │
└──────┘    │     └──────┘
         ┌──┴───┐
         │ 매장 │
         └──────┘

순환 관계: 같은 개체끼리
┌──────┐ 관리자
│ 사원 │────┐
└──┬───┘    │
   │부하  <관리>
   │        │
   └────────┘
```

이항 관계가 가장 흔하다. 삼항 관계는 세 개체가 한꺼번에 얽힌 사실을 담는다. "고객 A가 매장 X에서 상품 P를 샀다"는 고객과 상품, 고객과 매장, 상품과 매장 사이의 이항 관계 셋으로 쪼개면 표현되지 않는다.

```text
실제 구매 (고객, 상품, 매장)
  (A, P, X)
  (A, Q, Y)
  (B, P, Y)

이항 관계 셋으로 쪼개면
  고객-상품  A-P  A-Q  B-P
  고객-매장  A-X  A-Y  B-Y
  상품-매장  P-X  Q-Y  P-Y

셋을 다시 맞추면
  (A, P, Y)도 성립한다
  A는 Y에서 P를 산 적이 없다
```

쪼갠 세 관계에 A-P, A-Y, P-Y가 모두 있으니 (A, P, Y)를 걸러 낼 방법이 없다. P-Y는 B의 구매에서 왔는데, 쪼개는 순간 누가 산 것인지가 사라졌기 때문이다. 세 개체가 동시에 묶인 사실은 셋을 함께 담는 관계 하나로 그려야 한다.

순환 관계는 같은 개체 타입의 인스턴스끼리 맺는 관계다. 같은 사원이 한쪽에서는 관리자, 다른 쪽에서는 부하라는 역할을 맡으므로 선마다 역할 이름을 붙인다. 테이블에서는 자기 자신을 가리키는 외래 키가 된다(7절).

### 매핑 카디널리티 (Cardinality)

카디널리티는 한 개체의 인스턴스 하나가 상대 개체의 인스턴스 몇 개와 짝이 되는지를 나타낸다. 정하는 방법은 간단하다. 양쪽에서 한 번씩 묻는다.

```text
부서 하나에 사원은?  여럿 (N)
사원 하나에 부서는?  하나 (1)
결론  부서 : 사원 = 1 : N
```

| 유형 | 예 | 의미 | 왜 그렇게 정했나 |
|:---|:---|:---|:---|
| 일대일 (1:1) | 사원 ─ 이끈다 ─ 부서 | 부서마다 부서장은 한 명, 한 사원은 한 부서만 이끈다 | 부서장 겸임을 허용하지 않는다는 규칙 |
| 일대다 (1:N) | 부서 ─ 소속 ─ 사원 | 한 부서에 여러 사원, 사원은 한 부서에만 속한다 | 사원의 소속은 하나라는 규칙 |
| 다대다 (M:N) | 학생 ─ 수강 ─ 과목 | 학생은 여러 과목을, 과목은 여러 학생을 | 수강은 양쪽 모두 여럿이라는 규칙 |

마지막 열이 중요하다. 카디널리티는 자연법칙이 아니라 업무 규칙이다. 겸직을 허용하는 회사라면 부서와 사원은 M:N이 되고, 그러면 테이블 구조가 통째로 바뀐다(7절). 개념적 모델링에서 업무 담당자에게 확인해야 하는 것이 바로 이런 규칙이다. 한쪽만 물으면 1:N을 1:1로, M:N을 1:N으로 잘못 적기 쉽다.

### Chen 표기법과 Crow's Foot 표기법

같은 카디널리티를 두 표기법은 다르게 적는다. Chen 표기법은 관계선 위에 1, N, M 같은 문자를 쓰고, Crow's Foot 표기법은 선 끝의 모양으로 나타낸다. Crow's Foot은 정보 공학(IE, Information Engineering) 표기법이라고도 하며, 실무 ERD 도구에서 가장 널리 쓰인다.

```text
Chen: 선 위에 수를 적는다
┌──────┐ 1        N ┌──────┐
│ 부서 │──<소속>════│ 사원 │
└──────┘            └──────┘

Crow's Foot: 선 끝 모양으로
┌──────┐            ┌──────┐
│ 부서 │─┼┼───────o<│ 사원 │
└──────┘            └──────┘
```

Crow's Foot의 선 끝은 두 기호로 이루어진다. 개체에 붙은 쪽이 최대, 바깥쪽이 최소다. `<`(까마귀 발)는 여럿, `┼`(막대)는 하나, `o`(원)는 없음을 뜻한다. 위 그림에서 부서 쪽 `┼┼`는 "사원 하나에 부서는 정확히 하나", 사원 쪽 `o<`는 "부서 하나에 사원은 없거나 여럿"이다. 아래 표의 마지막 열은 이 그림처럼 1:N이고 외래 키가 N쪽(사원)에 있을 때의 이야기다.

| 선 끝 | 최소 | 최대 | 뜻 | 왜 구분하나 |
|:---|:---|:---|:---|:---|
| `┼┼` | 1 | 1 | 정확히 하나 | 상대 쪽 외래 키가 `NOT NULL`이 된다 |
| `o┼` | 0 | 1 | 없거나 하나 | 상대 쪽 외래 키가 `NULL`을 허용한다 |
| `┼<` | 1 | 여럿 | 하나 이상 | 외래 키만으로는 강제할 수 없다(7절) |
| `o<` | 0 | 여럿 | 없거나 여럿 | 따로 걸 제약이 없다 |

| 표기법 | 카디널리티 | 속성 | 주로 쓰는 곳 | 왜 |
|:---|:---|:---|:---|:---|
| Chen | 선 위의 문자 (1, N, M) | 타원으로 따로 그린다 | 개념적 모델링, 교재 | 관계를 도형으로 따로 그려 관계의 속성과 삼항 관계를 나타내기 쉽다 |
| Crow's Foot | 선 끝 모양 | 개체 상자 안에 목록으로 적는다 | 논리·물리 모델링, 실무 ERD | 상자가 곧 테이블이라 설계도로 바로 읽힌다. 대신 M:N과 관계의 속성은 연결 테이블로 풀어야 그릴 수 있다 |

{{< callout type="warning" >}}
교재에 따라 `(최소, 최대)` 쌍을 적는 표기도 쓴다. 이 표기는 **자기 쪽**에 적는다. 사원 옆의 `(1,1)`은 "사원 하나는 소속 관계에 정확히 한 번 참여한다", 부서 옆의 `(0,N)`은 "부서 하나는 0번 이상 참여한다"는 뜻이다. Chen의 1:N 표기와 Crow's Foot은 반대로 **상대 쪽**에 적는다. 부서 쪽 끝이 "사원 하나에 부서가 몇 개인가"를 말한다. 같은 관계인데 숫자의 위치가 뒤바뀌어 보이는 이유다.
{{< /callout >}}

### 참여 특성

```text
┌──────┐            ┌──────┐
│ 사원 │══<소속>────│ 부서 │
└──────┘            └──────┘
 전체 참여          부분 참여
 모든 사원이        사원이 없는
 어느 부서에 속한다 부서도 있다
```

전체 참여(필수 참여)는 개체의 모든 인스턴스가 관계에 참여하는 것이고, 부분 참여(선택 참여)는 일부만 참여하는 것이다. 이것도 업무 규칙이다. 소속 부서가 정해지지 않은 신입 사원을 허용하는 순간 사원 쪽도 부분 참여가 된다.

| 구분 | 뜻 | Chen | Crow's Foot | 테이블에서 | 왜 |
|:---|:---|:---|:---|:---|:---|
| 전체 참여 | 모든 인스턴스가 참여 | 이중선 | 최소 `┼` | 외래 키 `NOT NULL` | 짝이 없는 행이 들어오면 안 된다 |
| 부분 참여 | 일부만 참여 | 단일선 | 최소 `o` | 외래 키 `NULL` 허용 | 짝이 없는 상태도 정상이다 |

셋째 원리대로 이 차이는 테이블에서 `NOT NULL` 하나로 드러난다. 사원 테이블의 부서ID에 `NOT NULL`을 붙이느냐가 곧 사원이 전체 참여냐다. 다만 외래 키가 자기 테이블에 있을 때만 그렇다. "사원이 한 명도 없는 부서는 없다"처럼 외래 키가 상대 테이블에 있는 쪽의 전체 참여는 `NOT NULL`로 표현되지 않는다. 이 한계는 7절에서 다시 본다.

### 강한 개체와 약한 개체

```text
┌──────┐            ╔══════════╗
│ 사원 │──<<부양>>══║ 부양가족 ║
└──────┘            ╚══════════╝
 강한 개체          약한 개체
 키: 사원ID         구별자: 이름
                    키: 사원ID+이름
```

강한 개체는 자기 키 속성만으로 인스턴스를 구별할 수 있는 개체다. 약한 개체는 그러지 못한다. 부양가족의 이름만으로는 누구네 가족인지 알 수 없다. 두 사원이 저마다 "민준"이라는 자녀를 둘 수 있기 때문이다. 그래서 약한 개체는 주인 개체(owner)의 키를 빌려 와 자기 구별자(discriminator, 부분 키)와 합쳐 식별하고, 키를 빌려 주는 관계를 식별 관계라 한다. 주인 없이는 식별도 존재도 안 되니 약한 개체는 식별 관계에 언제나 전체 참여한다.

| 구분 | 강한 개체 | 약한 개체 | 왜 |
|:---|:---|:---|:---|
| 식별 | 자기 키로 | 주인 키 + 구별자 | 자기 속성만으로는 다른 주인의 것과 겹칠 수 있다 |
| 존재 | 독립 | 주인에 종속 | 주인이 사라지면 가리킬 대상이 없다 |
| 식별 관계 참여 | - | 항상 전체 참여 | 주인 없는 약한 개체는 식별조차 되지 않는다 |
| 테이블에서 | 자기 기본키 | 복합 기본키, `ON DELETE CASCADE` | 주인이 지워지면 함께 지워져야 한다 |

{{< callout type="info" >}}
실무 ERD에서는 관계를 식별 관계와 비식별 관계로 나눈다. 부모의 기본키가 자식의 **기본키 일부**가 되면 식별 관계(실선), 자식의 일반 외래 키로만 들어가면 비식별 관계(점선)다. 약한 개체는 식별 관계의 대표적인 예다. 다만 실무에서는 부양가족에도 `부양가족ID` 같은 대리 키를 주고 사원ID는 `NOT NULL` 외래 키로만 두는 경우가 많다. 식별 관계가 여러 단계 이어지면 손자 테이블의 기본키가 서너 열로 불어나기 때문이다. 이때도 주인에 기대는 존재 종속은 `NOT NULL`과 `ON DELETE CASCADE`로 그대로 남는다.
{{< /callout >}}

## 6. E-R 다이어그램 실전 예제

쇼핑몰의 요구사항으로 E-R 다이어그램을 그려 보자.

- 고객은 고객ID, 이름, 생년월일, 주소를 가지고 연락처를 여러 개 등록할 수 있다.
- 고객은 여러 번 주문할 수 있고, 모든 주문에는 주문한 고객이 있다.
- 주문 하나에 여러 상품을 담을 수 있고, 상품마다 수량과 주문 당시의 가격을 기록한다.
- 상품은 상품ID, 상품명, 가격, 재고를 가진다.

### 쇼핑몰 E-R 다이어그램

```text
        ┌──────────┐
        │   고객   │─┬(_고객ID_)
        └────┬─────┘ ├(이름)
             │ 1     ├(생년월일)
             │       ├(주소)
             │       └((연락처))
        <주문하다>
             ║ N
        ┌────╨─────┐
        │   주문   │─┬(_주문ID_)
        └────╥─────┘ └(주문일자)
             ║ M
           <포함>────┬(수량)
             │ N     └(단가)
        ┌────┴─────┐
        │   상품   │─┬(_상품ID_)
        └──────────┘ ├(상품명)
                     ├(가격)
                     └(재고)
```

1절에서는 "고객이 상품을 주문한다"를 `[고객]──<주문>──[상품]`으로 그렸다. 요구사항을 다시 읽으면 주문은 관계가 아니라 개체다. 배송 조회나 환불을 하려면 주문을 따로 가리켜야 하고, 주문일자 같은 자기 속성이 있으며, 한 번의 주문이 여러 상품을 묶는다. 3절의 질문에 모두 "예"다. 그래서 주문을 개체로 올리고, 고객과 주문 사이에 `<주문하다>`, 주문과 상품 사이에 `<포함>` 관계를 둔다. 둘째 원리의 판단 하나가 그림을 어떻게 바꾸는지 보여 주는 예다.

| 관계 | 카디널리티 | 참여 | 왜 |
|:---|:---|:---|:---|
| 고객 ─ 주문하다 ─ 주문 | 1 : N | 주문은 전체, 고객은 부분 | 한 고객이 여러 번 주문하고 주인 없는 주문은 없다. 가입만 하고 주문하지 않은 고객도 있다 |
| 주문 ─ 포함 ─ 상품 | M : N | 주문은 전체, 상품은 부분 | 한 주문에 여러 상품이, 한 상품이 여러 주문에 담긴다. 빈 주문은 없지만 한 번도 팔리지 않은 상품은 있다 |

수량과 단가가 `<포함>` 관계에 붙은 점도 눈여겨볼 만하다. 수량은 주문에도 상품에도 혼자 속하지 않는다. "주문 101에 담긴 상품 P의 수량"이니 둘이 짝을 이룰 때 비로소 생기는 값, 즉 관계의 속성이다. 단가도 그렇다. 상품의 가격은 나중에 바뀔 수 있지만 이미 끝난 주문의 금액이 따라 바뀌면 안 되므로, 주문할 때의 가격을 관계 쪽에 따로 남긴다. 상품의 가격과 포함의 단가는 같은 값처럼 보여도 뜻이 다른 속성이다.

## 7. E-R 다이어그램 → 릴레이션 변환 규칙

E-R 다이어그램은 아래 규칙으로 테이블로 옮긴다. 규칙이 많아 보이지만 셋째 원리 하나로 꿰인다. 관계 모델에서 열 하나에는 원자 값 하나만 들어간다. 그래서 "여러 개"를 담아야 하는 곳에는 열이 아니라 행이 필요하고, 행이 필요한 자리에 외래 키나 새 테이블이 생긴다.

| E-R 요소 | 관계형 요소 | 변환 규칙 | 왜 |
|:---|:---|:---|:---|
| 개체 | 테이블 | 개체 타입 하나가 테이블 하나 | 개체 인스턴스 하나가 행 하나가 된다 |
| 단순·단일 값 속성 | 열 | 속성 하나가 열 하나 | 값이 하나라 열에 그대로 들어간다 |
| 키 속성 | 기본키 | `PRIMARY KEY` | 행을 구별할 값이 있어야 다른 테이블이 가리킬 수 있다 |
| 복합 속성 | 여러 열 | 하위 속성마다 열 하나 (또는 한 열) | 부분으로 검색할 일이 있으면 나눈다 |
| 다중 값 속성 | 별도 테이블 | 주인 키 + 값을 기본키로 | 값이 여럿이면 열이 아니라 행이 필요하다 |
| 유도 속성 | 저장하지 않음 | 조회할 때 계산, 필요하면 생성 열 | 저장하면 원본과 어긋날 수 있다 |
| 1:N 관계 | 외래 키 | N쪽에 1쪽의 기본키 | N쪽 행 하나는 상대 하나만 가리키니 열 하나로 충분하다 |
| 1:1 관계 | 외래 키 + `UNIQUE` | 전체 참여 쪽에 외래 키 | `UNIQUE`가 없으면 1:N이 되고, 전체 참여 쪽에 두어야 `NULL`이 생기지 않는다 |
| M:N 관계 | 연결 테이블 | 양쪽 기본키를 외래 키로, 둘을 합쳐 기본키로 | 어느 쪽에 두어도 열 하나에 값이 여럿 들어가야 한다 |
| 관계의 속성 | 열 | 1:N이면 N쪽, M:N이면 연결 테이블 | 관계가 저장되는 곳에 그 속성도 둔다 |
| 전체 참여 | `NOT NULL` | 외래 키에 `NOT NULL` | 짝 없는 행을 막는다 |
| 약한 개체 | 복합 기본키 | 주인 기본키 + 구별자, `ON DELETE CASCADE` | 주인 없이는 식별도 존재도 안 된다 |
| 순환 관계 | 자기 참조 외래 키 | 같은 테이블의 기본키를 가리킨다 | 관계의 양 끝이 같은 테이블이다 |
| 삼항 관계 | 연결 테이블 | 세 기본키를 외래 키로 | 세 개체가 한꺼번에 묶인 사실을 한 행에 담는다 |

### 쇼핑몰 스키마

6절의 다이어그램을 옮긴 결과다.

```sql
-- 개체: 테이블 하나
-- 복합 속성 주소: 열 넷
-- 유도 속성 나이: 저장하지 않음
CREATE TABLE 고객 (
    고객ID   INT PRIMARY KEY,
    이름     VARCHAR(50) NOT NULL,
    생년월일 DATE,
    시       VARCHAR(20),
    구       VARCHAR(20),
    동       VARCHAR(20),
    상세주소 VARCHAR(100)
);

CREATE TABLE 상품 (
    상품ID INT PRIMARY KEY,
    상품명 VARCHAR(100) NOT NULL,
    가격   DECIMAL(10,2) NOT NULL,
    재고   INT DEFAULT 0
);

-- 1:N 주문하다: N쪽에 외래 키
-- 주문은 전체 참여: NOT NULL
CREATE TABLE 주문 (
    주문ID   INT PRIMARY KEY,
    고객ID   INT NOT NULL,
    주문일자 DATE NOT NULL,
    FOREIGN KEY (고객ID)
      REFERENCES 고객(고객ID)
);

-- M:N 포함: 연결 테이블
-- 관계의 속성 수량·단가도 여기
CREATE TABLE 주문상세 (
    주문ID INT,
    상품ID INT,
    수량   INT NOT NULL,
    단가   DECIMAL(10,2) NOT NULL,
    PRIMARY KEY (주문ID, 상품ID),
    FOREIGN KEY (주문ID)
      REFERENCES 주문(주문ID),
    FOREIGN KEY (상품ID)
      REFERENCES 상품(상품ID)
);
```

고객ID가 고객 테이블이 아니라 주문 테이블에 들어간 이유가 셋째 원리다. 고객 쪽에 주문ID를 두면 한 고객의 주문 여럿을 열 하나에 넣어야 하지만, 주문 쪽에 고객ID를 두면 주문 하나가 가리키는 고객은 하나뿐이다. 주문과 상품 사이는 양쪽 모두 여럿이라 어느 쪽에도 열 하나로는 담을 수 없고, 그래서 둘의 짝을 한 행씩 담는 연결 테이블이 생긴다. 연결 테이블의 이름은 관계 이름(포함)을 그대로 써도 되지만, 실무에서는 주문상세나 주문항목처럼 무엇을 담는지 드러나는 이름을 흔히 쓴다. 기본키가 (주문ID, 상품ID)이므로 같은 주문에 같은 상품이 두 줄로 들어갈 수 없고, 같은 상품을 더 사면 수량이 늘어난다.

### 다중 값 속성 변환

```sql
-- 잘못된 방법: 한 열에 여러 값
CREATE TABLE 고객_잘못 (
    고객ID INT PRIMARY KEY,
    이름   VARCHAR(50),
    연락처 VARCHAR(100)
);
-- 연락처: '010-1234, 010-5678'

-- 번호로 고객 찾기: 문자열을 훑는다
SELECT 이름
  FROM 고객_잘못
 WHERE 연락처 LIKE '%010-5678%';
```

```sql
-- 올바른 방법: 별도 테이블
CREATE TABLE 고객연락처 (
    고객ID     INT,
    연락처     VARCHAR(20),
    연락처유형 VARCHAR(10),
    PRIMARY KEY (고객ID, 연락처),
    FOREIGN KEY (고객ID)
      REFERENCES 고객(고객ID)
      ON DELETE CASCADE
);

-- 번호로 고객 찾기: 값을 비교한다
SELECT c.이름
  FROM 고객 c
  JOIN 고객연락처 t
    ON t.고객ID = c.고객ID
 WHERE t.연락처 = '010-5678';
```

다중 값 속성을 옮긴 테이블은 주인 개체에 기대어 존재하므로 약한 개체와 같은 모양이 된다. 기본키가 (고객ID, 연락처)이니 한 고객이 같은 번호를 두 번 등록할 수는 없지만, 가족이 같은 집 전화를 쓰듯 서로 다른 고객이 같은 번호를 가질 수는 있다. 휴대폰 번호로 로그인하는 서비스라 번호가 전체에서 유일해야 한다면 `UNIQUE (연락처)`를 더한다. 키를 어디까지 잡느냐도 업무 규칙이다.

{{< callout type="warning" >}}
다중 값 속성을 한 열에 쉼표로 이어 넣으면 원자 값 규칙, 즉 [제1정규형](../normalization)을 어긴다. 번호 하나로 고객을 찾으려면 `LIKE '%010-5678%'`로 문자열 전체를 훑어야 해서 인덱스를 쓸 수 없고, 번호 하나를 지우려면 문자열을 잘라 붙여야 하며, 번호 형식이나 중복을 제약조건으로 검사할 수도 없다. PostgreSQL의 배열이나 JSON 열에 여러 값을 담는 방법도 있지만, 관계 모델 밖으로 나가는 선택이라 그 안의 값에는 외래 키를 걸 수 없다.
{{< /callout >}}

### 1:1, 순환 관계, 약한 개체

사원과 부서로 나머지 규칙을 본다. 사원은 반드시 한 부서에 속하고(1:N, 사원은 전체 참여), 사원 가운데 한 명이 부서를 이끌며(1:1), 사원끼리는 관리자와 부하로 이어진다(순환). 부양가족은 사원의 약한 개체다.

```sql
CREATE TABLE 부서 (
    부서ID   INT PRIMARY KEY,
    부서명   VARCHAR(50) NOT NULL,
    부서장ID INT UNIQUE
);

-- 1:N 소속 + 순환 관계 관리
CREATE TABLE 사원 (
    사원ID   INT PRIMARY KEY,
    이름     VARCHAR(50) NOT NULL,
    부서ID   INT NOT NULL,
    관리자ID INT,
    FOREIGN KEY (부서ID)
      REFERENCES 부서(부서ID),
    FOREIGN KEY (관리자ID)
      REFERENCES 사원(사원ID)
);

-- 1:1 이끈다: 사원이 생긴 뒤 잇는다
ALTER TABLE 부서
  ADD FOREIGN KEY (부서장ID)
      REFERENCES 사원(사원ID);

-- 약한 개체: 주인 키 + 구별자
CREATE TABLE 부양가족 (
    사원ID INT,
    이름   VARCHAR(50),
    관계   VARCHAR(10) NOT NULL,
    PRIMARY KEY (사원ID, 이름),
    FOREIGN KEY (사원ID)
      REFERENCES 사원(사원ID)
      ON DELETE CASCADE
);
```

세 군데를 보면 된다.

- **부서장ID의 `UNIQUE`가 1:1을 만든다.** 이것이 없으면 한 사원이 여러 부서의 부서장이 될 수 있어 사원 : 부서 = 1 : N이 된다. 외래 키는 "가리킨다"까지만 말하고, "한 번만 가리킨다"는 `UNIQUE`가 맡는다.
- **관리자ID는 `NULL`을 허용한다.** 맨 위의 대표에게는 관리자가 없기 때문이다. 순환 관계에서 부하 역할은 대개 부분 참여다. 자기 참조 외래 키는 [관계 데이터 모델](../relational-model)에서 다시 본다.
- **부양가족의 기본키 (사원ID, 이름)이 "주인 키 + 구별자"다.** `ON DELETE CASCADE`는 존재 종속을 표현한다. 사원 행을 지우면 그 사원의 부양가족 행도 함께 지워진다.

규칙은 값이 들어오는 순간 검사된다.

```sql
INSERT INTO 부서 VALUES
  (10, '개발팀', NULL),
  (20, '영업팀', NULL);
INSERT INTO 사원 VALUES
  (1, '김대표', 10, NULL),
  (2, '이팀장', 10, 1),
  (3, '박사원', 20, 2);
UPDATE 부서 SET 부서장ID = 2
 WHERE 부서ID = 10;

-- 한 사람이 두 부서를: UNIQUE 위반
UPDATE 부서 SET 부서장ID = 2
 WHERE 부서ID = 20;

-- 부서 없는 사원: NOT NULL 위반
INSERT INTO 사원
VALUES (4, '최신입', NULL, 2);

-- 사원 삭제: 부양가족도 삭제
INSERT INTO 부양가족
VALUES (3, '박민준', '자녀');
DELETE FROM 사원
 WHERE 사원ID = 3;
```

{{< callout type="warning" >}}
개념적으로는 부서도 이끈다 관계에 전체 참여한다(부서장 없는 부서는 없다). 그러면 부서장ID에 `NOT NULL`을 붙여야 맞지만, 사원의 부서ID도 `NOT NULL`이라 두 테이블이 서로를 반드시 가리키게 된다. 첫 부서를 넣으려면 부서장이 될 사원이, 그 사원을 넣으려면 부서가 먼저 있어야 하니 어느 쪽도 먼저 넣을 수 없다. PostgreSQL, Oracle, SQLite는 외래 키를 `DEFERRABLE INITIALLY DEFERRED`로 만들어 검사를 커밋 시점으로 미룰 수 있지만, MySQL은 외래 키를 언제나 즉시 검사한다. 그래서 위 예처럼 한쪽을 `NULL` 허용으로 두고, 두 행을 넣은 뒤 같은 트랜잭션에서 채우는 방식을 흔히 쓴다.
{{< /callout >}}

### 변환으로 잡히지 않는 제약

외래 키, `NOT NULL`, `UNIQUE`로 대부분의 규칙을 옮길 수 있지만, 그물에 걸리지 않는 것도 있다.

| 개념 모델의 제약 | 예 | 테이블에서는 | 왜 |
|:---|:---|:---|:---|
| 1쪽의 전체 참여 | 빈 주문은 없다 | 트리거나 응용 프로그램이 검사 | 외래 키가 주문상세에 있어 주문 쪽에는 "하나 이상"을 검사할 열이 없다 |
| 서로를 가리키는 전체 참여 | 부서장 없는 부서는 없다 | 지연 제약, 또는 `NULL` 허용 뒤 채우기 | 즉시 검사하면 어느 행도 먼저 넣을 수 없다 |
| 개수의 상한 | 한 주문에 상품은 100종까지 | 트리거나 응용 프로그램이 검사 | 카디널리티의 N에는 상한이 없다 |

SQL 표준에는 여러 테이블에 걸친 조건을 거는 `CREATE ASSERTION`이 있지만, 주요 DBMS 가운데 이를 구현한 제품은 사실상 없다. 그래서 이런 규칙은 트리거나 응용 프로그램이 트랜잭션 안에서 검사한다. 트랜잭션은 [회복과 병행 제어](../recovery-concurrency)에서 다룬다.

## 8. 논리적 데이터 모델

개념적 구조를 DBMS가 지원하는 형태로 옮긴 것이 논리적 데이터 모델이다. 어떤 논리적 모델을 고르느냐에 따라 관계를 표현하는 방법이 달라진다.

| 모델 | 구조 | 관계를 표현하는 법 | 대표 제품 | 왜 지금의 자리인가 |
|:---|:---|:---|:---|:---|
| 관계 데이터 모델 | 2차원 테이블 | 외래 키 **값** | MySQL, PostgreSQL, Oracle | 관계가 값이라 저장 위치와 무관하고, 무엇을만 말하는 질의가 통한다 |
| 계층 데이터 모델 | 트리 | 부모와 자식 사이의 **포인터** | IBM IMS | 자식의 부모가 하나뿐이라 M:N을 표현하려면 데이터를 중복하거나 가상 레코드를 둬야 한다 |
| 네트워크 데이터 모델 | 그래프 | 오너와 멤버 사이의 **포인터** | IDMS (CODASYL) | 한 레코드가 여러 오너에 속할 수 있어 계층보다 낫지만, 포인터를 따라 한 레코드씩 찾아가는 절차적 접근이라 구조가 바뀌면 프로그램도 바뀐다 |

관계 데이터 모델이 자리를 굳힌 이유는 [DBMS 개요](../dbms-overview)에서 본 대로 관계를 값으로 표현한다는 단순한 원칙이다. 포인터는 레코드가 저장된 위치를 가리키니 저장 구조가 바뀌면 함께 바뀌지만, 외래 키 값은 "고객ID가 1인 고객"이라는 뜻만 담고 위치는 DBMS가 찾는다. [데이터베이스 시스템](../db-system)에서 본 물리적 독립성과 비절차적 질의가 그 위에서 성립한다. 7절의 규칙이 외래 키와 연결 테이블만으로 모든 관계를 옮길 수 있었던 것도 이 덕분이다.

### 관계 데이터 모델 구조

```text
고객
┌────────┬────────┐
│ 고객ID │ 이름   │
├────────┼────────┤
│ 1      │ 홍길동 │
│ 2      │ 김철수 │
│ 3      │ 이영희 │
└────────┴────────┘
    ▲ 주문.고객ID = 고객.고객ID
    └───────┐
주문        │
┌────────┬──┴─────┬────────────┐
│ 주문ID │ 고객ID │ 주문일자   │
├────────┼────────┼────────────┤
│ 101    │ 1      │ 2026-01-01 │
│ 102    │ 1      │ 2026-01-05 │
│ 103    │ 2      │ 2026-01-07 │
└────────┴────────┴────────────┘
```

주문 101과 102는 같은 고객 1을 가리킨다. 포인터나 디스크 주소가 아니라 `1`이라는 값이다. 이 표가 다음 장 [관계 데이터 모델](../relational-model)의 출발점이다. 릴레이션, 투플, 도메인이라는 용어와 키, 무결성 제약을 거기서 정식으로 다룬다.

### 모델링 점검표

| 점검할 것 | 놓치면 | 왜 |
|:---|:---|:---|
| 개체마다 키 속성이 있는가 | 같은 고객을 구별하지 못해 중복 행이 생긴다 | 키가 있어야 다른 테이블이 가리킬 수 있다 |
| 다중 값 속성을 별도 테이블로 뺐는가 | 쉼표로 이은 문자열이 생긴다 | 열 하나에는 값 하나만 들어간다 |
| 카디널리티를 양쪽에서 물었는가 | 1:N을 1:1로, M:N을 1:N으로 옮긴다 | 한쪽만 물으면 절반만 안다 |
| 전체 참여를 `NOT NULL`로 옮겼는가 | 부서 없는 사원이 들어온다 | 참여 제약은 `NOT NULL`로 드러난다 |
| 1:1 외래 키에 `UNIQUE`를 붙였는가 | 1:1이 조용히 1:N이 된다 | 외래 키는 "가리킨다"까지만 말한다 |
| M:N을 연결 테이블로 풀었는가 | 한 열에 여러 ID가 들어간다 | 어느 쪽에도 열 하나로는 담을 수 없다 |
| 관계의 속성을 제자리에 두었는가 | 주문 당시의 가격이 사라진다 | 관계가 저장되는 곳에 관계의 속성도 있어야 한다 |
| 약한 개체에 주인 키와 `CASCADE`를 주었는가 | 주인 없는 부양가족이 남는다 | 존재 종속은 삭제 규칙으로 표현된다 |

점검표를 통과한 스키마에도 이상 현상은 남아 있을 수 있다. 그것을 걸러 내는 기준이 [정규화](../normalization)이고, 요구사항 분석부터 물리적 설계까지의 전체 흐름은 [데이터베이스 설계](../database-design)에서 다시 본다.

## 핵심 정리

| 항목 | 핵심 | 왜 |
|:---|:---|:---|
| 데이터 모델링 | 현실 → 개념(E-R) → 논리(테이블) → 물리(저장 구조) | 단계마다 바뀌는 이유가 달라 나누어 옮긴다 |
| 데이터 모델 3요소 | 구조, 연산, 제약조건 | E-R 모델은 연산이 없어 DBMS가 바로 실행할 수 없다 |
| 개체 / 속성 / 관계 | 구별되는 대상 / 설명하는 값 / 잇는 사실 | 이 판단이 그대로 테이블, 열, 외래 키가 된다 |
| 개체 타입 / 개체 집합 | 틀 / 어느 시점의 인스턴스 전체 | 스키마와 인스턴스의 E-R판이다 |
| 속성 유형 | 단일·다중, 단순·복합, 저장·유도, 널, 키 | 유형마다 테이블로 옮기는 법이 다르다 |
| 관계의 차수 | 이항, 삼항, 순환 | 삼항 관계를 이항 셋으로 쪼개면 가짜 사실이 생긴다 |
| 카디널리티 | 1:1, 1:N, M:N | 업무 규칙이고, 외래 키의 자리를 정한다 |
| 참여 제약 | 전체(이중선) / 부분(단일선) | 외래 키의 `NOT NULL` 여부를 정한다 |
| Chen / Crow's Foot | 선 위의 문자 / 선 끝 모양 | 개념 설계는 관계를 그리기 쉽고, 실무 ERD는 테이블로 바로 읽힌다 |
| 약한 개체 | 주인 키 + 구별자, 식별 관계 | 혼자 식별되지 않고 주인 없이 존재하지 않는다 |
| 1:N / 1:1 변환 | N쪽 외래 키 / 외래 키 + `UNIQUE` | 열 하나에는 값 하나만 들어간다 |
| M:N / 다중 값 변환 | 연결 테이블 / 별도 테이블 | 여러 개는 열이 아니라 행으로 담는다 |
| 논리적 데이터 모델 | 관계형이 표준 | 관계를 포인터가 아니라 값으로 표현한다 |

**용어 정리**
- **데이터 모델링**: 현실 세계의 데이터를 데이터베이스 구조로 옮기는 과정. 개념적·논리적·물리적 모델링으로 나뉜다
- **데이터 모델**: 구조, 연산, 제약조건으로 데이터를 표현하는 도구
- **E-R 모델**: 개체, 속성, 관계로 현실을 표현하는 개념적 데이터 모델 (Chen, 1976)
- **개체 (Entity)**: 현실에서 구별되는 사람·사물·개념·사건
- **개체 타입 / 개체 인스턴스 / 개체 집합**: 틀 / 틀에 값을 채운 하나 / 어느 시점의 인스턴스 전체
- **속성 (Attribute)**: 개체나 관계가 가지는 특성. 의미 있는 데이터의 가장 작은 논리적 단위
- **키 속성 (Key Attribute)**: 개체 인스턴스를 구별하는 속성
- **다중 값 / 복합 / 유도 속성**: 값이 여럿인 / 더 작은 속성으로 나뉘는 / 다른 속성에서 계산되는 속성
- **관계 (Relationship)**: 개체 사이의 의미 있는 연관. 관계도 속성을 가질 수 있다
- **차수 (Degree)**: 관계에 참여하는 개체 타입의 수. 이항, 삼항, 순환(같은 개체끼리)
- **매핑 카디널리티 (Cardinality)**: 한 인스턴스가 상대 인스턴스 몇 개와 짝이 되는가 (1:1, 1:N, M:N)
- **전체 참여 / 부분 참여**: 모든 인스턴스가 / 일부만 관계에 참여한다
- **Chen 표기법 / Crow's Foot 표기법**: 선 위의 문자로 / 선 끝 모양으로 카디널리티를 적는 표기법. Crow's Foot은 IE 표기법이라고도 한다
- **약한 개체 (Weak Entity)**: 주인 개체의 키를 빌려야 식별되는 개체
- **구별자 (Discriminator)**: 약한 개체의 부분 키
- **식별 관계 / 비식별 관계**: 부모 키가 자식 기본키의 일부가 되는 / 일반 외래 키로만 들어가는 관계
- **연결 테이블**: M:N 관계를 담는 테이블. 양쪽 기본키를 외래 키로 가진다
- **생성 열 (Generated Column)**: 다른 열에서 DBMS가 계산하는 열. 유도 속성을 저장해야 할 때 쓴다
- **스키마 (Schema)**: 데이터베이스의 구조와 제약조건 정의
