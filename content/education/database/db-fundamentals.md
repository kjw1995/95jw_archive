데이터베이스를 배우기 시작하면 정의부터 외우게 된다. "여러 사용자가 함께 사용할 수 있도록 통합해 저장한 운영 데이터의 집합." 그런데 이 정의의 단어 하나하나가 왜 들어갔는지, 데이터베이스의 네 가지 특징이 왜 그 넷인지는 잘 설명되지 않는다. 이 장은 데이터와 정보의 구분에서 시작해 데이터베이스가 무엇이고 무엇을 약속하는지, 그 안에 담기는 데이터는 어떻게 나뉘는지를 본다. 원리는 셋이다. 첫째, **데이터는 가공을 거쳐야 정보가 된다.** 정보 시스템은 그 가공의 흐름이고, 데이터베이스는 그 흐름의 중심에서 원료인 데이터를 지키는 저장소다. 둘째, **데이터베이스의 정의와 네 가지 특징은 "여러 사람이 함께 쓴다"는 한 가지 사실에서 전부 나온다.** 함께 쓰니 하나로 통합해야 하고, 묻는 즉시 답해야 하고, 현실을 따라 계속 바뀌어야 하고, 동시에 접근해도 되어야 하며, 주소가 아니라 내용으로 찾아야 한다. 셋째, **데이터는 구조가 어디에 있는가와 어떤 연산이 되는가로 나뉘고, 그 구조를 설명하는 것이 스키마와 메타데이터다.** 이 분류가 저장 방식과 분석 방법을 정한다.

## 1. 데이터와 정보

데이터(Data)는 관찰이나 측정으로 수집한, 아직 가공되지 않은 사실이나 값이다. `25`, `서울`, `2024-01-15`는 그 자체로는 아무 판단도 주지 않는다. 정보(Information)는 데이터를 가공하고 해석해 의사결정에 쓸 수 있게 만든 결과물이다. 같은 값들이 "서울의 1월 평균 기온은 영하 2도"처럼 맥락과 묶이면 그제야 판단의 근거가 된다. 첫째 원리의 출발점이다.

```text
  데이터           가공           정보
 ┌───────┐      ─────→      ┌───────┐
 │ 사실  │                  │ 판단  │
 │ 값    │                  │ 근거  │
 └───────┘                  └───────┘
```

| 구분 | 데이터 | 정보 | 왜 |
|:---|:---|:---|:---|
| 정의 | 관찰·측정한 사실과 값 | 가공·해석된 결과물 | 가공 전과 후를 부르는 이름이다 |
| 상태 | 원시 상태 | 의사결정에 활용 가능 | 판단에 바로 쓸 수 있는가로 갈린다 |
| 예시 | `25`, `서울`, `2024-01-15` | "서울 1월 평균 기온 -2도" | 같은 값도 맥락이 붙으면 정보가 된다 |

이 구분이 중요한 이유는 데이터베이스가 **정보가 아니라 데이터**를 저장하기 때문이다. 정보는 질문마다 다르게 만들어지지만, 그 원료인 데이터는 한 번 잘 모아 두면 여러 질문에 다시 쓸 수 있다. 원료를 모아 두는 곳이 데이터베이스다.

## 2. 정보 시스템과 데이터베이스

정보 시스템은 데이터를 수집하고 저장하며 처리해 정보를 제공하는 시스템이다. 네 단계 가운데 저장을 맡는 구성요소가 데이터베이스이고, 나머지 단계는 전부 데이터베이스를 읽고 쓰는 일이다.

```text
 수집 → 저장 → 처리 → 제공
         │
         ▼
    데이터베이스
```

수집된 데이터가 어디에도 저장되지 않으면 처리할 것이 없고, 저장만 되고 처리되지 않으면 정보가 되지 않는다. 데이터베이스가 정보 시스템의 중심에 있다는 말은 그래서 비유가 아니다. 입력도 출력도 결국 데이터베이스를 거친다.

## 3. 데이터 수명 주기

조직에서 다루는 데이터는 정적인 값이 아니라 생성부터 폐기까지 단계적으로 변화한다. 데이터베이스는 이 주기 가운데 저장 단계를 맡지만, 앞뒤 단계가 어떻게 이어지는지 알아야 무엇을 어떤 모양으로 저장할지 정할 수 있다.

```text
 생성 → 가공 → 저장 → 분석 → 폐기
```

| 단계 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| 생성 | 업무 이벤트로 데이터 발생 | 주문 접수, 로그 기록 | 업무가 일어나면 기록이 남아야 한다 |
| 가공 | 정제, 변환, 통합 | 형식 변환, 결측치 처리 | 원시 데이터는 형식이 제각각이라 그대로 쓸 수 없다 |
| 저장 | DB·파일·웨어하우스에 적재 | RDB, 데이터 레이크 | 다시 쓰려면 매체에 남겨야 한다 |
| 분석 | 집계·모델링으로 정보 추출 | BI 리포트, 예측 모델 | 모아 둔 이유는 결국 판단이다 |
| 폐기 | 보존 기한 경과 데이터 삭제 | 개인정보 파기 | 기한을 넘긴 데이터는 자산이 아니라 위험이다 |

{{< callout type="info" >}}
법·규정에 따른 보존 기한과 파기 절차는 수명 주기의 필수 단계다. 삭제되지 않은 개인정보는 보안 사고와 컴플라이언스 위반으로 이어진다.
{{< /callout >}}

## 4. 데이터베이스의 정의

데이터베이스(DB)는 **여러 사용자가 함께 사용할 수 있도록 조직적으로 통합되어 저장된 운영 데이터의 집합**이다. 정의에 들어 있는 네 단어, 공유·통합·저장·운영이 각각 하나의 조건이다. 둘째 원리대로 넷은 모두 "여러 사람이 함께 쓴다"에서 나온다.

```text
 DB = 공유 + 통합 + 저장 + 운영 데이터
```

| 특성 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| 공유 데이터 | 여러 사용자가 함께 사용 | 회사 전체가 고객 DB 공유 | 부서마다 따로 두면 같은 고객이 여러 명이 된다 |
| 통합 데이터 | 중복 최소화, 통제된 중복만 허용 | 고객 정보 단일 관리 | 중복은 불일치를 낳는다 |
| 저장 데이터 | 컴퓨터가 접근 가능한 매체에 저장 | HDD, SSD, 클라우드 | 사람의 기억 속 데이터는 조직의 자산이 아니다 |
| 운영 데이터 | 조직 운영에 필수적인 데이터 | 주문, 재고, 회원 정보 | 임시 계산값이나 개인 메모는 관리 대상이 아니다 |

### 데이터 중복의 문제

통합이라는 조건이 왜 필요한지는 중복을 허용했을 때 무슨 일이 생기는지 보면 된다. 같은 고객의 전화번호가 두 테이블에 따로 있으면, 한쪽만 바뀌는 순간 어느 것이 맞는지 알 수 없다. 값 사이의 불일치, 즉 데이터 일관성이 깨진다.

```text
[중복 허용] B의 번호가 A와 달라 불일치
테이블 A: "홍길동", "010-1234-5678"
테이블 B: "홍길동", "010-9999-8888"

[통합 DB]
고객: id=1, "홍길동", "010-1234-5678"
주문: customer_id=1 (참조만)
```

중복을 없앤다고 하지 않고 **통제**한다고 하는 데도 이유가 있다. 성능이나 가용성을 위해 일부러 복사본을 두는 경우가 있고, 그때는 복사본이 원본을 따라가도록 관리된다는 전제가 붙는다. 문제가 되는 것은 아무도 관리하지 않는 중복이다.

## 5. 데이터베이스의 4가지 특징

네 가지 특징도 같은 뿌리에서 나온다. 여러 사람이 함께 쓰는 데이터 저장소라면 어떤 성질을 가져야 하는가를 적은 목록이다.

### 실시간 접근 (Real-time Accessibility)

사용자 요청에 즉시 응답하는 것이 원칙이다. 함께 쓰는 데이터를 하루 뒤에 받아 볼 수 있다면 그것은 보고서이지 데이터베이스가 아니다. 질의가 들어오는 순간의 값을 돌려줘야 하므로, 데이터베이스는 저장 구조와 인덱스로 응답 시간을 관리한다.

```sql
-- 밀리초 단위 응답
SELECT * FROM orders
 WHERE customer_id = 123;
```

### 계속 변화 (Continuous Evolution)

현실 세계의 상태를 반영하는 것이 목적이므로, 현실이 바뀌면 데이터베이스도 바뀐다. 삽입·수정·삭제가 끊임없이 일어나면서도 전체가 일관된 상태를 유지해야 한다.

```sql
INSERT INTO orders
VALUES (1001, 123, CURRENT_TIMESTAMP);
UPDATE products
   SET stock = stock - 1;
DELETE FROM cart
 WHERE order_completed = true;
```

### 동시 공유 (Concurrent Sharing)

여러 사용자가 같은 데이터 또는 서로 다른 데이터에 동시에 접근할 수 있어야 한다. 한 사람이 쓰는 동안 다른 사람이 기다려야 한다면 공유라 부르기 어렵다. 동시에 같은 행을 바꾸려 할 때 무엇을 보장할지는 트랜잭션과 병행 제어의 몫이고, [회복과 병행 제어](../recovery-concurrency)에서 다룬다.

```text
 사용자 A ─┐
 사용자 B ─┼─→ 데이터베이스
 사용자 C ─┘
```

### 내용으로 참조 (Content Reference)

물리적 주소가 아니라 값(내용)으로 데이터를 찾는다. 파일 시스템에서는 "몇 번째 블록"으로 접근하지만 데이터베이스에서는 "이름이 홍길동인 사원"이라고 묻는다. 데이터가 디스크의 어디에 있는지 사용자가 몰라도 되는 것은 이 성질 덕분이고, 저장 위치를 바꿔도 질문은 그대로다.

```sql
SELECT * FROM employees
 WHERE name = '홍길동';
SELECT * FROM products
 WHERE price > 10000;
SELECT * FROM orders
 WHERE order_date = '2024-01-15';
```

## 6. 데이터 분류

셋째 원리의 자리다. 데이터는 두 축으로 나뉜다. 구조가 어디에 있는가(형태)와 어떤 연산이 가능한가(특성)다. 형태는 어디에 어떻게 저장할지를 정하고, 특성은 무엇을 계산할 수 있는지를 정한다.

### 형태에 따른 분류

```text
 ┌───────────────────────────┐
 │    데이터 형태 분류         │
 ├────────┬────────┬─────────┤
 │ 정형   │ 반정형  │ 비정형  │
 ├────────┼────────┼─────────┤
 │ 스키마 │ 내부   │ 구조     │
 │ 사전   │ 구조   │ 없음     │
 │ 정의   │ 포함   │          │
 ├────────┼────────┼─────────┤
 │ RDB    │ JSON   │ 이미지   │
 │ 시트   │ XML    │ 영상     │
 └────────┴────────┴─────────┘
```

구조가 데이터 **밖에** 미리 정해져 있으면 정형, 데이터 **안에** 함께 들어 있으면 반정형, 구조라 할 것이 없으면 비정형이다. 구조의 위치가 저장 방식을 정한다.

#### 정형 데이터 (Structured)

```sql
CREATE TABLE customers (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    email VARCHAR(255),
    created_at DATETIME
);
```

테이블을 만들 때 열과 타입을 먼저 정하고, 모든 행이 그 모양을 따른다. 구조가 밖에 있으니 데이터 자체는 값만 담으면 되고, 그래서 저장이 촘촘하고 질의가 빠르다. 관계형 데이터베이스가 다루는 데이터이며 [관계 데이터 모델](../relational-model)에서 본격적으로 다룬다.

#### 반정형 데이터 (Semi-structured)

```json
{
  "id": 1,
  "name": "홍길동",
  "email": "hong@example.com",
  "orders": [
    {"id": 101, "amount": 50000},
    {"id": 102, "amount": 30000}
  ]
}
```

```xml
<customer>
  <id>1</id>
  <name>홍길동</name>
  <email>hong@example.com</email>
</customer>
```

키 이름이 값 옆에 붙어 있어 스키마 없이도 읽을 수 있고, 항목마다 모양이 달라도 된다. 구조를 값마다 반복해서 담으니 저장 공간은 더 들지만, 미리 정한 틀이 없어도 데이터를 받을 수 있다는 유연함이 있다. NoSQL 저장소가 이 형태를 즐겨 쓰는 이유이고, [데이터 과학과 빅데이터](../data-science-bigdata)에서 다시 만난다.

#### 비정형 데이터 (Unstructured)

```text
- 이미지 (.jpg, .png)
- 동영상 (.mp4, .avi)
- 문서 (.txt, .pdf)
- 소셜 미디어 게시글
- 음성 (.mp3, .wav)
```

구조가 없으니 내용으로 찾기도 어렵다. 그래서 비정형 데이터는 보통 파일 그대로 두고, 그것을 설명하는 메타데이터(제목, 촬영일, 태그)만 데이터베이스에 넣어 찾는 데 쓴다.

### 특성에 따른 분류

```text
 ┌─────────────────────────┐
 │      데이터 특성         │
 ├──────────────┬──────────┤
 │   범주형      │  수치형   │
 ├──────┬───────┼─────┬────┤
 │ 명목 │ 순서  │이산│연속 │
 └──────┴───────┴─────┴────┘
```

범주형은 **세는** 데이터이고 수치형은 **계산하는** 데이터다. 성별을 1과 2로 저장했다고 평균 1.5를 내는 것은 아무 뜻이 없다. 어떤 연산이 허용되는지를 특성이 정한다.

#### 범주형 데이터

| 유형 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| 명목형 | 서열 없는 분류 | 성별, 혈액형, 지역 | 값 사이에 크고 작음이 없어 개수만 의미가 있다 |
| 순서형 | 서열 있는 분류 | 학점(A>B>C), 만족도 | 순서는 있지만 간격이 같다고 할 수 없어 비교까지만 된다 |

```sql
-- 명목형
SELECT * FROM users WHERE gender = 'M';

-- 순서형
SELECT * FROM reviews WHERE rating >= 4;
```

#### 수치형 데이터

| 유형 | 설명 | 예시 | 왜 |
|:---|:---|:---|:---|
| 이산형 | 셀 수 있는 값 | 주문 수, 클릭 횟수 | 하나씩 셀 수 있어 개수와 합계가 자연스럽다 |
| 연속형 | 측정으로 얻는 값 | 키, 몸무게, 온도 | 어떤 두 값 사이에도 값이 있어 평균과 분포로 다룬다 |

```sql
-- 이산형
SELECT COUNT(*) FROM orders
 WHERE customer_id = 1;

-- 연속형
SELECT AVG(height) FROM students;
```

## 7. 스키마와 메타데이터

정형 데이터는 외부에 스키마가 사전 정의되고, 반정형 데이터는 데이터 내부에 구조 설명(메타데이터)이 함께 담긴다. 어느 쪽이든 데이터만으로는 그 뜻을 알 수 없다는 점은 같다. 구조를 설명하는 정보가 어디에 있는지가 다를 뿐이다.

| 용어 | 설명 | 사용 위치 | 왜 |
|:---|:---|:---|:---|
| 스키마 (Schema) | 사전에 정의된 데이터 구조 | 정형 데이터 | 구조를 먼저 정해야 모든 행이 같은 모양이 된다 |
| 메타데이터 (Metadata) | 데이터 자체에 대한 설명 데이터 | 반정형·전 영역 | 값만 있으면 그것이 무엇인지 알 수 없다 |

### 메타데이터의 역할

메타데이터는 데이터에 대한 데이터다. 단순히 형식 설명에 머물지 않고 데이터 관리·검색·보안의 핵심 수단이 된다.

| 분류 | 예시 | 왜 |
|:---|:---|:---|
| 구조 메타데이터 | 테이블/컬럼 정의, JSON 키 이름 | 어디에 무엇이 있는지 알려 준다 |
| 기술 메타데이터 | 데이터 타입, 크기, 인코딩 | 어떻게 읽고 저장해야 하는지 알려 준다 |
| 업무 메타데이터 | 데이터 의미, 담당자, 출처 | 무슨 뜻이고 누가 책임지는지 알려 준다 |
| 운영 메타데이터 | 생성 시각, 최종 수정, 접근 권한 | 언제 바뀌었고 누가 볼 수 있는지 알려 준다 |

{{< callout type="info" >}}
DBMS는 스키마·제약조건·권한 같은 메타데이터를 **데이터 사전(시스템 카탈로그)** 에 별도로 저장해 질의 최적화와 보안 제어에 활용한다. 데이터 사전이 시스템 안에서 어디에 놓이는지는 [데이터베이스 시스템](../db-system)에서 본다.
{{< /callout >}}

## 8. 정성적 vs 정량적 데이터

| 구분 | 정성적 (Qualitative) | 정량적 (Quantitative) | 왜 |
|:---|:---|:---|:---|
| 의미 | 질적 데이터 | 양적 데이터 | 무엇인가를 말하는가, 얼마인가를 말하는가 |
| 대응 | 범주형 | 수치형 | 6절의 특성 분류를 다른 이름으로 부른 것이다 |
| 연산 | 산술 연산 불가 | 산술 연산 가능 | 숫자가 아니면 더하거나 평균 낼 수 없다 |

## 9. 실무 예시

쇼핑몰 DB는 정형 데이터를 관계형 테이블로 저장하고, 데이터베이스의 4가지 특징을 모두 활용한다. 한 테이블 안에 이 장의 분류가 전부 들어 있다.

```sql
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(200),       -- 명목형
    category VARCHAR(50),    -- 명목형
    price DECIMAL(10,2),     -- 연속형
    stock INT,               -- 이산형
    rating VARCHAR(10)       -- 순서형
);

-- 1. 실시간 접근
SELECT * FROM products WHERE id = 100;

-- 2. 계속 변화
UPDATE products
   SET stock = stock - 1
 WHERE id = 100;

-- 3. 동시 공유 (트랜잭션)
BEGIN TRANSACTION;
UPDATE products
   SET stock = stock - 1
 WHERE id = 100;
INSERT INTO orders
  (product_id, quantity)
VALUES (100, 1);
COMMIT;

-- 4. 내용으로 참조
SELECT * FROM products
 WHERE category = '전자제품'
   AND price BETWEEN 10000 AND 50000;
```

재고를 줄이고 주문을 넣는 두 문장을 하나의 트랜잭션으로 묶은 것이 동시 공유의 실체다. 다른 사용자가 같은 상품을 동시에 주문해도 재고가 둘 다 깎이거나 하나만 깎이는 식으로 어긋나지 않게 하는 장치가 여기서 시작된다.

## 핵심 정리

| 항목 | 핵심 | 왜 |
|:---|:---|:---|
| 데이터와 정보 | 관찰·측정한 값과, 그것을 가공한 판단 근거 | 데이터베이스는 정보가 아니라 재사용할 원료를 저장한다 |
| 정보 시스템 | 수집·저장·처리·제공의 흐름 | 저장을 맡는 데이터베이스를 모든 단계가 거친다 |
| 수명 주기 | 생성 → 가공 → 저장 → 분석 → 폐기 | 기한을 넘긴 데이터는 위험이 된다 |
| 데이터베이스 | 공유·통합·저장·운영 데이터의 집합 | 네 조건이 전부 "함께 쓴다"에서 나온다 |
| 중복 통제 | 없애는 것이 아니라 관리한다 | 관리되지 않은 중복만 불일치를 낳는다 |
| 4가지 특징 | 실시간 접근, 계속 변화, 동시 공유, 내용 참조 | 함께 쓰는 저장소가 갖춰야 할 성질의 목록이다 |
| 형태 분류 | 정형·반정형·비정형 | 구조가 밖에 있는가, 안에 있는가, 없는가 |
| 특성 분류 | 범주형(명목·순서)·수치형(이산·연속) | 세는 데이터와 계산하는 데이터는 허용 연산이 다르다 |
| 스키마와 메타데이터 | 구조를 설명하는 정보 | 값만으로는 뜻을 알 수 없다 |

{{< callout type="info" >}}
**용어 정리**
- **데이터 (Data)**: 관찰·측정으로 수집한 사실과 값
- **정보 (Information)**: 가공·해석되어 판단에 쓰이는 결과물
- **정보 시스템**: 데이터 수집·저장·처리·제공 전반의 시스템
- **데이터베이스**: 공유·통합·저장·운영 데이터의 집합
- **실시간 접근 / 계속 변화 / 동시 공유 / 내용 참조**: DB의 4가지 특징
- **정형 / 반정형 / 비정형**: 구조의 위치와 유무에 따른 데이터 분류
- **범주형 / 수치형**: 특성에 따른 분류. 각각 명목·순서 / 이산·연속으로 세분
- **정성적 / 정량적**: 질적 / 양적 데이터
- **스키마 (Schema)**: 사전에 정의된 데이터 구조
- **메타데이터 (Metadata)**: 데이터에 대한 데이터. 구조·의미·운영 정보
- **데이터 사전 (시스템 카탈로그)**: DBMS가 메타데이터를 모아 두는 곳
- **데이터 수명 주기**: 생성·가공·저장·분석·폐기의 단계적 흐름
- **데이터 중복성**: 동일 데이터가 여러 곳에 존재하는 상태
{{< /callout >}}
