[관계 데이터 모델](../relational-model)에서 데이터를 릴레이션에 담고, 키와 무결성 제약으로 그 값을 믿을 만하게 지키는 법을 봤다. 담았으면 꺼낼 수 있어야 한다. "DB101을 들은 컴퓨터공학과 학생의 이름"을 얻으려면 릴레이션에 어떤 처리를 할지 적을 수단이 필요하고, 관계 데이터 모델은 그 수단으로 관계 대수와 관계 해석을 정의한다. 이 장은 관계 대수의 연산자 여덟 개에서 시작해, 실무에서 자주 쓰는 확장 연산자, 같은 질의를 조건으로 적는 관계 해석, DBMS가 관계 대수로 질의를 고쳐 쓰는 최적화까지 본다. 원리는 셋이다. 첫째, **연산의 입력도 결과도 릴레이션이다.** 결과가 다시 릴레이션이니 그 위에 또 연산을 걸 수 있고, 아무리 복잡한 질의도 작은 연산을 이어 붙인 식 하나로 적힌다. 이를 폐쇄 특성이라 한다. 둘째, **여덟 연산자 가운데 근본은 다섯이다.** 셀렉트, 프로젝트, 합집합, 차집합, 카티션 프로덕트만 있으면 교집합, 조인, 디비전은 그 조합으로 만들어진다. 조인은 카티션 프로덕트에서 짝이 맞는 투플만 고른 것이고, 디비전은 빠진 짝이 있는 후보를 차집합으로 덜어 낸 것이다. 낯선 연산자도 기본 연산으로 풀어 보면 결과가 왜 그렇게 나오는지 보인다. 셋째, **관계 대수와 관계 해석은 표현력이 같다.** 해석은 결과가 만족할 조건만 적고, 대수는 그 결과를 얻는 순서를 적는다. SQL은 해석처럼 무엇을 원하는지만 적게 하고, DBMS는 그것을 대수 식으로 옮긴 뒤 결과가 같은 식 가운데 가장 싼 것을 골라 실행한다. 틈이 하나 있다. 관계 대수는 집합 위의 연산이고 SQL은 멀티셋과 `NULL` 위의 연산이라, 둘이 갈라지는 자리를 절마다 짚는다.

## 1. 관계 데이터 연산의 개념

[데이터 모델링](../data-modeling)에서 데이터 모델은 구조, 연산, 제약조건 세 요소로 이루어진다고 했다. 관계 데이터 모델의 구조(릴레이션)와 제약조건(무결성)은 앞 장에서 봤고, 이 장이 남은 하나인 연산이다. 관계 데이터 연산은 원하는 데이터를 얻으려고 릴레이션에 하는 처리를 적는 방법이고, 관계 대수와 관계 해석 두 가지가 있다.

| 구분 | 관계 대수 (Relational Algebra) | 관계 해석 (Relational Calculus) |
|:---|:---|:---|
| 적는 것 | 결과를 얻는 연산의 순서 | 결과가 만족할 조건 |
| 언어 유형 | 절차적: 어떻게 (how) | 비절차적: 무엇을 (what) |
| 수학적 바탕 | 집합론의 연산 | 술어 논리 (predicate calculus) |
| 주로 쓰이는 곳 | DBMS 안에서 질의를 표현하고 최적화할 때 | SQL, QBE 같은 사용자 언어의 바탕 |
| 표현력 | 같다 | 같다 |

같은 질의를 두 방식으로 적어 보면 차이가 보인다.

```text
질의: CS 학과 학생의 이름

관계 대수: 순서를 적는다
 π(이름)(σ(학과코드='CS')(학생))
 ① 학생에서 CS인 투플을 고르고
 ② 이름 속성만 남긴다

관계 해석: 조건을 적는다
 { t.이름 | 학생(t)
          ∧ t.학과코드 = 'CS' }
 학생의 투플 t 가운데
 학과코드가 CS인 t의 이름
```

```sql
SELECT 이름
  FROM 학생
 WHERE 학과코드 = 'CS';
```

SQL은 관계 해석에 가깝다. `FROM 학생`이 "학생의 투플 t"이고, `WHERE`가 조건, `SELECT`가 결과로 낼 속성이다. 어떤 순서로 처리할지는 적지 않는다. 그 순서를 정하는 일, 즉 해석을 대수로 옮기는 일은 DBMS가 맡는다(8절).

{{< callout type="info" >}}
**관계적으로 완전(Relationally Complete)**: 관계 대수로 표현할 수 있는 모든 질의를 표현할 수 있는 언어를 말한다. 코드가 질의 언어의 기준으로 제안했고, SQL은 이를 만족한다. 다만 완전하다는 것은 하한선이다. 관계 대수에는 개수나 합계를 내는 집계, 정렬, "상사의 상사를 끝까지 따라가기" 같은 반복이 없다. SQL은 여기에 `GROUP BY`, `ORDER BY`, `WITH RECURSIVE`를 더해 관계 대수보다 많은 것을 표현한다. [관계 데이터 모델](../relational-model)의 자기 참조 외래 키에서 본 재귀 질의가 관계 대수 밖의 일이다.
{{< /callout >}}

### 폐쇄 특성 (Closure Property)

첫째 원리다. 관계 대수의 연산은 피연산자도 릴레이션이고 결과도 릴레이션이다. 그래서 한 연산의 결과를 다음 연산의 입력으로 넣어 식을 이어 갈 수 있다. 위의 관계 대수 식을 나무로 그리면 아래에서 위로 계산된다.

```text
      π(이름)          → 2개
         │
  σ(학과코드='CS')      → 2개
         │
       학생            → 4개

 단계마다 결과가 릴레이션이라
 다음 연산의 입력이 된다
```

SQL에서는 질의 결과를 테이블 자리에 넣을 수 있다는 것으로 드러난다. `FROM` 절의 서브쿼리와 [SQL](../sql)의 뷰가 그렇다.

```sql
SELECT cs.이름
  FROM (SELECT *
          FROM 학생
         WHERE 학과코드 = 'CS') cs;
```

안쪽 질의의 결과가 테이블처럼 쓰인다. 폐쇄 특성이 없었다면 질의 결과는 다시 질의할 수 없는, 그 자리에서 끝나는 값이었을 것이다.

{{< callout type="warning" >}}
`ORDER BY`는 폐쇄 특성 밖에 있다. [관계 데이터 모델](../relational-model)에서 본 대로 릴레이션에는 순서가 없으니, 정렬된 결과는 릴레이션이 아니라 목록이다. 그래서 서브쿼리나 뷰 안의 `ORDER BY`는 바깥 질의의 순서를 보장하지 않는다. SQL Server는 `TOP`이나 `OFFSET` 없이 서브쿼리나 뷰에 `ORDER BY`를 쓰면 아예 오류를 낸다. 순서가 필요하면 가장 바깥 질의에 `ORDER BY`를 둔다.
{{< /callout >}}

## 2. 연산자 분류

관계 대수의 연산자 여덟 개는 어디서 왔는지에 따라 둘로 나뉘고, 다른 연산으로 만들 수 있는지에 따라 다시 둘로 나뉜다.

```text
관계 대수 연산자
├─ 일반 집합 연산자
│   ├─ 합집합 ∪          기본
│   ├─ 교집합 ∩          파생
│   ├─ 차집합 −          기본
│   └─ 카티션 프로덕트 × 기본
└─ 순수 관계 연산자
    ├─ 셀렉트 σ          기본
    ├─ 프로젝트 π        기본
    ├─ 조인 ⋈            파생
    └─ 디비전 ÷          파생
```

| 구분 | 연산자 | 기호 | 하는 일 | 기본 연산으로 쓰면 |
|:---|:---|:---|:---|:---|
| 일반 집합 | 합집합 | ∪ | R이나 S에 있는 투플 | 기본 |
| 일반 집합 | 교집합 | ∩ | R과 S에 모두 있는 투플 | R − (R − S) |
| 일반 집합 | 차집합 | − | R에는 있고 S에는 없는 투플 | 기본 |
| 일반 집합 | 카티션 프로덕트 | × | R과 S 투플의 모든 짝 | 기본 |
| 순수 관계 | 셀렉트 | σ | 조건을 만족하는 투플 (행) | 기본 |
| 순수 관계 | 프로젝트 | π | 고른 속성 (열) | 기본 |
| 순수 관계 | 조인 | ⋈ | 조건이 맞는 투플끼리 연결 | σ(조건)(R × S) |
| 순수 관계 | 디비전 | ÷ | S의 모든 투플과 짝이 있는 R의 투플 | π, ×, −의 조합 (5.4) |

일반 집합 연산자는 수학의 집합 연산을 그대로 가져온 것이라 릴레이션을 투플의 집합으로만 본다. 투플 안의 속성은 들여다보지 않는다. 순수 관계 연산자는 관계 데이터 모델을 위해 만든 연산이라 속성을 다룬다. 어느 속성으로 고를지(σ), 어느 속성을 남길지(π), 어느 속성으로 이을지(⋈)를 정한다.

파생 연산자를 따로 두는 이유는 둘이다. 자주 쓰는 조합에 이름을 붙이면 식이 짧아지고, DBMS가 그 조합을 더 싸게 실행할 길을 따로 마련할 수 있다. 조인이 대표적이다. 정의는 카티션 프로덕트를 만든 뒤 고르는 것이지만, 실제 DBMS는 카티션 프로덕트를 만들지 않고 인덱스나 해시로 짝이 맞는 투플만 바로 찾는다.

{{< callout type="info" >}}
교재에 따라 이름 바꾸기(rename, ρ)를 기본 연산에 넣어 여섯으로 세기도 한다. ρ는 값을 하나도 바꾸지 않고 릴레이션이나 속성의 이름만 바꾸지만, 같은 릴레이션을 한 식에 두 번 쓰려면 꼭 필요하다(5.3). SQL의 테이블 별칭이 ρ다.
{{< /callout >}}

## 3. 예제 릴레이션

이 장의 예제는 [관계 데이터 모델](../relational-model)의 학과·학생·과목·수강을 줄여 쓴다. 일부러 빈자리를 셋 두었다. 박민수는 학과를 아직 정하지 않았고(`NULL`) 수강 기록도 없다. 전자공학과(EE)에는 학생이 없다. 조인이 어떤 투플을 떨어뜨리고, `NULL`이 연산을 어떻게 비트는지 보려는 것이다.

```text
학과
┌──────────┬────────────┐
│ 학과코드 │ 학과명     │
├──────────┼────────────┤
│ CS       │ 컴퓨터공학 │
│ BA       │ 경영학     │
│ EE       │ 전자공학   │
└──────────┴────────────┘

학생
┌───────┬────────┬──────┬──────────┐
│ 학번  │ 이름   │ 학년 │ 학과코드 │
├───────┼────────┼──────┼──────────┤
│ 23001 │ 홍길동 │ 2    │ CS       │
│ 23002 │ 김영희 │ 1    │ BA       │
│ 23003 │ 이철수 │ 3    │ CS       │
│ 23004 │ 박민수 │ 1    │ NULL     │
└───────┴────────┴──────┴──────────┘
```

```text
과목
┌──────────┬──────────────┬──────┐
│ 과목번호 │ 과목명       │ 학점 │
├──────────┼──────────────┼──────┤
│ DB101    │ 데이터베이스 │ 3    │
│ OS201    │ 운영체제     │ 3    │
│ NW301    │ 네트워크     │ 2    │
└──────────┴──────────────┴──────┘

수강
┌───────┬──────────┬──────┐
│ 학번  │ 과목번호 │ 성적 │
├───────┼──────────┼──────┤
│ 23001 │ DB101    │ A    │
│ 23001 │ OS201    │ B    │
│ 23001 │ NW301    │ B    │
│ 23002 │ OS201    │ A    │
│ 23003 │ DB101    │ C    │
└───────┴──────────┴──────┘
```

직접 따라 하려면 다음 SQL로 만든다. 이 장의 SQL 결과는 모두 이 데이터 위에서 적었다.

```sql
CREATE TABLE 학과 (
    학과코드 CHAR(2) PRIMARY KEY,
    학과명   VARCHAR(50) NOT NULL
);
CREATE TABLE 학생 (
    학번     CHAR(5) PRIMARY KEY,
    이름     VARCHAR(50) NOT NULL,
    학년     INT NOT NULL,
    학과코드 CHAR(2)
      REFERENCES 학과(학과코드)
);
CREATE TABLE 과목 (
    과목번호 CHAR(5) PRIMARY KEY,
    과목명   VARCHAR(50) NOT NULL,
    학점     INT NOT NULL
);
CREATE TABLE 수강 (
    학번     CHAR(5)
      REFERENCES 학생(학번),
    과목번호 CHAR(5)
      REFERENCES 과목(과목번호),
    성적     CHAR(1),
    PRIMARY KEY (학번, 과목번호)
);

INSERT INTO 학과
  (학과코드, 학과명)
VALUES ('CS', '컴퓨터공학'),
       ('BA', '경영학'),
       ('EE', '전자공학');
INSERT INTO 학생
  (학번, 이름, 학년, 학과코드)
VALUES ('23001', '홍길동', 2, 'CS'),
       ('23002', '김영희', 1, 'BA'),
       ('23003', '이철수', 3, 'CS'),
       ('23004', '박민수', 1, NULL);
INSERT INTO 과목
  (과목번호, 과목명, 학점)
VALUES ('DB101', '데이터베이스', 3),
       ('OS201', '운영체제', 3),
       ('NW301', '네트워크', 2);
INSERT INTO 수강
  (학번, 과목번호, 성적)
VALUES ('23001', 'DB101', 'A'),
       ('23001', 'OS201', 'B'),
       ('23001', 'NW301', 'B'),
       ('23002', 'OS201', 'A'),
       ('23003', 'DB101', 'C');
```

## 4. 일반 집합 연산자

### 합병 가능 조건

합집합, 교집합, 차집합은 두 릴레이션이 합병 가능(union compatible)해야 쓸 수 있다.

| 조건 | 예 | 왜 |
|:---|:---|:---|
| 차수가 같다 | 둘 다 속성이 하나(학번) | 속성 수가 다르면 두 투플이 같은지 비교할 방법이 없다 |
| 대응하는 속성의 도메인이 같다 | 학번과 학번 | 학번 23001과 과목번호 DB101이 한 열에 섞이면 그 열은 아무 사실도 나타내지 않는다 |

속성 이름은 달라도 된다. SQL은 위치로 열의 짝을 짓고, 결과의 열 이름은 첫째 `SELECT`를 따른다.

여기서 SQL은 도메인이 아니라 데이터 타입만 본다. 학번과 과목번호는 둘 다 `CHAR(5)`라서 다음 질의는 오류 없이 학번과 과목번호가 섞인 7건을 돌려준다.

```sql
-- 23001 … 23004, DB101, NW301, OS201
SELECT 학번 FROM 학생
UNION
SELECT 과목번호 FROM 과목;
```

[관계 데이터 모델](../relational-model)에서 도메인에는 비교의 뜻이 담겨 있지만 SQL은 그것을 모른다고 했다. 합병 가능한지는 DBMS가 아니라 질의를 쓰는 사람이 판단해야 한다.

### 예제: 두 과목의 수강생

네 연산을 다음 두 릴레이션으로 본다. 둘 다 수강에서 고른 학번이라 합병 가능하다.

```text
DB = π(학번)(σ(과목번호='DB101')(수강))
OS = π(학번)(σ(과목번호='OS201')(수강))
```

```text
DB (DB101 수강생)    OS (OS201 수강생)
┌───────┐            ┌───────┐
│ 학번  │            │ 학번  │
├───────┤            ├───────┤
│ 23001 │            │ 23001 │
│ 23003 │            │ 23002 │
└───────┘            └───────┘

DB ∪ OS = {23001, 23002, 23003}
DB ∩ OS = {23001}
DB − OS = {23003}
OS − DB = {23002}
```

### 4.1 합집합 (Union): R ∪ S

R이나 S, 또는 둘 다에 속하는 투플을 모은다. DB101이나 OS201을 들은 학생이다. 23001은 양쪽에 있지만 결과에는 한 번만 나온다. 같은 원소가 두 번 들어가지 않는 집합이기 때문이다.

```sql
-- 23001, 23002, 23003
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'DB101'
UNION
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'OS201';
```

`UNION`을 `UNION ALL`로 바꾸면 23001이 두 번 나와 4건이 된다. `UNION`은 중복을 없애려고 결과를 정렬하거나 해시로 한 번 더 훑는다. 두 결과가 겹칠 수 없거나 겹쳐도 상관없다면 `UNION ALL`이 싸다.

### 4.2 교집합 (Intersection): R ∩ S

R과 S에 모두 속하는 투플이다. 두 과목을 모두 들은 23001 하나가 나온다. 교집합은 파생 연산이다. R에서 S에 없는 것(R − S)을 덜어 내면 S에도 있는 것만 남는다.

```text
DB ∩ OS = DB − (DB − OS)
        = {23001, 23003} − {23003}
        = {23001}
```

```sql
-- 23001
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'DB101'
INTERSECT
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'OS201';
```

### 4.3 차집합 (Difference): R − S

R에는 있고 S에는 없는 투플이다. DB − OS는 "DB101은 들었지만 OS201은 듣지 않은 학생" 23003이고, OS − DB는 반대로 23002다. 순서를 바꾸면 답이 바뀌니 차집합에는 교환법칙이 없다.

```sql
-- 23003
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'DB101'
EXCEPT
SELECT 학번 FROM 수강
 WHERE 과목번호 = 'OS201';
```

차집합은 기본 연산 가운데 성질이 특별하다. 합집합, 카티션 프로덕트, 셀렉트, 프로젝트는 입력에 투플이 늘면 결과도 늘거나 그대로다. 차집합만 S에 투플이 늘면 결과가 줄어든다. 그래서 다른 투플이 **없다**는 것을 확인해야 하는 질의, 즉 "OS201을 듣지 않은", "학생이 없는", "모두 들은" 같은 질의에는 차집합이 꼭 필요하다. 한 투플 안의 값만 보는 부정(학과가 CS가 아닌)은 셀렉트로 충분하다. SQL에서는 `EXCEPT`나 `NOT EXISTS`가 차집합 자리에 온다. 디비전이 차집합으로 만들어지는 것(5.4)도 이 때문이다.

{{< callout type="info" >}}
제품마다 이름과 지원 여부가 다르다. Oracle은 차집합을 `MINUS`라 부르고, 21c부터 표준 `EXCEPT`도 받는다. MySQL은 8.0.31부터 `INTERSECT`와 `EXCEPT`를 지원한다. 그 전 버전이라면 `EXISTS`와 `NOT EXISTS`로 바꿔 쓴다(6.1, 6.2).
{{< /callout >}}

### 4.4 카티션 프로덕트 (Cartesian Product): R × S

R의 투플 하나하나에 S의 투플을 모두 이어 붙인다. 차수는 더하고, 투플 수는 곱한다. CS 학생과 3학점 과목의 모든 짝을 만들면 다음과 같다.

```text
CS 학생         3학점 과목
┌────────┐      ┌──────────┐
│ 이름   │      │ 과목번호 │
├────────┤      ├──────────┤
│ 홍길동 │  ×   │ DB101    │
│ 이철수 │      │ OS201    │
└────────┘      └──────────┘

CS 학생 × 3학점 과목
┌────────┬──────────┐
│ 이름   │ 과목번호 │
├────────┼──────────┤
│ 홍길동 │ DB101    │
│ 홍길동 │ OS201    │
│ 이철수 │ DB101    │
│ 이철수 │ OS201    │
└────────┴──────────┘
 차수     1 + 1 = 2
 투플 수  2 × 2 = 4
```

"모든 학생에게 필수 과목을 배정한 목록"처럼 모든 조합 자체가 필요할 때 쓴다. 더 자주는 다른 연산의 재료가 된다. 조인(5.3)과 디비전(5.4)이 카티션 프로덕트에서 출발한다.

```sql
SELECT s.이름, c.과목번호
  FROM 학생 s
 CROSS JOIN 과목 c
 WHERE s.학과코드 = 'CS'
   AND c.학점 = 3;
```

{{< callout type="warning" >}}
`FROM 학생, 수강`처럼 테이블을 쉼표로 나열하고 조인 조건을 빠뜨리면 카티션 프로덕트가 된다. 예제에서는 4 × 5 = 20건으로 끝나지만, 10만 건과 100만 건이면 1,000억 건이다. 결과가 이상하게 많거나 질의가 끝나지 않으면 조인 조건 누락부터 의심한다. `JOIN ... ON`으로 쓰면 조인 조건이 테이블 바로 옆에 붙어 빠진 것이 눈에 잘 띈다.
{{< /callout >}}

### 일반 집합 연산자 요약

표의 R, S는 각 릴레이션의 투플 수다.

| 연산자 | 합병 가능 | 교환법칙 | 결합법칙 | 결과 차수 | 결과 투플 수 | 왜 |
|:---|:---|:---|:---|:---|:---|:---|
| 합집합 ∪ | 필요 | O | O | 그대로 | R + S 이하 | 양쪽에 있는 투플은 한 번만 센다 |
| 교집합 ∩ | 필요 | O | O | 그대로 | min(R, S) 이하 | 양쪽에 다 있어야 남는다 |
| 차집합 − | 필요 | X | X | 그대로 | R 이하 | R에서 덜어 내기만 한다 |
| 카티션 프로덕트 × | 불필요 | O | O | R과 S 차수의 합 | R × S | 모든 짝을 만든다 |

카티션 프로덕트의 교환법칙은 속성에 순서가 없어서 성립한다. R × S와 S × R은 열의 순서만 다르니 같은 릴레이션이다.

### SQL의 집합 연산과 중복

[관계 데이터 모델](../relational-model)에서 SQL 테이블은 멀티셋이라고 했다. 그런데 집합 연산자만은 기본이 중복 제거이고, `ALL`을 붙여야 중복을 남긴다. `SELECT`가 기본으로 중복을 남기고 `DISTINCT`를 붙여야 없애는 것과 정반대다.

| 관계 대수 | SQL (중복 제거) | SQL (중복 유지) | 한쪽에 m번, 다른 쪽에 n번 있는 행이 `ALL`에서 나오는 횟수 |
|:---|:---|:---|:---|
| ∪ | `UNION` | `UNION ALL` | m + n번 |
| ∩ | `INTERSECT` | `INTERSECT ALL` | min(m, n)번 |
| − | `EXCEPT` | `EXCEPT ALL` | max(m − n, 0)번 |

`UNION ALL`은 거의 모든 제품이 지원하지만 `INTERSECT ALL`과 `EXCEPT ALL`은 PostgreSQL, Oracle(21c부터), MySQL(8.0.31부터) 정도만 지원하고 SQL Server와 SQLite에는 없다.

## 5. 순수 관계 연산자

### 5.1 셀렉트 (Select): σ

조건을 만족하는 투플만 고른다. 표에서 행을 고르는 것이라 수평적 부분집합이라고도 한다. 속성은 그대로이니 차수는 같고, 투플 수는 줄거나 같다.

```text
σ(조건)(R)
```

```text
σ(학과코드='CS')(학생)
┌───────┬────────┬──────┬──────────┐
│ 학번  │ 이름   │ 학년 │ 학과코드 │
├───────┼────────┼──────┼──────────┤
│ 23001 │ 홍길동 │ 2    │ CS       │
│ 23003 │ 이철수 │ 3    │ CS       │
└───────┴────────┴──────┴──────────┘

σ(학과코드='CS' ∧ 학년≥3)(학생)
┌───────┬────────┬──────┬──────────┐
│ 학번  │ 이름   │ 학년 │ 학과코드 │
├───────┼────────┼──────┼──────────┤
│ 23003 │ 이철수 │ 3    │ CS       │
└───────┴────────┴──────┴──────────┘
```

조건식에는 비교 연산자와 논리 연산자를 쓴다.

| 관계 대수 | SQL | 뜻 |
|:---|:---|:---|
| `=`, `≠` | `=`, `<>` | 같다, 다르다 |
| `<`, `≤`, `>`, `≥` | `<`, `<=`, `>`, `>=` | 크기 비교 |
| `∧`, `∨`, `¬` | `AND`, `OR`, `NOT` | 그리고, 또는, 아니다 |

```sql
-- 이철수
SELECT *
  FROM 학생
 WHERE 학과코드 = 'CS'
   AND 학년 >= 3;
```

셀렉트는 투플을 하나씩 따로 판정한다. 어떤 투플이 조건을 만족하는지는 다른 투플과 상관없다. 그래서 셀렉트는 순서를 바꾸거나 조건을 쪼개도 결과가 같다.

```text
σ(c1)(σ(c2)(R))
 = σ(c2)(σ(c1)(R))
 = σ(c1 ∧ c2)(R)
```

DBMS는 이 성질로 조건을 쪼개고 순서를 바꾼다(8절).

#### NULL과 셀렉트

조건에 `NULL`이 닿으면 결과는 참도 거짓도 아닌 UNKNOWN이고, 셀렉트는 참인 투플만 고른다. [관계 데이터 모델](../relational-model)에서 본 3값 논리다. 학과가 CS가 아닌 학생을 고르면 이렇게 된다.

```sql
-- 김영희 1건
SELECT 이름 FROM 학생
 WHERE 학과코드 <> 'CS';

-- 김영희, 박민수
SELECT 이름 FROM 학생
 WHERE 학과코드 <> 'CS'
    OR 학과코드 IS NULL;
```

박민수의 학과코드는 `NULL`이라 `= 'CS'`도 `<> 'CS'`도 UNKNOWN이다. 그래서 CS인 학생과 CS가 아닌 학생을 합쳐도 전체가 되지 않는다.

```text
c = (학과코드='CS')

σ(c)(학생) ∪ σ(¬c)(학생) ≠ 학생
 {홍길동, 이철수} ∪ {김영희}
 박민수는 어느 쪽에도 없다
```

"아니다"를 묻는 조건에서는 `NULL`인 투플을 넣을지 뺄지 따로 정해야 한다. 표준의 `IS DISTINCT FROM`은 `NULL`도 값처럼 비교해서, `학과코드 IS DISTINCT FROM 'CS'`는 박민수까지 고른다. PostgreSQL, SQLite(3.39.0부터), SQL Server(2022부터)가 지원하고, MySQL에서는 `NOT (학과코드 <=> 'CS')`로 쓴다.

### 5.2 프로젝트 (Project): π

고른 속성만 남긴다. 표에서 열을 고르는 것이라 수직적 부분집합이라고도 한다. 결과도 릴레이션이니, 속성을 덜어 내서 같아진 투플은 하나로 합쳐진다.

```text
π(속성 리스트)(R)
```

```text
π(이름, 학년)(학생)     π(학년)(학생)
┌────────┬──────┐       ┌──────┐
│ 이름   │ 학년 │       │ 학년 │
├────────┼──────┤       ├──────┤
│ 홍길동 │ 2    │       │ 2    │
│ 김영희 │ 1    │       │ 1    │
│ 이철수 │ 3    │       │ 3    │
│ 박민수 │ 1    │       └──────┘
└────────┴──────┘        1이 하나로
```

학생은 넷인데 π(학년)(학생)은 셋이다. 1학년이 둘이었기 때문이다. 투플 수는 줄거나 같고, 남긴 속성에 후보키가 들어 있으면 같아질 투플이 없어 그대로다. π(학번, 이름)(학생)은 학번이 키라 늘 학생 수와 같다.

SQL의 `SELECT`는 여기서 관계 대수와 갈린다. 중복을 지우지 않는다.

```sql
-- 2, 1, 3, 1: 4건
SELECT 학년 FROM 학생;

-- 1, 2, 3: 3건
SELECT DISTINCT 학년 FROM 학생;
```

SQL이 중복을 기본으로 남기는 이유는 둘이다. 중복을 지우려면 결과를 정렬하거나 해시로 한 번 더 훑어야 해서 비싸다. 그리고 집계에는 중복이 필요하다. 학생들의 평균 학년은 (2 + 1 + 3 + 1) / 4 = 1.75인데, 중복을 지운 {2, 1, 3}으로 계산하면 2가 된다.

```sql
-- 4, 3
SELECT COUNT(학년),
       COUNT(DISTINCT 학년)
  FROM 학생;
```

거꾸로 남긴 열에 키가 있으면 `DISTINCT`는 지울 것이 없어 비용만 더할 수 있다. `DISTINCT`는 중복이 생길 수 있고, 그 중복이 문제가 될 때만 쓴다.

#### 셀렉트와 프로젝트 잇기

폐쇄 특성 덕분에 셀렉트 결과에 바로 프로젝트를 걸 수 있다. 다만 순서가 중요하다.

```text
[올바름] 고른 뒤 남긴다
 π(이름)(σ(학과코드='CS')(학생))
 → {홍길동, 이철수}

[잘못됨] 남긴 뒤 고른다
 σ(학과코드='CS')(π(이름)(학생))
 → π가 학과코드를 지워서
   σ가 볼 속성이 없다
```

SQL에서 `SELECT`에 없는 열로 `WHERE`를 걸 수 있는 것은, SQL이 `FROM`과 `WHERE`를 먼저 처리하고 `SELECT`를 나중에 처리하기 때문이다([SQL](../sql)의 실행 순서). 쓰는 순서는 `SELECT`가 먼저지만 계산은 σ 다음에 π다.

### 5.3 조인 (Join): ⋈

두 릴레이션에서 조건이 맞는 투플끼리 이어 붙인다. 정의는 둘째 원리 그대로, 카티션 프로덕트에 셀렉트를 건 것이다.

```text
R ⋈(조건) S = σ(조건)(R × S)
```

학생과 수강을 학번으로 이으면 정의상 이렇게 계산된다.

```text
  학생 4개      수강 5개
      │            │
      └─────┬──────┘
            ▼  ×
   모든 짝 4 × 5 = 20개
            │
            ▼  σ(학생.학번 = 수강.학번)
   학번이 같은 짝 5개
   = 학생 ⋈ 수강
```

이 절의 그림은 폭을 줄이려고 학생은 학번과 이름만, 수강은 학번과 과목번호만 그린다.

#### 세타 조인과 동등 조인

조건이 `R의 속성 θ S의 속성` 꼴이면 세타 조인(θ-join)이다. θ는 `=`, `≠`, `<`, `≤`, `>`, `≥` 가운데 하나다. θ가 `=`이면 동등 조인(equi join)이고, 외래 키로 잇는 조인은 거의 모두 동등 조인이다.

```text
학생 ⋈(학생.학번 = 수강.학번) 수강
┌───────┬────────┬───────┬──────────┐
│ 학번  │ 이름   │ 학번  │ 과목번호 │
├───────┼────────┼───────┼──────────┤
│ 23001 │ 홍길동 │ 23001 │ DB101    │
│ 23001 │ 홍길동 │ 23001 │ OS201    │
│ 23001 │ 홍길동 │ 23001 │ NW301    │
│ 23002 │ 김영희 │ 23002 │ OS201    │
│ 23003 │ 이철수 │ 23003 │ DB101    │
└───────┴────────┴───────┴──────────┘
 학번 열이 둘이고 값은 늘 같다
 23004 박민수는 짝이 없어 빠진다
```

#### 자연 조인

동등 조인 결과에는 값이 늘 같은 열이 둘 남는다. 같은 값을 두 번 둘 이유가 없으니 하나를 지운 것이 자연 조인(natural join)이다. 조건을 따로 적지 않고, 두 릴레이션에서 이름이 같은 속성을 모두 같다고 놓는다. 교재에 따라 ⋈N으로 적기도 한다.

```text
학생 ⋈ 수강
┌───────┬────────┬──────────┐
│ 학번  │ 이름   │ 과목번호 │
├───────┼────────┼──────────┤
│ 23001 │ 홍길동 │ DB101    │
│ 23001 │ 홍길동 │ OS201    │
│ 23001 │ 홍길동 │ NW301    │
│ 23002 │ 김영희 │ OS201    │
│ 23003 │ 이철수 │ DB101    │
└───────┴────────┴──────────┘
```

이 정의에서 두 극단이 나온다. 이름이 같은 속성이 하나도 없으면 같다고 놓을 조건이 없으니 카티션 프로덕트가 되고, 모든 속성의 이름이 같으면 모든 값이 같은 투플만 남으니 교집합이 된다. 교집합은 자연 조인의 특수한 경우인 셈이다.

```sql
-- 동등 조인: 학번 열이 둘
SELECT *
  FROM 학생
  JOIN 수강 ON 학생.학번 = 수강.학번;

-- 자연 조인: 학번 열이 하나
SELECT *
  FROM 학생 NATURAL JOIN 수강;

-- 조인할 열을 직접 지정
SELECT *
  FROM 학생 JOIN 수강 USING (학번);
```

| 종류 | 조건 | 결과 속성 | 언제 쓰나 |
|:---|:---|:---|:---|
| 세타 조인 | `A θ B` | 양쪽 속성 모두 | 크기 비교로 짝을 지을 때 (이 절 끝의 예) |
| 동등 조인 | `A = B` | 양쪽 속성 모두, 같은 값의 열이 둘 | 외래 키로 이을 때 |
| 자연 조인 | 이름이 같은 속성끼리 `=` | 이름이 같은 속성은 하나만 | 같은 이름이 곧 같은 뜻일 때 |

{{< callout type="warning" >}}
`NATURAL JOIN`은 관계 대수에서는 깔끔하지만 SQL에서는 위험하다. 조인 조건이 열 이름 속에 숨어 있어서, 스키마가 바뀌면 질의를 고치지 않아도 결과가 바뀐다. 학생과 수강에 `수정일` 열을 하나씩 더하면 자연 조인은 학번과 수정일이 모두 같은 짝만 찾는다. 새 열이 모두 `NULL`이면 `NULL = NULL`이 UNKNOWN이라 결과는 0건이다. 학과 테이블의 학과명을 `이름`으로 지었다면 `학생 NATURAL JOIN 학과`는 학생 이름과 학과 이름이 같은 짝을 찾는다. 실무에서는 `USING`이나 `ON`으로 조인할 열을 직접 적는다.
{{< /callout >}}

#### 이름 바꾸기와 셀프 조인

같은 릴레이션을 한 식에 두 번 쓰면 속성 이름이 겹친다. 학생 × 학생에는 학년이 둘인데, 어느 쪽 학년인지 가리킬 방법이 없다. 이름 바꾸기 ρ로 릴레이션에 새 이름을 붙여 구별한다. 세타 조인의 예로 "홍길동보다 학년이 높은 학생"을 찾아 보자.

```text
S1 = ρ(S1)(학생)
S2 = ρ(S2)(학생)
 같은 학생에 이름을 둘 붙인다

π(S2.이름)(
  σ(S1.이름='홍길동')(S1)
  ⋈(S1.학년 < S2.학년) S2 )

 홍길동(2학년)보다 높은 학생
 → {이철수}
```

```sql
-- 이철수
SELECT s2.이름
  FROM 학생 s1
  JOIN 학생 s2
    ON s1.학년 < s2.학년
 WHERE s1.이름 = '홍길동';
```

SQL의 테이블 별칭 `s1`, `s2`가 ρ다. [관계 데이터 모델](../relational-model)의 사원 테이블에서 상사의 이름을 찾는 것도 같은 모양의 셀프 조인이다.

### 5.4 디비전 (Division): ÷

R(X, Y) ÷ S(Y)는 S의 **모든** Y 값과 짝을 이루는 R의 X 값이다. "모두 들은", "모두 가진"처럼 "모든"을 묻는 질의가 디비전이다. "3학점 과목을 모두 들은 학생"을 구해 보자.

```text
R = π(학번, 과목번호)(수강)
S = π(과목번호)(σ(학점=3)(과목))
```

```text
R                    S
┌───────┬──────────┐ ┌──────────┐
│ 학번  │ 과목번호 │ │ 과목번호 │
├───────┼──────────┤ ├──────────┤
│ 23001 │ DB101    │ │ DB101    │
│ 23001 │ OS201    │ │ OS201    │
│ 23001 │ NW301    │ └──────────┘
│ 23002 │ OS201    │
│ 23003 │ DB101    │
└───────┴──────────┘

R ÷ S
┌───────┐
│ 학번  │
├───────┤
│ 23001 │
└───────┘
 23002는 DB101이, 23003은
 OS201이 빠져 제외된다
 23001이 더 들은 NW301은
 상관없다
```

결과의 속성은 R의 속성에서 S의 속성을 뺀 것, 여기서는 학번이다.

#### 기본 연산으로 풀기

디비전은 파생 연산이다. "모두 들었다"를 바로 고를 수는 없으니, 빠진 과목이 하나라도 있는 학생을 찾아 후보에서 덜어 낸다.

```text
R ÷ S = π(학번)(R)
      − π(학번)(
          (π(학번)(R) × S) − R )
```

```text
① 후보: π(학번)(R)
   {23001, 23002, 23003}

② 다 들었다면 있어야 할 짝
   ① × S → 3 × 2 = 6개

③ 그 가운데 R에 없는 짝
   ② − R
   (23002, DB101)
   (23003, OS201)

④ 빠진 과목이 있는 후보
   π(학번)(③)
   {23002, 23003}

⑤ 후보에서 덜어 낸다
   ① − ④ = {23001}
```

차집합이 두 번 들어간다. 4.3에서 본 대로 "모든"은 "빠진 짝이 없다"는 뜻이고, 다른 투플이 없음을 표현하는 기본 연산은 차집합뿐이기 때문이다.

#### SQL로 쓰기

SQL에는 디비전 연산자가 없어서 풀어 쓴다. 하나는 7절에서 관계 해석으로 끌어낼 이중 `NOT EXISTS`이고, 다른 하나는 개수를 세는 것이다. "들은 3학점 과목 수가 3학점 과목 전체 수와 같은 학생"으로 바꿔 묻는다.

```sql
-- 23001
SELECT 학번
  FROM 수강
 WHERE 과목번호 IN
       (SELECT 과목번호 FROM 과목
         WHERE 학점 = 3)
 GROUP BY 학번
HAVING COUNT(DISTINCT 과목번호) =
       (SELECT COUNT(*) FROM 과목
         WHERE 학점 = 3);
```

`WHERE`의 `IN`을 빠뜨리기 쉽다. 빼면 23001이 들은 NW301까지 세어 3이 되고, 3학점 과목 수 2와 맞지 않아 23001이 빠진다. 결과는 0건이다. 세기 전에 S에 있는 과목만 남겨야 한다. `DISTINCT`는 수강의 기본키가 (학번, 과목번호)라 같은 과목이 두 번 세어질 일이 없으면 없어도 되지만, 그런 보장이 없는 테이블에서는 필요하다.

## 6. 확장된 관계 대수 연산자

기본 연산으로 표현은 되지만 자주 쓰여서 이름을 붙인 연산(세미 조인, 안티 조인)과, 기본 연산에는 없는 일을 하는 연산(없는 짝을 `NULL`로 채우는 외부 조인, 새 값을 계산하는 그룹과 집계)을 더한 것이 확장된 관계 대수다.

### 6.1 세미 조인 (Semi Join): ⋉

R ⋉ S는 S에 짝이 있는 R의 투플이다. 조인한 뒤 R의 속성만 남긴 것과 같다.

```text
R ⋉ S = π(R의 속성)(R ⋈ S)
      = R ⋈ π(공통 속성)(S)
```

```text
학생 ⋉ 수강: 수강 기록이 있는 학생
┌───────┬────────┬──────┬──────────┐
│ 학번  │ 이름   │ 학년 │ 학과코드 │
├───────┼────────┼──────┼──────────┤
│ 23001 │ 홍길동 │ 2    │ CS       │
│ 23002 │ 김영희 │ 1    │ BA       │
│ 23003 │ 이철수 │ 3    │ CS       │
└───────┴────────┴──────┴──────────┘
```

조인과 다른 점은 둘이다. 결과에 수강의 속성이 없고, 23001이 세 과목을 들었어도 한 번만 나온다. 조인은 짝마다 투플을 만들지만 세미 조인은 짝이 있는지만 본다. 그래서 교환법칙도 없다. 수강 ⋉ 학생은 학생이 있는 수강 기록이고, 외래 키가 있으니 수강 전체다.

```sql
SELECT *
  FROM 학생
 WHERE 학번 IN (SELECT 학번 FROM 수강);

SELECT *
  FROM 학생 s
 WHERE EXISTS (
       SELECT 1
         FROM 수강 e
        WHERE e.학번 = s.학번);
```

{{< callout type="warning" >}}
"수강 기록이 있는 학생"을 `JOIN`으로 쓰면 홍길동이 세 번 나온다. 그것을 `DISTINCT`로 지우는 질의는 대개 세미 조인을 쓰려던 것이다. 조인으로 투플을 불렸다가 다시 지우는 것보다 `EXISTS`로 짝이 있는지만 묻는 편이 뜻도 분명하고, DBMS도 짝을 하나 찾으면 그 학생은 더 찾지 않아도 된다.
{{< /callout >}}

세미 조인은 분산 데이터베이스에서 특히 쓸모가 크다. 다른 사이트에 있는 두 테이블을 조인할 때 S 전체를 보내지 않고 조인 속성만 보내 짝이 있는 R의 투플을 먼저 추리면, 네트워크로 옮기는 데이터가 줄어든다. 분산 데이터베이스는 [데이터베이스 응용 기술](../db-applications)에서 본다.

### 6.2 안티 조인 (Anti Join): ▷

세미 조인의 반대로, S에 짝이 **없는** R의 투플이다. 차집합으로 정의된다.

```text
R ▷ S = R − (R ⋉ S)
```

학생 ▷ 수강은 수강 기록이 없는 박민수다. 교재의 기본 연산자 목록에는 없지만 "듣지 않은", "학생이 없는"처럼 짝이 없음을 묻는 질의가 모두 이 모양이라 따로 이름이 붙었다. SQL에서는 `NOT EXISTS`로 쓴다.

```sql
-- 박민수
SELECT 이름
  FROM 학생 s
 WHERE NOT EXISTS (
       SELECT 1
         FROM 수강 e
        WHERE e.학번 = s.학번);
```

#### NOT IN과 NULL

안티 조인을 `NOT IN`으로 쓰면 `NULL`에 걸린다. "학생이 한 명도 없는 학과"를 두 가지로 써 보자.

```sql
-- 0건
SELECT 학과코드
  FROM 학과
 WHERE 학과코드 NOT IN
       (SELECT 학과코드 FROM 학생);

-- EE
SELECT 학과코드
  FROM 학과 d
 WHERE NOT EXISTS (
       SELECT 1
         FROM 학생 s
        WHERE s.학과코드 = d.학과코드);
```

서브쿼리 결과에 박민수의 `NULL`이 들어 있는 것이 문제다. `NOT IN`은 목록의 모든 값과 다르다는 뜻이라 `AND`로 풀린다.

```text
'EE' NOT IN ('CS','BA','CS',NULL)
 = 'EE'<>'CS' AND 'EE'<>'BA'
   AND 'EE'<>'CS' AND 'EE'<>NULL
 = 참 AND 참 AND 참 AND UNKNOWN
 = UNKNOWN → 걸러진다
```

목록에 `NULL`이 하나라도 있으면 `NOT IN`은 참이 될 수 없어 결과가 늘 0건이다. `NOT EXISTS`는 짝이 되는 행이 있는지만 묻고, `NULL`인 행은 어느 학과와도 짝이 되지 않을 뿐이라 영향을 받지 않는다. 안티 조인은 `NOT EXISTS`로 쓰고, `NOT IN`을 쓴다면 서브쿼리에 `WHERE 학과코드 IS NOT NULL`을 붙인다. `IN`(세미 조인)은 참인 비교가 하나만 있으면 되므로 이 문제가 없다. `EXCEPT`도 EE를 돌려주는데, 그 이유는 9절에서 본다.

```sql
-- EE
SELECT 학과코드 FROM 학과
EXCEPT
SELECT 학과코드 FROM 학생;
```

### 6.3 외부 조인 (Outer Join)

조인은 짝이 없는 투플을 버린다. 학생과 학과를 학과코드로 자연 조인하면 학과코드가 `NULL`인 박민수와 학생이 없는 EE가 사라진다. 버려지는 투플을 결과에 살리고 빈 속성을 `NULL`로 채운 것이 외부 조인이다. 이 절의 그림은 이름, 학과코드, 학과명만 그린다.

```text
학생 ⋈ 학과
┌────────┬──────────┬────────────┐
│ 이름   │ 학과코드 │ 학과명     │
├────────┼──────────┼────────────┤
│ 홍길동 │ CS       │ 컴퓨터공학 │
│ 김영희 │ BA       │ 경영학     │
│ 이철수 │ CS       │ 컴퓨터공학 │
└────────┴──────────┴────────────┘
 박민수: 학과코드가 NULL이라 짝 없음
 EE: 이 학과의 학생이 없음

학생 ⟗ 학과
┌────────┬──────────┬────────────┐
│ 이름   │ 학과코드 │ 학과명     │
├────────┼──────────┼────────────┤
│ 홍길동 │ CS       │ 컴퓨터공학 │
│ 김영희 │ BA       │ 경영학     │
│ 이철수 │ CS       │ 컴퓨터공학 │
│ 박민수 │ NULL     │ NULL       │ ⟕
│ NULL   │ EE       │ 전자공학   │ ⟖
└────────┴──────────┴────────────┘
 ⟕ 줄: 왼쪽 외부 조인에 더해진다
 ⟖ 줄: 오른쪽 외부 조인에 더해진다
 둘 다 더한 것이 완전 외부 조인
```

| 연산 | 기호 | 결과 | SQL | 언제 쓰나 |
|:---|:---|:---|:---|:---|
| 왼쪽 외부 조인 | ⟕ | 조인 결과 + 짝 없는 왼쪽 투플 | `LEFT [OUTER] JOIN` | 모든 학생과, 있다면 그 학과 |
| 오른쪽 외부 조인 | ⟖ | 조인 결과 + 짝 없는 오른쪽 투플 | `RIGHT [OUTER] JOIN` | 왼쪽 외부 조인에서 테이블 순서만 바꾼 것 |
| 완전 외부 조인 | ⟗ | 조인 결과 + 양쪽의 짝 없는 투플 | `FULL [OUTER] JOIN` | 두 목록을 맞춰 보며 어긋난 것을 찾을 때 |

```sql
SELECT s.이름, d.학과코드, d.학과명
  FROM 학생 s
  LEFT JOIN 학과 d
    ON s.학과코드 = d.학과코드;
```

`LEFT`를 `RIGHT`, `FULL`로 바꾸면 나머지 둘이 된다. 외부 조인은 "없음"까지 세어야 할 때 쓴다. 학과별 학생 수에 학생이 없는 EE도 0으로 나오게 하려면 학과를 왼쪽에 두고 외부 조인한다.

```sql
-- BA 1, CS 2, EE 0
SELECT d.학과코드, COUNT(s.학번)
  FROM 학과 d
  LEFT JOIN 학생 s
    ON s.학과코드 = d.학과코드
 GROUP BY d.학과코드;
```

`COUNT(*)`로 세면 EE가 1이 된다. EE 줄은 학생 속성이 `NULL`로 채워진 한 줄이고, `COUNT(*)`는 줄 수를 세기 때문이다. `COUNT(s.학번)`은 `NULL`을 빼고 센다.

#### WHERE에 둔 조건이 외부 조인을 지운다

"모든 학생과, 들었다면 그 학생의 DB101 성적"을 구한다고 하자.

```sql
-- 홍길동 A, 이철수 C: 2건
SELECT s.이름, e.성적
  FROM 학생 s
  LEFT JOIN 수강 e
    ON e.학번 = s.학번
 WHERE e.과목번호 = 'DB101';

-- 4건: 김영희, 박민수는 NULL
SELECT s.이름, e.성적
  FROM 학생 s
  LEFT JOIN 수강 e
    ON e.학번 = s.학번
   AND e.과목번호 = 'DB101';
```

첫째 질의는 외부 조인으로 박민수를 `NULL`로 살려 놓고, `WHERE`가 셀렉트로 다시 지운다. `NULL = 'DB101'`은 UNKNOWN이기 때문이다. 김영희는 OS201 줄만 있어 거기서 걸러진다. 결과는 그냥 조인과 같아진다. 관계 대수로 쓰면 차이가 분명하다.

```text
① σ(과목번호='DB101')(학생 ⟕ 수강)
   외부 조인한 뒤 고른다: 2건

② 학생 ⟕ σ(과목번호='DB101')(수강)
   수강을 먼저 고르고
   외부 조인한다: 4건
```

외부 조인의 짝을 정하는 조건은 `ON`에, 결과를 거르는 조건은 `WHERE`에 둔다. 오른쪽 테이블의 조건을 `WHERE`에 두면 외부 조인이 사라진다는 점을 기억하자. 이 차이는 8절의 최적화 규칙으로 이어진다.

{{< callout type="info" >}}
MySQL은 `FULL OUTER JOIN`을 지원하지 않는다. 왼쪽 외부 조인에 오른쪽에만 있는 줄을 `UNION ALL`로 더해 만든다. `UNION`으로 합치면 원래부터 값이 같았던 줄까지 하나로 합쳐질 수 있다. SQLite는 3.39.0부터 `RIGHT JOIN`과 `FULL OUTER JOIN`을 지원한다.
{{< /callout >}}

```sql
-- MySQL에서 학생 ⟗ 학과
SELECT s.이름, d.학과코드, d.학과명
  FROM 학생 s
  LEFT JOIN 학과 d
    ON s.학과코드 = d.학과코드
UNION ALL
SELECT s.이름, d.학과코드, d.학과명
  FROM 학생 s
 RIGHT JOIN 학과 d
    ON s.학과코드 = d.학과코드
 WHERE s.학번 IS NULL;
```

### 6.4 그룹과 집계: γ

"학과별 학생 수"처럼 여러 투플을 묶어 값 하나를 계산하는 일은 기본 연산으로 할 수 없다. 기본 연산은 있는 값을 고르고 잇기만 할 뿐, 개수나 합계 같은 새 값을 만들지 않는다. 확장된 관계 대수는 이를 그룹 연산 γ로 적는다. 묶을 속성과 계산할 집계 함수를 함께 쓴다.

```text
γ(학과코드; COUNT(학번))(학생)
┌──────────┬─────────────┐
│ 학과코드 │ COUNT(학번) │
├──────────┼─────────────┤
│ CS       │ 2           │
│ BA       │ 1           │
│ NULL     │ 1           │
└──────────┴─────────────┘
```

```sql
-- CS 2, BA 1, NULL 1
SELECT 학과코드, COUNT(학번)
  FROM 학생
 GROUP BY 학과코드;
```

박민수의 `NULL`이 버려지지 않고 한 그룹이 된다. `WHERE`와 `ON`에서는 `NULL = NULL`이 UNKNOWN이었지만, `GROUP BY`는 `NULL`끼리 같은 그룹으로 묶는다. 이 규칙은 9절에서 정리한다. 집계 함수와 `HAVING`은 [SQL](../sql)에서 자세히 본다.

## 7. 관계 해석

관계 해석은 원하는 결과가 만족할 조건을 술어 논리의 식으로 적는다. 코드가 관계 대수와 함께 내놓은 것이 투플 관계 해석이고, 변수가 값 하나를 가리키게 바꾼 도메인 관계 해석이 뒤에 나왔다.

| 구분 | 투플 관계 해석 | 도메인 관계 해석 |
|:---|:---|:---|
| 변수가 가리키는 것 | 투플 하나 (투플 변수) | 속성 값 하나 (도메인 변수) |
| 범위 지정 | `학생(t)`: t는 학생의 투플 | `학생(h, n, y, d)`: 값 넷이 학생의 투플을 이룬다 |
| 바탕을 둔 언어 | QUEL, SQL | QBE |

식은 다음 재료로 만든다.

| 재료 | 예 | 뜻 |
|:---|:---|:---|
| 원자식 | `학생(t)`, `t.학년 > 2`, `t.학번 = e.학번` | 참과 거짓을 판정할 수 있는 가장 작은 식 |
| 논리 연산자 | `∧`, `∨`, `¬`, `→` | 원자식을 묶는다. `P → Q`는 "P이면 Q" |
| 존재 정량자 | `∃e (…)` | 조건을 만족하는 e가 하나라도 있다 |
| 전칭 정량자 | `∀c (…)` | 모든 c가 조건을 만족한다 |

정량자로 묶인 변수를 속박 변수, 묶이지 않고 결과 자리(`|`의 왼쪽)에 나오는 변수를 자유 변수라 한다.

### 7.1 투플 관계 해석

식은 `{ 결과 | 조건 }` 꼴이다. 두 질의를 적어 보자.

```text
① CS 학과 학생의 이름
{ t.이름 | 학생(t)
         ∧ t.학과코드 = 'CS' }

② DB101을 들은 학생의 이름
{ t.이름 | 학생(t) ∧ ∃e (
    수강(e) ∧ e.학번 = t.학번
    ∧ e.과목번호 = 'DB101' ) }
```

②는 관계 대수로 쓰면 조인이지만, 관계 해석에서는 "그런 수강 투플이 있다(∃)"로 적힌다. SQL의 `EXISTS`가 이 ∃다.

```sql
-- 홍길동, 이철수
SELECT t.이름
  FROM 학생 t
 WHERE EXISTS (
       SELECT 1
         FROM 수강 e
        WHERE e.학번 = t.학번
          AND e.과목번호 = 'DB101');
```

#### ∀와 이중 NOT EXISTS

"3학점 과목을 모두 들은 학생"은 관계 대수에서는 디비전이었지만, 관계 해석에서는 ∀ 하나로 적힌다.

```text
③ 3학점 과목을 모두 들은 학생
{ t.학번 | 학생(t) ∧ ∀c (
    (과목(c) ∧ c.학점 = 3)
    → ∃e ( 수강(e)
         ∧ e.학번 = t.학번
         ∧ e.과목번호
           = c.과목번호 ) ) }
```

SQL에는 ∀가 없다. 그래서 논리 법칙으로 ∃와 ¬만 남게 바꾼다.

```text
∀c (P → Q)
 = ¬∃c ¬(P → Q)
 = ¬∃c (P ∧ ¬Q)

"모든 3학점 과목을 들었다"
 = "3학점이면서 듣지 않은
    과목이 하나도 없다"
```

바깥의 ¬∃가 `NOT EXISTS` 하나, 그 안의 ¬Q, 즉 "그 과목을 들은 수강이 없다"(¬∃e)가 또 하나의 `NOT EXISTS`다. 그래서 디비전은 SQL에서 이중 `NOT EXISTS`로 쓰인다.

```sql
-- 23001
SELECT t.학번
  FROM 학생 t
 WHERE NOT EXISTS (
       SELECT 1
         FROM 과목 c
        WHERE c.학점 = 3
          AND NOT EXISTS (
              SELECT 1
                FROM 수강 e
               WHERE e.학번 = t.학번
                 AND e.과목번호
                   = c.과목번호));
```

5.4의 `COUNT` 버전보다 길지만, 식이 "빠진 것이 없다"는 뜻을 그대로 따르고 `IN`을 빠뜨리는 실수가 생기지 않는다.

{{< callout type="warning" >}}
나누는 쪽이 비면 두 SQL의 답이 갈린다. 4학점 과목은 없으니 `학점 = 3`을 `학점 = 4`로 바꿔 "4학점 과목을 모두 들은 학생"을 물어 보자. 이중 `NOT EXISTS`는 확인할 과목이 하나도 없어 조건이 참이 되므로(공허한 참) 박민수까지 학생 넷을 모두 돌려준다. `COUNT` 버전은 `IN`이 모든 수강을 걸러 0건이다. 관계 대수의 정의대로라면 R의 학번 전부, 즉 수강 기록이 있는 셋이다. 어느 답이 맞는지는 업무 규칙이 정한다. 나누는 쪽이 빌 수 있다면 그 경우를 따로 처리하자.
{{< /callout >}}

### 7.2 도메인 관계 해석

도메인 관계 해석의 변수는 투플이 아니라 값 하나를 가리킨다. 학생의 속성이 넷이니 학생 투플 하나를 변수 넷으로 적는다.

```text
① CS 학과 학생의 이름
{ n | ∃h ∃y ∃d (
    학생(h, n, y, d)
    ∧ d = 'CS' ) }

② DB101을 들은 학생의 이름
{ n | ∃h ∃y ∃d ∃g (
    학생(h, n, y, d)
    ∧ 수강(h, 'DB101', g) ) }

 h 학번, n 이름, y 학년,
 d 학과코드, g 성적
```

②에서 학생과 수강에 같은 변수 h를 쓴 것이 조인 조건이다. 두 투플의 학번 자리에 같은 값이 와야 한다는 뜻이다. 도메인 관계 해석은 표의 칸 하나하나를 변수로 보는 셈이고, 빈 표의 칸에 값이나 변수를 채워 질의하는 QBE(Query By Example)가 이 방식을 따른다.

### 안전한 식

관계 해석으로는 무한한 결과도 적을 수 있다. `{ t | ¬학생(t) }`는 "학생이 아닌 모든 투플"인데, 학생이 아닌 투플은 끝이 없다. 그래서 결과에 나오는 값이 데이터베이스에 있는 값으로 제한되는 안전한 식(safe expression)만 쓴다. 관계 대수와 안전한 관계 해석은 표현력이 같다는 것이 증명되어 있고, 셋째 원리의 근거가 이것이다. SQL은 `FROM`이 변수의 범위를 늘 테이블로 묶으니 자연스럽게 안전한 식만 쓰게 된다.

## 8. 관계 대수와 질의 최적화

[데이터베이스 시스템](../db-system)에서 SQL 한 문장이 파싱, 의미 검사, 뷰 펼치기를 거쳐 최적화 단계에 이른다는 것을 봤다. 그 단계에서 DBMS는 질의를 관계 대수 식(나무)으로 바꾸고, 결과가 같은 다른 식으로 고쳐 쓴 뒤 가장 싼 것을 고른다. 셋째 원리가 실제로 쓰이는 자리다. "DB101을 들은 학생의 이름"을 예로 든다.

```sql
SELECT s.이름
  FROM 학생 s
  JOIN 수강 e ON e.학번 = s.학번
 WHERE e.과목번호 = 'DB101';
```

쓴 그대로 옮기면 ①이고, 셀렉트를 조인 아래로 내리면 ②가 된다.

```text
① 쓴 그대로
        π(이름)
           │
   σ(과목번호='DB101')
           │
           ⋈
        ┌──┴──┐
      학생   수강

② 셀렉트를 먼저
        π(이름)
           │
           ⋈
        ┌──┴──┐
      학생   σ(과목번호='DB101')
              │
             수강
```

예제 데이터로는 차이가 작으니 [관계 데이터 모델](../relational-model)에서 본 규모(학생 3,000명, 수강 52,000건)로 키우고, DB101 수강이 120건이라 하자.

| 계획 | 조인에 들어가는 투플 | 조인 결과 | 왜 |
|:---|:---|:---|:---|
| ① 조인 먼저 | 학생 3,000, 수강 52,000 | 52,000 | 모든 수강을 학생과 이은 뒤에야 DB101을 고른다 |
| ② 셀렉트 먼저 | 학생 3,000, 수강 120 | 120 | 조인 전에 DB101이 아닌 수강 51,880건을 버린다 |

두 식의 결과가 같다는 것은 데이터와 상관없이 수학적으로 보장된다. 그래서 DBMS는 사용자가 어떤 순서로 썼든 마음 놓고 바꿔 쓸 수 있고, SQL은 순서를 적지 않는 선언적 언어여도 된다.

### 자주 쓰는 동치 규칙

| 규칙 | 식 | 왜 쓰나 |
|:---|:---|:---|
| 셀렉트 분해 | `σ(c1 ∧ c2)(R) = σ(c1)(σ(c2)(R))` | 조건을 쪼개 각각 알맞은 자리로 내린다 |
| 셀렉트 교환 | `σ(c1)(σ(c2)(R)) = σ(c2)(σ(c1)(R))` | 인덱스가 있거나 많이 거르는 조건을 먼저 건다 |
| 셀렉트 내리기 | `σ(c)(R ⋈ S) = σ(c)(R) ⋈ S` (c가 R의 속성만 볼 때) | 조인에 들어가는 투플 수를 줄인다 |
| 프로젝트 내리기 | 위에서 쓰는 속성만 아래에서 미리 남긴다 | 중간 결과의 폭을 줄인다 |
| 조인 교환 | `R ⋈ S = S ⋈ R` | 작은 쪽으로 해시 테이블을 만드는 식으로 실행 방법을 고른다 |
| 조인 결합 | `(R ⋈ S) ⋈ T = R ⋈ (S ⋈ T)` | 중간 결과가 작아지는 순서로 잇는다 |

규칙으로 만든 후보 계획 가운데 무엇이 가장 싼지는 테이블 크기, 값의 분포, 인덱스 같은 통계로 추정한다. 그렇게 고른 계획은 MySQL과 PostgreSQL에서 `EXPLAIN`으로 볼 수 있다. [DBMS 개요](../dbms-overview)에서 본 인덱스가 이 선택에 끼어든다.

{{< callout type="warning" >}}
외부 조인에서는 셀렉트를 마음대로 내릴 수 없다. 6.3에서 본 것처럼 `σ(c)(학생 ⟕ 수강)`과 `학생 ⟕ σ(c)(수강)`은 결과가 다르다. 외부 조인은 짝 없는 투플을 `NULL`로 살리는 연산이라, `NULL`로 채워지는 쪽(오른쪽)의 속성을 보는 조건은 거르는 시점에 따라 살아남는 투플이 달라진다. 옵티마이저는 이런 경우를 가려서 바꿔 쓰지만, 질의를 쓰는 사람도 조건을 `ON`에 둘지 `WHERE`에 둘지를 결과가 다른 두 질의 가운데 하나를 고르는 일로 봐야 한다.
{{< /callout >}}

## 9. 관계 대수와 SQL

| 관계 대수 | 기호 | SQL | 주의 |
|:---|:---|:---|:---|
| 셀렉트 | σ | `WHERE` | UNKNOWN도 걸러지니 `NULL`은 따로 챙긴다 |
| 프로젝트 | π | `SELECT DISTINCT 열` | `DISTINCT`가 없으면 중복이 남는다 |
| 이름 바꾸기 | ρ | `AS`, 테이블 별칭 | 셀프 조인에 필요하다 |
| 합집합 | ∪ | `UNION` | `UNION ALL`은 중복을 남긴다 |
| 교집합 | ∩ | `INTERSECT` | MySQL은 8.0.31부터 |
| 차집합 | − | `EXCEPT` | Oracle은 `MINUS` (21c부터 `EXCEPT`도) |
| 카티션 프로덕트 | × | `CROSS JOIN`, `FROM A, B` | 조인 조건을 빠뜨리면 이것이 된다 |
| 세타·동등 조인 | ⋈(조건) | `JOIN ... ON` | 외래 키 조인은 대부분 동등 조인 |
| 자연 조인 | ⋈ | `NATURAL JOIN`, `JOIN ... USING` | 이름이 같은 열이 모두 조건이 된다 |
| 디비전 | ÷ | 이중 `NOT EXISTS`, `GROUP BY` + `HAVING COUNT` | 나누는 쪽이 비면 답이 갈린다 |
| 세미 조인 | ⋉ | `IN`, `EXISTS` | `JOIN`으로 쓰면 중복이 생긴다 |
| 안티 조인 | ▷ | `NOT EXISTS` | `NOT IN`은 `NULL`이 있으면 0건 |
| 외부 조인 | ⟕ ⟖ ⟗ | `LEFT`, `RIGHT`, `FULL OUTER JOIN` | 오른쪽 조건은 `ON`에 둔다. MySQL은 `FULL`이 없다 |
| 그룹과 집계 | γ | `GROUP BY` + 집계 함수 | `NULL`끼리 한 그룹이 된다 |

### 집합, 멀티셋, 그리고 NULL

관계 대수와 SQL이 같은 질의에 다른 답을 내는 곳은 둘로 모인다. 하나는 중복이고, 하나는 `NULL`이다.

| 차이 | 관계 대수 | SQL | 왜 |
|:---|:---|:---|:---|
| 질의 결과 | 집합: 중복이 없다 | 멀티셋: `DISTINCT`를 붙여야 중복이 없다 | 중복 제거는 비싸고, 집계에는 중복이 필요하다 |
| 집합 연산 | 집합 | 기본은 중복 제거, `ALL`이면 유지 | 이름 그대로 집합의 정의를 따른다 |
| 순서 | 없다 | `ORDER BY`로 정할 수 있다 | 정렬된 결과는 릴레이션이 아닌 목록이다 |
| 값이 없음 | 다루지 않는다 | `NULL`과 3값 논리 | 모름과 해당 없음을 나타낼 수단이 필요했다 |

`NULL`에는 규칙이 두 개 있다. **값을 비교할 때**(`=`, `<>`, `IN`, `WHERE`, `ON`)는 `NULL = NULL`이 UNKNOWN이라 짝이 되지 않는다. **같은 것을 하나로 묶을 때**(`DISTINCT`, `UNION`, `INTERSECT`, `EXCEPT`, `GROUP BY`)는 `NULL`끼리 같다고 본다. 표준은 이를 "구별되지 않는다(not distinct)"고 표현한다. 그래서 같은 뜻의 질의도 어느 쪽으로 쓰느냐에 따라 결과가 갈린다.

```sql
-- CS, BA, NULL: 묶을 때는 같다
SELECT 학과코드 FROM 학생
INTERSECT
SELECT 학과코드 FROM 학생;

-- CS, BA: 비교할 때는 UNKNOWN
SELECT DISTINCT 학과코드
  FROM 학생
 WHERE 학과코드 IN
       (SELECT 학과코드 FROM 학생);
```

어떤 릴레이션과 그 자신의 교집합은 자기 자신이어야 하고, `INTERSECT`는 그렇게 답한다. 같은 뜻을 세미 조인(`IN`)으로 쓰면 `NULL`이 빠진다. 6.2에서 `NOT IN`은 0건을 냈는데 `EXCEPT`는 EE를 돌려준 것, 6.3의 외부 조인이 박민수를 짝 없이 남긴 것, 6.4의 `GROUP BY`가 `NULL` 그룹을 만든 것이 모두 이 두 규칙으로 설명된다.

이 장의 연산은 [SQL](../sql)에서 실제 문법으로 다시 만난다. `SELECT`는 π, `WHERE`는 σ, `JOIN`은 ⋈라는 대응을 알면 긴 질의도 관계 대수의 나무로 읽힌다. 관계 대수는 설계에도 쓰인다. 릴레이션을 프로젝트로 쪼갠 뒤 자연 조인으로 다시 합쳤을 때 원래 릴레이션이 그대로 돌아오는지가 [정규화](../normalization)에서 좋은 분해를 가리는 기준, 무손실 분해다.

## 핵심 정리

| 항목 | 핵심 | 왜 |
|:---|:---|:---|
| 관계 대수 / 관계 해석 | 연산의 순서를 적는 절차적 언어 / 결과의 조건을 적는 비절차적 언어 | 표현력이 같아 DBMS가 해석에 가까운 SQL을 대수로 옮겨 실행한다 |
| 폐쇄 특성 | 연산의 입력도 결과도 릴레이션 | 연산을 이어 붙여 식을 만들고, 질의 결과를 다시 질의한다 |
| 기본 연산 | σ, π, ∪, −, × (교재에 따라 ρ 포함) | 교집합, 조인, 디비전은 이것들의 조합이다 |
| 합병 가능 | 차수가 같고 대응하는 속성의 도메인이 같다 | 그래야 두 투플이 같은지 비교할 수 있다. SQL은 타입만 본다 |
| 차집합 − | R에만 있는 투플, 교환법칙 없음 | 다른 투플이 없음("듣지 않은", "모두 들은")을 표현하는 유일한 기본 연산이다 |
| 카티션 프로덕트 × | 모든 짝, 차수는 합, 투플 수는 곱 | 조인 조건을 빠뜨리면 이것이 된다 |
| 셀렉트 σ | 조건이 참인 투플 (행) | UNKNOWN도 걸러지니 `NULL`은 따로 챙긴다 |
| 프로젝트 π | 고른 속성 (열), 중복 제거 | SQL `SELECT`는 `DISTINCT` 없이는 중복을 남긴다 |
| 조인 ⋈ | σ(조건)(R × S) | 세타, 동등, 자연 조인은 조건과 남는 열이 다르다 |
| 자연 조인 | 이름이 같은 속성끼리 동등 조인하고 열은 하나만 | SQL `NATURAL JOIN`은 스키마 변경에 흔들려 `USING`, `ON`을 쓴다 |
| 디비전 ÷ | S의 모든 투플과 짝이 있는 R의 투플 | SQL에선 이중 `NOT EXISTS`나 `COUNT`로 쓰고, 나누는 쪽이 비면 답이 갈린다 |
| 세미 / 안티 조인 | 짝이 있는 / 없는 R의 투플 | `EXISTS` / `NOT EXISTS`로 쓴다. `NOT IN`은 `NULL`에 0건 |
| 외부 조인 | 짝 없는 투플을 `NULL`로 채워 살린다 | 오른쪽 조건을 `WHERE`에 두면 외부 조인이 사라진다 |
| 그룹과 집계 γ | 묶어서 새 값을 계산한다 | 기본 연산은 새 값을 만들지 못한다 |
| 관계 해석의 ∀ | ¬∃¬로 바꿔 쓴다 | SQL의 이중 `NOT EXISTS`가 이것이다 |
| 질의 최적화 | 결과가 같은 대수 식 가운데 싼 것을 고른다 | 셀렉트를 조인 아래로 내리면 중간 결과가 준다 |
| `NULL`의 두 규칙 | 비교할 때는 UNKNOWN, 묶을 때는 같다 | `IN`과 `INTERSECT`, `NOT IN`과 `EXCEPT`가 다른 답을 낸다 |

**용어 정리**
- **관계 대수 (Relational Algebra)**: 결과를 얻는 연산의 순서를 적는 절차적 언어
- **관계 해석 (Relational Calculus)**: 결과가 만족할 조건을 술어 논리로 적는 비절차적 언어
- **관계적으로 완전 (Relationally Complete)**: 관계 대수로 표현할 수 있는 모든 질의를 표현할 수 있다
- **폐쇄 특성 (Closure Property)**: 연산 결과도 릴레이션이라 연산을 이어 쓸 수 있다
- **합병 가능 (Union Compatible)**: 차수가 같고 대응하는 속성의 도메인이 같다
- **합집합 / 교집합 / 차집합 (∪ / ∩ / −)**: R이나 S에 / 둘 다에 / R에만 있는 투플
- **카티션 프로덕트 (Cartesian Product, ×)**: 두 릴레이션 투플의 모든 짝
- **셀렉트 (Select, σ)**: 조건을 만족하는 투플을 고른다 (수평적 부분집합)
- **프로젝트 (Project, π)**: 고른 속성만 남기고 중복을 없앤다 (수직적 부분집합)
- **이름 바꾸기 (Rename, ρ)**: 릴레이션이나 속성에 새 이름을 붙인다. SQL의 별칭
- **세타 / 동등 / 자연 조인**: 비교 연산자로 / `=`로 / 이름이 같은 속성끼리 `=`로 잇고 겹친 열을 하나로
- **디비전 (Division, ÷)**: S의 모든 투플과 짝을 이루는 R의 투플
- **세미 조인 (Semi Join, ⋉)**: S에 짝이 있는 R의 투플. R의 속성만 남는다
- **안티 조인 (Anti Join, ▷)**: S에 짝이 없는 R의 투플
- **외부 조인 (Outer Join, ⟕ ⟖ ⟗)**: 짝 없는 투플도 `NULL`로 채워 결과에 넣는 조인
- **그룹 연산 (γ)**: 속성 값으로 투플을 묶고 집계 함수로 새 값을 계산한다
- **투플 / 도메인 관계 해석**: 변수가 투플을 / 속성 값을 가리키는 관계 해석
- **존재 / 전칭 정량자 (∃ / ∀)**: 조건을 만족하는 것이 하나라도 있다 / 모두가 만족한다
- **안전한 식 (Safe Expression)**: 결과가 데이터베이스에 있는 값으로 제한되는 관계 해석 식
- **질의 최적화 (Query Optimization)**: 결과가 같은 관계 대수 식 가운데 가장 싼 실행 계획을 고르는 일
