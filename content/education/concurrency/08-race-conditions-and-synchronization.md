앞 장에서 문제를 조각으로 나눠 동시에 돌리기 시작했다. 그 순간 새 문제가 따라온다. 조각들이 **같은 것**을 건드리는 순간이다. 원리는 셋이다. 첫째, **경쟁 조건은 공유와 교차의 곱이고, 문제는 자원이 아니라 구간에서 생긴다.** 공유 변수가 있어서가 아니라 그 변수를 읽고 쓰는 몇 줄 사이에 다른 스레드가 끼어들어서 틀린다. 그 몇 줄이 임계 구역이고, 동기화가 하는 일은 그 구간에 한 번에 하나만 들이는 것뿐이다. 둘째, **수단은 넷이고 고르는 기준은 둘이다. 연산이 하드웨어 명령 하나로 묶이는가, 동시에 몇이 들어가야 하는가.** 묶이면 원자적 연산이고 락이 필요 없다. 안 묶이면 락이고, 하나만 들일 거면 뮤텍스, 몇 명까지 들일 거면 세마포어다. 셋째, **동기화의 값은 락을 잡는 시간이 아니라 락이 잡혀 있는 시간의 합이다.** 락 하나를 잡고 푸는 데는 몇 ns지만, 락이 잡혀 있는 동안 나머지 코어는 그 구간을 못 들어간다. 임계 구역이 넓으면 코어 열 개가 하나처럼 돈다. 이 PC(Apple M4 10코어, JDK 23)에서 스레드 열 개의 `count++`가 얼마를 잃는지, 점검하고 행동하는 코드가 객체를 몇 개나 헛되이 만드는지, 디버그 출력 한 줄이 증상을 어떻게 없애는지, 네 가지 카운터가 스레드 수에 따라 얼마나 드는지, CAS가 성공 한 번에 몇 번 실패하는지, 락과 세마포어가 남의 해제와 재진입에 어떻게 다르게 답하는지, 그리고 임계 구역의 폭을 100%에서 0%까지 줄이며 처리량이 어디서 멈추는지 봤다.

## 1. 공유 자원이 부르는 문제

### 1.1 교차 실행이 값을 망가뜨린다

```text
counter = 0, 둘이 +1씩 (기대 2)
A          B          counter
읽기 0                  0
           읽기 0       0
+1 → 1                  0
쓰기 1                  1
           +1 → 1       1
           쓰기 1       1  ← 손실
```

```java
// counter++ 는 세 명령. 사이에 끼어든다
int cur = counter;   // 읽기
cur = cur + 1;       // 더하기
counter = cur;       // 쓰기
```

| `counter++` 스레드 10개 × 10만 번 (기대 1,000,000) | 결과 | 잃은 갱신 | 왜 |
|:----------------------------------------|-------:|-------:|:---|
| 1회 | 215,886 | 78% | 열 스레드가 같은 값을 읽고 같은 값을 쓴다 |
| 2회 | 199,795 | 80% | |
| 3회 | 200,965 | 80% | |
| 4회 | 201,453 | 80% | |
| 5회 | 209,954 | 79% | 스레드 둘일 때([04](../04-concurrency-ingredients)장) 1~48%였던 것이 열이면 80% |

동시성 프로그램은 거의 항상 무언가를 함께 쓴다. 카운터, 캐시, 커넥션, 파일. 문제는 여러 스레드의 실행이 **교차**될 때 생긴다. 한 스레드가 값을 읽고 고쳐 쓰는 사이에 다른 스레드가 끼어들면, 둘 다 같은 값에서 출발해 같은 값을 쓰고 갱신 하나가 사라진다. `counter++`는 한 줄이지만 코어에는 읽기, 더하기, 쓰기 세 명령이고, [06](../06-multitasking)장의 선점형 스케줄러는 그 사이 어디서든 스레드를 바꾼다. 스레드 열 개면 열 개가 같은 값을 읽는 일이 잦아 다섯 번 돌려 다섯 번 80% 근처를 잃었다.

### 1.2 경쟁 조건

```java
// 점검 후 행동: 둘 사이에 틈이 있다
if (!map.containsKey(k))
    map.put(k, new Item()); // 2,712개
// 복합 동작을 하나로
map.computeIfAbsent(k,
    x -> new Item());     // 1,000개
```

| 키 1,000개를 스레드 10개가 "없으면 만든다" | 키 | 만들어진 객체 | 왜 |
|:----------------------------------|-----:|--------:|:---|
| `containsKey` 뒤 `put` (`ConcurrentHashMap`) | 1,000 | 2,502 ~ 2,712 | 점검과 행동 사이에 다른 스레드가 같은 키를 만든다 |
| `computeIfAbsent` | 1,000 | 1,000 | 점검과 행동이 하나의 원자적 연산 |

경쟁 조건은 둘 이상의 작업이 공유 자원을 동시에 바꾸려 할 때 **결과가 접근 순서에 따라 달라지는** 상황이다. 이름은 자원을 향해 달리는 경주에서 왔다. 누가 먼저 닿느냐로 결과가 갈리고, 그 순서는 스케줄러가 매번 다르게 정한다. 위 표는 [01](../01-what-is-concurrency)장 2절의 ATM과 같은 모양이다. 점검(`containsKey`)과 행동(`put`)이 각각은 안전한 `ConcurrentHashMap`인데도 둘 사이의 틈에 다른 스레드가 들어와 객체가 1,700개나 헛되이 만들어졌다. 개별 연산이 원자적이어도 그것을 잇는 코드는 원자적이지 않다. 생성 비용이 큰 객체(커넥션, 캐시 항목)였다면 성능 문제이고, 하나여야 하는 객체(싱글턴)였다면 정합성 문제다.

{{< callout type="warning" >}}
**경쟁 조건은 대부분의 실행에서 우연히 맞는다.** 그래서 테스트를 통과하고 운영에서 가끔 틀린다. 더 나쁜 것은 관찰이 증상을 바꾼다는 것이다. 이 PC에서 스레드 둘의 `counter++`가 38%를 잃었는데, 매 단계에 `println`을 하나 넣자 손실이 0%가 됐다. 출력 스트림의 락이 두 스레드를 줄 세운 것이다. 디버거의 중단점도 같은 일을 한다. 그래서 하이젠버그(Heisenbug)라 부르고, 관찰로 잡는 대신 **설계로 막는다**. 재현되는 경우도 있다. [07](../07-task-decomposition)장 6.3절의 뺄셈 리듀스는 매번 같은 0을 냈다. 재현이 되든 안 되든 원인은 같다. 공유하는 것을 순서 없이 건드렸다.
{{< /callout >}}

## 2. 임계 구역

```text
진입부       임계 구역       퇴장부
락 획득 ─▶ [공유 자원 읽고 씀] ─▶ 해제
           한 번에 하나만
다른 스레드는 진입부에서 기다린다
```

| 임계 구역의 폭 | 결과 | 이 PC에서 (7절) | 왜 |
|:-----------|:-----|:-------------|:---|
| 너무 넓다 | 직렬 실행. 코어가 논다 | 100%면 코어 10개가 1.0배 | 락이 잡혀 있는 시간의 합이 전체 시간 |
| 너무 좁다 | 공유 접근이 새어 나간다 | 1.2절의 2,712개 | 점검과 행동 사이가 구역 밖 |
| 딱 맞다 | 안전하고 병렬 | 10%면 6.1배 | 공유를 건드리는 줄만 감싼다 |

첫째 원리다. 경쟁 조건은 코드 아무 데서나 생기지 않는다. 공유 자원을 읽고 쓰는 **바로 그 구간**에서만 생긴다. 그 구간이 임계 구역이고, 동기화의 목표는 하나다. 임계 구역에 한 번에 한 작업만 들이는 것, 상호 배제다. 진입부에서 자격을 얻고 퇴장부에서 돌려준다. 그래서 동기화의 첫 일은 락을 고르는 것이 아니라 **구간을 찾는 것**이다. 1.2절의 버그는 구간을 `put` 한 줄로 잡아서 생겼다. 구간은 `containsKey`부터 `put`까지다. 반대로 구간을 함수 전체로 잡으면 안전하지만 7절에서 보듯 코어 열 개가 하나처럼 돈다. 구간의 폭이 동기화의 값을 정하고, 그 값은 7절에서 잰다.

## 3. 동기화 수단 ① 원자적 연산

```java
// incrementAndGet 의 속: CAS 재시도
long cur;
do {
    cur = value.get();
} while (!value.compareAndSet(
    cur, cur + 1));
// 10 스레드: 성공 1번에 실패 5.5번
```

| `AtomicLong` 증가 | 걸린 시간 | 하나당 | 왜 |
|:---------------|--------:|------:|:---|
| 스레드 1개, 100만 번 | 2.1 ms | 2.1 ns | 경쟁이 없으면 CAS는 한 번에 성공 |
| 스레드 2개, 200만 번 | 12 ms | 6.0 ns | 캐시 라인을 두 코어가 뺏고 뺏긴다 |
| 스레드 10개, 1,000만 번 | 364 ms | 36 ns | 성공 하나에 실패 5.5번. 5,500만 번 헛돌았다 |

임계 구역을 막는 가장 단순한 방법은 연산 자체를 쪼갤 수 없게 만드는 것이다. 원자적 연산은 중간 단계를 다른 스레드가 볼 수 없는 연산이다. 전부 일어났거나 전혀 안 일어났거나 둘 중 하나만 보인다. `counter++`의 읽기·더하기·쓰기를 코어의 명령 하나(compare-and-swap, CAS)로 묶으면 끼어들 틈이 없다. CAS는 "내가 읽은 값이 아직 그대로면 새 값으로 바꿔라"이고, 그 사이 누가 바꿨으면 실패하니 다시 읽어 다시 시도한다. 락이 없어 잠들지 않는다. 대신 경쟁이 심하면 헛돈다. 스레드 열 개가 같은 변수를 두고 다투니 성공 한 번에 5.5번을 실패했고, 한 스레드일 때 2ns였던 것이 36ns가 됐다. [05](../05-inter-process-communication)장 2.2절에서 프로세스 둘의 공유 메모리에 쓴 `getAndAdd`도 같은 명령이다.

{{< callout type="info" >}}
**원자적 연산은 하드웨어가 주는 단순 연산에만 쓸 수 있다.** 증가, 교체, CAS다. 변수 둘을 한꺼번에 맞춰 바꾸는 일, 점검하고 행동하는 일은 명령 하나로 안 묶인다. 그때는 복합 동작 자체를 원자화한 API(`computeIfAbsent`, `putIfAbsent`)를 찾고, 그것도 없으면 락이다. "원자적"과 "스레드 안전"은 같은 말이 아니다. 1.2절의 `ConcurrentHashMap`이 그 증거다. 자바 바이트코드에서 `count++`가 어떻게 넷으로 쪼개지는지는 [자바 동시성 02](../../java/concurrency/02-thread-safety)장이다.
{{< /callout >}}

## 4. 동기화 수단 ② 락

```java
var lock = new ReentrantLock();
lock.lock();            // 진입부
try {
    balance += amount;  // 임계 구역
} finally {
    lock.unlock();   // 퇴장부. 반드시
}
```

| 락을 잡고 푸는 값 | 스레드 1개 | 2개 | 4개 | 10개 | 왜 |
|:-------------|--------:|----:|----:|-----:|:---|
| `synchronized` | 3.4 ns | 20 ns | 39 ns | 39 ns | 경쟁이 생기면 잠들고 깨운다 |
| `ReentrantLock` | 7.5 ns | 29 ns | 6.8 ns | 7.9 ns | 공정하지 않은 락은 같은 스레드가 연달아 잡는다 |

락은 공유 자원에 거는 자물쇠다. 잡은 스레드만 자원에 손대고, 못 잡은 스레드는 앞 스레드가 풀 때까지 기다린다. 임계 구역의 진입부에서 잡고 퇴장부에서 푸는 것으로 상호 배제를 만드는 일반 수단이고, 뮤텍스와 세마포어는 이 락의 두 모양이다. 경쟁이 없을 때 락은 몇 ns다. 경쟁이 생기면 못 잡은 스레드가 잠들고([04](../04-concurrency-ingredients)장 5절의 `BLOCKED`), 앞 스레드가 풀 때 깨워야 하니 [06](../06-multitasking)장 3절의 전환 비용이 붙는다. `ReentrantLock`이 스레드 넷에서 둘보다 빠른 것은 기본이 불공정 모드라서다. 방금 푼 스레드가 줄 선 스레드보다 먼저 다시 잡을 수 있어, 깨우는 횟수가 준다. 공정성을 켜면 순서는 지켜지고 처리량은 떨어진다. 자바의 `synchronized`와 모니터의 속은 [자바 기초 13](../../java/basics/13-thread)장 5절이다.

{{< callout type="warning" >}}
**해제는 반드시 `finally`에서.** 임계 구역에서 예외가 나 락을 못 풀면 그 락을 기다리는 모든 스레드가 영원히 선다. `synchronized` 블록은 이것을 언어가 해 주고, `ReentrantLock`은 내가 해야 한다. 그리고 락이 둘 이상이면 잡는 순서를 프로그램 전체에서 하나로 정한다. 스레드 A가 1번 뒤 2번을, B가 2번 뒤 1번을 잡으면 둘 다 영원히 기다리는 교착이고, 그것이 [09](../09-deadlock-and-starvation)장이다.
{{< /callout >}}

## 5. 동기화 수단 ③ 뮤텍스

```text
[뮤텍스]  열쇠 하나, 잠근 사람이 연다
A: 잠금 ▶ 사용 ▶ 해제
B: ── 대기 ──────▶ 잠금 ▶ 사용 ▶ 해제
동시에 들어가는 수 = 1
```

| 이 PC에서 | `ReentrantLock` | `Semaphore(1)` | 왜 |
|:--------|:--------------|:-------------|:---|
| 다른 스레드가 풀려 하면 | `IllegalMonitorStateException` | 허용. 잡지 않은 스레드가 돌려줘 허가증이 도로 1개 | 뮤텍스에는 주인이 있다 |
| 같은 스레드가 다시 잡으면 | 잡힌다. 보유 횟수 2 | 200ms 기다려도 못 잡는다. 자기 자신과 교착 | 뮤텍스는 주인을 알아본다 |

어떤 자원을 읽고 바꾸는 동안 아무도 끼어들지 못하게 하는 것이 상호 배제(mutual exclusion)이고, 그 락이 뮤텍스다. 이름이 그 줄임말이다. 뮤텍스의 핵심 규칙은 **소유권**이다. 잠근 스레드만 풀 수 있다. 위 표가 그 규칙의 실물이다. `ReentrantLock`을 잡은 채 다른 스레드가 풀려 하니 예외가 났고, 같은 스레드가 다시 잡으니 보유 횟수가 2가 됐다. 주인을 아니까 주인이 또 들어오는 것(재진입)을 허용하고, 남이 푸는 것을 막는다. 열쇠 하나 달린 화장실이다. 자바의 `synchronized`도 같은 규칙을 따르는 뮤텍스다.

## 6. 동기화 수단 ④ 세마포어

```text
[세마포어(3)]  허가증 셋, 누구나 반납
A acquire ▶ 사용      (남은 2)
B acquire ▶ 사용      (남은 1)
C acquire ▶ 사용      (남은 0)
D acquire ▶ ── 대기 ── 누가 release 하면
```

```java
var sem = new Semaphore(3);
sem.acquire();          // 허가증 하나
try {
    useConnection();  // 셋까지 동시에
} finally {
    sem.release();
}
```

| 100ms짜리 작업 10개, 허가증 | 동시에 들어간 최대 | 걸린 시간 | 왜 |
|:---------------------|-------------:|--------:|:---|
| 10 | 10 | 106 ms | 아무도 안 기다린다 |
| 3 | 3 | 412 ms | 열을 셋씩, 네 번 |
| 1 (뮤텍스처럼) | 1 | 1,030 ms | 열을 하나씩 |

세마포어도 공유 자원의 접근을 막지만, **여럿을 동시에** 허용한다는 점이 다르다. 허가증 N개를 든 카운터다. 들어갈 때 하나를 받고(`acquire`) 나올 때 돌려준다(`release`). 허가증이 떨어지면 다음 스레드는 누군가 돌려줄 때까지 기다린다. 위 표에서 허가증 셋에 열 작업을 넣으니 정확히 셋씩 들어가 네 번에 나눠 끝났다. 커넥션 풀의 크기, 동시에 열 수 있는 파일 수, 외부 API의 초당 호출 한도가 이것으로 만들어진다. 뮤텍스와 다른 또 하나는 **소유권이 없다**는 것이다. 철도의 신호기처럼 "지금 몇 대까지 들어와도 되는가"만 관리하고 누가 들어왔는지는 모른다. 그래서 5절 표에서 남의 허가증을 돌려줄 수 있었고, 같은 스레드가 두 번 잡으려다 자기 자신과 교착했다.

| 구분 | 뮤텍스 | 세마포어 | 왜 |
|:-----|:-----|:------|:---|
| 동시에 들어가는 수 | 1 | N | 상호 배제 vs 개수 제한 |
| 소유권 | 있다. 잠근 스레드만 푼다 | 없다. 누구나 돌려준다 | 열쇠 vs 신호기 |
| 재진입 | 된다 | 안 된다. 자기와 교착 | 주인을 아느냐 |
| 쓰임 | 공유 변수 보호 | 풀, 한도, 스레드 사이의 신호 | |
| 자바 | `synchronized`, `ReentrantLock` | `Semaphore` | [자바 동시성 05](../../java/concurrency/05-building-blocks)장 5.3절 |

{{< callout type="info" >}}
**허가증 하나짜리 세마포어는 뮤텍스가 아니다.** 동시에 하나만 들이는 것은 같지만 소유권이 없어서, 잡지 않은 스레드가 풀어도 막지 못하고 실수를 잡아 주지도 않는다. 대신 그 성질이 쓸모 있는 곳이 있다. 한 스레드가 `acquire`로 기다리고 다른 스레드가 `release`로 깨우는 신호 용도다. 상호 배제에는 뮤텍스, 개수 제한과 신호에는 세마포어를 쓰면 코드가 의도를 말한다.
{{< /callout >}}

## 7. 동기화는 공짜가 아니다

### 7.1 무엇이 드나

| 카운터 1,000만 번 (스레드 10개) | 걸린 시간 | 하나당 | 왜 |
|:------------------------|--------:|------:|:---|
| `counter++` | 4.7 ms | 0.5 ns | 빠르고 80% 틀리다 |
| `synchronized` | 388 ms | 39 ns | 잠들고 깨우는 전환 |
| `ReentrantLock` | 79 ms | 7.9 ns | 불공정 모드가 전환을 아낀다 |
| `AtomicLong` | 364 ms | 36 ns | CAS 5.5번 실패마다 캐시 라인 왕복 |
| `LongAdder` | 7.8 ms | 0.8 ns | 스레드마다 자기 칸에 더하고 읽을 때 합친다 |

| 비용 | 뜻 | 이 PC에서 | 왜 |
|:-----|:---|:--------|:---|
| 락 자체 | 잡고 푸는 명령 | 경쟁 없을 때 2~8 ns | CAS 한두 번 |
| 경쟁 | 못 잡은 스레드가 자고 깬다 | 39 ns, 곧 열 배 이상 | [06](../06-multitasking)장 3절의 전환 |
| 캐시 라인 | 같은 변수를 코어 열 개가 당긴다 | CAS 5.5번 실패 | [04](../04-concurrency-ingredients)장 4.3절 |
| 직렬화 | 락이 잡힌 동안 나머지는 못 들어간다 | 7.2절 | 가장 크다 |

셋째 원리다. 락 하나를 잡고 푸는 값은 몇 ns이고 그것은 문제가 아니다. 문제는 경쟁이다. 스레드 열 개가 같은 락을 다투면 못 잡은 아홉이 자고 깨는 전환 비용이 붙고, 같은 캐시 라인을 코어 열 개가 뺏고 뺏긴다. `AtomicLong`이 락 없이도 `synchronized`만큼 느린 이유가 그것이다. 표의 마지막 줄이 해법의 방향이다. `LongAdder`는 스레드마다 자기 칸에 더하고 읽을 때만 합친다. 공유하는 순간을 없애니 락도 CAS 실패도 없다.

### 7.2 값을 정하는 것은 임계 구역의 폭이다

```java
double v = work(free);     // 락 밖
lock.lock();
try {
    shared += v + work(locked);
} finally { lock.unlock(); }
```

```text
락이 잡혀 있는 시간의 합이 하한
작업 1,000개 × 1ms, 코어 10개
락 100%  ████████████████████ 1,044 ms
락  50%  ██████████           524 ms
락  10%  ███                  173 ms
락   0%  ███                  148 ms
```

| 1ms짜리 작업 1,000개, 스레드 10개. 락이 감싸는 비율 | 락 점유의 합 | 계산의 합 ÷ 6.8 | 걸린 시간 | 배속 | 왜 |
|:-------------------------------------|-------:|-----------:|--------:|----:|:---|
| 100% | 1,000 ms | 147 ms | 1,044 ms | 1.0 | 코어 열 개가 하나처럼 |
| 50% | 500 ms | 147 ms | 524 ms | 2.0 | 락 점유의 합이 그대로 시간 |
| 20% | 200 ms | 147 ms | 280 ms | 3.7 | 점유의 합에 다툼 비용이 얹힌다 |
| 10% | 100 ms | 147 ms | 173 ms | 6.1 | 이제야 계산이 병목 |
| 1% | 10 ms | 147 ms | 150 ms | 7.0 | |
| 0% | 0 | 147 ms | 148 ms | 7.1 | 실효 코어 6.8의 바닥 |

같은 1ms짜리 작업 1,000개를 스레드 열 개로 돌리며, 작업 중 락으로 감싸는 부분을 100%에서 0%까지 줄였다. 락이 잡혀 있는 동안 다른 스레드는 그 구간에 못 들어가니, **락 점유 시간의 합**이 전체 시간의 하한이다. 100%면 1,000ms, 50%면 500ms이고 실측이 그 위에 딱 얹힌다. 10% 아래로 내려가야 계산 자체가 병목이 되어 코어 열 개의 바닥에 닿는다. [02](../02-sequential-and-parallel-execution)장 4절의 암달의 법칙이 락의 언어로 다시 나온 것이다. 순차 부분이 곧 임계 구역이다. 그래서 동기화의 규칙은 "락을 빨리 잡아라"가 아니라 "락을 **짧게** 잡아라"다. 공유하는 줄만 감싸고, 계산과 I/O는 밖으로 뺀다.

### 7.3 해소 수단 고르기

| 수단 | 조건 | 값 | 왜 이걸 고르나 |
|:-----|:----|:---|:-----------|
| 공유하지 않기 | 조각마다 자기 데이터, 불변 객체 | 0 | `LongAdder` 0.8 ns. 지킬 것이 없다 |
| 메시지 전달 | 자원을 넘기고 나는 손을 뗀다 | 큐 하나 | [05](../05-inter-process-communication)장. 소유자가 항상 하나 |
| 원자적 연산 | 명령 하나로 묶이는 단순 연산 | 경쟁 없으면 2 ns | 락 없이, 잠들지 않고 |
| 복합 원자 API | 점검 후 행동을 라이브러리가 묶어 둔 것 | 해시 한 칸의 락 | `computeIfAbsent`가 1,000개 |
| 뮤텍스 | 여러 변수를 함께, 하나만 | 폭에 비례 | 7.2절 |
| 세마포어 | 동시에 N까지 | 허가증 셋에 412 ms | 개수를 세는 것이 목적일 때 |

{{< callout type="warning" >}}
**가장 싼 동기화는 동기화하지 않는 것이다.** 위 표는 위에서 아래로 갈수록 비싸다. 조각마다 자기 데이터를 갖게 하고 끝에 합치면([07](../07-task-decomposition)장의 맵과 포크/조인이 그 모양이다), 바뀌지 않는 객체는 누가 봐도 같고, 자원을 큐로 넘기면 손댈 사람이 늘 하나다. 그래도 공유해야 하면 원자적 연산, 그것도 안 되면 락이고, 락은 짧게다. 락을 잡은 채 다른 락을 기다리면 다음 장의 교착이고, 락을 영영 못 잡는 스레드가 생기면 기아다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 경쟁 조건 | 결과가 접근 순서에 달린다 | 열 스레드 `count++` 80% 손실 |
| 점검 후 행동 | 각각 원자적이어도 둘은 아니다 | 객체 2,712개 vs 1,000개 |
| 하이젠버그 | 관찰이 증상을 바꾼다 | `println` 하나에 38% → 0% |
| 임계 구역 | 공유를 건드리는 구간. 한 번에 하나 | 구간 찾기가 락 고르기보다 먼저 |
| 원자적 연산 | 명령 하나, 락 없음 | 경쟁 없으면 2 ns, 열 스레드면 CAS 5.5번 실패 |
| 락 | 진입부에서 잡고 퇴장부에서 푼다 | `finally`, 잡는 순서 통일 |
| 뮤텍스 | 하나만, 소유권 | 남이 풀면 예외, 재진입 허용 |
| 세마포어 | N까지, 소유권 없음 | 허가증 셋에 정확히 셋 |
| 값 | 락 자체보다 경쟁과 직렬화 | 39 ns vs 3 ns, 100%면 1.0배 |
| 폭 | 락 점유 시간의 합이 하한 | 50%면 524 ms, 10%면 173 ms |
| 안 공유하기 | 가장 싼 해법 | `LongAdder` 0.8 ns |

{{< callout type="info" >}}
**용어 정리**
- **경쟁 조건**: 여러 작업이 공유 자원을 동시에 바꿀 때 결과가 순서에 따라 달라지는 것
- **교차 실행**: 스레드들의 명령이 섞여 실행되는 것. 선점형 스케줄러가 만든다
- **점검 후 행동**: 확인하고 행동하는 사이에 다른 스레드가 끼는 경쟁 조건의 모양
- **하이젠버그**: 관찰하면 사라지는 버그. 출력, 중단점이 타이밍을 바꾼다
- **임계 구역**: 공유 자원을 읽고 쓰는 코드 구간
- **상호 배제**: 임계 구역에 한 번에 하나만 들이는 것
- **원자적 연산**: 중간을 볼 수 없는 연산. 전부 아니면 전무
- **CAS**: compare-and-swap. 읽은 값이 그대로면 바꾸는 하드웨어 명령. 실패하면 재시도
- **락**: 잡은 스레드만 자원에 손대는 자물쇠. 획득과 해제
- **뮤텍스**: 동시에 하나, 소유권 있는 락. `synchronized`, `ReentrantLock`
- **세마포어**: 허가증 N개짜리 카운터. 소유권 없음
- **소유권 / 재진입**: 잠근 스레드만 푼다 / 잠근 스레드가 또 잠글 수 있다
- **공정성**: 기다린 순서대로 주느냐. 불공정이 빠르다
- **직렬화**: 락 때문에 하나씩 도는 것. 락 점유 시간의 합이 하한
{{< /callout >}}
