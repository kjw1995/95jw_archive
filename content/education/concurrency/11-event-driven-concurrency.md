[10](../10-nonblocking-io)장은 스레드 없이 연결 1만 개를 드는 법이었고, 답은 셀렉터 위의 이벤트 루프였다. 이 장은 그 루프를 하나의 설계로 끌어올린다. 이벤트 기반 동시성이다. 원리는 셋이다. 첫째, **통신은 둘 중 하나다. 동기는 둘이 만날 때까지 멈추고, 비동기는 던져 두고 간다.** 순서에 묶인 일은 동기가 맞다. 그러나 기다림을 겹치려면 비동기여야 한다. 스레드 100개로 겹치든 스레드 하나가 완료를 이벤트로 받든 겹치는 양은 같고, 다른 것은 그 값이다. 둘째, **이벤트 기반 시스템은 스레드를 늘리지 않고 일이 생긴 것에만 반응한다.** 연결마다 남는 것은 상태와 콜백뿐이고, 스레드 하나가 준비된 이벤트를 골라 짝지어진 콜백을 부른다. 이것이 리액터 패턴이고, 성능은 한 바퀴의 길이가 정한다. 셋째, **콜백은 짧아야 한다. 루프 스레드에서 쓴 시간은 남의 지연이 된다.** 콜백 하나가 1ms를 계산하면 관계없는 연결이 1ms를 기다린다. 긴 일은 워커 풀에, 코어를 다 쓰려면 서브 리액터에 넘기고, 그 대가로 코드가 콜백 조각으로 쪼개진다. 이 PC(Apple M4 10코어, macOS, JDK 23)에서 동기 큐와 비동기 큐로 보낼 때 보내는 쪽이 얼마나 멈추는지, 10ms짜리 요청 100개를 동기 순차·스레드 100개·셀렉터 스레드 하나·가상 스레드 100개로 보낼 때의 시간과 OS 스레드 수, 이벤트 루프 한 바퀴의 해부(초당 이벤트, 한 바퀴에 묶이는 이벤트 수, 이벤트당 시간), 콜백이 10µs에서 10ms까지 계산할 때 다른 연결의 지연, 리액터와 프로액터(`AsynchronousSocketChannel`)의 지연과 스레드 수, 서브 리액터 1~10개의 배속, 콜백 사슬과 `CompletableFuture` 사슬의 비용과 예외가 났을 때 누가 아는지를 쟀다.

## 1. 이벤트 기반 동시성이란

```text
스레드 기반 (연결 = 스레드)
 C1─[T1]  C2─[T2]  C3─[T3]
 연결 1만 개 → 스레드 1만 개
 스택 수 GB, 전환 비용

이벤트 기반 (연결 = 상태 + 콜백)
 C1┐
 C2┼─▶[이벤트 루프]─▶ 콜백
 C3┘   스레드 하나
 연결 1만 개 → 스레드 1개
```

| 구분 | 스레드 기반 | 이벤트 기반 | 왜 |
|:-----|:---------|:---------|:---|
| 동시성 단위 | OS 스레드 | 이벤트와 콜백 | 기다림을 스레드가 하느냐, 커널에 맡기느냐 |
| 연결당 비용 | 스택 (이 PC에서 잠든 스레드 88 KB) | 상태 객체 수십 B~수 KB | 스택이 없다. 진행 상태는 필드에 든다 |
| 스레드 수 | 연결 수 (이 PC의 천장 4,069) | 1 ~ 코어 수 | 루프 하나가 준비된 것만 돈다 |
| 문맥 전환 | 연결이 깰 때마다 | 없음 | 같은 스레드가 콜백을 차례로 부른다 |
| 기다림 | 스레드가 잔다 | 다른 이벤트를 처리한다 | 이벤트당 3.4 µs면 다음 이벤트로 |
| 코드 흐름 | 위에서 아래로 | 콜백으로 쪼개진다 | 스택이 없으니 상태를 객체가 든다 |
| 맞는 일 | 연결 적고 계산 무거움 | 연결 많고 대부분 기다림 | 이득은 계산이 아니라 기다림에서 난다 |

[10](../10-nonblocking-io)장 3절에서 연결마다 스레드는 이 PC에서 4,069개에서 끝났고, 5절의 셀렉터 루프는 스레드 하나로 1만 개를 21MB에 들었다. 이벤트 기반 동시성은 그 둘째 길을 설계 원칙으로 세운 것이다. 작업을 미리 스레드에 나눠 주지 않는다. 일이 생겼을 때, 즉 이벤트가 발생했을 때만 그 이벤트에 등록된 코드를 실행한다. 연결마다 남는 것은 "어디까지 진행했나"라는 상태와 "다음에 무엇을 할까"라는 콜백이고, 실행은 루프 하나가 맡는다. 값은 코드의 모양이다. 스레드 기반에서는 진행 상태가 스택에 저절로 남지만, 콜백은 매번 반환하므로 상태를 객체에 직접 들고 있어야 한다(4.2절). 이 장에서 잰 값으로 말하면, 10ms짜리 요청 100개를 셀렉터 스레드 하나가 14ms에 끝냈고(2.3절), 루프 하나가 초당 25.7만 이벤트를 이벤트당 3.4µs로 처리했다(4.1절).

{{< callout type="info" >}}
**이득의 출처는 계산이 아니라 기다림이다.** 요청 100개가 각각 10ms를 기다릴 때 그 기다림 100개를 겹치는 것이 이 모델의 전부다. 그래서 I/O 바운드(웹 서버, 프록시, 채팅, 게이트웨이)에서 극적이고 CPU 바운드에는 오히려 불리하다. 계산은 코어를 더 쓰는 병렬화([02](../02-sequential-and-parallel-execution)장)가 답이고, 6절의 멀티 리액터가 그 둘을 잇는다.
{{< /callout >}}

## 2. 동기 통신과 비동기 통신

첫째 원리다. 이벤트 기반 동시성의 바탕은 두 작업이 정보를 어떻게 주고받느냐의 구분이다.

### 2.1 동기 통신

```text
[동기] 둘이 만나야 넘어간다
보내는 쪽 ─┐
           ├─ 만남 ─▶ 둘 다 진행
받는 쪽 ───┘
먼저 온 쪽은 상대가 올 때까지 잔다
```

```java
// 동기: 상대가 올 때까지 멈춘다
var q = new SynchronousQueue<Long>();
q.put(1L);   // 상대가 take할 때까지
```

```java
// 동기 호출: 답이 와야 다음 줄로 간다
var user = userApi.find(id);  // 200 ms
var order = orderApi.find(user);
render(user, order);
// 500 ms. 그동안 이 스레드는 잔다
```

| `SynchronousQueue`에 넣기 | 보내는 쪽이 멈춘 시간 | 왜 |
|:-----------------------|----------------:|:---|
| 받는 스레드가 막 출발했다 | 0.36 ms | 상대가 도착할 때까지. 만남 자체는 µs 단위([03](../03-how-computers-work)장 1.2절) |
| 받는 쪽이 10 ms 뒤에 온다 | 12.5 ms | 상대가 올 때까지 잔다. 내 시간이 아니라 상대의 시간 |
| 받는 쪽이 100 ms 뒤에 온다 | 105.1 ms | 같다 |
| 받는 쪽이 안 온다, `offer(200 ms)` | 205 ms 뒤 `false` | 상대가 없다는 것을 시간 초과로만 안다 |

동기 통신은 정해진 순서로 실행해야 결과가 나오는 작업 사이에서 일어난다. 보내는 쪽과 받는 쪽이 둘 다 준비된 상태에서 값을 건네고, 건네는 동안 먼저 온 쪽은 멈춘다. 위 표가 그 멈춤이다. `SynchronousQueue`는 큐라는 이름과 달리 칸이 없어서 `put`은 상대의 `take`를 만나야 돌아온다. 받는 쪽이 10ms 뒤에 오면 보내는 쪽이 12.5ms를 멈추고, 100ms 뒤에 오면 105ms를 멈춘다. 멈춘 시간은 내 일의 길이가 아니라 상대의 사정이다. 상대가 영영 안 오면 시간 초과로만 그것을 안다. 핵심은 둘이다. 순서에 의존한다. B는 A의 결과가 있어야 시작한다. 그리고 만나는 동안 자원이 다른 일을 못 한다. `userApi.find(id)`가 200ms를 기다리는 동안 이 스레드는 [04](../04-concurrency-ingredients)장 5절의 `WAITING`이고, CPU는 논다.

### 2.2 비동기 통신

```text
[비동기] 던져 두고 간다
보내는 쪽 ─값─▶ [큐] ─▶ 받는 쪽
   └▶ 바로 다음 일       (나중에)
완료는 이벤트로 돌아온다
```

```java
// 비동기: 큐에 넣고 바로 돌아온다
var q = new LinkedBlockingQueue<Long>();
q.put(1L);          // 42 ns
doSomethingElse();  // 상대와 무관
```

```java
// 비동기 호출: 요청만 걸고 바로 간다
userApi.findAsync(id, user ->
    orderApi.findAsync(user, order ->
        render(user, order)));
doSomethingElse();  // 답을 안 기다린다
```

| `LinkedBlockingQueue`에 넣기 | 보내는 쪽이 멈춘 시간 | 받는 쪽이 값을 든 시각 | 왜 |
|:--------------------------|----------------:|----------------:|:---|
| 받는 쪽이 아직 없다 | 42 ns (p99 208 ns) | | 큐가 값을 들고 있다. 만남이 없다 |
| 받는 쪽이 10 ms 뒤에 온다 | 1 µs | 12.6 ms | 보낸 쪽은 갔고, 값은 상대가 왔을 때 건너간다 |
| 받는 쪽이 100 ms 뒤에 온다 | 1 µs | 105.1 ms | 같다 |

비동기 통신은 요청하는 쪽이 시작만 하고 완료를 기다리지 않는다. 보내는 쪽과 받는 쪽이 만날 필요가 없다. `LinkedBlockingQueue`는 칸이 있어서 `put`이 값을 넣고 42ns에 돌아온다. 받는 쪽이 아직 없어도, 100ms 뒤에 와도 같다. 값은 받는 쪽이 왔을 때 건너간다. 보낸 쪽이 그 사이에 한 일이 이 방식의 이득 전부다. 시작 시점과 완료 시점이 갈라지므로 완료는 나중에 따로 알아야 한다. 되묻거나(폴링), 통지받는다(콜백, 이벤트). 이벤트 기반 시스템은 후자다.

### 2.3 동기 vs 비동기 비교

| 구분 | 동기 통신 | 비동기 통신 | 왜 |
|:-----|:-------|:--------|:---|
| 순서 | 정해진 순서로 | 순서 제약 없음 | 동기는 B가 A의 결과를 전제한다 |
| 양쪽 준비 | 둘 다 준비돼야 건넨다 | 무관. 큐가 들고 있다 | 만남이 있느냐 없느냐 |
| 진행 | 건네는 동안 멈춘다 | 멈추지 않는다 | 12.5 ms vs 42 ns |
| 완료 확인 | 반환값으로 그 자리에서 | 이벤트·콜백으로 나중에 | 시작과 완료가 갈라졌다 |
| 자원 | 기다리는 동안 논다 | 기다리는 동안 다른 일 | 겹침의 출처 |
| 코드 | 위에서 아래로 | 콜백으로 쪼개진다 | 7절 |
| 맞는 곳 | 순서가 본질인 곳 | 관계없는 기다림이 많은 곳 | 의존하는 단계는 어차피 못 겹친다 |

| 10 ms 걸리는 요청 100개 | 걸린 시간 | 클라이언트가 더한 OS 스레드 | 왜 |
|:--------------------|--------:|--------------:|:---|
| 동기, 순차 | 1,209~1,252 ms | 0 | 하나가 끝나야 다음을 보낸다. 100 × 10 ms + 왕복 |
| 동기, 스레드 100개 | 15 ms | +100 | 기다림을 스레드 100개가 겹친다 |
| 비동기, 셀렉터 스레드 하나 | 14~15 ms | 0 | 100개를 다 던지고 완료를 이벤트로 받는다. `select()` 2~3번 |
| 가상 스레드 100개 | 14 ms | 0 | 코드는 동기, 런타임이 비동기로 바꾼다 |
| A의 답으로 B를 부르는 사슬 | 순차 2,454 / 스레드 27 / 셀렉터 28 / 가상 27 ms | | 의존은 겹칠 수 없다. 겹치는 것은 연결 사이뿐 |

같은 요청 100개다. 동기 순차는 1.2초다. 100개 × 10ms에 왕복 비용이 얹힌 값이고, 그동안 클라이언트 스레드는 99%를 잔다. 겹치는 방법은 둘이다. 스레드 100개로 동기 호출을 100번 겹치면 15ms이고 OS 스레드가 100개 는다. 셀렉터 스레드 하나가 100개를 다 던져 두고 `select()`로 완료를 받으면 14ms이고 스레드는 그대로다. `select()`는 두세 번이면 됐다. 답 100개가 거의 한꺼번에 도착해 한 바퀴에 묶였기 때문이다. 결과가 같은 것은 우연이 아니다. 둘 다 기다림 100개를 겹쳤고, 겹칠 수 있는 기다림의 총량은 같다. 다른 것은 누가 기다리느냐, 그 값이 스레드 100개냐 상태 객체 100개냐다. 가상 스레드 100개는 코드가 동기이면서 스레드가 늘지 않는다. 런타임이 셀렉터 쪽 일을 대신하기 때문이고, [10](../10-nonblocking-io)장 6절이 그 모습이었다. 마지막 줄이 비동기의 한계다. A의 답으로 B를 부르는 사슬은 어떤 방법으로도 2 × 14ms다. 의존하는 두 단계는 겹칠 수 없고, 비동기는 관계없는 기다림만 겹친다. [07](../07-task-decomposition)장 2절의 의존 그래프가 여기서도 상한이다.

{{< callout type="warning" >}}
**동기/비동기와 블로킹/논블로킹은 다른 축이다.** [10](../10-nonblocking-io)장 2.3절대로 블로킹/논블로킹은 *이 호출이 나를 멈추는가*, 동기/비동기는 *완료를 내가 되묻는가, 통지받는가*다. 이벤트 기반 동시성은 **논블로킹 연산 + 비동기 통지**의 조합이다. 호출은 즉시 돌아오고(논블로킹), 완료는 이벤트로 온다(비동기). 위 표의 셀렉터 줄이 그 조합이고, 스레드 100개 줄은 블로킹 + 동기를 스레드로 겹친 것이다.
{{< /callout >}}

## 3. 이벤트 기반 시스템의 구성 요소

둘째 원리다. 이름은 프레임워크마다 다르지만 조각은 같다.

```text
 소켓·타이머·시그널 (이벤트 소스)
          │ 이벤트 발생
          ▼
┌──────────────────────────┐
│   이벤트 디멀티플렉서    │
│   (select/epoll/kqueue)  │
└────────────┬─────────────┘
             │ 준비된 것만 통지
             ▼
┌──────────────────────────┐
│   이벤트 루프·디스패처   │
└────────────┬─────────────┘
             │ 이벤트 → 짝지어진 콜백
             ▼
┌──────────────────────────┐
│  핸들러 A   B   C (콜백) │
└──────────────────────────┘
```

| 구성 요소 | 역할 | 4절의 에코 서버에서 | 왜 필요한가 |
|:--------|:-----|:---------------|:---------|
| 이벤트 | "무슨 일이 생겼다"는 사실 | 연결 도착, 읽을 수 있음 | 반응할 계기 |
| 이벤트 소스 | 이벤트를 내는 것 | 소켓, 타이머, 시그널 | 등록해 둬야 감시된다 |
| 이벤트 디멀티플렉서 | 소스 여럿을 한 번에 감시해 준비된 것만 통지 | `Selector` (이 PC에서는 kqueue) | 준비 안 된 것을 내가 묻지 않게 |
| 이벤트 큐 | 발생한 이벤트를 순서대로 보관 | `selectedKeys()`, 워커의 완료 큐 | 한 바퀴에 묶어 처리한다 |
| 이벤트 루프 | 큐에서 꺼내 도는 무한 루프 | `while (true) { select(); … }` | 스레드 하나가 전부를 돈다 |
| 디스패처 | 이벤트를 알맞은 핸들러에 배정 | `key.attachment()` | 이벤트와 코드를 잇는다 |
| 핸들러(콜백) | 이벤트별 실제 처리 | `Acceptor`, `EchoHandler` | 짧아야 한다(4.3절) |

조각들이 잇는 흐름은 하나다. 소스에서 이벤트가 나면 디멀티플렉서가 그것을 골라 루프에 주고, 루프가 디스패처를 통해 짝지어진 핸들러를 부른다. [10](../10-nonblocking-io)장 6절의 셀렉터 루프가 이 조각 전부를 20줄에 담고 있었다. `select()`가 디멀티플렉서, `selectedKeys()`가 큐, `while (true)`가 루프, `key.attachment()`가 디스패처, 그 attachment가 핸들러다. 이름을 나누는 이유는 바꿔 끼우기 위해서다. 디멀티플렉서를 kqueue에서 epoll로, 핸들러를 에코에서 HTTP 파서로 바꿔도 나머지는 그대로다.

{{< callout type="info" >}}
**디멀티플렉서(demultiplexer)** 라는 이름은 신호 처리에서 왔다. 여러 입력선을 하나로 모으는 것이 멀티플렉싱이고, 그 하나를 다시 원래의 여러 갈래로 되돌리는 것이 디멀티플렉싱이다. 여기서는 "여러 소켓을 한 번의 `select()`로 감시하고, 준비된 소켓을 각자의 핸들러로 되돌려 보낸다"는 뜻이다.
{{< /callout >}}

## 4. 리액터 패턴

> **리액터 패턴(reactor pattern)** 은 단일 스레드로 도는 이벤트 루프와 논블로킹 이벤트로 이루어지고, 발생한 이벤트의 처리를 알맞은 콜백에 맡긴다.

입출력 중심 프로그램에서 이벤트 기반 동시성을 구현하는 가장 흔한 형태다. 스스로 일을 찾아 나서지 않고 들어온 이벤트에 반응(react)만 한다. 1995년 슈미트(Douglas Schmidt)가 이름 붙인 패턴이고, [10](../10-nonblocking-io)장 5절의 이벤트 루프가 그 뼈대였다.

### 4.1 동작 흐름

```text
① 핸들러 등록
   채널 + 관심 이벤트 + 콜백
       ▼
② select()
   준비된 이벤트 생길 때까지 잔다
       ▼
③ 이벤트 수신
   준비된 채널 목록을 받는다
       ▼
④ 디스패치
   각 이벤트를 짝 콜백에 넘긴다
       ▼
⑤ 콜백 실행
   짧게, 기다리지 않고
       └──▶ ②로 (무한 반복)
```

| 쉬지 않고 에코를 보내는 클라이언트 N개, 루프 하나 | 초당 이벤트 | `select()` 한 번에 준비된 키 | 이벤트당 루프 시간 | 루프가 바쁜 비율 | 응답 지연 (중앙값 / p99) | 왜 |
|:-----------------------------|--------:|----------:|---------:|------:|--------------:|:---|
| 1 | 64,905 | 1.0 | 2.75 µs | 18% | 14 / 20 µs | 이벤트마다 잔다. 왕복이 곧 지연 |
| 10 | 256,674 | 4.5 | 3.23 µs | 83% | 34 / 67 µs | 한 바퀴에 4.5개를 묶는다 |
| 50 | 257,163 | 41.6 | 3.39 µs | 87% | 156 / 358 µs | 초당 25.7만이 이 루프의 천장 |
| 100 | 255,241 | 80.0 | 3.41 µs | 87% | 329 / 721 µs | 천장 위에서는 지연이 N에 비례 |

③에서 ⑤까지가 한 바퀴(tick)다. 리액터의 성능은 한 바퀴를 얼마나 빨리, 얼마나 많이 묶어 도느냐다. 위 표가 이 PC의 루프 하나를 해부한 것이다. 클라이언트 하나가 쉬지 않고 보내면 이벤트마다 한 바퀴를 돌고, 바퀴마다 `select()`에서 잠들었다 깨니 루프는 18%만 바쁘고 초당 6.5만 개다. 열 개가 보내면 한 번 깨어날 때 평균 4.5개가 준비돼 있다. `select()` 한 번의 값이 4.5개에 나뉘고 초당 25.7만 개가 된다. 50개, 100개가 보내도 초당 개수는 그대로다. 루프가 87% 바쁘고 이벤트당 3.4µs가 이 루프의 천장이기 때문이다. 천장 위에서는 한 바퀴에 묶이는 이벤트가 42개, 80개로 늘고 응답 지연이 클라이언트 수에 비례한다. 100개가 줄을 서면 내 차례까지 80개 × 3.4µs다. 이벤트당 3.4µs 중 계산은 거의 없다. `read()`와 `write()` 시스템 콜 두 번이 대부분이고, 그래서 이 숫자가 커지는 유일한 길은 콜백이 길어지는 것이다(4.3절).

{{< callout type="info" >}}
**한 바퀴에 묶이는 이벤트 수가 처리량을 만든다.** `select()`는 시스템 콜이라 한 번에 수 µs이고, 준비된 이벤트가 하나뿐이면 그 값을 이벤트 하나가 다 낸다. 부하가 오르면 한 번 깨어날 때 준비된 것이 여럿이고 값이 나뉜다. 그래서 이벤트 루프는 한가할 때 이벤트당 비용이 가장 높고 바쁠수록 싸진다. 스레드 기반이 바쁠수록 전환 비용으로 비싸지는 것([04](../04-concurrency-ingredients)장 4.2절)과 반대 방향이다.
{{< /callout >}}

### 4.2 Java NIO로 구현한 리액터

`Selector`가 디멀티플렉서, `loop()`의 무한 루프가 이벤트 루프, `SelectionKey`의 attachment가 이벤트와 핸들러를 이어 주는 고리다.

```java
// 핸들러: 이벤트마다 루프가 부른다
interface Handler {
    void handle() throws IOException;
}
```

```java
// 리액터: 이벤트 루프 + 디스패처
class Reactor {
    final Selector sel;

    Reactor(ServerSocketChannel server)
            throws IOException {
        sel = Selector.open();
        server.configureBlocking(false);
        var key = server.register(sel,
                SelectionKey.OP_ACCEPT);
        key.attach(
            new Acceptor(sel, server));
    }

    void loop() throws IOException {
        while (true) {
            sel.select();   // ② 잔다
            var keys =
                sel.selectedKeys();
            for (var k : keys) {
                dispatch(k); // ④ 위임
            }
            keys.clear();
        }
    }

    void dispatch(SelectionKey k) {
        var h = (Handler)
            k.attachment();
        try {
            h.handle();     // ⑤ 콜백
        } catch (IOException e) {
            k.cancel();     // 이 연결만
        }
    }
}
```

```java
// 연결 수락 핸들러
class Acceptor implements Handler {
    final Selector sel;
    final ServerSocketChannel server;

    Acceptor(Selector sel,
            ServerSocketChannel srv) {
        this.sel = sel;
        this.server = srv;
    }

    public void handle()
            throws IOException {
        SocketChannel c;
        while ((c = server.accept())
                != null) {
            new EchoHandler(sel, c);
        }
    }
}
```

```java
// 읽기·쓰기 핸들러: 연결 하나의 상태
class EchoHandler implements Handler {
    final SocketChannel ch;
    final SelectionKey key;
    final ByteBuffer buf =
        ByteBuffer.allocate(1024);

    EchoHandler(Selector sel,
            SocketChannel ch)
            throws IOException {
        this.ch = ch;
        ch.configureBlocking(false);
        key = ch.register(sel,
                SelectionKey.OP_READ);
        // 이벤트와 콜백을 잇는다
        key.attach(this);
    }

    public void handle()
            throws IOException {
        buf.clear();
        int n = ch.read(buf);
        if (n < 0) {
            key.cancel();
            ch.close();
        } else if (n > 0) {
            buf.flip();
            ch.write(buf);
        }
    }
}
```

세 조각이 3절의 표 그대로다. `Reactor.loop()`가 ②~⑤를 무한히 돌고, `dispatch()`가 키에 붙은 핸들러를 부른다. `Acceptor`는 연결 수락 이벤트의 콜백이고, 새 연결마다 `EchoHandler`를 만들어 읽기 이벤트에 붙인다. `EchoHandler`는 연결 하나의 콜백이자 상태다. 이 장의 실험에 쓴 서버가 이 뼈대에 16바이트 메시지 형식과 계산 콜백을 얹은 것이다. `dispatch()`가 `IOException`을 받아 그 키만 취소하는 것은 사소해 보이지만 7절의 실험이 그 이유다. 콜백에서 새어 나온 예외 하나가 루프 스레드를 죽인다.

{{< callout type="info" >}}
**연결 상태는 스레드가 아니라 객체가 들고 있다.** 스레드 기반 서버에서는 "어디까지 읽었는가"가 스레드의 스택에 저절로 남는다. 이벤트 기반에서는 콜백이 매번 반환하므로 스택이 사라진다. 그래서 진행 상태를 `EchoHandler`의 필드(`buf`, 그리고 실제 프로토콜이라면 "헤더까지 읽었다" 같은 단계)에 직접 보관해야 한다. 이것이 이벤트 기반 코드가 스레드 기반보다 까다로운 근본 이유이고, [12](../12-asynchronous-communication)장 3.3절의 코루틴이 이 일을 컴파일러에 넘기는 이유다.
{{< /callout >}}

### 4.3 리액터의 절대 규칙 — 콜백은 블로킹하면 안 된다

```text
정상: 콜백이 짧다
루프 │▪▪▪│▪▪▪│▪▪▪│▪▪▪│ 촘촘히

콜백 하나가 10ms를 잡는다
루프 │▪▪▪│■■■■■■■■■■■│▪▪▪│
              ▲
      그동안 모든 연결이 멈춘다
```

| 보통 클라이언트 10개에 콜백이 W만큼 계산하는 클라이언트 하나를 더함 | 보통 클라이언트의 지연, 루프 안에서 계산 (중앙값 / p99) | 루프가 바쁜 비율 | 워커 풀 4개에 넘기면 | 무거운 클라이언트 자신 (넘겼을 때) | 왜 |
|:----------------------------------|-------------------:|------:|------------:|------------:|:---|
| W = 0 | 20 / 55 µs | 24% | 20 / 54 µs | 14 / 22 µs | 기준 |
| W = 10 µs | 22 / 57 µs | 61% | 20 / 57 µs | 32 / 47 µs | 10 µs는 한 바퀴 안에 묻힌다 |
| W = 100 µs | 73 / 144 µs | 91% | 19 / 57 µs | 128 / 157 µs | 남의 p99 ≈ W |
| W = 1 ms | 439 / 1,133 µs | 96% | 48 / 88 µs | 1,121 / 1,208 µs | 남의 중앙값 ≈ W/2. 넘기면 워커의 시간. 48 µs는 유휴 루프가 깨는 시간 |
| W = 10 ms | 9,173 / 9,801 µs | 99% | 48 / 93 µs | 10,706 / 13,114 µs | 콜백이 루프고, 루프가 서버다 |

셋째 원리다. 리액터는 모든 콜백을 같은 스레드에서 부른다. 콜백 하나가 멈추면 루프가 멈추고, 그 순간 이 루프에 달린 모든 연결이 멈춘다. 위 표는 보통 클라이언트 열 개가 0.5~1.5ms에 한 번씩 메시지를 보내는 서버에 콜백이 W만큼 계산하는 클라이언트 하나를 더한 것이다. W가 10µs면 아무도 모른다. 한 바퀴 안에 묻힌다. 100µs면 남의 p99가 144µs다. 1ms면 남의 중앙값이 439µs, p99가 1.1ms다. 남이 도착하는 시점이 그 계산의 아무 데나이니 평균 W/2를 기다리고 운이 나쁘면 W를 기다린다. 10ms면 남의 요청 전부가 9~10ms다. [10](../10-nonblocking-io)장 5.1절의 12ms가 이것이다. 같은 계산을 워커 풀 네 스레드에 넘기고 결과를 완료 큐로 돌려받으면 남의 지연은 W와 무관하게 48µs다. 무거운 클라이언트 자신은 여전히 W를 기다리지만 그것은 그의 값이다. 48µs가 20µs보다 큰 것은 넘기는 값이 아니다. 무거운 클라이언트 없이 보통 클라이언트 열 개만 1ms에 한 번씩 보내도 46~50µs였다. 루프가 잠들었다 깨는 시간이고, W가 100µs까지 20µs였던 것은 무거운 클라이언트의 쉼 없는 메시지가 루프를 깨어 있게 한 덕이다. 넘기는 값 자체는 워커를 깨우고 완료를 큐에 넣고 `wakeup()`으로 루프를 깨우는 왕복, [04](../04-concurrency-ingredients)장 4.2절의 3µs 단위다. 그래서 짧은 일은 루프에서 하고 긴 일만 넘긴다. 경계는 한 바퀴의 길이다. 이 PC에서는 수십 µs다.

| 루프 안에서 하면 안 되는 것 | 대신 | 왜 |
|:---------------------|:-----|:---|
| 블로킹 DB 드라이버(JDBC) 호출 | 논블로킹 드라이버(R2DBC), 또는 워커 풀 | 쿼리 10 ms가 모든 연결의 10 ms |
| `Thread.sleep()`, 동기 `read()` | 타이머 이벤트, 논블로킹 채널 | 기다림을 커널에 맡기는 것이 루프의 존재 이유 |
| 무거운 계산(암호화, 압축, 직렬화) | 워커 풀, 또는 서브 리액터(6절) | 100 µs부터 남의 p99에 보인다 |
| 락 대기 | 단일 스레드 소유, 락 없는 큐 | 루프가 락을 기다리면 [09](../09-deadlock-and-starvation)장의 교착이 서버 전체가 된다 |

{{< callout type="warning" >}}
**이벤트 루프 블로킹은 이벤트 기반 서버에서 가장 흔한 장애 원인이다.** 스레드 기반 서버에서 느린 쿼리 하나는 그 요청 하나만 느리게 만들지만, 이벤트 기반에서는 서버 전체를 세운다. Node.js에서 동기 `fs.readFileSync()`를 요청 경로에 쓰거나, Spring WebFlux에서 블로킹 JDBC를 그대로 부르는 것이 대표적인 사고다. 위 표의 W = 10ms 줄이 그 사고의 크기이고, 사고가 나면 CPU 그래프는 조용하다. 루프는 한 스레드라 코어 하나 위로는 안 올라간다.
{{< /callout >}}

## 5. 프로액터 패턴 — 준비 통지 vs 완료 통지

```text
리액터: "이제 읽을 수 있다"
 커널 ─준비 통지─▶ 콜백
 콜백이 직접 read()

프로액터: "다 읽어 놨다"
 커널·런타임이 버퍼까지 채움
 커널 ─완료 통지─▶ 콜백
 콜백은 결과만 쓴다
```

| 구분 | 리액터 | 프로액터 | 왜 |
|:-----|:-----|:------|:---|
| 통지 시점 | I/O **준비** | I/O **완료** | 누가 read()를 부르느냐 |
| 실제 read/write | 콜백이 직접 | 커널·런타임이 대신 | 프로액터는 버퍼를 미리 넘긴다 |
| [10](../10-nonblocking-io)장 2.3절의 칸 | 논블로킹 + 동기 | 논블로킹 + 비동기 | 준비는 되묻는 것, 완료는 통지받는 것 |
| 기반 기술 | select, poll, epoll, kqueue | IOCP, io_uring, POSIX AIO | 커널이 완료 큐를 주느냐 |
| 자바 API | `Selector` (NIO) | `AsynchronousSocketChannel` (NIO.2) | |
| 구현 난이도 | 상대적으로 단순 | 버퍼 수명 관리가 까다롭다 | 읽는 동안 버퍼를 건드리면 안 된다 |

```java
// 프로액터: 다 읽은 뒤 콜백이 불린다
var buf = ByteBuffer.allocate(1024);
ch.read(buf, conn,
    new CompletionHandler<>() {
        public void completed(
                Integer n, Conn c) {
            buf.flip(); // 이미 차 있다
            handle(buf);
        }
        public void failed(
                Throwable t, Conn c) {
            close(c);
        }
    });
// read()는 즉시 돌아온다
```

| 에코, 쉬지 않는 클라이언트 N개 | 리액터 (`Selector`) 지연 (중앙값 / p99), 초당 | 프로액터 (`AsynchronousSocketChannel`) 지연, 초당 | 왜 |
|:--------------------|-------------------:|-------------------:|:---|
| 1 | 14 / 21 µs, 72,543 | 16 / 27 µs, 59,745 | 완료 통지가 스레드 풀을 거친다 |
| 10 | 35 / 72 µs, 283,152 | 51 / 112 µs, 186,498 | 왕복이 16 µs 더 걸린다 |
| 100 | 330 / 718 µs, 284,198 | 528 / 1,002 µs, 194,602 | 천장이 낮으니 줄이 길다 |
| 핸들러가 돈 스레드 | 1개 (루프 스레드) | N = 1에서 11개, N = 100에서 40개 | 프로액터의 콜백은 아무 스레드에서나 불린다 |
| OS 스레드 (서버 시작 전 27) | 27 | 67 | JDK가 kqueue 위에 스레드 풀로 흉내 낸다 |

리액터와 짝지어 나오는 것이 프로액터다. 둘의 차이는 커널이 무엇을 알려 주느냐다. 리액터는 "이제 읽을 수 있다"는 준비를 통지받고 콜백이 직접 `read()`를 부른다. [10](../10-nonblocking-io)장 2.3절의 둘째 칸, 논블로킹이되 동기다. 프로액터는 "다 읽어 버퍼에 넣어 뒀다"는 완료를 통지받고 콜백은 결과만 쓴다. 넷째 칸, 비동기다. 자바에서는 `Selector`와 `AsynchronousSocketChannel`이다. 위 표는 같은 에코 서버를 둘로 만들어 잰 것이다. 이 PC에서는 프로액터가 느리다. 클라이언트 열 개에서 중앙값 35µs가 51µs이고, 초당 28만이 19만이다. 이유는 스레드 수에 있다. macOS와 리눅스에는 완료 기반 소켓 I/O가 없어서 JDK가 kqueue·epoll 위에 스레드 풀을 두고 프로액터를 흉내 낸다. 풀의 스레드가 준비를 받아 대신 읽고 완료 핸들러를 부른다. 그래서 핸들러가 도는 스레드가 클라이언트 하나일 때도 11개, 100개일 때 40개였고 OS 스레드가 40개 늘었다. 완료가 스레드 사이를 건너는 값이다. 클라이언트 하나에서 왕복 2µs, 열 개에서 16µs가 더 걸렸고, 처리량으로 보면 이벤트당 3.5µs가 5.4µs다. 4.3절에서 워커 풀에 넘길 때 치르는 것과 같은 성질의 값인데, 여기서는 모든 이벤트가 그 값을 낸다. 그리고 콜백이 어느 스레드에서 불릴지 모르니 연결 상태를 만지는 코드에 다시 동기화가 필요하다. 리액터가 스레드 하나로 없앴던 그 값이다.

{{< callout type="info" >}}
**프로액터가 제값을 하는 곳은 커널이 정말 완료 기반인 곳이다.** 리눅스는 오랫동안 완료 기반 소켓 I/O가 없어 `epoll` 위의 리액터가 사실상 표준이 됐고, 자바의 `AsynchronousSocketChannel`도 리눅스와 macOS에서는 위 표처럼 스레드 풀로 흉내 낸다. 윈도우의 IOCP는 처음부터 완료 기반이라 그 위에서는 스레드 풀 없이 커널이 버퍼를 채우고 완료 큐에 넣어 준다. 리눅스 5.1(2019)의 io_uring이 같은 완료 기반 인터페이스를 제공하면서 이 구도가 바뀌고 있다.
{{< /callout >}}

## 6. 멀티 리액터 — 단일 스레드의 한계를 넘기

```text
      클라이언트 연결들
            │
     ┌──────▼──────┐
     │ 메인 리액터 │ accept 전담
     └──────┬──────┘
     ┌──────┼──────┐
     ▼      ▼      ▼
  [서브1] [서브2] [서브3]  read/write
   코어1   코어2   코어3   + 콜백
     └──────┼──────┘
            ▼
      워커 스레드 풀
    (블로킹·긴 계산 격리)
```

| 계층 | 스레드 수 | 담당 | 왜 |
|:-----|:-------|:-----|:---|
| 메인 리액터 | 1 | 연결 수락(accept)만 | 수락은 가볍고, 배정을 한곳에서 |
| 서브 리액터 | 코어 수만큼 | 각자 맡은 연결의 read/write와 콜백 | 코어마다 루프 하나. 연결은 한 루프에 고정 |
| 워커 풀 | 별도 | 블로킹, 긴 계산 | 루프를 비우는 4.3절의 답 |

```java
// 메인은 accept만, 연결은 서브에 배정
while (true) {
    boss.select();
    SocketChannel c;
    while ((c = server.accept())
            != null) {
        // 큐에 넣고 wakeup()
        subs[rr++ % subs.length]
            .assign(c);
    }
}
```

| 연결 64개, 메시지마다 콜백이 20 µs 계산 | 초당 메시지 | 배속 | 지연 (중앙값 / p99) | 왜 |
|:---------------------------|--------:|-----:|--------------:|:---|
| 서브 리액터 1 | 34,801 | 1.0 | 1,817 / 3,630 µs | 20 µs × 64가 줄을 선다 |
| 2 | 71,438 | 2.05 | 860 / 1,748 µs | 코어 둘 |
| 4 | 125,852 | 3.6 | 422 / 1,264 µs | |
| 6 | 153,717 | 4.4 | 376 / 1,067 µs | |
| 8 | 179,425 | 5.2 | 309 / 981 µs | |
| 10 | 191,273 | 5.5 | 233 / 2,209 µs | 실효 코어 6.8([02](../02-sequential-and-parallel-execution)장). 클라이언트 64개도 코어를 쓴다 |
| 계산 없는 에코, 서브 1 → 10 | 281,338 → 217,613 | 0.77 | 207 / 470 → 288 / 522 µs | 일이 없으면 나누는 값만 남는다 |
| 연결이 스레드를 옮긴 횟수 | 0 (모든 실험) | | | 한 연결은 한 서브 리액터. 락이 필요 없다 |

리액터는 스레드 하나가 원칙이고, 그러면 코어 하나만 쓴다. 4.1절의 루프 하나는 초당 25.7만 이벤트가 천장이고, 콜백에 계산이 있으면 그보다 훨씬 낮다. 위 표에서 메시지마다 20µs를 계산하니 루프 하나는 초당 3.5만이다. 실무 프레임워크는 리액터를 여럿 둔다. 메인 리액터 하나가 `accept`만 하고 받은 연결을 서브 리액터에 돌아가며 배정하며, 서브 리액터는 각자 맡은 연결의 읽기·쓰기·콜백을 돈다. 서브가 둘이면 2.05배, 넷이면 3.6배, 열이면 5.5배다. 열에서 10배가 안 되는 이유는 [02](../02-sequential-and-parallel-execution)장의 실효 코어 6.8에 클라이언트 64개도 같은 코어를 쓴다는 것이고, 열에서 p99가 튄 것은 스레드 75개가 코어 10개를 나눠 쓰며 밀려난 것이다([06](../06-multitasking)장 5.2절). 표의 마지막 두 줄이 이 설계의 조건이다. 콜백에 계산이 없으면 서브를 늘릴수록 느려진다. 28만이 22만이다. 한 바퀴에 묶이던 이벤트가 루프 10개에 흩어져 `select()`의 값이 나뉘지 않고, 스레드 75개가 코어 10개를 나눠 쓰는 값이 얹힌다. 멀티 리액터는 콜백에 일이 있을 때의 답이다. 그리고 모든 실험에서 연결이 스레드를 옮긴 횟수는 0이었다. 한 연결은 처음 배정된 서브 리액터가 끝까지 든다.

{{< callout type="info" >}}
Netty의 `bossGroup`(메인 리액터)과 `workerGroup`(서브 리액터)이 정확히 이 구조다. 핵심 원칙은 **한 연결은 언제나 같은 서브 리액터 스레드가 처리한다**는 것이다. 연결 상태를 만지는 코드에 락이 필요 없고, [08](../08-race-conditions-and-synchronization)장 7절의 동기화 값이 아예 없다. 5절의 프로액터가 스레드 풀 때문에 잃었던 것을 되찾는 설계다.
{{< /callout >}}

## 7. 콜백 지옥과 그 해법

```java
// 콜백 지옥: 흐름이 오른쪽으로 밀린다
findUser(id, user ->
    findOrders(user, orders ->
        findItems(orders, items ->
            calcPrice(items, price ->
                render(price)))));
// 에러는 어디로 가나?
```

```java
// 퓨처: 중첩을 평평한 사슬로
findUserAsync(id)
    .thenCompose(this::findOrdersAsync)
    .thenCompose(this::findItemsAsync)
    .thenCompose(this::calcPriceAsync)
    .thenAccept(this::render)
    .exceptionally(e -> {  // 한곳에서
        log.error("조회 실패", e);
        return null;
    });
```

| 4단 사슬, 단계마다 루프 스레드의 큐를 거침 | 사슬 하나의 비용 | 둘째 단계에서 예외가 나면 | 왜 |
|:----------------------------|-----------:|:-------------------|:---|
| 중첩 콜백 | 180~236 ns | 루프 스레드가 죽는다. 뒤의 요청은 큐에 남은 채 영원히 대기, 요청자는 모른다 | 콜백에는 실패가 갈 길이 없다 |
| 중첩 콜백, 루프가 예외를 삼킴 | | 루프는 살고 뒤의 요청도 처리된다. 요청자는 여전히 모른다 | 같다 |
| `CompletableFuture.thenCompose` | 865~917 ns | `join()`이 `CompletionException`으로 던지고, `exceptionally`가 대신 값을 준다 | 퓨처가 결과와 예외를 같이 나른다 |
| 사슬 하나를 보내고 답을 기다린 지연 | 콜백 4.5~4.7 µs, 퓨처 5.1~5.2 µs | | 스레드 사이 왕복이 대부분 |

이벤트 기반 코드의 값은 가독성이다. 순차로 읽히던 코드가 콜백 단위로 쪼개지고, 의존하는 단계가 이어지면 오른쪽으로 밀린다. 그리고 에러가 갈 길이 없다. 위 표가 그 둘을 잰 것이다. 네 단계 사슬을 루프 스레드에 흘리면 콜백은 사슬당 180ns, `CompletableFuture`는 900ns다. 퓨처는 단계마다 객체를 만들고 완료를 전파하니 다섯 배 비싸다. 사슬 하나를 보내고 답을 기다리면 둘 다 5µs 언저리다. 스레드 사이 왕복이 대부분이고 그 안에서 700ns 차이는 묻힌다. 값은 거기가 아니라 셋째 열에 있다. 둘째 단계 콜백이 예외를 던지자 손으로 짠 루프 스레드가 죽었다. 그 뒤에 들어온 요청은 큐에 남은 채 영원히 기다렸고, 예외가 난 요청을 보낸 쪽은 아무 통지도 못 받았다. 루프가 예외를 삼키게 고치면 뒤의 요청은 살지만 그 요청자는 여전히 모른다. 콜백에는 결과가 가는 길만 있고 실패가 가는 길이 없기 때문이다. `CompletableFuture`는 결과와 예외를 같은 객체에 나른다. 같은 예외가 `join()`에서 `CompletionException`으로 던져졌고, `exceptionally`가 대신 값을 줬으며, 뒤의 요청은 정상이었다. 해법은 콜백을 값으로 다루는 것이다. [12](../12-asynchronous-communication)장 4절이 그 값(퓨처)이고, 같은 장 5절과 6절이 그 값을 다시 순차 코드처럼 읽게 하는 두 길이다.

| 세대 | 방식 | 특징 | 왜 다음 세대가 나왔나 |
|:-----|:-----|:-----|:---------------|
| 1 | 콜백 | 가장 단순. 중첩되고, 에러가 갈 길이 없다 | 위 표의 셋째 열 |
| 2 | Future·Promise | 결과와 예외를 값으로 다뤄 중첩을 편다 | 조합은 되지만 여전히 콜백 문법 |
| 3 | 리액티브 스트림 | 스트림과 배압(backpressure) | 값 하나가 아니라 흐름을 다루려고 |
| 4 | 코루틴·async/await | 비동기를 순차처럼 쓴다. 컴파일러가 상태 기계로 바꾼다 | 4.2절의 "상태를 필드에"를 컴파일러가 대신 |
| 4 | 가상 스레드 | 블로킹 코드를 그대로, 스레드를 싸게 | 루프를 런타임 아래로 숨긴다 |

{{< callout type="info" >}}
**자바 21의 가상 스레드(virtual thread)** 는 이 문제를 다른 방향에서 푼다. 이벤트 루프에 맞춰 코드를 비틀지 않고, 스레드 자체를 싸게 만들어 블로킹 스타일 코드를 그대로 쓰게 한다. 블로킹 호출이 일어나면 런타임이 캐리어 스레드에서 가상 스레드를 걷어내므로 겉은 동기 코드이고 속은 이벤트 기반이다. [10](../10-nonblocking-io)장 6절에서 OS 스레드 42개로 연결 1만 개를 든 것과 2.3절에서 요청 100개를 14ms에 끝낸 것이 그 실물이고, 얹히는 방식은 [12](../12-asynchronous-communication)장 6절이다.
{{< /callout >}}

## 8. 실전에서의 이벤트 기반 시스템

| 시스템 | 구조 | 비고 | 왜 그 구조인가 |
|:-----|:-----|:-----|:-----------|
| **Node.js** | libuv 이벤트 루프 + 콜백 | I/O는 논블로킹, 계산은 루프를 세운다 | 자바스크립트가 단일 스레드라 리액터가 자연스럽다. 계산은 워커 스레드로 |
| **Nginx** | 워커 프로세스마다 이벤트 루프 | 코어 수만큼 워커 | 6절의 멀티 리액터를 프로세스로. 워커끼리 연결을 나누지 않으니 락이 거의 없다 |
| **Redis** | 명령 실행은 스레드 하나 | 6.0부터 소켓 읽기·쓰기만 I/O 스레드 | 명령이 한 스레드에서 돌면 락 없이 원자적이다 |
| **Netty** | 메인·서브 리액터 + 워커 풀 | 자바 비동기 서버의 사실상 표준 | 연결을 서브 리액터에 고정해 상태에 락이 없다 |
| **Spring WebFlux** | Netty 위의 리액티브 스택 | 블로킹 드라이버를 섞으면 4.3절의 사고 | 루프가 보이지 않아 규칙을 잊기 쉽다 |

{{< callout type="warning" >}}
**이벤트 기반이 항상 빠른 것은 아니다.** 연결 수가 적고 요청마다 무거운 계산을 하는 서비스라면 스레드 기반 + 스레드 풀이 더 단순하고 더 빠르다. 6절에서 콜백에 계산이 없으면 리액터를 늘려도 느려졌고, 계산이 있으면 결국 코어 수가 상한이었다. 이벤트 기반의 이점은 연결이 많고 각 연결이 대부분 기다리는 상황에서 나온다. 구조를 고르기 전에 워크로드가 I/O 바운드인지부터 확인해야 한다.
{{< /callout >}}

| 규칙 | 콜백은 블로킹하면 안 된다 | W = 1 ms면 남의 p99 1.1 ms, 넘기면 48 µs |
| 프로액터 | 완료를 통지받는다 | 이 PC에서는 스레드 풀 흉내. 스레드 40개, 35 → 51 µs |
| 멀티 리액터 | 메인은 accept, 서브는 연결을 나눠 든다 | 서브 10개 5.5배, 계산 없으면 0.77배, 연결 이동 0 |
| 콜백 지옥 | 흐름이 쪼개지고 에러가 갈 길이 없다 | 예외 하나에 루프가 죽는다. 퓨처는 예외도 나른다 |

{{< callout type="info" >}}
**용어 정리**
- **이벤트 기반 동시성**: 작업을 스레드에 미리 나누지 않고, 이벤트가 생겼을 때만 등록된 코드를 실행하는 방식
- **동기 통신**: 보내는 쪽과 받는 쪽이 둘 다 준비돼 만나야 건네지고, 그때까지 멈추는 통신
- **비동기 통신**: 시작만 하고 완료를 기다리지 않는 통신. 완료는 이벤트로 통지받는다
- **이벤트 / 이벤트 소스**: "무슨 일이 생겼다"는 사실 / 그것을 내는 소켓, 타이머, 시그널
- **이벤트 디멀티플렉서**: 소스 여럿을 한 번에 감시해 준비된 것만 통지하는 것. `select`, `epoll`, `kqueue`
- **이벤트 루프**: 준비된 이벤트를 꺼내 콜백에 넘기는 단일 스레드 무한 루프
- **디스패처**: 이벤트를 알맞은 핸들러에 배정하는 부분. 자바에서는 `SelectionKey`의 attachment
- **핸들러 / 콜백**: 이벤트마다 루프가 부르는 코드. 짧아야 한다
- **한 바퀴(tick)**: 이벤트 수신부터 콜백 실행까지. 묶이는 이벤트가 많을수록 이벤트당 비용이 준다
- **리액터 패턴**: 단일 스레드 이벤트 루프 + 논블로킹 이벤트 + 콜백 위임. 준비를 통지받는다
- **프로액터 패턴**: 완료를 통지받는 패턴. IOCP, io_uring. 자바의 `AsynchronousSocketChannel`
- **워커 풀**: 루프가 기다리거나 오래 계산해야 하는 일을 넘기는 스레드 풀
- **멀티 리액터**: 메인 리액터가 accept, 서브 리액터가 연결을 나눠 드는 구조. 한 연결은 한 스레드
- **콜백 지옥**: 의존하는 비동기 단계가 중첩돼 흐름이 밀리고 에러가 갈 길을 잃는 것
- **CompletableFuture**: 결과와 예외를 같이 나르는 자바의 퓨처. `thenCompose`로 사슬을 편다
- **가상 스레드**: 런타임이 이벤트 루프 위에 얹은 싼 스레드. 블로킹 코드로 논블로킹 효과
