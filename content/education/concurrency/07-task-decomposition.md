앞 장들은 무엇으로 동시성을 만드는지였다. 이 장부터는 어떻게 쓰는지다. 동시성 프로그램의 첫 단추는 알고리즘도 동기화도 아니고 **문제를 동시에 돌 수 있는 조각으로 쪼개는 것**이다. 원리는 셋이다. 첫째, **분해의 출발점은 코어 수가 아니라 의존 관계다.** 어떤 작업이 어떤 작업을 기다리는지 그리면, 화살표로 이어지지 않은 것만 동시에 돌 수 있고, 가장 긴 사슬이 코어를 아무리 늘려도 넘지 못하는 하한이 된다. 둘째, **나누는 방향은 둘이다. 일이 다르면 일을 나누고, 같으면 데이터를 나눈다.** 일을 나누면 병렬도가 일의 개수에 묶이고, 데이터를 나누면 조각 수만큼 늘어난다. 실무는 둘을 겹쳐 쓴다. 셋째, **입도가 성패를 가른다.** 조각이 코어보다 적으면 코어가 놀고, 조각이 너무 잘면 만들고 합치는 비용이 일을 먹는다. 자원보다 넉넉하되 비용보다 큰 조각이 답이고, 그 사이는 재서 찾는다. 이 PC(Apple M4 10코어, JDK 23)에서 작업 넷의 의존 그래프를 돌려 임계 경로에 닿는지 보고, 기능 셋을 나눠 3배에서 막히는 것과 데이터를 더 나눠 6배가 되는 것을 보고, 세 단계 파이프라인의 처리율과 지연을 따로 재고, 포크/조인의 임계값을 10에서 400만까지 바꿔 가며 시간과 작업 수를 재고, 결합법칙이 없는 연산을 병렬로 접었을 때 답이 어떻게 틀리는지 봤다.

## 1. 왜 분해가 필요한가

```text
① 분해     문제 → 동시에 돌 수 있는 작업
      │
② 의존 분석  누가 누구를 기다리나 (DAG)
      │
③ 매핑     스레드·코어에 배치
      │
④ 동기화   공유하는 것을 지킨다 (08장)
이 장은 ①과 ②
```

| 단계 | 정하는 것 | 물음 | 왜 이 순서인가 |
|:-----|:-------|:-----|:-----------|
| 분해 | 무엇을 나눌지 | 어떤 조각이 서로 독립인가 | 독립이 아니면 나눈 의미가 없다 |
| 의존 분석 | 순서 | 누가 누구를 기다리나 | 임계 경로가 하한이다 |
| 매핑 | 어디서 돌릴지 | 스레드 몇 개, 코어 몇 개 | 자원은 나중에 맞춘다 |
| 동기화 | 공유의 규칙 | 조각이 무엇을 같이 쓰나 | [08](../08-race-conditions-and-synchronization)장 |

하나의 문제를 코어와 스레드 여럿에 나눠 주려면 먼저 그 문제를 동시에 실행할 수 있는 작업 단위로 나눠야 한다. 이것이 분해이고, 만능 공식은 없다. 같은 문제도 데이터의 모양과 자원의 구성에 따라 답이 다르다. 대신 출발점은 늘 같다. 작업 사이의 의존 관계를 먼저 그린다. [02](../02-sequential-and-parallel-execution)장 1절에서 스레드 다섯을 줘도 앞 결과에 의존하는 작업은 순차와 같은 시간이 걸렸다. 무엇을 동시에 돌릴 수 있는지는 코어가 아니라 의존 관계가 정한다.

{{< callout type="info" >}}
**분해는 "무엇을"이고 매핑은 "어디서"다.** 둘을 섞으면 "코어가 열 개니까 열 조각"처럼 자원에 끌려가는 분해를 하게 된다. 문제의 구조를 보고 나눈 뒤, 자원에 맞춰 입도(7절)를 조정하는 순서가 맞다. 이 장의 실험이 그 순서로 되어 있다.
{{< /callout >}}

## 2. 작업 의존 관계 그래프

### 2.1 화살표 없는 것만 동시에

```text
         ┌────────┐
         │ A 100ms│
         └───┬────┘
      ┌──────┴──────┐
      ▼             ▼
 ┌────────┐    ┌────────┐
 │ B 200ms│    │ C 150ms│  서로 모른다
 └───┬────┘    └───┬────┘  → 동시에
      └──────┬──────┘
             ▼
         ┌────────┐
         │ D 100ms│  B와 C를 기다린다
         └────────┘
임계 경로 A→B→D = 400 ms
```

| 그래프에서 읽는 것 | 뜻 | 위 그래프에서 | 왜 |
|:--------------|:---|:----------|:---|
| 화살표로 안 이어진 노드 | 동시에 돌 수 있다 | B와 C | 서로의 결과가 필요 없다 |
| 임계 경로 | 가장 긴 의존 사슬 | A→B→D, 400 ms | 이 길이보다 빨라질 수 없다 |
| 폭 | 한 순간에 동시에 돌 수 있는 최대 수 | 2 | 코어 셋째부터는 놀 것이다 |
| 합류 지점 | 기다렸다 합치는 곳 | D의 앞 | `join`이 필요한 자리 |

작업 의존 관계 그래프는 작업을 노드로, "먼저 끝나야 한다"를 화살표로 그린 방향 비순환 그래프(DAG)다. A→B는 A가 끝나야 B를 시작할 수 있다는 뜻이고, 화살표로 이어지지 않은 B와 C는 서로 모르니 동시에 돌 수 있다. 그래프에서 가장 긴 사슬이 임계 경로다. 이 경로 위의 작업은 반드시 순서대로 돌아야 하므로 그 길이가 전체 시간의 하한이고, 코어를 아무리 줘도 그보다 빠를 수 없다. [02](../02-sequential-and-parallel-execution)장 4절의 암달의 법칙이 분해 단계에서 보이는 모습이 이것이다. 순차 부분이 곧 임계 경로다.

### 2.2 이 PC에서 재 보기

```java
var A = supplyAsync(() -> stepA());
var B = A.thenApplyAsync(a -> stepB(a));
var C = A.thenApplyAsync(a -> stepC(a));
var D = B.thenCombineAsync(C,
    (b, c) -> stepD(b, c));
D.join();   // 428 ms. 합은 561 ms
```

| 작업 넷 (100·200·150·100 ms 계산) | 걸린 시간 | 왜 |
|:---------------------------|--------:|:---|
| 순서대로 | 561 ms | 넷의 합 |
| 그래프대로 (`CompletableFuture`) | 428 ms | B와 C가 겹친다 |
| 임계 경로 | 400 ms | A + B + D. 여기가 하한 |

그래프를 `CompletableFuture`의 사슬로 그대로 옮기면 실행 시간이 임계 경로에 닿는다. 428ms와 400ms의 차이는 B와 C 중 하나가 효율 코어에 갔거나 스레드를 넘긴 비용이다([02](../02-sequential-and-parallel-execution)장 2.1절). 코어가 열 개인데 넷 중 둘만 겹치니 나머지 여덟은 논다. 이 그래프로는 그게 최선이고, 더 빨리 가려면 그래프를 바꿔야 한다. B 안의 200ms를 다시 쪼갤 수 있는지, 곧 3절과 5절의 물음이다. 빌드 도구(Make, Gradle), 데이터 파이프라인(Airflow), `CompletableFuture`의 조합이 전부 이 그래프를 속에 만들어 "독립인 것은 동시에, 의존하는 것은 순서대로" 돌린다. 조합 API의 속은 [12](../12-asynchronous-communication)장 4.3절이다.

## 3. 작업 분해 (Task Decomposition)

```text
        [대시보드]
     ┌─────┼─────┐
     ▼     ▼     ▼
   매출   사용자   로그    서로 다른 일
   집계   통계    분석    → 동시에, MIMD
```

```java
var sales = supplyAsync(
    () -> buildSalesReport());
var users = supplyAsync(
    () -> buildUserStats());
var logs = supplyAsync(
    () -> analyzeLogs());
// 셋이 다 끝나면 합류
allOf(sales, users, logs).join();
```

| 200 ms짜리 기능 셋, 코어 열 개 | 걸린 시간 | 배속 | 왜 |
|:-----------------------|--------:|----:|:---|
| 순서대로 | 608 ms | 1.0 | 합 |
| 기능마다 스레드 하나 (작업 분해) | 229 ms | 2.7 | 기능이 셋이니 3배가 천장. 코어 일곱이 논다 |
| 기능마다 안의 데이터를 다시 20조각으로 | 99 ms | 6.1 | 조각 60개가 코어 열 개를 채운다 |

둘째 원리의 앞부분이다. 애플리케이션에 기능적으로 독립인 부분이 있으면 그것을 따로 떼어 동시에 돌린다. 매출 집계, 사용자 통계, 로그 분석은 서로 다른 일이고 서로의 결과가 필요 없다. 서로 다른 명령 흐름이 서로 다른 데이터를 다루니 [03](../03-how-computers-work)장 2절의 MIMD다. 위 표의 둘째 줄이 그 결과인데, 한계도 같이 보인다. 기능이 셋이면 병렬도가 셋에 묶여 코어 열 개 중 일곱이 논다. 셋째 줄은 각 기능 안의 데이터를 다시 20조각으로 나눈 것이고, 그제야 코어가 찬다. 작업 분해의 병렬도는 기능의 개수이고, 그 위로 가려면 5절의 데이터 분해와 겹쳐야 한다.

## 4. 파이프라인 패턴 (Pipeline)

### 4.1 단계가 겹쳐 돈다

```text
[순차] 한 항목을 끝내야 다음 항목
[읽][파스][쓰][읽][파스][쓰]...

[파이프라인] 단계가 겹쳐 돈다
읽기 │[1][2][3][4][5]
파싱 │  [1  ][2  ][3  ][4  ]  ← 병목
쓰기 │       [1][2][3][4]
처리율은 가장 느린 단계가 정한다
```

파이프라인은 작업을 단계로 나누고 데이터가 단계를 차례로 지나게 하는 작업 분해다. 핵심은 단계들이 **겹쳐서** 돈다는 것이다. 1번 항목이 파싱 단계에 있을 때 2번 항목은 읽기 단계에 들어와 있다. 세탁기와 건조기가 하나씩인 세탁소가 옷을 쉬지 않고 돌리는 것과 같다. 같은 데이터가 여러 단계를 거쳐 가니 [03](../03-how-computers-work)장 플린 분류에서 드문 MISD에 가장 가까운 모양이기도 하다.

### 4.2 처리율은 오르고 지연은 그대로

```java
var q1 = new ArrayBlockingQueue
    <Line>(4);      // 유계 큐 = 배압
var q2 = new ArrayBlockingQueue
    <Record>(4);
// 읽기: 앞에서 만들어 q1에
q1.put(read());
// 파싱: q1에서 꺼내 q2로
q2.put(parse(q1.take()));
// 쓰기: q2에서 꺼내
write(q2.take());
// 끝은 독약(poison) 항목으로 알린다
```

| 읽기 1ms → 파싱 2ms → 쓰기 1ms, 항목 300개 | 걸린 시간 | 처리율 | 항목 하나의 지연 (중앙값) | 왜 |
|:--------------------------------|--------:|------:|-------------------:|:---|
| 순차 | 1,248 ms | 240개/초 | 4 ms | 단계의 합 |
| 파이프라인, 단계마다 스레드 하나, 큐 64 | 647 ms | 464개/초 | 138 ms | 파싱 2ms가 천장(500개/초). 큐에 쌓여 기다린다 |
| 같은 파이프라인, 큐 4 | 657 ms | 457개/초 | 14 ms | 처리율은 같고 지연만 준다 |
| 파싱 스레드 둘, 큐 4 | 342 ms | 877개/초 | 5.5 ms | 병목을 나누니 천장이 1,000개/초로 |

파이프라인은 처리율을 올리지만 지연은 줄이지 못한다. 항목 하나는 여전히 모든 단계를 지나야 하니 4ms 아래로는 못 가고, 오히려 늘어난다. 첫째 파이프라인에서 항목 하나가 끝나기까지 138ms가 걸렸다. 읽기(1ms)가 파싱(2ms)보다 빨라 항목이 큐에 64개까지 쌓이고, 새 항목은 그 뒤에 줄을 선다. 큐를 4로 줄이니 처리율은 그대로인 채 지연이 14ms로 내려왔다. 처리율은 가장 느린 단계가 정한다. 파싱이 2ms면 초당 500개가 천장이고, 파싱 스레드를 둘로 나누자 877개가 됐다. 파이프라인을 설계하는 일은 병목 단계를 찾아 나누는 일이고, 그것이 3절의 작업 분해와 5절의 데이터 분해를 한 단계 안에서 겹치는 것이다.

{{< callout type="warning" >}}
**단계 사이의 큐는 반드시 유계여야 한다.** 느린 단계 앞의 큐는 무한히 자라 메모리를 잠식하고, 위 표처럼 지연을 수십 배로 키운다. 용량이 있는 큐는 느린 단계가 앞 단계를 세우는 배압(backpressure)을 공짜로 준다. [05](../05-inter-process-communication)장 4절에서 본 그 큐다. 큐 용량은 처리율에 거의 영향이 없고 지연만 정하니, 작게 시작해서 늘린다.
{{< /callout >}}

## 5. 데이터 분해 (Data Decomposition)

```text
[작업 분해]  다른 일을 나눈다
  읽기 │ 계산 │ 쓰기        (MIMD)

[데이터 분해]  같은 일을 조각마다
  데이터 ─┬─[f]─┐
         ├─[f]─┼─ 합친다   (SIMD)
         └─[f]─┘
```

| 구분 | 작업 분해 | 데이터 분해 | 왜 |
|:-----|:-------|:--------|:---|
| 나누는 것 | 기능 (다른 일) | 데이터 (같은 일) | 무엇이 여럿인가 |
| 병렬도의 천장 | 기능의 수 | 조각의 수 | 3절은 3, 아래는 400만 |
| 플린 분류 | MIMD, MISD | SIMD | [03](../03-how-computers-work)장 2절 |
| 맞는 문제 | 이질적인 기능의 조합 | 크고 균질한 데이터 | 대시보드 vs 픽셀 1억 개 |
| 패턴 | 파이프라인 | 맵, 포크/조인, 맵/리듀스 | 6절 |
| 이 PC에서 | 3배에서 정지 | 400만 원소 6.2배 | 코어 수까지 |

| 원소 400만 개에 같은 계산 (하나 0.1 µs) | 걸린 시간 | 배속 | 왜 |
|:------------------------------|--------:|----:|:---|
| 순차 루프 | 395 ms | 1.0 | 코어 하나 |
| `parallelStream` | 64 ms | 6.2 | 실효 코어 6.8개 ([02](../02-sequential-and-parallel-execution)장 4절) |

둘째 원리의 뒷부분이다. 문제에 서로 독립인 데이터 뭉치를 같은 방법으로 처리하는 단계가 있으면, 데이터를 조각으로 나눠 같은 연산을 조각마다 동시에 건다. 1억 개의 합, 픽셀마다의 필터, 로그 줄마다의 검색이 그렇다. 같은 명령이 여러 데이터에 걸리니 SIMD이고, GPU와 `parallelStream`이 이 모델이다. 작업 분해와 다른 점은 천장이다. 기능은 셋이지만 원소는 400만이라, 병렬도가 조각 수가 아니라 코어 수에서 멈춘다. 그래서 실무는 둘을 겹친다. 기능으로 크게 나누고(3절), 기능 안의 데이터를 다시 나누고(이 절), 흐름이 있으면 단계로 잇는다(4절).

## 6. 데이터 분해 패턴: 맵 · 포크/조인 · 맵/리듀스

### 6.1 맵 (Map)

```java
var thumbs = images.parallelStream()
    .map(img -> resize(img, 128))
    .toList();
```

조각마다 같은 함수를 독립적으로 걸어 같은 개수의 결과를 만든다. 조각 사이에 아무 관계가 없어 가장 단순하고, 5절의 6.2배가 이 패턴이다. 조건은 함수가 순수해야 한다는 것뿐이다. 공유 상태를 건드리면 [04](../04-concurrency-ingredients)장 6절의 문제가 조각 수만큼 생긴다.

### 6.2 포크/조인 (Fork/Join)

```text
        [0 .. 400만]
       fork ↙    ↘
   [0..200만]  [200만..400만]
    ↙    ↘       ↙     ↘
  ...   ...    ...    ...  1만 이하면
    ↘    ↙       ↘     ↙   직접 더한다
    join          join
        ↘        ↙
         join → 합
```

```java
class Sum
        extends RecursiveTask<Double> {
    static final int CUTOFF = 10_000;
    protected Double compute() {
        if (hi - lo <= CUTOFF)
            return sumDirectly();
        int mid = (lo + hi) >>> 1;
        var left = new Sum(lo, mid);
        left.fork();     // 풀에 맡긴다
        var right = new Sum(mid, hi);
        return right.compute()
            + left.join();
    }
}
```

| 비용이 고르지 않은 원소 400만 개 (뒤로 갈수록 무겁다) | 걸린 시간 | 왜 |
|:--------------------------------------|--------:|:---|
| 순차 | 401 ms | |
| 스레드 10개에 똑같이 10조각 | 93 ms | 조각별 7~88 ms. 가장 무거운 조각이 끝을 정한다 |
| 포크/조인, 1만 개 이하면 직접 (1,023 조각) | 71 ms | 한가한 워커가 남의 조각을 가져간다 |

문제를 재귀적으로 반씩 쪼개다(fork) 충분히 작아지면 직접 계산하고, 결과를 거꾸로 합치는(join) 분할 정복이다. 반으로 쪼갠 왼쪽은 풀에 맡기고 오른쪽은 내가 계산하니 스레드가 놀지 않는다. 자바의 `ForkJoinPool`에는 여기에 작업 훔치기(work stealing)가 붙어 있다. 자기 큐가 빈 워커가 바쁜 워커의 큐에서 조각을 가져간다. 위 표가 그 효과다. 원소의 비용이 뒤로 갈수록 무거운 데이터를 10조각으로 똑같이 나누면 첫 조각은 7ms, 마지막 조각은 88ms라 스레드 아홉이 마지막 하나를 기다린다. 포크/조인으로 1,023조각을 내니 워커들이 무거운 조각을 나눠 들어 71ms다. 실제로 워커마다 처리한 원소 수를 세어 보니 9만 개에서 117만 개까지 달랐다. 원소 수가 아니라 **시간**을 고르게 나눈 것이다. 자바 쪽의 쓰임은 [자바 기초 13](../../java/basics/13-thread)장 7.4절, 훔치기의 속은 [자바 동시성 05](../../java/concurrency/05-building-blocks)장 3.5절이다.

### 6.3 맵/리듀스 (MapReduce)

```java
long revenue = orders.parallelStream()
    .map(Order::amount)        // 맵
    .reduce(0L, Long::sum);    // 리듀스
```

| 결합 함수 | 순차 | 병렬 | 왜 |
|:-------|-----:|-----:|:---|
| `(x, y) -> x - y`, 1..100만 | -500,000,500,000 | 0 | 조각 안에서 뺀 것을 조각끼리 다시 빼니 부호가 뒤집힌다 |
| `(x, y) -> 2x + y`, 1..20 | 2,097,130 | 738 | 순서에 따라 값이 다르다 |
| `Long::sum` | 500,000,500,000 | 500,000,500,000 | 어떤 순서로 더해도 같다 |
| `double` 합 100만 개 (정답 399999.7) | 399999.7000002603 | 399999.7000000001 | 부동소수점은 결합법칙이 근사. 마지막 자리가 다르다 |

맵으로 조각을 독립 변환한 뒤 리듀스로 결과를 하나로 접는다. 하둡과 스파크의 토대이고, 자바 스트림의 `map`과 `reduce`가 같은 모양이다. 병렬로 접으려면 조각 안에서 접은 것들을 조각끼리 다시 접어야 하고, 그러려면 접는 순서가 달라도 답이 같아야 한다. 결합법칙이다. 위 표가 그것을 어긴 결과다. 뺄셈은 결합법칙이 없어서 병렬로 접으면 0이 나왔고, 돌릴 때마다 같은 0이 나오니 테스트로는 잡기 어렵다. 실수의 덧셈은 결합법칙을 근사로만 만족해서 마지막 자리가 흔들린다. 돈이라면 정수로, 과학 계산이라면 오차를 감안하고 접는다.

{{< callout type="warning" >}}
**병렬 리듀스의 조건은 둘이다.** 결합 함수가 결합법칙을 만족해야 하고, 항등원이 진짜 항등원이어야 한다. 뺄셈, 나눗셈, 문자열 이어 붙이기(순서가 뜻이다)는 안 된다. 그리고 맵 함수는 부수 효과가 없어야 한다. 조각이 어느 스레드에서 어떤 순서로 돌지 모르기 때문이다. 이 두 조건이 맞으면 나머지는 프레임워크가 하고, 안 맞으면 위 표처럼 조용히 틀린다.
{{< /callout >}}

| 패턴 | 하는 일 | 합치기 | 자바에서 | 왜 이 패턴인가 |
|:-----|:------|:-----|:-------|:-----------|
| 맵 | 조각마다 같은 변환 | 없음. 결과 수가 같다 | `parallelStream().map` | 가장 단순. 조각이 서로 모른다 |
| 포크/조인 | 반씩 쪼개 직접 계산 | 거꾸로 올라오며 | `ForkJoinPool`, `Arrays.parallelSort` | 훔치기로 부하를 맞춘다 |
| 맵/리듀스 | 맵 뒤 하나로 접기 | 결합법칙 있는 함수로 | `reduce`, 하둡, 스파크 | 기계 수천 대로 늘어난다 |

## 7. 입도 (Granularity)

```text
굵게  ██████  ██████  ██████   조각 3개
      코어 10개 중 7개가 논다

잘게  ▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪▪  조각 100만 개
      조각마다 만들고 합치는 비용

적정  ████ ████ ████ ████ ... 1,023개
      코어를 다 채우고 비용은 작다
```

| 포크/조인 임계값 (이 이하면 직접) | 조각 수 | 걸린 시간 | 배속 | 왜 |
|:----------------------|-------:|--------:|----:|:---|
| 4,000,000 (안 나눔) | 1 | 396 ms | 1.0 | 코어 하나 |
| 1,000,000 | 7 | 102 ms | 3.9 | 조각 넷이 코어 열 개를 못 채운다 |
| 100,000 | 127 | 57 ms | 6.9 | |
| 10,000 | 1,023 | 53 ms | 7.5 | 여기가 바닥 |
| 1,000 | 8,191 | 54 ms | 7.3 | |
| 100 | 131,071 | 57 ms | 6.9 | 조각을 만들고 합치는 비용이 보인다 |
| 10 | 1,048,575 | 77 ms | 5.1 | 조각 100만 개. 일보다 관리 |

셋째 원리다. 입도는 분해된 조각의 수와 크기다. 조각이 적고 크면 굵은 입도, 많고 작으면 잔 입도다. 위 표가 같은 400만 원소의 합을 임계값만 바꿔 가며 잰 것이다. 안 나누면 코어 하나이고, 7조각이면 코어 열 개 중 넷만 일해서 3.9배, 1,023조각에서 7.5배로 바닥에 닿고, 100만 조각이 되면 조각 하나가 4개 원소라 만들고 합치는 비용이 일을 넘어 5.1배로 도로 떨어진다. 6.2절의 부하 불균형은 굵은 쪽의 실패이고, 이 표의 마지막 줄은 잔 쪽의 실패다. [02](../02-sequential-and-parallel-execution)장 2.3절에서 1,000개짜리 배열 합이 병렬이 열 배 느렸던 것도 같은 줄이다.

| 입도 | 조각 | 좋은 점 | 나쁜 점 | 이 PC에서 |
|:-----|:----|:------|:------|:--------|
| 굵다 | 적고 크다 | 만들고 합치는 비용이 작다 | 코어가 놀고, 무거운 조각이 끝을 정한다 | 7조각 3.9배, 10조각 88 ms |
| 잘다 | 많고 작다 | 부하가 고르다 | 조각마다 비용 | 100만 조각 5.1배 |
| 적정 | 코어보다 넉넉히, 비용보다 크게 | 둘 다 | | 127~8,191조각, 7.3~7.5배 |

{{< callout type="info" >}}
**조각 수는 코어 수보다 넉넉하게, 조각 하나는 만드는 비용보다 훨씬 크게.** 코어 수만큼 딱 맞추면 조각 하나가 늦는 순간 나머지가 논다. 몇 배 넉넉하면 런타임이 늦는 조각을 나눠 들 여지가 생기고, 포크/조인의 훔치기가 그 여지를 쓴다. 상한은 조각 하나의 일이 조각을 만들고 합치는 비용(수 µs)보다 충분히 커야 한다는 것이다. 위 표에서 그 범위가 100배쯤(127~8,191조각) 넓으니 정확히 맞출 필요는 없고, 양 끝만 피하면 된다. 포크/조인의 임계값이 이 손잡이다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 분해 | 문제를 동시에 돌 수 있는 조각으로 | 동시성의 첫 단추. 공식은 없다 |
| 의존 관계 그래프 | 화살표 없는 것만 동시에 | B와 C가 겹쳐 561 → 428 ms |
| 임계 경로 | 가장 긴 사슬이 하한 | 400 ms. 코어를 더 줘도 못 넘는다 |
| 작업 분해 | 다른 일을 나눈다 (MIMD) | 천장은 기능 수. 셋이면 3배 |
| 파이프라인 | 단계를 겹친다 | 처리율은 병목 단계, 지연은 그대로 이상 |
| 유계 큐 | 배압 | 큐 64는 지연 138 ms, 큐 4는 14 ms |
| 데이터 분해 | 같은 일을 조각마다 (SIMD) | 천장은 코어 수. 6.2배 |
| 겹쳐 쓰기 | 기능으로, 그 안을 데이터로 | 2.7배 → 6.1배 |
| 맵 | 조각마다 순수 함수 | 가장 단순 |
| 포크/조인 | 반씩 쪼개고 훔친다 | 불균형 88 ms → 71 ms |
| 맵/리듀스 | 결합법칙 있는 함수로 접기 | 뺄셈은 0, 실수는 마지막 자리 |
| 입도 | 코어보다 넉넉히, 비용보다 크게 | 7조각 3.9배, 1,023조각 7.5배, 100만 조각 5.1배 |

{{< callout type="info" >}}
**용어 정리**
- **분해(decomposition)**: 문제를 동시에 실행할 수 있는 작업으로 나누는 것
- **작업 의존 관계 그래프**: 작업이 노드, "먼저 끝나야"가 화살표인 DAG
- **임계 경로**: 그래프에서 가장 긴 의존 사슬. 실행 시간의 하한
- **작업 분해**: 서로 다른 기능을 나누는 것. MIMD
- **데이터 분해**: 같은 일을 데이터 조각마다 거는 것. SIMD
- **파이프라인**: 단계로 나눠 겹쳐 돌리는 것. 처리율은 오르고 지연은 안 준다
- **병목 단계**: 파이프라인에서 가장 느린 단계. 전체 처리율을 정한다
- **배압**: 느린 단계가 앞 단계를 세우는 것. 유계 큐가 준다
- **맵 / 포크·조인 / 맵·리듀스**: 조각마다 변환 / 반씩 쪼개 합침 / 변환 뒤 하나로 접기
- **작업 훔치기**: 한가한 워커가 바쁜 워커의 조각을 가져가는 것
- **결합법칙**: (a∘b)∘c = a∘(b∘c). 병렬 리듀스의 조건
- **입도**: 조각의 수와 크기. 굵으면 불균형, 잘면 오버헤드
- **임계값(cutoff)**: 포크/조인에서 더 안 쪼개는 크기. 입도의 손잡이
