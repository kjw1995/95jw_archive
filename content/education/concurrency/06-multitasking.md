코어 하나는 한 순간에 명령 하나만 실행한다. 그런데도 음악을 들으며 브라우저를 켜고 파일을 내려받는다. 이 장은 그 착각을 만드는 장치의 이야기다. 원리는 셋이다. 첫째, **멀티태스킹은 하드웨어가 아니라 런타임의 기능이고, 파는 것은 착각이다.** 코어는 하나만 돌리지만 10ms마다 바꿔 태우면 셋이 동시에 도는 것으로 보인다. 착각의 값이 전환이고, 전환의 값은 저장하고 복원하는 1.5µs보다 그 뒤에 오는 것, 곧 식은 캐시와 코어보다 많은 스레드가 차례를 기다리는 시간이다. 둘째, **전환을 누가 결정하느냐가 두 세계를 가른다.** 선점형은 스케줄러가 시계를 보고 뺏는다. 독점이 불가능한 대신 아무 데서나 잘린다. 협력형은 작업이 스스로 내놓을 때만 바뀐다. 싸고 잘리는 자리가 분명한 대신 하나가 안 내놓으면 전부 멈춘다. 현대 운영체제는 선점형이고, 현대 런타임의 코루틴과 가상 스레드는 그 위에 협력형을 다시 얹은 것이다. 셋째, **스케줄러는 CPU 바운드와 I/O 바운드를 갈라 대한다.** 잠에서 깬 스레드는 코어가 전부 바빠도 곧바로 코어를 받고, 계산하는 스레드는 시간이 되면 잘린다. 앞 장들에서 "계산은 코어 수만큼, 기다림은 많아도 된다"고 했던 규칙이 성립하는 이유가 이 편애다. 이 PC(Apple M4 10코어, macOS, JDK 23)에서 계산만 하는 스레드가 몇 ms마다 잘리는지 재고, 우선순위가 정말 통하는지 보고, 코어 열 개가 전부 바쁠 때 잠에서 깬 스레드가 얼마나 늦게 코어를 받는지 재고, 전환 뒤 식은 캐시의 값을 재고, 양보하지 않는 가상 스레드 하나가 다른 일을 얼마나 세우는지 봤다.

## 1. 멀티태스킹이란

```text
코어 하나, 시간 →
│T1│T2│T3│T1│T2│T3│T1│  10 ms마다 교대
사용자: 셋이 동시에 돈다
실제:   한 순간엔 하나

코어 둘
코어0 │T1 T1 T1 T1│  진짜 동시 (병렬)
코어1 │T2 T2 T2 T2│
```

| 구분 | 멀티태스킹 | 병렬성 | 왜 갈라 보나 |
|:-----|:--------|:-----|:-----------|
| 어디서 | 런타임(운영체제)의 소프트웨어 | 하드웨어의 코어 여럿 | 코어 하나에도 멀티태스킹은 있다 |
| 한 순간에 | 하나 | 코어 수만큼 | 착각 vs 실제 |
| 얻는 것 | 응답성, 기다리는 시간의 활용 | 처리 속도 | [02](../02-sequential-and-parallel-execution)장 3절 |
| 이 PC에서 | 스레드 40개가 코어 10개에서 전부 진행 | 10개까지만 같은 순간 | 둘이 겹쳐 있다 |

멀티태스킹은 일정 시간 동안 여러 작업을 교차 실행하는 것이다. 하드웨어에는 없는 개념이다. 코어는 한 순간에 스레드 하나를 돌릴 뿐이고, 운영체제가 그 스레드를 몇 ms마다 바꿔 태워서 여럿이 동시에 도는 착각을 만든다. 이 PC에서 계산만 하는 스레드 40개를 코어 10개에 올리니 40개 전부가 진행했다. 각 스레드는 3.8ms쯤 돌고 10ms쯤 밀려나기를 반복했고(5절), 그 반복이 빠르니 사람 눈에는 40개가 함께 도는 것으로 보인다. 멀티코어에서는 두 층이 겹친다. 코어마다 병렬로 돌면서, 각 코어가 다시 멀티태스킹으로 여럿을 교대시킨다. [01](../01-what-is-concurrency)장의 정의로 돌아가면, 멀티태스킹은 동시성을 코어 하나 위에 구현하는 방법이다.

## 2. 작업의 두 유형: CPU 바운드 vs I/O 바운드

```text
CPU 바운드  ████████████████  계속 계산
I/O 바운드  ██····██····██··  대개 대기
            ↑계산 ↑응답을 기다린다
```

```java
// CPU 바운드: 코어를 계속 쓴다
static boolean isPrime(int n) {
    for (long i = 2; i * i <= n; i++)
        if (n % i == 0) return false;
    return true;
}
// I/O 바운드: send() 안에서 잔다
var res = client.send(req,
    BodyHandlers.ofString());
```

| 구분 | CPU 바운드 | I/O 바운드 | 왜 |
|:-----|:---------|:---------|:---|
| 병목 | 코어의 계산 능력 | 디스크, 네트워크, 상대 서버 | 무엇을 기다리는가 |
| 코어 점유 | 계속 | 잠깐 쓰고 잔다 | 응답이 올 때까지 할 일이 없다 |
| 스레드를 늘리면 | 코어 수까지만 | 대기하는 만큼 계속 | [01](../01-what-is-concurrency)장 3.2절: 7.2배에서 정지 vs 917개/초 |
| 스케줄러가 보기에 | 타임 슬라이스를 다 쓴다 | 슬라이스가 끝나기 전에 스스로 잔다 | 5.4절의 편애 기준 |
| 예 | 암호화, 인코딩, 행렬, 압축 | DB 조회, API 호출, 파일 읽기 | |

| 10코어를 꽉 채운 계산 스레드 10개 옆에 | 계산 스레드의 일 | 자는 스레드 | 왜 |
|:-----------------------------|-------------:|:---------|:---|
| 아무것도 없음 | 2,597,266 단위 | | 기준 |
| 1ms마다 깨는 스레드 100개 | 2,541,629 단위 (−2%) | 2초에 128,662번 깼다 | 깬 스레드는 잠깐 쓰고 바로 잔다 |

프로그램의 병목이 계산이면 CPU 바운드, 기다림이면 I/O 바운드다. 이 구분이 이 장의 출발점인 이유는 두 유형이 코어를 쓰는 모양이 달라서다. 계산 스레드는 코어를 주면 계속 쓴다. I/O 스레드는 코어를 잠깐 쓰고 응답을 기다리며 잔다. 멀티태스킹은 이 잠든 시간을 다른 스레드로 채우는 것이고, 위 표가 그 실물이다. 코어 열 개를 계산 스레드 열 개가 꽉 채운 상태에서 1ms마다 깨는 스레드 100개를 얹었더니, 자는 스레드들은 2초에 12만 번 넘게 코어를 받았는데 계산 스레드들은 2%만 잃었다. 잠깐 쓰고 바로 자니 자리를 거의 안 뺏는다. 반대로 계산 스레드를 코어보다 많이 두면 서로 자리를 뺏을 뿐이고, 그 값은 3절에 있다. 스레드 풀 크기 공식이 두 유형에서 갈렸던 것([05](../05-inter-process-communication)장 7.2절)이 이 표의 결론이다.

## 3. 컨텍스트 스위칭

### 3.1 무엇을 저장하나

```text
A 실행 중
  │ 타이머 인터럽트, 또는 A가 잔다
  ▼
A의 PC·레지스터·SP 저장 → TCB
  │
  ▼
스케줄러가 B를 고른다
  │
  ▼
B의 TCB → PC·레지스터·SP 복원
  │
  ▼
B 실행. A의 캐시 라인은 식어 간다
```

| 저장하는 것 | 뜻 | 왜 |
|:---------|:---|:---|
| 프로그램 카운터 | 다음에 실행할 명령의 주소 | 어디까지 했는지 |
| 레지스터 | 계산 중이던 값 | 계산 도중이었으니까 |
| 스택 포인터 | 호출 스택의 현재 위치 | 어느 함수 안이었는지 |
| 메모리 맵 | 주소 공간 (프로세스가 바뀔 때만) | 스레드끼리는 같다 |

컨텍스트 스위칭은 한 작업의 상태를 나중에 재개할 수 있게 저장하고 다른 작업의 상태로 바꾸는 행위다. 운영체제가 하고, 멀티태스킹의 심장이다. 저장하는 것은 위 표의 넉 줄이고, 스레드 하나의 제어 블록(TCB)에 들어간다. 이 전환 자체는 아무 일도 하지 않는 순수한 비용이다. [04](../04-concurrency-ingredients)장 4절에서 그 직접 비용을 쟀다. 스레드 둘이 서로를 깨우며 바통을 넘기는 왕복이 3.1µs, 전환 하나에 1.5µs다.

### 3.2 직접 비용과 간접 비용

| 비용 | 뜻 | 이 PC에서 | 왜 |
|:-----|:---|:--------|:---|
| 직접 | 저장하고 복원하는 시간 | 전환 하나 1.5 µs | 레지스터 수십 개와 커널 진입 |
| 간접: 순차 접근 | 다른 스레드가 돈 뒤 내 데이터가 캐시에 없다 | 4MB 훑기 131 µs → 134~143 µs | 프리페처가 순차 읽기는 가려 준다 |
| 간접: 무작위 접근 | 같은 상황, 캐시 미스마다 기다린다 | 2MB 무작위 걷기 2,728 µs → 3,110~3,230 µs (+15%) | 재개된 코어의 L1이 비어 있다 |
| 기다림 | 코어보다 많으면 차례를 기다린다 | 스레드 40개: 3.8ms 돌고 10.3ms 대기 | 5절 |

전환의 진짜 값은 저장과 복원이 아니다. 전환 뒤에 온다. 내가 코어에서 내려간 사이 다른 스레드가 그 코어의 캐시를 자기 데이터로 채우고, 내가 다시 올라오면(대개 다른 코어에) 내 데이터를 메모리에서 다시 읽어야 한다. 이 PC에서 스레드 A가 자기 데이터를 훑는 시간을 재며 사이사이에 다른 스레드로 전환했다. 순차로 훑는 4MB는 거의 안 느려졌다. 하드웨어 프리페처가 다음 줄을 미리 가져오니 캐시가 식어도 티가 안 난다. 무작위로 걷는 2MB는 15% 느려졌다. 다음 주소를 예측할 수 없으니 미스마다 기다린다. 이 간접 비용은 접근 패턴에 달려 있고, 해시 테이블과 트리와 객체 그래프를 걷는 보통의 프로그램은 뒤쪽에 가깝다. 그리고 넷째 줄이 가장 크다. 전환이 잦다는 것은 코어보다 스레드가 많다는 뜻이고, 그러면 스레드는 전환보다 훨씬 긴 시간을 기다리며 보낸다.

### 3.3 프로세스 전환과 스레드 전환

| 비교 | 스레드 ↔ 스레드 | 프로세스 ↔ 프로세스 | 이 PC에서 | 왜 |
|:-----|:-------------|:----------------|:--------|:---|
| 저장하는 것 | 레지스터, PC, SP | + 메모리 맵 | | 주소 공간이 바뀐다 |
| TLB | 그대로 | 비운다 | | 다른 주소 공간의 변환은 못 쓴다 |
| 캐시 | 식는다 | 식는다, 더 많이 | | 코드와 데이터가 전부 남이다 |
| 바통 넘기기 왕복 | 3.1 µs (`park`/`unpark`) | 5.4 µs (파이프) | [04](../04-concurrency-ingredients)장, [05](../05-inter-process-communication)장 | 파이프는 커널 복사도 포함 |

같은 프로세스의 스레드끼리는 주소 공간이 같아서 메모리 맵을 갈아 끼울 일도, 주소 변환 캐시(TLB)를 비울 일도 없다. 프로세스가 바뀌면 둘 다 해야 하고, 그 뒤에 오는 간접 비용도 크다. 코드도 데이터도 전부 남의 것이라 캐시에 남은 것이 하나도 쓸모없다. 스레드 전환이 프로세스 전환보다 싼 이유이고, 6절에서 멀티태스킹의 단위로 스레드를 고르는 이유다.

{{< callout type="warning" >}}
**스레드가 코어보다 많으면 일보다 전환이 늘어난다.** 이 PC에서 같은 계산을 스레드 4,000개로 나누면 10개로 나눌 때보다 35% 느렸고([04](../04-concurrency-ingredients)장 4.2절), 40개만 되어도 각 스레드가 도는 시간보다 기다리는 시간이 길었다(5절). 극단으로 가면 전환만 하고 진척은 없는 스래싱이 된다. 계산 스레드의 수는 코어 수가 상한이고, 그 위로는 어느 하나도 빨라지지 않는다.
{{< /callout >}}

## 4. 멀티태스킹의 두 방식: 협력형 vs 선점형

```text
[협력형]  작업이 내놓을 때만
T1 ██████[yield] T2 ████[yield] T1 ██
  양보하지 않으면 T2는 영원히 못 돈다

[선점형]  시계가 뺏는다
T1 ███│T2 ███│T1 ███│T2 ███│ (│=10 ms)
  독점은 없다. 대신 아무 데서나 잘린다
```

### 4.1 협력형: 양보하는 순간에만

```java
// 캐리어 하나 위의 가상 스레드 둘
Thread.ofVirtual().start(() -> {
    while (busy()) {    // 1초 계산
        // Thread.yield() 가 없다
    }
});
Thread.ofVirtual().start(
    () -> mark());  // 1,003 ms 뒤 시작
```

| 캐리어(OS 스레드) 하나 위에서 | 두 번째 작업이 시작되기까지 | 왜 |
|:----------------------|-------------------:|:---|
| 가상 스레드가 1초를 계산, 양보 없음 | 1,003 ms | 첫째가 안 내놓으니 둘째는 못 탄다 |
| 같은 계산, 루프마다 `Thread.yield()` | 6 ms | 양보 지점에서 교대한다 |
| 플랫폼 스레드 40개가 계산 중 (선점형, 코어 10) | 0.57 ms | 시계가 자리를 만든다 |

둘째 원리다. 협력형 멀티태스킹에서는 작업이 스스로 제어권을 내놓을 때만 전환이 일어난다. 전환 지점이 코드에 보이니 동기화가 단순하고 전환이 싸다. 대신 약점이 치명적이다. 하나가 안 내놓으면 전부 멈춘다. 이 PC에서 자바의 가상 스레드를 캐리어 하나 위에 둘 띄웠다. 가상 스레드는 블로킹 지점에서만 캐리어를 내놓는 협력형이다. 첫째가 양보 없이 1초를 계산하니 둘째는 1,003ms 뒤에야 시작됐다. 루프에 `yield`를 넣으니 6ms다. 윈도우 3.x와 옛 맥 OS가 이 방식이었고 프로그램 하나가 멈추면 컴퓨터가 멈췄다. 그 방식이 코루틴, `async`/`await`, 이벤트 루프, 가상 스레드라는 이름으로 돌아왔다. `await`가 곧 양보 지점이다.

### 4.2 선점형: 시계가 뺏는다

| 구분 | 협력형 | 선점형 | 왜 |
|:-----|:-----|:-----|:---|
| 전환을 정하는 것 | 작업 | 스케줄러의 타이머 | 누가 시계를 보나 |
| 전환 지점 | `yield`, `await`, 블로킹 | 슬라이스 만료, 인터럽트 | 코드에 보이나 |
| 독점 | 가능. 하나가 전부를 세운다 | 불가능 | 1,003 ms vs 0.57 ms |
| 동기화 | 양보 지점 사이는 안전 | 아무 데서나 잘리니 전부 지켜야 | [04](../04-concurrency-ingredients)장 6절 |
| 전환 비용 | 낮다. 레지스터 몇 개 | 커널 진입 1.5 µs와 캐시 | 3절 |
| 실물 | 코루틴, 이벤트 루프, 가상 스레드 | 리눅스, 윈도우, macOS의 스레드 | 층이 다르다 |

선점형에서는 스케줄러가 타이머 인터럽트로 정해진 시간마다 작업을 강제로 내리고 다른 작업을 올린다. 위 표의 셋째 줄이 실물이다. 계산 스레드 40개가 코어 10개를 전부 차지한 상태에서 새 스레드를 띄우니 0.57ms 만에 돌기 시작했다. 아무도 양보하지 않았는데 시계가 자리를 만들었다. 대가는 "아무 데서나 잘린다"는 것이다. `count++`의 읽기와 쓰기 사이에서도 잘리고, 그래서 [04](../04-concurrency-ingredients)장 6절의 세 문제가 생긴다. 현대 운영체제는 전부 선점형이고, 그 위에 협력형 런타임이 얹힌다. 가상 스레드 실험에서 캐리어 하나가 1초를 독점하는 동안에도 운영체제는 그 캐리어를 다른 프로세스와 교대시키고 있었다.

{{< callout type="info" >}}
**협력형이 돌아온 이유는 값이다.** 연결 수십만 개를 다루는 서버가 연결마다 OS 스레드를 두면 [04](../04-concurrency-ingredients)장의 천장 4,096개와 3절의 전환 비용에 부딪힌다. 코루틴과 가상 스레드는 OS 스레드 몇 개 위에서 수만 개의 논리 작업을 협력적으로 교대시켜 그 값을 피한다. 조건은 하나다. 작업이 양보 지점(블로킹 I/O)을 자주 지나야 한다. 계산만 하는 작업을 가상 스레드에 올리면 위 표의 첫 줄이 된다. 어떻게 얹히는지는 [12](../12-asynchronous-communication)장 2절이다.
{{< /callout >}}

## 5. 스케줄러

### 5.1 어떤 작업을 언제 얼마나

```text
        스케줄러가 고른다
 ┌──────┐ ─────────▶ ┌──────┐
 │ 준비 │            │ 실행 │
 └──────┘ ◀───────── └──┬───┘
    ▲     타임 슬라이스 │ I/O 요청
    │     만료 (선점)   ▼
    │  I/O 완료     ┌──────┐
    └───────────────│ 대기 │
                    └──────┘
```

| 상태 | 뜻 | 이 상태로 가는 길 | 왜 |
|:-----|:---|:-------------|:---|
| 준비 | 코어만 주면 돈다 | 슬라이스 만료, I/O 완료, 새로 시작 | 코어보다 스레드가 많다 |
| 실행 | 코어 위에 있다 | 스케줄러가 골랐다 | 코어당 하나 |
| 대기 | 코어를 줘도 못 돈다 | I/O 요청, 락, `sleep` | 기다리는 것이 있다 |

스케줄러는 준비된 작업 중 하나를 골라 코어에 올리고, 슬라이스가 끝나거나 작업이 대기로 빠지면 다음 것을 고르는 운영체제의 부품이다. [04](../04-concurrency-ingredients)장 5절의 여섯 상태를 운영체제 쪽에서 보면 위의 셋이다. 자바의 `RUNNABLE`이 준비와 실행 둘 다인 이유가 여기 있다. 어느 쪽인지는 스케줄러만 안다.

### 5.2 타임 슬라이스

```java
// 스레드마다 시각을 계속 읽는다
long now = System.nanoTime();
if (now - last > 200_000) {
    // 0.2ms 넘게 못 읽었다 = 밀려났다
    runs.add(last - runStart);
    gaps.add(now - last);
    runStart = now;
}
last = now;
```

| 계산 스레드 | 코어당 | 2초 동안 잘린 횟수 | 연속 실행 (중앙값 / p90) | 밀려난 시간 (중앙값 / p90) | 왜 |
|---------:|-----:|--------------:|------------------:|-------------------:|:---|
| 10 | 1.0 | 710 | 12.3 / 73 ms | 0.4 / 1.6 ms | 자리가 있다. 잘려도 곧 돌아온다 |
| 11 | 1.1 | 1,872 | 10.0 / 20.4 ms | 0.9 / 3.3 ms | 하나가 남아 돌아가며 밀린다 |
| 20 | 2.0 | 2,741 | 7.3 / 11.1 ms | 6.7 / 15.1 ms | 절반은 항상 기다린다 |
| 40 | 4.0 | 4,308 | 3.8 / 10.1 ms | 10.3 / 31.9 ms | 도는 시간보다 기다리는 시간이 길다 |

스레드가 코어에 올라 강제로 내려오기까지의 길이가 타임 슬라이스다. 이 PC에서 계산만 하는 스레드들에게 시각을 계속 읽게 하고, 0.2ms 넘게 못 읽은 구간을 "밀려난 시간"으로 잡았다. 코어보다 스레드가 많아지면 연속 실행이 10ms 근처에서 잘리고, p90이 10~11ms에 모인다. 이 PC의 슬라이스는 10ms쯤이다. 슬라이스가 짧으면 전환이 잦아 3절의 비용이 커지고, 길면 새 작업이 오래 기다려 응답성이 떨어진다. 10ms는 그 사이의 타협이다. 표의 마지막 열이 3절 넷째 줄의 출처다. 스레드 40개면 각 스레드는 3.8ms 돌고 10.3ms를 기다린다. 일보다 대기가 길다.

| 우선순위 | 2초 동안 한 일 | 왜 |
|:-------|------------:|:---|
| `MIN_PRIORITY` 스레드 10개 | 24,850,116 | |
| `MAX_PRIORITY` 스레드 10개 | 25,184,098 (1.01배) | 자바의 우선순위는 힌트이고, 이 PC의 JVM은 운영체제에 전달하지 않는다 |

스레드 20개 중 절반에 최저, 절반에 최고 우선순위를 주고 같은 계산을 시켰더니 한 일의 양이 1%밖에 차이 나지 않았다. 자바의 `setPriority`는 힌트일 뿐이고 이 PC의 JVM 기본 설정은 그것을 운영체제 스케줄러에 넘기지 않는다. 우선순위로 응답성을 설계하면 안 되는 이유다.

### 5.3 스케줄링 알고리즘

| 알고리즘 | 고르는 법 | 좋은 점 | 나쁜 점 | 왜 |
|:-------|:-------|:------|:------|:---|
| FCFS | 먼저 온 것 먼저 | 단순 | 긴 작업 뒤에 전부 줄 선다 | 선점이 없다 |
| 라운드 로빈 | 슬라이스씩 돌아가며 | 공정, 응답성 | 슬라이스 길이가 전부 | 5.2절 |
| 우선순위 | 높은 것 먼저 | 급한 일을 먼저 | 낮은 것이 굶는다 | [09](../09-deadlock-and-starvation)장 4절 |
| 다단계 피드백 큐 | 행동을 보고 급을 바꾼다 | I/O 바운드를 우대 | 복잡 | 5.4절. 실제 운영체제의 선택 |

### 5.4 스케줄러는 I/O 바운드를 편애한다

```java
long t0 = System.nanoTime();
Thread.sleep(1);
long late = System.nanoTime() - t0
    - 1_000_000;   // 늦게 깬 시간
```

| `sleep(1ms)`에서 깨어난 스레드가 코어를 받기까지 | 중앙값 | p99 | 최대 | 왜 |
|:-------------------------------------|-----:|-----:|-----:|:---|
| 계산 스레드 0개 | 0.26 ms | 0.29 ms | 0.33 ms | 타이머 자체의 여유 |
| 계산 스레드 10개 (코어 전부 바쁨) | 0.26 ms | 3.8 ms | 5.7 ms | 대개는 바로, 가끔 슬라이스를 기다린다 |
| 계산 스레드 20개 | 0.26 ms | 0.31 ms | 3.9 ms | |
| 계산 스레드 40개 | 0.26 ms | 0.35 ms | 1.2 ms | 코어당 넷이 줄 서 있어도 깬 스레드가 먼저다 |

셋째 원리다. 코어 열 개를 계산 스레드 40개가 나눠 쓰는 상태, 곧 계산 스레드 하나가 10ms를 기다리는 상태에서 잠에서 깬 스레드는 0.26ms 만에 코어를 받았다. 계산 스레드가 하나도 없을 때와 같다. 스케줄러가 줄의 맨 앞에 세운 것이다. 이유는 2절의 표에 있다. I/O 바운드 스레드는 코어를 잠깐 쓰고 바로 다시 잔다. 먼저 돌려 I/O 요청을 던지게 하면 그 응답을 기다리는 동안 계산 스레드가 코어를 채우고, 결과적으로 코어와 디스크와 네트워크가 동시에 바쁘다. 다단계 피드백 큐가 이것을 한다. 슬라이스를 다 쓰고 잘린 스레드는 급을 낮추고, 슬라이스가 끝나기 전에 스스로 잔 스레드는 급을 올린다. 리눅스의 CFS와 macOS의 스케줄러가 같은 휴리스틱을 쓴다. 우선순위를 내가 정하지 않아도 스케줄러가 행동을 보고 정한다.

## 6. 프로세스 vs 스레드로 멀티태스킹

```text
프로세스 여럿        스레드 여럿
┌──────┐┌──────┐    ┌────────────────┐
│ 주소 ││ 주소 │    │ 주소 공간 하나 │
│ 공간 ││ 공간 │    │ ┌──┐┌──┐┌──┐   │
│  T   ││  T   │    │ │T1││T2││T3│   │
└──────┘└──────┘    │ └──┘└──┘└──┘   │
격리 ↑ 비용 ↑       └────────────────┘
                     공유 ↑ 비용 ↓
```

| 비교 | 다중 프로세스 | 단일 프로세스, 다중 스레드 | 이 PC에서 | 왜 |
|:-----|:----------|:------------------|:--------|:---|
| 메모리 | 주소 공간이 각자 | 하나를 공유 | 스레드 하나 88 KB | 중복이 없다 |
| 만드는 비용 | 크다 | 작다 | 1.8 ms vs 26 µs | 주소 공간 vs 스택 |
| 전환 비용 | 메모리 맵과 TLB까지 | 레지스터만 | 왕복 5.4 vs 3.1 µs | 3.3절 |
| 데이터 공유 | IPC | 같은 힙 | 4.7 µs vs 72 ns | [05](../05-inter-process-communication)장 |
| 격리 | 하나가 죽어도 나머지는 산다 | 하나가 전부를 죽일 수 있다 | 종료 코드 139 vs 같은 힙 | [04](../04-concurrency-ingredients)장 3절 |

멀티태스킹의 단위는 프로세스일 수도 스레드일 수도 있다. 같은 프로세스의 스레드는 메모리를 공유하니 만들기도 전환하기도 주고받기도 싸고, 그래서 일반적으로는 프로세스 하나에 스레드 여럿이 효율적이다. 단, 그 효율은 두 조건 위에 선다. 하나는 격리를 포기해도 된다는 것이고, 다른 하나는 공유하는 것을 올바르게 지킨다는 것이다. 크롬이 탭마다 프로세스를 두는 것은 첫째 조건을 거부한 것이고, [04](../04-concurrency-ingredients)장 6절의 세 문제가 둘째 조건의 값이다. "스레드가 더 효율적"이라는 명제는 동기화를 제대로 했을 때만 참이다.

## 7. 멀티태스킹과 현대 런타임

```java
var pool = Executors
    .newVirtualThreadPerTaskExecutor();
try (pool) {
    for (var url : urls)
        pool.submit(() -> fetch(url));
}   // 블로킹 지점마다 캐리어를 내놓는다
```

| 런타임 | 모델 | 전환 방식 | 양보 지점 | 왜 이렇게 |
|:------|:-----|:-------|:-------|:-------|
| Node.js | 스레드 하나의 이벤트 루프 | 협력형 | 콜백 반환, `await` | I/O가 대부분인 서버 |
| Python `asyncio` | 코루틴 + 이벤트 루프 | 협력형 | `await` | 같다 |
| Go | 고루틴, M:N 스케줄러 | 협력형에 일부 선점 | 함수 호출, 블로킹, 10ms 타이머 | 계산 고루틴이 독점하지 않게 |
| Java 21 | 가상 스레드, 캐리어 위에 | 협력형 | 블로킹 I/O, `sleep`, 락 대기 | 4.1절. 계산은 독점한다 |
| 운영체제 | 스레드 | 선점형 | 10 ms | 그 아래의 바닥 |

멀티태스킹은 운영체제 안에만 있지 않다. 런타임이 같은 착각을 사용자 공간에서 다시 만든다. 이벤트 루프, 코루틴, 고루틴, 가상 스레드는 전부 OS 스레드 몇 개 위에서 논리 작업 수만 개를 교대시키는 협력형 멀티태스킹이고, 그 아래에서 운영체제가 그 OS 스레드들을 선점형으로 교대시킨다. 두 층이 겹쳐 있으니 규칙도 둘이다. 위층에서는 양보 지점을 자주 지나야 하고(계산은 4.1절처럼 독점한다), 아래층에서는 캐리어 수가 코어 수를 넘지 않아야 한다. Go가 협력형에 10ms 타이머의 선점을 섞은 것은 첫째 규칙을 어긴 고루틴에 대한 보험이다. 이 층이 어떻게 생겼는지는 [12](../12-asynchronous-communication)장, 이벤트 루프의 속은 [11](../11-event-driven-concurrency)장이다.

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 멀티태스킹 | 코어 하나에서 여럿을 교대. 런타임의 기능 | 착각을 판다 |
| 병렬성과의 관계 | 코어마다 병렬, 코어 안에서 멀티태스킹 | 두 층이 겹친다 |
| CPU 바운드 | 코어를 계속 쓴다 | 코어 수까지만 |
| I/O 바운드 | 잠깐 쓰고 잔다 | 100개를 얹어도 계산은 2% 손해 |
| 컨텍스트 스위칭 | 상태를 저장하고 복원 | 직접 1.5 µs |
| 간접 비용 | 식은 캐시 | 순차는 거의 0, 무작위는 15% |
| 기다림 | 코어보다 많은 스레드의 값 | 40개면 3.8ms 돌고 10.3ms 대기 |
| 협력형 | 작업이 내놓을 때만 | 양보 없는 가상 스레드가 1,003 ms 독점 |
| 선점형 | 시계가 뺏는다 | 40개가 바빠도 0.57 ms에 시작 |
| 타임 슬라이스 | 이 PC 10 ms | 짧으면 전환, 길면 응답성 |
| 우선순위 | 자바에서는 힌트 | MIN과 MAX가 1.01배 |
| I/O 편애 | 깬 스레드가 줄 맨 앞 | 코어가 전부 바빠도 0.26 ms |
| 단위 | 스레드가 싸고 프로세스가 안전 | 동기화를 전제로 스레드 |
| 현대 런타임 | 선점형 위의 협력형 | 양보 지점을 자주, 캐리어는 코어 수 |

{{< callout type="info" >}}
**용어 정리**
- **멀티태스킹**: 여러 작업을 빠르게 교대 실행해 동시에 도는 것처럼 보이게 하는 것
- **동시성의 착각**: 코어 하나가 한 순간 하나만 돌려도 교대가 빠르면 동시로 보이는 것
- **CPU 바운드 / I/O 바운드**: 병목이 계산 / 병목이 기다림
- **컨텍스트 스위칭**: 실행 중인 작업의 상태를 저장하고 다른 작업의 상태를 복원하는 것
- **TCB**: 스레드 제어 블록. PC, 레지스터, 스택 포인터가 저장되는 곳
- **직접 비용 / 간접 비용**: 저장·복원 시간 / 전환 뒤 식은 캐시와 TLB
- **스래싱**: 전환만 하고 진척이 없는 상태
- **협력형**: 작업이 스스로 양보할 때만 전환. 코루틴, 이벤트 루프, 가상 스레드
- **선점형**: 스케줄러가 타이머로 강제 전환. 현대 운영체제
- **타임 슬라이스(퀀텀)**: 한 번 올라가 강제로 내려오기까지의 시간. 이 PC 약 10 ms
- **스케줄러**: 준비 큐에서 다음에 돌 작업을 고르는 운영체제 부품
- **준비 / 실행 / 대기**: 코어만 주면 돈다 / 코어 위에 있다 / 코어를 줘도 못 돈다
- **다단계 피드백 큐**: 행동을 보고 급을 바꾸는 스케줄러. 스스로 자는 스레드를 우대
- **캐리어 스레드**: 가상 스레드를 태워 나르는 OS 스레드
