앞 장들은 스레드로 동시성을 만드는 법과 그 값이었다. 이 장부터는 스레드 없이 만드는 법이다. 출발점은 서버다. 연결 수천 개가 각자 무언가를 기다리는데, 기다림마다 스레드를 붙일 수는 없다. 원리는 셋이다. 첫째, **I/O 바운드 프로그램의 시간은 기다림이고, 누가 기다리느냐가 설계다.** 블로킹 호출은 스레드가 기다린다. 스레드 하나가 연결 하나에 묶이고, 코드는 단순하다. 논블로킹 호출은 즉시 돌아온다. 기다림이 내 몫이 되고, 그 대신 스레드 하나로 연결 여럿을 다룰 수 있다. 둘째, **연결마다 스레드는 천장에 부딪히고, 폴링은 CPU를 태우고, 멀티플렉싱은 기다림을 커널에 맡긴다.** 스레드는 이 PC에서 4,069개가 끝이고, 준비됐는지 계속 묻는 폴링은 연결이 늘수록 느려지며 코어 하나를 통째로 태운다. 준비된 것이 생기면 깨워 달라고 커널에 맡기면 스레드 하나가 연결 1만 개를 CPU 0%로 들고 있는다. 셋째, **이벤트 루프의 규칙은 하나다. 루프 안에서 기다리지 마라.** 스레드 하나가 모든 연결을 돌보니, 그 스레드가 10ms를 멈추면 연결 1만 개가 10ms를 잃는다. 이 PC(Apple M4 10코어, macOS, JDK 23)에서 블로킹 읽기와 논블로킹 읽기와 `select()`가 각각 어떻게 기다리는지 CPU 시간으로 재고, 유휴 연결 1,000개와 1만 개를 든 채 연결마다 스레드·바쁜 폴링·셀렉터 이벤트 루프·가상 스레드 네 가지 서버의 메모리, OS 스레드 수, 유휴 CPU, 응답 지연을 재고, 이벤트 루프 안에서 핸들러 하나가 10ms를 멈출 때 나머지 연결이 얼마를 잃는지 봤다.

## 1. 입출력 바운드와 동시성의 필요성

```text
I/O 바운드 작업의 시간
▓░░░░░░░▓░░░░░░░▓░░░░░░░
▓ CPU 계산 (짧다)  ░ I/O 대기 (길다)
기다리는 동안 CPU는 논다
```

| 구분 | 병목 | 시간의 대부분 | 예 | 왜 동시성이 필요한가 |
|:-----|:-----|:----------|:---|:---------------|
| CPU 바운드 | 코어 | 계산 | 암호화, 인코딩, 정렬 | 코어를 더 써야 빨라진다 ([02](../02-sequential-and-parallel-execution)장) |
| I/O 바운드 | 디스크, 네트워크, 상대 | 기다림 | 웹 서버, DB 프록시, 채팅 | 기다리는 동안 다른 연결을 돌봐야 한다 |

클라이언트와 서버가 메시지를 주고받는 프로그램은 상대가 여럿이고, 여럿이 동시에 말을 건다. 여기서 동시성은 선택이 아니다. 그리고 이런 프로그램은 거의 다 I/O 바운드다. 요청 하나를 처리하는 CPU 시간은 µs인데 응답이 오기까지는 ms다. [01](../01-what-is-concurrency)장 3절에서 본 대로 그 기다림을 겹치는 것이 동시성의 이득 전부이고, 기다림이 길수록 이득이 크다. 문제는 그 기다림을 **누가** 하느냐다. 스레드가 하면 [04](../04-concurrency-ingredients)장의 값을 치르고, 이 장은 그 값을 안 치르는 길이다.

## 2. 블로킹 vs 논블로킹 I/O

### 2.1 제어를 언제 돌려주는가

```text
[블로킹]
호출 ─▶ [ I/O 진행 … ] ─▶ 반환
        호출자는 여기서 잔다

[논블로킹]
호출 ─▶ 반환 (즉시, 0 바이트)
        [ I/O 진행 … ]  나중에 되묻는다
```

| 이 PC에서, 상대가 300ms 뒤에 한 바이트를 보낼 때 | 돌아온 시각 | 그동안 이 스레드의 CPU | 왜 |
|:----------------------------------|:---------|-----------:|:---|
| 블로킹 `read()` | 바이트가 도착한 뒤 (보낸 지 897 µs 뒤) | 0 ms | 커널이 재웠다가 깨운다 |
| 논블로킹 `read()` | 즉시, 0 바이트. 200ms에 103만 번 부를 수 있다 | 200 ms | 물을 때마다 0.19 µs. 기다림은 내 몫 |
| `select()` (5절) | 바이트가 도착한 뒤 (보낸 지 833 µs 뒤) | 0 ms | 커널이 재웠다가 준비되면 깨운다 |

첫째 원리다. 두 방식의 차이는 제어를 언제 돌려주느냐다. 블로킹은 일을 다 마친 뒤 돌아오고, 그때까지 호출한 스레드는 [04](../04-concurrency-ingredients)장 5절의 `WAITING`으로 잔다. CPU를 안 쓰니 낭비는 없지만 그 스레드는 그 연결 말고는 아무것도 못 한다. 논블로킹은 시작만 하고 즉시 돌아온다. 준비된 것이 없으면 0을 돌려주고, 스레드는 다른 일을 하다가 나중에 다시 묻는다. 기다림이 커널에서 내 코드로 넘어온 것이고, 그래서 스레드 하나가 연결 여럿을 다룰 수 있다. 대신 어떻게 기다릴지를 내가 정해야 하고, 4절과 5절이 그 두 답이다.

### 2.2 코드

```java
// 블로킹: 올 때까지 잔다
var server = new ServerSocket(8080);
var socket = server.accept(); // 기다림
var in = socket.getInputStream();
int b = in.read();          // 기다림
```

```java
// 논블로킹: 없으면 바로 돌아온다
var server = ServerSocketChannel.open();
server.bind(
    new InetSocketAddress(8080));
server.configureBlocking(false);
var c = server.accept();  // 없으면 null
if (c != null) {
    var buf = ByteBuffer.allocate(1024);
    int n = c.read(buf);   // 없으면 0
}
```

### 2.3 블로킹·논블로킹과 동기·비동기

| | 블로킹 | 논블로킹 | 왜 다른 축인가 |
|:--|:-----|:------|:-----------|
| 동기 (완료를 내가 확인) | 보통의 `read()` | 논블로킹 `read()` + 다시 묻기 | 블로킹은 제어를 언제 돌려주느냐 |
| 비동기 (완료를 통지받음) | 거의 없다 | 완료 콜백, `CompletableFuture` | 동기·비동기는 결과를 어떻게 아느냐 |

두 축이 자주 섞인다. 블로킹과 논블로킹은 **이 호출이 나를 멈추는가**이고, 동기와 비동기는 **끝난 것을 내가 되묻는가, 누가 알려 주는가**다. 이 장의 논블로킹 소켓은 둘째 칸이다. 즉시 돌아오지만 결과는 내가 다시 물어야 한다. 완료를 통지받는 넷째 칸은 [11](../11-event-driven-concurrency)장의 프로액터와 [12](../12-asynchronous-communication)장의 퓨처다. 문헌마다 정의가 조금씩 달라서, 실무에서는 "멈추는가"와 "되묻는가" 두 물음으로 갈라 보면 충분하다.

## 3. 스레드 기반 동시성의 한계

```text
C1 ─▶ [스레드 1]  read()에서 잔다
C2 ─▶ [스레드 2]  read()에서 잔다
 ⋮
CN ─▶ [스레드 N]  이 PC는 4,069에서 끝
```

```java
while (true) {
    var socket = server.accept();
    new Thread(() -> handle(socket))
        .start();   // 연결마다 스레드
}
```

| 연결마다 스레드, 유휴 연결 N개 | 메모리 | OS 스레드 | 유휴 CPU | 응답 지연 (중앙값 / p99) | 왜 |
|:---------------------|------:|-------:|-------:|-----------------:|:---|
| 1,000 | +86 MB | 1,030 | 0% | 87 / 206 µs | 스레드마다 스택. 잠든 동안은 공짜 |
| 3,000 | +130~244 MB | 3,028 | 0% | 88~118 / 211~325 µs | 스택이 쌓인다 |
| 5,000 | | 4,069개째 생성 실패 | | 4,197번째부터 연결 거부, 프로세스가 스레드를 더 못 만든다 | macOS의 프로세스당 4,096개 ([04](../04-concurrency-ingredients)장 2.4절) |

가장 단순한 서버는 연결마다 스레드를 하나 붙이는 것이다. 블로킹 `read()`로 스레드가 자도 다른 연결은 다른 스레드가 돌보니 동시성이 생긴다. 코드가 순차 프로그램과 같아서 이해하기 쉽고, 위 표의 응답 지연이 네 모델 중 가장 짧다. 스레드가 자다가 깨는 것이 커널의 기본 동작이라서다. 문제는 개수다. 스레드 하나에 스택이 붙고([04](../04-concurrency-ingredients)장에서 잠든 스레드 하나가 88KB였다), 운영체제가 프로세스 하나에 허락하는 수가 있다. 이 PC에서 5,000개를 시도하니 4,069개째에서 스레드를 못 만들었고, 그 뒤의 연결은 거부됐고, 같은 프로세스 안의 다른 코드도 스레드를 못 만들었다. 서버 하나가 통째로 멈춘 것이다. 운영체제의 스레드는 적은 수로 오래 도는 일에 맞지, 수만 개가 각자 잠들어 있는 일에는 맞지 않는다.

{{< callout type="warning" >}}
**C10K.** 1999년의 물음이다. 서버 한 대가 연결 1만 개를 동시에 들 수 있는가. 연결마다 스레드면 스레드 1만 개이고, 스택만으로 GB 단위에 [06](../06-multitasking)장의 전환 비용이 코어를 먹는다. 이 PC의 답은 그보다 앞에 있었다. 4,069개다. 이 물음이 이 장의 나머지를 만들었고, 오늘의 서버들(Nginx, Node.js, Redis, Netty)이 전부 그 답 위에 서 있다.
{{< /callout >}}

## 4. 바쁜 대기와 단일 스레드 다중 처리

```text
┌─▶ accept? ─▶ C1 read? ─▶ C2 read? ─┐
└──────── CN read? ◀──────── … ◀─────┘
쉬지 않는다. 한 바퀴 = 연결 수 × 0.2 µs
```

```java
while (true) {        // 쉬지 않는 루프
    SocketChannel c;
    while ((c = server.accept())
            != null)
        clients.add(nonBlocking(c));
    for (var ch : clients) {
        buf.clear();  // 없으면 0이 온다
        if (ch.read(buf) > 0)
            echo(ch, buf);
    }
}
```

| 스레드 하나가 돌며 묻기, 유휴 연결 N개 | 메모리 | OS 스레드 | 유휴 CPU | 응답 지연 (중앙값 / p99) | 왜 |
|:--------------------------|------:|-------:|-------:|-----------------:|:---|
| 1,000 | +0 MB | 27 | 100% | 231 / 328 µs | 한 바퀴에 1,000번 묻는다. 코어 하나가 꽉 찬다 |
| 10,000 | +36 MB | 30 | 100% | 2,710 / 4,681 µs | 한 바퀴에 1만 번. 지연이 연결 수에 비례한다 |

스레드를 안 만드는 첫 방법이다. 논블로킹 `read()`는 즉시 돌아오니, 스레드 하나가 모든 연결을 차례로 돌며 "준비됐나"를 묻고 준비된 것만 처리한다. 스레드는 하나, 메모리는 거의 0이다. 대신 두 가지 값을 치른다. 준비된 것이 하나도 없어도 루프는 돌고, 그래서 아무 일이 없는 서버가 코어 하나를 100% 태운다. 그리고 한 바퀴가 연결 수에 비례해 길어진다. 연결 1만 개에 한 바퀴 2.7ms, 응답 지연도 2.7ms다. 연결이 열 배가 되면 지연도 열 배다. 2절의 논블로킹 읽기 한 번이 0.19µs였던 것이 이 숫자의 출처다.

{{< callout type="warning" >}}
**바쁜 대기는 기다림을 없앤 것이 아니라 CPU로 바꾼 것이다.** 준비된 소켓이 하나도 없는 밤에도 서버는 코어 하나를 다 쓴다. [03](../03-how-computers-work)장 1.2절의 스핀 대기가 72ns를 위해 코어를 태우는 것과 같은 거래이고, 그 거래가 맞는 곳은 기다림이 µs 단위로 짧고 코어가 남는 곳뿐이다. 소켓은 아니다.
{{< /callout >}}

## 5. I/O 멀티플렉싱과 이벤트 루프

```text
C1  C2  C3  …  C10000   연결 1만 개
 └───┴───┴──────┘
        ▼
  ┌────────────┐
  │ Selector   │  준비된 것만 골라 준다
  └─────┬──────┘
        ▼  준비된 채널만
  ┌────────────┐
  │ 이벤트 루프│  스레드 하나
  └────────────┘
```

| 커널 API | 방식 | 한계 | 왜 |
|:-------|:-----|:----|:---|
| `select` | 감시할 소켓 집합을 넘기고 준비될 때까지 잔다 | 보통 1,024개, 매번 전체를 훑는다 | 비트 집합 하나 |
| `poll` | 같다. 개수 제한이 없다 | 여전히 매번 전체를 훑는다 | 배열 |
| `epoll` (리눅스), `kqueue` (macOS, BSD), IOCP (윈도우) | 감시 목록을 커널에 등록해 두고 준비된 것만 받는다 | 없음 | 커널이 준비된 목록을 유지한다 |

| 셀렉터 이벤트 루프, 유휴 연결 N개 | 메모리 | OS 스레드 | 유휴 CPU | 응답 지연 (중앙값 / p99) | 왜 |
|:---------------------|------:|-------:|-------:|-----------------:|:---|
| 1,000 | +4 MB | 28 | 0% | 105 / 448 µs | 준비된 것이 없으면 잔다 |
| 10,000 | +21 MB | 28 | 0% | 134 / 260 µs | 연결이 열 배여도 지연은 같다 |

둘째 원리다. 바쁜 대기의 문제는 준비되지 않은 소켓까지 내가 묻는 것이다. 답은 묻는 일을 커널에 넘기는 것이다. "이 소켓들 중 준비된 것이 생기면 깨워 달라"고 맡기고 잔다. 이것이 I/O 멀티플렉싱이고, 2절 표에서 `select()`가 CPU 0ms로 305ms를 잔 뒤 바이트가 도착하자 833µs 만에 깬 것이 그 실물이다. 자바의 `Selector`가 운영체제마다 다른 이 API(이 PC에서는 kqueue)를 감싼다. 위 표가 그 결과다. 스레드 하나가 연결 1만 개를 21MB로 들고 있으면서 유휴 CPU는 0%이고, 응답 지연은 연결이 열 배가 되어도 그대로다. 커널이 준비된 목록만 주니 한 바퀴의 일이 연결 수가 아니라 **준비된 수**에 비례한다. 준비된 이벤트만 골라 처리하는 이 단일 스레드 루프를 이벤트 루프, 또는 리액터라 부른다.

### 5.1 규칙: 루프 안에서 기다리지 마라

| 유휴 연결 1,000개, 보통 클라이언트 10개, 그리고 핸들러가 10ms 걸리는 클라이언트 하나 | 보통 클라이언트의 응답 지연 (중앙값 / p99) | 왜 |
|:-------------------------------------------------------|-------------------------:|:---|
| 느린 핸들러를 루프 스레드에서 실행 | 12,288 / 12,882 µs | 루프가 10ms 멈추면 모두가 10ms 기다린다 |
| 느린 핸들러를 워커 풀에 넘김 | 86 / 168 µs | 루프는 넘기고 바로 다음 이벤트로 |

셋째 원리다. 이벤트 루프는 스레드 하나가 모든 연결을 돌보는 구조라, 그 스레드가 멈추면 전부 멈춘다. 클라이언트 하나의 요청을 처리하는 데 10ms가 걸리자 관계없는 다른 열 클라이언트의 응답이 86µs에서 12ms가 됐다. 연결 1만 개였다면 1만 개가 그랬을 것이다. 그래서 루프 안의 코드는 절대 기다리면 안 된다. 블로킹 I/O도, 락 대기도, 긴 계산도 안 된다. 기다려야 하는 일은 워커 풀에 넘기고 결과가 오면 다시 이벤트로 받는다. 이 규칙과 그것을 지키는 구조가 [11](../11-event-driven-concurrency)장의 리액터 패턴이고, 규칙을 어겼을 때의 모양은 그 장 4.3절이다.

## 6. Java NIO Selector 실전

```java
var sel = Selector.open();
server.register(sel, OP_ACCEPT);
while (true) {
    sel.select();  // 준비될 때까지 잔다
    for (var key : sel.selectedKeys()) {
        if (key.isAcceptable()) {
            var c = server.accept();
            c.configureBlocking(false);
            c.register(sel, OP_READ);
        } else if (key.isReadable()) {
            var ch = (SocketChannel)
                key.channel();
            buf.clear();
            int n = ch.read(buf);
            if (n < 0) ch.close();
            else ch.write(buf.flip());
        }
    }
    sel.selectedKeys().clear();
}
```

이 장의 실측에 쓴 에코 서버의 뼈대다. 채널을 논블로킹으로 두고 셀렉터에 관심(연결 수락, 읽기)을 등록하면, `select()`가 준비된 채널이 생길 때까지 CPU를 안 쓰고 잔다. 깨어나면 준비된 키만 돌며 처리하고, 처리한 키는 지운다. 4절의 폴링 루프와 코드 모양은 비슷한데 `select()` 한 줄이 "묻기"를 "맡기기"로 바꾼다.

```java
// 넷째 길: 연결마다 가상 스레드
while (true) {
    var socket = server.accept();
    Thread.ofVirtual()
        .start(() -> handle(socket));
}
```

| 모델 | 스레드 | 유휴 연결 1만 개에서 | 유휴 CPU | 응답 지연 | 코드 | 왜 |
|:-----|:-----|:---------------|-------:|-------:|:-----|:---|
| 연결마다 스레드 | 연결 수 | 4,069개에서 실패 | 0% | 87 µs | 순차와 같다 | 스레드의 천장 |
| 바쁜 폴링 | 1 | +36 MB | 100% | 2,710 µs | 루프 | 연결 수만큼 묻는다 |
| 셀렉터 이벤트 루프 | 1 (~코어 수) | +21 MB, OS 스레드 28 | 0% | 134 µs | 상태 기계 | 커널이 준비된 것만 준다 |
| 연결마다 가상 스레드 | 연결 수 (가상) | +4 MB, OS 스레드 42 | 0% | 86 µs | 순차와 같다 | 런타임이 셀렉터를 대신 돌린다 |

넷째 길이 표의 마지막 줄이다. 코드는 3절의 연결마다 스레드와 똑같은데 스레드가 가상이다. 블로킹 `read()`를 부르면 런타임이 그 가상 스레드를 떼어 두고 OS 스레드를 다른 가상 스레드에 준다. 속에서는 런타임이 셀렉터를 돌리고, 겉에서는 내가 순차 코드를 쓴다. 이 PC에서 연결 1만 개를 OS 스레드 42개로 들고 응답 지연은 네 모델 중 가장 짧았다. 이벤트 루프의 성능과 블로킹 코드의 단순함을 같이 갖는 대신, 그 루프가 내 눈에 안 보인다는 값을 치른다. 어떻게 얹히는지는 [12](../12-asynchronous-communication)장 6절이다. 자바 소켓 API의 기본은 [자바 기초 16](../../java/basics/16-networking)장 3절이다.

{{< callout type="info" >}}
**폴링과 `select()`의 차이는 한 줄이고 결과는 CPU 100%와 0%다.** 폴링은 준비된 것이 없어도 묻고, `select()`는 준비된 것이 생길 때까지 잔다. 커널이 이벤트가 생겼을 때 깨워 주니 낭비가 없고, 스레드 하나로 연결 수만 개를 들 수 있다. Node.js, Netty, Redis, Nginx의 공통 뼈대가 이 한 줄 위에 있고, 그 뼈대에 붙는 규칙이 5.1절의 "루프 안에서 기다리지 마라"다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| I/O 바운드 | 시간의 대부분이 기다림 | 겹칠 것이 많다 |
| 블로킹 | 끝나야 돌아온다. 스레드가 잔다 | CPU 0, 스레드 하나가 묶인다 |
| 논블로킹 | 즉시 돌아온다. 기다림은 내 몫 | 0.19 µs에 0 바이트 |
| 동기·비동기 | 되묻는가, 통지받는가 | 블로킹과 다른 축 |
| 연결마다 스레드 | 단순하고 빠르다. 개수가 천장 | 4,069개에서 서버가 멈춘다 |
| 바쁜 대기 | 스레드 하나, CPU 100% | 지연이 연결 수에 비례. 1만 개에 2.7 ms |
| 멀티플렉싱 | 준비된 것이 생기면 커널이 깨운다 | `select`, `poll`, `epoll`, `kqueue` |
| 이벤트 루프 | 스레드 하나가 연결 1만 개 | +21 MB, CPU 0%, 134 µs |
| 규칙 | 루프 안에서 기다리지 마라 | 핸들러 10 ms가 모두의 12 ms |
| 가상 스레드 | 순차 코드로 이벤트 루프의 성능 | OS 스레드 42개에 연결 1만 개, 86 µs |

{{< callout type="info" >}}
**용어 정리**
- **I/O 바운드**: 병목이 입출력 대기인 작업. 웹 서버, 프록시, 채팅
- **블로킹 / 논블로킹**: 끝나야 돌아온다 / 시작만 하고 즉시 돌아온다
- **동기 / 비동기**: 완료를 내가 되묻는다 / 완료를 통지받는다
- **연결마다 스레드**: 연결 하나에 스레드 하나. 코드는 순차, 개수는 천장
- **C10K**: 연결 1만 개를 서버 하나가 드는 문제
- **바쁜 대기**: 준비됐는지 쉬지 않고 묻는 것. CPU 100%
- **I/O 멀티플렉싱**: 소켓 여럿을 커널에 맡기고 준비된 것만 받는 것
- **select / poll / epoll / kqueue / IOCP**: 멀티플렉싱 API. 뒤의 셋은 준비된 것만 준다
- **Selector**: 자바가 운영체제의 멀티플렉싱 API를 감싼 것
- **이벤트 루프 / 리액터**: 준비된 이벤트만 골라 처리하는 단일 스레드 루프
- **핸들러 / 콜백**: 이벤트마다 루프가 부르는 코드. 기다리면 안 된다
- **워커 풀**: 루프가 기다려야 하는 일을 넘기는 곳
- **가상 스레드**: 런타임이 셀렉터 위에 얹은 스레드. 블로킹 코드로 논블로킹 효과
{{< /callout >}}
