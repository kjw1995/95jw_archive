앞 세 장은 "왜 동시에"와 "무엇 위에서"였다. 이 장부터는 "무엇으로"다. 운영체제가 실행을 하드웨어에 배정하는 단위는 둘이고, 그 둘로 모든 동시성이 만들어진다. 원리는 셋이다. 첫째, **프로세스는 격리를 사고 스레드는 공유를 산다.** 프로세스는 자기만의 주소 공간을 받아 서로를 건드릴 수 없고, 스레드는 프로세스 안에서 코드와 힙을 같이 쓰며 스택만 따로 갖는다. 격리의 값은 만드는 비용과 통신 비용이고, 공유의 값은 동기화다. 둘째, **스레드는 싸지만 공짜가 아니고 무한하지도 않다.** 만드는 데 수십 µs, 잠들어 있어도 수십 KB, 코어를 바꿔 타는 데 µs가 들고, 운영체제가 프로세스 하나에 허락하는 개수에 천장이 있다. 셋째, **공유하는 순간 세 가지가 깨진다. 원자성, 가시성, 순서다.** 한 줄짜리 `count++`가 절반을 잃고, 한 스레드가 바꾼 값을 다른 스레드가 영영 못 보고, 코드에 적힌 순서가 실행 순서가 아니게 된다. 이 PC(Apple M4 10코어, macOS, JDK 23)에서 스레드와 프로세스를 수천 개 만들며 비용과 천장을 재고, 코어 사이를 오가는 전환 시간을 재고, 세 가지가 깨지는 순간을 숫자로 봤다.

## 1. 프로세스 (Process)

### 1.1 프로그램과 프로세스

```text
디스크           메모리
java 실행 파일 ─▶ 프로세스 A (pid 1)
 (정적인 코드)  ─▶ 프로세스 B (pid 2)
같은 프로그램을 여러 번 띄울 수 있다
```

| 구분 | 프로그램 | 프로세스 | 왜 갈라 보나 |
|:-----|:-------|:-------|:-----------|
| 무엇 | 디스크의 파일 | 메모리에 올라와 실행 중인 인스턴스 | 하나가 여럿이 된다 |
| 가진 것 | 코드 | 코드 + 주소 공간 + 열린 파일 + 스레드 | 실행에는 상태가 필요하다 |
| 개수 | 하나 | 띄운 만큼 | 브라우저 탭마다 프로세스 하나 |
| 스레드 | 없음 | 하나 이상 | 스레드는 프로세스 밖에 못 산다 |

프로세스는 실행 중인 프로그램의 한 인스턴스다. 프로그램이 디스크에 있는 정적인 코드라면, 프로세스는 그 코드가 메모리에 올라와 주소 공간과 열린 파일과 스레드를 거느리고 **돌고 있는 상태**다. 같은 프로그램을 두 번 띄우면 프로세스가 둘이고, 둘은 서로의 존재를 모른다. 프로세스는 하나 이상의 스레드를 갖고, 프로세스에 속하지 않은 스레드는 없다. 이 PC에서 JVM을 띄우면 내 코드가 스레드를 하나도 만들지 않아도 프로세스 안에 운영체제 스레드가 27개 있었다([03](../03-how-computers-work)장 4절).

### 1.2 프로세스의 메모리 구조

```text
높은 주소
┌────────────────────────────┐
│ 스택   지역 변수, 호출 정보│
├────────────────────────────┤
│ (빈 공간)                  │
├────────────────────────────┤
│ 힙     new로 만든 객체     │
├────────────────────────────┤
│ 데이터  전역 · 정적 변수   │
├────────────────────────────┤
│ 코드   기계어 명령         │
└────────────────────────────┘
낮은 주소
스택은 아래로, 힙은 위로 자란다
```

| 영역 | 담는 것 | 누가 쓰나 | 왜 따로 두나 |
|:-----|:------|:--------|:----------|
| 코드 | 기계어 명령 | 읽기만 | 바뀌지 않으니 공유하고 보호한다 |
| 데이터 | 전역 변수, 정적 변수 | 모든 스레드 | 프로그램이 도는 내내 산다 |
| 힙 | `new`로 만든 객체 | 모든 스레드 | 크기를 실행 중에 정한다 |
| 스택 | 지역 변수, 호출 정보 | **스레드마다 하나** | 함수가 돌아오면 사라진다 |

운영체제는 프로세스마다 독립된 주소 공간을 준다. 프로세스 A의 주소 0x1000과 프로세스 B의 주소 0x1000은 다른 물리 메모리를 가리키고, A가 B의 메모리를 읽으려 하면 운영체제가 막는다. 이 격리가 프로세스의 존재 이유다. 위 표에서 눈여겨볼 곳은 마지막 줄이다. 코드·데이터·힙은 프로세스에 하나씩인데 스택은 **스레드마다** 하나다. 2절에서 스레드를 정의할 때 이 줄이 스레드의 정체가 된다. JVM이 이 구조를 어떻게 자기 식으로 다시 나누는지는 [JVM 메모리 관리](../../java/jvm/memory-management) 1절이다.

### 1.3 격리의 값

```java
var p = new ProcessBuilder(
        "java", "-version")
    .redirectErrorStream(true)
    .start();          // 새 프로세스
try (var in = p.inputReader()) {
    in.lines().forEach(
        System.out::println); // 파이프
}
int code = p.waitFor();
```

| 만드는 것 | 이 PC에서 | 왜 |
|:--------|--------:|:---|
| 프로세스 (`/usr/bin/true`) | 1.8 ms | 주소 공간을 만들고 실행 파일을 적재한다 |
| 프로세스 (`java -version`) | 29 ms | JVM 시동까지 |
| 스레드 (2절) | 26 µs | 스택만 잡는다. 프로세스의 70분의 1 |

| 격리가 주는 것 | 뜻 | 이 PC에서 | 왜 |
|:-----------|:---|:--------|:---|
| 안전 | 하나가 죽어도 나머지는 산다 | 자식 `sh`를 SIGSEGV로 죽였더니 종료 코드 139, 부모는 그대로 | 주소 공간이 다르니 오염이 안 번진다 |
| 자원 소유 | 메모리, 파일, 소켓이 프로세스 것 | | 종료하면 운영체제가 전부 회수한다 |
| 통신 비용 | 직접 못 읽으니 IPC | 파이프 4.7 µs, TCP 13 µs ([03](../03-how-computers-work)장 1.2절) | 커널을 지나야 한다 |
| 생성 비용 | 위 표 | 1.8 ms | 주소 공간 하나가 통째로 |

첫째 원리의 앞부분이다. 프로세스는 격리를 산다. 값은 둘이다. 만드는 데 스레드의 70배가 들고, 서로 데이터를 직접 못 보니 파이프·소켓·공유 메모리·메시지 큐 같은 프로세스 간 통신(IPC)을 운영체제에 부탁해야 한다. 위 코드가 그 가장 흔한 모양이다. 자식 프로세스를 띄우고 그 표준 출력을 파이프로 받는다. 대신 얻는 것이 안전이다. 자식이 세그먼트 폴트로 죽어도 부모는 종료 코드 139를 읽고 다음 줄로 간다. 브라우저가 탭마다 프로세스를 두는 이유, 데이터베이스가 연결마다 프로세스를 두던 이유가 이것이다. IPC 네 가지의 속과 고르는 법은 [05](../05-inter-process-communication)장이다.

## 2. 스레드 (Thread)

### 2.1 스레드는 스택 하나와 실행 위치다

```text
프로세스 (JVM 하나)
┌─────────────────────────────┐
│ 공유: 코드 · 데이터 · 힙    │
├─────────┬─────────┬─────────┤
│ 스레드 1│ 스레드 2│ 스레드 3│
│ 스택    │ 스택    │ 스택    │
│ PC, 레지│ PC, 레지│ PC, 레지│
└─────────┴─────────┴─────────┘
```

| 구분 | 공유 (프로세스에 하나) | 비공유 (스레드마다) | 왜 |
|:-----|:-----------------|:---------------|:---|
| 메모리 | 코드, 데이터, 힙 | 스택 | 지역 변수는 그 함수를 도는 스레드의 것 |
| 레지스터 | | PC, 스택 포인터, 범용 레지스터 | "지금 어디를 실행 중인가"가 스레드마다 다르다 |
| 자원 | 열린 파일, 소켓, 시그널 핸들러 | 스레드 ID, 우선순위, 상태 | 파일은 프로세스가 열고 스레드가 같이 쓴다 |

스레드는 어떤 결과를 내기 위한 독립적인 명령의 흐름이고, 운영체제가 코어에 올리는 **실행의 단위**다. 프로세스가 작업장이라면 스레드는 그 안의 작업자다. 작업자마다 자기 손(스택, 레지스터)은 따로 있지만 도구와 자재(코드, 힙)는 같이 쓴다. 1.2절의 표에서 스택만 스레드마다 하나였던 이유가 이것이다. 스레드 하나를 만든다는 것은 새 스택을 잡고 "여기서부터 실행하라"는 PC를 주는 것이고, 그게 전부다. 주소 공간은 이미 있는 것을 쓴다.

### 2.2 만들기

```java
// 1. Thread 상속
class Worker
        extends Thread {
    @Override public void run() {
        System.out.println(getName());
    }
}
new Worker().start();

// 2. Runnable을 넘긴다 (권장)
Runnable job = () -> System.out
    .println(Thread.currentThread()
        .getName());
new Thread(job, "작업자-1").start();

// 3. 가상 스레드 (JDK 21+)
Thread.ofVirtual().start(job);
```

| 방법 | 언제 | 왜 |
|:-----|:----|:---|
| `Thread` 상속 | 거의 없다 | 스레드와 일이 한 클래스에 묶인다 |
| `Runnable`을 넘긴다 | 스레드를 직접 만들 때 | 일과 실행 수단이 분리된다. 풀에도 같은 객체를 넘긴다 |
| 스레드 풀에 넘긴다 | 일이 많고 짧을 때 | 2.3절. 만드는 비용을 재사용으로 없앤다 |
| 가상 스레드 | 기다리는 일이 수만 개일 때 | 2.4절. OS 스레드가 아니다 |

`start()`가 새 스레드를 만들어 그 안에서 `run()`을 부르고, `run()`을 직접 부르면 지금 스레드에서 메서드 하나가 실행될 뿐이다([자바 기초 13](../../java/basics/13-thread)장 2.2절). 세 방법 모두 "무엇을 할지"는 `run()` 안에 있고 다른 것은 "누가 실행하느냐"뿐이다. 그래서 일을 `Runnable`로 떼어 두면 직접 만든 스레드에도, 풀에도, 가상 스레드에도 같은 것을 넘길 수 있다.

### 2.3 공유의 값: 싸다, 그러나 공짜는 아니다

| 만들고 시작하고 끝나기까지 | 이 PC에서 | 왜 |
|:---------------------|--------:|:---|
| 플랫폼 스레드 | 26~28 µs | OS 호출, 스택 2MB 예약, 스케줄러 등록 |
| 가상 스레드 | 8 µs | JVM 안의 객체. OS 호출이 없다 |
| 프로세스 (`/usr/bin/true`) | 1,839 µs | 주소 공간부터 |

| 제곱근 1,000번짜리 일감 2,000개 | 하나당 | 왜 |
|:--------------------------|------:|:---|
| 일감마다 새 스레드 | 25 µs | 일(약 3 µs)보다 스레드 만들기가 비싸다 |
| 스레드 하나짜리 풀에 넘김 | 6 µs | 스레드를 다시 쓴다. 남는 건 넘기고 받는 비용 |

첫째 원리의 뒷부분이다. 스레드는 공유를 산다. 주소 공간을 새로 안 만드니 26µs에 생기고, 같은 힙을 보니 데이터를 넘길 필요 없이 그냥 읽는다. 프로세스의 70분의 1이다. 그런데 26µs는 0이 아니다. 제곱근 1,000번은 3µs면 끝나는 일인데 그 일을 하려고 스레드를 만들면 25µs, 일의 여덟 배가 만드는 데 든다. 같은 일을 이미 있는 스레드에 넘기면 6µs다. 스레드 풀이 존재하는 이유가 이 두 줄이고 [05](../05-inter-process-communication)장 7절에서 본다.

### 2.4 스레드는 몇 개까지

| 잠든 스레드 | 하나당 실제 메모리 | 이 PC의 천장 | 왜 |
|:---------|-------------:|:----------|:---|
| 플랫폼 스레드 | 88 KB | 4,069개에서 `OutOfMemoryError` | macOS가 프로세스당 스레드 4,096개까지 |
| 가상 스레드 | 1.6 KB | 10만 개를 OS 스레드 37개 위에서 | 스택을 힙에 조각으로 둔다 |

```text
스레드를 만들어 재우고 RSS를 쟀다
플랫폼 1,000개  108 MB → 194 MB
               (+88 KB씩)
가상 10만 개    +152 MB (+1.6 KB씩)
플랫폼 4,069개째:
  pthread_create failed (EAGAIN)
  stacksize: 2048k
```

둘째 원리다. 스레드 하나는 스택으로 2MB를 **예약**하지만 실제로 만진 만큼만 물리 메모리를 쓴다. 잠들어 있는 스레드 1,000개가 88MB였으니 하나에 88KB다. 문제는 메모리보다 개수다. 이 PC의 운영체제는 프로세스 하나에 스레드 4,096개까지만 허락하고, JVM이 이미 27개를 쓰고 있어 4,069개째에서 만들기가 실패했다. 요청마다 스레드 하나를 주는 서버는 동시 접속 4,000명이 천장이다. 스레드가 코어 하나에 400개씩 있어도 대부분은 자고 있는데 개수 제한과 스택 예약은 그대로 든다. 그래서 스레드를 운영체제 것이 아니라 런타임 것으로 만드는 길이 생겼다. 가상 스레드는 스택을 힙에 조각으로 두고 OS 스레드 37개 위에서 10만 개가 돈다. 그 원리는 [12](../12-asynchronous-communication)장 2.2절과 6절이다.

## 3. 프로세스 vs 스레드

```text
프로세스 둘            스레드 둘
┌────────┐┌────────┐  ┌──────────────┐
│ 힙 A   ││ 힙 B   │  │ 힙 하나      │
│ 파일 A ││ 파일 B │  │ ┌────┐┌────┐ │
└────────┘└────────┘  │ │ T1 ││ T2 │ │
 완전 분리, IPC 필요  │ └────┘└────┘ │
                      └──────────────┘
                       공유, 동기화 필요
```

| 구분 | 프로세스 | 스레드 | 왜 |
|:-----|:-------|:------|:---|
| 주소 공간 | 독립 | 프로세스 것을 공유 | 격리 vs 공유 |
| 만드는 비용 | 1.8 ms | 26 µs | 주소 공간 vs 스택 |
| 전환 비용 | 높다 (메모리 맵 교체, TLB 비움) | 낮다 (레지스터만) | 4절 |
| 데이터 주고받기 | IPC, 4.7 µs 이상 | 같은 힙, 72 ns | 커널을 지나느냐 |
| 하나가 죽으면 | 나머지는 산다 (종료 코드 139) | 예외는 그 스레드만, 메모리 고갈이나 네이티브 크래시는 전부 | 힙을 같이 쓴다 |
| 동기화 | 대체로 필요 없다 | 반드시 | 공유하니까 (6절) |
| 디버깅 | 쉽다 | 어렵다. 돌릴 때마다 다르다 | 스케줄러가 순서를 정한다 |

둘을 가르는 것은 결국 한 줄이다. 같은 메모리를 보느냐. 본다면 스레드이고, 싸고 빠르고 대신 지켜야 한다. 안 본다면 프로세스이고, 비싸고 느리고 대신 안전하다. 이 PC에서 둘의 죽음을 비교해 봤다. 자식 프로세스를 SIGSEGV로 죽이니 부모는 종료 코드 139를 받고 계속 돌았다. 스레드 하나가 잡히지 않은 예외를 던지니 그 스레드만 `TERMINATED`가 되고 나머지는 돌았다. 여기까지는 같아 보이지만, 스레드 하나가 힙을 다 먹거나 네이티브 코드에서 크래시하면 같은 힙을 쓰는 스레드 전부가 함께 죽는다. 브라우저가 탭을 스레드가 아니라 프로세스로 두는 이유다. 이 선택은 격리와 비용의 트레이드오프이고, 대부분의 애플리케이션이 스레드를 고르는 이유는 값(26µs, 72ns)이 그만큼 싸기 때문이다. 스레드가 왜 위험한지는 6절, 그 위험을 어떻게 다루는지는 [08](../08-race-conditions-and-synchronization)장이다.

## 4. 컨텍스트 스위칭 (Context Switching)

### 4.1 무엇을 저장하고 복원하나

```text
코어 하나에 스레드 둘
A ████░░░░████░░░░
B ░░░░████░░░░████
      ↑       ↑
  A를 저장하고 B를 복원 (1.5 µs)
```

| 저장·복원하는 것 | 스레드 전환 | 프로세스 전환 | 왜 |
|:-------------|:---------|:-----------|:---|
| PC, 스택 포인터, 레지스터 | 예 | 예 | "어디까지 했나"의 전부 |
| 메모리 맵 (페이지 테이블) | 아니오 | 예 | 주소 공간이 바뀐다 |
| TLB (주소 변환 캐시) | 유지 | 비운다 | 다른 주소 공간의 변환은 쓸모없다 |
| 캐시 안의 데이터 | 남는다 | 대부분 못 쓴다 | 다른 프로세스의 데이터 |

코어는 한 번에 스레드 하나를 돈다. 다른 스레드를 돌리려면 지금 스레드의 PC와 레지스터를 메모리에 적어 두고, 다음 스레드의 것을 읽어 올려야 한다. 이것이 컨텍스트 스위칭이고 운영체제가 한다. 스레드끼리는 주소 공간이 같으니 레지스터 한 벌만 바꾸면 되지만, 프로세스가 바뀌면 메모리 맵을 갈아 끼우고 주소 변환 캐시(TLB)를 비워야 한다. 스레드 전환이 프로세스 전환보다 가벼운 이유이고, 동시적 프로그램이 스레드를 고르는 두 번째 이유다. 언제 전환이 일어나는지(타임 슬라이스, I/O 대기, 선점)는 [06](../06-multitasking)장 3절과 5절이다.

### 4.2 전환의 값

```java
// 스레드 둘이 park/unpark로 핑퐁
// 나
LockSupport.unpark(other);
LockSupport.park();
// 상대
LockSupport.park();
LockSupport.unpark(me);
// 왕복 3.1 µs = 전환 두 번
```

| 스레드 둘이 바통을 넘기는 방법 | 왕복 | 왜 |
|:----------------------|-----:|:---|
| 공유 변수를 돌며 기다림 (스핀) | 72 ns | 전환이 없다. 코어 둘이 캐시 라인을 주고받는다 |
| `park`/`unpark` | 3.1 µs | 전환 두 번. 하나에 1.5 µs |
| 블로킹 큐 | 3.7 µs | 전환 두 번에 큐의 락 |

| 같은 계산(약 1초)을 스레드 몇 개로 나누나 | 걸린 시간 | 왜 |
|:----------------------------|--------:|:---|
| 10 | 155 ms | 코어 열 개에 하나씩 |
| 100 | 155 ms | 아직 전환이 드물다 |
| 1,000 | 162 ms | 만들고 전환하는 비용이 보이기 시작 |
| 4,000 | 209 ms | 35% 손해. 개수 천장 직전 |

전환 하나가 1.5µs다. 코어가 곱셈을 수천 번 할 시간이고, 3µs짜리 일감을 스레드 사이에 넘기면 넘기는 데 일만큼 든다. 그래도 전환 자체보다 큰 비용이 있다. 스레드가 코어보다 많으면 스레드들은 일을 하는 게 아니라 **차례를 기다린다**. 같은 계산을 스레드 10개로 나누나 100개로 나누나 시간은 같고, 1,000개부터 느려져 4,000개면 35%를 잃는다. 전환할 때마다 코어의 캐시에 앞 스레드의 데이터가 남아 다음 스레드는 메모리에서 다시 읽어야 하고, 스레드마다 스택을 만들고 스케줄러에 등록하는 비용이 얹힌다. 코어 열 개짜리 기계에서 계산 스레드는 열 개면 충분하다는 것이 [02](../02-sequential-and-parallel-execution)장 4절의 결론이었고, 이 표가 그 이유다.

### 4.3 코어는 메모리를 캐시 라인으로 본다

```java
long[] arr = new long[64];
// 스레드 넷이 각각 1억 번 +1
// 같은 라인: arr[0], [1], [2], [3]
// 다른 라인: arr[0], [16], [32], [48]
//            (long 16개 = 128바이트)
```

| 스레드 넷이 각자의 칸을 1억 번 | 걸린 시간 | 왜 |
|:-----------------------|--------:|:---|
| 스레드 하나만 | 64 ms | 기준 |
| 넷이 같은 128바이트 라인 안의 칸 | 82~91 ms | 서로 다른 칸인데 라인을 뺏고 뺏긴다 |
| 넷이 서로 다른 라인 | 64~70 ms | 각자 자기 라인을 갖는다 |

스레드들이 **서로 다른 변수**를 만지는데도 느려지는 경우가 있다. 코어는 메모리를 바이트가 아니라 캐시 라인 단위로 가져오고, 이 PC의 라인은 128바이트다([03](../03-how-computers-work)장). `arr[0]`과 `arr[1]`은 다른 변수지만 같은 라인에 있어서, 코어 A가 `arr[0]`을 쓰면 코어 B의 캐시에 있던 그 라인이 무효가 되고 B는 `arr[1]`을 쓰려고 라인을 다시 가져와야 한다. 넷이 이걸 1억 번씩 반복하니 30%가 느려졌다. 거짓 공유(false sharing)라 부르고, 스레드마다 자기 카운터를 배열에 나란히 두는 흔한 코드가 정확히 이 모양이다. 공유가 없어 보이는 코드에도 하드웨어 층의 공유가 있다.

## 5. 스레드 생명주기

```text
new Thread()
     │ start()
     ▼
  RUNNABLE ◀──────────────┐
     │                    │
     ├─ 락 대기 ───▶ BLOCKED ─┤
     ├─ wait, join ▶ WAITING ┤
     ├─ sleep(ms) ▶ TIMED_WAITING
     │ run() 끝
     ▼
  TERMINATED
```

```java
var t = new Thread(() -> {
    Thread.sleep(300);  // TIMED_WAITING
    synchronized (lock) {
        lock.wait();        // WAITING
    }
    synchronized (lock) {}  // BLOCKED
});                 // 예외 처리 생략
t.getState();       // NEW
t.start();          // RUNNABLE
```

| 상태 | 뜻 | 들어가는 길 | 이 PC에서 본 순간 | 왜 갈라 두나 |
|:-----|:---|:---------|:-------------|:----------|
| `NEW` | 만들었고 아직 안 시작 | `new Thread()` | `new Thread():` NEW | OS 스레드가 아직 없다 |
| `RUNNABLE` | 코어에서 돌거나 차례를 기다림 | `start()` | main → RUNNABLE | 자바는 둘을 구분 안 한다. 스케줄러의 일 |
| `TIMED_WAITING` | 시간이 지나면 깨어남 | `sleep(ms)`, `wait(ms)` | `sleep(300)` 중 | 타이머가 깨운다 |
| `WAITING` | 누가 깨워 줘야 함 | `wait()`, `join()`, `park()` | `lock.wait()` 중 | `notify`나 `unpark`가 깨운다 |
| `BLOCKED` | 모니터 락을 기다림 | `synchronized` 진입 | main이 락을 쥔 동안 | 락 주인이 나가야 깨어난다 |
| `TERMINATED` | 끝남 | `run()` 종료, 예외 | `run()` 끝 | 다시 `start()` 못 한다 |

이 PC에서 스레드 하나를 만들고 단계마다 `getState()`를 찍은 결과가 표의 넷째 열이다. 자바가 정의하는 상태는 여섯이고, 그중 셋이 "기다림"이라는 것이 이 표의 요점이다. 무엇을 기다리느냐로 갈린다. 시간을 기다리면 `TIMED_WAITING`, 다른 스레드의 신호를 기다리면 `WAITING`, 락을 기다리면 `BLOCKED`다. 스레드 덤프에서 `BLOCKED`가 잔뜩 보이면 락 경합이고, `WAITING`이 잔뜩이면 신호를 못 받은 것이고, 둘 다 영원히면 [09](../09-deadlock-and-starvation)장의 교착이다. `RUNNABLE`이 "돌고 있다"가 아니라 "돌 수 있다"인 것도 기억할 만하다. 코어에 올라갈지는 운영체제가 정하고, 자바는 그 둘을 구분하지 않는다.

| JVM이 시작 직후 갖고 있는 스레드 | 상태 | 왜 |
|:-------------------------|:-----|:---|
| main | RUNNABLE | 내 코드 |
| Reference Handler, Signal Dispatcher, Notification Thread | RUNNABLE | 신호가 오면 바로 처리 |
| Finalizer | WAITING | 소멸 대상이 생길 때까지 |
| Common-Cleaner | TIMED_WAITING | 주기적으로 깨어나 정리 |

프로그램이 `main` 하나로 시작한 것 같아도 JVM은 이미 스레드 여섯을 세 가지 상태로 돌리고 있다. `Thread.getAllStackTraces()`로 언제든 볼 수 있고, 운영 중인 서버의 스레드 덤프를 읽는 첫걸음이 이 여섯 상태를 읽는 것이다. 세 가지 기다림을 만드는 `sleep`, `join`, `wait`, `interrupt`의 쓰임은 [자바 기초 13](../../java/basics/13-thread)장 3절이다.

## 6. 스레드의 위험성

스레드는 같은 힙을 본다. 그래서 싸고, 그래서 위험하다. 셋째 원리다. 공유하는 순간 세 가지가 깨지고, 이 PC에서 셋 다 깨뜨려 봤다.

### 6.1 원자성: `count++`는 한 번에 일어나지 않는다

```java
static int counter;
// 스레드 둘이 각각 100만 번
for (int i = 0; i < 1_000_000; i++)
    counter++;  // 읽기, +1, 쓰기
```

| 시도 | 결과 (기대 2,000,000) | 잃은 갱신 | 왜 |
|:----|-------------------:|-------:|:---|
| 1 | 1,032,323 | 48% | 둘이 같은 값을 읽고 같은 값을 썼다 |
| 2 | 1,136,935 | 43% | |
| 3 | 1,752,542 | 12% | 스케줄러가 둘을 덜 겹치게 돌렸다 |
| 4 | 1,975,922 | 1% | 거의 안 겹쳤다 |
| 5 | 1,784,066 | 11% | 매번 다르다 |
| `AtomicInteger` | 2,000,000 | 0 | 읽고 더하고 쓰기가 한 명령 |

`counter++`는 한 줄이지만 코어에는 세 명령이다. 읽고, 더하고, 쓴다. 스레드 A가 읽은 뒤 쓰기 전에 스레드 B가 같은 값을 읽으면 둘 다 같은 값에 1을 더해 쓰고, 갱신 하나가 사라진다. 이 PC에서 200만 번 중 많게는 절반이 사라졌고, 다섯 번 돌려 다섯 번 다른 결과가 나왔다. 사라지는 비율이 매번 다른 것이 이 문제의 가장 나쁜 점이다. 테스트에서 1%였던 것이 운영에서 48%가 된다. 이것이 경쟁 조건이고, 읽기·더하기·쓰기를 하나로 묶는 것이 원자적 연산이다. 같은 실험을 자바 바이트코드 수준에서 보는 것은 [자바 동시성 02](../../java/concurrency/02-thread-safety)장이다.

### 6.2 가시성: 바꿨는데 안 보인다

```java
static boolean ready;   // volatile 없음
// 읽는 스레드
while (!ready) { }  // 3초 뒤에도 못 봄
// 쓰는 스레드
ready = true;
```

| 플래그 | 쓴 뒤 읽는 스레드가 멈추기까지 | 왜 |
|:-----|:--------------------|:---|
| 평범한 `boolean` | 3초 뒤에도 안 멈춤 (영원히) | JIT이 "안 바뀌는 값"으로 보고 읽기를 루프 밖으로 뺐다 |
| `volatile boolean` | 38 µs | 매번 메모리에서 읽는다 |

한 스레드가 `ready = true`를 썼는데 다른 스레드가 3초가 지나도 못 본다. 코어마다 캐시가 따로 있어서이기도 하고, 더 흔하게는 JIT이 "이 루프 안에서 `ready`를 바꾸는 코드가 없다"고 판단해 읽기를 한 번만 하고 루프를 `while (true)`로 바꿔서다. 둘 다 단일 스레드에서는 완전히 옳은 최적화다. 공유한다고 말해 주지 않으면 런타임과 하드웨어는 공유하지 않는 것으로 취급한다. 그 말이 `volatile`이고, 붙이자 38µs 만에 봤다. 어떤 값이 다른 스레드에게 보이는가의 규칙은 [자바 동시성 03](../../java/concurrency/03-object-sharing)장 1절이다.

### 6.3 순서: 적힌 순서가 실행 순서가 아니다

```java
static int x, y, r1, r2;
// 스레드 A         // 스레드 B
x = 1;              y = 1;
r1 = y;             r2 = x;
// 적힌 순서대로면 (r1, r2) = (0, 0)은
// 나올 수 없다. 이 PC: 91%가 (0, 0)
```

| 변수 | 100만 번 중 (0, 0) | 왜 |
|:-----|----------------:|:---|
| 평범한 `int` | 914,214번 (91%) | 저장이 끝나기 전에 읽기가 먼저 갔다 |
| `volatile int` | 0번 | 저장과 읽기의 순서를 지키게 한다 |

스레드 A가 `x = 1` 다음에 `y`를 읽고, B가 `y = 1` 다음에 `x`를 읽는다. 적힌 순서대로 실행된다면 둘 중 하나는 반드시 1을 본다. 그런데 이 PC에서 100만 번 중 91만 번이 둘 다 0이었다. 컴파일러와 코어는 한 스레드 안에서 결과가 같기만 하면 명령 순서를 바꿔도 된다고 보고, 실제로 바꾼다. 저장은 느리니 버퍼에 넣어 두고 다음 읽기를 먼저 보낸다. 한 스레드만 보면 아무 문제가 없고, 다른 스레드가 그 사이를 보면 있을 수 없는 조합이 나온다. ARM은 x86보다 순서를 더 자유롭게 바꾸는 편이라 이 PC에서는 열에 아홉이 그렇다. `volatile`이나 락은 값을 보이게 할 뿐 아니라 그 앞뒤의 **순서**도 고정한다. 0번이 된 이유다.

### 6.4 해결의 방향

| 깨지는 것 | 실물 | 도구 | 어디서 | 왜 그 도구인가 |
|:--------|:-----|:-----|:------|:-----------|
| 원자성 | `count++` 48% 손실 | `synchronized`, `Lock`, `Atomic*` | [08](../08-race-conditions-and-synchronization)장 | 읽기·쓰기 사이에 아무도 못 끼게 |
| 가시성 | 3초 뒤에도 못 봄 | `volatile`, `synchronized` | [자바 동시성 03](../../java/concurrency/03-object-sharing)장 | 캐시와 JIT에 "공유한다"고 알린다 |
| 순서 | 91% (0, 0) | `volatile`, 락, `final` | [자바 동시성 03](../../java/concurrency/03-object-sharing)장 | 앞뒤 순서를 고정한다 |
| 셋 다 | | 불변 객체, 스레드 한정 | [자바 동시성 03](../../java/concurrency/03-object-sharing)장 3~4절 | 공유하지 않으면 깨질 것이 없다 |
| 거짓 공유 | 같은 라인 30% 손해 | 라인 간격 두기, `@Contended` | 이 장 4.3절 | 하드웨어의 공유를 끊는다 |

{{< callout type="warning" >}}
**세 문제의 공통 원인은 "공유한다고 말하지 않은 공유"다.** 런타임과 하드웨어는 단일 스레드 기준으로 최적화하고, 그 최적화는 전부 옳다. 여러 스레드가 보는 변수라고 알려 주는 것이 `volatile`과 락이고, 그 순간 최적화가 물러난다. 대신 값을 치른다. 6.1절의 `AtomicInteger`가 그 값이고, 얼마인지는 [08](../08-race-conditions-and-synchronization)장 7절에서 잰다. 가장 싼 해결은 공유하지 않는 것이다. 지역 변수는 스택에 있어서 처음부터 그 스레드만의 것이고, 불변 객체는 바뀌지 않아서 누가 봐도 같다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 프로세스 | 실행 중인 프로그램, 자기 주소 공간 | 격리를 산다. 1.8 ms, IPC |
| 메모리 구조 | 코드·데이터·힙은 하나, 스택은 스레드마다 | 스택이 스레드의 정체 |
| 스레드 | 스택 하나 + 실행 위치, 힙은 공유 | 공유를 산다. 26 µs, 72 ns |
| 만드는 비용 | 스레드 26 µs, 가상 8 µs, 프로세스 1.8 ms | 3 µs 일감은 풀에 (6 µs) |
| 개수의 천장 | 88 KB씩, 4,069개에서 실패 | OS가 프로세스당 4,096개 |
| 가상 스레드 | 1.6 KB씩, OS 스레드 37개 위에 10만 개 | 스택을 힙에 |
| 죽음 | 프로세스는 혼자 죽고 스레드는 같이 죽을 수 있다 | 종료 코드 139 vs 같은 힙 |
| 컨텍스트 스위칭 | PC와 레지스터를 저장하고 복원 | 스레드 1.5 µs, 프로세스는 TLB까지 |
| 스레드 과다 | 코어보다 많으면 차례만 기다린다 | 4,000개에 35% 손해 |
| 거짓 공유 | 다른 변수, 같은 128바이트 라인 | 30% 손해 |
| 여섯 상태 | 기다림이 셋: 시간, 신호, 락 | 덤프 읽기의 기본 |
| 원자성 | `count++`는 세 명령 | 48% 손실, 매번 다르다 |
| 가시성 | 말 안 하면 공유가 아니다 | 3초 뒤에도 못 봄 |
| 순서 | 적힌 순서 ≠ 실행 순서 | 91% (0, 0) |

{{< callout type="info" >}}
**용어 정리**
- **프로세스**: 실행 중인 프로그램의 인스턴스. 자기 주소 공간, 열린 파일, 스레드 하나 이상
- **주소 공간**: 프로세스가 보는 메모리. 프로세스마다 독립이라 서로 못 읽는다
- **IPC**: 프로세스 간 통신. 파이프, 소켓, 공유 메모리, 메시지 큐
- **스레드**: 실행의 단위. 자기 스택과 레지스터, 나머지는 프로세스와 공유
- **플랫폼 스레드 / 가상 스레드**: OS 스레드와 1:1인 자바 스레드 / JVM이 OS 스레드 위에 얹는 스레드
- **스레드 풀**: 만들어 둔 스레드에 일을 넘겨 재사용하는 것
- **컨텍스트 스위칭**: 코어가 스레드를 바꿀 때 상태를 저장하고 복원하는 것
- **TLB**: 주소 변환 캐시. 프로세스 전환 때 비운다
- **캐시 라인 / 거짓 공유**: 코어가 메모리를 가져오는 단위(128바이트) / 다른 변수가 같은 라인에 있어 생기는 경합
- **RUNNABLE / WAITING / TIMED_WAITING / BLOCKED**: 돌 수 있음 / 신호 대기 / 시간 대기 / 락 대기
- **경쟁 조건**: 결과가 스레드의 실행 순서에 달리는 것
- **원자적 연산**: 중간에 끼어들 수 없는 연산
- **가시성**: 한 스레드의 쓰기를 다른 스레드가 보는가
- **재배치**: 컴파일러와 코어가 명령 순서를 바꾸는 것
- **volatile**: 이 변수는 공유한다는 표시. 가시성과 순서를 보장
{{< /callout >}}
