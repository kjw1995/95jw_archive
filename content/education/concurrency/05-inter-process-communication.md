앞 장에서 프로세스는 격리를 산다고 했다. 격리의 값이 이 장이다. 서로의 메모리를 볼 수 없는 두 프로세스가 어떻게 협업하는가. 운영체제가 주는 답이 프로세스 간 통신(IPC)이고, 원리는 셋이다. 첫째, **IPC는 두 갈래다. 메모리를 같이 보거나, 커널에 맡기거나.** 공유 메모리는 커널을 안 거쳐 코어 사이의 캐시 속도로 주고받지만 동기화와 프로토콜이 내 책임이다. 파이프·큐·소켓은 커널이 복사하고 순서를 지키고 흐름을 조절해 주는 대신 커널을 두 번 지난다. 둘째, **IPC 수단은 속도와 범위를 맞바꾼다. 그리고 처리량은 방식이 아니라 버퍼가 정한다.** 지연은 같은 기계의 메모리에서 시작해 파이프, 소켓, 인터넷으로 갈수록 백 배씩 커지고, 처리량은 두 쪽이 서로를 몇 번 깨우느냐, 곧 버퍼 크기가 정한다. 소켓이 기본값이 된 이유는 빨라서가 아니라 어디든 닿아서다. 셋째, **스레드 풀은 스레드가 아니라 큐를 판다.** 워커를 재사용해 만드는 비용을 없애고, 큐가 몰려드는 요청을 받아 두고, 상한이 자원을 지킨다. 풀 크기는 감이 아니라 계산과 대기의 비율로 정한다. 이 PC(Apple M4 10코어, macOS, JDK 23)에서 JVM 프로세스 둘 사이에 공유 메모리·파이프·유닉스 소켓·TCP로 바이트 하나를 주고받는 왕복 시간과 256MB를 옮기는 시간을 재고, 프로세스 둘이 공유 메모리의 숫자 하나를 동시에 올리면 얼마를 잃는지 보고, 스레드 풀 크기를 바꿔 가며 같은 일의 시간을 재고, 상한 없는 풀이 어디서 죽는지 봤다.

## 1. IPC가 필요한 이유

### 1.1 격리의 대가

```text
프로세스 A            프로세스 B
┌────────────┐  ✗   ┌────────────┐
│ 주소 공간  │ ─X─  │ 주소 공간  │
└─────┬──────┘ 직접 └──────┬─────┘
      │      못 본다       │
      └───▶ 운영체제 IPC ◀──┘
```

| 격리가 막는 것 | 그래서 필요한 것 | 왜 |
|:-----------|:------------|:---|
| 다른 프로세스의 메모리 읽기 | 운영체제가 중개하는 통로 | 주소 0x1000이 서로 다른 물리 페이지 |
| 다른 프로세스의 변수 바꾸기 | 데이터를 복사하거나 같은 페이지를 매핑 | 한쪽의 버그가 다른 쪽을 못 깨뜨리게 |
| 서로의 존재를 아는 것 | 이름(파일 경로, 포트) | 프로세스 ID는 매번 바뀐다 |

운영체제는 한 프로세스가 다른 프로세스의 메모리를 읽거나 쓰지 못하게 막는다. [04](../04-concurrency-ingredients)장 1절에서 본 격리이고, 덕분에 하나가 죽어도 나머지는 산다. 그런데 협업도 못 한다. 웹 서버가 데이터베이스에 질의를 넘기고, 셸이 한 명령의 출력을 다음 명령에 넣고, 브라우저의 탭 프로세스가 화면 프로세스에 그림을 넘기는 일이 전부 프로세스를 넘는 통신이다. 격리를 유지한 채 통로를 여는 것이 IPC이고, 운영체제가 통로마다 다른 비용과 다른 보장을 붙여 둔다.

### 1.2 두 갈래

```text
[공유 메모리]  커널을 안 거친다
A ─쓰기─▶ [같은 물리 페이지] ◀─읽기─ B
          동기화는 내 몫

[메시지 전달]  커널이 중개한다
A ─send─▶ [커널 버퍼] ─recv─▶ B
          복사·순서·흐름 제어는 커널 몫
```

| 갈래 | 방식 | 데이터가 있는 곳 | 동기화 책임 | 왜 갈라지나 |
|:-----|:-----|:------------|:---------|:----------|
| 공유 메모리 | mmap, shm_open | 두 프로세스가 매핑한 같은 물리 페이지 | 나 | 커널이 끼지 않으니 커널이 지켜 주지도 않는다 |
| 메시지 전달 | 파이프, 메시지 큐, 소켓 | 커널 버퍼, 또는 네트워크 | 커널 | 복사할 때 순서를 매기고 가득 차면 세운다 |

첫째 원리다. 모든 IPC는 이 둘 중 하나다. 같은 물리 페이지를 두 프로세스의 주소 공간에 매핑하면 한쪽이 쓴 값이 다른 쪽에 바로 보이고 커널은 한 번 매핑해 준 뒤 빠진다. 대신 [04](../04-concurrency-ingredients)장 6절의 세 가지 문제가 프로세스 사이에서 그대로 생긴다. 커널에 맡기면 `send`와 `recv` 사이에 커널이 데이터를 자기 버퍼로 복사하고, 넣은 순서대로 꺼내 주고, 버퍼가 차면 보내는 쪽을 세운다. 그 대가로 커널을 두 번 지난다. 이 PC에서 JVM 프로세스 둘 사이에 바이트 하나를 보내고 답을 받는 왕복 시간과 256MB를 옮기는 시간을 수단마다 쟀다.

| 수단 | 왕복 | 256MB | 커널 버퍼 | 왜 |
|:-----|-----:|------:|:--------|:---|
| 공유 메모리 (mmap) | 281 ns | 40 ms | 없음 | 캐시 라인이 코어 사이를 오간다. 복사는 내 코드 |
| 파이프 | 5.4 µs | 44 ms | 64 KB 고정 | 커널 두 번, 64KB마다 상대를 깨운다 |
| 유닉스 도메인 소켓 | 6.5 µs | 132 ms | 8 KB 기본 | 8KB마다 깨운다 |
| 유닉스 도메인 소켓, 버퍼 1MB | 6.5 µs | 9 ms | 1 MB | 깨우는 횟수가 128분의 1 |
| TCP 루프백 | 15 µs | 20 ms | 128 KB, 자동으로 4 MB까지 | TCP 스택을 두 번 지나지만 버퍼가 크다 |
| 인터넷 ([03](../03-how-computers-work)장) | 6.7 ms | | | 케이블과 라우터 |

둘째 원리가 이 표에 있다. 왕복은 위에서 아래로 백 배씩 커진다. 공유 메모리의 281ns는 [03](../03-how-computers-work)장 1.2절에서 스레드 둘이 공유 변수로 주고받던 72ns의 네 배로, 프로세스가 달라도 메모리는 메모리라는 뜻이다. 커널을 지나는 순간 µs가 되고, 기계를 넘으면 ms다. 그런데 256MB 열을 보면 순서가 다르다. 유닉스 소켓이 버퍼를 8KB에서 1MB로 키우자 132ms에서 9ms로, 파이프보다 빨라졌다. 처리량을 정하는 것은 "커널을 거치느냐"가 아니라 **두 쪽이 서로를 몇 번 깨우느냐**다. 버퍼가 8KB면 256MB를 옮기는 동안 3만 번 깨우고, 1MB면 256번이다. 한 번 깨우는 데 [04](../04-concurrency-ingredients)장 4절의 전환 비용 1.5µs가 든다.

## 2. 공유 메모리 (Shared Memory)

### 2.1 같은 물리 페이지를 둘이 매핑한다

```text
프로세스 A            프로세스 B
가상 0x7f...          가상 0x9b...
     │                     │
     └──▶ 물리 페이지 ◀────┘
          하나
가상 주소는 달라도 같은 곳을 가리킨다
```

```java
// 두 JVM이 같은 파일을 매핑한다
var seg = ch.map(READ_WRITE, 0, size,
    Arena.global());
var INT = ValueLayout.JAVA_INT
    .varHandle();
// 보내는 쪽: 값을 쓰고 깃발을 올린다
INT.setVolatile(seg, 0L, round);
// 받는 쪽: 깃발이 오를 때까지 돈다
while ((int) INT.getVolatile(seg, 0L)
        != round)
    Thread.onSpinWait();
```

| 특성 | 공유 메모리 | 왜 |
|:-----|:---------|:---|
| 왕복 | 281 ns | 커널이 없다. 코어 A의 캐시 라인이 코어 B로 간다 |
| 256MB | 40 ms, 6.6 GB/s | 내 코드가 두 번 복사한다. 청크를 64KB에서 4MB로 키워도 같다 |
| 큰 데이터 | 복사 없이 자료 구조를 그대로 | 영상 프레임, 행렬, 버퍼 풀 |
| 동기화 | 전부 내 책임 | 커널이 순서도 흐름도 안 지켜 준다 |
| 범위 | 같은 기계뿐 | 물리 메모리를 나눠야 한다 |

두 프로세스가 같은 물리 페이지를 각자의 가상 주소 공간에 매핑한다. 가상 주소는 다르지만 같은 곳을 가리키니, A가 쓰면 B가 바로 본다. 위 코드가 이 장의 모든 실측에 쓴 공유 메모리다. 파일 하나를 두 JVM이 매핑하고, 정수 하나를 깃발 삼아 한쪽이 올리면 다른 쪽이 도는 동안 본다. 왕복 281ns는 커널 호출 하나보다 짧다. 그런데 256MB 처리량은 6.6GB/s로 유닉스 소켓의 4분의 1이다. 커널이 없으니 복사도 깨움도 순서도 전부 내가 짜야 하고, 위 실험의 프로토콜은 내가 짠 가장 단순한 것이다. 공유 메모리의 속도는 하드웨어가 아니라 그 위에 내가 짠 프로토콜이 정한다. 데이터베이스의 버퍼 풀이 여러 프로세스가 공유하는 페이지 캐시이고, 초저지연 메시징(LMAX Disruptor, Aeron)이 이 위에 링 버퍼를 짠 것이며, 레디스가 스냅샷을 뜰 때 `fork`로 부모의 페이지를 자식과 공유하는 것도 같은 원리다.

### 2.2 동기화는 내 몫이다

```java
// 두 프로세스가 각각 100만 번
LONG.set(seg, 8L,
    (long) LONG.get(seg, 8L) + 1);
// 결과 1,634,301. 18%가 사라졌다

LONG.getAndAdd(seg, 8L, 1L);
// 결과 2,000,000
```

| 프로세스 둘이 같은 숫자를 100만 번씩 | 결과 | 왜 |
|:---------------------------|-------:|:---|
| 읽고, 더하고, 쓰기 | 1,184,942 ~ 1,664,845 | 두 프로세스가 같은 값을 읽고 같은 값을 썼다. 돌릴 때마다 다르다 |
| 원자적 더하기 (`getAndAdd`) | 2,000,000 | 읽고 더하고 쓰기가 코어의 명령 하나 |

[04](../04-concurrency-ingredients)장 6.1절의 `count++`가 프로세스 사이에서 그대로 재현된다. 스레드가 아니라 프로세스인데도 같은 이유로 같은 만큼 잃는다. 메모리를 공유하면 문제도 공유한다. 커널이 끼지 않으니 락도 원자적 연산도 내가 골라 써야 하고, 그 도구가 파일 락, 프로세스 사이에서 쓰는 세마포어, 그리고 위처럼 공유 메모리 위의 원자적 명령이다. 어떤 도구를 언제 쓰는지는 [08](../08-race-conditions-and-synchronization)장이다.

{{< callout type="warning" >}}
**공유 메모리를 매핑했다고 끝이 아니다.** 두 프로세스가 같은 영역에 동시에 쓰는 순간 데이터가 깨지고, 한쪽이 죽으면 반쯤 쓴 데이터가 남는다. 커널이 해 주던 복사·순서·흐름 제어를 내가 다 짜야 한다. 실무에서 공유 메모리를 직접 쓰는 곳이 데이터베이스와 초저지연 메시징 정도인 이유이고, 그 밖에는 커널에 맡기는 쪽이 값싸다.
{{< /callout >}}

## 3. 파이프 (Pipe)

### 3.1 단방향 바이트 스트림

```text
A ─write─▶ [커널 버퍼 64 KB] ─read─▶ B
가득 차면 A가 선다, 비면 B가 선다
```

```java
var child = new ProcessBuilder(
        "python3", "-c",
        "import sys; ...")
    .start();
// 부모 → 자식: 자식의 stdin
try (var w = child.outputWriter()) {
    w.write("hello\n");
}
// 자식 → 부모: 자식의 stdout
try (var r = child.inputReader()) {
    r.lines().forEach(
        System.out::println);
}
```

| 특성 | 파이프 | 이 PC에서 | 왜 |
|:-----|:-----|:--------|:---|
| 방향 | 한쪽 | 양방향이면 둘 | 쓰기 끝과 읽기 끝이 하나씩 |
| 단위 | 바이트 스트림 | | 메시지 경계가 없다. 줄바꿈 등을 내가 정한다 |
| 버퍼 | 커널 안 64 KB | 65,536바이트째에서 쓰기가 막힌다 | 가득 차면 쓰는 쪽이 자고, 비면 읽는 쪽이 잔다 |
| 왕복 | | 5.4 µs | 커널을 두 번 지난다 |
| 256MB | | 44 ms | 64KB마다 4,096번 상대를 깨운다 |
| 관계 | 부모와 자식 | `ProcessBuilder` | 파일 디스크립터를 물려받는다 |

파이프는 한 프로세스의 출력을 다른 프로세스의 입력으로 흘리는 단방향 바이트 스트림이다. 커널이 64KB짜리 버퍼를 만들고 한쪽에 쓰기 끝, 다른 쪽에 읽기 끝을 준다. 이 PC에서 쓰기 끝에 계속 쓰니 65,536바이트째에서 막혔다. 버퍼가 차면 쓰는 쪽이 자동으로 서고 읽는 쪽이 비우면 깨어난다. 이것이 흐름 제어이고, 파이프가 커널에 맡긴 덕에 공짜로 얻는 것이다. 위 코드의 `ProcessBuilder`가 자식 프로세스를 띄우면서 파이프를 셋(stdin, stdout, stderr) 만들어 잇고, [04](../04-concurrency-ingredients)장 1.3절과 [03](../03-how-computers-work)장 1.2절의 프로세스 실험이 전부 이 파이프로 자식과 이야기했다.

### 3.2 익명 파이프와 명명 파이프

```bash
ps -ef | grep java | wc -l  # 익명
mkfifo /tmp/chan            # 명명
echo hello > /tmp/chan      # 터미널 1
cat /tmp/chan               # 터미널 2
```

| 구분 | 익명 파이프 | 명명 파이프 (FIFO) | 왜 |
|:-----|:---------|:---------------|:---|
| 이름 | 없음, 디스크립터만 | 파일 시스템의 경로 | 남남인 프로세스가 만나려면 이름이 필요하다 |
| 관계 | 부모와 자식 | 아무 프로세스 | 디스크립터는 물려받는 것뿐 |
| 수명 | 양쪽이 닫으면 사라진다 | 지울 때까지 | 파일이니까 |
| 쓰임 | 셸 파이프라인 | 데몬과 클라이언트 | `cat | grep`이 익명, `/tmp/chan`이 명명 |

셸의 `|`가 익명 파이프다. 셸이 두 프로세스를 띄우며 파이프의 양 끝을 하나씩 물려준다. 남남인 두 프로세스가 만나려면 이름이 필요하고, 파일 시스템에 경로를 하나 만들어 그 이름으로 여는 것이 명명 파이프다. 열면 이름만 다르지 속은 같은 커널 버퍼다.

{{< callout type="info" >}}
**파이프가 깨지면 신호가 온다.** 읽는 쪽이 먼저 닫힌 뒤에도 쓰면 운영체제가 쓰는 프로세스에 `SIGPIPE`를 보내 죽인다. `yes | head`가 끝나는 이유다. `head`가 열 줄을 읽고 닫는 순간 `yes`가 그 신호로 죽는다. 자바에서는 `IOException: Broken pipe`로 나타나고, 자식 프로세스의 출력을 끝까지 안 읽고 닫을 때 흔히 만난다.
{{< /callout >}}

## 4. 메시지 큐 (Message Queue)

### 4.1 넣어 두면 나중에 누군가 가져간다

```text
P1 ─┐                ┌─▶ C1
P2 ─┼─▶ [m1][m2][m3] ┼─▶ C2
P3 ─┘   먼저 넣은 순  └─▶ C3
보내는 쪽과 받는 쪽이 같은 시각에
살아 있을 필요가 없다
```

| 비교 | 파이프 | 메시지 큐 | 왜 |
|:-----|:-----|:-------|:---|
| 단위 | 바이트 | 메시지 하나 | 경계를 큐가 지킨다 |
| 시간 | 양쪽이 동시에 | 넣어 두고 나중에 | 큐가 메시지를 들고 있다 |
| 관계 | 1:1 | N:M | 이름 하나에 여럿이 붙는다 |
| 결합 | 상대를 알아야 | 큐 이름만 알면 | 상대가 바뀌어도 나는 그대로 |
| 실물 | 셸, `ProcessBuilder` | POSIX mq, Kafka, RabbitMQ, SQS, `BlockingQueue` | 층이 다 다르다 |

메시지 큐는 이름 붙은 큐에 메시지를 넣고 꺼내는 IPC다. 파이프와 다른 점은 둘이다. 바이트가 아니라 메시지 단위라 경계를 내가 안 그어도 되고, 보내는 쪽과 받는 쪽이 같은 시각에 살아 있을 필요가 없다. 메시지는 큐에 쌓여 기다린다. 이 두 성질이 느슨한 결합을 만든다. 주문 서비스는 큐에 넣고 끝이고, 결제 서비스가 언제 몇 대가 꺼내 가든 주문 서비스의 코드는 그대로다. 같은 "큐"라는 말이 운영체제의 POSIX 큐에도, 서버 수백 대를 잇는 카프카에도, 한 JVM 안의 `BlockingQueue`에도 쓰이는데 원리는 같다.

### 4.2 이 PC에서 재 보기

```java
var q = new ArrayBlockingQueue
    <String>(1024);
// 생산자: 가득 차면 여기서 선다
q.put("order-" + i);
// 소비자: 비어 있으면 여기서 선다
var msg = q.take();
```

| 큐 (한 JVM 안, 스레드 사이) | 메시지 하나 | 초당 | 왜 |
|:-----------------------|--------:|--------:|:---|
| `SynchronousQueue` | 1,932 ns | 52만 | 버퍼가 없다. 넣을 때마다 상대를 깨운다 |
| `ArrayBlockingQueue(1024)` | 50~60 ns | 1,600만~2,000만 | 배열에 쌓아 두고 가끔 깨운다 |
| `LinkedBlockingQueue` | 55~100 ns | 1,000만~1,800만 | 노드를 만든다 |
| `LinkedTransferQueue` | 35~40 ns | 2,400만~2,800만 | 락 없이 넘긴다 |
| `ArrayBlockingQueue`, 생산·소비 4:4 | 26 ns | 3,700만 | 여덟이 나눠 든다 |

| 용량 1,024인 큐에 느린 소비자 | 결과 | 왜 |
|:----------------------|:-----|:---|
| 생산자가 5,000개를 한꺼번에 넣으려 하면 | 1,025번째에서 선다 | 큐가 차면 `put`이 막힌다 |
| 소비자가 다 꺼낼 때까지 | 5,000개 전부 도착 | 잃는 것이 없다. 대신 생산자가 기다렸다 |

1절 표의 통신 사다리에서 큐는 가장 위, 스레드 사이의 3.7µs에 해당한다. 그 3.7µs는 `SynchronousQueue`처럼 넣을 때마다 상대를 깨우는 비용이고, 배열에 쌓아 두고 가끔 깨우면 50ns까지 내려간다. 파이프의 64KB 버퍼와 같은 이야기다. 둘째 표가 큐의 진짜 쓸모다. 용량이 있는 큐는 소비자가 느리면 생산자를 세운다. 이것이 배압(backpressure)이고, 큐가 스파이크를 흡수하되 메모리를 무한히 먹지는 않게 하는 장치다. 7절의 스레드 풀이 정확히 이 큐 위에 서 있다. 생산자-소비자 패턴의 함정은 [09](../09-deadlock-and-starvation)장 5절, `BlockingQueue`의 네 가지 연산은 [자바 동시성 05](../../java/concurrency/05-building-blocks)장 3절이다.

## 5. 소켓 (Socket)

### 5.1 같은 API로 옆 프로세스와 지구 반대편

```text
같은 기계   A ◀─ /tmp/app.sock ─▶ B
같은 기계   A ◀─ 127.0.0.1:9000 ─▶ B
다른 기계   A ◀──── 인터넷 ────▶ B
쓰는 코드는 같다
```

```java
var addr = UnixDomainSocketAddress
    .of("/tmp/app.sock");
var server = ServerSocketChannel
    .open(StandardProtocolFamily.UNIX);
server.bind(addr);
var ch = server.accept();
// TCP면 open()과
// new InetSocketAddress(host, port)
```

| 종류 | 신뢰성 | 순서 | 범위 | 이 PC에서 | 왜 |
|:-----|:-----|:----|:----|:--------|:---|
| TCP | 보장 | 보장 | 어디든 | 왕복 15 µs, 256MB 20 ms | 스택이 두껍지만 버퍼가 4MB까지 자란다 |
| 유닉스 도메인 | 보장 | 보장 | 같은 기계 | 왕복 6.5 µs, 256MB 132 ms → 버퍼 1MB면 9 ms | TCP 스택이 없다. 기본 버퍼 8KB가 발목 |
| UDP | 없음 | 없음 | 어디든 | 받는 쪽이 느리면 82%를 버린다 | 봉투를 던질 뿐 기다리지 않는다 |

소켓은 양방향이고 네트워크를 넘을 수 있는 유일한 IPC다. 같은 기계의 두 프로세스든 다른 대륙의 서버든 코드가 같다. 그래서 마이크로서비스 시대의 기본값이 됐다. 가장 빨라서가 아니라 범위가 가장 넓어서다. 같은 기계 안이라면 유닉스 도메인 소켓이 TCP 루프백보다 왕복이 절반이다. IP도 TCP도 없이 커널 버퍼만 있어서다. 도커 데몬, Nginx와 PHP-FPM, PostgreSQL의 로컬 접속이 `unix:///var/run/...` 경로로 이것을 쓴다. 단, 이 PC의 기본 버퍼가 8KB라 처리량은 옵션으로 버퍼를 키워야 나온다. 1절의 교훈이다. TCP의 속과 순서 번호는 [네트워크 24](../../network/24-tcp-structure)장, 자바 소켓 API는 [자바 기초 16](../../java/basics/16-networking)장 2절이다.

### 5.2 신뢰성은 흐름 제어의 다른 이름이다

| 1KB짜리 5,000개를 받는 쪽이 하나에 100µs 걸릴 때 | 보내는 데 | 도착 | 왜 |
|:--------------------------------------|-------:|-----:|:---|
| UDP | 19 ms | 876개, 82.5% 손실 | 수신 버퍼 787KB가 차면 커널이 나머지를 버린다 |
| TCP | 469 ms | 5,000개 전부 | 받는 쪽이 느리면 보내는 쪽을 세운다 |

받는 쪽이 따라오지 못할 때 무엇을 하느냐가 TCP와 UDP의 차이다. UDP는 보내는 쪽이 19ms 만에 다 던지고 끝났고, 커널의 수신 버퍼에 못 들어간 4,124개는 조용히 사라졌다. 같은 기계 안에서, 케이블 하나 없이 그렇다. TCP는 보내는 쪽이 469ms 동안 서 있었다. 받는 쪽의 버퍼가 비는 속도에 맞춰 보내는 쪽을 세우는 것이 흐름 제어이고, 파이프의 64KB와 큐의 1,024가 하던 일이다. 받는 쪽이 충분히 빠르면(10만 개를 한꺼번에 던졌을 때) UDP도 하나도 안 잃었다. UDP가 나쁜 것이 아니라 "느린 쪽을 기다리지 않는다"는 선택이고, 그 선택이 맞는 곳(DNS, 영상, 게임)이 있다. UDP의 구조는 [네트워크 27](../../network/27-udp-structure)장이다.

|:-----|:---|:---|

책의 관찰대로 편의성, 확장성, 성능을 합치면 소켓이 가장 무난하다. 표의 왕복 열에서 소켓은 가장 느린 축인데도 그렇다. 지연 15µs는 대부분의 요청 처리 시간(ms)에 묻히고, 그 대신 프로세스가 같은 기계에 있든 옆 서버에 있든 컨테이너 안에 있든 코드가 같다. [01](../01-what-is-concurrency)장 4절의 수평 확장이 소켓 위에서만 되는 이유다. 지연이 정말로 전부인 곳에서만 공유 메모리로 내려간다.

## 7. 스레드 풀 (Thread Pool)

### 7.1 만드는 비용과 큐

```text
main ─submit─▶ [T1][T2][T3]...  큐
                  │ take
        ┌─────────┼─────────┐
        ▼         ▼         ▼
     워커 1     워커 2     워커 3
     끝나면 큐에서 다음 작업을 꺼낸다
```

| 제곱근 1,000번짜리 일감 ([04](../04-concurrency-ingredients)장) | 하나당 | 왜 |
|:---------------------------------------|------:|:---|
| 일감마다 새 스레드 | 25 µs | 일(3 µs)의 여덟 배가 만드는 데 |
| 풀에 넘김 | 6 µs | 넘기고 받는 비용만 |

| 풀이 주는 것 | 뜻 | 이 장의 실물 | 왜 |
|:----------|:---|:----------|:---|
| 재사용 | 만들고 없애는 비용이 없다 | 25 → 6 µs | 스레드는 26µs, 넘기기는 6µs |
| 버퍼 | 몰려온 요청을 큐가 받아 둔다 | 5,000개 중 4,900개가 큐에 | 4절의 큐 |
| 상한 | 동시에 도는 스레드 수를 정한다 | 상한 없으면 4,070개에서 죽는다 | [04](../04-concurrency-ingredients)장 2.4절의 천장 |
| 단순함 | 호출자는 넘기고 끝 | `pool.submit(task)` | 스레드 관리가 코드에서 사라진다 |

셋째 원리다. 스레드 풀은 미리 만든 워커 스레드 몇 개와 작업 큐 하나다. 호출자는 큐에 작업을 넣고, 워커는 큐에서 꺼내 실행하고 끝나면 다음 것을 꺼낸다. [04](../04-concurrency-ingredients)장에서 3µs짜리 일에 스레드를 만들면 25µs가 든다고 했고, 풀은 그 비용을 없앤다. 그런데 풀의 핵심은 스레드 재사용이 아니라 **큐**다. 요청이 한꺼번에 5,000개 와도 워커는 100개뿐이고 나머지 4,900개는 큐에서 차례를 기다린다. 4절에서 본 배압이 여기서 서버를 지킨다.

### 7.2 풀 크기는 계산과 대기의 비율이 정한다

```java
// 코어 10, 계산 1ms + 대기 9ms
int size = cores * (1 + 9 / 1); // 100
try (var pool = Executors
        .newFixedThreadPool(size)) {
    for (var t : tasks)
        pool.submit(t);
}
```

| 계산 1ms + 대기 9ms인 작업 1,000개 | 걸린 시간 | 왜 |
|:---------------------------|--------:|:---|
| 풀 10 (코어 수) | 1,273 ms | 열 개가 각자 9ms씩 잔다. 코어가 논다 |
| 풀 50 | 254 ms | 다섯 배 |
| 풀 100 (코어 × (1 + 9/1)) | 163 ms | 계산 1,000ms를 코어 6.8개가 나눈 값. 여기가 바닥 |
| 풀 200 | 162 ms | 더 줘도 계산이 병목 |
| 가상 스레드 | 165 ms | 크기를 안 정해도 같은 바닥 |

| 계산만 10ms인 작업 1,000개 | 걸린 시간 | 왜 |
|:--------------------|--------:|:---|
| 풀 10 | 1,556 ms | 코어 열 개가 꽉 찼다 |
| 풀 100 | 1,501 ms | 스레드를 더 줘도 코어는 열 개 |

| 작업의 성격 | 풀 크기 | 왜 |
|:---------|:------|:---|
| 계산만 | 코어 수 | 스레드가 코어보다 많으면 차례만 기다린다 ([04](../04-concurrency-ingredients)장 4.2절) |
| 계산과 대기가 섞임 | 코어 수 × (1 + 대기 시간 ÷ 계산 시간) | 자는 스레드만큼 더 있어야 코어가 찬다 |
| 대기가 대부분 | 위 공식이 수백이 된다 | 그때는 가상 스레드 (7.4절) |

공식이 실측과 맞는다. 계산 1ms에 대기 9ms인 작업은 스레드 하나가 시간의 90%를 자므로, 코어 열 개를 채우려면 스레드가 100개 필요하다. 100개에서 163ms로 바닥에 닿았고, 그 바닥은 계산 1,000ms를 실효 코어 6.8개로 나눈 값이다. 계산만 하는 작업은 풀 10이나 100이나 같다. 풀 크기는 감으로 정하는 것이 아니라 작업 하나가 계산하는 시간과 기다리는 시간을 재서 정한다. 어떤 작업이 CPU 바운드이고 I/O 바운드인지는 [06](../06-multitasking)장 2절이다.

### 7.3 상한이 없으면 어디서 죽나

```java
new ThreadPoolExecutor(
    10, 100,            // core, max
    60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadPoolExecutor
        .CallerRunsPolicy());
```

| 1초짜리 작업 5,000개를 한꺼번에 | 결과 | 왜 |
|:----------------------|:-----|:---|
| `newCachedThreadPool` | 4,070개째 `OutOfMemoryError`, 스레드 4,071개 | 노는 워커가 없으면 계속 만든다. 상한이 OS의 천장 |
| `newFixedThreadPool(100)` | 5,247 ms (100ms 작업), 큐 최대 4,900 | 스레드 100개, 큐는 무한 |
| 최대 100, 큐 1,000, 거절 정책 | 3,900개 거절, 1,154 ms | 큐도 상한이 있다. 넘치면 호출자에게 돌려준다 |

상한이 없는 풀은 요청이 몰리면 [04](../04-concurrency-ingredients)장 2.4절의 천장에 부딪힌다. 이 PC에서 4,070개째에서 `OutOfMemoryError`였고, 서버라면 그 순간 요청 하나가 아니라 프로세스 전체가 위험하다. 고정 풀은 스레드는 100개로 막지만 큐가 무한이라 메모리가 큐로 샌다. 큐에도 상한을 두면 넘친 요청을 어떻게 할지 정해야 하고, 그것이 거절 정책이다. 예외로 돌려주거나, 버리거나, 호출자 스레드가 직접 실행해 호출자를 늦추거나(`CallerRunsPolicy`, 가장 흔한 선택). 세 숫자를 전부 내가 정하는 것이 운영 가능한 풀이다.

{{< callout type="warning" >}}
**`newCachedThreadPool`은 상한이 없다.** 노는 워커가 없으면 스레드를 새로 만들고, 그 상한이 운영체제의 천장이다. 이 PC에서는 4,070개, 리눅스 서버에서는 메모리가 먼저 바닥난다. 실무에서는 `ThreadPoolExecutor`를 직접 만들어 스레드 수, 큐 크기, 거절 정책 셋을 명시한다. 셋 중 하나라도 무한이면 그 하나가 서버의 약점이다.
{{< /callout >}}

### 7.4 가상 스레드와의 관계

```java
// JDK 21+. 크기를 정하지 않는다
var pool = Executors
    .newVirtualThreadPerTaskExecutor();
try (pool) {
    for (var req : requests)
        pool.submit(() -> handle(req));
}
```

| 구분 | 플랫폼 스레드 풀 | 가상 스레드 | 왜 |
|:-----|:------------|:---------|:---|
| 크기 | 내가 정한다 | 작업마다 하나 | 1.6KB짜리라 10만 개도 된다 ([04](../04-concurrency-ingredients)장 2.4절) |
| 대기가 많은 작업 | 공식대로 수백 개 | 그냥 만든다 | 자는 동안 OS 스레드를 놓는다 |
| 계산이 많은 작업 | 코어 수 | 이득 없음 | 코어는 여전히 열 개 |
| 이 PC에서 | 풀 100에 163 ms | 165 ms | 같은 바닥에 크기 고민 없이 |

가상 스레드가 흔든 것은 "대기가 많으면 풀을 크게"라는 전제다. 스레드가 1.6KB면 작업마다 하나씩 만들어도 되고, 자는 동안 OS 스레드를 내놓으니 상한 걱정도 없다. 7.2절 표에서 크기를 안 정한 가상 스레드가 최적 크기의 풀과 같은 165ms였다. 그래서 분업이 바뀐다. 대기가 많은 일은 가상 스레드에, 계산이 많은 일은 코어 수만큼의 플랫폼 스레드 풀에. 가상 스레드가 어떻게 OS 스레드 위에 얹히는지는 [12](../12-asynchronous-communication)장 6절, 자바의 `Executor` 계열은 [자바 기초 13](../../java/basics/13-thread)장 7절이다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| IPC | 격리를 지키며 여는 통로 | 프로세스는 서로의 메모리를 못 본다 |
| 두 갈래 | 같은 페이지를 보거나, 커널에 맡기거나 | 동기화 책임이 나에게 있느냐 커널에 있느냐 |
| 통신 사다리 | 281 ns → 5 µs → 15 µs → 6.7 ms | 범위가 넓을수록 느리다 |
| 처리량 | 방식이 아니라 버퍼 | 유닉스 소켓 8KB 132 ms → 1MB 9 ms |
| 공유 메모리 | 가장 빠른 왕복, 전부 내 책임 | 프로세스 둘의 `++`가 18% 사라진다 |
| 파이프 | 단방향 바이트 스트림, 64KB | 가득 차면 쓰는 쪽이 선다 |
| 메시지 큐 | 넣어 두면 나중에, N:M | 1,025번째에서 생산자를 세운다 |
| 소켓 | 어디든 닿는 양방향 | 같은 기계면 유닉스 도메인이 왕복 절반 |
| UDP와 TCP | 느린 쪽을 버리느냐 기다리느냐 | 82% 손실 vs 469 ms 대기 |
| 소켓이 기본값 | 빨라서가 아니라 범위 | 코드가 같다 |
| 스레드 풀 | 워커 재사용 + 큐 + 상한 | 25 → 6 µs, 큐 4,900, 상한 |
| 풀 크기 | 코어 × (1 + 대기 ÷ 계산) | 100에서 바닥 163 ms |
| 상한 없는 풀 | OS 천장에서 죽는다 | 4,070개째 OOM |
| 가상 스레드 | 크기 고민 없이 같은 바닥 | 대기 많은 일은 가상, 계산은 풀 |

{{< callout type="info" >}}
**용어 정리**
- **IPC**: 프로세스 간 통신. 격리된 프로세스가 데이터를 주고받는 운영체제의 통로
- **공유 메모리**: 같은 물리 페이지를 두 프로세스가 매핑. 커널을 안 거친다
- **메시지 전달**: 커널이 복사하고 순서와 흐름을 맡는 방식. 파이프, 큐, 소켓
- **mmap**: 파일이나 메모리를 주소 공간에 매핑하는 호출
- **파이프 / 명명 파이프**: 단방향 커널 버퍼. 이름이 없으면 부모 자식, 있으면 아무나
- **SIGPIPE**: 읽는 쪽이 닫힌 파이프에 쓰면 오는 신호
- **메시지 큐**: 메시지 단위, 비동기, N:M의 이름 붙은 큐
- **배압(backpressure)**: 받는 쪽이 느리면 보내는 쪽을 세우는 것. 파이프, 큐, TCP가 한다
- **소켓**: 양방향, 네트워크를 넘는 IPC. TCP, UDP, 유닉스 도메인
- **유닉스 도메인 소켓**: 같은 기계 전용 소켓. 파일 경로가 주소
- **흐름 제어**: 받는 쪽의 속도에 보내는 쪽을 맞추는 것. TCP는 하고 UDP는 안 한다
- **스레드 풀**: 워커 스레드 묶음 + 작업 큐
- **워커 / 작업 큐**: 큐에서 꺼내 실행하는 스레드 / 실행을 기다리는 작업의 줄
- **거절 정책**: 큐도 찼을 때 새 작업을 어떻게 할지. 예외, 버림, 호출자가 실행
- **CPU 바운드 / I/O 바운드**: 계산이 병목 / 대기가 병목. 풀 크기 공식이 갈린다
{{< /callout >}}
