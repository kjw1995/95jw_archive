앞 장의 동기화는 틀린 값을 막는다. 대신 새 문제를 부른다. 값이 틀리는 게 아니라 **값이 안 나오는** 문제다. 원리는 셋이다. 첫째, **동기화는 안전을 사고 활성을 판다.** 락을 걸수록 나쁜 일은 안 일어나지만 좋은 일이 끝내 일어난다는 보장은 약해진다. 서로가 서로를 기다려 멈추는 교착, 바쁘게 움직이는데 진행은 없는 라이브락, 남들은 도는데 하나만 굶는 기아가 그 값이다. 둘째, **교착은 네 조건의 곱이고, 하나만 깨면 된다. 실무의 답은 순서다.** 상호 배제, 점유와 대기, 비선점, 순환 대기가 전부 성립해야 교착이고, 모든 스레드가 락을 같은 순서로 잡으면 순환이 생길 수 없다. 셋째, **누가 굶느냐는 관계가 아니라 정책이 정한다.** 같은 스레드들, 같은 일인데 락이 불공정하면 하나가 16배를 가져가고, 공정하면 똑같이 나눈다. 리더를 우대하면 라이터가 굶고 라이터가 끼어들면 리더가 굶는다. 정책을 고르는 것이 설계다. 이 PC(Apple M4 10코어, JDK 23)에서 락 순서를 엇갈리게 잡은 두 스레드가 몇 번 만에 멈추는지 열 번 재고 JVM이 그 교착을 어떻게 찾아내는지 보고, 순서를 맞추면 안 멈추는지, 타임아웃으로 물러나면 얼마를 치르는지 재고, 서로 양보만 하는 두 스레드가 1초에 몇 번 양보하고 몇 번 먹는지 세고, 불공정한 락과 공정한 락이 스레드 열 개에 자원을 어떻게 나누는지, 교과서의 리더-라이터 락이 라이터를 어떻게 굶기는지 봤다.

## 1. 동기화가 부르는 새로운 문제

| 멈춤의 얼굴 | 뜻 | 겉모습 | 이 PC에서 | 왜 |
|:---------|:---|:-----|:--------|:---|
| 교착 (deadlock) | 서로 상대의 자원을 기다리며 멈춘다 | 조용하다. CPU 0% | 열 번 중 열 번, 558번 만에 | 순환 대기 |
| 라이브락 (livelock) | 서로 반응만 하고 진행이 없다 | 바쁘다. CPU 100% | 1초에 2,000만 번 양보, 식사 0 | 같은 타이밍의 양보 |
| 기아 (starvation) | 하나가 자원을 못 받는다 | 남들은 돈다 | 락 획득 1,873번 vs 30,271번 | 불공정한 정책 |

경쟁 조건을 막으려고 락을 걸면 이번에는 락이 만드는 정체가 문제가 된다. 셋의 공통점은 맡긴 일이 끝나지 않는다는 것이다. [08](../08-race-conditions-and-synchronization)장의 경쟁 조건이 "나쁜 일이 일어났다"라면 이 장의 셋은 "좋은 일이 안 일어난다"이고, 앞을 안전성(safety), 뒤를 활성(liveness)이라 부른다.

{{< callout type="info" >}}
**안전성과 활성은 자주 상충한다.** 안전을 위해 락을 더 걸수록, 더 넓게 걸수록 활성은 위험해진다. 락 하나면 교착이 없지만 락이 둘이면 순서가 생기고, 락을 오래 쥘수록 뒤에 선 스레드가 굶는다. 그래서 동기화 설계는 안전을 확보한 뒤 활성을 잃지 않았는지 다시 묻는 두 단계다. 첫째 원리다.
{{< /callout >}}

## 2. 교착 상태

### 2.1 엇갈린 순서가 만드는 순환

```text
A: 락1 ✔ ──▶ 락2 ? (B가 쥐고 있다)
B: 락2 ✔ ──▶ 락1 ? (A가 쥐고 있다)
A ─기다림─▶ B ─기다림─▶ A   순환
```

```java
// 스레드 A: 락1 → 락2
synchronized (lock1) {
    synchronized (lock2) { transfer(); }
}
// 스레드 B: 락2 → 락1 (엇갈림)
synchronized (lock2) {
    synchronized (lock1) { transfer(); }
}
```

| 두 스레드가 각각 이체 10만 번 | 결과 | 왜 |
|:--------------------|:-----|:---|
| A는 락1→락2, B는 락2→락1 | 열 번 중 열 번 교착. 평균 558번 만에 (115~215번도) | 둘이 각자 첫 락을 쥔 순간이 한 번만 겹치면 끝 |
| 둘 다 락1→락2 | 20만 번 완료, 44 ms | 순환이 생길 수 없다 |

교착은 둘 이상의 작업이 각자 상대가 쥔 자원을 기다리며 영원히 멈추는 것이다. 가장 흔한 모양이 위 코드다. A는 락1을 쥐고 락2를 기다리고, B는 락2를 쥐고 락1을 기다린다. 둘 다 상대가 놓아 주기를 기다리니 아무도 못 움직인다. 이 PC에서 열 번 돌려 열 번 멈췄고, 빠르면 115번째 이체에서 멈췄다. 조건은 단순하다. A가 락1을 쥐고 락2를 잡기 전 그 짧은 틈에 B가 락2를 쥐면 된다. 20만 번 중 한 번이면 충분하고, 그 한 번은 반드시 온다. 순서를 맞추자 20만 번이 44ms에 끝났다.

```java
var mx = ManagementFactory
    .getThreadMXBean();
long[] ids = mx.findDeadlockedThreads();
// A BLOCKED on Object held by B
// B BLOCKED on Object held by A
```

교착은 조용하다. CPU는 0%이고 스레드는 [04](../04-concurrency-ingredients)장 5절의 `BLOCKED` 상태로 영원히 서 있다. 그래서 알아채기는 오히려 쉽다. JVM은 대기 그래프의 순환을 찾아 주고, 위 출력이 이 PC에서 실제로 찾아낸 것이다. A는 B가 쥔 객체를, B는 A가 쥔 객체를 기다린다. 운영 중인 서버의 스레드 덤프에서 `BLOCKED`가 짝을 이루고 있으면 이것이다.

### 2.2 네 조건

| 조건 | 뜻 | 깨는 법 | 왜 깨지나 |
|:-----|:---|:------|:-------|
| 상호 배제 | 자원을 한 번에 하나만 쥔다 | 읽기 전용, 불변, 복사 | 쥘 것이 없으면 기다릴 것도 없다 |
| 점유와 대기 | 쥔 채로 다른 것을 기다린다 | 필요한 락을 한꺼번에 잡거나 아무것도 안 쥔 채 기다린다 | 쥔 것이 없으면 남을 막지 않는다 |
| 비선점 | 남이 쥔 것을 뺏을 수 없다 | 타임아웃 뒤 스스로 놓는다 | 기다림이 유한해진다 |
| 순환 대기 | 기다림이 원을 이룬다 | **락 순서를 전역에서 통일** | 순서가 있으면 원이 안 생긴다 |

둘째 원리다. 교착은 코프먼(Coffman)의 네 조건이 **전부** 성립할 때만 생긴다. 뒤집으면 하나만 깨면 된다. 첫 두 조건은 자원의 성질이라 바꾸기 어렵고, 셋째는 값이 있다. 넷째가 실무의 답이다. 모든 스레드가 락을 같은 순서로 잡으면 "A가 B를 기다리고 B가 A를 기다린다"가 성립할 수 없다. 두 계좌 사이의 이체라면 계좌 번호가 작은 쪽을 먼저 잡는다. 어느 이체가 어느 방향이든 순서는 같다. [08](../08-race-conditions-and-synchronization)장 4절의 `finally` 규칙과 함께 락의 두 규칙이다.

### 2.3 예방, 회피, 탐지

```java
lock1.lock();
try {
    if (lock2.tryLock(10,
            TimeUnit.MILLISECONDS)) {
        try { transfer(); }
        finally { lock2.unlock(); }
        return;
    }
} finally { lock1.unlock(); }
// 못 잡으면 둘 다 놓고 잠깐 뒤 재시도
```

| 전략 | 하는 일 | 이 PC에서 | 값 | 왜 |
|:-----|:------|:--------|:---|:---|
| 예방 | 조건 하나를 애초에 없앤다. 락 순서 통일 | 20만 번 44 ms | 거의 없음 | 설계 규칙 하나 |
| 예방 | 타임아웃으로 비선점을 깬다 | 20만 번 완료, 575번 물러남, 5,338 ms | 120배 느리다 | 물러날 때마다 10 ms를 기다린다 |
| 회피 | 요청마다 안전한지 미리 검사 (은행원 알고리즘) | | 매 요청의 검사 | 실무에서 드물다 |
| 탐지·복구 | 일단 두고 순환을 찾아 한쪽을 죽인다 | `findDeadlockedThreads` | 희생자와 재시도 | 데이터베이스의 방식 |

엇갈린 순서를 그대로 두고 둘째 락을 `tryLock`으로 잡게 했다. 10ms 안에 못 잡으면 첫 락도 놓고 잠깐 뒤 다시 시도한다. 교착은 사라졌지만 575번 물러났고, 물러날 때마다 10ms를 기다리느라 44ms짜리 일이 5.3초가 됐다. 비선점을 깨는 것은 교착을 재시도로 바꾸는 것이고, 재시도는 공짜가 아니다. 그리고 재시도의 타이밍이 겹치면 3절의 라이브락이 된다.

{{< callout type="info" >}}
**데이터베이스는 탐지·복구를 쓴다.** 두 트랜잭션이 서로의 행 락을 기다리면 DB가 대기 그래프에서 순환을 찾아 한쪽을 희생자로 골라 롤백한다. PostgreSQL의 `deadlock detected`, InnoDB의 자동 감지가 그것이다. 애플리케이션 쪽의 의무는 그 예외를 잡아 **재시도**하는 것이고, 재시도 안에서 또 같은 순서로 락을 잡으면 또 교착이다. 트랜잭션 안에서도 행을 건드리는 순서를 통일하는 것이 정석이다.
{{< /callout >}}

## 3. 라이브락

```text
좁은 복도, 마주친 둘
A →       ← B    마주침
A ↖       ↗ B    같은 쪽으로 비킴
A ↗       ↖ B    또 같은 쪽으로
… 움직임은 있는데 진행은 0
```

```java
// 둘 다 예의 바르다
while (hungry) {
    if (spoon.owner != this) continue;
    if (other.hungry) { // "먼저 드세요"
        spoon.owner = other;
        continue;
    }
    eat(); hungry = false;
}
```

| 숟가락 하나, 배고픈 둘, 1초 | 식사 | 양보 | 왜 |
|:-------------------------|----:|-----:|:---|
| 둘 다 상대가 배고프면 양보 | 0번 | 20,265,067번 | 받자마자 돌려준다. 영원히 |
| A만 양보 | 각 1번 | 1번 | 대칭이 깨지면 끝난다 |
| 둘 다 양보하되 무작위로 조금 기다림 | 각 1번 | 29번 | 타이밍이 어긋나는 순간 하나가 먹는다 |

라이브락은 작업들이 멈추지는 않는데 서로의 동작에 반응만 하느라 진행이 없는 상태다. 교착은 조용해서 찾기 쉽지만 라이브락은 CPU를 100% 쓰며 바쁘니 살아 있는 것처럼 보인다. 위 표의 첫 줄이 그것이다. 두 스레드가 1초에 2,000만 번 숟가락을 주고받았고 아무도 먹지 못했다. 2.3절의 타임아웃 재시도가 똑같은 모양이 될 수 있다. 둘이 완벽히 같은 타이밍에 물러나고 같은 타이밍에 다시 잡으면 이 짓을 무한히 반복한다. 해법은 대칭을 깨는 것이다. 한쪽만 양보하게 하거나, 물러나는 시간을 무작위로 준다. 이더넷이 충돌 뒤 무작위로 기다리는 것과 같은 원리이고, 2.3절의 재시도 코드에 `sleep(0, rnd.nextInt(...))`가 들어간 이유다.

## 4. 기아 상태

```text
욕심 많은 스레드 ──▶ 자원 ─┐
욕심 많은 스레드 ──▶ 자원 ─┤ 계속
욕심 많은 스레드 ──▶ 자원 ─┘
얌전한 스레드   ──▶ 대기 … 대기 … 굶는다
```

```java
new ReentrantLock();      // 불공정
new ReentrantLock(true);  // 공정
// 공정: 오래 기다린 순서대로 준다
```

| 같은 일을 하는 스레드 10개, 락 하나, 2초 | 전체 획득 | 스레드당 최소 | 중앙값 | 최대 | 왜 |
|:-----------------------------|--------:|--------:|-------:|-------:|:---|
| 불공정 락 (기본) | 168,679 | 2,526 | 15,503 | 39,678 | 방금 놓은 스레드가 줄을 건너뛰어 다시 잡는다. 16배 |
| 같은 실험 한 번 더 | 171,254 | 1,873 | 21,203 | 30,271 | 누가 굶을지는 매번 다르다 |
| 공정 락 | 162,168 | 16,215 | 16,217 | 16,219 | 오래 기다린 순서. 편차 0 |

| 기아를 부르는 것 | 뜻 | 이 PC에서 | 왜 |
|:-------------|:---|:--------|:---|
| 불공정한 락 | 기다린 순서를 안 지킨다 | 위 표 | 방금 놓은 스레드가 캐시에 있고 깨어 있다 |
| 정책의 편애 | 리더를 우대하면 라이터가 굶는다 | 6절, 라이터 1번 | 우대는 누군가의 굶주림 |
| 우선순위 | 높은 것이 코어를 독차지 | 이 PC의 JVM은 우선순위를 무시 ([06](../06-multitasking)장 5.2절) | 운영체제와 런타임에 달렸다 |

셋째 원리다. 기아는 한 작업이 다른 작업들에 밀려 자원을 계속 못 받는 것이다. 교착과 라이브락이 여럿의 **관계**에서 생긴다면 기아는 하나가 **소외**되는 것이고, 원인은 대개 정책이다. 위 표에서 스레드 열 개가 똑같은 일을 하는데 불공정 락은 하나에게 39,678번, 다른 하나에게 2,526번을 줬다. 락을 놓은 스레드가 곧바로 다시 잡으려 하면 기다리던 스레드를 깨우는 것보다 그냥 주는 것이 빠르기 때문이고([08](../08-race-conditions-and-synchronization)장 4절), 그 빠름이 누군가의 굶주림이다. 공정 락은 셋째 자리까지 같다. 값은 처리량 4%였다. 처리량이 아니라 지연의 꼬리가 문제인 곳(모든 요청이 제때 답해야 하는 서버)에서는 그 4%를 낸다.

{{< callout type="info" >}}
**공정성은 공짜가 아니고, 언제나 답도 아니다.** 공정 락은 기다린 순서대로 주느라 방금 놓은 스레드를 잠재우고 잠든 스레드를 깨운다. 이 실험에서는 4%였지만 락을 짧게 쥐는 코드에서는 몇 배가 된다. 운영체제 스케줄러는 같은 문제를 에이징(aging)으로 푼다. 오래 기다린 작업의 급을 조금씩 올려 언젠가는 차례가 오게 한다. [06](../06-multitasking)장 5.4절의 다단계 피드백 큐가 그것이다.
{{< /callout >}}

### 우선순위 역전

| 순간 | 낮은 우선순위 L | 중간 M | 높은 우선순위 H | 왜 |
|:----|:-------------|:------|:-------------|:---|
| 1 | 락을 쥐고 일한다 | | | |
| 2 | 락을 쥔 채 밀려난다 | | 깨어나 그 락을 기다린다 | H는 L이 놓아야 간다 |
| 3 | 코어를 못 받는다 | 깨어나 코어를 차지한다 | 여전히 기다린다 | M이 L보다 높으니 L은 못 돈다 |
| 결과 | | M이 다 끝날 때까지 | H가 M에 밀린다 | 우선순위가 뒤집혔다 |

기아와 얽힌 유명한 함정이다. 낮은 우선순위 작업이 락을 쥔 채 밀려나면 그 락을 기다리는 높은 작업도 멈추고, 그 사이 중간 작업이 코어를 차지하면 높은 작업이 중간 작업에 밀린다. 1997년 화성 탐사선 패스파인더가 이 문제로 재부팅을 반복했다. 해법은 락을 쥔 낮은 작업의 우선순위를 그 락을 기다리는 가장 높은 작업의 것으로 잠시 끌어올리는 우선순위 상속이다. 이 PC의 JVM은 자바 우선순위를 운영체제에 넘기지 않아 재현되지 않았고, 그래서 실시간 시스템의 문제로 남아 있다.

## 5. 고전적 동시성 문제 ① 프로듀서-컨슈머

```text
프로듀서 ─put▶ [■ ■ □ □ □] ─take▶ 컨슈머
                유한 버퍼 N칸
가득 차면 프로듀서가, 비면 컨슈머가 선다
empty: 빈 칸 수   full: 찬 칸 수   mutex
```

```java
var empty = new Semaphore(N);  // 빈 칸
var full = new Semaphore(0);   // 찬 칸
var mutex = new ReentrantLock();
// 프로듀서
empty.acquire();
mutex.lock();
try { buf.add(item); }
finally { mutex.unlock(); }
full.release();
// 컨슈머는 full.acquire … empty.release
```

| 16칸 버퍼로 200만 개 | 처리량 | 경계 위반 | 왜 |
|:------------------|------:|:-------|:---|
| 세마포어 둘 + 뮤텍스, 1:1 | 382만~395만 개/초 | 0 | 빈 칸과 찬 칸을 세마포어가 센다 |
| `ArrayBlockingQueue`, 1:1 | 388만~394만 개/초 | 0 | 같은 구조를 라이브러리가 |
| 세마포어 둘 + 뮤텍스, 4:4 | 227만 개/초 | 0 | 여덟이 뮤텍스 하나를 다툰다 |
| `ArrayBlockingQueue`, 4:4 | 120만~143만 개/초 | 0 | 락 하나에 조건 둘 |
| 프로듀서가 `empty`를 안 잡으면 | | 100번 넣어 84개 덮어씀 | 가득 찼는지 아무도 안 센다 |
| 컨슈머가 `full`을 안 잡으면 | | 빈 버퍼에서 20번 쓰레기 | 비었는지 아무도 안 센다 |

동시성은 오래된 주제라 반복되는 문제에는 모범 답안이 있다. 첫째가 유한 버퍼를 사이에 둔 생산자와 소비자다. 버퍼가 가득 찼는데 넣거나 비었는데 꺼내면 안 되고, 버퍼 자체는 한 번에 하나만 만져야 한다. 답은 세마포어 둘과 뮤텍스 하나다. `empty`는 빈 칸 수, `full`은 찬 칸 수를 세고, 프로듀서는 빈 칸 허가증을 얻어야 넣고 컨슈머는 찬 칸 허가증을 얻어야 꺼낸다. 넣은 쪽이 `full`을 올리고 꺼낸 쪽이 `empty`를 올리니 [08](../08-race-conditions-and-synchronization)장 6절에서 본 "남이 돌려주는" 세마포어의 성질이 여기서 쓸모가 된다. 위 표의 아래 두 줄이 세마포어 하나를 빼면 생기는 일이다. [07](../07-task-decomposition)장의 파이프라인과 [05](../05-inter-process-communication)장의 스레드 풀이 전부 이 버퍼 위에 서 있다.

{{< callout type="info" >}}
**자바에서는 직접 짤 일이 거의 없다.** `BlockingQueue`가 이 패턴이다. `put`은 가득 차면 서고 `take`는 비면 선다. 위 표에서 직접 짠 것과 처리량이 같다. 여덟 스레드에서 세마포어 판이 빨랐던 것은 `ArrayBlockingQueue`가 락 하나에 조건 변수 둘로 깨울 상대를 고르느라 드는 값이고, 그 대신 `poll`, `offer`, 타임아웃, 인터럽트를 공짜로 준다. 네 가지 연산 형태는 [자바 동시성 05](../../java/concurrency/05-building-blocks)장 3절이다.
{{< /callout >}}

## 6. 고전적 동시성 문제 ② 리더-라이터

```text
읽기 락  R R R R   여럿이 동시에
쓰기 락    W       혼자. 아무도 못 온다
읽기가 많고 쓰기가 드물수록 이득
```

```java
var rw = new ReentrantReadWriteLock();
rw.readLock().lock();     // 여럿 동시에
try { return cache.get(k); }
finally { rw.readLock().unlock(); }
rw.writeLock().lock();    // 혼자
try { cache.put(k, v); }
finally { rw.writeLock().unlock(); }
```

| 쉬지 않는 리더 8개와 라이터 1개, 2초 | 읽기 | 쓰기 | 누가 굶나 | 왜 |
|:---------------------------|-------:|-------:|:-------|:---|
| 평범한 뮤텍스 (읽기도 배타) | 5,151 | 165,693 | 리더 | 놓자마자 다시 잡는 라이터가 불공정 락을 독점 |
| 교과서의 리더 우선 락 | 1,978,215 | 1 | 라이터 | 리더 수가 0이 되는 순간이 없다 |
| `ReentrantReadWriteLock` 불공정 | 5,149 | 158,598 | 리더 | 줄 맨 앞이 라이터면 새 리더를 막고, 라이터는 끼어든다 |
| `ReentrantReadWriteLock` 공정 | 413,859 | 51,626 | 아무도 | 기다린 순서대로 |

둘째 고전 문제다. 읽기끼리는 값을 안 바꾸니 동시에 해도 안전하고, 쓰기는 혼자여야 한다. 뮤텍스로 전부 막으면 안전하지만 읽기 동시성을 버리는 것이라 읽기가 여럿, 쓰기가 혼자인 락을 쓴다. 문제는 여기 기아가 숨어 있다는 것이다. 교과서의 답(리더 수를 세고 첫 리더가 쓰기 락을 잡는다)은 리더가 끊임없이 들어오면 리더 수가 0이 되는 순간이 없어 라이터가 영원히 못 들어간다. 이 PC에서 2초에 한 번 들어갔다. JDK의 락은 반대로 기울었다. 라이터가 놓자마자 다시 잡으니 리더가 굶었다. 공정 모드에서야 둘이 나눴다. 누가 굶느냐는 자원의 성질이 아니라 락의 정책이 정하고, 그 정책은 내가 고른다.

{{< callout type="warning" >}}
**리더-라이터 락은 읽기가 압도적으로 많을 때만 이득이다.** 쓰기가 잦으면 읽기 락과 쓰기 락을 오가는 비용이 뮤텍스보다 크고, 정책을 어느 쪽으로 기울여도 한쪽이 굶는다. 캐시처럼 읽기가 수천 배 많은 곳이 자리이고, 그마저도 JDK에는 `StampedLock`의 낙관적 읽기(락 없이 읽고 나중에 검증)와 `ConcurrentHashMap`처럼 아예 락을 잘게 쪼갠 구조가 있어 먼저 그쪽을 본다. 자바의 교착과 락 도구는 [자바 기초 13](../../java/basics/13-thread)장 5.3절과 6절이다.
{{< /callout >}}

| 안전 vs 활성 | 락을 걸수록 활성이 위험 | 두 단계로 설계한다 |

| 기아 | 정책이 하나를 굶긴다 | 불공정 16배, 공정 1배 |
| 공정성 | 순서를 지킨다. 처리량을 조금 낸다 | 4% |
| 우선순위 역전 | 낮은 것이 쥔 락에 높은 것이 걸린다 | 우선순위 상속 |

| 리더-라이터 | 읽기는 여럿, 쓰기는 혼자 | 정책에 따라 라이터 1번 또는 리더 5,149번 |

{{< callout type="info" >}}
**용어 정리**
- **안전성 / 활성**: 나쁜 일이 안 일어난다 / 좋은 일이 끝내 일어난다
- **교착 상태**: 둘 이상이 서로 상대의 자원을 기다리며 영원히 멈춘 상태
- **코프먼의 네 조건**: 상호 배제, 점유와 대기, 비선점, 순환 대기. 전부 성립해야 교착
- **순환 대기 / 락 순서 통일**: 기다림이 원을 이룸 / 원을 못 만들게 순서를 정함
- **예방 / 회피 / 탐지**: 조건을 없앤다 / 요청마다 검사한다 / 생긴 뒤 찾아 푼다
- **교착 희생자**: 탐지 뒤 롤백당하는 트랜잭션. 재시도가 의무
- **라이브락**: 멈추지 않는데 진행이 없는 상태. 서로에게 반응만
- **무작위 물러나기**: 재시도 타이밍을 흩어 라이브락을 깨는 것
- **기아 상태**: 한 작업이 자원을 계속 못 받는 것
- **공정성 / 에이징**: 기다린 순서대로 준다 / 오래 기다리면 급을 올린다
- **우선순위 역전 / 상속**: 낮은 작업의 락에 높은 작업이 걸려 중간에 밀림 / 락을 쥔 동안 높은 급을 빌려줌
- **프로듀서-컨슈머**: 유한 버퍼를 생산자와 소비자가 나눠 쓰는 문제. 세마포어 둘 + 뮤텍스
- **리더-라이터**: 읽기는 여럿, 쓰기는 혼자. 어느 쪽을 우대하느냐가 정책
{{< /callout >}}
