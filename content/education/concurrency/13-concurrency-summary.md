## 1. 전체 지도

동시성 학습은 하나의 질문에서 출발해 꼬리를 물고 확장된다.

```
 ① 왜 동시성인가          1~3장
    기다림이 아깝다
        │
        ▼
 ② 무엇으로 만드나        4~6장
    프로세스·스레드·스케줄링
        │
        ▼
 ③ 어떻게 나누나          7장
    작업 분해와 입도
        │
        ▼
 ④ 무엇이 깨지나          8~9장
    경쟁 조건·교착·기아
        │
        ▼
 ⑤ 스레드 없이 하기       10~12장
    논블로킹 → 이벤트 → 비동기
```

| 파트 | 장 | 핵심 질문 |
|:-----|:-----|:-----|
| Ⅰ. 동기 | [1](../01-what-is-concurrency)~[3](../03-how-computers-work) | 왜 동시에 처리해야 하는가 |
| Ⅱ. 재료 | [4](../04-concurrency-ingredients)~[6](../06-multitasking) | 무엇으로 동시성을 만드는가 |
| Ⅲ. 설계 | [7](../07-task-decomposition) | 일을 어떻게 쪼개는가 |
| Ⅳ. 문제 | [8](../08-race-conditions-and-synchronization)~[9](../09-deadlock-and-starvation) | 공유하면 무엇이 깨지는가 |
| Ⅴ. 대안 | [10](../10-nonblocking-io)~[12](../12-asynchronous-communication) | 스레드 없이 어떻게 하는가 |

## 2. Ⅰ. 왜 동시성인가 — 1~3장

### 2.1 출발점: 기다림은 낭비다

[1장](../01-what-is-concurrency)의 핵심은 **동시성은 빠른 계산이 아니라 자원 활용**이라는 것이다. 순차 처리는 I/O를 기다리는 동안 CPU를 놀린다. 동시성은 그 유휴 시간을 다른 작업으로 채운다.

| 얻는 것 | 의미 |
|:-----|:-----|
| 지연 시간 숨기기 | 대기 시간을 다른 작업으로 덮음 |
| 처리율 개선 | 같은 시간에 더 많은 작업 완료 |
| 자원 활용도 | 유휴 상태의 CPU·I/O를 동시에 가동 |
| 현실 모델링 | 본래 동시적인 세계를 자연스럽게 표현 |

### 2.2 동시성과 병렬성은 다른 축이다

전 장을 관통하는 가장 중요한 구분이다.

```
동시성 = 구조 (여러 일을 다룬다)
 ┌─ A ──┐ ┌─ B ──┐ ┌─ A ──┐
 코어 1개로도 성립

병렬성 = 실행 (여러 일을 동시에)
 코어1 ─ A ────────────
 코어2 ─ B ────────────
 코어가 여러 개여야 성립
```

| 구분 | 동시성 | 병렬성 |
|:-----|:-----|:-----|
| 본질 | 다루는 방식(구조) | 실행하는 방식(하드웨어) |
| 필요 조건 | 코어 1개로도 가능 | 코어 2개 이상 |
| 목표 | 응답성·자원 활용 | 처리 속도 |
| 잘 맞는 작업 | I/O 바운드 | CPU 바운드 |

### 2.3 한계를 규정하는 두 법칙

[2장](../02-sequential-and-parallel-execution)의 두 법칙은 "코어를 늘리면 얼마나 빨라지는가"에 대한 정반대의 답이다.

| 법칙 | 전제 | 결론 |
|:-----|:-----|:-----|
| **암달의 법칙** | 문제 크기 고정 | 순차 부분이 상한을 정한다 (5%면 최대 20배) |
| **구스타프슨의 법칙** | 자원에 맞춰 문제 확대 | 문제를 키우면 이득도 계속 커진다 |

{{< callout type="info" >}}
두 법칙은 모순이 아니라 **질문이 다르다.** "이 작업을 얼마나 빨리 끝낼 수 있나"는 암달, "같은 시간에 얼마나 큰 문제를 풀 수 있나"는 구스타프슨이다. 실무에서 "코어를 두 배로 늘렸는데 왜 두 배가 안 되나"라는 질문의 답은 거의 항상 암달 쪽에 있다.
{{< /callout >}}

### 2.4 하드웨어가 정하는 상한

[3장](../03-how-computers-work)의 플린 분류는 "어떤 하드웨어에 어떤 병렬성을 맡길 것인가"의 지도다.

| 분류 | 대표 | 잘 맞는 작업 |
|:-----|:-----|:-----|
| SISD | 단일 코어 | 순차 로직 |
| SIMD | GPU, 벡터 명령 | 동일 연산 × 대량 데이터 |
| MIMD | 멀티코어 CPU | 서로 다른 작업 여러 개 |

## 3. Ⅱ. 무엇으로 만드나 — 4~6장

### 3.1 프로세스와 스레드

[4장](../04-concurrency-ingredients)의 선택은 **격리와 비용의 트레이드오프**다.

```
프로세스 — 격리는 강하고 비용은 비싸다
 ┌─────────┐  ┌─────────┐
 │ 독립 메모리│  │ 독립 메모리│
 └─────────┘  └─────────┘
    통신하려면 IPC 필요

스레드 — 통신은 싸고 위험은 크다
 ┌───────────────────────┐
 │  공유: 힙·정적 영역    │
 │  독립: 스택·레지스터   │
 └───────────────────────┘
    포인터 하나로 통신, 그래서 위험
```

| 구분 | 프로세스 | 스레드 |
|:-----|:-----|:-----|
| 메모리 | 독립 | 힙·코드 공유, 스택 독립 |
| 생성 비용 | 비쌈 | 상대적으로 쌈 |
| 통신 | IPC 필요 | 변수 직접 접근 |
| 장애 전파 | 격리됨 | 프로세스 전체 종료 |
| 문맥 전환 | 비쌈(주소 공간 교체) | 쌈(같은 주소 공간) |

### 3.2 프로세스 간 통신

[5장](../05-inter-process-communication)의 IPC 수단은 **속도와 범위의 교환**이다.

| 방식 | 속도 | 범위 | 특징 |
|:-----|:-----|:-----|:-----|
| 공유 메모리 | 가장 빠름 | 같은 장비 | 동기화를 직접 해야 함 |
| 파이프 | 빠름 | 같은 장비 | 단방향 스트림 |
| 메시지 큐 | 중간 | 같은 장비~네트워크 | 비동기, 느슨한 결합 |
| 소켓 | 느림 | 네트워크 | 장비 경계를 넘음 |

여기서 나온 **스레드 풀**은 이후 모든 장에 등장하는 기본 도구다. 매번 스레드를 만드는 비용을 없애고, 동시 실행 개수에 상한을 두어 시스템을 보호한다.

### 3.3 작업의 두 유형과 멀티태스킹

[6장](../06-multitasking)의 **CPU 바운드 / I/O 바운드** 구분은 이 시리즈 전체에서 가장 실용적인 분류다. 어떤 동시성 모델을 고를지가 여기서 갈린다.

| 구분 | CPU 바운드 | I/O 바운드 |
|:-----|:-----|:-----|
| 병목 | 연산 능력 | 외부 응답 대기 |
| 예시 | 인코딩, 암호화, 정렬 | DB 조회, API 호출, 파일 |
| 적정 동시성 | 코어 수 근처 | 코어 수보다 훨씬 많이 |
| 해법 | **병렬화**(코어 추가) | **비동기·논블로킹** |

```
협동형 vs 선점형
────────────────────────
선점형: OS가 뺏는다
 A▪▪▪│B▪▪▪│A▪▪▪
     ▲ 커널 개입

협동형: 작업이 넘긴다
 A▪▪▪▶B▪▪▪▶A▪▪▪
     ▲ yield
```

{{< callout type="warning" >}}
**워크로드를 분류하지 않고 모델부터 고르는 것**이 동시성 설계에서 가장 흔한 실수다. CPU 바운드 작업에 이벤트 루프를 씌우면 오히려 느려지고, I/O 바운드 작업에 스레드를 늘리면 메모리만 먹는다. 측정이 먼저다.
{{< /callout >}}

## 4. Ⅲ. 어떻게 나누나 — 7장

[7장](../07-task-decomposition)은 "동시에 실행할 조각을 어떻게 만드는가"를 다룬다. 출발점은 **의존 관계 그래프**이고, 그래프의 **임계 경로**가 병렬화의 상한을 정한다.

| 전략 | 기준 | 패턴 |
|:-----|:-----|:-----|
| **작업 분해** | 서로 다른 '일'로 나눔 | 파이프라인 |
| **데이터 분해** | 같은 '일'을 데이터 조각마다 | 맵, 포크/조인, 맵리듀스 |

```
입도(granularity)의 균형
────────────────────────
너무 잘게  ▪▪▪▪▪▪▪▪▪▪
  → 관리 오버헤드가 이득을 잡아먹음

너무 굵게  ██████
  → 부하 불균형, 코어가 논다

적정 입도  ███ ███ ███
  → 조각당 작업 > 전환 비용
```

{{< callout type="info" >}}
**임계 경로는 아무리 코어를 늘려도 줄지 않는다.** 암달의 법칙이 말한 "순차 부분"이 그래프에서는 임계 경로로 나타난다. 병렬화 이득이 기대에 못 미친다면 코어를 더 붙이기 전에 그래프를 그려 임계 경로부터 확인해야 한다.
{{< /callout >}}

## 5. Ⅳ. 무엇이 깨지나 — 8~9장

### 5.1 공유가 부르는 문제

[8장](../08-race-conditions-and-synchronization)의 출발점은 단순하다. **공유 자원 + 동시 접근 + 쓰기 = 경쟁 조건.** 셋 중 하나만 없애도 문제가 사라진다.

```
count++ 는 원자적이 아니다
────────────────────────
 T1: 읽기(10)
 T2: 읽기(10)
 T1: +1 → 쓰기(11)
 T2: +1 → 쓰기(11)
   두 번 증가했는데 결과는 11
```

| 수단 | 성격 | 쓰임 |
|:-----|:-----|:-----|
| 원자적 연산 | 하드웨어 지원(CAS) | 단일 변수 갱신 |
| 락 | 임계 구역 보호의 총칭 | 범용 |
| 뮤텍스 | 소유권 있는 상호 배제(1개) | 한 번에 하나만 |
| 세마포어 | 카운터 기반(N개) | 자원 개수 제한 |

### 5.2 동기화가 부르는 새 문제

락을 쓰면 경쟁 조건은 사라지지만 [9장](../09-deadlock-and-starvation)의 문제가 새로 생긴다.

| 문제 | 증상 | 대표 해법 |
|:-----|:-----|:-----|
| **교착 상태** | 서로를 기다리며 영원히 멈춤 | 락 획득 순서 통일, 타임아웃 |
| **라이브락** | 계속 움직이지만 진전이 없음 | 무작위 백오프 |
| **기아 상태** | 특정 스레드만 자원을 못 얻음 | 공정성 옵션, 우선순위 상속 |

```
교착 상태의 4조건 (모두 성립해야 발생)
──────────────────────────────
 ① 상호 배제   자원을 혼자만 씀
 ② 점유와 대기 쥔 채로 더 기다림
 ③ 비선점     뺏을 수 없음
 ④ 순환 대기  A→B→C→A

 하나만 깨면 교착은 일어나지 않는다
 → 실무에서는 ④(락 순서 통일)를 깬다
```

{{< callout type="warning" >}}
**동기화는 공짜가 아니다.** 락은 정확성을 사는 대신 병렬성을 판다. 락 구간이 넓으면 직렬화되고, 좁히면 버그 위험이 커진다. 그래서 가장 좋은 동기화는 **동기화를 없애는 설계**다 — 불변 객체, 스레드 로컬, 단일 스레드 소유(11장의 리액터)가 모두 이 방향이다.
{{< /callout >}}

## 6. Ⅴ. 스레드 없이 하기 — 10~12장

### 6.1 문제 제기: 스레드는 비싸다

[10장](../10-nonblocking-io)은 **C10K 문제**에서 시작한다. 연결마다 스레드 하나를 두면 연결 1만 개에 스레드 1만 개, 스택만 수 GB에 문맥 전환이 폭증한다.

| 축 | 질문 | 값 |
|:-----|:-----|:-----|
| 블로킹 / 논블로킹 | 제어를 **언제** 돌려주는가 | 즉시 vs 완료 후 |
| 동기 / 비동기 | 완료를 **어떻게** 아는가 | 반환값 vs 통지 |

```
두 축은 독립적이다
────────────────────────
        동기        비동기
블로킹  read()      드묾
논블로킹 폴링 루프   epoll+콜백
                    ▲ 여기가 목표
```

### 6.2 해법의 진화

```
연결마다 스레드
    │ 비싸다 (C10K)
    ▼
논블로킹 + 바쁜 대기          10장
    │ CPU를 태운다
    ▼
I/O 멀티플렉싱 (select/epoll)  10장
    │ 구조가 필요하다
    ▼
이벤트 루프 + 리액터 패턴      11장
    │ 콜백 지옥
    ▼
코루틴 · 퓨처 · 가상 스레드    12장
```

### 6.3 이벤트 기반 동시성

[11장](../11-event-driven-concurrency)의 리액터 패턴은 **단일 스레드 이벤트 루프 + 논블로킹 이벤트 + 콜백 위임**이다.

```
 이벤트 소스 (소켓·타이머)
        │
        ▼
   디멀티플렉서 (epoll)
        │ 준비된 것만
        ▼
   이벤트 루프·디스패처
        │
        ▼
   핸들러 A  B  C (콜백)
```

| 구분 | 리액터 | 프로액터 |
|:-----|:-----|:-----|
| 통지 | I/O **준비** 완료 | I/O **수행** 완료 |
| read/write | 콜백이 직접 | 커널이 대신 |
| 기반 | epoll, kqueue | IOCP, io_uring |
| 자바 | `Selector` | `AsynchronousChannel` |

### 6.4 비동기 통신

[12장](../12-asynchronous-communication)은 이벤트 기반을 **코드로 쓰기 좋게** 만드는 추상화를 다룬다.

| 추상화 | 정체 |
|:-----|:-----|
| **협동적 멀티태스킹** | 작업이 스스로 제어권을 반납하는 실행 모델 |
| **코루틴** | 멈췄다가 그 자리에서 재개하는 함수 |
| **퓨처** | 미래에 완료될 결과의 프록시 |
| **async/await** | 비동기를 순차 코드처럼 쓰는 문법 |
| **가상 스레드** | 코드는 블로킹, 실행은 논블로킹 |

{{< callout type="info" >}}
10~12장은 하나의 이야기다. **"스레드가 비싸다"** 는 문제(10장)에 **"이벤트에만 반응하자"** 는 구조(11장)로 답했고, 그 구조가 만든 **"코드가 쪼개진다"** 는 새 문제를 **코루틴과 퓨처**(12장)로 풀었다. 각 단계는 앞 단계의 해법이 만든 새 문제를 푸는 과정이다.
{{< /callout >}}

## 8. 실전 의사결정 가이드

### 8.1 어떤 동시성 모델을 고를 것인가

```
        워크로드는?
             │
   ┌─────────┴─────────┐
CPU 바운드          I/O 바운드
   │                    │
   ▼                    ▼
병렬화              동시 연결 수는?
스레드 풀           ┌────┴────┐
Fork-Join         적다      많다
코어 수만큼          │        │
                    ▼        ▼
             스레드 풀   이벤트 기반
              (단순)    코루틴/가상스레드
```

| 상황 | 권장 모델 | 이유 |
|:-----|:-----|:-----|
| 이미지 변환, 암호화, 대량 정렬 | 스레드 풀 (코어 수) | CPU 바운드 — 비동기는 무의미 |
| 배치 집계, 대규모 데이터 처리 | Fork-Join, 맵리듀스 | 데이터 분해가 자연스러움 |
| 일반 웹 API (동시 수백) | 스레드 풀 + 블로킹 | 단순함이 최고의 미덕 |
| 게이트웨이·프록시 (동시 수만) | 이벤트 기반(Netty, WebFlux) | 연결당 비용이 지배적 |
| 채팅·실시간 스트림 | 이벤트 기반 + 코루틴 | 대부분의 연결이 대기 상태 |
| 기존 블로킹 코드 확장 | 가상 스레드(Java 21+) | 코드 변경 없이 동시성 확보 |

### 8.2 자주 하는 실수

| 실수 | 무엇이 문제인가 | 어디를 볼 것인가 |
|:-----|:-----|:-----|
| 워크로드 분류 없이 모델 선택 | 잘못된 축으로 최적화 | [6장 2절](../06-multitasking) |
| 스레드 풀 크기를 감으로 설정 | 과소는 병목, 과대는 전환 폭증 | [5장 7절](../05-inter-process-communication) |
| 코어만 늘리고 이득을 기대 | 순차 부분·임계 경로가 상한 | [2장](../02-sequential-and-parallel-execution), [7장](../07-task-decomposition) |
| 락 순서를 팀마다 다르게 | 순환 대기 → 교착 | [9장 2절](../09-deadlock-and-starvation) |
| 임계 구역에 I/O를 포함 | 락 보유 시간 폭증, 직렬화 | [8장 7절](../08-race-conditions-and-synchronization) |
| 이벤트 루프에서 블로킹 호출 | 서버 **전체** 정지 | [11장 4.3절](../11-event-driven-concurrency) |
| 코루틴에서 JDBC 직접 호출 | 캐리어 스레드가 묶임 | [12장 2.4절](../12-asynchronous-communication) |
| 가상 스레드 무제한 생성 | DB 커넥션 풀이 먼저 붕괴 | [12장 6절](../12-asynchronous-communication) |
| 동기화만 늘려 문제 회피 | 정확하지만 느린 코드 | [8장](../08-race-conditions-and-synchronization) |

{{< callout type="warning" >}}
**동시성 버그는 재현되지 않는다.** 개발 환경에서 100번 통과한 코드가 운영에서 하루 한 번 깨지는 일이 흔하다. 그래서 "테스트로 잡는다"보다 **"구조적으로 불가능하게 만든다"** 가 훨씬 나은 전략이다 — 불변 객체를 쓰고, 공유를 없애고, 소유권을 한 스레드에 고정하는 설계가 락을 정교하게 다루는 것보다 안전하다.
{{< /callout >}}

### 8.3 설계 시 점검 목록

| 점검 | 확인할 것 |
|:-----|:-----|
| 워크로드 | CPU 바운드인가 I/O 바운드인가 — 측정했는가 |
| 의존 관계 | 정말 독립적인가, 임계 경로는 얼마인가 |
| 공유 상태 | 공유를 없앨 수 있는가(불변·스레드 로컬) |
| 락 | 범위가 최소인가, 획득 순서가 통일됐는가 |
| 상한 | 스레드·커넥션·큐 크기에 상한이 있는가 |
| 블로킹 | 이벤트 루프·코루틴 경로에 블로킹이 없는가 |
| 실패 | 타임아웃·취소·백프레셔가 설계돼 있는가 |
| 관측 | 큐 길이·활성 스레드·대기 시간을 볼 수 있는가 |

## 9. 하나의 문장으로

```
 동시성 12장의 요약
 ──────────────────────────────
 기다리는 시간이 아까워서 시작했고
   (1~3장)

 프로세스·스레드로 만들었더니
   비싸고 다루기 까다로웠으며
   (4~6장)

 일을 잘 쪼개는 것이 관건이었는데
   (7장)

 공유하는 순간 다 깨져서
   락으로 막았더니 또 멈췄고
   (8~9장)

 결국 스레드를 줄이는 쪽으로 갔다
   논블로킹 → 이벤트 → 비동기
   (10~12장)
```

{{< callout type="info" >}}
**최종 정리:**
1. 동시성의 목적은 **빠른 계산이 아니라 자원 활용**이다. 병렬성은 그 목적을 하드웨어로 달성하는 한 가지 수단일 뿐이며, 코어 1개로도 동시성은 성립한다
2. 성능 향상에는 **상한이 있다.** 암달의 법칙과 임계 경로가 그 천장을 정하므로, 코어를 늘리기 전에 순차 구간부터 찾아야 한다
3. **CPU 바운드와 I/O 바운드의 구분**이 모델 선택을 결정한다. 전자는 병렬화, 후자는 비동기·논블로킹이 답이며 이를 바꿔 적용하면 오히려 느려진다
4. 스레드가 위험한 이유는 **메모리를 공유**하기 때문이다. 경쟁 조건을 락으로 막으면 교착·기아라는 새 문제가 따라오므로, 가장 좋은 해법은 **공유를 없애는 설계**다
5. 스레드의 비용이 한계에 부딪히자 **논블로킹 I/O → 이벤트 루프 → 코루틴·퓨처**로 진화했다. 각 단계는 앞 단계 해법이 만든 새 문제를 푸는 과정이었다
6. 오늘날의 선택지는 **스레드 풀·이벤트 기반·코루틴·가상 스레드**로 넓어졌지만, 고르는 기준은 12장 내내 같았다 — **워크로드를 먼저 측정하고, 공유를 최소화하고, 상한을 두는 것**
{{< /callout >}}
