[01](../01-what-is-concurrency)장부터 [12](../12-asynchronous-communication)장까지를 하나로 잇는 장이다. 개념을 다시 설명하기보다 어떤 문제가 다음 개념을 불러왔는지, 그리고 실무에서 무엇을 골라야 하는지에 초점을 맞춘다. 열두 장을 관통하는 원리는 셋이다. 첫째, **동시성의 이득은 전부 기다림에서 나오고, 상한은 의존과 순차 부분이 정한다.** 요청 다섯 개 957ms가 458ms로 준 것도, 호출 셋 771ms가 309ms로 준 것도 기다림을 겹친 것이고, 앞의 답이 필요한 사슬은 스레드가 몇이든 그대로였다. 둘째, **동시성의 문제는 전부 공유에서 나오고, 가장 싼 해법은 공유를 없애는 것이다.** `count++` 하나가 80%를 잃고, 락은 경쟁이 붙으면 3ns가 39ns가 되고, 순서가 엇갈린 락 둘은 558번 만에 멈춘다. 공유를 없앤 `LongAdder`가 0.8ns이고 스레드 하나가 연결 전부를 소유하는 리액터에 락이 없는 이유다. 셋째, **스레드는 비싸서 안 만드는 길이 생겼고, 그 길의 규칙은 물러나라는 것이다.** 이 PC의 스레드는 4,069개에서 끝나지만 이벤트 루프 하나가 초당 25.7만 이벤트를, `Continuation` 하나가 51ns에 갈아탄다. 대신 루프 안의 10ms가 모두의 12ms이고, `synchronized` 안에서 잠든 가상 스레드 100개가 열 배를 치른다. 이 장의 숫자는 각 장에서 이 PC(Apple M4 10코어, macOS, JDK 23)로 잰 것을 모은 것이고, 하나를 새로 더했다. 같은 작업 1,000개를 세 워크로드(계산 10ms, 계산 1ms + 대기 9ms, 대기 10ms)와 일곱 모델(순차, 풀 10·100·1,000, 가상 스레드, 이벤트 루프, 루프 + 워커)로 돌려 8절의 선택 표를 숫자로 채웠다.

## 1. 전체 지도

```text
 ① 왜 동시성인가         1~3장
    기다림이 아깝다
        │
        ▼
 ② 무엇으로 만드나       4~6장
    프로세스·스레드·스케줄링
        │
        ▼
 ③ 어떻게 나누나         7장
    작업 분해와 입도
        │
        ▼
 ④ 무엇이 깨지나         8~9장
    경쟁 조건·교착·기아
        │
        ▼
 ⑤ 스레드 없이 하기      10~12장
    논블로킹 → 이벤트 → 비동기
```

| 파트 | 장 | 핵심 질문 | 이 PC의 답 한 줄 |
|:-----|:---|:-------|:------------|
| Ⅰ. 동기 | [01](../01-what-is-concurrency)~[03](../03-how-computers-work) | 왜 동시에 처리해야 하는가 | 기다림을 겹치면 957 ms가 458 ms. 계산은 실효 코어 6.8까지 |
| Ⅱ. 재료 | [04](../04-concurrency-ingredients)~[06](../06-multitasking) | 무엇으로 동시성을 만드는가 | 스레드 26 µs·88 KB·4,069개, 프로세스 1.8 ms, 전환 1.5 µs, 슬라이스 10 ms |
| Ⅲ. 설계 | [07](../07-task-decomposition) | 일을 어떻게 쪼개는가 | 임계 경로 400 ms는 코어로 못 넘고, 입도는 7조각 3.9배·1,023조각 7.5배 |
| Ⅳ. 문제 | [08](../08-race-conditions-and-synchronization)~[09](../09-deadlock-and-starvation) | 공유하면 무엇이 깨지는가 | `count++` 80% 손실, 락 3 → 39 ns, 교착은 558번 만에 |
| Ⅴ. 대안 | [10](../10-nonblocking-io)~[12](../12-asynchronous-communication) | 스레드 없이 어떻게 하는가 | 루프 하나가 연결 1만 개·초당 25.7만 이벤트, 가상 스레드 10만 개가 175 MB |

동시성 학습은 하나의 질문에서 출발해 꼬리를 문다. 기다림이 아까워서 시작했고(Ⅰ), 프로세스와 스레드로 만들었더니 비싸고 까다로웠고(Ⅱ), 잘 쪼개는 것이 관건이었는데(Ⅲ), 공유하는 순간 깨져서 락으로 막았더니 또 멈췄고(Ⅳ), 결국 스레드를 줄이는 쪽으로 갔다(Ⅴ). 각 절의 링크를 따라가면 그 장의 실측과 설명으로 이어진다.

## 2. Ⅰ. 왜 동시성인가 — 1~3장

### 2.1 출발점: 기다림은 낭비다

| 얻는 것 | 의미 | 이 PC에서 | 왜 |
|:------|:-----|:-------|:---|
| 지연 시간 숨기기 | 대기 시간을 다른 일로 덮는다 | 요청 다섯 개 957 ms → 458 ms | 걸린 시간이 합에서 최댓값으로 |
| 처리율 개선 | 같은 시간에 더 많은 일 | I/O 작업 초당 9.6개 → 917개 | 기다림은 스레드 수만큼 겹친다 |
| 자원 활용도 | 노는 CPU·I/O를 같이 돌린다 | CPU 활용도 24% → 96% → 236% | 같은 CPU 시간을 더 짧은 벽시계에 |
| 현실 모델링 | 본래 동시적인 세계를 그대로 | | 대신 세계의 문제(공유)도 따라온다 |

[01](../01-what-is-concurrency)장의 핵심은 동시성은 빠른 계산이 아니라 자원 활용이라는 것이다. 순차 처리는 I/O를 기다리는 동안 CPU를 놀리고, 동시성은 그 유휴 시간을 다른 작업으로 채운다. 리틀의 법칙이 그 산수다. 진행 중인 일 = 처리율 × 지연이니, 지연을 못 줄이면 진행 중인 일을 늘려 처리율을 올린다.

### 2.2 동시성과 병렬성은 다른 축이다

```text
동시성 = 구조 (여러 일을 다룬다)
 ┌─ A ──┐ ┌─ B ──┐ ┌─ A ──┐
 코어 1개로도 성립

병렬성 = 실행 (여러 일을 같은 순간에)
 코어1 ─ A ────────────
 코어2 ─ B ────────────
 코어가 여러 개여야 성립
```

| 구분 | 동시성 | 병렬성 | 왜 |
|:-----|:-----|:-----|:---|
| 본질 | 다루는 방식(구조) | 실행하는 방식(하드웨어) | 설계와 실행 환경은 다른 층 |
| 필요 조건 | 코어 1개로도 가능 | 코어 2개 이상 | 같은 스레드 20개로 대기는 211 ms, 계산은 615 ms |
| 목표 | 응답성·자원 활용 | 처리 속도 | 겹치는 것이 기다림이냐 계산이냐 |
| 잘 맞는 작업 | I/O 바운드 | CPU 바운드 | I/O는 스레드 수만큼, 계산은 코어 수까지 |

전 장을 관통하는 가장 중요한 구분이다. [02](../02-sequential-and-parallel-execution)장에서 `sleep(200)` 작업 20개는 스레드 20개면 코어와 무관하게 211ms였고, 같은 스레드 20개로 계산 작업을 돌리면 615ms였다. 기다림은 코어 없이도 겹치고 계산은 코어가 있어야 겹친다.

### 2.3 한계를 규정하는 두 법칙

| 법칙 | 전제 | 결론 | 이 PC에서 | 왜 |
|:-----|:-----|:-----|:-------|:---|
| 암달의 법칙 | 문제 크기 고정 | 순차 부분이 상한을 정한다 (5%면 최대 20배) | 순차 10%에 4.4배, 50%에 1.75배 | 순차 부분은 코어를 더 줘도 그대로 |
| 실효 코어 | 코어가 다 같지 않다 | 공식의 N은 코어 수가 아니다 | 10코어에 6.8, 순수 계산 천장 7.2배 | 성능 코어 4 + 효율 코어 6 |
| 구스타프슨의 법칙 | 자원에 맞춰 문제 확대 | 문제를 키우면 이득도 커진다 | 일 9.1배에 시간 36% 증가 | 문제가 크면 순차 비중이 준다 |

{{< callout type="info" >}}
두 법칙은 모순이 아니라 **질문이 다르다.** "이 작업을 얼마나 빨리 끝낼 수 있나"는 암달, "같은 시간에 얼마나 큰 문제를 풀 수 있나"는 구스타프슨이다. 실무에서 "코어를 두 배로 늘렸는데 왜 두 배가 안 되나"라는 질문의 답은 거의 항상 암달 쪽에 있고, 이 PC에서는 그 앞에 실효 코어 6.8이 먼저 있다.
{{< /callout >}}

### 2.4 하드웨어가 정하는 상한

| 분류 | 대표 | 잘 맞는 작업 | 이 PC에서 | 왜 |
|:-----|:-----|:---------|:-------|:---|
| SISD | 단일 코어 | 순차 로직 | 한 코어 초당 73억 원소 | 분기 예측과 캐시가 한 스레드를 빠르게 |
| SIMD | 벡터 명령, GPU | 같은 연산 × 대량 데이터 | 벡터화 3.2배, 분기 있으면 0배, GPU는 열 코어의 4.5배 | 한 명령에 원소 넷, GPU는 수천 |
| MIMD | 멀티코어 CPU | 서로 다른 작업 여러 개 | 열 코어 305억 원소/초 | 코어마다 자기 명령 흐름 |
| 통신 사다리 | 코어 안 → 칩 안 → 기계 밖 | 조각은 통신보다 커야 | 72 ns → 3.7 µs → 13 µs → 6.7 ms | 층마다 백 배 |

[03](../03-how-computers-work)장의 플린 분류는 어떤 하드웨어에 어떤 병렬성을 맡길 것인가의 지도이고, 통신 사다리는 조각을 얼마나 굵게 쪼갤지의 자다. 공유 변수 72ns, 큐로 건네기 3.7µs, TCP 루프백 13µs, 인터넷 6.7ms이니 조각 하나의 일은 그보다 커야 한다. 그리고 프로그램은 하드웨어를 직접 만지지 않고 런타임을 거친다. JIT를 끄면 12배 느렸다.

## 3. Ⅱ. 무엇으로 만드나 — 4~6장

### 3.1 프로세스와 스레드

```text
프로세스: 격리는 강하고 비용은 비싸다
 ┌──────────┐  ┌──────────┐
 │ 독립 메모리 │  │ 독립 메모리 │
 └──────────┘  └──────────┘
    통신하려면 IPC가 필요

스레드: 통신은 싸고 위험은 크다
 ┌───────────────────────┐
 │  공유: 힙·정적 영역    │
 │  독립: 스택·레지스터   │
 └───────────────────────┘
    포인터 하나로 통신, 그래서 위험
```

| 구분 | 프로세스 | 스레드 | 이 PC에서 | 왜 |
|:-----|:-------|:-----|:-------|:---|
| 메모리 | 독립 | 힙·코드 공유, 스택 독립 | 잠든 스레드 88 KB | 스택이 스레드의 정체 |
| 생성 비용 | 비싸다 | 싸다 | 1.8 ms vs 26 µs (가상 8 µs) | 주소 공간을 만드느냐 스택만 붙이느냐 |
| 통신 | IPC 필요 | 변수 직접 접근 | 파이프 5 µs vs 공유 변수 72 ns | 같은 힙 |
| 장애 전파 | 격리된다 | 프로세스 전체가 죽는다 | 자식 종료 코드 139, 부모는 그대로 | 같은 힙이면 같이 죽는다 |
| 개수 | 수십~수백 | 수천 | 4,069개에서 실패 | OS가 프로세스당 4,096개 |
| 공유의 값 | 없음 | 원자성·가시성·순서가 깨진다 | 48% 손실, 3초 뒤에도 못 봄, 91% 재배치 | 말 안 하면 공유가 아니다 |

[04](../04-concurrency-ingredients)장의 선택은 격리와 비용의 트레이드오프다. 프로세스는 격리를 사고 스레드는 공유를 산다. 스레드는 싸지만 공짜가 아니고 무한하지도 않다. 잠든 스레드 하나가 88KB이고 이 PC에서 4,069개째에 만들기가 실패했다. 그리고 공유하는 순간 셋이 깨진다. `count++`가 세 명령이라 원자성이, 캐시 때문에 가시성이, 컴파일러와 CPU의 재배치 때문에 순서가 깨진다.

### 3.2 프로세스 간 통신

| 방식 | 속도 | 범위 | 이 PC 왕복 | 왜 |
|:-----|:-----|:-----|--------:|:---|
| 공유 메모리 | 가장 빠르다 | 같은 장비 | 281 ns | 같은 페이지를 본다. 동기화는 내 몫 |
| 파이프 | 빠르다 | 같은 장비 | 5 µs | 커널의 64 KB 버퍼를 거친다 |
| 메시지 큐 | 중간 | 같은 장비~네트워크 | | 넣어 두면 나중에. 1,025번째에서 생산자를 세운다 |
| 소켓 | 느리다 | 네트워크 | 15 µs (인터넷 6.7 ms) | 어디든 닿는다. 코드가 같다 |
| 처리량 | | | 유닉스 소켓 8 KB 버퍼 132 ms → 1 MB 9 ms | 방식이 아니라 버퍼가 정한다 |

[05](../05-inter-process-communication)장의 IPC 수단은 속도와 범위의 교환이다. 그리고 여기서 나온 스레드 풀이 이후 모든 장의 기본 도구다. 매번 스레드를 만드는 25µs를 6µs로 줄이고, 동시 실행 개수에 상한을 두어 시스템을 지킨다. 풀 크기는 코어 × (1 + 대기 ÷ 계산)이고, 계산 1ms + 대기 9ms 작업 1,000개는 풀 100에서 163ms로 바닥에 닿았다. 상한 없는 풀은 4,070개째에서 죽었다.

### 3.3 작업의 두 유형과 멀티태스킹

| 구분 | CPU 바운드 | I/O 바운드 | 왜 |
|:-----|:--------|:--------|:---|
| 병목 | 연산 능력 | 외부 응답 대기 | 시간이 어디에 쓰이느냐 |
| 예시 | 인코딩, 암호화, 정렬 | DB 조회, API 호출, 파일 | |
| 적정 동시성 | 코어 수 근처 | 코어 수보다 훨씬 많이 | 계산은 코어 수까지, 대기는 겹칠수록 |
| 해법 | 병렬화 (코어 추가) | 비동기·논블로킹 | 회수할 것이 계산이냐 기다림이냐 |
| 이 PC에서 | 스레드 4,000개가 코어 10개에 35% 손해 | 잠든 100개를 얹어도 계산은 2% 손해 | 자는 스레드는 거의 공짜 |

```text
협력형 vs 선점형
선점형: OS가 뺏는다
 A▪▪▪│B▪▪▪│A▪▪▪
     ▲ 커널 개입, 슬라이스 10 ms

협력형: 작업이 넘긴다
 A▪▪▪▶B▪▪▪▶A▪▪▪
     ▲ yield, 안 넘기면 1,003 ms
```

[06](../06-multitasking)장의 CPU 바운드 / I/O 바운드 구분은 이 시리즈에서 가장 실용적인 분류다. 어떤 동시성 모델을 고를지가 여기서 갈린다. 멀티태스킹은 하드웨어가 아니라 런타임의 기능이고, 전환을 누가 결정하느냐가 두 세계를 가른다. 선점형은 이 PC에서 10ms 슬라이스로 뺏고, 협력형은 양보 없는 가상 스레드 하나가 1,003ms를 독점했다. 스케줄러는 I/O 바운드를 편애해서 코어가 전부 바빠도 깬 스레드는 0.26ms에 돈다.

{{< callout type="warning" >}}
**워크로드를 분류하지 않고 모델부터 고르는 것**이 동시성 설계에서 가장 흔한 실수다. CPU 바운드 작업에 이벤트 루프를 씌우면 오히려 느려지고(8.1절 표의 10,571ms), I/O 바운드 작업에 스레드를 늘리면 메모리만 먹는다. 측정이 먼저다.
{{< /callout >}}

## 4. Ⅲ. 어떻게 나누나 — 7장

| 전략 | 기준 | 패턴 | 이 PC에서 | 왜 |
|:-----|:-----|:-----|:-------|:---|
| 의존 관계 그래프 | 화살표 없는 것만 동시에 | `CompletableFuture` 사슬 | 561 → 428 ms, 임계 경로 400 ms | 가장 긴 사슬이 하한. 코어를 더 줘도 못 넘는다 |
| 작업 분해 | 서로 다른 일로 나눈다 | 파이프라인 | 기능 셋 2.7배, 파이프라인 240 → 877/s | 천장은 기능 수 |
| 데이터 분해 | 같은 일을 조각마다 | 맵, 포크/조인, 맵리듀스 | 400만 원소 6.2배, 불균형 88 → 71 ms | 천장은 코어 수 |
| 겹쳐 쓰기 | 기능으로, 그 안을 데이터로 | | 2.7배 → 6.1배 | 두 천장을 곱한다 |

```text
입도(granularity)의 균형
너무 잘게  ▪▪▪▪▪▪▪▪▪▪
  100만 조각 5.1배: 관리 비용이 먹는다

너무 굵게  ██████
  7조각 3.9배: 코어가 논다

적정 입도  ███ ███ ███
  1,023조각 7.5배: 조각 > 전환 비용
```

[07](../07-task-decomposition)장은 동시에 실행할 조각을 어떻게 만드는가다. 출발점은 코어 수가 아니라 의존 관계이고, 그래프의 임계 경로가 병렬화의 상한을 정한다. 나누는 방향은 둘이다. 일이 다르면 일을 나누고(MIMD), 같으면 데이터를 나눈다(SIMD). 파이프라인의 유계 큐는 배압이다. 큐 64는 지연 138ms, 큐 4는 14ms였다. 맵/리듀스는 결합법칙이 있는 함수로만 접어야 한다. 뺄셈을 병렬로 접으니 0이 나왔다.

{{< callout type="info" >}}
**임계 경로는 아무리 코어를 늘려도 줄지 않는다.** 암달의 법칙이 말한 순차 부분이 그래프에서는 임계 경로로 나타난다. 병렬화 이득이 기대에 못 미친다면 코어를 더 붙이기 전에 그래프를 그려 임계 경로부터 확인해야 한다. 그래프로는 428ms가 최선이었고, 더 빨리 가려면 그래프 자체를 바꿔야 했다.
{{< /callout >}}

## 5. Ⅳ. 무엇이 깨지나 — 8~9장

### 5.1 공유가 부르는 문제

```text
count++ 는 원자적이 아니다
 T1: 읽기(10)
 T2: 읽기(10)
 T1: +1 → 쓰기(11)
 T2: +1 → 쓰기(11)
   두 번 증가했는데 결과는 11
   열 스레드면 80%가 사라진다
```

| 수단 | 성격 | 쓰임 | 이 PC에서 | 왜 |
|:-----|:-----|:-----|:-------|:---|
| 원자적 연산 | 하드웨어 지원(CAS) | 단일 변수 갱신 | 경쟁 없으면 2 ns, 열 스레드면 CAS 5.5번 실패 | 명령 하나, 락 없음 |
| 락 | 임계 구역 보호의 총칭 | 범용 | 경쟁 없으면 3 ns, 붙으면 39 ns | 값은 락이 아니라 경쟁과 직렬화 |
| 뮤텍스 | 소유권 있는 상호 배제 | 한 번에 하나만 | 남이 풀면 예외, 재진입 허용 | 소유권이 있다 |
| 세마포어 | 카운터 기반 | 자원 N개 제한 | 허가증 셋에 정확히 셋 | 소유권이 없다 |
| 안 공유하기 | 스레드마다 자기 것 | 카운터, 집계 | `LongAdder` 0.8 ns | 가장 싼 해법 |

[08](../08-race-conditions-and-synchronization)장의 출발점은 단순하다. 공유 자원 + 동시 접근 + 쓰기 = 경쟁 조건. 셋 중 하나만 없애도 문제가 사라진다. 경쟁 조건은 공유와 교차의 곱이고, 문제는 자원이 아니라 구간에서 생긴다. 그래서 임계 구역을 찾는 것이 락을 고르는 것보다 먼저다. 그리고 값은 락 자체보다 폭에 든다. 락 점유 시간의 합이 하한이라 락 비율 50%면 524ms, 10%면 173ms였다.

### 5.2 동기화가 부르는 새 문제

| 문제 | 증상 | 대표 해법 | 이 PC에서 | 왜 |
|:-----|:-----|:-------|:-------|:---|
| 교착 상태 | 서로를 기다리며 영원히 멈춤 | 락 순서 통일, 타임아웃 | 엇갈린 순서 열 번 중 열 번, 558번 만에. 순서 맞추면 20만 번 44 ms에 교착 0 | 네 조건 중 순환 대기를 깬다 |
| 라이브락 | 계속 움직이지만 진전이 없음 | 무작위 백오프, 대칭 깨기 | 1초에 2,000만 번 양보, 식사 0. 한쪽만 양보하니 29번 만에 | 둘이 똑같이 행동한다 |
| 기아 상태 | 특정 스레드만 자원을 못 얻음 | 공정성 옵션, 우선순위 상속 | 불공정 락 16배 차이, 공정 락은 1배에 처리량 4% 값 | 정책이 하나를 굶긴다 |

```text
교착 상태의 4조건 (모두 성립해야)
 ① 상호 배제   자원을 혼자만 쓴다
 ② 점유와 대기 쥔 채로 더 기다린다
 ③ 비선점      뺏을 수 없다
 ④ 순환 대기   A→B→C→A

 하나만 깨면 교착은 없다
 → 실무에서는 ④(락 순서 통일)를 깬다
```

락을 쓰면 경쟁 조건은 사라지지만 [09](../09-deadlock-and-starvation)장의 문제가 새로 생긴다. 값이 틀린 것이 아니라 값이 안 나온다. 동기화는 안전을 사고 활성을 판다. 교착은 네 조건의 곱이고 하나만 깨면 된다. 실무의 답은 순서다. 타임아웃으로 비선점을 깨는 길도 있지만 575번 물러나 5.3초를 치렀다. 고전 문제 둘이 그 응용이다. 프로듀서-컨슈머에서 `empty` 세마포어를 빼니 84개를 덮어썼고, 리더-라이터는 정책에 따라 라이터가 1번 또는 리더가 5,149번만 지나갔다.

{{< callout type="warning" >}}
**동기화는 공짜가 아니다.** 락은 정확성을 사는 대신 병렬성을 판다. 락 구간이 넓으면 직렬화되고(100%면 1.0배), 좁히면 버그 위험이 커진다. 그래서 가장 좋은 동기화는 **동기화를 없애는 설계**다. 불변 객체, 스레드 로컬, `LongAdder`의 스레드별 칸, 단일 스레드 소유([11](../11-event-driven-concurrency)장의 리액터)가 모두 이 방향이다.
{{< /callout >}}

## 6. Ⅴ. 스레드 없이 하기 — 10~12장

### 6.1 문제 제기: 스레드는 비싸다

| 축 | 질문 | 값 | 이 PC에서 | 왜 다른 축인가 |
|:---|:-----|:---|:-------|:----------|
| 블로킹 / 논블로킹 | 제어를 **언제** 돌려주는가 | 완료 후 vs 즉시 | 블로킹 `read()`는 CPU 0, 논블로킹은 0.19 µs에 0 바이트 | 이 호출이 나를 멈추는가 |
| 동기 / 비동기 | 완료를 **어떻게** 아는가 | 되묻기 vs 통지 | 동기 큐 `put`은 상대가 늦으면 12.5 ms, 비동기 큐는 42 ns | 끝난 것을 누가 알려 주는가 |

```text
두 축은 독립적이다
          동기         비동기
블로킹    read()       드묾
논블로킹  폴링 루프    epoll + 콜백
                      ▲ 여기가 목표
```

[10](../10-nonblocking-io)장은 C10K 문제에서 시작한다. 연결마다 스레드 하나를 두면 연결 1만 개에 스레드 1만 개인데, 이 PC는 4,069개에서 서버가 멈췄다. 논블로킹으로 바꾸고 스레드 하나가 돌며 물으면 스레드는 하나지만 CPU가 100%이고 지연이 연결 수에 비례한다. 1만 개에 2.7ms였다. 묻는 일을 커널에 맡기면(멀티플렉싱) 스레드 하나가 연결 1만 개를 21MB, CPU 0%, 134µs로 든다.

### 6.2 해법의 진화

```text
연결마다 스레드
    │ 비싸다: 4,069개에서 끝
    ▼
논블로킹 + 바쁜 대기       10장
    │ CPU 100%, 1만 개에 2.7 ms
    ▼
I/O 멀티플렉싱 (select)    10장
    │ 구조가 필요하다
    ▼
이벤트 루프 + 리액터       11장
    │ 콜백 지옥, 스택이 끊긴다
    ▼
코루틴·퓨처·가상 스레드    12장
```

### 6.3 이벤트 기반 동시성

```text
 이벤트 소스 (소켓·타이머)
        │
        ▼
   디멀티플렉서 (kqueue)
        │ 준비된 것만
        ▼
   이벤트 루프·디스패처
        │
        ▼
   핸들러 A  B  C (콜백)
```

| 구분 | 리액터 | 프로액터 | 이 PC에서 | 왜 |
|:-----|:-----|:------|:-------|:---|
| 통지 | I/O **준비** | I/O **완료** | 리액터 35 / 72 µs, 프로액터 51 / 112 µs | 프로액터는 완료 통지가 스레드 풀을 거친다 |
| read/write | 콜백이 직접 | 커널이 대신 | 핸들러 스레드 1개 vs 11~40개 | macOS·리눅스는 프로액터를 흉내 낸다 |
| 기반 | epoll, kqueue | IOCP, io_uring | | 커널이 완료 큐를 주느냐 |
| 자바 | `Selector` | `AsynchronousSocketChannel` | | |
| 한 바퀴 | 준비된 것을 묶어 돈다 | | 초당 25.7만, 이벤트당 3.4 µs, 준비된 키 1 → 80 | 바쁠수록 이벤트당 비용이 준다 |
| 규칙 | 콜백은 블로킹하면 안 된다 | | 콜백 1 ms면 남의 p99 1.1 ms, 넘기면 48 µs | 루프 하나가 전부다 |
| 멀티 리액터 | 메인은 accept, 서브는 연결을 나눠 든다 | | 서브 10개 5.5배, 계산 없으면 0.77배 | 코어를 다 쓰되 연결은 한 스레드에 |

[11](../11-event-driven-concurrency)장의 리액터 패턴은 단일 스레드 이벤트 루프 + 논블로킹 이벤트 + 콜백 위임이다. 이 PC의 루프 하나는 초당 25.7만 이벤트가 천장이고, 그 천장을 넘으려면 서브 리액터를 둔다. 대가는 코드다. 콜백으로 쪼개지고, 예외 하나가 루프를 죽이고, 상태를 객체 필드에 직접 들어야 한다.

### 6.4 비동기 통신

| 추상화 | 정체 | 이 PC에서 | 왜 |
|:-----|:-----|:-------|:---|
| 협동적 멀티태스킹 | 작업이 스스로 제어권을 반납하는 실행 모델 | 전환 51 ns vs OS 스레드 1,730 ns, 반납 안 하면 1,002 ms 정지 | 커널을 거치지 않는다. 대신 뺏을 수 없다 |
| 코루틴 | 멈췄다가 그 자리에서 재개하는 함수 | 제너레이터 `next()` 26 ns, 깊이 1,000에서도 52 ns | 프레임을 버리지 않고 접어 둔다 |
| 퓨처 | 미래에 완료될 결과의 자리표 | `get()`은 스레드 1,041개, 폴링은 코어 100%, `thenAccept`는 16 ns | 완료를 통지받느냐 되묻느냐 |
| async/await | 비동기를 순차 코드처럼 쓰는 문법 | `await` 25 ns, 10만 개 대기가 146 ms에 스레드 1개 | 컴파일러가 코루틴 변환을 한다 |
| 가상 스레드 | 코드는 블로킹, 실행은 논블로킹 | 10만 개 175 MB, OS 스레드 41개. `synchronized` 핀 10배(JDK 23), 커넥션 10개면 1만 개가 14초 | 상한은 스레드가 아니라 아래층 |

{{< callout type="info" >}}
10~12장은 하나의 이야기다. **"스레드가 비싸다"** 는 문제(10장)에 **"이벤트에만 반응하자"** 는 구조(11장)로 답했고, 그 구조가 만든 **"코드가 쪼개진다"** 는 새 문제를 **코루틴과 퓨처**(12장)로 풀었다. 각 단계는 앞 단계의 해법이 만든 새 문제를 푸는 과정이고, 마지막 단계의 가상 스레드는 첫 단계의 코드 모양으로 돌아온다.
{{< /callout >}}

| 10 | 동기 / 비동기 | 완료를 어떻게 알게 되는가 | 12.5 ms vs 42 ns |
| 10 | I/O 멀티플렉싱 | 한 번의 호출로 수천 소켓을 감시 | 1만 개를 21 MB, CPU 0% |
| 11 | 이벤트 루프 | 이벤트를 꺼내 콜백에 넘기는 무한 루프 | 초당 25.7만, 3.4 µs |
| 11 | 리액터 패턴 | 단일 스레드 + 논블로킹 + 콜백 위임 | 콜백 1 ms가 남의 1.1 ms |
| 11 | 프로액터 패턴 | 준비가 아니라 완료를 통지받는다 | 스레드 40개, 35 → 51 µs |
| 12 | 협동적 멀티태스킹 | 제어권을 스스로 반납하는 실행 모델 | 51 ns vs 1,730 ns |
| 12 | 코루틴 | 멈췄다가 그 자리에서 재개하는 함수 | `next()` 26 ns |
| 12 | 퓨처 / 프로미스 | 결과를 읽는 쪽 vs 값을 써 넣는 쪽 | `thenAccept` 16 ns |
| 12 | 가상 스레드 | 코드는 그대로, 스레드를 싸게 | 10만 개 175 MB |

## 8. 실전 의사결정 가이드

### 8.1 어떤 동시성 모델을 고를 것인가

```text
        워크로드는?
             │
   ┌─────────┴─────────┐
CPU 바운드          I/O 바운드
   │                    │
   ▼                    ▼
병렬화              동시 연결 수는?
스레드 풀           ┌────┴────┐
Fork-Join         적다      많다
코어 수만큼          │        │
                    ▼        ▼
             스레드 풀   이벤트 기반
              (단순)    가상 스레드
```

| 같은 작업 1,000개, 이 PC | 순차 | 풀 10 (코어 수) | 풀 100 | 풀 1,000 | 가상 스레드 | 이벤트 루프 1스레드 | 루프 + 워커 10 | 왜 |
|:-------------------|-----:|-----:|-----:|-----:|-----:|-----:|-----:|:---|
| 계산 10 ms | 10,083 ms | 1,512 | 1,497 | 1,491 | 1,715 | 10,571 | 1,570 | 코어 수(실효 6.8)가 천장. 루프는 스레드 하나라 순차와 같다 |
| 계산 1 ms + 대기 9 ms | 13,182 ms | 1,247 | 160 | 170 | 163 | 1,053 | 160 | 기다림은 스레드 수만큼 겹친다. 루프는 계산 1,000 × 1 ms를 혼자 한다 |
| 대기 10 ms | 12,070 ms | 1,199 | 127 | 56 | 13 | 12 | 13 | 계산이 없으면 스레드 하나로 충분하다 |

| 상황 | 권장 모델 | 왜 |
|:-----|:-------|:---|
| 이미지 변환, 암호화, 대량 정렬 | 스레드 풀 (코어 수) | 위 표 첫 줄. 풀 10과 1,000이 같고, 비동기는 무의미하다 |
| 배치 집계, 대규모 데이터 처리 | Fork-Join, 맵리듀스 | 데이터 분해가 자연스럽다. [07](../07-task-decomposition)장 6.2배 |
| 일반 웹 API (동시 수백) | 스레드 풀 + 블로킹 | 둘째 줄의 풀 100. 단순함이 최고의 미덕 |
| 게이트웨이·프록시 (동시 수만) | 이벤트 기반 (Netty, WebFlux) | 연결당 비용이 지배적. [10](../10-nonblocking-io)장 1만 개를 21 MB로 |
| 채팅·실시간 스트림 | 이벤트 기반 + 코루틴 | 대부분의 연결이 대기 상태. 셋째 줄 |
| 기존 블로킹 코드 확장 | 가상 스레드 (Java 21+) | 둘째·셋째 줄에서 풀 100과 같고 크기 고민이 없다 |
| 계산과 대기가 섞인 대규모 | 루프 + 워커 풀, 또는 가상 스레드 | 둘째 줄 160 ms. 루프 혼자는 1,053 ms |

표를 읽는 법은 한 줄이다. 계산은 코어 수까지, 기다림은 스레드 수만큼 겹친다. 계산 10ms짜리 1,000개는 무엇으로 돌려도 1.5초 언저리이고, 스레드 하나짜리 루프에 올리면 순차와 같은 10초다. 계산 1ms에 대기 9ms면 풀 10은 1,247ms인데 풀 100과 가상 스레드는 160ms다. 대기가 9ms이니 스레드 100개가 있어야 코어 10개가 논다. 이벤트 루프 혼자는 1,053ms로, 대기는 완벽히 겹쳤지만 계산 1,000 × 1ms를 혼자 하는 값이다. 계산을 워커 10개에 넘기면 160ms로 가상 스레드와 같아진다. 대기만 10ms면 가상 스레드와 루프가 12~13ms로 같고, 플랫폼 스레드 1,000개는 만드는 데만 56ms다.

### 8.2 자주 하는 실수

| 실수 | 무엇이 문제인가 | 이 PC에서 | 어디를 볼 것인가 |
|:-----|:-----------|:-------|:-----------|
| 워크로드 분류 없이 모델 선택 | 잘못된 축으로 최적화 | 계산 작업을 루프에 올리면 10,571 ms | [06](../06-multitasking)장 2절, 8.1절 |
| 스레드 풀 크기를 감으로 설정 | 과소는 병목, 과대는 전환 폭증 | 풀 10은 1,247 ms, 100은 163 ms, 4,000개는 35% 손해 | [05](../05-inter-process-communication)장 7.2절 |
| 코어만 늘리고 이득을 기대 | 순차 부분·임계 경로가 상한 | 순차 10%에 4.4배, 임계 경로 400 ms | [02](../02-sequential-and-parallel-execution)장 4절, [07](../07-task-decomposition)장 2절 |
| 락 순서를 팀마다 다르게 | 순환 대기 → 교착 | 558번 만에 멈춘다 | [09](../09-deadlock-and-starvation)장 2절 |
| 임계 구역에 I/O를 포함 | 락 보유 시간 폭증, 직렬화 | 락 점유 50%면 524 ms | [08](../08-race-conditions-and-synchronization)장 7절 |
| 이벤트 루프에서 블로킹 호출 | 서버 **전체** 정지 | 핸들러 10 ms가 모두의 12 ms | [11](../11-event-driven-concurrency)장 4.3절 |
| 코루틴에서 JDBC 직접 호출 | 캐리어 스레드가 묶인다 | `synchronized` 안 100 ms 잠이 1,085 ms | [12](../12-asynchronous-communication)장 2.4절 |
| 가상 스레드 무제한 생성 | DB 커넥션 풀이 먼저 붕괴 | 커넥션 10개에 1만 개가 14초 | [12](../12-asynchronous-communication)장 6절 |
| 동기화만 늘려 문제 회피 | 정확하지만 느린 코드 | 락 100%면 1.0배, `LongAdder`는 0.8 ns | [08](../08-race-conditions-and-synchronization)장 7절 |
| 테스트가 통과했으니 안전하다고 믿기 | 관찰이 증상을 바꾼다 | `println` 하나에 손실 38% → 0% | [08](../08-race-conditions-and-synchronization)장 1절 |

{{< callout type="warning" >}}
**동시성 버그는 재현되지 않는다.** 개발 환경에서 100번 통과한 코드가 운영에서 하루 한 번 깨지는 일이 흔하고, [08](../08-race-conditions-and-synchronization)장에서 로그 한 줄이 손실을 38%에서 0%로 감췄다. 그래서 "테스트로 잡는다"보다 **"구조적으로 불가능하게 만든다"** 가 훨씬 나은 전략이다. 불변 객체를 쓰고, 공유를 없애고, 소유권을 한 스레드에 고정하는 설계가 락을 정교하게 다루는 것보다 안전하다.
{{< /callout >}}

### 8.3 설계 시 점검 목록

| 점검 | 확인할 것 | 왜 |
|:-----|:-------|:---|
| 워크로드 | CPU 바운드인가 I/O 바운드인가. 측정했는가 | 모델 선택의 첫 갈림길 (8.1절 표) |
| 의존 관계 | 정말 독립인가, 임계 경로는 얼마인가 | 의존은 스레드가 몇이든 순차 |
| 공유 상태 | 공유를 없앨 수 있는가 (불변, 스레드 로컬, 단일 소유) | 가장 싼 동기화는 없는 동기화 |
| 락 | 범위가 최소인가, 획득 순서가 통일됐는가 | 폭이 값이고, 순서가 교착을 막는다 |
| 상한 | 스레드·커넥션·큐 크기에 상한이 있는가 | 상한 없는 풀은 4,070개에서 죽고, 아래층이 먼저 무너진다 |
| 블로킹 | 이벤트 루프·코루틴 경로에 블로킹이 없는가 | 하나가 전부를 세운다 |
| 실패 | 타임아웃·취소·배압이 설계돼 있는가 | 유계 큐 4가 지연을 138 ms에서 14 ms로 |
| 관측 | 큐 길이·활성 스레드·대기 시간을 볼 수 있는가 | 재현되지 않는 버그는 숫자로만 보인다 |

## 핵심 정리

```text
 동시성 12장의 요약
 기다리는 시간이 아까워서 시작했고
   (1~3장)

 프로세스·스레드로 만들었더니
   비싸고 다루기 까다로웠으며
   (4~6장)

 일을 잘 쪼개는 것이 관건이었는데
   (7장)

 공유하는 순간 다 깨져서
   락으로 막았더니 또 멈췄고
   (8~9장)

 결국 스레드를 줄이는 쪽으로 갔다
   논블로킹 → 이벤트 → 비동기
   (10~12장)
```

| 파트 | 핵심 | 왜 |
|:-----|:-----|:---|
| 목적 | 빠른 계산이 아니라 자원 활용. 코어 하나로도 동시성은 성립 | 기다림을 겹친다. 957 → 458 ms |
| 상한 | 암달의 순차 부분과 임계 경로가 천장 | 실효 코어 6.8, 임계 경로 400 ms |
| 분류 | CPU 바운드는 병렬화, I/O 바운드는 비동기 | 바꿔 적용하면 루프에 계산 10,571 ms |
| 재료 | 프로세스는 격리, 스레드는 공유. 스레드는 싸지만 무한하지 않다 | 26 µs, 88 KB, 4,069개 |
| 위험 | 공유하면 원자성·가시성·순서가 깨진다 | `count++` 80% 손실 |
| 동기화 | 안전을 사고 활성을 판다. 순서를 통일하고 폭을 줄인다 | 3 → 39 ns, 558번 만에 교착 |
| 최선 | 공유를 없애는 설계 | `LongAdder` 0.8 ns, 리액터의 단일 소유 |
| 대안 | 논블로킹 → 이벤트 루프 → 코루틴·퓨처 → 가상 스레드 | 4,069개 → 루프 하나가 1만 개 → 10만 개 175 MB |
| 규칙 | 물러나라. 루프와 코루틴 안에서 기다리지 마라 | 10 ms가 모두의 12 ms, 핀은 10배 |
| 기준 | 워크로드를 재고, 공유를 줄이고, 상한을 둔다 | 열두 장 내내 같았다 |

{{< callout type="info" >}}
**용어 정리**
- **기다림**: 동시성이 회수하는 유일한 것. 계산은 코어 수까지, 기다림은 스레드 수만큼 겹친다
- **의존**: 앞의 결과가 있어야 시작하는 관계. 스레드가 몇이든 순차이고, 가장 긴 사슬이 임계 경로
- **실효 코어**: 공식의 N에 넣어야 맞는 코어 수. 이 PC는 10코어에 6.8
- **공유**: 동시성의 모든 문제의 출처. 없애는 것이 가장 싼 해법
- **임계 구역**: 공유를 건드리는 구간. 값은 락이 아니라 폭과 경쟁
- **활성**: 값이 나오는 성질. 락을 걸수록 위험해진다(교착, 라이브락, 기아)
- **상한**: 스레드·커넥션·큐의 한도. 없으면 OS 천장이나 아래층에서 죽는다
- **양보 지점**: 협동형 실행 단위가 물러나는 자리. 없으면 하나가 전부를 세운다
- **캐리어 스레드**: 코루틴과 가상 스레드를 실제로 실행하는 OS 스레드. 코어 수만큼
- **배압**: 느린 쪽이 빠른 쪽을 세우는 장치. 유계 큐, 세마포어
- **다운스트림**: 요청이 결국 닿는 아래층 자원. 처리율의 진짜 상한
{{< /callout >}}
