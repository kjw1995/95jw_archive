앞 장에서 코어 열 개가 6.8개분의 힘을 냈다. 나머지 3.2개는 어디로 갔는가. 답은 하드웨어에 있고, 이 장은 프로그램 아래에 있는 그 하드웨어를 본다. 원리는 셋이다. 첫째, **병렬성은 한 층이 아니라 세 층에 있다.** 코어 하나 안에서 명령어 하나가 데이터 여럿을 처리하고, 칩 하나 안에서 코어 여럿이 각자 명령어를 처리하고, 네트워크 너머에서 컴퓨터 여럿이 일을 나눈다. 층이 올라갈수록 나눌 수 있는 일은 많아지고, 부품끼리 말을 주고받는 비용은 백 배씩 뛴다. 둘째, **하드웨어는 "같은 일을 여럿에게"와 "다른 일을 여럿에게"를 다른 장치로 한다.** 플린 분류가 이 구분이다. 같은 명령을 데이터 여럿에 한꺼번에 거는 SIMD는 분기가 없는 일에만 통하고, GPU는 그 SIMD를 수천 스레드로 밀어붙인 장치다. 서로 다른 명령 흐름을 나란히 돌리는 MIMD가 멀티코어이고, 분기가 많은 보통의 프로그램은 여기서 돈다. 셋째, **프로그램은 하드웨어를 직접 만지지 않고 런타임을 거쳐 만진다.** JVM이 스레드를 운영체제 스레드에 얹고, JIT이 내 루프를 벡터 명령으로 바꾸고, 힙의 크기를 정한다. 그 덕에 하드웨어를 몰라도 프로그램은 돌지만, 성능은 그 아래 층이 설명한다. 이 PC(Apple M4 10코어, JDK 23)에서 스레드·프로세스·소켓·인터넷의 왕복 시간을 재고, JIT의 자동 벡터화를 끄고 켜며 같은 루프의 속도를 재고, 메탈(Metal)로 GPU에 같은 계산을 시켜 CPU 열 코어와 비교하고, JIT을 꺼 봤다.

## 1. 하드웨어와 프로그램 실행

### 1.1 세 층의 처리 자원

```text
[코어 안]  명령어 하나가 데이터 넷
[칩 안]    코어 열 개가 메모리를 공유
┌────┬────┬────┬────┐┌──────────┐
│ P  │ P  │ P  │ P  ││ E × 6    │
└────┴────┴────┴────┘└──────────┘
         통합 메모리 16 GB
[기계 밖]  컴퓨터 여럿이 네트워크로
```

| 층 | 무엇이 여럿인가 | 어떻게 통신하나 | 이 PC | 왜 그 비용인가 |
|:---|:------------|:-------------|:------|:------------|
| 코어 안 (SIMD) | 한 명령이 다루는 데이터 | 같은 레지스터 안 | 128비트, float 4개 | 통신이 없다 |
| 멀티코어 | 코어 | 공유 메모리, 캐시 | 성능 4 + 효율 6, L2 16MB + 4MB | 캐시 라인 128바이트가 코어 사이를 오간다 |
| 멀티 프로세서 | CPU 칩 | 칩 사이 버스 | 없음 | 칩 사이에 캐시를 맞춰야 한다 |
| 클러스터 | 컴퓨터 | 네트워크 | 인터넷 너머 6.7 ms | 패킷이 케이블과 라우터를 지난다 |

현대 하드웨어는 처리 자원을 여러 층에 두고 있다. 코어 하나 안에도 병렬성이 있고(2절), 칩 하나에 코어가 열 개 있고, 컴퓨터를 네트워크로 묶으면 코어가 수천 개가 된다. 어느 층을 쓰느냐는 일을 얼마나 잘게 나눌 수 있느냐만이 아니라, 나눈 조각이 **서로 얼마나 자주 말을 주고받느냐**로 정한다. 층마다 통신 비용이 다르기 때문이다. [02](../02-sequential-and-parallel-execution)장 2.3절에서 1,000개짜리 배열 합은 나누는 비용이 일보다 커서 병렬이 느렸다. 그 "나누는 비용"의 실체가 이 통신이다.

### 1.2 통신 비용의 사다리

```java
// 스레드 둘이 공유 변수로 핑퐁
var flag = new AtomicInteger(0);

// 상대: 1이 되면 0으로 되돌린다
while (flag.get() != 1)
    Thread.onSpinWait();
flag.set(0);

// 나: 1로 바꾸고 0이 되길 기다린다
flag.set(1);
while (flag.get() != 0)
    Thread.onSpinWait();
```

| 주고받는 사이 | 왕복 | 앞 단계의 몇 배 | 왜 |
|:-----------|-----:|-----------:|:---|
| 스레드 ↔ 스레드, 공유 변수 | 72 ns | 기준 | 캐시 라인 하나가 코어 사이를 오간다 |
| 스레드 ↔ 스레드, 블로킹 큐 | 3.7 µs | 51배 | 잠든 스레드를 스케줄러가 깨운다 |
| 프로세스 ↔ 프로세스, 파이프 | 4.7 µs | 1.3배 | 커널을 두 번 지난다 |
| 프로세스 ↔ 프로세스, TCP 루프백 | 13 µs | 2.8배 | TCP 스택을 두 번 지난다 |
| 컴퓨터 ↔ 컴퓨터, 인터넷 | 6.7 ms | 500배 | 빛의 속도와 라우터 |

첫째 원리다. 이 PC에서 바이트 하나를 보내고 답을 받는 왕복 시간을 층마다 쟀다. 같은 칩의 두 코어가 공유 변수로 주고받으면 72ns다. 스레드가 기다리다 잠들고 스케줄러가 깨우면 3.7µs, 쉰 배가 넘는다. 프로세스를 넘고 소켓을 넘으면 µs 단위가 되고, 기계를 넘으면 ms가 된다. 맨 위와 맨 아래가 십만 배 차이다. 조각 하나의 일이 이 비용보다 작으면 그 층에서는 나눌 수 없다. 72ns면 float 곱셈 수백 개를 할 수 있고, 6.7ms면 수천만 개를 할 수 있다. 그래서 코어 사이에는 배열 한 조각도 나눌 수 있지만, 컴퓨터 사이에는 파일 하나나 요청 하나 단위로만 나눈다. 스레드와 프로세스가 무엇인지는 [04](../04-concurrency-ingredients)장, 파이프와 소켓은 [05](../05-inter-process-communication)장 3절과 5절, 잠든 스레드를 깨우는 비용은 [06](../06-multitasking)장 3절이다.

## 2. 플린 분류 (Flynn's Taxonomy)

### 2.1 네 칸

```text
            데이터 하나   데이터 여럿
명령어 하나    SISD         SIMD
              코어 하나     NEON, GPU
명령어 여럿    MISD         MIMD
              (드묾)        멀티코어
```

| 분류 | 명령어 | 데이터 | 실물 | 왜 이 칸인가 |
|:-----|:-----|:-----|:-----|:----------|
| SISD | 하나 | 하나 | 벡터화 안 된 루프 | 한 명령에 원소 하나 |
| SIMD | 하나 | 여럿 | NEON, AVX, GPU | 한 명령에 원소 넷에서 수천 |
| MISD | 여럿 | 하나 | 비행 제어의 다중화 | 같은 데이터를 다른 방식으로 검산 |
| MIMD | 여럿 | 여럿 | 멀티코어, 클러스터 | 코어마다 자기 명령 흐름 |

둘째 원리다. 1972년 마이클 플린은 컴퓨터를 두 질문으로 갈랐다. 같은 순간에 실행되는 **명령어**가 하나인가 여럿인가, 그 명령어가 다루는 **데이터**가 하나인가 여럿인가. 답의 조합이 네 칸이고, 그중 두 칸이 오늘의 병렬 하드웨어 전부다. 같은 명령을 데이터 여럿에 거는 SIMD와, 다른 명령을 각자의 데이터에 거는 MIMD다. 둘은 잘하는 일이 다르고, 이 PC 한 대 안에 둘 다 들어 있다.

### 2.2 SISD와 SIMD: 한 명령에 원소 하나와 넷

```text
[SISD] 한 번에 하나
t1  a0*b0
t2  a1*b1
t3  a2*b2
t4  a3*b3

[SIMD] 한 명령에 넷 (128비트 NEON)
t1  a0*b0  a1*b1  a2*b2  a3*b3
```

```java
// 평범한 루프. JIT이 벡터 명령으로
for (int i = 0; i < n; i++)
    c[i] = a[i] * b[i] + c[i];

// 같은 일을 Vector API로 직접
static final VectorSpecies<Float> SP =
    FloatVector.SPECIES_PREFERRED;
// 이 PC: 4 lanes, 128비트

for (int i = 0; i < n; i += 4) {
    var va = FloatVector
        .fromArray(SP, a, i);
    var vb = FloatVector
        .fromArray(SP, b, i);
    var vc = FloatVector
        .fromArray(SP, c, i);
    va.mul(vb).add(vc)
        .intoArray(c, i);
}
```

| 루프 | 걸린 시간 | 원소당 | 왜 |
|:-----|--------:|------:|:---|
| 평범한 루프, 자동 벡터화 끔 | 229 ms | 0.44 ns | 한 명령에 원소 하나 (SISD) |
| 평범한 루프, 기본 | 72 ms | 0.14 ns | JIT이 한 명령에 원소 넷으로 바꿨다 (SIMD) |
| Vector API로 직접 | 71 ms | 0.14 ns | 같은 NEON 명령을 내가 쓴 것 |
| 콜라츠 (원소마다 분기) | 110 ms | 140 ns | 벡터화 못 한다. 끄나 켜나 111 ms |

이 PC에서 float 26만 개짜리 배열 셋으로 `c = a × b + c`를 2,000번, 원소 5.2억 개를 돌렸다. 평범한 루프가 72ms인데 JIT의 자동 벡터화를 끄면(`-XX:-UseSuperWord`) 229ms, 3.2배 느려진다. 내 코드에는 벡터 명령이 한 줄도 없다. JIT이 루프를 보고 "이 원소 넷은 서로 독립이고 같은 연산이다"를 알아채서 128비트 NEON 명령 하나로 넷을 처리하게 바꾼 것이다. Vector API로 같은 명령을 직접 쓰면 71ms로 같다. 넷이 아니라 3.2배인 것은 명령 하나가 넷을 처리해도 메모리에서 읽고 쓰는 시간은 줄지 않아서다.

```java
// 원소마다 분기와 반복 횟수가 다르다
long v = x[i]; int steps = 0;
while (v != 1) {
    v = (v & 1) == 0
        ? v >> 1 : 3 * v + 1;
    steps++;
}
```

마지막 줄이 SIMD의 조건이다. 원소마다 "짝수면 반으로, 홀수면 세 배 더하기 1"을 1이 될 때까지 반복하는 콜라츠 수열은 원소마다 분기가 다르고 반복 횟수도 다르다. 한 명령으로 넷을 처리하려면 넷이 **같은 명령**을 원해야 하는데, 이 넷은 각자 다른 길을 간다. 자동 벡터화를 끄나 켜나 110ms 안팎으로 같은 이유다. 원소당 140ns로 곱셈-덧셈의 천 배가 드는 것은 분기가 많아서가 아니라 원소마다 평균 130번을 돌기 때문이고, 그 130번을 넷씩 묶을 수 없다는 것이 요점이다.

{{< callout type="info" >}}
**SIMD가 통하는 일의 조건은 셋이다.** 모든 원소에 같은 연산을 하고, 원소끼리 독립이고, 분기가 없거나 드물어야 한다. 이미지의 모든 픽셀에 같은 필터, 행렬의 모든 원소에 같은 곱셈, 모든 입자에 같은 물리 법칙이 그렇다. 이 조건을 극단까지 밀면 GPU가 된다(3절). 조건에 안 맞는 일은 JIT이 알아서 벡터화하지 않으니, 배열 루프가 기대만큼 빠르지 않다면 루프 안의 분기부터 의심한다. 병렬 스트림이 왜 공짜가 아닌지는 [자바 기초 14](../../java/basics/14-lambda-stream)장 5절이다.
{{< /callout >}}

### 2.3 MIMD: 코어마다 자기 명령 흐름

```text
코어1  명령 흐름 A ── 데이터 A
코어2  명령 흐름 B ── 데이터 B
코어3  명령 흐름 C ── 데이터 C
     각자 다른 프로그램을 돈다
```

| 스레드 | 처리량 | 코어 하나 대비 | 왜 |
|------:|------:|----------:|:---|
| 1 | 7.3 G원소/초 | 1.0 | 성능 코어 하나의 SIMD |
| 2 | 17.0 G원소/초 | 2.3 | 성능 코어 둘 |
| 4 | 29.6 G원소/초 | 4.1 | 성능 코어 넷 |
| 6 | 32.3 G원소/초 | 4.4 | 효율 코어가 조금 보탠다 |
| 10 | 30.5 G원소/초 | 4.2 | 효율 코어의 벡터 유닛이 좁고 L2가 4MB뿐 |

MIMD는 코어마다 자기 명령 흐름을 갖는 구조이고, 멀티코어 CPU가 그것이다. [02](../02-sequential-and-parallel-execution)장의 실험이 전부 MIMD였다. 여기서는 두 층을 곱해 봤다. 2.2절의 SIMD 루프를 스레드마다 자기 배열로 돌린 것이다. 코어 하나가 초당 73억 원소, 성능 코어 넷이 296억으로 거의 비례하고, 그 위로는 늘지 않는다. 효율 코어 여섯이 보태는 것이 10%도 안 된다. 앞 장의 제곱근 계산에서는 효율 코어가 6.8배까지 밀어 올렸는데 여기서는 아니다. 효율 코어는 벡터 유닛이 성능 코어보다 좁고, 효율 코어 여섯이 나눠 쓰는 L2 캐시가 4MB라 스레드마다 3MB인 배열이 들어가지 않는다. 배열을 256KB로 줄이면 열 스레드가 388억 원소로 올라간다. 스레드 둘이 하나의 두 배를 넘는 것은 스레드 하나만 돌 때 그 스레드가 늘 성능 코어에 있지는 않기 때문으로 보인다.

| 구분 | SIMD | MIMD | 왜 갈라 보나 |
|:-----|:-----|:-----|:-----------|
| 나누는 것 | 데이터 | 명령 흐름 | 같은 일을 여럿에게 vs 다른 일을 여럿에게 |
| 단위 | 레지스터 한 줄 (넷) | 코어 (열) | 곱하면 40 |
| 조건 | 분기 없음, 독립 | 독립 | SIMD가 더 까다롭다 |
| 누가 만드나 | JIT, 컴파일러 | 나 (스레드) | 2.2절은 코드를 안 바꿨고 여기는 스레드를 만들었다 |
| 실물 | NEON, AVX, GPU | 멀티코어, 클러스터 | 이 PC에 둘 다 있다 |

### 2.4 MISD

여러 명령이 같은 데이터 하나를 처리하는 칸이다. 상용 컴퓨터에는 거의 없고, 우주선이나 비행기의 제어 컴퓨터가 같은 센서 값을 서로 다른 알고리즘 셋으로 계산해 다수결로 답을 내는 것이 이 칸의 예다. 목적이 속도가 아니라 **안전**이라 이 시리즈에서는 더 다루지 않는다.

## 3. CPU와 GPU

### 3.1 굵은 코어 몇 개와 가는 코어 수천 개

```text
CPU: 굵은 코어 몇 개
┌──────┐┌──────┐  캐시 크고
│ 코어 ││ 코어 │  분기를 예측하고
└──────┘└──────┘  한 스레드가 빠르다

GPU: 가는 코어 수천 개
┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐
└─┘└─┘└─┘└─┘└─┘└─┘└─┘└─┘
┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐┌─┐
└─┘└─┘└─┘└─┘└─┘└─┘└─┘└─┘
같은 명령을 스레드 묶음마다
```

| 특성 | CPU | GPU | 왜 |
|:-----|:----|:----|:---|
| 코어 | 이 PC 10개. 크고 빠르다 | 이 PC 10코어에 스레드 수천 | 한 스레드를 빨리 vs 많은 스레드를 한꺼번에 |
| 명령 흐름 | 코어마다 다르게 (MIMD) | 한 명령을 스레드 묶음에 (SIMD) | 2절의 두 칸 |
| 분기 | 예측해서 건너뛴다 | 묶음 안에서 갈리면 양쪽을 다 돈다 | 분기가 GPU의 적인 이유 |
| 메모리 기다리기 | 큰 캐시로 안 기다리게 | 다른 묶음으로 바꿔 숨긴다 | 스레드가 수천이라 항상 할 일이 있다 |
| 잘하는 일 | 웹 서버, DB, 비즈니스 로직 | 행렬, 픽셀, 입자, 학습 | 분기 많은 일 vs 같은 연산 대량 |
| 이 PC의 메모리 | 통합 메모리 16GB | 같은 메모리 | 복사 없이 같은 배열을 본다 |

CPU와 GPU는 같은 트랜지스터 예산을 정반대로 쓴 장치다. CPU는 코어 하나를 크게 만든다. 큰 캐시, 분기 예측, 명령 순서를 바꿔 실행하는 회로가 그 코어에 들어가고, 그래서 한 스레드가 빠르다. GPU는 그 회로를 다 빼고 대신 작은 코어를 수천 개 넣는다. 한 코어는 느리지만, 같은 명령을 수천 스레드에 걸 수 있고, 어떤 스레드가 메모리를 기다리면 다른 스레드 묶음을 돌려 기다림을 숨긴다. 2.2절의 SIMD 조건이 그대로 GPU의 조건이고, 거기에 "원소가 수천만 개"가 붙는다.

### 3.2 이 PC에서 재 보기

```cpp
// Metal 커널. 원소마다 GPU 스레드 하나
kernel void poly(
    device const float* a,
    device const float* b,
    device float* c,
    uint i [[thread_position_in_grid]])
{
    float x = a[i], y = b[i];
    for (int k = 0; k < 1024; k++)
        x = x * y + 0.5f;
    c[i] = x;
}
```

| 원소 1,677만 개에 | CPU 1스레드 | CPU 10스레드 | GPU | 왜 |
|:--------------|----------:|-----------:|----:|:---|
| 곱셈-덧셈 1번 | 2.9 ms | 2.6 ms | 3.1 ms | 셋 다 메모리 대역폭에 막힌다 |
| 곱셈-덧셈 64번 사슬 | 67 ms | 12.9 ms | 3.4 ms | GPU는 아직도 메모리 시간뿐 |
| 곱셈-덧셈 1,024번 사슬 | 1,533 ms | 228 ms | 50 ms | 계산이 병목. GPU가 열 코어의 4.5배 |

같은 배열을 스위프트로 CPU에서, 메탈로 GPU에서 계산했다. 첫 줄이 뜻밖이다. 원소마다 곱셈-덧셈을 한 번만 하면 CPU 한 스레드, 열 스레드, GPU가 전부 3ms 근처다. 배열 셋을 한 번 훑는 데 192MB를 읽고 쓰고, 이 PC의 메모리가 그것을 3ms에 옮긴다. 계산이 아니라 **메모리 대역폭**이 병목이고, CPU와 GPU가 같은 통합 메모리를 쓰니 같은 벽에 막힌다. 곱셈-덧셈을 64번 사슬로 걸면 CPU는 늘어나는데 GPU는 3.4ms 그대로다. 수천 스레드가 메모리를 기다리는 사이에 계산이 끝난다. 1,024번을 걸어야 GPU가 계산에 막히기 시작하고, 그때 열 코어의 4.5배, 한 코어의 30배다. 초당 부동소수점 연산으로 바꾸면 한 코어 22G, 열 코어 151G, GPU 685G다.

| CPU 1스레드, 64번 사슬 | 걸린 시간 | 왜 |
|:--------------------|--------:|:---|
| 원소 하나씩 사슬을 끝까지 | 561 ms | 곱셈-덧셈 하나가 앞 결과를 기다린다. 코어가 논다 |
| 원소 16개를 한 묶음으로 | 67 ms | 독립인 사슬 16개가 파이프라인을 채운다 |

CPU 쪽에도 배울 것이 있다. 원소 하나의 사슬 64번을 순서대로 하면 561ms인데, 원소 16개를 한 묶음으로 잡아 사슬 16개를 번갈아 진행하면 67ms, 8.4배다. 곱셈-덧셈 하나는 앞 결과가 나와야 시작할 수 있어서 코어의 파이프라인이 그 사이 논다. 독립인 사슬을 여럿 주면 그 빈 자리가 찬다. GPU가 수천 스레드로 하는 지연 숨기기를 CPU 코어 하나는 독립인 계산 여럿으로 한다. [02](../02-sequential-and-parallel-execution)장 1절의 의존 사슬이 코어 안에서도 같은 벽이다.

{{< callout type="warning" >}}
**GPU로 보내기 전에 두 가지를 잰다.** 원소당 계산이 메모리 읽기보다 훨씬 많은가, 그리고 원소가 수천만 개인가. 첫째가 아니면 위 표의 첫 줄처럼 CPU와 같고, 둘째가 아니면 GPU를 깨우고 일을 넘기는 고정 비용이 계산보다 크다. 배열 수백만 개에 같은 연산이면 JIT의 자동 벡터화가 이미 3배를 주고 있으니(2.2절) 거기서 끝내는 것이 보통 맞다.
{{< /callout >}}

## 4. 런타임 시스템

### 4.1 프로그램과 하드웨어 사이의 층

```text
┌────────────────────────┐
│ 애플리케이션 (내 코드) │
├────────────────────────┤
│ 런타임 (JVM)           │
│ 스레드 · 힙 · JIT · GC │
├────────────────────────┤
│ 운영체제               │
│ 스케줄러 · 시스템 호출 │
├────────────────────────┤
│ 하드웨어               │
│ 코어 · 캐시 · 메모리   │
└────────────────────────┘
```

| JVM이 하는 일 | 내 코드에서 | 실제로 일어나는 것 | 이 PC에서 본 것 | 왜 필요한가 |
|:------------|:---------|:--------------|:-------------|:----------|
| 스레드 | `new Thread`, 스레드 풀 | OS 스레드를 1:1로 만든다 | Java 스레드 6개일 때 OS 스레드 27개 | GC와 JIT도 스레드로 돈다 |
| JIT | 평범한 루프 | 네이티브 코드로, 벡터 명령까지 | JIT을 끄면 12배, 벡터화만 끄면 3.2배 | 바이트코드는 하드웨어를 모른다 |
| 메모리 | `new` | 힙에서 할당하고 GC가 회수 | 최대 힙 4,096MB, 물리 메모리의 4분의 1 | 코어마다 다른 캐시를 하나의 힙으로 보이게 |
| 동기화 | `synchronized` | 모니터와 메모리 배리어 | [08](../08-race-conditions-and-synchronization)장 | 코어 사이의 캐시를 맞춘다 |
| 하드웨어 정보 | `availableProcessors()` | OS에 묻는다 | 10 | 스레드 풀 크기의 출발점 |

```java
var rt = Runtime.getRuntime();
rt.availableProcessors();   // 10
rt.maxMemory() >> 20;       // 4,096 MB
Thread.getAllStackTraces()
    .size();                // 6
// ps -M <pid> → OS 스레드 27개
```

```bash
java JitTest.java              # 10 ms
java -Xint JitTest.java        # 120 ms
java -XX:-UseSuperWord ...     # 3.2배
```

셋째 원리다. 내 코드는 하드웨어를 직접 만지지 않는다. `new Thread`라고 쓰면 JVM이 운영체제에 스레드를 만들어 달라고 하고, 운영체제의 스케줄러가 그 스레드를 코어에 올린다([06](../06-multitasking)장 5절). 평범한 루프를 쓰면 JIT이 이 PC의 NEON 명령으로 바꾼다. 위 표의 숫자가 그 층이 하는 일의 크기다. 제곱근 2,000만 번이 JIT을 켜면 10ms, 끄고 바이트코드를 해석만 하면 120ms다. 프로그램을 시작만 했는데 운영체제에는 스레드가 27개 있다. 내가 아는 여섯 개 말고 GC 스레드와 JIT 컴파일러 스레드가 돌고 있다. 런타임이 하는 일을 몰라도 프로그램은 돌지만, 2.3절에서 효율 코어가 벡터 연산을 거의 못 거든 것이나 3.2절에서 CPU와 GPU가 같은 3ms에 막힌 것은 런타임 아래 층을 알아야 설명된다.

### 4.2 런타임이 주는 추상화와 그 아래

| 추상화 | 감추는 것 | 드러나는 순간 | 어디서 |
|:------|:--------|:-----------|:------|
| 스레드는 다 같다 | 성능 코어와 효율 코어 | 스레드 10개가 6.8개분 | 이 장 2.3절, [02](../02-sequential-and-parallel-execution)장 4절 |
| 메모리는 하나다 | 코어마다 다른 캐시 | 한 스레드가 쓴 값을 다른 스레드가 못 본다 | [08](../08-race-conditions-and-synchronization)장, [자바 동시성 03](../../java/concurrency/03-object-sharing)장 |
| 스레드는 싸다 | OS 스레드 하나의 스택과 전환 비용 | 스레드 수천 개에서 느려진다 | [06](../06-multitasking)장 3절, [12](../12-asynchronous-communication)장 6절 |
| 힙은 넓다 | 물리 메모리의 4분의 1 | OutOfMemoryError | [JVM 메모리 관리](../../java/jvm/memory-management) |
| 루프는 루프다 | 벡터화 여부 | 분기 하나로 3.2배가 사라진다 | 이 장 2.2절 |

추상화는 감추는 것으로 값을 한다. 스레드가 코어 종류를 모르니 코드가 단순하고, 힙이 하나로 보이니 포인터 걱정이 없다. 대신 감춘 것이 드러나는 순간이 있고, 그 순간마다 아래 층으로 내려가야 한다. 위 표의 세 번째 줄이 이 시리즈 뒷부분의 동기다. JVM 스레드가 OS 스레드와 1:1이라 스레드 하나에 스택 수백 KB와 전환 비용이 들고, 그래서 요청마다 스레드를 주는 서버는 수천 명에서 막힌다. 런타임이 OS 스레드 위에 자기 스레드를 여럿 얹는 것(사용자 수준 스레드, 코루틴, 자바의 가상 스레드)이 그 답이고 [12](../12-asynchronous-communication)장에서 본다. 스레드를 직접 만드는 대신 풀에 넘기는 이유는 [자바 기초 13](../../java/basics/13-thread)장 7절이다.

## 5. 문제에 맞는 장치 고르기

| 문제 | 장치 | 이 장의 근거 | 왜 |
|:-----|:-----|:----------|:---|
| 웹 서버, DB, 비즈니스 로직 | CPU (MIMD) | 콜라츠는 벡터화가 안 됐다 | 요청마다 분기가 다르다 |
| 배열 수백만 개에 같은 연산 | CPU의 SIMD | 평범한 루프가 3.2배 | JIT이 알아서 한다. GPU는 시동 비용이 더 크다 |
| 원소 수천만 개, 원소당 계산 많음 | GPU (SIMD) | 1,024번 사슬에서 열 코어의 4.5배 | 스레드 수천이 지연을 숨긴다 |
| 배열을 한 번 훑는 일 | 어느 쪽이든 같다 | 곱셈-덧셈 1번은 셋 다 3 ms | 메모리 대역폭이 병목 |
| 한 기계로 안 되는 양 | 클러스터 | 통신 13 µs → 6.7 ms | 조각을 요청·파일 단위로 키워야 |
| 기다림이 대부분인 일 | 코어 수와 무관 | [02](../02-sequential-and-parallel-execution)장 3절 | 동시성이면 되고 병렬성은 필요 없다 |

장치를 고르는 질문은 둘이다. 원소마다 같은 연산인가 다른 연산인가, 그리고 조각 하나의 계산이 그 층의 통신 비용보다 큰가. 첫 질문이 SIMD와 MIMD를 가르고(2절), 둘째 질문이 코어·기계·클러스터 중 어느 층인지를 가른다(1절). 둘 다 추측이 아니라 측정으로 답한다. 이 장의 모든 표가 그 측정이었고, 같은 코드가 어느 층에서 도느냐에 따라 3ms와 1,533ms 사이를 오갔다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 세 층 | 코어 안, 칩 안, 기계 밖 | 층마다 통신 비용이 백 배씩 |
| 통신 사다리 | 72 ns → 3.7 µs → 13 µs → 6.7 ms | 조각은 통신 비용보다 커야 한다 |
| 플린 분류 | 명령 하나/여럿 × 데이터 하나/여럿 | SIMD와 MIMD가 오늘의 두 칸 |
| SIMD | 한 명령에 원소 넷 | 평범한 루프 3.2배, 분기 있으면 0배 |
| MIMD | 코어마다 명령 흐름 | 성능 코어 넷까지 4.1배, 효율 코어는 조금 |
| 두 층의 곱 | SIMD × 코어 | 코어 하나 73억에서 열 코어 305억 원소/초 |
| CPU | 굵은 코어 몇 개, 분기 예측 | 한 스레드가 빠르다 |
| GPU | 가는 코어 수천, 묶음 교체로 지연 숨김 | 1,024번 사슬에서 열 코어의 4.5배 |
| 메모리 대역폭 | 한 번 훑는 일은 장치 무관 | 셋 다 3 ms |
| 지연 숨기기 | 독립인 계산을 여럿 | 사슬 16개로 8.4배 |
| 런타임 | 스레드·JIT·힙·동기화의 층 | JIT 끄면 12배, OS 스레드 27개 |
| 추상화의 값 | 감춘 것이 드러날 때 아래로 | 스레드는 다 같지 않고 메모리는 하나가 아니다 |

{{< callout type="info" >}}
**용어 정리**
- **SIMD / MIMD**: 한 명령을 데이터 여럿에 / 여러 명령을 각자의 데이터에
- **SISD / MISD**: 한 명령에 데이터 하나 / 여러 명령에 데이터 하나(드묾)
- **NEON, AVX**: ARM과 x86의 CPU 안 SIMD 명령. 이 PC는 128비트 NEON, float 4개
- **자동 벡터화**: JIT이나 컴파일러가 평범한 루프를 SIMD 명령으로 바꾸는 것
- **Vector API**: 자바에서 SIMD 명령을 직접 쓰는 API (인큐베이터)
- **성능 코어 / 효율 코어**: 크고 빠른 코어 / 작고 전력이 적은 코어. 벡터 유닛 폭이 다르다
- **캐시 라인**: 코어 사이를 오가는 메모리의 단위. 이 PC는 128바이트
- **메모리 대역폭**: 초당 옮길 수 있는 바이트. 한 번 훑는 일의 천장
- **통합 메모리**: CPU와 GPU가 같은 메모리를 쓰는 구조. 복사가 없다
- **커널(GPU)**: GPU 스레드마다 실행되는 함수
- **지연 숨기기**: 기다리는 동안 독립인 다른 일을 하는 것. GPU는 스레드 묶음으로, CPU는 독립인 사슬로
- **런타임 시스템**: 애플리케이션과 OS·하드웨어 사이의 층. 자바에서는 JVM
- **JIT**: 실행 중에 바이트코드를 네이티브 코드로 바꾸는 컴파일러
- **사용자 수준 스레드**: OS 스레드 위에 런타임이 얹는 스레드. 코루틴, 가상 스레드
{{< /callout >}}
