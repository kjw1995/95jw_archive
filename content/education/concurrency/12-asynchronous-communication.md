[11](../11-event-driven-concurrency)장은 비동기 통신을 개념으로 다뤘다. 던져 두고 가고, 완료는 이벤트로 받는다. 이 장은 그것을 어떻게 코드로 만드는가다. 원리는 셋이다. 첫째, **비동기가 회수하는 것은 기다림이고, 독립인 기다림만 겹친다.** 300ms, 200ms, 250ms짜리 호출 셋을 차례로 부르면 771ms이고 겹치면 309ms다. 그러나 앞의 답이 있어야 다음을 부르는 사슬은 어떻게 해도 777ms다. 둘째, **비동기를 떠받치는 실행 모델은 협동적 멀티태스킹이다. 작업이 스스로 물러나고, 전환은 함수 호출 값이다.** OS 스레드 사이의 전환이 1.7µs일 때 가상 스레드 속의 `Continuation` 전환은 51ns이고, 그래서 OS 스레드 41개 위에 가상 스레드 10만 개가 올라간다. 대신 물러나지 않는 작업 하나가 전부를 세운다. 셋째, **추상화는 둘이다. 코루틴은 함수를 멈췄다 잇고, 퓨처는 결과의 자리를 판다. 그 둘을 다시 순차 코드처럼 읽게 만든 것이 async/await와 가상 스레드다.** 이 PC(Apple M4 10코어, macOS, JDK 23, Node.js 25, Python 3.9)에서 독립인 호출 셋과 의존하는 셋의 시간, 예외가 났을 때 스택 트레이스에 내 코드가 몇 프레임 남는지, OS 스레드·가상 스레드·`Continuation`·파이썬 제너레이터·자바스크립트 `await`의 전환 비용, 잠든 스레드 3,000개와 10만 개의 메모리와 OS 스레드 수, 양보하지 않는 가상 스레드와 `synchronized` 안에서 잠든 가상 스레드가 남을 얼마나 세우는지, 결과 1,000개를 `get()`·`isDone()` 폴링·`thenAccept`로 기다릴 때의 스레드와 CPU, `thenApply` 콜백이 어느 스레드에서 도는지, async 함수 10만 개의 대기, 그리고 가상 스레드 1만 개가 커넥션 10개 앞에 줄을 설 때 걸리는 시간을 쟀다.

## 1. 비동기 통신이란

> **비동기 통신**은 오래 걸리는 작업이 블로킹을 일으키지 않게 하면서 단일 프로세스로 실행하는 개발 기법이다. 작업을 백그라운드에서 시작한 뒤 완료를 기다리지 않고 다음 작업으로 넘어간다.

```text
동기 호출
호출자 ██──────대기──────██
피호출        ████████
   총 시간 = 처리 시간의 합

비동기 호출
호출자 ██──다른 일──██(결과)
피호출   ████████
   대기 시간을 일로 회수
```

```java
// 독립인 셋: 771 ms가 309 ms로
var u = supplyAsync(() -> user(id));
var p = supplyAsync(() -> point(id));
var c = supplyAsync(() -> coupon(id));
CompletableFuture.allOf(u, p, c).join();
render(u.join(), p.join(), c.join());
```

| 300·200·250 ms가 걸리는 호출 셋 | 걸린 시간 | 왜 |
|:---------------------------|-------:|:---|
| 동기, 차례로 | 771 ms | 셋의 합 |
| 비동기, `allOf` | 309 ms | 셋 중 가장 긴 것. 기다림 세 개를 겹쳤다 |
| 비동기, `anyOf` | 206 ms | 가장 짧은 것이 오면 끝 |
| 의존 사슬, `thenCompose` | 777 ms | 앞의 답이 있어야 다음을 시작한다. 겹칠 기다림이 없다 |
| 가상 스레드 셋 + `get()` | 311 ms | 코드는 동기인데 기다림이 겹친다. 6절 |

첫째 원리다. 핵심은 빨리 계산하기가 아니라 기다리는 시간을 회수하기다. 세 호출이 각각 서버의 답을 기다리는 동안 이 스레드는 [04](../04-concurrency-ingredients)장 5절의 `WAITING`이고, 그 세 기다림을 겹치면 771ms가 309ms가 된다. 셋 중 가장 긴 것이 남는다. 반대로 `findPoint`가 `findUser`의 답을 받아야 시작한다면 겹칠 기다림이 없고 777ms가 그대로다. [07](../07-task-decomposition)장 2절의 의존 그래프가 여기서도 상한이다. 비동기로 바꾸기 전에 그래프부터 그려 보는 이유다.

### 1.1 비동기성은 구현이 아니라 성질이다

| 계층 | 비동기가 나타나는 모습 | 왜 그 층에도 있나 |
|:-----|:----------------|:-------------|
| 하드웨어 | DMA. CPU 없이 장치가 메모리에 직접 쓴다 | 전송이 끝날 때까지 CPU가 바이트를 나르면 낭비다 |
| OS 커널 | 인터럽트, `epoll`·`kqueue`, `io_uring`의 완료 큐 | 준비나 완료를 커널이 알려 주면 스레드가 안 잔다 |
| 언어 런타임 | 코루틴, `async`/`await`, 이벤트 루프 | 기다림 지점에서 함수를 접어 둔다 |
| 라이브러리 | `CompletableFuture`, Reactor, RxJava | 결과와 완료를 값으로 다룬다 |
| 시스템 아키텍처 | 메시지 큐(Kafka, RabbitMQ), 이벤트 소싱 | 보내는 서비스가 받는 서비스를 기다리지 않는다 |

짚고 갈 것이 있다. 비동기성은 연산의 호출이나 정보 교환이 갖는 성질이지 특정 구현에 얽매인 개념이 아니다. 같은 말이 스레드 하나 안의 코루틴에도, 서버 수백 대를 잇는 메시지 큐에도 쓰인다. 어느 층의 이야기인지 먼저 확인하는 습관이 혼란을 크게 줄인다.

{{< callout type="info" >}}
이 장은 **한 프로세스 안에서의 비동기**를 다룬다. 시스템 사이의 비동기는 [05](../05-inter-process-communication)장 4절의 메시지 큐이고, 커널이 준비와 완료를 알려 주는 층은 [10](../10-nonblocking-io)장 5절과 [11](../11-event-driven-concurrency)장 5절이다.
{{< /callout >}}

### 1.2 얻는 것과 잃는 것

| 이득 | 설명 | 왜 (이 장에서 잰 값) |
|:-----|:-----|:----------------|
| 자원 효율 | 대기 시간에 다른 일을 한다 | 잠든 가상 스레드 10만 개가 OS 스레드 41개 위에 (2.2절) |
| 지연 시간 감소 | 독립인 요청을 동시에 시작한다 | 771 ms가 309 ms로 |
| 처리율 향상 | 같은 스레드로 더 많은 요청을 | 스레드 하나가 async 함수 10만 개의 대기를 146 ms에 (5절) |
| 확장성 | 연결이 늘어도 메모리가 선형으로 폭증하지 않는다 | 플랫폼 스레드 51 KB, 가상 스레드 1.8 KB (2.2절) |

| 대가 | 설명 | 왜 |
|:-----|:-----|:---|
| 코드 복잡도 | 흐름이 쪼개져 위에서 아래로 읽히지 않는다 | [11](../11-event-driven-concurrency)장 7절의 콜백 지옥 |
| 디버깅 곤란 | 스택 트레이스가 끊긴다 | 아래 표. 내 프레임 4개가 2개로 |
| 전파성 | 한 곳을 비동기로 만들면 호출 사슬 전체가 비동기가 된다 | 퓨처를 돌려주는 함수를 부른 쪽도 퓨처를 다뤄야 한다 |
| 오염 위험 | 블로킹 호출 하나가 전체를 멈춘다 | [11](../11-event-driven-concurrency)장 4.3절, 이 장 2.4절 |

| 둘째 단계에서 예외가 났을 때 스택 트레이스 | 내 코드의 프레임 | 왜 |
|:------------------------------|:------------|:---|
| 동기 (블로킹 호출) | 4개: `fetchOrder` ← `loadDashboard` ← `handle` ← `main` | 호출 사슬이 스택에 그대로 있다 |
| `CompletableFuture` 사슬 | 2개: `fetchOrder` ← 람다. `join()` 쪽 예외에는 0개 | 단계는 풀 스레드에서 돌고, 부른 쪽의 스택은 이미 사라졌다 |
| 가상 스레드 (블로킹 호출) | 4개: 사슬 전부 | 스레드 하나의 스택이 살아 있다 |
| Node.js `async`/`await` | `findOrders` ← `async loadDashboard` ← … | 컴파일러가 접어 둔 프레임을 V8이 되살린다 (5절) |

{{< callout type="warning" >}}
**비동기의 이득은 작업들이 서로 독립일 때만 나온다.** 위 표의 의존 사슬 777ms가 그 한계다. 그리고 대가는 코드에 든다. 퓨처 사슬에서 예외가 나면 스택 트레이스에 그 단계의 람다만 남고, `join()`한 쪽의 예외에는 내 코드가 한 줄도 없다. 어느 요청의 어느 단계가 실패했는지 알려면 컨텍스트를 직접 실어 날라야 한다.
{{< /callout >}}

## 2. 협동적 멀티태스킹 — 비동기를 떠받치는 실행 모델

> **협동적 멀티태스킹**은 여러 작업이 프로세서 시간과 자원을 나눠 쓰되, 각 작업이 스스로 제어권을 반납하는 방식이다.

둘째 원리다. [06](../06-multitasking)장 4절에서 선점형과 나란히 비교한 그 개념이다. 비동기 시스템을 구현하는 데 가장 널리 쓰이는 방식이므로, 여기서는 왜 비동기와 궁합이 좋은지에 초점을 맞춰 다시 본다.

### 2.1 누가 전환을 결정하는가

```text
선점형 (OS가 뺏는다)
 A▪▪▪│B▪▪▪│A▪▪▪│C▪▪▪
     ▲ 타이머 인터럽트
       커널 개입 = 문맥 전환

협동형 (작업이 넘긴다)
 A▪▪▪▶B▪▪▪▶A▪▪▪▶C▪▪▪
     ▲ yield / suspend / await
       함수 호출 수준의 전환
```

| 구분 | 선점형 | 협동형 | 왜 |
|:-----|:-----|:-----|:---|
| 전환 주체 | OS 스케줄러 | 작업 자신 | 커널은 코드를 모르고, 작업은 자기 기다림을 안다 |
| 전환 시점 | 예측 불가, 언제든 | 명시적 지점에서만 | 아래 표의 `count++`가 그 차이 |
| 전환 비용 | 시스템 콜 + 문맥 전환 | 함수 호출 수준 | 커널을 거치지 않는다 |
| 공평성 | 커널이 보장 | 작업의 협조에 의존 | 안 물러나면 못 뺏는다 (2.4절) |
| 동기화 | 락 필요 | 전환점이 명시적이라 단순 | 코어가 하나일 때 |

| 전환 한 번 | 이 PC | 왜 |
|:--------|-----:|:---|
| OS 스레드 사이 park/unpark 건네기 | 1,730 ns | 시스템 콜, 커널 스케줄러, 식은 캐시 |
| 가상 스레드 사이 park/unpark 건네기 | 1,200 ns | 런타임 스케줄러(ForkJoinPool)를 거치고, 잠든 캐리어를 깨우기도 한다 |
| 자바 `Continuation` yield/run (가상 스레드의 속) | 51 ns | 함수 호출 몇 개. 프레임을 힙에 접어 둔다 |
| 파이썬 제너레이터 `next()` | 26 ns | 프레임을 버리지 않고 두었다 다시 쓴다. 함수 호출(50 ns)보다 싸다 |
| Node.js `await` | 23~26 ns | 마이크로태스크 큐 한 바퀴 |

| `count++` 100만 번 × 스레드 둘, 락 없이 | 잃은 갱신 | 왜 |
|:-----------------------------|-------:|:---|
| 플랫폼 스레드 | 50% | 읽고-더하고-쓰기 사이에서도 뺏긴다 ([08](../08-race-conditions-and-synchronization)장 1절) |
| 가상 스레드, 캐리어 1개 (양보를 64번마다 넣어도) | 0% | 전환은 양보 지점에서만. `count++` 안에는 양보가 없다 |
| 가상 스레드, 캐리어 10개 | 50% (양보 넣으면 5%) | 코어가 여럿이면 협동형이라도 병렬이다. 락이 다시 필요하다 |

선점형은 타이머가 뺏는다. 작업은 자기가 언제 밀려날지 모르고, 그래서 [08](../08-race-conditions-and-synchronization)장의 모든 문제가 생긴다. 협동형은 작업이 넘긴다. `yield`, `suspend`, `await`처럼 코드에 적힌 지점에서만 전환이 일어나고, 그 사이는 통째로 실행된다. 둘째 표가 그 값이다. OS 스레드 사이의 건네기는 1.7µs이고, 가상 스레드 사이도 1.2µs로 크게 다르지 않다. 깨어날 쪽을 런타임 스케줄러에 넣고, 그 스케줄러의 캐리어가 잠들어 있으면 커널이 깨워야 하기 때문이다. 진짜 협동형 전환은 그 아래에 있다. 가상 스레드의 속인 `Continuation`이 멈췄다 이어지는 데 51ns, 파이썬 제너레이터가 26ns, 자바스크립트 `await`가 25ns다. 커널이 없고, 스택을 통째로 저장하지 않고, 함수 하나가 반환했다 다시 불리는 값이다. 셋째 표가 동기화의 차이다. 캐리어가 하나인 가상 스레드 둘이 락 없이 `count++`를 100만 번씩 해도 잃은 갱신이 0이다. `count++` 안에는 양보 지점이 없으니 그 사이에 남이 끼어들 수 없다. 조건은 코어가 하나라는 것이다. 캐리어를 10개로 두면 협동형이라도 둘이 진짜 병렬로 돌고, 다시 50%를 잃는다.

{{< callout type="info" >}}
**협동형에서는 전환이 일어나는 지점을 코드에서 볼 수 있다.** `suspend`나 `await`가 없는 구간은 통째로 실행된다는 뜻이고, 그래서 [08](../08-race-conditions-and-synchronization)장의 경쟁 조건이 생길 자리가 양보 지점 사이로 좁아진다. Node.js와 파이썬 asyncio가 락 없이 돌아가는 이유다. 단, 위 표대로 이 성질은 실행 스레드가 하나일 때만 성립한다. 코루틴을 스레드 여럿에 올리는 코틀린과 캐리어가 여럿인 자바 가상 스레드에서는 락이 그대로 필요하다.
{{< /callout >}}

### 2.2 사용자 수준 스레드 vs 커널 수준 스레드

```text
   사용자 공간
┌────────────────────────┐
│ 코루틴 C1 C2 C3 … Cn   │
└───────────┬────────────┘
            │ 런타임 스케줄러
            ▼
   커널 공간
┌────────────────────────┐
│  커널 스레드 T1   T2   │
└───────────┬────────────┘
            ▼
       코어1   코어2
```

| 구분 | 커널 수준 스레드 | 사용자 수준 스레드(코루틴) | 왜 |
|:-----|:------------|:-------------------|:---|
| 스택 | 고정 예약 (이 PC 2 MB, 잠들면 51~88 KB) | 힙에 필요한 만큼 (1.8 KB) | 커널은 최악을 예약하고, 런타임은 쓴 만큼만 접어 둔다 |
| 생성 비용 | 시스템 콜, 23 µs | 객체 할당, 1 µs 아래 | 커널 객체가 없다 |
| 전환 비용 | µs | ns (51 ns) | 커널을 거치지 않는다 |
| 스케줄링 | OS 커널 | 언어 런타임 | 런타임이 기다림 지점을 안다 |
| 실용적 개수 | 수천 (이 PC 4,069) | 수십만~수백만 | 메모리와 커널 한도 |
| 코어 활용 | 커널이 자동 분산 | 런타임이 캐리어 여럿에 배치 | M:N |

| 잠든 스레드 N개 | 만드는 데 | 메모리 | OS 스레드 | 왜 |
|:------------|-------:|------:|--------:|:---|
| 플랫폼 스레드 3,000 | 124 ms (23 µs/개) | +152 MB (51 KB/개) | 38 → 3,041 | 스레드마다 커널 객체와 스택 |
| 가상 스레드 3,000 | 5 ms | +9 MB (3.1 KB/개) | 41 → 41 | 힙의 객체. 커널은 모른다 |
| 가상 스레드 100,000 | 92 ms (0.9 µs/개) | +175 MB (1.8 KB/개) | 41 → 41 | 캐리어 10개 위에 10만 개 |
| 파이썬 asyncio 코루틴 100,000 | | 250 MB | 1 | 스레드 하나 위의 코루틴 (3.2절) |
| Node.js async 함수 100,000 | | +110 MB | 7 | 스레드 하나 위의 프로미스 (5절) |

협동적 멀티태스킹의 실행 단위는 OS가 모르는 사용자 수준 스레드다. 커널은 스레드 몇 개만 보고 있고, 그 위에서 런타임이 수많은 작업을 갈아 끼운다. [04](../04-concurrency-ingredients)장 2.4절에서 이 PC의 플랫폼 스레드는 4,069개에서 끝났다. 커널이 프로세스 하나에 허락하는 수이고, 그 전에 스레드마다 51KB([04](../04-concurrency-ingredients)장에서는 88KB, 만진 스택의 양이 다르다)가 쌓인다. 가상 스레드 10만 개는 1.8KB씩 175MB이고 OS 스레드는 41개 그대로다. 자바가 스레드를 만든 것이 아니라 힙에 객체를 만들고, 그 객체가 실행될 차례에만 캐리어라 부르는 OS 스레드 10개 중 하나에 올라탄다. 잠들면 내려온다. 파이썬과 Node.js는 캐리어가 하나뿐이고 10만 개를 그 하나 위에서 돌린다.

### 2.3 왜 오버헤드가 극적으로 줄어드는가

```text
동시 요청 10,000건, 이 PC

스레드 기반
  스레드 10,000개 × 51 KB
  그 전에 4,069개째에서 생성 실패

가상 스레드 기반
  캐리어 10개 + 가상 스레드 10,000개
  메모리 18 MB, 전환은 51 ns
```

협동적 멀티태스킹을 채용하면 CPU와 메모리 오버헤드가 크게 준다. 입출력 위주 작업이 많은 서버나 데이터베이스에서 효과가 크다. 위 표의 잠든 스레드 10만 개가 그것이다. 요청 하나가 대부분 기다림이면 그 요청은 스택 하나를 통째로 잡고 잘 이유가 없고, 접어 둔 1.8KB면 충분하다. 1초를 자는 가상 스레드 10만 개가 1,209ms에 전부 끝났다. 커널이 스케줄한 것은 41개뿐이었다.

{{< callout type="info" >}}
적은 스레드로 많은 작업을 처리하니 하드웨어를 효율적으로 쓰고, **비동기 I/O와 결합하면 자원 효율이 한 번 더 오른다.** 코루틴이 I/O를 기다릴 때 스레드를 붙잡지 않고 반납하기 때문이다. 반납할 수 있으려면 그 I/O가 [10](../10-nonblocking-io)장의 논블로킹이어야 한다. 협동적 멀티태스킹과 비동기 I/O는 따로 쓸 때보다 함께 쓸 때 훨씬 강하고, 가상 스레드는 그 둘을 런타임 안에서 묶은 것이다.
{{< /callout >}}

### 2.4 협동의 대가 — 반납하지 않는 작업

```text
정상: 제때 반납
 A▪▪▶B▪▪▶C▪▪▶A▪▪▶B▪▪

배신: B가 반납하지 않음
 A▪▪▶B■■■■■■■■■■■■■■
             ▲
     C와 A는 영원히 대기
```

| 물러나지 않는 작업 | 결과 | 왜 |
|:-------------|:-----|:---|
| 캐리어 1개, 가상 스레드 하나가 1초를 계산만 | 다음 가상 스레드가 1,002 ms 뒤에 시작 | 양보 지점이 없다. 뺏을 타이머도 없다 |
| 같은 계산에 `Thread.yield()`를 끼움 | 2 ms 뒤에 시작 | 양보 지점을 지난다 |
| Node.js에서 한 함수가 100 ms 바쁜 루프 | 10 ms 타이머가 100 ms에 울린다 | 스레드가 하나다 |
| 가상 스레드 100개가 `synchronized` 안에서 100 ms 잠 (JDK 23) | 1,085 ms. 락 없이는 114 ms, `ReentrantLock`은 111 ms | 모니터를 든 채로는 캐리어에서 못 내려온다(핀). 캐리어 10개가 10개씩 차례로 |

| 위험 행동 | 대안 | 왜 |
|:--------|:-----|:---|
| 코루틴 안에서 블로킹 I/O 호출 (JDBC 등) | 논블로킹 API, 또는 전용 디스패처·워커 풀 | 코루틴은 물러나지 못하고 스레드가 묶인다 |
| 긴 CPU 계산을 통째로 실행 | 중간에 `yield()`, 또는 별도 스레드 풀 | 위 표의 1,002 ms |
| `Thread.sleep()` | `delay()` 같은 논블로킹 대기 | 자는 동안 스레드를 놓아야 한다 (가상 스레드의 `sleep`은 놓는다) |
| 동기 락 대기 | 코루틴용 `Mutex`, 단일 스레드 소유 | 락을 기다리며 스레드를 든다 |

협동형의 유일한 전제는 각 작업이 적절한 시기에 제어권을 반납한다는 것이다. 이 약속이 깨지면 그 순간 전체가 멈춘다. 캐리어를 하나로 둔 가상 스레드 하나가 양보 없이 1초를 계산하자 그다음 가상 스레드는 1,002ms 뒤에야 시작했고, 계산 사이에 `Thread.yield()`를 넣자 2ms였다. Node.js는 스레드가 하나라 항상 이 상태다. 한 함수의 바쁜 루프 100ms가 다른 함수의 10ms 타이머를 100ms로 만들었다. 넷째 줄이 자바 특유의 함정이다. 가상 스레드는 블로킹 호출에서 스스로 캐리어를 내놓는데, JDK 23까지는 `synchronized` 블록 안에서는 내놓지 못했다. 캐리어에 핀(pin)된다. 각자 자기 모니터를 든 가상 스레드 100개가 100ms를 자는 데 1,085ms가 걸렸다. 캐리어 10개가 10개씩 열 번 순서를 기다린 것이고, 같은 코드를 락 없이 또는 `ReentrantLock`으로 하면 111ms다. 그래서 [13](../13-concurrency-summary)장 8.2절의 "코루틴에서 JDBC 직접 호출"이 사고 목록에 있다. 코틀린 코루틴이 JDBC를 부르면 드라이버가 소켓을 기다리는 동안 그 코루틴이 올라탄 디스패처 스레드가 통째로 묶이고, 자바 가상 스레드에서도 JDK 23까지는 드라이버 안의 `synchronized`가 같은 핀을 만들었다.

{{< callout type="warning" >}}
[11](../11-event-driven-concurrency)장 4.3절의 **"콜백은 블로킹하면 안 된다"** 와 정확히 같은 문제다. 실행 단위가 콜백이든 코루틴이든 가상 스레드든, 협동형 위에서 도는 코드는 스스로 물러날 의무를 진다. 코틀린에서 `runBlocking`을 `suspend` 함수 안에 쓰거나 코루틴에서 JDBC를 그대로 부르는 것이 대표적인 사고다. 자바의 `synchronized` 핀은 JDK 24의 JEP 491로 사라졌고, 남은 핀은 클래스 로딩·초기화와 네이티브 프레임뿐이다.
{{< /callout >}}

## 3. 코루틴

> **코루틴**은 실행 도중에 멈췄다가, 나중에 조건이 충족되면 그 자리에서 재개할 수 있는 함수다.

셋째 원리의 첫 추상화다. 1963년 콘웨이가 이름 붙였고, 파이썬의 제너레이터, 코틀린의 `suspend` 함수, 자바 가상 스레드의 속인 `Continuation`이 전부 이것이다.

### 3.1 서브루틴과 무엇이 다른가

```text
서브루틴: 진입 1회, 종료 1회
  호출 ─▶ [ 함수 ] ─▶ 반환
    끝나면 지역 상태 소멸

코루틴: 진입 n회, 중단 n회
  호출 ─▶ [ 함수 ]
          ⏸ suspend (상태 보존)
  재개 ─▶ [ 함수 ]
          ⏸ suspend
  재개 ─▶ [ 함수 ] ─▶ 반환
```

```python
# 파이썬 제너레이터: 멈췄다 잇는 함수
def pages():
    yield "1쪽"   # 여기서 멈춘다
    yield "2쪽"   # 다시 들어와 잇는다
    yield "3쪽"

g = pages()
next(g)   # "1쪽"
next(g)   # "2쪽"  지역 상태 그대로
```

| 구분 | 서브루틴 | 코루틴 | 왜 |
|:-----|:------|:-----|:---|
| 진입점 | 시작 지점 1개 | 재개할 때마다 여러 개 | 어디서 멈췄는지를 기억한다 |
| 종료 | 반환 1회 | 중단 n회 + 반환 1회 | 중단은 반환이 아니다 |
| 지역 상태 | 반환 시 소멸 | 중단해도 보존 | 프레임을 스택에서 버리지 않고 힙에 둔다 |
| 호출 관계 | 호출자-피호출자 종속 | 대등한 협력 | 서로를 재개한다 |
| 스택 | 스레드 스택 | 힙의 프레임 | 그래서 수십만 개를 둘 수 있다 |
| 재개 비용 (이 PC) | 함수 호출 | 파이썬 `next()` 26 ns, 자바 `Continuation` 51 ns | 함수 호출과 같은 급 |

우리가 아는 보통의 함수는 서브루틴이다. 한 번 들어가면 끝까지 실행하고 한 번 반환하며, 반환하면 지역 변수는 사라진다. 코루틴은 중간에 멈춘다. 파이썬의 `yield`가 그 지점이고, `next()`로 다시 들어오면 멈춘 자리의 다음 줄부터 지역 변수 그대로 이어 간다. 그 값이 위 표의 마지막 줄이다. 파이썬에서 제너레이터를 한 번 재개하는 데 26ns, 보통 함수를 한 번 부르는 데 50ns였다. 프레임을 새로 만들지 않고 두었던 것을 다시 쓰니 호출보다 싸다. 자바에는 언어 수준의 코루틴이 없지만 가상 스레드의 속에 `Continuation`이 있고, 그것이 멈췄다 이어지는 데 51ns다.

### 3.2 비동기 I/O를 코루틴으로 처리하기

```text
코루틴 A ─▶ I/O 요청
   ⏸ suspend (스레드 반납)
        ▼
코루틴 B ─▶ 실행
   ⏸ suspend
        ▼
코루틴 A ◀─ I/O 완료 통지
   같은 자리에서 재개
   스레드 1개, 유휴 시간 0
```

```kotlin
// 동기처럼 읽히지만 멈추지 않는다
suspend fun load(id: Long) =
    coroutineScope {
        val u = async { users.find(id) }
        val o = async { orders.by(id) }
        val c = async { coupons.by(id) }
        // await에서만 멈춘다
        Dashboard(u.await(),
            o.await(), c.await())
    }
```

```kotlin
// 코루틴 10만 개, 스레드는 코어 수만큼
fun main() = runBlocking {
    val jobs = List(100_000) {
        launch(Dispatchers.IO) {
            delay(1000) // 놓고 잔다
        }
    }
    jobs.forEach { it.join() }
}
```

| 파이썬 asyncio, 코루틴 N개가 각각 1초 대기 | 전부 끝나는 데 | OS 스레드 | 메모리 | 왜 |
|:----------------------------|---------:|-------:|-----:|:---|
| 1,000 | 1,016 ms | 1 | 17 MB | 대기 1,000개가 겹친다 |
| 10,000 | 1,090 ms | 1 | 38 MB | 90 ms는 만들고 깨우는 값 |
| 100,000 | 2,045 ms | 1 | 250 MB | 10만 개를 깨우는 데 1초. 코루틴 하나에 2.3 KB |

코루틴이 I/O를 요청하고 멈추면 스레드가 다른 코루틴으로 넘어가고, I/O가 끝나면 원래 코루틴이 멈춘 자리에서 이어진다. 코드는 위에서 아래로 읽히는데 실행은 [11](../11-event-driven-concurrency)장의 이벤트 루프다. 코틀린의 `async`는 세 호출을 동시에 시작하고, `await`에서만 멈춘다. 그동안 스레드는 다른 코루틴을 돌린다. 위 표는 같은 일을 파이썬 asyncio로 잰 것이다. 1초를 기다리는 코루틴 10만 개가 스레드 하나에서 2초에 끝났다. 스레드였다면 [04](../04-concurrency-ingredients)장에서 4,069개째에 죽었다. 2.2절의 자바 가상 스레드 10만 개가 1,209ms였으니 파이썬의 깨우는 값이 더 크지만, 스레드 수는 1과 41로 둘 다 코어 수 아래다.

### 3.3 코루틴은 어떻게 상태를 기억하는가

```kotlin
// 우리가 쓰는 코드
suspend fun load(id: Long): Result {
    val user = fetchUser(id)  // 중단 1
    val order =
        fetchOrder(user)      // 중단 2
    return Result(user, order)
}
```

```java
// 컴파일러가 만드는 구조 (개념적)
class LoadCoroutine {
    int label = 0;   // 어디까지 왔나
    User user;       // 지역 변수 → 필드

    Object resume(Object prev) {
        switch (label) {
            case 0:
                label = 1;
                return fetchUser(id);
            case 1:
                user = (User) prev;
                label = 2;
                return fetchOrder(user);
            default:
                return new Result(user,
                        (Order) prev);
        }
    }
}
```

```java
// 자바 가상 스레드의 속: Continuation
// (jdk.internal.vm, 공개 API 아님)
var c = new Continuation(scope, () -> {
    step1();
    Continuation.yield(scope); // 멈춤
    step2();
});
c.run();   // step1까지 돌고 돌아온다
c.run();   // step2부터 끝까지
```

| `Continuation.yield()` 한 번, 스택 깊이 | 이 PC | 왜 |
|:------------------------------|-----:|:---|
| 1 | 51 ns | 프레임 하나를 힙에 접는다 |
| 10 | 52 ns | |
| 100 | 52 ns | |
| 1,000 | 52 ns | 스택 전체를 복사하지 않는다. 바뀐 위쪽 프레임만 접고, 아래는 그대로 둔다 |

코루틴의 마법처럼 보이는 부분은 컴파일러가 함수를 상태 기계로 바꾼 결과다. 중단 지점마다 번호를 붙이고, 지역 변수를 객체의 필드로 옮긴다. `resume()`이 불릴 때마다 `label`을 보고 멈춘 자리로 뛴다. [11](../11-event-driven-concurrency)장 4.2절에서 이벤트 기반 코드는 진행 상태를 객체 필드에 직접 보관해야 한다고 했다. 코루틴은 바로 그 일을 컴파일러가 대신하는 것이다. 우리는 순차 코드를 쓰고 컴파일러가 콜백과 상태 기계로 바꾼다. 코루틴이 콜백 지옥의 해법이라 불리는 이유가 여기 있다. 자바는 다른 길을 택했다. 컴파일러 대신 JVM이 실행 중인 스택 프레임을 힙에 접어 두는 `Continuation`을 만들고, 그 위에 가상 스레드를 얹었다. 그래서 `suspend` 표시 없이 어떤 메서드 깊이에서든 멈출 수 있고, 위 표대로 깊이 1,000의 스택에서 멈춰도 52ns다. 스택을 통째로 복사하는 것이 아니라 바뀐 위쪽 프레임만 접기 때문이다.

{{< callout type="info" >}}
**상태를 어디에 두느냐가 세 방식의 차이 전부다.** 스레드는 스택에(그래서 비싸고), 콜백은 내가 객체 필드에(그래서 괴롭고), 코루틴은 컴파일러가 만든 객체에(코틀린) 또는 런타임이 접은 프레임에(자바 가상 스레드) 둔다. 세 번째가 첫 번째의 코드 모양으로 두 번째의 값을 낸다.
{{< /callout >}}

### 3.4 코루틴과 스레드의 관계

| 구분 | 스레드 | 코루틴 | 왜 |
|:-----|:-----|:-----|:---|
| 소속 | OS가 관리 | 언어 런타임이 관리 | 커널 객체가 있느냐 |
| 개수 | 수천 (이 PC 4,069) | 수십만~수백만 (10만 개에 175~250 MB) | 스택 예약과 커널 한도 |
| 중단 | OS가 강제로 뺏는다 | 중단점에서 스스로 | 2.1절 |
| 대기 | 스레드가 통째로 멈춘다 | 스레드를 놓고 물러난다 | 그래서 캐리어 10개면 된다 |
| 취소 | 안전한 취소가 어렵다 | 협조적 취소가 구조화된다 | 중단점이 곧 취소 확인 지점 |
| 관계 | | 코루틴 다수 ↔ 스레드 소수 (M:N) | 2.2절 표 |

{{< callout type="warning" >}}
**코루틴은 "가벼운 스레드"가 아니라 "스레드를 양보할 줄 아는 작업"이다.** 코루틴을 10만 개 띄워도 블로킹 호출을 하면 그 코루틴이 올라탄 스레드가 그대로 묶인다. 디스패처의 스레드가 8개라면 블로킹 호출 8개로 전체가 선다. 2.4절의 `synchronized` 핀이 자바에서의 그 모양이었다. 코루틴의 이득은 논블로킹 API와 함께 쓸 때만 실현된다.
{{< /callout >}}

## 4. 퓨처와 프로미스

> **퓨처 객체**는 미래에 완료될, 아직 알 수 없는 연산 결과를 전달받기 위한 프록시 객체다.

셋째 원리의 둘째 추상화다. 비동기 호출은 결과를 즉시 줄 수 없다. 그래서 "결과가 들어올 자리"를 먼저 돌려준다. 그 자리표가 퓨처다.

### 4.1 결과의 자리표

```text
   비동기 호출
        │
        ▼
┌────────────────┐
│  Future<T>     │ ← 즉시 반환
│  state: 대기중 │
└────────┬───────┘
         │ 백그라운드 완료
         ▼
┌────────────────┐
│  Future<T>     │
│  state: 완료   │
│  value: 결과   │ → get() 즉시 반환
└────────────────┘
```

| 상태 | 의미 | 왜 따로 두나 |
|:-----|:-----|:---------|
| 대기(pending) | 연산이 아직 진행 중 | 자리만 있고 값이 없다 |
| 완료(fulfilled) | 결과값이 채워졌다 | 이때부터 `get()`이 즉시 돌아온다 |
| 실패(rejected) | 예외로 끝났다 | 예외도 결과다. 값과 같은 길로 나른다 |
| 취소(cancelled) | 외부에서 중단됐다 | 기다리던 쪽도, 일하던 쪽도 알아야 한다 |

### 4.2 자바의 Future와 그 한계

```java
var pool = Executors
    .newFixedThreadPool(4);
Future<String> f = pool.submit(() -> {
    Thread.sleep(1000);
    return "결과";
});
doSomethingElse();   // 여기까지는 이득
var r = f.get();     // 결국 잔다
```

| 200 ms 작업 1,000개의 결과를 아는 법 | 기다리는 동안 OS 스레드 | 기다리는 동안 CPU | 완료 → 반응 | 왜 |
|:---------------------------|-------------:|------------:|--------:|:---|
| `Future.get()`, 기다리는 스레드 1,000개 | 1,041 | 0.12 s | 7 µs | 스레드가 잔다. 통지를 스레드 하나가 통째로 받는다 |
| `isDone()` 폴링, 스레드 하나 | 41 | 0.29 s (코어 하나 100%) | 1.2 ms (1 ms마다 물을 때) | 되묻는다. [10](../10-nonblocking-io)장 4절의 바쁜 대기 |
| `CompletableFuture.thenAccept` | 41 | 0.02 s | 16~81 ns | 완료한 스레드가 콜백을 그 자리에서 부른다 |

| 한계 | 설명 | 왜 문제인가 |
|:-----|:-----|:---------|
| 완료 통지 없음 | 콜백을 등록할 수 없다 | `get()`으로 자거나 `isDone()`으로 묻는 수밖에. 위 표의 첫 두 줄 |
| 조합 불가 | 두 퓨처를 잇거나 합칠 방법이 없다 | 사슬은 `get()`의 사슬이 되고, 그러면 동기다 |
| 예외 처리 빈약 | `ExecutionException`으로 감싸여 온다 | 원인을 매번 풀어야 한다 |
| 수동 완료 불가 | 외부에서 값을 채울 수 없다 | 콜백 API를 퓨처로 못 감싼다 (4.4절) |

`Future`는 결과를 담는 그릇일 뿐 완료를 통지받는 수단이 없다. 결과를 쓰려면 `get()`으로 기다리거나 `isDone()`으로 물어야 하는데, 둘 다 비동기의 취지를 무너뜨린다. 위 표가 그 값이다. 200ms짜리 작업 1,000개의 결과를 `get()`으로 기다리면 기다리는 스레드가 1,000개 필요하고 OS 스레드가 1,041개가 된다. 스레드 하나가 `isDone()`을 돌면 스레드는 안 늘지만 코어 하나가 221ms 동안 1억 9천만 번을 묻는다. `thenAccept`는 둘 다 없다. 결과를 채우는 스레드가 그 자리에서 콜백을 부르니 기다리는 스레드도, 묻는 CPU도 없고, 완료에서 반응까지 수십 ns다.

### 4.3 CompletableFuture — 조합 가능한 퓨처

```java
CompletableFuture
    .supplyAsync(() -> users.find(id))
    .thenApply(u -> u.grade())
    .thenCompose(g -> discounts.of(g))
    .thenCombine(policy, this::apply)
    .thenAccept(this::render)
    .exceptionally(e -> {
        log.error("조회 실패", e);
        return null;
    });
// 어느 지점에서도 스레드가 자지 않는다
```

| 메서드 | 역할 | 왜 |
|:-----|:-----|:---|
| `supplyAsync` | 비동기 연산 시작 | 풀 스레드에서 돌고 퓨처를 즉시 돌려준다 |
| `thenApply` | 결과를 동기 함수로 변환 | 스트림의 `map` |
| `thenCompose` | 결과로 다음 비동기 연산을 잇는다(평탄화) | 스트림의 `flatMap`. 다음 단계가 퓨처를 돌려줄 때 |
| `thenCombine` | 독립인 두 퓨처의 결과를 합친다 | 둘 다 돌고 있어야 겹친다 |
| `allOf` / `anyOf` | 모두 / 먼저 끝난 것을 기다린다 | 1절의 309 ms / 206 ms |
| `exceptionally` | 예외 복구 | 예외도 같은 사슬로 온다 |
| `orTimeout` | 제한 시간을 넘기면 실패 처리 (Java 9+) | 500 ms 작업에 100 ms를 걸자 104 ms에 `TimeoutException` |

| `thenApply`의 콜백이 도는 스레드 | 왜 |
|:-------------------------|:---|
| 완료 전에 등록 → 완료한 스레드 (풀 스레드) | 완료가 콜백을 부른다 |
| 완료 후에 등록 → 등록한 스레드, 그 자리에서 | 기다릴 것이 없다 |
| `thenApplyAsync` → 공용 `ForkJoinPool` (또는 준 실행기) | 명시적으로 넘긴다 |
| 프로미스를 `complete()`한 스레드 X → X | 완료한 쪽이 콜백을 든다. 레거시 콜백의 스레드에서 돌 수 있다 |

자바 8의 `CompletableFuture`는 4.2절의 한계를 모두 푼다. 완료 시점에 실행할 코드를 등록할 수 있으니 블로킹 없이 파이프라인을 만들고, [11](../11-event-driven-concurrency)장 7절에서 잰 대로 네 단계 사슬 하나가 900ns다. [07](../07-task-decomposition)장 2절의 의존 그래프를 그대로 옮긴 것이 이 사슬이고, 독립인 가지는 `thenCombine`과 `allOf`로 겹치고 의존하는 가지는 `thenCompose`로 잇는다. 둘째 표가 실무에서 가장 자주 놀라는 부분이다. 콜백이 어느 스레드에서 도는지는 등록 시점이 정한다. 완료 전에 등록하면 완료한 스레드가 부르고, 이미 완료된 퓨처에 등록하면 등록한 스레드가 그 자리에서 부른다. 같은 코드가 어떤 날은 풀 스레드에서, 어떤 날은 `main`에서 돈다. 콜백이 오래 걸리면 완료한 스레드(풀 스레드, 또는 이벤트 루프)를 잡는 것이고, 그래서 무거운 콜백은 `thenApplyAsync`로 넘긴다.

{{< callout type="warning" >}}
**`thenApply`와 `thenCompose`를 혼동하면 `CompletableFuture<CompletableFuture<T>>`가 생긴다.** 다음 단계가 또 비동기라면 `thenCompose`다. 스트림의 `map`과 `flatMap`의 관계와 같다. 그리고 `exceptionally`에 오는 예외는 감싸여 있기도 하고 아니기도 하다. 실패한 퓨처 자체에 붙이면 원래 예외(`IllegalStateException`)가, 한 단계라도 거친 뒤에 붙이면 `CompletionException`으로 감싸인 것이 온다. 원인을 볼 때는 `getCause()`가 `null`인지부터 확인해야 한다.
{{< /callout >}}

### 4.4 퓨처와 프로미스

```text
프로미스 (쓰기 측)     퓨처 (읽기 측)
 생산자가 값을 채움 ─▶ 소비자가 읽음
   complete(v)         thenApply(…)
```

| 구분 | 퓨처(Future) | 프로미스(Promise) | 왜 나누나 |
|:-----|:----------|:--------------|:-------|
| 관점 | 결과를 **읽는** 쪽 | 결과를 **쓰는** 쪽 | 읽는 쪽에 쓰기 권한을 주면 아무나 완료시킨다 |
| 완료 권한 | 없음, 관찰만 | 있음, 직접 채움 | |
| 자바 | `Future`, `CompletionStage` | `CompletableFuture.complete()` | `CompletableFuture`는 둘을 겸한다 |
| 자바스크립트 | `Promise`(둘을 합친 형태) | `resolve` / `reject` | 생성자 안에서만 쓰기 |

```java
// 퓨처와 프로미스를 겸한다
var promise =
    new CompletableFuture<String>();

// 읽는 쪽: 기다리지 않고 처리기를 등록
promise.thenAccept(log::info);

// 쓰는 쪽: 콜백 API를 퓨처로 감쌀 때
legacy.onMessage(promise::complete);
legacy.onError(
    promise::completeExceptionally);
```

두 용어는 자주 섞여 쓰이지만 원래는 읽는 쪽과 쓰는 쪽을 나눈 이름이다. 1988년 리스코프의 프로미스가 그 출처다. 실무에서 프로미스 쪽이 필요한 순간은 콜백 API를 퓨처로 감쌀 때다. 레거시 클라이언트의 `onMessage` 콜백이 `promise.complete`를 부르면 그 순간 등록된 `thenAccept`가 그 콜백의 스레드에서 돈다(4.3절 둘째 표의 마지막 줄). 이 PC에서 `complete()`에서 `thenAccept`까지 같은 스레드면 16~81ns, 다른 스레드가 완료해도 65~140ns였다. 통지 자체에는 값이 거의 없다.

## 5. async/await — 비동기를 동기처럼 쓰기

```javascript
// 콜백 → 퓨처 사슬 → async/await
async function loadDashboard(id) {
  try {
    const user = await findUser(id);
    // 여기서 접어 두고 스레드를 놓는다
    const orders =
      await findOrders(user);
    return render(user, orders);
  } catch (e) {
    log.error('조회 실패', e); // 그대로
  }
}
```

| 세대 | 방식 | 흐름 표현 | 예외 처리 | 왜 다음이 나왔나 |
|:-----|:-----|:-------|:-------|:------------|
| 1 | 콜백 | 중첩 (콜백 지옥) | 인자로 전달, 빠뜨리기 쉽다 | [11](../11-event-driven-concurrency)장 7절 |
| 2 | 퓨처·프로미스 | 사슬 (평탄) | `exceptionally` 한곳 | 여전히 사슬 문법. 조건문·루프가 어색하다 |
| 3 | 리액티브 스트림 | 스트림 + 배압 | `onErrorResume` | 값 하나가 아니라 흐름 |
| 4 | 코루틴·async/await | **순차 코드와 같다** | `try-catch` 그대로 | 컴파일러가 3.3절의 변환을 한다 |

| Node.js, 스레드 하나 | 이 PC | 왜 |
|:----------------|-----:|:---|
| `await` 한 번 | 23~26 ns | 마이크로태스크 큐 한 바퀴. 콜백 호출은 3 ns |
| 4단 async 사슬 하나 | 100 ns | 큐를 거치지 않는다. 자바 `CompletableFuture` 4단은 900 ns |
| async 함수 1,000 / 10,000 / 100,000개가 각각 100 ms 대기 | 103 / 105 / 146 ms, OS 스레드 7 → 7 | 대기 10만 개가 겹친다. 메모리 +110 MB |
| 한 함수가 100 ms 바쁜 루프 | 10 ms 타이머가 100 ms에 울린다 | 2.4절. 스레드가 하나다 |
| 둘째 `await`에서 예외 | `try/catch`가 받고, 스택에 `async loadDashboard`가 남는다 | 접어 둔 프레임을 V8이 되살린다 |

콜백과 퓨처 사슬은 여전히 평소 코드와 다르게 생겼다. `async`/`await`는 컴파일러가 3.3절의 코루틴 변환을 수행해 비동기 코드를 순차 코드처럼 쓰게 한다. `await`마다 함수를 접어 두고 이벤트 루프로 돌아가며, 프로미스가 완료되면 그 자리에서 이어진다. 그 값이 위 표다. `await` 한 번이 25ns, 네 단계 사슬이 100ns다. [11](../11-event-driven-concurrency)장 7절의 자바 `CompletableFuture` 사슬 900ns보다 싼 것은 스레드 사이의 큐가 없어서다. 스레드가 하나이니 큐도 락도 없다. async 함수 10만 개가 각각 100ms를 기다리는 데 146ms가 걸렸고 OS 스레드는 7개 그대로였다. 대신 그 스레드 하나가 100ms를 계산하면 모두가 100ms를 기다린다. 마지막 줄이 1.2절의 대가 하나를 되찾는 부분이다. 코틀린과 자바스크립트는 접어 둔 프레임을 알기 때문에 예외의 스택 트레이스에 `await` 이전의 호출 사슬을 되살려 준다. 퓨처 사슬에서 잃었던 것이다.

{{< callout type="info" >}}
**`await`는 블로킹이 아니라 중단이다.** 겉으로는 `Future.get()`처럼 결과를 기다리는 것 같지만, 실제로는 함수를 그 지점에서 접어 두고 스레드를 놓는다. "동기처럼 보이는 코드가 실제로는 이벤트 루프 위에서 돈다"는 것이 async/await의 전부이고, 그래서 [11](../11-event-driven-concurrency)장 4.3절과 이 장 2.4절의 규칙이 그대로 적용된다. `await` 사이에서 오래 계산하면 루프가 선다.
{{< /callout >}}

## 6. 자바의 선택 — 가상 스레드

```java
// 블로킹 코드 그대로, 요청 10만 개
var ex = Executors
    .newVirtualThreadPerTaskExecutor();
try (ex) {
    for (int i = 0; i < 100_000; i++) {
        ex.submit(() -> {
            var u = users.find(id);
            var o = orders.find(u);
            return render(u, o);
        });
    }
}
```

```text
가상 스레드의 동작
가상 스레드가 블로킹 호출
        │
        ▼
JVM이 프레임을 힙에 접어 둠
캐리어 스레드 즉시 반납
        │
        ▼
I/O 완료 → 프레임 펴고 재개
   코드는 동기, 실행은 비동기
```

| 구분 | 코루틴(Kotlin) | 가상 스레드(Java 21) | 왜 |
|:-----|:------------|:----------------|:---|
| 표현 | `suspend` 함수 | 평범한 블로킹 코드 | 컴파일러 변환 vs 런타임의 `Continuation` |
| 전파성 | `suspend`가 호출 사슬 전체로 번진다 | 없음, 기존 코드 그대로 | 멈추는 곳을 런타임이 안다 |
| 중단 지점 | 코드에 보인다 | 보이지 않는다 | 장점이자 단점. 2.1절의 "전환점이 보인다"를 잃는다 |
| 라이브러리 | 코루틴 지원 API 필요 | 기존 블로킹 API 대부분 호환 | JDK가 소켓·잠금·`sleep`에서 내려오게 고쳤다 |
| 배압 제어 | 구조화된 동시성으로 명시 | 세마포어 등으로 직접 | 아래 표 |
| 이 PC에서 | | 10만 개 175 MB, 캐리어 10개, 전환 51 ns | 2.2절 |

| 요청 1만 개를 가상 스레드 1만 개로, 아래층(커넥션 풀)이 동시에 N개 × 10 ms | 걸린 시간 | 줄 선 스레드 최대 | 왜 |
|:-------------------------------------------------|-------:|-----------:|:---|
| N = 10 | 14.1 s | 9,980 | 처리율의 상한은 커넥션 10개다. 스레드가 싸진 것과 무관하다 |
| N = 100 | 1.4 s | 9,900 | 열 배 |
| N = 1,000 | 0.14 s | 9,000 | 백 배 |
| N = 10, 부르는 쪽이 동시에 100개만 들여보냄 | 13.9 s | 100 | 처리율은 같다. 줄이 힙이 아니라 문 앞에 선다 |

자바 21의 가상 스레드는 같은 문제를 정반대 방향에서 푼다. 코드를 비동기로 바꾸는 대신 스레드를 코루틴만큼 싸게 만들어 블로킹 스타일 코드를 그대로 쓰게 한다. 속은 3.3절의 `Continuation`이다. 가상 스레드가 소켓 읽기나 `sleep`이나 락에서 막히면 JVM이 그 스레드의 프레임을 힙에 접어 두고 캐리어를 다른 가상 스레드에 준다. I/O가 끝나면 프레임을 펴서 이어 간다. [10](../10-nonblocking-io)장 6절에서 연결 1만 개를 OS 스레드 42개로 든 것, [11](../11-event-driven-concurrency)장 2.3절에서 요청 100개를 14ms에 끝낸 것, 이 장 1절에서 호출 셋이 311ms에 겹친 것이 전부 이 동작이다. 코틀린과의 차이는 표의 둘째 줄이다. `suspend`는 부르는 쪽 전부에 번지지만 가상 스레드는 기존 코드에 아무 표시가 없다. 대신 어디서 멈추는지도 안 보인다. 둘째 표가 이 장에서 가장 중요한 숫자다. 스레드가 싸졌다고 요청 1만 개에 스레드 1만 개를 주면, 그 아래 커넥션 풀이 10개일 때 9,980개가 줄을 선다. 걸린 시간은 커넥션 10개 × 10ms의 산수 그대로 14초이고, 부르는 쪽에서 100개만 들여보내도 14초다. 처리율은 가장 좁은 자원이 정하고, 값싼 동시성은 그 자원 앞의 줄을 길게 만들 뿐이다. [05](../05-inter-process-communication)장 7.3절에서 상한 없는 풀이 죽던 자리가 여기서는 다운스트림으로 옮겨 갔다.

{{< callout type="warning" >}}
**가상 스레드의 함정은 둘이다.** 첫째, 핀. JDK 23까지는 `synchronized` 안에서 블로킹하면 캐리어가 반납되지 않았고(2.4절의 1,085ms), JDK 24의 JEP 491이 이를 없앴다. 남은 핀은 클래스 로딩·초기화와 네이티브 프레임뿐이다. 둘째, 다운스트림. 스레드가 싸졌다고 무한정 만들면 DB 커넥션 풀, 외부 API의 속도 제한, 소켓 백로그 같은 아래층이 먼저 무너진다. 위 표가 그 산수다. 값싼 동시성이 곧 무제한 동시성은 아니다. 구조화된 동시성(JEP 533)은 JDK 27에서도 일곱 번째 프리뷰다.
{{< /callout >}}

## 7. 비동기 추상화 선택 가이드

| 상황 | 권장 | 왜 |
|:-----|:-----|:---|
| 독립인 API 호출 여러 개 합치기 | `CompletableFuture.allOf` + `thenCombine` | 1절: 771 ms가 309 ms로 |
| 콜백 기반 레거시 API 감싸기 | `CompletableFuture`를 프로미스로 | 4.4절: `complete()` 한 줄 |
| 스트림 + 배압이 필요한 데이터 흐름 | 리액티브 스트림(Reactor, RxJava) | 값 하나가 아니라 흐름과 속도 조절 |
| 복잡한 비동기 흐름 + 취소·타임아웃 | 코루틴(구조화된 동시성) | 중단점이 취소 확인 지점이고, 부모가 자식을 거둔다 |
| 기존 블로킹 코드를 확장만 하고 싶을 때 | 가상 스레드 | 6절: 코드 그대로, 10만 개에 175 MB |
| 요청은 많고 아래층은 좁을 때 | 무엇을 고르든 상한(세마포어, 풀 크기)부터 | 6절: 처리율은 커넥션 수의 산수 |
| CPU 바운드 병렬 처리 | 스레드 풀 / Fork-Join ([07](../07-task-decomposition)장) | 기다림이 없으니 회수할 것도 없다 |

{{< callout type="warning" >}}
**비동기는 CPU 바운드 작업에 도움이 되지 않는다.** 비동기가 회수하는 것은 기다리는 시간인데, CPU 바운드 작업에는 기다림 자체가 없다. 2.4절에서 계산만 하는 가상 스레드 하나가 나머지를 1초 세운 것이 그 모양이다. 계산이 병목이라면 답은 코어를 더 쓰는 병렬화([02](../02-sequential-and-parallel-execution)장)이지 비동기가 아니다. 모델을 고르기 전에 워크로드부터 분류해야 한다([06](../06-multitasking)장 2절).
{{< /callout >}}

| 비동기 통신 | 완료를 안 기다리고 진행, 대기 시간을 일로 회수 | 771 ms가 309 ms로. 의존 사슬은 777 ms 그대로 |

| 사용자 수준 스레드 | 커널이 모르는 값싼 실행 단위 | 10만 개가 OS 스레드 41개 위에, 1.8 KB씩 |
| 협동의 대가 | 반납하지 않으면 전체가 멈춘다 | 1초 계산에 1,002 ms 정지, `synchronized` 핀에 10배 |
| 코루틴 | 멈췄다가 그 자리에서 다시 시작하는 함수 | 제너레이터 `next()` 26 ns |
| 상태 기계 변환 | 컴파일러가 순차 코드를 콜백+상태로 바꾼다 | 11장 4.2절의 "상태를 필드에"를 대신 |
| 퓨처 | 미래에 올 결과의 자리표 | `get()`은 스레드를, 폴링은 코어를, 콜백은 아무것도 안 든다 |
| 프로미스 | 그 퓨처에 값을 써 넣는 쪽 | 콜백 API를 감싸는 한 줄 |
| CompletableFuture | 조합 가능한 퓨처, 블로킹 없는 파이프라인 | 콜백은 완료한 스레드에서 돈다 |
| async/await | 비동기를 순차 코드처럼, try-catch도 그대로 | `await` 25 ns, 10만 개 대기가 146 ms |

{{< callout type="info" >}}
**용어 정리**
- **비동기 통신**: 오래 걸리는 작업을 시작만 하고 완료를 기다리지 않는 기법. 회수하는 것은 기다림
- **협동적 멀티태스킹**: 각 작업이 스스로 제어권을 반납해 프로세서를 나눠 쓰는 방식
- **선점형 멀티태스킹**: 타이머와 커널이 작업을 뺏는 방식. 전환 지점을 작업이 모른다
- **사용자 수준 스레드**: 커널이 모르는, 런타임이 스케줄하는 실행 단위. 코루틴, 가상 스레드
- **캐리어 스레드**: 사용자 수준 스레드를 실제로 실행하는 OS 스레드. 코어 수만큼
- **양보 지점**: `yield`, `suspend`, `await`, 블로킹 호출처럼 작업이 물러나는 자리
- **핀(pin)**: 가상 스레드가 캐리어에서 내려오지 못하는 상태. JDK 23의 `synchronized`, 네이티브 프레임
- **서브루틴**: 진입 1회, 반환 1회의 보통 함수
- **코루틴**: 중간에 멈췄다 그 자리에서 이어 갈 수 있는 함수. 제너레이터, `suspend` 함수
- **상태 기계 변환**: 컴파일러가 코루틴을 `label`과 필드를 가진 객체로 바꾸는 것
- **Continuation**: JVM이 실행 중인 프레임을 힙에 접어 두는 장치. 가상 스레드의 속
- **퓨처(Future)**: 아직 없는 결과의 자리표. 읽는 쪽
- **프로미스(Promise)**: 그 자리에 값이나 예외를 써 넣는 쪽
- **CompletableFuture**: 퓨처와 프로미스를 겸하며 조합(`thenCompose`, `allOf`)이 되는 자바의 퓨처
- **async/await**: 컴파일러가 코루틴 변환을 해 비동기를 순차 코드처럼 쓰게 하는 문법
- **가상 스레드**: 런타임이 `Continuation` 위에 얹은 싼 스레드. 블로킹 코드 그대로
- **다운스트림**: 요청이 결국 닿는 아래층 자원(커넥션 풀, 외부 API). 처리율의 진짜 상한
{{< /callout >}}
