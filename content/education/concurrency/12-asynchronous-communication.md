11장에서 비동기 통신을 **개념**으로 다뤘다면, 이 장은 그것을 **어떻게 코드로 만드는가**에 관한 이야기다. 비동기 통신은 네트워크 요청이나 입출력처럼 오래 걸리는 작업이 프로그램을 멈추지 않게 하면서도, 스레드를 늘리지 않고 단일 프로세스로 처리하는 개발 기법이다. 그 토대가 되는 실행 모델이 **협동적 멀티태스킹(cooperative multitasking)** 이고, 이를 코드로 표현하는 두 가지 대표 추상화가 **코루틴(coroutine)** 과 **퓨처(future)** 다.

---

## 1. 비동기 통신이란

> **비동기 통신**은 시간이 오래 걸리는 작업이 **블로킹을 일으키지 않도록** 하면서 단일 프로세스로 실행하는 소프트웨어 개발 기법이다. 작업을 백그라운드에서 시작한 뒤 **완료를 기다리지 않고** 다음 작업으로 넘어간다.

핵심은 "빨리 계산하기"가 아니라 **기다리는 시간을 회수하기**다. 대기하느라 놀고 있던 CPU에게 다른 일을 시키면, 같은 하드웨어로 더 많은 일을 처리할 수 있다.

```
동기 호출
─────────────────────────
호출자 ██──────대기──────██
피호출        ████████
   총 시간 = 처리 시간 전부

비동기 호출
─────────────────────────
호출자 ██──다른 일──██(결과)
피호출   ████████
   대기 시간을 일로 회수
```

### 1.1 비동기성은 구현이 아니라 성질이다

여기서 짚고 갈 것이 있다. **비동기성은 연산의 호출이나 정보 교환이 갖는 *특성*이지, 특정 구현에 얽매인 개념이 아니다.**

| 계층 | 비동기가 나타나는 모습 |
|:-----|:-----|
| 하드웨어 | DMA — CPU 개입 없이 장치가 메모리에 직접 전송 |
| OS 커널 | 인터럽트, `epoll`, `io_uring` 완료 통지 |
| 언어 런타임 | 코루틴, `async`/`await`, 이벤트 루프 |
| 라이브러리 | `CompletableFuture`, Reactor, RxJava |
| 시스템 아키텍처 | 메시지 큐(Kafka, RabbitMQ), 이벤트 소싱 |

{{< callout type="info" >}}
같은 "비동기"라는 말이 스레드 하나 안의 코루틴에도, 서버 수백 대를 잇는 메시지 큐에도 쓰인다. 어느 층위의 이야기인지 먼저 확인하는 습관이 혼란을 크게 줄여 준다. 이 장은 **한 프로세스 안에서의 비동기**를 다루고, 시스템 간 비동기는 [5장의 메시지 큐](../05-inter-process-communication)가 다룬다.
{{< /callout >}}

### 1.2 얻는 것과 잃는 것

| 이득 | 설명 |
|:-----|:-----|
| 자원 효율 | 대기 시간에 다른 작업 수행 → 스레드 수를 줄임 |
| 지연 시간 감소 | 독립적인 요청을 동시에 시작 → 총 시간이 최대값으로 수렴 |
| 처리율 향상 | 같은 스레드로 더 많은 요청 처리 |
| 확장성 | 커넥션 수가 늘어도 메모리가 선형으로 폭증하지 않음 |

| 대가 | 설명 |
|:-----|:-----|
| 코드 복잡도 | 흐름이 쪼개져 위에서 아래로 읽히지 않음 |
| 디버깅 곤란 | 스택 트레이스가 끊겨 원인 추적이 어려움 |
| 전파성 | 한 곳을 비동기로 만들면 호출 사슬 전체가 비동기가 됨 |
| 오염 위험 | 블로킹 호출 하나가 전체를 멈춤([11장 4.3절](../11-event-driven-concurrency)) |

```java
// 독립적인 세 호출 — 동기라면 300+200+250 = 750ms
// 비동기라면 max(300, 200, 250) = 300ms
CompletableFuture<User>    u = findUserAsync(id);      // 300ms
CompletableFuture<Point>   p = findPointAsync(id);     // 200ms
CompletableFuture<Coupon>  c = findCouponAsync(id);    // 250ms

CompletableFuture.allOf(u, p, c).join();               // 약 300ms
render(u.join(), p.join(), c.join());
```

{{< callout type="warning" >}}
비동기의 이득은 **작업들이 서로 독립적일 때** 나온다. 위 예제에서 `findPoint`가 `findUser`의 결과를 필요로 한다면 순서가 강제되므로 750ms가 그대로 유지된다. 비동기로 바꾸기 전에 [7장의 의존 관계 그래프](../07-task-decomposition)를 먼저 그려 보는 이유다.
{{< /callout >}}

## 2. 협동적 멀티태스킹 — 비동기를 떠받치는 실행 모델

> **협동적 멀티태스킹**은 여러 작업이 프로세서 시간과 시스템 자원을 공유하되, **각 작업이 스스로 제어권을 반납**하는 방식이다.

[6장](../06-multitasking)에서 선점형과 나란히 비교했던 그 개념이다. 비동기 시스템을 구현하는 데 가장 널리 쓰이는 방식이므로, 여기서는 **왜 비동기와 궁합이 좋은지**에 초점을 맞춰 다시 본다.

### 2.1 누가 전환을 결정하는가

```
선점형 (OS가 뺏는다)
 A▪▪▪│B▪▪▪│A▪▪▪│C▪▪▪
     ▲ 타이머 인터럽트
       커널 개입 = 문맥 전환

협동형 (작업이 넘긴다)
 A▪▪▪▶B▪▪▪▶A▪▪▪▶C▪▪▪
     ▲ yield / suspend
       함수 호출 수준의 전환
```

| 구분 | 선점형 | 협동형 |
|:-----|:-----|:-----|
| 전환 주체 | OS 스케줄러 | 작업 자신 |
| 전환 시점 | 예측 불가(언제든) | 명시적 지점에서만 |
| 전환 비용 | 시스템 콜 + 문맥 전환 | 함수 호출 수준 |
| 공평성 | 커널이 보장 | 작업의 협조에 의존 |
| 동기화 | 락 필요 | 전환점이 명시적이라 단순 |

{{< callout type="info" >}}
협동형에서는 **전환이 일어나는 지점을 코드에서 볼 수 있다**. `suspend`나 `await`가 없는 구간은 통째로 원자적으로 실행된다는 뜻이다. 이 성질 덕분에 [8장의 경쟁 조건](../08-race-conditions-and-synchronization)이 발생할 수 있는 위치가 극도로 좁아지고, 락이 필요한 자리도 크게 줄어든다.
{{< /callout >}}

### 2.2 사용자 수준 스레드 vs 커널 수준 스레드

협동적 멀티태스킹의 실행 단위는 OS가 모르는 **사용자 수준 스레드**다. 커널은 스레드 몇 개만 보고 있고, 그 위에서 런타임이 수많은 작업을 갈아 끼운다.

```
   사용자 공간
┌────────────────────────┐
│ 코루틴 C1 C2 C3 ... Cn │
└───────────┬────────────┘
            │ 런타임 스케줄러
            ▼
   커널 공간
┌────────────────────────┐
│  커널 스레드 T1   T2   │
└───────────┬────────────┘
            ▼
       코어1   코어2
```

| 구분 | 커널 수준 스레드 | 사용자 수준 스레드(코루틴) |
|:-----|:-----|:-----|
| 스택 | 고정 크기(기본 1MB 내외) | 힙에 가변 저장, 수백 B~KB |
| 생성 비용 | 시스템 콜, 수십 µs | 객체 할당, 수백 ns |
| 전환 비용 | 문맥 전환, µs 단위 | 함수 호출, ns 단위 |
| 스케줄링 | OS 커널 | 언어 런타임 |
| 실용적 개수 | 수천 개 | 수십만~수백만 개 |
| 코어 활용 | 커널이 자동 분산 | 런타임이 다중 스레드에 배치 |

### 2.3 왜 오버헤드가 극적으로 줄어드는가

협동적 멀티태스킹을 채용하면 **CPU와 메모리 오버헤드를 크게 줄일 수 있다.** 특히 입출력 위주 작업이 많은 서버나 데이터베이스에서 효과가 크다.

```
동시 요청 10,000건 처리

스레드 기반
  스레드 10,000개 × 1MB = 약 10GB
  문맥 전환 초당 수만 회

코루틴 기반
  스레드 8개 + 코루틴 10,000개
  메모리 수십 MB, 전환은 함수 호출
```

{{< callout type="info" >}}
적은 스레드로 많은 작업을 처리하므로 하드웨어를 효율적으로 쓸 수 있고, **비동기 통신과 결합하면 자원 효율이 한 번 더 올라간다.** 코루틴이 I/O를 기다릴 때 스레드를 붙잡고 있지 않고 반납하기 때문이다. 협동적 멀티태스킹과 비동기 I/O는 따로 쓸 때보다 함께 쓸 때 훨씬 강력하다.
{{< /callout >}}

### 2.4 협동의 대가 — 반납하지 않는 작업

협동형의 유일한 전제는 **각 작업이 적절한 시기에 제어권을 반납한다**는 것이다. 이 약속이 깨지면 그 순간 전체가 멈춘다.

```
정상 — 제때 반납
 A▪▪▶B▪▪▶C▪▪▶A▪▪▶B▪▪

배신 — B가 반납하지 않음
 A▪▪▶B■■■■■■■■■■■■■■
             ▲
     C와 A는 영원히 대기
```

| 위험 행동 | 대안 |
|:-----|:-----|
| 코루틴 안에서 블로킹 I/O 호출 | 논블로킹 API 또는 전용 디스패처로 위임 |
| 긴 CPU 연산을 통째로 실행 | 중간중간 `yield()`, 또는 별도 스레드 풀 |
| `Thread.sleep()` 사용 | `delay()` 같은 논블로킹 대기 |
| 동기 락 획득 대기 | 코루틴용 `Mutex`, 또는 단일 스레드 소유 |

{{< callout type="warning" >}}
[11장에서 본 "콜백은 블로킹하면 안 된다"](../11-event-driven-concurrency)는 규칙과 정확히 같은 문제다. 실행 단위가 콜백이든 코루틴이든, **협동형 위에서 도는 코드는 스스로 물러날 의무**를 진다. 코틀린에서 `runBlocking`을 `suspend` 함수 안에 쓰거나, 코루틴에서 JDBC를 그대로 호출하는 것이 대표적인 사고 사례다.
{{< /callout >}}

## 3. 코루틴

> **코루틴**은 실행 도중에 실행을 **멈췄다가**, 나중에 어떤 조건이 충족되면 **그 자리에서 재개**할 수 있는 함수다.

### 3.1 서브루틴과 무엇이 다른가

우리가 아는 보통의 함수는 **서브루틴(subroutine)** 이다. 한 번 들어가면 끝까지 실행하고 한 번 반환한다.

```
서브루틴 — 진입 1회, 종료 1회
  호출 ─▶ [ 함수 ] ─▶ 반환
    끝나면 지역 상태 소멸

코루틴 — 진입 n회, 중단 n회
  호출 ─▶ [ 함수 ]
          ⏸ suspend (상태 보존)
  재개 ─▶ [ 함수 ]
          ⏸ suspend
  재개 ─▶ [ 함수 ] ─▶ 반환
```

| 구분 | 서브루틴 | 코루틴 |
|:-----|:-----|:-----|
| 진입점 | 시작 지점 1개 | 재개할 때마다 여러 개 |
| 종료 | 반환 1회 | 중단(suspend) n회 + 반환 1회 |
| 지역 상태 | 반환 시 소멸 | 중단해도 보존 |
| 호출 관계 | 호출자–피호출자 종속 | 대등한 협력 관계 |
| 스택 | 스레드 스택 사용 | 힙에 프레임 저장 |

### 3.2 비동기 I/O를 코루틴으로 처리하기

```
코루틴 A ─▶ I/O 요청
   ⏸ suspend (스레드 반납)
        ▼
코루틴 B ─▶ 실행
   ⏸ suspend
        ▼
코루틴 A ◀─ I/O 완료 통지
   같은 자리에서 재개
   스레드 1개, 유휴 시간 0
```

```kotlin
// 코틀린 코루틴 — 동기처럼 읽히지만 블로킹하지 않는다
suspend fun loadDashboard(id: Long): Dashboard = coroutineScope {
    val user   = async { userApi.find(id) }      // 동시에 시작
    val orders = async { orderApi.findBy(id) }
    val coupon = async { couponApi.findBy(id) }

    // await 지점에서만 중단 — 그동안 스레드는 다른 코루틴을 실행
    Dashboard(user.await(), orders.await(), coupon.await())
}
```

```kotlin
// 코루틴 10만 개를 띄워도 스레드는 코어 수만큼만 쓴다
fun main() = runBlocking {
    val jobs = List(100_000) { i ->
        launch(Dispatchers.IO) {
            delay(1000)                 // 논블로킹 대기 — 스레드를 놓아 준다
            println("작업 $i 완료")
        }
    }
    jobs.forEach { it.join() }
}
// 스레드로 같은 일을 하면 10만 개 × 1MB ≈ 100GB 스택이 필요하다
```

### 3.3 코루틴은 어떻게 상태를 기억하는가

코루틴의 마법처럼 보이는 부분은 사실 **컴파일러가 함수를 상태 머신으로 변환**한 결과다. 중단 지점마다 번호를 붙이고, 지역 변수를 객체 필드로 옮긴다.

```kotlin
// 우리가 쓰는 코드
suspend fun load(id: Long): Result {
    val user = fetchUser(id)        // 중단점 1
    val order = fetchOrder(user)    // 중단점 2
    return Result(user, order)
}
```

```java
// 컴파일러가 만들어 내는 구조 (개념적 표현)
class LoadCoroutine {
    int label = 0;                  // 어디까지 진행했는가
    User user;                      // 지역 변수 → 필드로 승격

    Object resume(Object prev) {
        switch (label) {
            case 0:
                label = 1;
                return fetchUser(id);      // 중단 — 여기서 반환
            case 1:
                user = (User) prev;        // 재개 — 이전 결과 수령
                label = 2;
                return fetchOrder(user);   // 중단
            case 2:
                return new Result(user, (Order) prev);
        }
    }
}
```

{{< callout type="info" >}}
[11장에서 "이벤트 기반 코드는 진행 상태를 객체 필드에 직접 보관해야 한다"](../11-event-driven-concurrency)고 했다. 코루틴은 **바로 그 작업을 컴파일러가 대신해 주는 것**이다. 우리는 순차 코드를 쓰고, 컴파일러가 콜백과 상태 머신으로 바꾼다. 코루틴이 "콜백 지옥의 해법"이라 불리는 이유가 여기 있다.
{{< /callout >}}

### 3.4 코루틴과 스레드의 관계

| 구분 | 스레드 | 코루틴 |
|:-----|:-----|:-----|
| 소속 | OS가 관리 | 언어 런타임이 관리 |
| 개수 | 수천 개가 한계 | 수십만~수백만 개 |
| 중단 | OS가 강제로 뺏음 | 중단점에서 스스로 |
| 대기 | 스레드가 통째로 멈춤 | 스레드를 놓고 물러남 |
| 취소 | 안전한 취소가 어려움 | 협조적 취소가 구조화됨 |
| 관계 | — | 코루틴 다수 ↔ 스레드 소수 (M:N) |

{{< callout type="warning" >}}
**코루틴은 "가벼운 스레드"가 아니라 "스레드를 양보할 줄 아는 작업"이다.** 코루틴을 10만 개 띄워도 블로킹 호출을 하면 그 코루틴이 올라탄 스레드가 그대로 묶인다. 스레드 풀이 8개라면 8개의 블로킹 호출로 전체가 정지한다. 코루틴의 이득은 **논블로킹 API와 함께 쓸 때만** 실현된다.
{{< /callout >}}

## 4. 퓨처와 프로미스

> **퓨처 객체**는 미래에 완료될, **아직 알 수 없는 연산 결과**를 전달받기 위한 프록시 객체다.

비동기 호출은 결과를 즉시 줄 수 없다. 그래서 "결과가 들어올 자리"를 미리 반환한다. 그 자리표가 퓨처다.

### 4.1 결과의 자리표

```
   비동기 호출
        │
        ▼
┌────────────────┐
│  Future<T>     │ ← 즉시 반환
│  state: 대기중 │
└────────┬───────┘
         │ 백그라운드 완료
         ▼
┌────────────────┐
│  Future<T>     │
│  state: 완료   │
│  value: 결과   │ → get() 즉시 반환
└────────────────┘
```

| 상태 | 의미 |
|:-----|:-----|
| 대기(pending) | 연산이 아직 진행 중 |
| 완료(fulfilled) | 결과값이 채워짐 |
| 실패(rejected) | 예외로 종료됨 |
| 취소(cancelled) | 외부에서 중단됨 |

### 4.2 자바의 Future와 그 한계

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<String> future = pool.submit(() -> {
    Thread.sleep(1000);
    return "결과";
});

doSomethingElse();          // 여기까지는 비동기의 이득을 본다
String result = future.get();   // ← 하지만 결국 블로킹된다
```

`Future`는 결과를 담는 그릇일 뿐, **완료를 통지받는 수단이 없다.** 결과를 쓰려면 `get()`으로 기다리거나 `isDone()`으로 폴링해야 하는데, 둘 다 비동기의 취지를 무너뜨린다.

| 한계 | 설명 |
|:-----|:-----|
| 완료 통지 없음 | 콜백을 등록할 수 없음 → `get()` 블로킹 |
| 조합 불가 | 두 퓨처를 이어 붙이거나 합칠 방법이 없음 |
| 예외 처리 빈약 | `ExecutionException`으로 감싸여 전달 |
| 수동 완료 불가 | 외부에서 값을 채워 넣을 수 없음 |

### 4.3 CompletableFuture — 조합 가능한 퓨처

자바 8의 `CompletableFuture`는 위 한계를 모두 해결한다. 완료 시점에 실행할 코드를 **등록**할 수 있으므로 블로킹 없이 파이프라인을 만든다.

```java
CompletableFuture
    .supplyAsync(() -> userApi.find(id))          // 비동기 시작
    .thenApply(user -> user.getGrade())           // 결과 변환
    .thenCompose(grade -> discountApi.of(grade))  // 다른 비동기 연결
    .thenCombine(policyFuture, this::apply)       // 두 결과 합치기
    .thenAccept(result -> render(result))         // 최종 소비
    .exceptionally(e -> {                         // 예외 한곳에서 처리
        log.error("대시보드 조회 실패", e);
        return null;
    });
// 어느 지점에서도 스레드가 블로킹되지 않는다
```

| 메서드 | 역할 |
|:-----|:-----|
| `supplyAsync` | 비동기 연산 시작 |
| `thenApply` | 결과를 동기 함수로 변환 |
| `thenCompose` | 결과로 다음 비동기 연산 연결(평탄화) |
| `thenCombine` | 독립적인 두 퓨처의 결과 결합 |
| `allOf` / `anyOf` | 여러 퓨처를 모두 / 먼저 끝난 것 대기 |
| `exceptionally` | 예외 복구 |
| `orTimeout` | 제한 시간 초과 시 실패 처리(Java 9+) |

{{< callout type="warning" >}}
`thenApply`와 `thenCompose`를 혼동하면 `CompletableFuture<CompletableFuture<T>>`라는 중첩이 생긴다. **다음 단계가 또 비동기라면 `thenCompose`** 를 써야 한다. 스트림의 `map`과 `flatMap` 관계와 정확히 같다.
{{< /callout >}}

### 4.4 퓨처와 프로미스

두 용어는 자주 섞여 쓰이지만, 원래는 **읽는 쪽과 쓰는 쪽**을 나눈 이름이다.

```
프로미스 (쓰기 측)        퓨처 (읽기 측)
 생산자가 값을 채움  ──▶  소비자가 값을 읽음
   complete(v)             thenApply(...)
```

| 구분 | 퓨처(Future) | 프로미스(Promise) |
|:-----|:-----|:-----|
| 관점 | 결과를 **읽는** 쪽 | 결과를 **쓰는** 쪽 |
| 완료 권한 | 없음(관찰만) | 있음(직접 채움) |
| 자바 | `Future`, `CompletionStage` | `CompletableFuture.complete()` |
| 자바스크립트 | `Promise`(둘을 합친 형태) | `resolve` / `reject` |

```java
// CompletableFuture는 퓨처와 프로미스를 겸한다
CompletableFuture<String> promise = new CompletableFuture<>();

// 읽는 쪽 — 완료를 기다리지 않고 처리기를 등록
promise.thenAccept(msg -> log.info("수신: {}", msg));

// 쓰는 쪽 — 콜백 기반 레거시 API를 퓨처로 감쌀 때 유용
legacyClient.onMessage(promise::complete);
legacyClient.onError(promise::completeExceptionally);
```

## 5. async/await — 비동기를 동기처럼 쓰기

콜백과 퓨처 체인은 여전히 "평소 코드"와 다르게 생겼다. `async`/`await`는 **컴파일러가 코루틴 변환을 수행**해, 비동기 코드를 순차 코드처럼 쓰게 해 준다.

```javascript
// 콜백 → 퓨처 체인 → async/await 로의 진화
async function loadDashboard(id) {
  try {
    const user   = await findUser(id);      // 여기서 중단, 스레드는 반납
    const orders = await findOrders(user);  // 재개 후 다음 중단
    return render(user, orders);
  } catch (e) {
    log.error('조회 실패', e);              // try-catch가 그대로 동작
  }
}
```

| 세대 | 방식 | 흐름 표현 | 예외 처리 |
|:-----|:-----|:-----|:-----|
| 1세대 | 콜백 | 중첩(→ 콜백 지옥) | 인자로 전달, 누락되기 쉬움 |
| 2세대 | 퓨처·프로미스 | 체인(평탄) | `exceptionally` 한곳 |
| 3세대 | 리액티브 스트림 | 스트림 + 배압 | `onErrorResume` |
| 4세대 | 코루틴·async/await | **순차 코드와 동일** | `try-catch` 그대로 |

{{< callout type="info" >}}
`await`는 **블로킹이 아니라 중단**이다. 겉보기엔 `Future.get()`처럼 결과를 기다리는 것 같지만, 실제로는 함수를 그 지점에서 접어 두고 스레드를 반납한다. "동기처럼 보이는 코드가 실제로는 이벤트 루프 위에서 돈다"는 것이 async/await의 전부다.
{{< /callout >}}

## 6. 자바의 선택 — 가상 스레드

자바 21의 **가상 스레드(virtual thread)** 는 같은 문제를 정반대 방향에서 푼다. 코드를 비동기로 바꾸는 대신, **스레드를 코루틴만큼 싸게 만들어** 블로킹 스타일 코드를 그대로 쓰게 한다.

```java
// 블로킹 코드 그대로 — 그런데 요청 10만 개를 견딘다
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 100_000; i++) {
        executor.submit(() -> {
            var user = userApi.find(id);      // 블로킹 호출처럼 보이지만
            var order = orderApi.find(user);  // JVM이 캐리어 스레드를 회수한다
            return render(user, order);
        });
    }
}
```

```
가상 스레드의 동작
────────────────────────
가상 스레드가 블로킹 호출
        │
        ▼
JVM이 스택을 힙으로 대피
캐리어 스레드 즉시 반납
        │
        ▼
I/O 완료 → 스택 복원 후 재개
   코드는 동기, 실행은 비동기
```

| 구분 | 코루틴(Kotlin) | 가상 스레드(Java 21) |
|:-----|:-----|:-----|
| 표현 | `suspend` 함수 | 평범한 블로킹 코드 |
| 전파성 | `suspend`가 호출 사슬 전체로 번짐 | 없음 — 기존 코드 그대로 |
| 중단 지점 | 코드에 명시적으로 보임 | 보이지 않음(런타임이 판단) |
| 라이브러리 | 코루틴 지원 API 필요 | 기존 블로킹 API 대부분 호환 |
| 배압 제어 | 구조화된 동시성으로 명시 | 세마포어 등으로 직접 제어 |

{{< callout type="warning" >}}
가상 스레드에도 함정이 있다. `synchronized` 블록 안에서 블로킹하면 캐리어 스레드가 **핀(pin)** 되어 반납되지 않는다(Java 21 기준, `ReentrantLock`으로 대체하면 해결). 또 스레드가 싸졌다고 무한정 만들면 **다운스트림(DB 커넥션 풀 등)이 먼저 무너진다.** 값싼 동시성이 곧 무제한 동시성은 아니다.
{{< /callout >}}

## 7. 비동기 추상화 선택 가이드

| 상황 | 권장 |
|:-----|:-----|
| 독립적인 API 호출 여러 개 합치기 | `CompletableFuture.allOf` + `thenCombine` |
| 콜백 기반 레거시 API 감싸기 | `CompletableFuture` (프로미스로 사용) |
| 스트림 + 배압이 필요한 데이터 흐름 | 리액티브 스트림(Reactor, RxJava) |
| 복잡한 비동기 흐름 + 취소·타임아웃 | 코루틴(구조화된 동시성) |
| 기존 블로킹 코드를 확장만 하고 싶을 때 | 가상 스레드 |
| CPU 바운드 병렬 처리 | 스레드 풀 / Fork-Join([7장](../07-task-decomposition)) |

{{< callout type="warning" >}}
**비동기는 CPU 바운드 작업에 도움이 되지 않는다.** 비동기가 회수하는 것은 *기다리는 시간*인데, CPU 바운드 작업에는 기다림 자체가 없다. 계산이 병목이라면 답은 코어를 더 쓰는 **병렬화**([2장](../02-sequential-and-parallel-execution))이지 비동기가 아니다. 모델을 고르기 전에 워크로드부터 분류해야 한다([6장 2절](../06-multitasking)).
{{< /callout >}}

## 8. 정리

```
 비동기 통신 한눈에 보기
 ──────────────────────────────
 무엇?  완료를 기다리지 않고 진행
        대기 시간을 다른 일로 회수

 어떤 실행 모델로?
  협동적 멀티태스킹
   ├ 작업이 스스로 제어권 반납
   ├ 사용자 수준 스레드 = 값싸다
   └ 반납 안 하면 전체가 멈춘다

 어떤 추상화로?
  코루틴 : 멈췄다 재개하는 함수
  퓨처   : 미래 결과의 자리표
   └ async/await, 가상 스레드로 진화

 어디에?  I/O 바운드에만
          CPU 바운드는 병렬화
```

### 한 줄 정리

| 개념 | 한 줄 |
|:-----|:------|
| **비동기 통신** | "완료를 안 기다리고 진행, 대기 시간을 일로 회수" |
| **비동기성** | "구현이 아니라 호출·정보 교환의 *성질*" |
| **협동적 멀티태스킹** | "OS가 뺏는 게 아니라 작업이 스스로 넘긴다" |
| **사용자 수준 스레드** | "커널이 모르는 값싼 실행 단위, 수십만 개도 가능" |
| **코루틴** | "멈췄다가 그 자리에서 다시 시작하는 함수" |
| **상태 머신 변환** | "컴파일러가 순차 코드를 콜백+상태로 바꿔 준다" |
| **퓨처** | "미래에 올 결과를 대신 받아 두는 프록시" |
| **프로미스** | "그 퓨처에 값을 써 넣는 쪽" |
| **CompletableFuture** | "조합 가능한 퓨처 — 블로킹 없이 파이프라인" |
| **async/await** | "비동기를 순차 코드처럼, try-catch도 그대로" |
| **가상 스레드** | "코드는 그대로 두고 스레드를 싸게 만든다" |

{{< callout type="info" >}}
**핵심 정리:**
1. **비동기 통신**은 오래 걸리는 작업이 블로킹을 일으키지 않게 하면서 단일 프로세스로 처리하는 기법이다 — 백그라운드로 시작하고 완료를 기다리지 않아 자원 효율·지연 시간·처리율·확장성이 모두 개선된다
2. **비동기성은 특정 구현에 얽매인 개념이 아니라** 호출과 정보 교환이 갖는 성질이다. DMA부터 메시지 큐까지 모든 계층에 나타난다
3. 대가는 **작성과 디버깅의 어려움**이다. 제대로 된 라이브러리나 프레임워크 없이 비동기를 직접 다루면 흐름이 쪼개지고 원인 추적이 힘들어진다
4. **협동적 멀티태스킹**은 비동기 시스템 구현에 가장 널리 쓰이는 방식으로, 각 작업이 **스스로 제어권을 반납**해 프로세서 시간과 자원을 공유한다
5. 사용자 수준 스레드는 시스템 스레드보다 자원을 훨씬 덜 쓰므로 **코루틴을 많이 만들어도 심각한 오버헤드가 없다.** 다만 각 작업이 **적절한 시기에 제어권을 반납**하는 것이 전제다
6. 협동적 멀티태스킹은 CPU·메모리 오버헤드를 크게 줄이며, **I/O 위주 서버·데이터베이스에서 효과가 크고**, 비동기 통신과 결합하면 자원 효율이 한 번 더 올라간다
7. 비동기 호출의 두 대표 추상화는 **코루틴**(멈췄다 조건이 충족되면 재개하는 함수)과 **퓨처 객체**(미래에 완료될 결과를 받기 위한 프록시)다
8. 비동기가 회수하는 것은 **기다리는 시간**이므로 I/O 바운드에만 효과가 있고, CPU 바운드에는 병렬화가 답이다
{{< /callout >}}
