[32](../32-network-card-data-transfer)장에서 이 PC의 curl이 example.com에 보낸 75바이트 요청이 133바이트 프레임이 되어 카드를 떠났다. 이 장은 그 프레임이 사무실 스위치와 게이트웨이 라우터, 통신사의 라우터들을 지나 서버 앞까지 가는 길을 따라간다. [14](../14-switch-structure)장은 프레임 하나가 스위치와 라우터를 차례로 지나는 전 과정을, [22](../22-router-structure)장은 표를 만드는 일과 표대로 보내는 일이 나뉜 라우터의 안을 여기로 미뤘다. 원리는 셋이다. 첫째, **스위치는 겉봉만 보고 포트를 고르고, 라우터는 봉투를 뜯어 새 봉투에 싼다.** 읽는 깊이가 다르므로 하는 일도 다르다. 둘째, **홉마다 프레임은 새로 만들어지고 패킷은 그대로이며, 줄어드는 것은 TTL뿐이다.** 이 PC에서 example.com까지는 11홉이고, 답의 TTL을 읽으면 돌아오는 길의 라우터 수도 나온다. 셋째, **주소가 바뀌는 곳은 딱 두 군데다.** 프레임의 MAC은 홉마다 바뀌고, 패킷의 IP는 NAT에서만 바뀐다. 이 PC의 길에는 NAT가 없지만 집에서는 한 번, 통신사가 NAT를 하면 두 번 바뀐다. 이 장의 실측은 example.com까지의 경로 추적과 그 답의 TTL이다.

## 1. 역할 구분

| 항목 | 스위치 (L2) | 라우터 (L3) | 왜 다른가 |
|:-----|:-----------|:-----------|:----------|
| 읽는 층 | 1, 2 | 1, 2, 3 | [01](../01-network-basics)장. 장비의 계층은 어디까지 읽는가 |
| 주소 | MAC | IP | 이름과 위치. 13장 |
| 표 | MAC 주소 표 | 라우팅 표 | 엿보아 배운 표와 주고받아 만든 표. 22장 |
| 단위 | 프레임 | 패킷 | 봉투를 뜯느냐 안 뜯느냐 |
| 범위 | 같은 링크 | 망 사이 | 링크 밖의 이름은 뜻이 없다 |
| 브로드캐스트 | 넘긴다 | 막는다 | 프레임을 새로 싸므로 옛 주소가 버려진다 |

두 장비의 차이는 전부 첫 줄에서 나온다. 스위치는 프레임의 겉봉인 MAC 주소까지만 읽으므로 봉투를 뜯지 않고 그대로 다른 포트로 밀어내며, 라우터는 그 안의 IP 헤더까지 읽으므로 봉투를 벗기고 다음 링크의 봉투로 다시 싼다. 22장에서 본 대로 두 장비 모두 표를 만드는 일과 표대로 보내는 일이 나뉘어 있고, 이 장에서 따라가는 것은 "표대로 보내는" 쪽, 곧 패킷이 지나가는 순간의 일이다.

## 2. 네트워크 구성 예시

```text
[PC A] 192.168.1.10
   │
[스위치 A]
   │  LAN1  192.168.1.0/24
[라우터 A] WAN 172.16.0.1
   │
   │  WAN 링크 172.16.0.0/24
   │
[라우터 B] WAN 172.16.0.2
   │  LAN2  192.168.10.0/24
[스위치 B]
   │
[웹 서버] 192.168.10.100
```

책의 구성은 라우터 둘 사이에 링크 하나를 둔 가장 작은 인터넷이다. 실제 길은 이 모양이 여러 번 반복된 것이고, 이 PC에서 example.com까지를 추적하면 이렇다.

```
[이 PC]
   │ 사무실 스위치
[게이트웨이]        1홉   <1ms
[통신사 라우터들]   2~8홉 1~30ms
[클라우드플레어]    10홉  32ms
[example.com]      11홉  32ms
```

| 홉 | 누구 | 왕복 | 뜻 |
|:---|:-----|:-----|:---|
| 1 | 사무실 게이트웨이 | 1ms 미만 | 같은 건물 |
| 2, 3 | 통신사 | 8~11ms | 통신사의 첫 라우터들 |
| 4, 5 | 통신사 | 응답 없음 | 17장. ICMP를 보내지 않는 라우터 |
| 6 | 통신사 | 1~27ms | 100.64.0.0/10 대역의 주소 |
| 7, 8 | 통신사 | 30ms | 여기서 30ms가 붙는다. 국외로 나가는 구간 |
| 9 | ? | 응답 없음 | |
| 10 | 클라우드플레어 | 32ms | 서버 회사의 라우터 |
| 11 | example.com | 32ms | 도착 |

책의 라우터 A가 1홉의 게이트웨이, 라우터 B가 10홉의 클라우드플레어 라우터이고, 그 사이의 "WAN 링크 하나"가 실제로는 통신사 라우터 일곱 개다. 6홉부터 8홉의 주소가 [04](../04-home-lan-configuration)장에서 본 100.64.0.0/10 대역인 것은 통신사가 자기 안의 라우터 사이 링크에 공인 주소를 쓰지 않고 통신사용 대역을 쓰기 때문이다. 밖에서 닿을 필요가 없는 링크에 공인 주소를 낭비하지 않는 것이고, 그 라우터들이 우리 패킷을 넘기는 데는 아무 지장이 없다. 7홉에서 왕복이 1ms에서 30ms로 뛰는 것은 [01](../01-network-basics)장에서 본 빛의 시간이다. 그 앞은 같은 도시, 그 뒤는 바다 건너다.

{{< callout type="info" >}}
책의 그림은 WAN 링크에 사설 대역 172.16.0.0/24를 쓴 단순화한 실습 구성이고, 그래서 5절의 책 예제에서는 라우터 A가 NAT로 출발지를 172.16.0.1로 바꾼다. 이 PC의 실제 길에는 NAT가 없다. [18](../18-ip-address-structure)장에서 본 대로 이 PC는 공인 주소를 직접 갖고 있어 출발지 주소가 example.com까지 그대로 간다. 집이라면 공유기에서 한 번 바뀌고, 그 이야기는 6절에 있다.
{{< /callout >}}

## 3. 스위치의 동작

```
포트 1 → [물리]
           │ 전기 신호 → 비트
           ▼
         [데이터링크]
           │
           ▼
  ┌─────────────────────┐
  │ 1. 출발지 MAC 학습  │
  ├─────────────────────┤
  │ 2. 목적지 MAC 조회  │
  ├─────────────────────┤
  │ 3. 포워딩 결정      │
  └─────────────────────┘
           │
           ▼
         [물리]
           │ 전기 신호
           ▼
         포트 3
```

| 포트 | MAC 주소 | 남은 시간 |
|:-----|:---------|:----------|
| 1 | AA:BB:CC:DD:EE:FF | 300초 |
| 2 | 11:22:33:44:55:66 | 300초 |
| 3 | 77:88:99:AA:BB:CC | 300초 |

이 PC의 133바이트 프레임이 사무실 스위치의 포트에 들어오면 스위치는 세 가지를 한다. 출발지 MAC(이 카드의 B4:2E:99로 시작하는 주소)과 들어온 포트를 표에 적고, 목적지 MAC을 표에서 찾고, 그 포트로만 내보낸다. [14](../14-switch-structure)장에서 본 대로 이 표는 아무도 가르쳐 주지 않고 프레임의 출발지를 엿보아 채워진 것이며, 목적지인 게이트웨이의 MAC은 게이트웨이가 쉴 새 없이 프레임을 보내므로 표에서 지워질 틈이 없다. 그래서 이 프레임은 플러딩 없이 게이트웨이의 포트로 곧장 간다. 서버의 답이 게이트웨이에서 돌아올 때는 방금 배운 이 PC의 항목으로 이 PC의 포트에만 온다.

| 경우 | 조건 | 동작 | 왜 |
|:-----|:-----|:-----|:---|
| 유니캐스트 | 목적지가 표에 있다 | 그 포트로만 | 표가 답을 안다 |
| 플러딩 | 목적지가 표에 없다 | 들어온 포트를 뺀 전부로 | 모르면 모두에게 |
| 브로드캐스트 | FF:FF:FF:FF:FF:FF | 모든 포트로 | 표에 있을 수 없는 주소 |

스위치는 프레임 안을 보지 않는다. 이 프레임에 든 IP 주소가 클라우드플레어의 것이든 옆자리 PC의 것이든 스위치에게는 같은 일이고, 그래서 14장에서 본 대로 스위치의 전달은 봉투를 뜯지 않는 만큼 빠르다. TTL도 줄지 않는다. 스위치는 홉으로 세지 않는다.

{{< callout type="info" >}}
회사망의 중심에 있는 L3 스위치는 이 절의 스위치에 다음 절의 라우터를 전용 칩으로 얹은 것이다. [05](../05-office-lan-configuration)장의 VLAN 사이를 오가는 패킷은 라우터로 나갔다 오는 대신 이 칩 안에서 봉투를 갈아입는다. 하는 일은 같고 자리만 스위치 안이다.
{{< /callout >}}

## 4. 라우터의 동작

```
입력 포트
   │ 전기 신호 → 비트
   ▼
[데이터링크]
  - 목적지 MAC 확인
  - 이더넷 헤더 제거
   ▼
[네트워크]
  - 목적지 IP 확인
  - 라우팅 테이블 조회
  - TTL -1
  - NAT 처리 (필요 시)
   ▼
[데이터링크]
  - 다음 홉 MAC 조회(ARP)
  - 새 이더넷 헤더 추가
   ▼
출력 포트
   │ 전기 신호
   ▼
```

| 목적지 | 마스크 | 다음 홉 | 인터페이스 |
|:-------|:-------|:--------|:-----------|
| 192.168.1.0 | /24 | 직접 연결 | eth0 |
| 192.168.10.0 | /24 | 172.16.0.2 | eth1 |
| 172.16.0.0 | /16 | 직접 연결 | eth1 |
| 0.0.0.0 | /0 | 172.16.0.254 | eth1 |

게이트웨이는 프레임의 목적지 MAC이 자기 것임을 보고 받아들여 이더넷 헤더를 벗긴다. 여기서 프레임의 생애가 끝난다. 안에서 나온 IP 패킷의 목적지 104.20.23.154를 표에서 [17](../17-network-layer-role)장의 최장 일치로 찾으면, 사무실의 어느 망에도 맞지 않으므로 마지막 줄 0.0.0.0/0, 곧 통신사 쪽 인터페이스로 보내라는 답이 나온다. TTL을 128에서 127로 줄이고, [17](../17-network-layer-role)장에서 본 대로 TTL이 바뀌었으니 IP 헤더 체크섬을 다시 계산한다. 그리고 통신사 쪽 링크의 규칙대로 **새 프레임**을 만든다. 출발지 MAC은 게이트웨이의 그쪽 포트, 목적지 MAC은 통신사 라우터의 것이고, 그 MAC은 게이트웨이가 [15](../15-collision-free-structure)장의 ARP로 알아 두었다. 이 일을 2홉부터 10홉까지의 라우터가 똑같이 반복한다. 22장에서 본 대로 표를 찾고 봉투를 갈아입히는 일은 전달면의 칩이 하고, 그 표를 만드는 일은 별도로 돌아간다.

TTL이 줄어드는 이유는 [17](../17-network-layer-role)장에서 봤다. 라우터는 아무것도 기억하지 않으므로 표가 잘못되어 고리가 생기면 패킷이 스스로 죽어야 한다. 이 PC에서 example.com에 ping을 보내면 답의 TTL이 54다. 리눅스 서버의 시작값 64에서 10이 줄었으니 돌아오는 길에 라우터 열 개를 지났다는 뜻이고, 가는 길의 경로 추적이 11홉(라우터 열 개와 서버)인 것과 맞는다. 우리 패킷은 128에서 열을 빼 118로 도착한다. 4, 5, 9홉이 응답이 없는 것은 그 라우터가 없어서가 아니라 ICMP를 보내지 않도록 설정된 것이며, 패킷은 그 라우터에서도 똑같이 봉투를 갈아입고 TTL 하나를 냈다. 답의 TTL 54가 그 증거다.

## 5. 구간별 헤더 변화

책의 구성에서 세 구간이다.

```
구간 1: PC A → 라우터 A (LAN1)
ETH  src PC A      dst 라우터 A (LAN)
IP   src 192.168.1.10
     dst 192.168.10.100
```

```
구간 2: 라우터 A → 라우터 B (WAN)
ETH  src 라우터 A (WAN)  dst 라우터 B
IP   src 172.16.0.1  ← NAT
     dst 192.168.10.100
```

```
구간 3: 라우터 B → 웹 서버 (LAN2)
ETH  src 라우터 B (LAN)  dst 웹 서버
IP   src 172.16.0.1
     dst 192.168.10.100
```

이 PC의 실제 길에서는 이렇다.

| 구간 | 출발지 MAC | 목적지 MAC | 출발지 IP | 목적지 IP | TTL |
|:-----|:----------|:-----------|:----------|:----------|:----|
| 이 PC → 게이트웨이 | 이 카드 | 게이트웨이 | 이 PC의 공인 주소 | 104.20.23.154 | 128 |
| 게이트웨이 → 통신사 | 게이트웨이 | 통신사 라우터 | 같다 | 같다 | 127 |
| ... 통신사 안 일곱 번 ... | 그 링크의 둘 | 그 링크의 둘 | 같다 | 같다 | 126 ~ 120 |
| 클라우드플레어 → 서버 | 그쪽 라우터 | 서버 | 같다 | 같다 | 118 |

| 값 | 어디서 바뀌나 | 왜 |
|:---|:-------------|:---|
| MAC 주소 | 홉마다 | 프레임은 링크 하나의 것. 둘째 원리 |
| IP 주소 | NAT에서만 | 패킷은 끝에서 끝까지의 것. 이 길에는 NAT가 없다 |
| TTL | 라우터마다 1 | 패킷이 스스로 죽는 장치 |
| IP 체크섬 | 라우터마다 다시 | TTL이 바뀌었다 |
| TCP 헤더와 HTTP | 안 바뀐다 | 라우터는 4층을 읽지 않는다. 23장 |

원리를 한 줄로 줄이면 이렇다. 프레임은 링크 하나의 것이라 링크마다 새로 만들어지고, 패킷은 양 끝의 것이라 그대로 간다. 책 예제의 구간 2에서 출발지 IP가 바뀐 것은 라우터 A가 NAT를 했기 때문이고, 그것이 IP 주소가 바뀌는 유일한 경우다.

## 6. NAT

| 어디에 | NAT 횟수 | 왜 |
|:-------|:---------|:---|
| 이 PC → 인터넷 | 0 | 18장. 사무실이 공인 주소를 직접 준다 |
| 집의 PC → 인터넷 | 1 | 04장. 공유기가 사설 주소를 공인 주소로 |
| 통신사가 CGNAT를 하는 집 | 2 | 04장. 공유기에서 한 번, 통신사에서 한 번 더 |
| 이 PC 안의 WSL → 인터넷 | 1 | 18장. Hyper-V가 172.27.x를 이 PC의 공인 주소로 |

IPv4 주소가 모자라 집과 회사 안은 사설 주소를 쓰고 밖으로 나갈 때 경계의 라우터가 공인 주소로 바꾼다. [04](../04-home-lan-configuration)장에서 본 대로 주소만 바꾸면 답장이 누구 것인지 알 수 없으므로 포트까지 바꾸고 그 대응을 표에 적는다(PAT). 이 장의 관점에서 NAT는 4절의 라우터 동작에 한 단계가 끼어든 것이다. 봉투를 뜯어 IP 헤더를 읽는 김에 출발지 주소와 포트를 고쳐 쓰고, [23](../23-transport-layer-role)장에서 본 대로 원칙적으로 읽지 않는 4층 헤더까지 손대는 예외다. TCP 체크섬에는 주소가 들어 있으므로 그것까지 다시 계산한다.

| 안 | 밖 |
|:---|:---|
| 192.168.1.10:54321 | 203.0.113.10:54321 |
| 192.168.1.20:54322 | 203.0.113.10:54322 |
| 192.168.1.30:54323 | 203.0.113.10:54323 |

```bash
# Linux 상자를 NAT 라우터로
sudo sysctl -w net.ipv4.ip_forward=1
sudo iptables -t nat -A POSTROUTING \
  -o eth1 -j MASQUERADE
```

첫 줄이 [17](../17-network-layer-role)장에서 본 "Forwarding"이다. 이 PC는 그 값이 꺼져 있어 남의 패킷을 넘기지 않는 호스트이고, 리눅스 상자는 이 한 줄로 라우터가 된다. 둘째 줄이 나가는 패킷의 출발지를 그 인터페이스의 주소로 바꾸라는 NAT 규칙이다. 집의 공유기 안에서 도는 것이 이 두 줄과 같다.

## 7. 실무 명령

```bash
ip route show                 # Linux 라우팅 표
ip route get 104.20.23.154    # 이 목적지에 이기는 줄
route print -4                # Windows
show ip route                 # Cisco
```

```bash
tracert -d 104.20.23.154      # Windows
traceroute example.com        # Linux, macOS
mtr example.com               # ping과 추적을 함께
ping 104.20.23.154            # 답의 TTL로 홉 수를 센다
```

```
tracert -d 104.20.23.154

 1   <1 ms  게이트웨이
 2    9 ms  통신사
 3   11 ms  통신사
 4    *     응답 없음
 5    *     응답 없음
 6    1 ms  통신사 (100.65.x.x)
 7   32 ms  통신사 (100.67.x.x)
 8   30 ms  통신사 (100.67.x.x)
 9    *     응답 없음
10   32 ms  클라우드플레어
11   32 ms  104.20.23.154
```

2절의 표가 이 출력이다. 답의 TTL로 홉 수를 세는 법도 있다. 리눅스는 64, Windows는 128, 라우터는 255에서 시작하므로 답의 TTL을 그 값에서 빼면 돌아온 길의 라우터 수가 나온다. example.com의 답 54는 64에서 10을 뺀 것이다.

```
Switch# show mac address-table
Switch# show mac address-table \
        interface FastEthernet 0/1
```

스위치 쪽은 이 명령으로 3절의 표를 본다. 어느 MAC이 어느 포트에서 배워졌는지가 보이고, 케이블을 어디에 꽂았는지 모를 때 이 표에서 그 기기의 MAC을 찾는 것이 가장 빠르다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 스위치와 라우터 | 겉봉만 본다 / 뜯어서 새로 싼다 | 읽는 깊이 |
| 이 PC의 길 | 11홉, 왕복 32ms | 7홉에서 바다를 건넌다 |
| 통신사 안의 주소 | 100.64.0.0/10 | 밖에서 닿을 필요 없는 링크에 공인 주소를 안 쓴다 |
| 스위치의 일 | 배우고, 찾고, 그 포트로 | 게이트웨이의 MAC은 표에서 지워질 틈이 없다 |
| 스위치와 TTL | 안 줄인다 | 홉으로 세지 않는다 |
| 라우터의 일 | 벗기고, 찾고, 줄이고, 다시 싼다 | 프레임은 링크 하나의 것 |
| 체크섬 | 라우터마다 다시 | TTL이 바뀌었다 |
| 답의 TTL 54 | 64에서 10을 뺐다 | 돌아오는 길의 라우터 열 개 |
| 무응답 홉 | ICMP를 안 보낼 뿐 | TTL이 그 증거다 |
| 바뀌는 것 둘 | MAC은 홉마다, IP는 NAT에서만 | 4층과 HTTP는 그대로 |
| NAT 횟수 | 이 PC 0, 집 1, CGNAT 2, WSL 1 | 경계가 몇 개인가 |
| ip_forward | 호스트를 라우터로 | 이 PC는 꺼져 있다 |

{{< callout type="info" >}}
**용어 정리**
- **MAC 주소 표**: 스위치가 출발지 MAC을 엿보아 만든 포트 대응표
- **라우팅 표**: 목적지 망마다 다음 홉을 적은 표. 최장 일치로 찾는다
- **홉**: 라우터 하나를 지나는 것. TTL이 1 준다
- **다음 홉**: 이 링크에서 패킷을 건넬 라우터. 새 프레임의 목적지 MAC
- **NAT / PAT**: 경계에서 사설 주소를 공인 주소로, 포트까지 바꾸는 것
- **CGNAT**: 통신사가 한 번 더 하는 NAT. 100.64.0.0/10
- **경로 추적**: TTL을 1부터 올려 홉마다 누가 답하는지 적는 것
{{< /callout >}}
