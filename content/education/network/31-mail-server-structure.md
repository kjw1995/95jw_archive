[28. 응용 계층의 역할](../28-application-layer-role)에서 메일이 보내기와 받기에 다른 규칙을 쓰는 이유는 방향이 다르기 때문이고, 25번과 587번이 갈린 이유는 스팸이라고 했다. [05](../05-office-lan-configuration)장은 회사의 25번은 세상에 열려 있어야 하지만 POP3와 IMAP은 안에서만 열면 된다고 했고, [30](../30-dns-server-structure)장은 example.com의 MX가 점 하나뿐이고 TXT에 `v=spf1 -all`이 적힌 뜻을 여기로 미뤘다. 원리는 셋이다. 첫째, **메일은 밀어 넣기와 꺼내 가기가 다른 규칙이다.** 받는 사람의 PC는 늘 켜져 있지 않으므로 늘 켜져 있는 우체통(서버)이 필요하고, 보내는 쪽은 그 우체통에 밀어 넣으며(SMTP) 받는 쪽은 자기 우체통에서 꺼내 간다(POP3, IMAP). 둘째, **SMTP는 1982년의 텍스트 대화이고, 그 위에 40년의 확장이 얹혔다.** 이 PC에서 구글의 메일 서버에 인사를 건네 받은 목록의 줄 하나하나가 원래 없던 것이고, 7비트 규칙 때문에 첨부 파일을 글자로 바꾸는 MIME이 생겼다. 셋째, **메일의 문제는 보낸 사람을 믿을 수 없다는 것이고, 그 답은 DNS에 적혀 있다.** 봉투의 주소는 아무나 쓸 수 있으므로 SPF, DKIM, DMARC라는 세 레코드로 도메인의 주인이 "우리 메일은 이런 것"을 공표한다. 이 장의 실측은 구글 메일 서버와 나눈 SMTP, IMAP, POP3의 인사, 지메일의 MX 다섯 줄, 구글 도메인의 세 인증 레코드다.

## 1. 이메일 시스템 개요

| 규칙 | 하는 일 | 기본 포트 | 보안 포트 | 왜 |
|:-----|:--------|:----------|:----------|:---|
| SMTP | 보내고, 서버끼리 넘긴다 | 25, 587 | 465 | 밀어 넣기 |
| POP3 | 내려받는다 | 110 | 995 | 꺼내 가기. 한 기기에서 |
| IMAP | 서버에 둔 채 본다 | 143 | 993 | 꺼내 가기. 기기 여럿에서 |

```
[발신 클라이언트]
      │ SMTP (587)
      ▼
[발신 메일 서버]
      │ DNS MX 조회
      │ SMTP (25)
      ▼
[수신 메일 서버]
      │ 메일박스 저장
      ▲
      │ POP3/IMAP
[수신 클라이언트]
```

1. 보내는 사람의 프로그램이 자기 메일 서버에 SMTP로 메시지를 제출한다.
2. 그 서버가 받는 사람 도메인의 MX 레코드를 DNS에서 찾아 그 서버로 SMTP로 넘긴다.
3. 받는 쪽 서버가 메일박스에 넣어 둔다.
4. 받는 사람이 POP3나 IMAP으로 자기 메일박스에서 꺼내 간다.

웹과 다른 점은 상대가 **지금 없어도** 된다는 것이다. [29](../29-web-server-structure)장의 웹은 서버가 있어야 답이 오지만, 메일은 받는 사람의 PC가 꺼져 있어도 도착해야 한다. 그래서 양쪽에 늘 켜져 있는 서버를 두고, 보내는 쪽은 상대의 서버까지만 책임진다. 밀어 넣는 규칙과 꺼내 가는 규칙이 다른 것은 두 일이 방향도 상대도 다르기 때문이고, 05장에서 본 대로 밀어 넣는 문(25)은 세상에 열려 있어야 하지만 꺼내 가는 문(110, 143)은 우리 직원만 쓰니 안에서만 열면 된다.

| gmail.com의 MX | 우선순위 | 뜻 |
|:---------------|:---------|:---|
| gmail-smtp-in.l.google.com | 5 | 먼저 여기로 |
| alt1.gmail-smtp-in.l.google.com | 10 | 안 되면 여기로 |
| alt2, alt3, alt4 | 20, 30, 40 | 차례로 |

2단계의 MX 조회를 이 PC에서 지메일에 대해 해 보면 서버 다섯이 우선순위와 함께 온다. 숫자가 작은 쪽부터 시도하고 안 되면 다음으로 가므로, 서버 하나가 죽어도 메일은 도착한다. 30장에서 본 example.com의 MX가 점 하나뿐이었던 것은 "이 도메인으로는 메일을 보내지 말라"는 약속된 표기이고, 보내는 서버는 그 답을 보고 즉시 반송한다.

## 2. SMTP

| 포트 | 누가 누구에게 | 왜 따로인가 |
|:-----|:-------------|:-----------|
| 25 | 서버가 서버에게 | 원래의 문. 스팸 봇도 이 문을 쓰므로 가정용 회선에서 막는 통신사가 많다 |
| 587 | 사용자가 자기 서버에게 | 인증을 요구하는 제출 전용 문. 25가 막혀도 열려 있다 |
| 465 | 위와 같다. 처음부터 TLS | 6절. 자물쇠를 먼저 채우는 문 |

[28](../28-application-layer-role)장에서 본 대로 이 PC의 사무실 망에서는 구글의 25번과 587번이 둘 다 열려 있고, 이 장에서는 그 두 문에 직접 인사를 건넸다.

```
클라이언트           SMTP 서버
    │ TCP 연결          │
    ├──────────────────▶│
    │ 220 Ready         │
    │◀──────────────────┤
    │ EHLO client.com   │
    ├──────────────────▶│
    │ 250-...           │
    │◀──────────────────┤
    │ MAIL FROM:<a@x>   │
    ├──────────────────▶│
    │ 250 OK            │
    │◀──────────────────┤
    │ RCPT TO:<b@y>     │
    ├──────────────────▶│
    │ 250 OK            │
    │◀──────────────────┤
    │ DATA              │
    ├──────────────────▶│
    │ 354 End with "."  │
    │◀──────────────────┤
    │ (헤더+본문)       │
    │ .                 │
    ├──────────────────▶│
    │ 250 Queued        │
    │◀──────────────────┤
    │ QUIT              │
    ├──────────────────▶│
    │ 221 Bye           │
    │◀──────────────────┤
```

| 명령 | 뜻 | 왜 이 순서인가 |
|:-----|:---|:--------------|
| HELO, EHLO | 나는 누구다. E는 확장 목록을 달라는 뜻 | 서버가 무엇을 지원하는지 먼저 알아야 한다 |
| MAIL FROM | 봉투의 보낸 이 | 반송할 곳. 받는 이보다 먼저 |
| RCPT TO | 봉투의 받는 이. 여러 번 | 받는 이마다 서버가 받을지 말지 따로 답한다 |
| DATA | 이제 내용을 보낸다 | 봉투가 끝나야 내용이다. 점 하나뿐인 줄이 끝 |
| QUIT | 끝 | 서버가 221로 닫는다 |

| 응답 | 뜻 | 왜 |
|:-----|:---|:---|
| 2xx | 됐다 (220, 250) | |
| 3xx | 더 보내라 (354) | DATA 뒤에 내용을 기다린다 |
| 4xx | 지금은 안 된다. 나중에 다시 | 보내는 서버가 큐에 넣고 재시도한다. 7절 |
| 5xx | 영영 안 된다 | 반송한다 |

SMTP는 [28](../28-application-layer-role)장의 텍스트 규칙이고 1982년에 정해졌다. 명령과 응답이 HTTP처럼 사람이 읽는 글자라 손으로 쳐 볼 수 있다. 눈여겨볼 것은 **봉투와 내용이 따로**라는 점이다. MAIL FROM과 RCPT TO는 봉투이고, DATA 뒤에 오는 From과 To 헤더는 내용의 일부다. 우편 봉투의 주소와 편지지에 적은 이름이 다를 수 있듯 둘은 서로 검증되지 않으며, 셋째 원리의 문제가 여기서 시작된다.

```
S: 220 mx.google.com ESMTP ... - gsmtp
C: EHLO example.com
S: 250-mx.google.com at your service
S: 250-SIZE 157286400
S: 250-8BITMIME
S: 250-STARTTLS
S: 250-ENHANCEDSTATUSCODES
S: 250-PIPELINING
S: 250-CHUNKING
S: 250 SMTPUTF8
C: QUIT
S: 221 2.0.0 closing connection
```

이 PC에서 지메일의 수신 서버 25번 포트에 인사를 건네 받은 것이다. EHLO에 대한 답의 줄 하나하나가 둘째 원리다.

| 확장 | 뜻 | 원래 없던 이유 |
|:-----|:---|:--------------|
| SIZE 157286400 | 150MB까지 받는다 | 1982년의 메일은 몇 KB였다 |
| 8BITMIME | 8비트 본문도 받는다 | 원래는 7비트 ASCII만. 5절 |
| STARTTLS | 이 연결을 자물쇠로 바꿀 수 있다 | 원래는 평문뿐. 6절 |
| ENHANCEDSTATUSCODES | 2.0.0 같은 세 자리 상태 | 세 자리 숫자로는 이유가 부족했다 |
| PIPELINING | 답을 기다리지 않고 명령을 연달아 | 명령마다 왕복을 기다리면 느리다. 29장의 교훈 |
| CHUNKING | 점 하나로 끝내는 대신 크기를 미리 알려 보낸다 | 본문에 점만 있는 줄이 있으면 곤란했다 |
| SMTPUTF8 | 한글 주소도 된다 | 원래 주소는 영문뿐 |

587번의 smtp.gmail.com에 같은 인사를 하면 목록은 거의 같고 SIZE만 35,882,577로 다르다. 5절에서 이 숫자의 뜻을 본다. 두 목록에 인증(AUTH)이 없는 것도 눈여겨볼 점인데, 6절에서 본다.

## 3. POP3

```
클라이언트           POP3 서버
    │ TCP 연결 (110)    │
    ├──────────────────▶│
    │ +OK Ready         │
    │◀──────────────────┤
    │ USER alice        │
    ├──────────────────▶│
    │ +OK               │
    │◀──────────────────┤
    │ PASS ****         │
    ├──────────────────▶│
    │ +OK Logged in     │
    │◀──────────────────┤
    │ STAT              │
    ├──────────────────▶│
    │ +OK 3 12345       │
    │◀──────────────────┤
    │ RETR 1            │
    ├──────────────────▶│
    │ (메일 내용)       │
    │◀──────────────────┤
    │ DELE 1            │
    ├──────────────────▶│
    │ QUIT              │
    ├──────────────────▶│
```

POP3는 우체통을 비우는 규칙이다. 로그인하고, 몇 통이 있는지 묻고(STAT), 한 통씩 내려받고(RETR), 지우라고 표시하고(DELE), 나간다. 기본 동작이 "내려받고 서버에서 지운다"인 것은 1980년대의 서버 디스크가 작고 사용자의 기기는 하나였기 때문이다. 이 PC에서 지메일의 995번에 자물쇠를 채우고 붙으면 `+OK Gpop ready`가 오고 QUIT에 `+OK Bye`로 답한다. 성공은 `+OK`, 실패는 `-ERR`뿐인 단순한 규칙이다.

| 상태 | 뜻 | 왜 나뉘나 |
|:-----|:---|:----------|
| AUTHORIZATION | 접속 직후. USER와 PASS | 누군지 알기 전에는 아무것도 못 한다 |
| TRANSACTION | 로그인 뒤. LIST, RETR, DELE | 지우라는 표시만 한다 |
| UPDATE | QUIT 순간. 표시된 것을 실제로 지운다 | 도중에 끊기면 아무것도 안 지운다 |

DELE가 바로 지우지 않고 QUIT에서 지우는 이유가 셋째 상태다. 내려받는 도중 연결이 끊기면 표시는 전부 취소되어 메일이 남는다. 반쯤 받다 끊겼는데 서버에서 지워져 버리는 일을 막는 것이고, 데이터베이스의 트랜잭션과 같은 발상이다.

## 4. IMAP vs POP3

| 특성 | POP3 | IMAP | 왜 |
|:-----|:-----|:-----|:---|
| 메일이 있는 곳 | 내 기기 | 서버 | 기기가 여럿이면 서버에 있어야 한다 |
| 기기 여럿 | 각자 따로 받는다 | 읽음, 폴더, 삭제가 같이 보인다 | 상태가 서버에 있다 |
| 폴더 | 없다 | 있다 | 서버가 정리해 둔다 |
| 일부만 받기 | 안 된다 | 머리만, 첨부 빼고 | 폰에서 20MB 첨부를 안 받아도 된다 |
| 서버 디스크 | 조금 | 많이 | 전부 서버에 남는다 |
| 포트 | 110, 995 | 143, 993 | |

{{< callout type="info" >}}
지금은 폰, 노트북, PC를 오가며 같은 편지함을 보므로 IMAP이 기본이다. POP3는 메일을 한 기기에 몽땅 내려받아 보관하거나 서버 용량이 작을 때 남아 있다. 지메일의 993번에 붙으면 `* OK Gimap ready`가 오는데, `+OK` 대신 `* OK`인 것은 IMAP이 POP3와 다른 규칙이기 때문이다. 명령마다 꼬리표(a, b, ...)를 붙여 여러 명령을 동시에 보내고 답을 짝지을 수 있고, 서버가 묻지 않은 소식(새 메일 도착)을 `*`로 시작하는 줄로 먼저 알린다. 폴더와 동기화가 필요해지자 규칙 자체가 달라진 것이다.
{{< /callout >}}

## 5. 메일 헤더와 MIME

```
┌───────────────────────────┐
│ From: a@example.com       │
│ To: b@example.com         │
│ Subject: 제목             │
│ Date: ...                 │
│ Content-Type: text/plain  │
├───────────────────────────┤
│ (빈 줄로 헤더/본문 구분)  │
├───────────────────────────┤
│ 메일 본문                 │
└───────────────────────────┘
```

| 헤더 | 뜻 | 왜 |
|:-----|:---|:---|
| From, To, Cc, Bcc | 보낸 이와 받는 이 | 내용의 주소. 2절의 봉투와 별개다 |
| Subject, Date | 제목과 시각 | |
| Message-ID | 세계에서 하나뿐인 이 메일의 번호 | 답장과 스레드를 잇는다 |
| Content-Type | 본문의 종류 | 글인지, HTML인지, 여러 부분인지 |
| Received | 거쳐 온 서버마다 한 줄씩 | 서버가 찍는 소인. 위조 추적의 단서 |

메일의 모양은 1982년의 규격(RFC 822, 지금은 5322)이 정했고 [29](../29-web-server-structure)장의 HTTP와 같다. 헤더, 빈 줄, 본문. HTTP가 이 모양을 메일에서 빌려 왔기 때문이다. Received 헤더는 사용자가 적는 것이 아니라 메일을 넘겨받은 서버마다 맨 위에 한 줄씩 덧붙이는 소인이고, 그래서 위에서 아래로 읽으면 마지막 서버부터 첫 서버까지 거꾸로 거슬러 간다. 보낸 이를 속인 메일도 이 소인은 못 지운다.

```
MIME-Version: 1.0
Content-Type: multipart/mixed;
  boundary="b123"

--b123
Content-Type: text/plain; charset=UTF-8

본문 텍스트

--b123
Content-Type: application/pdf;
  name="doc.pdf"
Content-Transfer-Encoding: base64

JVBERi0xLjQK...
--b123--
```

SMTP는 [02](../02-bit-and-byte)장의 7비트 ASCII 시절에 만들어져 본문도 7비트 글자만 안전하게 지나갔다. 한글도 그림도 PDF도 그 안에 없었으므로, 그것들을 **글자로 바꿔** 싣는 규칙이 MIME이다. 경계 문자열로 본문을 여러 부분으로 나누고, 부분마다 종류를 적고, 이진 데이터는 base64로 바꾼다. base64는 바이트 셋을 글자 넷으로 적는다. 이 PC에서 "안녕"을 UTF-8로 적으면 6바이트이고 base64로는 `7JWI64WV`, 8글자다. 3분의 4배로 커지는 것이 이 방식의 값이고, 2절의 숫자가 여기서 풀린다. 지메일이 587번에서 받는 한도 35,882,577바이트는 첨부 한도 25MB에 4/3을 곱하고 헤더를 더한 값이다. 사용자가 보는 25MB와 서버가 보는 35MB의 차이가 base64다. 지금은 서버들이 8BITMIME으로 8비트 본문을 받지만, 이진 파일이 어느 서버를 거칠지 모르고 줄 길이 제한도 있어 첨부는 여전히 base64로 간다.

## 6. 메일 보안

| 방식 | 포트 | 어떻게 | 왜 둘인가 |
|:-----|:-----|:-------|:----------|
| STARTTLS | 25, 587, 143, 110 | 평문으로 인사한 뒤 자물쇠를 켠다 | 있던 포트를 그대로 쓴다. 서버끼리는 이것뿐 |
| SMTPS, IMAPS, POP3S | 465, 993, 995 | 처음부터 자물쇠 | 26장. TLS 판에 새 번호를 받던 시절의 방식 |

2절의 EHLO 목록에 STARTTLS는 있고 AUTH는 없었다. 순서 때문이다. 비밀번호를 평문 연결에서 보낼 수 없으므로 서버는 STARTTLS로 자물쇠를 켠 **뒤에야** AUTH를 목록에 올린다. 사용자의 제출 문(587)은 그렇게 인증을 거친 뒤에만 메일을 받고, 서버끼리의 문(25)은 인증이 없는 대신 아래의 레코드로 상대를 검증한다. 3절과 4절에서 본 995와 993은 자물쇠부터 채우고 인사한 경우다.

| 장치 | 무엇을 | 어디에 적나 | google.com에서 이 PC가 읽은 것 |
|:-----|:-------|:-----------|:------------------------------|
| SPF | 이 도메인의 메일을 보내도 되는 서버 목록 | TXT | `v=spf1 include:_spf.google.com ~all` |
| DKIM | 메일에 서명. 공개 키를 공개 | 선택자._domainkey의 TXT | `v=DKIM1; k=rsa; p=...` |
| DMARC | 둘이 안 맞으면 어떻게 할지 | _dmarc의 TXT | `v=DMARC1; p=reject; rua=...` |
| PTR | 보내는 서버 주소의 이름 | 역방향 DNS | 지메일 MX의 주소 → 1e100.net |

2절에서 본 대로 봉투의 보낸 이는 아무나 쓸 수 있다. [13](../13-mac-address-structure)장의 MAC 주소처럼 식별이지 인증이 아니다. 그래서 받는 서버는 보낸 이의 **도메인 주인에게 DNS로 묻는다.** SPF는 "우리 도메인의 메일은 이 서버들에서만 나간다"는 목록이고, 구글은 자기 서버 목록을 include로 가리키며 그 밖은 의심하라(`~all`)고 적었다. 30장의 example.com이 `-all`만 적은 것은 "우리 이름으로 나가는 메일은 없으니 전부 가짜"라는 뜻이다. DKIM은 보내는 서버가 메일에 비밀 키로 서명하고 공개 키를 DNS에 두어, 받는 서버가 서명을 검증하게 한다. 지메일은 그 키를 `20230601._domainkey.gmail.com`에 두고 있다. DMARC는 둘 중 하나라도 맞아야 하며 안 맞으면 어떻게 하라는 정책이고, 구글의 정책은 `p=reject`, 곧 버리라는 것이다. PTR은 보내는 서버의 주소에 이름이 붙어 있는지를 본다. 지메일의 MX 주소를 거꾸로 물으면 1e100.net으로 끝나는 이름이 온다. 이름 없는 주소에서 오는 메일은 대개 봇이다.

{{< callout type="warning" >}}
세 레코드가 없으면 정상 메일도 스팸함에 들어가거나 거절된다. 큰 메일 서비스들은 2024년부터 대량 발송자에게 SPF, DKIM, DMARC를 모두 요구한다. 회사 도메인을 만들면 웹 서버보다 이 세 줄을 먼저 적어야 하고, 메일을 보내지 않는 도메인이라도 example.com처럼 `v=spf1 -all`과 거부 정책을 적어 두어야 남이 그 이름으로 보내는 것을 막는다. 30장의 TXT 레코드가 자유 텍스트인 덕에 세 장치가 레코드 타입을 새로 만들지 않고 들어갔다.
{{< /callout >}}

## 7. 실무 도구

```bash
telnet smtp.example.com 25               # 평문 SMTP
openssl s_client -connect smtp.example.com:587 \
  -starttls smtp -crlf                    # STARTTLS
openssl s_client -connect pop.example.com:995 -crlf
openssl s_client -connect imap.example.com:993 -crlf
```

2절부터 4절까지의 실측이 이 도구들이 하는 일이다. 붙어서 220이나 +OK나 * OK가 오면 서버가 살아 있는 것이고, EHLO의 목록에 STARTTLS와 SIZE가 있으면 무엇이 되는지가 보인다. `-starttls smtp`는 평문으로 인사한 뒤 자물쇠를 켜 주는 옵션이다.

```bash
nslookup -type=MX gmail.com
dig gmail.com MX +short
Resolve-DnsName gmail.com -Type MX        # Windows
Resolve-DnsName _dmarc.google.com -Type TXT
```

메일이 안 갈 때 첫 확인은 MX다. 상대 도메인에 MX가 없거나 점 하나면 애초에 받지 않는 도메인이고, 내 도메인의 SPF와 DMARC는 위처럼 TXT로 읽어 확인한다.

```bash
mailq                       # 큐에 쌓인 메일
postqueue -f                # 지금 다시 보내기
postsuper -d ALL            # 큐 비우기
tail -f /var/log/mail.log
```

보내는 서버에는 큐가 있다. 2절의 4xx, 곧 "지금은 안 된다"를 받으면 메일을 버리지 않고 큐에 두었다가 몇 분, 몇 시간 간격으로 다시 시도하며, 보통 며칠을 버틴 뒤에야 포기하고 반송한다. 상대 서버가 잠깐 죽어도 메일이 "언젠가는" 가는 이유이고, 반대로 큐가 쌓이는 것은 상대가 우리를 거절하고 있다는 첫 신호다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 두 방향 | 밀어 넣기(SMTP)와 꺼내 가기(POP3, IMAP) | 받는 사람의 PC는 늘 켜져 있지 않다 |
| MX | 우선순위가 붙은 서버 목록 | 하나가 죽어도 간다. 지메일은 다섯 |
| 널 MX | 점 하나 | 받지 않는 도메인. 즉시 반송 |
| 25, 587, 465 | 서버 사이, 사용자 제출, 처음부터 TLS | 스팸이 25를 막았고 587이 생겼다 |
| 봉투와 내용 | MAIL FROM과 From은 다르다 | 서로 검증되지 않는다. 위조의 뿌리 |
| EHLO 목록 | SIZE, 8BITMIME, STARTTLS, PIPELINING ... | 1982년 규칙 위의 40년 |
| POP3의 UPDATE | 지우기는 QUIT에서 | 도중에 끊기면 남긴다 |
| IMAP | 서버에 두고 동기화 | 기기가 여럿이다 |
| 헤더와 본문 | 빈 줄 하나 | HTTP가 메일에서 빌려 간 모양 |
| Received | 서버마다 찍는 소인 | 위조해도 소인은 남는다 |
| base64 | 3바이트를 4글자로 | 7비트 규칙. 25MB 첨부가 35MB 한도 |
| STARTTLS | 평문으로 인사한 뒤 자물쇠 | AUTH는 자물쇠 뒤에만 나온다 |
| SPF, DKIM, DMARC | 목록, 서명, 정책 | 보낸 이는 식별이지 인증이 아니다 |
| 큐 | 4xx면 며칠을 다시 시도 | 메일은 언젠가는 간다 |

{{< callout type="info" >}}
**용어 정리**
- **SMTP**: 메일을 서버에 밀어 넣고 서버끼리 넘기는 규칙. 25, 587
- **POP3 / IMAP**: 우체통을 비우는 규칙 / 우체통을 서버에 둔 채 보는 규칙
- **MX 레코드**: 이 도메인의 메일을 받을 서버와 우선순위. 널 MX는 받지 않는다는 뜻
- **EHLO**: 확장 목록을 달라는 인사. 서버가 지원하는 것을 줄마다 답한다
- **봉투 / 헤더**: MAIL FROM, RCPT TO / From, To. 서로 검증되지 않는다
- **MIME / base64**: 글자가 아닌 것을 글자로 싣는 규칙 / 3바이트를 4글자로 적는 방식
- **STARTTLS**: 평문 연결을 같은 포트에서 TLS로 바꾸는 명령
- **SPF / DKIM / DMARC**: 보내는 서버 목록 / 서명과 공개 키 / 둘이 틀렸을 때의 정책. 전부 DNS의 TXT
- **큐**: 4xx를 받은 메일을 두었다가 다시 보내는 곳
{{< /callout >}}
