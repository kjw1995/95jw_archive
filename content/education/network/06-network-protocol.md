[01. 네트워크의 구조](../01-network-basics)의 마지막 원리가 "규칙이 있어야 대화가 된다"였고, [02. 비트와 바이트](../02-bit-and-byte)는 같은 비트열도 규칙이 있어야 뜻이 된다고 했다. 이 장은 그 규칙, 프로토콜 자체를 본다. 원리는 셋이다. 첫째, **프로토콜은 비트열에 뜻을 주는 약속이다.** 어떤 순서로 무엇을 적을지(구문), 그 값이 무슨 뜻인지(의미), 언제 보내고 언제 기다릴지(타이밍)를 정해 두면 처음 보는 기계와도 대화할 수 있다. 둘째, **규칙은 공개 문서여야 한다.** 누구나 읽고 구현할 수 있는 RFC 문화가 인터넷을 하나로 만들었고, 회사 소유의 규칙들은 그래서 졌다. 셋째, **한 규칙이 모든 문제를 풀지 않는다.** 계층마다 규칙이 따로 있고, 각 헤더의 번호 하나가 "이 안의 내용은 다음 층의 누구에게"를 가리키며 이어진다. 포트 번호와 프로토콜 번호 표가 존재하는 이유가 그것이다. 이 장의 예시는 필자의 PC에서 `curl`과 `nslookup`으로 실제로 주고받은 것이다.

## 1. 프로토콜: 비트열에 뜻을 주는 약속

| 요소 | 정하는 것 | 예 |
|:-----|:----------|:---|
| 구문 (syntax) | 어떤 순서로 몇 바이트씩 적는가 | 헤더의 필드 순서, 각 필드의 길이 |
| 의미 (semantics) | 그 값이 무슨 뜻인가 | `200`은 성공, `SYN` 비트는 연결 요청 |
| 타이밍 (timing) | 언제 보내고 얼마나 기다리는가 | 응답이 없으면 몇 초 뒤 다시 보낸다 |

2장에서 `01000001`이 규칙에 따라 65도 되고 `A`도 된다고 했다. 네트워크로 받은 비트열도 마찬가지다. 앞의 6바이트가 주소인지 길이인지, 그다음 2바이트가 무엇인지는 비트열 자체에 적혀 있지 않다. 보내는 쪽과 받는 쪽이 **미리 같은 표를 갖고 있어야** 하고, 그 표가 프로토콜이다. 구문만으로는 부족하다. 값이 무슨 뜻인지(의미), 그리고 상대가 답하지 않을 때 얼마나 기다렸다 다시 보낼지(타이밍)까지 정해야 대화가 끊기지 않는다.

```
1. 전화 걸기       (연결 요청)
2. "여보세요?"     (연결 수락)
3. 자기 소개       (신원 확인)
4. 대화            (데이터 전송)
5. "끊을게요"      (연결 종료)
```

전화 통화가 좋은 비유다. 상대가 받으면 "여보세요"라고 하고, 끊을 때는 끊는다고 말하며, 응답이 없으면 잠시 기다렸다 다시 부른다. 아무도 이것을 규칙이라 부르지 않지만 이 규칙이 없으면 통화가 되지 않는다. 뒤의 TCP가 정확히 이 순서로 연결을 맺고 끊는다.

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.21.0
Accept: */*

HTTP/1.1 200 OK
Content-Type: text/html
Transfer-Encoding: chunked
Connection: keep-alive
Server: cloudflare
```

실제 프로토콜은 이렇게 생겼다. 필자의 PC에서 `curl -v http://example.com`으로 보낸 요청과 받은 응답의 앞부분이다. 첫 줄에 "무엇을, 어떤 버전으로"(구문), `200 OK`는 성공(의미), 빈 줄 하나가 헤더의 끝(구문)이다. 서버는 이 글자들을 보고 무엇을 돌려줄지 정했고, 내 PC는 `200`을 보고 성공으로 처리했다. 두 기계는 서로를 모르고, 만든 회사도 다르지만, 이 형식을 둘 다 알고 있었다.

## 2. 왜 필요한가

규칙이 없으면 어떻게 되는지를 거꾸로 생각하면 프로토콜이 하는 일이 보인다.

| 규칙이 정하는 것 | 없으면 |
|:-----------------|:-------|
| 호환성 | 제조사가 다르면 통신이 안 된다. 1980년대에 실제로 그랬다 |
| 신뢰성 | 패킷이 깨지거나 사라져도 아무도 모른다 |
| 순서 | 1장에서 본 대로 순서가 뒤바뀐 패킷을 되돌릴 수 없다 |
| 오류 처리 | 문제가 생겼을 때 다시 보낼지, 포기할지, 누구에게 알릴지가 없다 |
| 흐름 제어 | 빠른 쪽이 느린 쪽을 넘치게 해 데이터가 버려진다 |

{{< callout type="info" >}}
프로토콜이 없다면 수신자는 받은 비트열이 어디서부터 어디까지가 무엇인지 알 길이 없다. 프로토콜은 **공통의 해석 규칙**이고, 그 규칙에는 형식만이 아니라 "잘못됐을 때 무엇을 할 것인가"까지 들어 있다.
{{< /callout >}}

## 3. 누가 정하나: 표준화 기관과 RFC

| 기관 | 정식 명칭 | 맡은 것 |
|:-----|:----------|:--------|
| IETF | Internet Engineering Task Force | 인터넷 프로토콜. IP, TCP, HTTP, DNS를 RFC로 |
| IEEE | Institute of Electrical and Electronics Engineers | 이더넷(802.3), Wi-Fi(802.11) |
| ISO | International Organization for Standardization | OSI 모델 |
| ITU | International Telecommunication Union | 전화와 통신 회선의 국제 표준 |
| W3C | World Wide Web Consortium | HTML, CSS 같은 웹 표준 |

세계의 모든 기기가 같은 표를 가지려면 그 표를 관리하는 곳이 있어야 한다. 기관이 여럿인 것은 맡은 층이 다르기 때문이다. 케이블과 전파의 규칙은 전기 기술자들의 IEEE가, 인터넷의 규칙은 IETF가, 그 위의 웹은 W3C가 정한다.

| 문서 | 프로토콜 | 비고 |
|:-----|:---------|:-----|
| RFC 791 | IP | 1981년. 지금도 유효 |
| RFC 793 → RFC 9293 | TCP | 1981년 문서를 2022년에 정리해 다시 냈다 |
| RFC 768 | UDP | 1980년. 세 쪽짜리 |
| RFC 1035 | DNS | 1987년 |
| RFC 2616 → RFC 9110 | HTTP | 1999년의 HTTP/1.1을 2022년에 재정리 |
| RFC 5321 | SMTP | 2008년 |

IETF의 문서는 RFC(Request for Comments)라 부른다. "의견을 구함"이라는 겸손한 이름은 1969년 ARPANET 초기에 대학원생들이 "우리는 표준을 정할 권위가 없으니 의견을 구하는 메모로 하자"며 붙인 것이고, 그 문화가 그대로 남아 지금도 인터넷의 표준은 **누구나 읽을 수 있고, 돈이 들지 않고, 합의로** 정해진다. IETF의 표어가 "대략의 합의와 돌아가는 코드"다. 투표가 아니라 실제로 동작하는 구현이 있어야 표준이 된다.

이 공개성이 인터넷이 이긴 이유다. 1980년대에는 노벨의 IPX, 애플의 AppleTalk, IBM의 SNA처럼 회사가 소유한 규칙이 여럿 있었고 성능은 TCP/IP보다 나은 것도 있었다. 그러나 규칙이 한 회사의 것이면 다른 회사의 장비는 그 규칙을 쓰기 어렵고, [03. LAN과 WAN](../03-lan-and-wan)에서 본 대로 인터넷은 수만 개 망의 연합이라 누구의 것도 아닌 규칙만이 그 전부를 이을 수 있었다.

## 4. 계층별 대표 프로토콜

| 계층 | 프로토콜 | 푸는 문제 |
|:-----|:---------|:----------|
| 응용 | HTTP, HTTPS, DNS, SMTP, POP3, IMAP, FTP, SSH | 프로그램이 주고받는 내용의 형식 |
| 전송 | TCP, UDP | 같은 기계의 어느 프로그램에게, 신뢰를 줄 것인가 |
| 네트워크 | IP, ICMP, ARP | 다른 망의 어느 기계에게 |
| 데이터 링크 | 이더넷, Wi-Fi(802.11), PPP | 같은 망 안의 옆 기계에게 |
| 물리 | 전기·광·전파 신호 규격 | 비트를 신호로 |

한 줄이 아니라 다섯 줄인 이유는 1장에서 봤다. 문제가 다르면 규칙도 다르고, 한 층은 아래 층을 믿고 자기 문제만 푼다. 이 표가 [07. OSI 모델과 TCP/IP 모델](../07-osi-tcpip-model)의 뼈대다.

### TCP와 UDP

| 항목 | TCP | UDP |
|:-----|:----|:----|
| 연결 | 먼저 맺는다 | 없다 |
| 신뢰와 순서 | 보장. 잃으면 다시 보낸다 | 없다 |
| 비용 | 연결 수립, 확인 응답, 재전송 | 거의 없다 |
| 용도 | 웹, 메일, 파일 | 영상, 게임, DNS 질의 |

```
클라이언트            서버
   │── SYN ─────────▶│  1. 연결 요청
   │◀── SYN+ACK ─────│  2. 수락
   │── ACK ─────────▶│  3. 확인
   │═══ 데이터 ═════▶│
```

전송 계층에 프로토콜이 둘인 이유는 신뢰에 값이 있기 때문이다. TCP는 1절의 전화 통화처럼 연결을 맺고(3-way handshake), 받았다는 답을 주고받으며, 잃은 것을 다시 보낸다. 그만큼 느리고 무겁다. UDP는 그 전부를 생략하고 봉투만 붙여 보낸다. 영상 통화에서 0.1초 전의 조각을 다시 받는 것은 의미가 없으므로 UDP가 맞고, 파일은 한 바이트라도 빠지면 안 되므로 TCP가 맞다. 필자의 PC에서 `Test-NetConnection example.com -Port 443`을 실행하면 `True`가 돌아오는데, 그 순간 위의 세 패킷이 오간 것이다. 자세한 구조는 [24. TCP의 구조](../24-tcp-structure)와 [27. UDP의 구조](../27-udp-structure)에서 본다.

### IP, ICMP, ARP

| 프로토콜 | 하는 일 | 왜 따로 있나 |
|:---------|:--------|:------------|
| IP | 패킷을 목적지 주소로 보낸다 | 다른 망으로 가려면 세계 공통의 주소가 필요하다 |
| ICMP | 오류와 상태를 알린다. `ping`이 이것이다 | IP에는 "못 갔다"를 알릴 방법이 없어서 따로 만들었다 |
| ARP | IP 주소로 MAC 주소를 찾는다 | 같은 망 안에서는 결국 MAC 주소로 보내야 한다 |

IP는 주소와 배달만 정한 단순한 규칙이라, 배달에 실패했을 때 알려 줄 방법이 없다. 그것을 보완하려고 IP 위에 얹은 것이 ICMP이고, `ping`은 "거기 있나?"라는 ICMP 메시지를 보내고 답이 오는 시간을 잰다. 1장의 지연 실측이 이것이다. ARP는 두 주소 체계 사이의 번역이다. 패킷의 목적지는 IP 주소로 적히지만 같은 LAN 안에서 프레임을 받는 것은 [13. MAC 주소의 구조](../13-mac-address-structure)의 MAC 주소라서, 보내기 전에 "이 IP 주소를 가진 사람 누구?"라고 브로드캐스트로 묻는다.

## 5. 스택과 캡슐화: 봉투를 겹쳐 붙인다

```
응용     [        데이터        ]
전송     [TCP][     데이터      ]
네트워크 [IP][TCP][   데이터    ]
링크  [ETH][IP][TCP][데이터][FCS]
물리  0101 1101 ... (신호)
```

프로토콜들이 함께 일하는 방식은 봉투를 겹쳐 붙이는 것이다. 보내는 쪽은 위층에서 아래층으로 내려가며 층마다 자기 헤더를 앞에 붙이고(캡슐화), 받는 쪽은 아래층에서 위층으로 올라가며 하나씩 뜯는다(역캡슐화). 1장에서 패킷에 붙는 봉투가 한 겹이 아니라 계층마다 한 겹이라고 한 것이 이것이고, 각 헤더에 무엇이 들어 있는지는 [08. 캡슐화와 역캡슐화](../08-encapsulation-decapsulation)에서 본다.

```
1. DNS   이름 → 주소 (UDP 53)
2. TCP   3-way handshake (포트 80)
3. HTTP  GET / 요청을 데이터로
4. 캡슐화 TCP → IP → 이더넷
5. 신호  케이블로 전송
```

브라우저에 주소를 치면 이 순서로 프로토콜이 차례로 등장한다. 먼저 DNS가 이름을 주소로 바꾸고(필자의 PC에서 `example.com`은 `104.20.23.154`였다), TCP가 그 주소의 80번 포트와 연결을 맺고, 그 연결 위로 1절의 HTTP 요청이 데이터로 실려, TCP와 IP와 이더넷의 봉투에 차례로 담겨 케이블로 나간다. 다섯 규칙이 한 번의 클릭에 전부 쓰인다.

## 6. 번호로 다음 층의 상대를 가리킨다

```
이더넷 헤더  타입 0x0800 ─▶ IP에게
IP 헤더      프로토콜 6  ─▶ TCP에게
TCP 헤더     포트 80     ─▶ 웹 서버에게
```

봉투를 뜯는 쪽에는 문제가 하나 있다. 이더넷 헤더를 뜯은 뒤 안의 것을 IP에게 줄지 ARP에게 줄지, IP 헤더를 뜯은 뒤 TCP에게 줄지 UDP에게 줄지, TCP 헤더를 뜯은 뒤 웹 서버에게 줄지 메일 서버에게 줄지를 알아야 한다. 그래서 **모든 헤더에는 "안의 내용은 다음 층의 누구에게"를 가리키는 번호가 하나씩 있다.** 이더넷은 타입, IP는 프로토콜 번호, TCP와 UDP는 포트 번호다. 세 표가 존재하는 이유가 이것이고, 번호가 세계 공통이어야 하는 이유도 이것이다.

| 포트 | 프로토콜 | 포트 | 프로토콜 |
|-----:|:---------|-----:|:---------|
| 20, 21 | FTP | 110 | POP3 |
| 22 | SSH | 143 | IMAP |
| 25, 587 | SMTP | 443 | HTTPS |
| 53 | DNS | 3306 | MySQL |
| 80 | HTTP | 3389 | 원격 데스크톱 |

| IP 프로토콜 번호 | 프로토콜 | | 이더넷 타입 | 프로토콜 |
|-----------------:|:---------|:--|:------------|:---------|
| 1 | ICMP | | 0x0800 | IPv4 |
| 6 | TCP | | 0x0806 | ARP |
| 17 | UDP | | 0x86DD | IPv6 |
| 50 | ESP (IPsec) | | | |

포트 번호는 [04. 가정에서의 LAN 구성](../04-home-lan-configuration)의 NAT 표에서 이미 한 번 봤다. 공유기가 포트를 바꿔 기기를 구분한 것도, 회사의 방화벽이 "80과 443만 허용"이라고 적는 것도, 이 번호가 "어느 프로그램에게"를 뜻하기 때문이다. 필자의 PC에는 지금 이 순간에도 200개가 넘는 TCP 연결이 열려 있고, 그 각각이 (내 주소, 내 포트, 상대 주소, 상대 포트)의 조합으로 구별된다. 포트의 범위와 소켓은 [26. 포트 번호의 구조](../26-port-number-structure)에서 본다.

## 7. 분석 도구

| 도구 | 무엇을 보나 | 언제 |
|:-----|:-----------|:-----|
| Wireshark | 지나가는 패킷을 층마다 뜯어 보여 준다 | 이 장의 봉투 구조를 눈으로 확인할 때 |
| tcpdump | 같은 일을 명령줄에서 | 화면 없는 서버에서 |

```bash
ping example.com        # ICMP. 닿는가, 얼마나 걸리나
nslookup example.com    # DNS. 이름이 어느 주소로 풀리나
curl -v http://example.com   # HTTP. 요청과 응답을 글자 그대로
tracert example.com     # ICMP. 어느 라우터들을 거치나 (Linux는 traceroute)
netstat -an             # 지금 열린 연결과 포트
arp -a                  # IP 주소와 MAC 주소의 대응표
```

도구는 층마다 하나씩 있다. `ping`은 ICMP로 IP 층을, `nslookup`은 DNS를, `curl -v`는 HTTP를, `netstat`은 TCP의 연결 표를, `arp -a`는 IP와 MAC의 대응을 보여 준다. 무엇이 안 될 때 어느 층이 문제인지 좁혀 가는 순서가 대개 이 순서의 역순이다. 이름이 풀리는지, 연결이 되는지, 응답이 오는지를 차례로 본다. Wireshark를 한 번 열어 보면 이 장의 표들이 실제 패킷 안에 그 번호 그대로 들어 있는 것을 볼 수 있고, [08. 캡슐화와 역캡슐화](../08-encapsulation-decapsulation)의 마지막 절이 그 예다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 프로토콜 | 비트열에 뜻을 주는 약속 | 비트열 자체에는 경계도 뜻도 없다 |
| 3요소 | 구문, 의미, 타이밍 | 형식만으로는 응답이 없을 때 할 일이 없다 |
| 호환성 | 회사가 달라도 같은 표 | 세계 공통의 표가 있어야 인터넷이 하나다 |
| 표준화 기관 | IETF, IEEE, ISO, ITU, W3C | 층마다 맡는 곳이 다르다 |
| RFC | 공개, 무료, 합의 | 회사 소유의 규칙은 연합을 잇지 못했다 |
| 계층별 프로토콜 | 응용, 전송, 네트워크, 링크, 물리 | 문제가 다르면 규칙도 다르다 |
| TCP와 UDP | 신뢰의 값을 낼 것인가 | 파일은 TCP, 영상은 UDP |
| ICMP | IP의 오류 보고 | IP에는 "못 갔다"를 알릴 길이 없다 |
| ARP | IP 주소로 MAC 주소 찾기 | 같은 망 안의 배달은 MAC 주소로 한다 |
| 캡슐화 | 층마다 봉투 한 겹 | 각 층이 자기 헤더만 붙이고 뜯는다 |
| 번호 표 | 타입, 프로토콜 번호, 포트 | 뜯은 뒤 다음 층의 누구에게 줄지 |
| 분석 도구 | 층마다 하나씩 | 어느 층이 문제인지 좁혀 간다 |

{{< callout type="info" >}}
**용어 정리**
- **프로토콜 (Protocol)**: 서로 다른 시스템이 통신하기 위해 미리 합의한 규칙. 구문, 의미, 타이밍을 정한다
- **RFC (Request for Comments)**: IETF가 발행하는 인터넷 표준 문서. 누구나 읽을 수 있다
- **TCP**: 연결을 맺고 순서와 재전송으로 신뢰를 주는 전송 프로토콜 ([24. TCP의 구조](../24-tcp-structure))
- **UDP**: 연결 없이 봉투만 붙여 보내는 전송 프로토콜 ([27. UDP의 구조](../27-udp-structure))
- **ICMP**: IP의 오류와 상태를 알리는 프로토콜. `ping`과 `tracert`가 쓴다
- **ARP**: IP 주소에 대응하는 MAC 주소를 브로드캐스트로 묻는 프로토콜
- **프로토콜 스택 / 캡슐화**: 계층별 프로토콜의 묶음 / 층마다 헤더를 덧붙여 내려보내는 것 ([07](../07-osi-tcpip-model), [08](../08-encapsulation-decapsulation))
- **포트 번호 / 프로토콜 번호 / 이더넷 타입**: 각 헤더에서 "안의 내용을 다음 층의 누구에게 줄지"를 가리키는 번호
{{< /callout >}}
