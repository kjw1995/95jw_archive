[28. 응용 계층의 역할](../28-application-layer-role)에서 HTTP는 글자로 된 요청과 응답이고, 그 구조와 버전과 연결 재사용은 이 장에서 본다고 했다. [01](../01-network-basics)장은 지연 100ms인 회선에서 요청을 100번 하면 10초라며 HTTP가 연결을 재사용하려 애쓰는 이유를 예고했고, [05](../05-office-lan-configuration)장은 웹 서버가 요청을 받는 구조를, [14](../14-switch-structure)장은 L7 스위치가 왜 HTTP까지 읽어야 하는지를 여기로 미뤘다. 원리는 셋이다. 첫째, **웹은 세 가지 발명의 조합이다.** 문서의 주소(URL), 문서의 형식(HTML), 문서를 주고받는 대화(HTTP)이고, 셋이 따로이기 때문에 각자 따로 진화했다. 둘째, **웹 요청 한 번의 시간은 바이트 수가 아니라 왕복 횟수로 정해진다.** 이 PC에서 example.com 한 페이지를 받는 데 HTTP는 왕복 셋, HTTPS는 넷이 들었고, 연결 재사용과 캐시와 HTTP/2, HTTP/3의 역사는 전부 그 왕복을 줄이려는 역사다. 셋째, **서버는 요청을 읽고 파일을 주거나 프로그램을 돌린다.** 한 주소 뒤에 사이트 여럿이 있을 수 있어 Host 헤더가 필수가 되었고, 그것이 14장의 답이다. 이 장의 실측은 curl이 재어 준 요청 한 번의 단계별 시간, 연결 재사용, 조건부 요청, 잘못된 Host의 결과다.

## 1. 웹의 기본 구조

| 발명 | 답하는 것 | 아래 층의 무엇에 기대나 |
|:-----|:----------|:----------------------|
| URL | 어느 문서인가 | 30장의 DNS, 26장의 포트, 서버 안의 경로 |
| HTML | 문서를 어떻게 적나 | 문서 안에 다른 문서의 URL을 품는다 |
| HTTP | 문서를 어떻게 달라고 하나 | 23장의 TCP 위의 요청과 응답 |

```
[사용자]
   │ URL 입력
   ▼
[브라우저]
   │ DNS 조회 → IP
   │ HTTP 요청
   ▼
[웹 서버]
   │ 파일/동적 처리
   ▼
[브라우저]
   │ HTML 파싱, 렌더링
   ▼
[사용자 화면]
```

웹(WWW)은 링크로 이어진 문서들을 인터넷으로 나눠 보는 체계이고, 1990년에 한 사람이 세 가지를 함께 만들었다. 셋이 따로인 것이 중요하다. URL은 30년 동안 거의 그대로이고, HTML은 5판까지 바뀌었고, HTTP는 1.0에서 3까지 바뀌었지만 서로를 깨지 않았다. 각자 아래 층의 다른 것에 기대기 때문이다. 흐름의 각 단계에 시간이 얼마나 드는지를 이 PC에서 curl로 재면 이렇다.

| 단계 | HTTP | HTTPS | 왜 이만큼인가 |
|:-----|:-----|:------|:-------------|
| 이름 풀이 끝 | 12ms | 9ms | 캐시된 DNS. 첫 조회는 47ms였다 |
| TCP 연결 끝 | 45ms | 41ms | [24](../24-tcp-structure)장의 세 번 인사. 왕복 한 번 |
| TLS 끝 | | 84ms | 자물쇠를 맞추는 데 왕복 한 번 더 |
| 첫 바이트 도착 | 86ms | 124ms | 요청을 보내고 답이 오는 왕복 한 번 |
| 받은 크기 | 559바이트 | 559바이트 | 본문. 헤더는 299바이트 |

example.com까지의 왕복이 40ms 안팎이라 단계마다 40ms씩 쌓인다. 559바이트를 받는 데 86ms가 걸린 것은 회선이 느려서가 아니라 **왕복이 세 번** 있었기 때문이고, HTTPS는 네 번이라 124ms다. 이 장의 나머지는 이 숫자를 줄이는 이야기다.

## 2. 클라이언트-서버 모델

```
[웹 브라우저]        [웹 서버 :80]
     │  GET /index     │
     │ ───────────────▶│
     │                 │ 리소스 조회
     │  200 OK + HTML  │
     │ ◀─────────────── │
     │                 │
```

브라우저가 묻고 서버가 답한다. 28장에서 본 요청과 응답의 비대칭이고, 서버가 80번이나 443번에서 기다리는 이유는 [26](../26-port-number-structure)장에서 봤다.

| 구분 | 정적 콘텐츠 | 동적 콘텐츠 | 왜 나누나 |
|:-----|:-----------|:-----------|:----------|
| 예 | HTML, CSS, JS, 이미지 | 검색 결과, 대시보드 | |
| 처리 | 디스크의 파일을 그대로 | 프로그램이 그때 만든다 | 파일은 읽기만 하면 되고 프로그램은 돌려야 한다 |
| 속도 | 빠르고 캐시된다 | 상대적으로 느리다 | 누가 요청해도 같은 답이면 저장해 둘 수 있다 |
| 도구 | Nginx, Apache | PHP, Node.js, Spring | 앞단과 뒷단 |

{{< callout type="info" >}}
실제 서비스는 둘을 섞는다. 앞단의 웹 서버가 정적 파일을 직접 답하고 캐시하며, 동적 요청만 뒤의 애플리케이션 서버(WAS)로 넘긴다. 이렇게 나누는 이유는 정적 요청이 훨씬 많고 훨씬 싸기 때문이다. 이미지 하나를 주는 데 프로그램을 깨울 이유가 없다. 앞단 서버가 요청을 읽고 뒤로 넘기는 과정은 [34. 웹 서버에서의 데이터 처리](../34-web-server-data-processing)에서 본다.
{{< /callout >}}

한 서버, 한 주소 뒤에 사이트가 여럿인 것도 보통이다. 서버는 요청의 `Host` 헤더를 읽어 어느 사이트의 파일을 줄지 정한다. 이 PC에서 example.com의 서버에 엉뚱한 `Host: nonexistent.invalid`를 적어 보내면 서버가 `409 Conflict`로 거절한다. 주소는 맞게 찾아갔지만 그 주소에 그런 사이트는 없다는 답이다. 14장에서 L7 스위치가 왜 응용 계층까지 읽어야 하는지를 미뤘는데, 답이 이것이다. 같은 443번으로 온 요청이라도 Host와 경로에 따라 갈 곳이 다르므로, 여러 서버 앞에서 요청을 나눠 주는 장비는 TCP 헤더가 아니라 HTTP 헤더를 읽어야 한다.

## 3. HTML

```html
<!DOCTYPE html>
<html lang="ko">
<head>
  <meta charset="UTF-8">
  <title>예제</title>
</head>
<body>
  <h1>제목</h1>
  <p><a href="about.html">소개</a></p>
</body>
</html>
```

| 분류 | 태그 | 하는 일 |
|:-----|:-----|:--------|
| 구조 | html, head, body, header, footer, main, nav | 문서의 뼈대 |
| 텍스트 | h1~h6, p, strong, em, span | 글의 층위 |
| 링크와 매체 | a, img, video, audio | 다른 문서와 파일의 URL |
| 목록과 표 | ul, ol, li, table, tr, td, th | 나열 |
| 폼 | form, input, button, textarea | 사용자가 서버로 보내는 것 |

HTML은 태그로 문서의 구조를 적는 언어이고, 웹을 웹으로 만드는 것은 `a`와 `img` 같은 **다른 문서의 주소를 품는 태그**다. 문서가 문서를 가리키므로 거미줄이 되고, 브라우저는 HTML을 읽다가 이미지나 CSS의 URL을 만나면 그것마다 다시 요청을 보낸다. 페이지 하나에 파일이 수십 개면 요청도 수십 번이고, 1절에서 본 대로 요청마다 왕복이 들므로 페이지가 느린 첫 번째 이유는 크기가 아니라 **파일의 수**다. `<meta charset="UTF-8">`은 [02](../02-bit-and-byte)장의 인코딩을 문서가 스스로 알리는 줄이다.

## 4. URL

```text
https://example.com:443/path?id=1#top

┌ 스킴        https
├ 호스트      example.com
├ 포트        443
├ 경로        /path
├ 쿼리        id=1
└ 프래그먼트  top
```

| 부분 | 뜻 | 누가 쓰나 | 왜 |
|:-----|:---|:----------|:---|
| 스킴 | 어떤 규칙으로 | 브라우저 | 규칙이 기본 포트를 정한다. https면 443 |
| 호스트 | 어느 기계 | 30장의 DNS가 주소로 바꾼다 | 사람은 이름을 쓰고 IP는 주소를 쓴다 |
| 포트 | 어느 프로그램 | 26장 | 기본값이면 생략한다 |
| 경로 | 서버 안의 어디 | 서버 | 파일일 수도, 프로그램의 입력일 수도 있다 |
| 쿼리 | 어떤 조건으로 | 서버의 프로그램 | 동적 콘텐츠의 입력 |
| 프래그먼트 | 문서 안의 어디 | 브라우저만 | 서버로 보내지 않는다. 문서를 받은 뒤의 일이다 |

URL은 [자바 기초 16장](../../java/basics/16-networking)에서 본 대로 "어떤 규칙으로, 어느 기계의, 어느 프로그램에게, 무엇을"을 한 줄에 적은 것이다. 스킴이 포트를 정하고 호스트가 DNS를 부르며 경로부터는 서버의 몫이다. 프래그먼트만 서버에 가지 않는 것은 그것이 문서를 다 받은 뒤 브라우저가 화면을 어디로 옮길지의 문제이기 때문이다.

## 5. HTTP 프로토콜

```text
GET /index.html HTTP/1.1  ← 요청 라인
Host: www.example.com     ┐
User-Agent: Mozilla/5.0   │ 헤더
Accept: text/html         ┘
                          ← 빈 줄
(본문, POST 등에서 사용)  ← 본문
```

```text
HTTP/1.1 200 OK           ← 상태 라인
Content-Type: text/html   ┐
Content-Length: 1234      │ 헤더
Server: nginx/1.25        ┘
                          ← 빈 줄
<html>...</html>          ← 본문
```

요청은 "무엇을 어떻게" 한 줄과 헤더들과 빈 줄과 본문이고, 응답은 "결과" 한 줄과 헤더들과 빈 줄과 본문이다. 28장에서 본 대로 전부 글자이고, 빈 줄이 머리와 몸의 경계다. `Host` 헤더가 1.1에서 필수가 된 것은 2절에서 본 대로 한 주소에 사이트가 여럿이기 때문이다.

| 메서드 | 뜻 | 왜 따로 있나 |
|:-------|:---|:------------|
| GET | 달라 | 서버를 바꾸지 않는다. 그래서 캐시해도 된다 |
| POST | 보낸다, 만든다 | 서버를 바꾼다 |
| PUT, PATCH | 통째로 바꾼다, 일부만 바꾼다 | 바꾸는 범위가 다르다 |
| DELETE | 지운다 | |
| HEAD | 머리만 달라 | 본문 없이 크기와 날짜만 알고 싶을 때. 1절의 curl -I |
| OPTIONS | 무엇이 되나 | 브라우저가 다른 사이트에 요청하기 전에 묻는다 |

| 범위 | 뜻 | 예 | 이 PC에서 본 것 |
|:-----|:---|:---|:---------------|
| 1xx | 계속하라 | 100 | |
| 2xx | 됐다 | 200, 201 | 559바이트의 본문과 함께 200 |
| 3xx | 다른 곳으로, 또는 그대로 써라 | 301, 302, 304 | 304. 아래 |
| 4xx | 네 잘못 | 400, 401, 403, 404 | 엉뚱한 Host에 409 |
| 5xx | 내 잘못 | 500, 502, 503, 504 | |

304는 원리 둘째의 예다. 이 PC에서 example.com에 "9월 10일 21시 이후에 바뀌었으면 달라"는 조건(`If-Modified-Since`)을 붙여 다시 요청하면 서버는 본문 없이 `304 Not Modified`만 돌려준다. 바뀌지 않은 파일을 다시 보내는 대신 "네가 가진 것을 써라"고 하는 것이고, 왕복은 그대로지만 바이트가 사라진다. 메서드와 상태 코드와 헤더 하나하나의 뜻은 별도 시리즈 [HTTP 메서드](../http/03-http-methods), [상태 코드](../http/04-http-status-codes), [헤더](../http/05-http-headers)에서 본다.

## 6. HTTP 버전 변천사

| 버전 | 연결 | 처리 | 왜 바꿨나 |
|:-----|:-----|:-----|:----------|
| HTTP/1.0 | 요청마다 새 연결 | 하나씩 | 문서 하나를 주는 대화였다 |
| HTTP/1.1 | 연결을 재사용(Keep-Alive) | 하나씩 | 파일이 수십 개가 되자 인사 비용이 커졌다 |
| HTTP/2 | 연결 하나에 여러 요청을 섞는다 | 병렬 | 순서대로 기다리는 것이 병목이 됐다 |
| HTTP/3 | QUIC(UDP) | 병렬 | TCP의 순서 보장이 오히려 발목을 잡았다 |

이 표는 1절의 왕복을 줄여 온 역사다. 1.0은 파일마다 [24](../24-tcp-structure)장의 인사를 다시 했다. 3절에서 본 대로 페이지 하나가 파일 수십 개가 되자 1.1은 연결을 끊지 않고 다음 요청에 다시 쓰게 했고, 이 PC에서 curl로 같은 서버에 요청 둘을 보내면 두 번째가 "연결 0번"을 그대로 쓴다. 인사 한 번에 요청 여럿이다. [26](../26-port-number-structure)장에서 본 동적 포트 소진과 24장의 TIME_WAIT도 이것으로 덜어진다.

{{< callout type="info" >}}
1.1에도 남은 문제가 줄 서기(Head-of-Line Blocking)다. 연결 하나에서는 앞 요청의 답이 와야 뒤 요청의 답이 오므로, 큰 이미지 하나가 뒤의 작은 파일들을 막는다. 브라우저가 서버마다 연결을 여섯 개씩 열던 이유다. HTTP/2는 연결 하나 안에 스트림 여러 개를 두어 응답이 섞여 오게 했고, 헤더를 이진으로 압축했다. 그런데 TCP는 세그먼트 하나가 사라지면 [25](../25-sequence-ack-number)장에서 본 대로 그 뒤의 것을 전부 붙들고 재전송을 기다리므로, 스트림이 섞여 있어도 손실 하나가 모든 스트림을 세운다. 줄 서기가 응용에서 전송 계층으로 내려간 것이다. HTTP/3는 [23](../23-transport-layer-role)장의 QUIC 위에서 스트림마다 따로 재전송해 그것까지 없앴고, 한 번 만난 서버와는 인사 없이 첫 패킷에 요청을 싣는다. 왕복이 셋에서 하나로 준다.
{{< /callout >}}

어느 버전으로 말할지는 [28](../28-application-layer-role)장에서 본 TLS 협상 중에 정한다. 이 PC의 curl은 HTTP/1.1까지만 제안해 서버가 그것을 받았고, 브라우저는 HTTP/2와 3을 제안해 서버가 되는 것 중 가장 높은 것을 고른다.

## 7. 실무 도구

```bash
curl -v http://www.example.com          # 요청과 응답 전부
curl -I http://www.example.com          # 머리만
curl -L http://short.ly/abc             # 3xx를 따라간다
curl -X POST https://api.example.com \
     -H "Content-Type: application/json" \
     -d '{"name":"John"}'
curl -o NUL -s -w "%{time_connect} %{time_starttransfer}\n" \
     https://example.com                # 단계별 시간. 1절의 표
```

브라우저의 개발자 도구도 같은 것을 보여 준다. Network 탭은 요청마다 1절의 단계별 시간과 크기와 상태 코드를, Application 탭은 쿠키와 저장소를, Console 탭은 스크립트의 오류를 보여 준다. 페이지가 느릴 때 Network 탭의 요청 수와 그 앞의 빈 시간(대기)을 먼저 보는 이유가 이 장의 둘째 원리다.

```
192.168.1.10 - -
[07/Jan/2026:12:34:56 +0900]
"GET /index.html HTTP/1.1" 200 1234
"-" "Mozilla/5.0"
```

서버 쪽에서는 요청마다 한 줄이 남는다. 누가(주소), 언제, 무엇을(요청 라인), 결과(상태 코드), 얼마나(바이트), 어디서 왔고(참조), 무엇으로(브라우저) 왔는지다. 5절의 상태 코드가 여기 그대로 쌓이므로, 404와 500이 갑자기 늘면 로그의 이 열부터 센다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 웹의 세 발명 | URL, HTML, HTTP | 따로이기 때문에 따로 진화했다 |
| 요청 한 번의 시간 | 왕복 횟수 × 왕복 시간 | 이 PC: HTTP 셋 86ms, HTTPS 넷 124ms |
| 파일의 수 | 페이지가 느린 첫 이유 | 파일마다 요청, 요청마다 왕복 |
| 정적과 동적 | 파일 그대로, 프로그램이 만든다 | 정적은 싸고 캐시된다. 앞단과 뒷단 |
| Host 헤더 | 한 주소에 사이트 여럿 | 엉뚱한 Host에 409. L7 스위치가 읽는 이유 |
| URL | 규칙, 기계, 프로그램, 무엇 | 프래그먼트만 서버에 안 간다 |
| 메시지 | 한 줄, 헤더, 빈 줄, 본문 | 빈 줄이 경계 |
| GET과 캐시 | 서버를 안 바꾸는 요청 | 그래서 저장해도 된다 |
| 304 | 본문 없는 답 | 왕복은 남고 바이트가 사라진다 |
| Keep-Alive | 연결 0번을 다시 쓴다 | 인사 한 번에 요청 여럿 |
| 줄 서기 | 앞이 뒤를 막는다 | 1.1은 연결에서, 2는 TCP에서, 3은 없앴다 |
| 버전 협상 | TLS 중에 정한다 | 이 PC의 curl은 1.1까지 |
| 서버 로그 | 요청마다 한 줄 | 상태 코드의 열부터 센다 |

{{< callout type="info" >}}
**용어 정리**
- **WWW**: 링크로 이어진 문서를 인터넷으로 나눠 보는 체계. URL, HTML, HTTP의 조합
- **HTML**: 태그로 문서의 구조를 적는 언어. 다른 문서의 주소를 품는다
- **URL**: 어떤 규칙으로 어느 기계의 어느 프로그램에게 무엇을 달라는지 적은 주소
- **정적 / 동적 콘텐츠**: 파일 그대로 / 프로그램이 그때 만드는 것
- **WAS**: 동적 콘텐츠를 만드는 뒷단 서버. 앞단 웹 서버가 넘겨준다
- **Host 헤더**: 한 주소 뒤의 여러 사이트 중 어느 것인지. 1.1부터 필수
- **Keep-Alive**: 연결을 끊지 않고 다음 요청에 다시 쓰는 것
- **줄 서기 (HOL 블로킹)**: 앞의 응답이 뒤의 응답을 막는 현상
- **멀티플렉싱**: 연결 하나에 스트림 여럿을 섞어 보내는 HTTP/2의 방식
- **304**: 바뀌지 않았으니 가진 것을 쓰라는 답
