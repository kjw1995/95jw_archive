[28. 응용 계층의 역할](../28-application-layer-role)에서 DNS는 이름을 주소로 바꾸는 규칙이고 그 구조와 서버의 종류와 캐시는 이 장에서 본다고 했다. [04](../04-home-lan-configuration)장은 DHCP가 알려 주는 DNS 서버가 보통 통신사의 것이지만 8.8.8.8이나 1.1.1.1로 바꿔 쓸 수 있다고 했고, [05](../05-office-lan-configuration)장은 우리 도메인의 주소를 세상에 알리는 쪽의 DNS를, [08](../08-encapsulation-decapsulation)장은 모든 통신의 준비 단계인 이름 풀이를 여기로 미뤘다. 원리는 셋이다. 첫째, **DNS는 이름의 소유권을 점(.)마다 위임하는 분산 데이터베이스다.** 루트가 com을 맡기고, com이 example.com을 맡기고, example.com의 주인이 www를 정한다. 중앙 서버가 없는데도 세계가 같은 답을 얻는 이유다. 둘째, **질의는 두 종류다.** 클라이언트는 "답을 가져와 달라"고 하고, 그 부탁을 받은 리졸버는 "다음에 물을 곳을 알려 달라"며 위임의 사슬을 따라간다. 셋째, **캐시와 TTL이 이 체계를 견디게 한다.** 세계의 질문 대부분은 루트에 닿지 않고, 답의 유효 기간은 이름의 주인이 정하며, 캐시마다 남은 시간이 다르다. 이 장의 실측은 이 PC에서 루트 서버부터 권한 서버까지 손으로 따라간 example.com의 이름 풀이, 그 도메인의 레코드 전부, 그리고 캐시에서 초 단위로 줄어드는 TTL이다.

## 1. DNS란

| 항목 | 값 | 왜 |
|:-----|:---|:---|
| 하는 일 | 이름을 주소로, 주소를 이름으로 | 사람은 이름을 쓰고 IP는 숫자를 쓴다 |
| 포트 | 53. [27](../27-udp-structure)장의 UDP, 답이 크면 TCP | 질문 하나 답 하나에 인사는 비싸다 |
| 모양 | 세계에 흩어진 서버들의 위임 사슬 | 중앙 하나로는 크기도 관리도 감당 못 한다 |
| 이름 | 인터넷의 전화번호부 | 이름으로 번호를 찾는다 |

```
사람:   www.example.com  (기억 쉬움)
컴퓨터: 104.20.23.154    (IP 필요)
          ↑
       DNS가 변환
```

이 PC에서 example.com을 물으면 104.20.23.154와 172.66.147.243 두 주소가 온다. [06](../06-network-protocol)장에서 본 그 주소이고, 둘인 것은 같은 이름에 서버 둘을 두어 부하를 나누는 것이다. 책과 옛 문서에 나오는 93.184.216.34는 이 도메인이 다른 회사의 서버에 있던 시절의 주소라 지금은 답이 다르다. 이름이 같아도 주소는 바뀔 수 있고, 그것을 바꿔도 세상이 알아채게 하는 것이 DNS의 존재 이유다.

## 2. 도메인 이름 구조

```
www.example.com.
└┬┘ └──┬──┘ └┬┘ │
 │    │     │  └─ 루트 (.)
 │    │     └─── TLD
 │    └───────── 2단계 도메인
 └────────────── 호스트
```

```
          루트 (.)
            │
    ┌───────┼───────┐
    │       │       │
  .com    .org    .kr
    │               │
  example           co
    │               │
   www           example
                    │
                   www
```

이름은 **오른쪽에서 왼쪽으로** 읽는다. 맨 오른쪽의 보이지 않는 점이 루트, 그다음이 최상위 도메인(TLD), 그다음이 누군가 등록한 도메인, 맨 왼쪽이 그 안의 기계다. 순서가 이런 이유는 위임의 순서이기 때문이다. 루트는 com이 누구 것인지만 알고, com은 example.com이 누구 것인지만 알며, www가 어느 주소인지는 example.com의 주인만 안다. 호스트와 도메인을 다 적은 이름을 FQDN이라 하고, 끝의 점까지 붙이면 "여기서 끝, 더 붙일 것 없음"이라는 뜻이다.

| 분류 | 예 | 누가 관리하나 |
|:-----|:---|:-------------|
| 일반 TLD | .com, .org, .net, .edu, .gov | ICANN이 위탁한 등록소 |
| 국가 TLD | .kr, .us, .jp, .cn, .uk | 나라마다. 한국은 KISA |
| 새 일반 TLD | .app, .dev, .cloud, .ai | 2012년 이후 신청으로 늘었다 |
| 한국의 2단계 | .co.kr, .or.kr, .go.kr, .ac.kr | 나라 안에서 한 단계 더 나눴다 |

## 3. DNS 서버의 종류

| 종류 | 하는 일 | 왜 따로인가 |
|:-----|:--------|:-----------|
| 리졸버 (로컬 DNS) | 클라이언트의 질문을 받아 대신 찾고 캐시한다 | 클라이언트는 단순하게, 찾는 일은 한곳에 모아 캐시한다 |
| 루트 | "com은 저기 물어라" | 위임 사슬의 출발점 |
| TLD | "example.com은 저기 물어라" | com 하나에 도메인이 1억 개가 넘는다 |
| 권한 서버 | "www는 이 주소다" | 이름의 주인이 답을 갖는다 |

네 종류가 있는 이유는 첫째 원리의 위임 사슬 때문이다. 루트, TLD, 권한 서버는 사슬의 세 단이고, 리졸버는 그 사슬을 대신 따라가 주는 심부름꾼이다. 이 PC의 리졸버는 [18](../18-ip-address-structure)장에서 본 대로 손으로 적은 8.8.8.8과 1.1.1.1이고, 04장에서 본 대로 DHCP를 쓰는 집이라면 통신사의 리졸버가 자동으로 들어온다. 루트 서버는 이 PC에서 물어보면 a부터 m까지 이름이 열셋인데, 이름이 열셋일 뿐 실제 기계는 세계에 수천 대다. 같은 주소를 여러 곳에서 동시에 광고해 가장 가까운 곳이 답하는 방식(애니캐스트)으로, 13이라는 수는 1980년대의 UDP 봉투 하나에 담기는 주소 수의 한계였다.

05장에서 "우리 도메인의 주소를 세상에 알리는 DNS"라고 한 것이 권한 서버다. 회사가 도메인을 등록하면 그 도메인의 권한 서버를 직접 운영하거나 등록 대행사나 클라우드에 맡기고, example.com의 경우 이 PC에서 물어보면 클라우드플레어의 서버 둘(elliott와 hera)이 권한 서버다. 세상의 리졸버들이 example.com을 물으면 결국 그 둘에게 닿는다.

## 4. 질의 방식

```
[클라이언트] ──재귀──▶ [리졸버]
                         │
              ┌──반복──┼──반복──┐
              ▼        ▼        ▼
          [루트]    [TLD]   [권한 서버]
                         │
[클라이언트] ◀── 결과 ────┘
```

| 방식 | 누가 누구에게 | 뜻 | 왜 |
|:-----|:-------------|:---|:---|
| 재귀 질의 | 클라이언트가 리졸버에게 | 완성된 답을 가져와 달라 | 클라이언트마다 사슬을 따라가면 캐시가 안 모인다 |
| 반복 질의 | 리졸버가 루트, TLD, 권한 서버에게 | 다음에 물을 곳을 알려 달라 | 루트와 TLD가 대신 찾아 주면 세계의 질문이 거기 몰린다 |

두 종류인 이유가 둘째 원리다. 클라이언트는 "답을 달라"고 한 번만 묻고 기다리며, 리졸버는 사슬을 한 단씩 내려가며 "다음은 어디냐"를 묻는다. 루트와 TLD가 답을 대신 찾아 주지 않고 다음 서버만 알려 주는 것은 그들이 세계의 모든 질문을 감당할 수 없기 때문이고, 그 대신 리졸버가 결과를 캐시해 다음 질문은 사슬을 타지 않게 한다.

```
1) 클라이언트 → 리졸버: www.example.com?
2) 리졸버: 캐시에 없다
3) 루트 → "com은 gtld-servers.net에"
4) com TLD → "example.com은
   elliott, hera.ns.cloudflare.com에"
5) 권한 서버 → "www는 104.20.23.154"
6) 리졸버: 캐시에 넣고 답한다
7) 클라이언트: 주소를 얻었다
```

이 사슬을 이 PC에서 손으로 따라갔다. 루트 서버 a.root-servers.net에 com을 물으면 답 대신 "l, j, h.gtld-servers.net에 물어라"가 온다. 그중 a.gtld-servers.net에 example.com을 물으면 "hera와 elliott.ns.cloudflare.com에 물어라"가 온다. elliott.ns.cloudflare.com에 www.example.com을 물으면 그제야 104.20.23.154와 172.66.147.243이 오고, 이 답에는 다른 서버의 답에 붙던 "권한 없는 답"이라는 표시가 없다. 이름의 주인이 직접 답한 것이기 때문이다. 리졸버는 이 세 단을 대신 밟고, 밟은 결과를 전부 캐시한다. 그래서 다음에 누가 other.example.com을 물으면 루트와 TLD는 건너뛰고 권한 서버에만 묻고, www.example.com을 다시 물으면 어디에도 묻지 않는다.

시간으로 보면 이렇다. 27장에서 잰 대로 리졸버에게 UDP로 묻고 답을 받는 데 42~56ms가 들고, [29](../29-web-server-structure)장에서 잰 대로 처음 묻는 이름은 47ms, 운영체제 캐시에 있는 이름은 12ms였다. 리졸버가 사슬을 처음부터 밟아야 하면 그 위에 단마다 왕복이 더 붙지만, 루트와 TLD의 답은 거의 늘 캐시에 있어 실제로는 권한 서버 한 번이 보통이다.

## 5. DNS 레코드 타입

| 레코드 | 뜻 | example.com에서 이 PC가 받은 것 | 왜 있나 |
|:-------|:---|:-------------------------------|:--------|
| A | 이름 → IPv4 | 104.20.23.154, 172.66.147.243 | 가장 기본. 둘이면 부하 분산 |
| AAAA | 이름 → IPv6 | 2606:4700:10::6814:179a 외 하나 | 18장. 주소가 넷 배 길어 A 넷 |
| CNAME | 별칭 → 진짜 이름 | (없음) | www를 다른 이름에 얹을 때 |
| MX | 이 도메인의 메일 서버 | `.` | 메일은 웹 서버와 다른 기계로 간다. 31장 |
| NS | 이 도메인의 권한 서버 | elliott, hera.ns.cloudflare.com | 3절의 위임 사슬 그 자체 |
| TXT | 자유 텍스트 | `v=spf1 -all` 외 하나 | 새 용도가 생길 때마다 여기 적는다 |
| PTR | 주소 → 이름 | 8.8.8.8 → dns.google | 메일 서버 검증, 로그의 이름 표시 |
| SOA | 영역의 관리 정보 | 주 서버 elliott.ns.cloudflare.com | 누가 주인이고 얼마나 자주 갱신하나 |

```
이름 TTL 클래스 타입 값
example.com. 300 IN A 104.20.23.154
```

레코드 하나는 이름, 유효 기간, 클래스(사실상 늘 IN), 타입, 값이다. example.com의 레코드에는 이 도메인의 성격이 그대로 적혀 있다. MX 값이 점 하나뿐인 것은 "이 도메인은 메일을 받지 않는다"는 약속된 표기이고, TXT의 `v=spf1 -all`은 "이 도메인 이름으로 메일을 보내는 서버는 없으니 그런 메일은 전부 가짜"라는 뜻이다. 예제용 도메인답게 메일을 주고받지 않겠다고 두 레코드로 선언한 것이며, 이 두 레코드가 메일에서 하는 일은 [31](../31-mail-server-structure)장에서 본다. TXT가 자유 텍스트인 이유는 새 용도가 생길 때마다 레코드 타입을 새로 만들 수 없어서이고, 그래서 메일 인증도 도메인 소유 확인도 여기 적힌다. example.com의 다른 TXT 하나가 그런 확인용 토큰이다.

## 6. DNS 캐시와 TTL

{{< callout type="info" >}}
TTL은 답이 캐시에 살아 있어도 되는 시간(초)이고, **이름의 주인이 권한 서버의 레코드에 적는다.** 길면 캐시에서 바로 답해 빠르지만 주소를 바꿔도 세상이 그 시간만큼 옛 주소를 쓴다. 그래서 서버를 옮길 때는 미리 TTL을 60~300초로 낮춰 두고 옮긴 뒤 다시 올린다. 옮기는 순간에 낮추면 이미 캐시된 긴 TTL이 그대로 살아 있어 소용이 없으므로, 낮추는 것은 옛 TTL이 다 지나기 전에 해 두어야 한다.
{{< /callout >}}

| 캐시 | 어디에 | 이 PC에서 | 왜 |
|:-----|:-------|:----------|:---|
| 브라우저 | 프로그램 안 | | 같은 페이지의 파일 수십 개가 같은 이름이다 |
| 운영체제 | DNS 클라이언트 | 12ms. 답의 TTL 58초가 6초 뒤 52초 | 모든 프로그램이 나눠 쓴다 |
| 리졸버 | 8.8.8.8, 1.1.1.1 | 47ms. 같은 이름의 남은 TTL이 300초와 79초 | 세계의 질문을 모아 사슬을 아낀다 |

캐시는 층층이 있고, 층마다 남은 시간이 다르다. 이 PC에서 example.com을 풀면 운영체제 캐시의 TTL이 58초였다가 6초 뒤 52초로 줄어 있다. 캐시는 받은 답을 그대로 두는 것이 아니라 **남은 시간을 세면서** 두고, 0이 되면 버린다. 같은 순간에 8.8.8.8에 물으면 300초, 1.1.1.1에 물으면 79초가 오는 것은 두 리졸버가 그 이름을 서로 다른 시각에 권한 서버에서 받아 왔기 때문이다. 권한 서버가 준 300초에서 각자 지난 시간을 뺀 값이다.

| example.com의 레코드 | TTL | 왜 |
|:--------------------|:----|:---|
| A, AAAA | 300초 | 서버를 갈아 끼우거나 부하를 옮길 때 5분 안에 반영되게 |
| NS | 21,600초 | 권한 서버는 거의 바뀌지 않는다 |
| SOA | 1,800초 | 영역 정보의 갱신 주기 |

TTL이 레코드마다 다른 것도 주인의 선택이다. 주소는 바뀔 수 있으니 짧게, 권한 서버는 안 바뀌니 길게. 구글처럼 트래픽을 수시로 옮기는 곳은 A 레코드를 몇 분짜리로 두고, 이 PC에서 google.com을 물으면 남은 TTL이 101초였다. 짧은 TTL의 대가는 질의 수이고, 그것을 감당할 수 있는 곳만 짧게 둔다.

```bash
ipconfig /displaydns          # Windows. 캐시와 남은 TTL
ipconfig /flushdns
Get-DnsClientCache            # Windows PowerShell
sudo resolvectl flush-caches  # Linux (systemd-resolved)
sudo dscacheutil -flushcache  # macOS
```

주소를 바꿨는데 내 PC만 옛 주소로 가면 캐시를 비운다. 비운 뒤에도 옛 주소가 오면 리졸버의 캐시가 아직 남은 것이고, 그것은 TTL이 지나기를 기다리거나 다른 리졸버에 묻는 수밖에 없다.

## 7. 실무 도구

```bash
nslookup www.google.com
nslookup -type=mx google.com
nslookup example.com 8.8.8.8      # 리졸버를 지정

dig www.google.com +short         # Linux, macOS
dig google.com MX
dig www.google.com +trace         # 루트부터 사슬을 따라간다

Resolve-DnsName example.com -Type NS          # Windows
Resolve-DnsName com -Type NS -Server a.root-servers.net
```

`+trace`가 4절에서 손으로 한 일을 자동으로 한다. Windows에는 dig가 없지만 `Resolve-DnsName`에 `-Server`로 루트, TLD, 권한 서버를 차례로 지정하면 같은 것을 볼 수 있고, 4절의 실측이 그 방법이다. 답에 "권한 없는 답"(Non-authoritative answer)이 붙어 있으면 리졸버의 캐시에서 온 것이고, 없으면 권한 서버가 직접 답한 것이다.

| 공용 리졸버 | 주소 | 왜 쓰나 |
|:-----------|:-----|:--------|
| Google | 8.8.8.8, 8.8.4.4 | 빠르고 세계 어디서나 같다 |
| Cloudflare | 1.1.1.1, 1.0.0.1 | 질의 기록을 남기지 않겠다는 약속 |
| Quad9 | 9.9.9.9 | 악성 도메인을 답하지 않는다 |
| OpenDNS | 208.67.222.222 | 가정용 필터링 |

04장에서 본 대로 리졸버는 보통 통신사가 DHCP로 알려 주지만, 통신사의 것이 느리거나 장애일 때 공용 리졸버로 바꿀 수 있다. 이 PC가 그렇게 되어 있다. 리졸버는 내가 어느 이름을 묻는지를 전부 보는 자리이므로, 어디에 묻는가는 속도만이 아니라 누구에게 내 질문을 보여 줄 것인가의 선택이기도 하다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| DNS | 점마다 위임하는 분산 데이터베이스 | 중앙 하나로는 감당 못 한다 |
| 이름의 방향 | 오른쪽에서 왼쪽으로 | 위임의 순서다 |
| 네 종류의 서버 | 루트, TLD, 권한 서버, 리졸버 | 사슬의 세 단과 심부름꾼 |
| 루트 13 | 이름은 열셋, 기계는 수천 | 애니캐스트. 13은 UDP 봉투의 한계였다 |
| 권한 서버 | 이름의 주인이 답한다 | example.com은 클라우드플레어 둘 |
| 재귀와 반복 | 답을 달라 / 다음을 알려 달라 | 루트와 TLD에 세계의 질문이 몰리지 않게 |
| 손으로 따라간 사슬 | 루트 → com → 권한 서버 → 주소 | "권한 없는 답" 표시가 사라진다 |
| 레코드 | A, AAAA, NS, MX, TXT, PTR, SOA | 도메인의 성격이 적힌다 |
| example.com의 MX와 TXT | `.`과 `v=spf1 -all` | 메일을 받지도 보내지도 않는다는 선언 |
| TTL | 주인이 정하고 캐시가 센다 | 58초가 6초 뒤 52초 |
| 리졸버마다 다른 TTL | 300초와 79초 | 각자 받아 온 시각이 다르다 |
| 짧은 TTL과 긴 TTL | A 300초, NS 21,600초 | 바뀔 것은 짧게, 안 바뀔 것은 길게 |
| 옮길 때 | 미리 TTL을 낮춘다 | 옮기는 순간에 낮추면 늦다 |
| 리졸버의 선택 | 통신사 또는 공용 | 속도와 함께 누가 내 질문을 보는가 |

{{< callout type="info" >}}
**용어 정리**
- **FQDN**: 호스트부터 루트까지 다 적은 이름. 끝의 점은 루트
- **TLD**: 최상위 도메인. com, kr처럼 루트 바로 아래
- **리졸버 (재귀 리졸버)**: 클라이언트 대신 사슬을 따라가고 캐시하는 서버. 8.8.8.8
- **권한 서버**: 이름의 주인이 운영하는, 그 도메인의 답을 가진 서버
- **재귀 질의 / 반복 질의**: 답을 가져와 달라 / 다음에 물을 곳을 알려 달라
- **레코드**: 이름, TTL, 클래스, 타입, 값의 한 줄
- **TTL**: 답이 캐시에 살아 있어도 되는 초. 권한 서버의 레코드에 적힌다
- **애니캐스트**: 같은 주소를 여러 곳에서 광고해 가장 가까운 곳이 답하는 방식
- **권한 없는 답**: 리졸버의 캐시에서 온 답. nslookup의 Non-authoritative answer
{{< /callout >}}
