[23. 전송 계층의 역할](../23-transport-layer-role)에서 TCP와 UDP의 모든 차이는 상태의 유무 하나에서 나오고, 신뢰는 상태와 시간으로 산다고 했다. 이 장은 그 상태가 어디에 적히고 어떻게 바뀌는지를 본다. [02](../02-bit-and-byte)장은 SYN과 ACK가 헤더의 비트 한 자리씩이라고 했고, [08](../08-encapsulation-decapsulation)장은 TCP 헤더가 20바이트이며 두 번호가 32비트인 이유를 여기로 미뤘다. 원리는 셋이다. 첫째, **헤더의 모든 필드는 양 끝이 기억하는 상태의 한 조각이다.** 번호는 어디까지 보냈고 받았는지, 창은 얼마나 더 받을 수 있는지, 플래그는 지금 연결이 어느 단계인지를 적는다. 필드가 20바이트인 이유는 그 상태가 그만큼이기 때문이다. 둘째, **연결은 상태 기계이고, 인사와 작별은 그 기계의 상태를 양쪽이 맞추는 절차다.** 세 번 오가는 인사는 서로의 시작 번호를 확인하는 최소 횟수이고, 네 번 오가는 작별은 방향마다 따로 닫기 때문이며, 마지막에 기다리는 시간은 늦게 온 패킷을 위한 것이다. 셋째, **창은 신뢰를 속도로 바꾸는 장치다.** 확인을 기다리며 하나씩 보내면 회선이 논다. 확인 없이 보내도 되는 양이 창이고, 그 크기가 곧 처리량이다. 이 장의 실측은 이 PC의 TCP 설정값(창 자동 조절, 타임스탬프, 초기 재전송 시간, SYN 재시도 횟수)과 [자바 기초 16장](../../java/basics/16-networking)에서 소켓으로 본 예외들이다.

## 1. TCP의 개념

| 성질 | 뜻 | 왜 |
|:-----|:---|:---|
| 연결 지향 | 세 번의 인사로 시작한다 | 상태를 기억하려면 시작이 있어야 한다 |
| 전이중 | 한 연결에서 양쪽이 동시에 보낸다 | 방향마다 번호와 창이 따로 있다 |
| 바이트 흐름 | 봉투가 없고 바이트의 줄만 있다 | 번호가 바이트 단위라 어디서 끊어 보냈는지 남지 않는다 |
| 신뢰 | 번호, 확인 응답, 재전송, 체크섬 | IP가 버린 것을 양 끝이 되찾는다 |
| 속도 조절 | 창과 혼잡 제어 | 받는 쪽과 길의 사정에 맞춘다 |

```text
응용 데이터
   ↓ TCP 헤더
[TCP][데이터]         세그먼트
   ↓ IP 헤더
[IP][TCP][데이터]     패킷
```

TCP 헤더가 붙은 단위를 세그먼트라 한다. 응용 프로그램이 쓴 바이트를 TCP가 적당한 크기로 잘라 헤더를 붙이고, 08장에서 본 대로 그 크기는 MSS 1,460바이트가 한도다. 자바 기초 16장에서 `ab`와 `cd`를 두 번 써 보내면 상대가 `abcd`를 한 번에 읽는 것을 확인했는데, 잘라 보내는 것도 붙여 읽는 것도 TCP의 몫이고 응용 프로그램의 쓰기 단위는 어디에도 남지 않기 때문이다. 이것이 "전이중"과 함께 이 장의 헤더를 읽는 열쇠다. 헤더의 번호와 창은 세그먼트가 아니라 **바이트**를 센다.

## 2. TCP 헤더 구조

```text
 0        8        16       24      31
 ├────────┴────────┼────────┴────────┤
 │   출발지 포트    │   목적지 포트    │
 ├─────────────────┴─────────────────┤
 │            순서 번호               │
 ├───────────────────────────────────┤
 │          확인 응답 번호            │
 ├────┬────┬───────┼─────────────────┤
 │길이│예약│ 플래그│    창 크기       │
 ├────┴────┴───────┼─────────────────┤
 │     체크섬       │   긴급 포인터    │
 ├─────────────────┴─────────────────┤
 │        옵션 (0~40바이트)           │
 ├───────────────────────────────────┤
 │             데이터                 │
 └───────────────────────────────────┘
```

| 필드 | 크기 | 적히는 것 | 왜 있나 |
|:-----|:-----|:----------|:--------|
| 출발지, 목적지 포트 | 16비트씩 | 어느 프로그램에서 어느 프로그램으로 | 23장. 4층의 주소 |
| 순서 번호 | 32비트 | 이 세그먼트 첫 바이트의 번호 | 다른 길로 온 조각을 제자리에 |
| 확인 응답 번호 | 32비트 | 다음에 받고 싶은 바이트 번호 | 여기까지 받았다는 누적 확인 |
| 헤더 길이 | 4비트 | 헤더가 4바이트 단위로 몇 개인가 | 옵션 때문에 길이가 변한다. 최대 60 |
| 플래그 | 8비트 | SYN, ACK, FIN 같은 스위치 | 3절 |
| 창 크기 | 16비트 | 확인 없이 더 받을 수 있는 바이트 수 | 8절. 받는 쪽의 사정 |
| 체크섬 | 16비트 | 헤더, 데이터, IP 주소까지의 검사 | 23장. IP는 헤더만 검사한다 |
| 긴급 포인터 | 16비트 | 긴급 데이터의 끝 | 사실상 쓰이지 않는다 |
| 옵션 | 0~40바이트 | MSS, 창 배율, 타임스탬프, 선택 확인 | 1981년에 없던 것을 뒤에 붙였다 |

번호가 32비트인 것은 바이트를 세기 때문이라고 08장에서 봤다. 1981년에는 43억 바이트가 넉넉했지만 1Gbps 회선에서는 34초면 한 바퀴를 돈다. 그래서 늦게 도착한 옛 세그먼트가 한 바퀴 뒤의 새 번호와 겹칠 수 있고, 그것을 가려내려고 옵션에 타임스탬프를 넣는다. 타임스탬프는 왕복 시간을 재는 데도 쓰이며, 이 PC의 설정에는 "RFC 1323 Timestamps: allowed"로 켜져 있다. 옵션 자리가 있는 이유가 이것이다. 40년 동안 필요해진 것들을 헤더를 깨지 않고 덧붙이려고 비워 둔 자리이고, 그래서 헤더 길이 필드가 따로 필요하다. 옵션 중 MSS와 창 배율은 **SYN에만** 실린다. 연결을 맺는 순간 정하고 그 뒤에는 바꾸지 않는 값이기 때문이다.

## 3. 제어 비트 (플래그)

| 플래그 | 뜻 | 언제 켜지나 | 왜 필요한가 |
|:-------|:---|:-----------|:-----------|
| SYN | 시작 번호를 맞추자 | 연결의 첫 두 세그먼트 | 번호는 0부터가 아니라 무작위에서 시작한다 |
| ACK | 확인 응답 번호가 유효하다 | 첫 SYN을 뺀 전부 | 확인할 것이 없는 순간은 처음뿐이다 |
| FIN | 보낼 것이 끝났다 | 닫을 때 | 방향마다 끝을 알려야 한다 |
| RST | 이 연결은 없다. 버려라 | 닫힌 포트, 깨진 연결 | 인사 없이 즉시 끊을 방법이 필요하다 |
| PSH | 버퍼에 두지 말고 바로 올려라 | 쓰기의 마지막 조각 | 받는 쪽이 모아 두다 늦을까 봐 |
| URG | 긴급 포인터가 유효하다 | 거의 없다 | 옛 원격 접속의 인터럽트. 지금은 권장하지 않는다 |
| ECE, CWR | 길이 붐빈다는 표시 | 라우터가 표시해 줄 때 | 버리기 전에 알리는 방식. 이 PC는 꺼져 있다 |

| 상황 | 켜진 플래그 | 왜 |
|:-----|:-----------|:---|
| 연결 요청 | SYN | 아직 확인할 것이 없다 |
| 연결 응답 | SYN + ACK | 내 시작 번호도 알리고 네 것도 확인한다 |
| 그 뒤 모든 세그먼트 | ACK (+ PSH) | 확인 응답 번호는 늘 실려 다닌다 |
| 정상 종료 | FIN + ACK | 끝을 알리면서 받은 것도 확인한다 |
| 강제 종료, 거절 | RST | 상대가 답할 것도 없다 |

02장에서 본 대로 플래그는 바이트 하나의 비트들이고, "SYN+ACK"는 두 비트가 함께 1인 것이다. RST는 나머지와 성격이 다르다. 다른 플래그는 대화의 일부이지만 RST는 대화의 거부다. 아무도 듣지 않는 포트에 SYN을 보내면 운영체제가 RST로 답하고, 자바 기초 16장에서 본 `Connection refused`가 그 RST를 받은 결과다. 통신 도중에 상대가 죽거나 프로그램이 소켓을 험하게 닫아 RST가 오면 `Connection reset`이 된다. 답이 아예 없는 것과 RST가 오는 것은 다른 진단이다. 앞은 방화벽이나 죽은 기계, 뒤는 살아 있는 기계의 닫힌 포트다.

## 4. 3-way Handshake (연결 수립)

```text
 Client                        Server
(CLOSED)                      (LISTEN)
   │                             │
   │── SYN, Seq=1000 ──────────→│
(SYN_SENT)              (SYN_RECEIVED)
   │                             │
   │←── SYN+ACK, Seq=2000 ──────│
   │     Ack=1001               │
   │                             │
   │── ACK, Seq=1001 ──────────→│
   │     Ack=2001               │
(ESTABLISHED)          (ESTABLISHED)
   │                             │
   │════  데이터 교환 가능  ════ │
```

연결을 맺는다는 것은 **양쪽이 각자의 시작 번호를 상대에게 알리고 상대의 것을 확인**하는 일이다. 클라이언트가 "내 번호는 1000부터"라고 하면 서버는 "받았다, 다음은 1001을 다오. 그리고 내 번호는 2000부터"라고 답하고, 클라이언트가 "받았다, 다음은 2001을 다오"로 끝낸다. 세 번인 이유는 알림 둘과 확인 둘이 필요한데 서버의 알림과 확인이 한 세그먼트에 실리기 때문이다. 두 번으로 끝내면 서버는 자기 번호가 클라이언트에게 닿았는지 모른 채 데이터를 보내야 한다. 확인 응답이 1001인 것은 SYN 자체가 번호 하나를 차지하기 때문이다. 데이터를 한 바이트도 안 보냈지만 "SYN을 받았다"를 번호로 표현하려면 SYN에도 자리가 있어야 한다. FIN도 같은 이유로 하나를 차지한다.

시작 번호가 0이 아니라 무작위인 이유는 둘이다. 같은 두 포트로 연결을 끊었다 곧 다시 맺었을 때 앞 연결의 늦은 세그먼트가 새 연결의 번호와 겹치지 않게 하려는 것이 원래 이유이고, 시작 번호를 맞힐 수 있으면 남의 연결에 세그먼트를 끼워 넣을 수 있다는 것이 뒤에 밝혀진 이유다. 지금은 주소와 포트에서 비밀값으로 만든 해시를 쓴다.

세 번의 인사는 23장에서 본 대로 왕복 한 번의 값이고, 그 값을 아끼려는 시도가 계속 있었다. 첫 SYN에 데이터를 함께 실어 보내는 TCP Fast Open이 그 하나이고, 이 PC의 설정에는 "Fast Open: enabled"로 켜져 있다. 다만 상대 서버와 중간 장비가 모두 받아 줘야 해서 널리 쓰이지는 못했고, 23장의 QUIC이 그 자리를 대신하고 있다. SYN을 보냈는데 아무 답이 없으면 운영체제는 1초, 2초, 4초로 간격을 두 배씩 늘리며 다시 보낸다. 이 PC는 "Initial RTO: 1000", "Max SYN Retransmissions: 4"라, 다섯 번을 보내고도 답이 없으면 30초쯤 뒤에 포기하며 그것이 자바 16장의 `Connect timed out`이다.

{{< callout type="warning" >}}
서버는 SYN을 받는 순간 SYN_RECEIVED 상태의 기억을 하나 만든다. 이것을 노려 가짜 출발지로 SYN만 수십만 개 보내면 서버의 기억이 가득 차 진짜 손님을 못 받는다(SYN 플러딩). 대응은 SYN을 받아도 기억을 만들지 않고, 시작 번호 자체에 정보를 암호화해 넣어 세 번째 ACK가 돌아올 때 검증하는 SYN 쿠키다. 상태를 갖는다는 것은 상태를 채워 넣는 공격에 노출된다는 뜻이고, 23장의 "신뢰는 상태로 산다"의 어두운 면이다.
{{< /callout >}}

## 5. 4-way Handshake (연결 해제)

```text
 Client                        Server
(ESTAB.)                      (ESTAB.)
   │── FIN ───────────────────→│
(FIN_WAIT_1)            (CLOSE_WAIT)
   │←── ACK ──────────────────│
(FIN_WAIT_2)                   │
   │        (남은 데이터 송신)  │
   │←── FIN ──────────────────│
(TIME_WAIT)              (LAST_ACK)
   │── ACK ───────────────────→│
   │   (2MSL 대기)             │
(CLOSED)                    (CLOSED)
```

끊을 때 네 번인 이유는 연결이 전이중이라 **방향이 둘**이고 방향마다 따로 닫기 때문이다. 클라이언트의 FIN은 "나는 다 보냈다"일 뿐 "너도 그만 보내라"가 아니다. 서버는 그것을 확인만 하고, 아직 보낼 것이 남았으면 마저 보낸 뒤에 자기 FIN을 보낸다. 서버의 확인과 FIN이 한 세그먼트에 합쳐지지 않는 것은 그 사이에 시간이 있을 수 있기 때문이고, 보낼 것이 없으면 둘을 합쳐 세 번으로 끝나기도 한다.

한쪽만 닫힌 상태를 반쪽 닫힘이라 부르고, 일부러 쓰기도 한다. 클라이언트가 요청을 다 보낸 뒤 "보내기 쪽"만 닫아 서버에게 요청의 끝을 알리고, 서버의 응답은 계속 받는 식이다. 자바에서 `shutdownOutput()`이 그것이다. 원문 그림에서 서버의 CLOSE_WAIT는 "상대가 끝냈으니 나도 닫아야 한다"를 프로그램에게 알리는 상태인데, 프로그램이 소켓을 닫지 않으면 이 상태가 영원히 남는다. 9절의 첫 번째 문제다.

## 6. TCP 상태 전이

```text
          CLOSED
        ┌───┴───┐
     active   passive
        │       │
    SYN_SENT  LISTEN
        │       │
        │    SYN_RECEIVED
        │       │
        └───────┴──→ ESTABLISHED
                        │
              ┌─────────┴─────────┐
          send FIN            recv FIN
              │                   │
        FIN_WAIT_1           CLOSE_WAIT
              │                   │
        FIN_WAIT_2            LAST_ACK
              │                   │
        TIME_WAIT              CLOSED
              │
           CLOSED
```

| 상태 | 뜻 | 누가 |
|:-----|:---|:-----|
| LISTEN | 문을 열고 SYN을 기다린다 | 서버 |
| SYN_SENT | SYN을 보내고 답을 기다린다 | 클라이언트 |
| SYN_RECEIVED | SYN을 받고 마지막 ACK를 기다린다 | 서버. 4절 callout의 자리 |
| ESTABLISHED | 데이터가 오간다 | 양쪽 |
| FIN_WAIT_1, 2 | 내 FIN을 보내고 상대의 ACK, FIN을 기다린다 | 먼저 닫는 쪽 |
| CLOSE_WAIT | 상대의 FIN을 받았다. 내 프로그램이 닫기를 기다린다 | 나중에 닫는 쪽 |
| LAST_ACK | 내 FIN을 보내고 마지막 ACK를 기다린다 | 나중에 닫는 쪽 |
| TIME_WAIT | 다 끝났지만 2MSL 동안 기다린다 | 먼저 닫는 쪽 |

23장에서 TCP와 UDP의 차이는 상태의 유무라고 했는데, 이 그림이 그 상태의 전부다. 소켓 하나는 언제나 이 열 개 중 하나에 있고, 세그먼트를 주고받을 때마다 옮겨 간다. 연결이 이상할 때 `netstat`이 보여 주는 것이 이 상태이고, 어느 상태에 쌓여 있는지가 곧 진단이다.

### TIME_WAIT

먼저 닫은 쪽은 마지막 ACK를 보낸 뒤 바로 사라지지 않고 **2MSL** 동안 기다린다. MSL은 세그먼트가 망에서 살아 있을 수 있는 최대 시간으로 규격은 2분을 잡았고, 실제 값은 Windows가 기본 2분, Linux가 60초다. 이 PC는 그 설정을 바꾼 적이 없어 기본값이다. 기다리는 이유는 둘이다.

1. **마지막 ACK가 사라졌을 때.** 상대는 FIN을 다시 보낼 텐데, 내가 이미 사라졌으면 그 FIN에 답할 소켓이 없어 상대는 LAST_ACK에 갇힌다. 기다리고 있어야 다시 ACK를 보낼 수 있다.
2. **늦게 온 세그먼트가 새 연결에 섞이지 않게.** 같은 네 값(주소 둘, 포트 둘)의 연결을 곧바로 다시 맺으면 옛 연결의 늦은 세그먼트가 새 연결의 데이터로 읽힐 수 있다. 세그먼트가 살아 있을 수 있는 시간만큼 그 네 값을 묶어 둔다.

기다리는 쪽이 먼저 닫은 쪽인 것은 그쪽만이 마지막 ACK를 보내기 때문이다. 나중에 닫는 쪽은 자기 FIN에 대한 ACK를 받으면 할 일이 끝난다. 그래서 서버가 먼저 닫는 설계(짧은 HTTP 연결을 서버가 끊는 식)에서는 서버에 TIME_WAIT가 쌓인다.

{{< callout type="warning" >}}
서버를 껐다 곧 다시 켤 때 `Address already in use`가 나는 원인이 TIME_WAIT다. 자바 기초 16장에서 본 `BindException`이 그것이다. 옛 연결이 그 포트를 2MSL 동안 붙들고 있기 때문이고, `SO_REUSEADDR` 소켓 옵션이 "TIME_WAIT 중인 포트라도 다시 열겠다"는 뜻이다. Linux의 `net.ipv4.tcp_tw_reuse`는 클라이언트 쪽에서 TIME_WAIT 소켓을 새 연결에 재사용하게 해 준다.
{{< /callout >}}

## 7. 순서 번호와 확인 응답 (재전송 메커니즘)

```text
다음 Seq = 현재 Seq + 보낸 바이트 수
ACK      = 받은 Seq + 받은 바이트 수
           (= 다음에 기대하는 번호)
```

```text
Client ─ Seq=1001, Len=200 ─→ Server
Client ←─── ACK=1201 ──────── Server
Client ─ Seq=1201, Len=300 ─→ Server
Client ←─── ACK=1501 ──────── Server
```

두 번호는 바이트를 센다. 1001번부터 200바이트를 보내면 다음 세그먼트는 1201번부터이고, 받은 쪽은 "1201을 다오"로 답한다. 확인 응답은 받은 것의 끝이 아니라 **기대하는 다음**이라 누적이 되고, 그래서 확인 응답 하나가 사라져도 다음 것이 대신한다. 잃어버린 것을 알아채는 방법은 둘이다.

| 방식 | 언제 알아채나 | 왜 둘 다 있나 |
|:-----|:-------------|:-------------|
| 타이머 재전송 | 보내고 RTO 안에 확인이 없을 때 | 확실하지만 느리다. 확인이 아예 안 오는 경우의 최후 수단 |
| 빠른 재전송 | 같은 확인 응답이 세 번 겹쳐 올 때 | 뒤의 세그먼트가 도착했다는 뜻이니 기다릴 이유가 없다 |

```text
Seq=1101 ─→ 손실
Seq=1201 ─→ 받음, ACK=1101 (중복 1)
Seq=1301 ─→ 받음, ACK=1101 (중복 2)
Seq=1401 ─→ 받음, ACK=1101 (중복 3)
Seq=1101 ─→ 곧바로 재전송
```

1101이 사라지고 뒤의 것들이 도착하면 받는 쪽은 계속 "1101을 다오"라고 한다. 같은 답이 세 번 겹치면 보내는 쪽은 타이머를 기다리지 않고 1101을 다시 보낸다. 세 번인 이유는 한두 번은 순서가 잠깐 바뀐 것일 수 있어서다. RTO를 왕복 시간에서 계산하는 법과 두 번호의 자세한 흐름은 [25. 일련번호와 확인 응답 번호의 구조](../25-sequence-ack-number)에서 본다.

## 8. 흐름 제어와 윈도우

```text
[v][v][*][*][*][*][5][6][7][8]
 확인됨 │ 보냄, 대기중 │ 보낼 수 있음
        └── 창 = 4 ──┘
```

세그먼트 하나를 보내고 확인이 올 때까지 기다렸다 다음을 보내면, 왕복 시간마다 세그먼트 하나씩만 간다. 01장의 핀란드 서버라면 0.25초에 1,460바이트, 초당 6KB다. 회선이 1Gbps인데 말이다. 그래서 확인을 기다리지 않고 **창 크기만큼 연속으로** 보내고, 확인이 올 때마다 창을 오른쪽으로 밀어 그만큼 더 보낸다. 이것이 슬라이딩 윈도우이고, 창 크기를 왕복 시간으로 나눈 것이 처리량의 상한이다. 창이 64KB이고 왕복이 0.25초면 초당 256KB가 한계이고, 회선이 아무리 넓어도 그 이상 나오지 않는다.

| 받는 쪽 버퍼 | 알리는 창 | 왜 |
|:------------|:----------|:---|
| 넉넉하다 | 크게 | 보내는 쪽이 마음껏 보내도 된다 |
| 차고 있다 | 작게 | 프로그램이 읽는 속도가 못 따라온다 |
| 가득 찼다 | 0 | 멈춰라. 버리는 것보다 낫다 |

창의 값은 받는 쪽이 정한다. 받은 데이터는 프로그램이 읽어 갈 때까지 버퍼에 있고, 버퍼의 빈자리가 곧 창이다. 받는 쪽이 자기 사정을 확인 응답마다 실어 보내므로 보내는 쪽은 상대의 버퍼를 넘치게 할 수 없다. 이것이 흐름 제어이고, 23장에서 본 대로 길의 사정(혼잡 제어)과는 별개의 조절이다. 실제로 보내는 양은 둘 중 작은 쪽이다.

### 창이 0이 된 뒤

받는 쪽이 창 0을 알리면 보내는 쪽은 멈춘다. 그 뒤 버퍼가 비어 "이제 받을 수 있다"는 갱신을 보냈는데 그 세그먼트가 사라지면, 보내는 쪽은 영원히 기다리고 받는 쪽은 영원히 안 온다고 여기는 교착이 된다. 그래서 보내는 쪽은 창이 0인 동안 1바이트짜리 탐침을 주기적으로 보내 창의 값을 다시 받아 낸다. 규칙이 사라진 세그먼트 하나에 무너지지 않게 하는 안전장치다.

### 창 배율

창 필드는 16비트라 64KB가 한도다. 1981년의 회선에는 넉넉했지만 위의 계산대로 1Gbps에 왕복 0.25초면 64KB로는 회선의 1%도 못 쓴다. 그래서 SYN에서 배율(2의 몇 제곱)을 교환해 `창 × 2ⁿ`으로 읽는다. 최대 2¹⁴배, 1GB까지다. SYN에서만 정하는 이유는 배율이 연결 도중 바뀌면 양쪽이 같은 값을 다르게 읽기 때문이다. 이 PC의 설정 "Receive Window Auto-Tuning Level: normal"이 이 배율을 쓰겠다는 뜻이고, 운영체제가 왕복 시간과 회선 속도를 보아 가며 창을 키운다. 회선 속도와 왕복 시간에서 창의 적정 크기를 계산하는 법은 25장에서 본다.

## 9. 실무 활용

```bash
# Windows
netstat -an
netstat -ano | findstr "ESTABLISHED"
netstat -an | findstr "TIME_WAIT"

# Linux
ss -tan
ss -tanp          # 프로세스까지
```

```text
tcp.flags.syn == 1
tcp.flags.syn == 1 && tcp.flags.ack == 1
tcp.flags.fin == 1
tcp.flags.reset == 1
tcp.analysis.retransmission
tcp.analysis.duplicate_ack
tcp.port == 443
```

두 번째 블록은 Wireshark의 필터다. 이 장의 플래그와 재전송이 캡처 화면에서 그대로 보인다.

| 증상 | 원인 | 왜 그런가 | 대응 |
|:-----|:-----|:----------|:-----|
| CLOSE_WAIT가 쌓인다 | 프로그램이 소켓을 안 닫는다 | 상대의 FIN은 받았는데 내 FIN을 안 보낸다. 5절 | 예외 경로에서도 닫히게 |
| TIME_WAIT가 쌓인다 | 짧은 연결을 내가 먼저 끊는다 | 먼저 닫는 쪽이 2MSL을 기다린다. 6절 | 연결 재사용(Keep-Alive), SO_REUSEADDR |
| RST가 온다 | 포트가 닫혔거나 방화벽이 거절한다 | 대화의 거부. 3절 | 서비스가 떠 있는지, 방화벽 규칙 |
| SYN에 답이 없다 | 방화벽이 버리거나 기계가 없다 | RST조차 없다. 4절 | 30초 뒤 시간 초과. 경로 확인 |
| 연결은 됐는데 느리다 | 재전송, 작은 창, 긴 왕복 | 창 ÷ 왕복 시간이 상한. 8절 | 재전송 여부와 창 크기 확인 |

{{< callout type="info" >}}
**용어 정리**
- **세그먼트**: TCP 헤더가 붙은 단위. 응용 프로그램의 쓰기 단위와 무관하다
- **순서 번호 / 확인 응답 번호**: 이 세그먼트 첫 바이트의 번호 / 다음에 기대하는 바이트의 번호
- **ISN**: 무작위로 정하는 초기 순서 번호
- **제어 비트**: SYN, ACK, FIN, RST, PSH, URG와 혼잡 표시 ECE, CWR
- **3-way / 4-way 핸드셰이크**: 시작 번호를 확인하는 세 번 / 방향마다 닫는 네 번
- **반쪽 닫힘**: 한 방향만 닫힌 상태. 보낼 것은 끝났지만 받는 것은 계속
- **MSL / TIME_WAIT**: 세그먼트의 최대 생존 시간 / 먼저 닫은 쪽이 2MSL 동안 기다리는 상태
- **SYN 쿠키**: 상태를 만들지 않고 SYN에 답하는 방어
- **창 (윈도우)**: 확인 없이 보내도 되는 바이트 수. 받는 쪽이 정한다
- **슬라이딩 윈도우 / 창 0 탐침 / 창 배율**: 창을 밀며 연속 전송 / 창 0에서 1바이트로 묻기 / 16비트 한계를 2ⁿ으로 넓히기
