[01. 네트워크의 기본](../01-network-basics)에서 패킷 교환의 대가인 손실과 순서 뒤바뀜을 TCP가 번호로 되돌리는 방법은 이 장에서 본다고 했다. [24](../24-tcp-structure)장은 두 번호가 바이트를 세고 SYN과 FIN도 한 자리를 차지한다는 것까지 보고, 재전송 시간을 왕복 시간에서 계산하는 법과 창의 적정 크기를 여기로 미뤘다. 원리는 셋이다. 첫째, **두 번호는 방향마다 하나씩 있는 카운터이고, 확인은 반대 방향의 세그먼트에 얹혀 간다.** 확인 응답이 "다음에 기대하는 번호"인 것은 누적이기 위해서이고, 누적이라 확인 하나쯤은 잃어도 되지만 구멍은 말하지 못한다. 둘째, **재전송의 어려운 점은 "언제 포기하고 다시 보내는가"이고, 그 답은 재어서 정한다.** 이 PC에서 구글까지는 왕복 40ms, 핀란드까지는 250ms인데 같은 기다림을 쓸 수는 없다. 그리고 기다리지 않아도 되는 지름길이 있다. 셋째, **창은 확인 없이 회선에 떠 있어도 되는 양이고, 적정값은 회선 속도 × 왕복 시간이다.** 그 값이 이 PC에서 핀란드 서버까지는 31MB라, 1981년의 64KB 창으로는 회선의 1%도 못 쓴다. 이 장의 실측은 두 서버로 보낸 ping 열 번씩의 왕복 시간과, 거기서 규격의 공식으로 계산한 재전송 시간이다.

## 1. 두 번호의 역할

| 번호 | 누가 적나 | 뜻 | 왜 |
|:-----|:---------|:---|:---|
| 일련번호 | 보내는 쪽 | 이 세그먼트 첫 바이트의 번호 | 다른 길로 온 조각을 제자리에 꽂는다 |
| 확인 응답 번호 | 받는 쪽 | 다음에 기대하는 바이트의 번호 | 여기까지 다 받았다는 누적 확인 |

```text
TCP 헤더
┌─────────────────────────────┐
│ 일련번호           (32비트) │
├─────────────────────────────┤
│ 확인 응답 번호     (32비트) │
└─────────────────────────────┘
```

```text
A → B  Seq=101, Ack=501, 데이터 200
B → A  Seq=501, Ack=301, 데이터 1000
       (A의 200바이트 확인 + B의 데이터)
```

연결은 전이중이라 방향이 둘이고, 방향마다 일련번호가 따로 있다. A가 보내는 바이트의 번호와 B가 보내는 바이트의 번호는 서로 무관하며, 각자 24장에서 본 무작위 시작 번호에서 출발한다. 확인 응답은 그 반대 방향의 카운터를 가리킨다. A의 세그먼트에 실린 Ack=501은 "B가 보낸 것은 500번까지 받았다"이고, B의 세그먼트에 실린 Ack=301은 "A가 보낸 것은 300번까지 받았다"다. 확인만 보내려고 빈 세그먼트를 만들 필요가 없다. 어차피 보낼 데이터가 있으면 거기에 확인 응답 번호를 얹어 보내고, 이것이 헤더의 ACK 비트가 첫 SYN을 빼고는 늘 켜져 있는 이유다.

## 2. 일련번호

일련번호는 세그먼트가 아니라 **바이트**의 번호다. 24장에서 본 대로 응용 프로그램의 쓰기 단위는 남지 않고, 재전송할 때 원래와 다른 크기로 잘라 보낼 수도 있으므로 세그먼트에 번호를 붙여서는 맞출 수가 없다. 시작 번호가 무작위인 이유도 24장에서 봤다.

```text
다음 Seq = 현재 Seq + 보낸 바이트 수
```

| 보낸 것 | Seq의 변화 | 왜 |
|:--------|:-----------|:---|
| 데이터 N바이트 | N만큼 는다 | 바이트마다 번호 하나 |
| SYN | 1 는다 | 받았다는 것을 번호로 확인하려면 자리가 있어야 한다 |
| FIN | 1 는다 | 위와 같다 |
| 순수 ACK | 늘지 않는다 | 확인은 재전송하지 않으므로 번호가 필요 없다 |

| 전송 | Seq | 길이 | 바이트 범위 |
|:-----|:----|:-----|:-----------|
| 1회 | 1000 | 1000 | 1000 ~ 1999 |
| 2회 | 2000 | 1000 | 2000 ~ 2999 |
| 3회 | 3000 | 1000 | 3000 ~ 3999 |

순수 확인 응답이 번호를 쓰지 않는 것은 확인은 잃어버려도 다시 보내지 않기 때문이다. 다음 확인이 그것을 대신한다. 번호가 필요한 것은 잃어버리면 다시 보내야 하는 것들, 곧 데이터와 SYN과 FIN뿐이다.

## 3. 확인 응답 번호

```text
ACK = 받은 Seq + 받은 바이트 수
    = 다음에 기대하는 번호
```

```text
송신 ─ Seq=1000, Len=100 ─→ 수신
송신 ─ Seq=1100, Len=100 ─→ 수신
송신 ─ Seq=1200, Len=100 ─→ 수신
송신 ←─ ACK=1300 ──────── 수신
       "1300번부터 보내 다오"
       (1000~1299까지 다 받았다는 뜻)
```

확인 응답 번호가 받은 것의 끝이 아니라 **기대하는 다음**인 것은 누적 확인을 위해서다. ACK=1300은 1299까지 전부 받았다는 뜻이라 세그먼트마다 확인을 보낼 필요가 없고, 앞의 확인이 사라져도 뒤의 확인이 대신한다. 이 PC에서 세그먼트 셋을 받고 확인 하나로 답해도 보내는 쪽은 셋 다 확인된 것으로 안다.

### 확인을 미룬다

받는 쪽은 세그먼트를 받는 즉시 확인하지 않고 잠시 미룬다. 곧 두 번째 세그먼트가 오면 둘을 한 번에 확인할 수 있고, 응용 프로그램이 답을 쓰면 그 데이터에 얹어 보낼 수 있기 때문이다. 규격은 두 번째 세그먼트가 오거나 수십에서 200ms가 지나면 확인하도록 한다. 세그먼트 하나에 확인 하나면 회선의 절반이 빈 확인으로 채워지므로, 미루는 것은 절약이다.

```text
보내는 쪽: 확인이 와야 다음 조각을 보냄
받는 쪽:   조각이 더 와야 확인을 보냄
결과: 둘 다 기다린다 (최대 200ms)
```

이 절약이 다른 절약과 부딪히면 유명한 정체가 생긴다. 보내는 쪽에는 작은 조각을 모아 보내는 규칙(Nagle)이 있어, 확인이 안 온 조각이 있으면 다음 작은 조각을 보내지 않고 모은다. 받는 쪽은 조각이 하나뿐이라 확인을 미룬다. 둘이 서로를 기다려 200ms가 그냥 간다. 작은 요청을 두 번에 나눠 쓰고 답을 기다리는 프로그램에서 요청마다 0.2초씩 느려지는 원인이고, 대화형 프로그램과 데이터베이스 드라이버가 `TCP_NODELAY`로 Nagle을 끄는 이유다. [자바 기초 16장](../../java/basics/16-networking)에서 버퍼를 비우지 않으면 서로 기다린다고 했는데, 그것이 응용 프로그램 층의 같은 병이다.

### 누적의 한계와 선택 확인

누적 확인은 "여기까지"만 말할 수 있다. 1100~1199가 사라지고 1200~1499가 도착해도 확인은 계속 1100이고, 보내는 쪽은 1200부터도 못 받은 줄 알고 다시 보낼 수 있다. 창이 커질수록 이 낭비가 커지므로 옵션으로 "1200~1499는 받았다"는 **선택 확인**(SACK)을 함께 보낸다. 24장에서 본 옵션 자리에 실리고, 이 PC를 비롯한 요즘 운영체제는 기본으로 켜 둔다. 구멍만 다시 보내면 되니 큰 창에서 손실이 나도 회선을 낭비하지 않는다.

## 4. 데이터 전송 전체 흐름

시작 번호를 클라이언트 100, 서버 300으로 두면 이렇다.

| 단계 | 방향 | 내용 | Seq / Ack | 왜 |
|:-----|:-----|:-----|:----------|:---|
| 1 | C → S | SYN | Seq=100 | SYN이 1을 쓴다 |
| 2 | S → C | SYN+ACK | Seq=300, Ack=101 | 100까지 받았으니 101을 다오 |
| 3 | C → S | ACK | Seq=101, Ack=301 | 서버의 SYN도 1을 썼다 |
| 4 | C → S | 데이터 200 | Seq=101, Ack=301 | 101~300을 보낸다 |
| 5 | S → C | ACK | Seq=301, Ack=301 | 301을 다오 |
| 6 | S → C | 데이터 1000 | Seq=301, Ack=301 | 301~1300을 보낸다 |
| 7 | C → S | ACK | Seq=301, Ack=1301 | 1301을 다오 |

3단계의 ACK와 4단계의 데이터는 실제로는 자주 합쳐진다. 3단계에 데이터를 실어 보내도 되기 때문이다. 5단계와 6단계도 마찬가지로, 서버가 바로 답할 것이 있으면 4단계의 확인은 6단계의 데이터에 얹혀 가고 5단계는 없다. 표의 단계들은 논리적인 순서이고, 실제 세그먼트 수는 1절의 얹어 보내기 때문에 이보다 적다. 요청 하나와 답 하나로 끝나는 HTTP 대화가 인사 셋, 데이터 둘, 확인 하나 정도로 끝나는 이유다.

## 5. 재전송 제어

| 무슨 일이 | 어떻게 드러나나 | 누가 고치나 |
|:----------|:---------------|:-----------|
| 세그먼트가 사라졌다 | 확인이 안 온다, 또는 같은 확인이 겹쳐 온다 | 보내는 쪽이 다시 보낸다 |
| 세그먼트가 깨졌다 | 체크섬이 틀려 받는 쪽이 버린다. 위와 같아진다 | 위와 같다 |
| 확인이 사라졌다 | 다음 확인이 대신한다 | 아무도. 누적이 해결한다 |
| 마지막 확인이 사라졌다 | 대신할 다음 확인이 없다 | 보내는 쪽이 다시 보내고, 받는 쪽은 번호로 중복임을 알고 버린다 |

### 타이머 재전송: 얼마나 기다릴 것인가

```text
RTO = SRTT + 4 × RTTVAR

SRTT   : 최근 왕복 시간의 가중 평균
RTTVAR : 왕복 시간이 흔들리는 폭
```

보내고 확인이 안 오면 다시 보내는데, **얼마나 기다렸다가**가 문제다. 짧으면 아직 오는 중인 확인을 못 기다리고 다시 보내 회선을 낭비하고, 길면 진짜 잃어버렸을 때 한참을 논다. 정답은 길마다 다르므로 재어서 정한다. 세그먼트를 보낸 시각과 확인이 온 시각의 차이가 왕복 시간(RTT)이고, 그 가중 평균(SRTT)에 흔들리는 폭(RTTVAR)의 네 배를 더한 것이 재전송 시간(RTO)이다. 평균만 쓰지 않고 흔들림을 더하는 것은 왕복 시간이 늘 같지 않기 때문이다.

| 상대 | ping 열 번의 왕복 (ms) | SRTT | RTTVAR | RTO |
|:-----|:----------------------|:-----|:-------|:----|
| 구글 DNS | 50, 38, 39, 38, 41, 38, 38, 38, 38, 40 | 42.1 | 6.9 | 70ms |
| 핀란드 ftp.funet.fi | 247, 247, 274, 247, 248, 247, 247, 247, 247, 247 | 248.4 | 11.9 | 296ms |

이 PC에서 두 서버로 ping을 열 번씩 보내고 규격의 공식대로 계산한 값이다. 구글까지는 70ms, 핀란드까지는 296ms가 나온다. 재전송 시간을 1초로 고정했다면 구글 쪽에서는 손실 하나에 왕복 25번 분량을 놀고, 70ms로 고정했다면 핀란드 쪽에서는 멀쩡히 오고 있는 세그먼트를 전부 다시 보낸다. 하나의 값으로는 두 길을 다 감당할 수 없고, 그래서 연결마다 따로 잰다. 실제 동작에는 세 가지 규칙이 더 붙는다.

| 규칙 | 뜻 | 왜 |
|:-----|:---|:---|
| 초기값 1초 | 첫 표본이 오기 전에는 1초로 시작한다 | 아직 아무것도 모른다. 이 PC의 설정도 1000ms |
| 하한 | 계산값이 작아도 어느 밑으로는 안 내린다. Windows 300ms, Linux 200ms | 3절의 미뤄진 확인이 오기 전에 다시 보내면 안 된다 |
| 재전송한 것은 재지 않는다 | 다시 보낸 세그먼트의 확인으로는 왕복 시간을 갱신하지 않는다 | 원래 것의 확인인지 재전송의 확인인지 알 수 없다 |
| 실패마다 두 배 | 재전송도 실패하면 2초, 4초, 8초 | 길이 막혔을 때 더 밀어 넣지 않는다 |

구글까지의 계산값 70ms가 실제로는 하한 300ms로 올라간다. 확인을 미루는 3절의 규칙 때문에 확인이 200ms 늦게 올 수 있으니, 그보다 짧게 기다리면 정상인 세그먼트를 다시 보내게 된다. 두 배씩 늘리는 규칙은 23장의 혼잡 제어와 같은 발상이다. 확인이 안 오는 것은 길이 막혔다는 뜻일 수 있으므로 물러서야 하고, 이것을 여러 번 반복해도 답이 없으면 연결을 끊는다. Windows는 데이터 재전송을 다섯 번, Linux는 열다섯 번까지 한다.

### 빠른 재전송: 기다리지 않는 지름길

```text
Seq=1000 ─→ 받음 (ACK=1100)
Seq=1100 ─→ 손실
Seq=1200 ─→ 받음 (ACK=1100 중복 1)
Seq=1300 ─→ 받음 (ACK=1100 중복 2)
Seq=1400 ─→ 받음 (ACK=1100 중복 3)
              ↓ 빠른 재전송
Seq=1100 ─→ 재전송 → ACK=1500
```

타이머는 최후의 수단이다. 뒤의 세그먼트들이 도착하고 있다면 받는 쪽은 그때마다 "1100을 다오"를 반복하고, 보내는 쪽은 그 겹친 확인을 보고 1100이 사라졌음을 타이머보다 먼저 안다. 같은 확인이 **세 번** 겹치면 바로 다시 보내는 것이 빠른 재전송이고, 3절의 선택 확인이 있으면 1200~1499는 받았다는 것까지 알아 1100 하나만 보낸다. 재전송된 1100이 도착하면 받는 쪽은 1499까지 전부 갖게 되어 ACK=1500 하나로 한꺼번에 확인한다. 세 번인 이유는 한두 번은 순서가 잠깐 뒤바뀐 것일 수 있어서다. 01장에서 본 대로 다른 길로 간 조각은 늦게 도착할 수 있고, 그것까지 손실로 보면 멀쩡한 것을 다시 보내게 된다.

빠른 재전송 뒤에는 **빠른 회복**이 따른다. 타이머로 손실을 안 것은 길이 심하게 막혔다는 뜻이라 창을 처음부터 다시 키우지만, 겹친 확인으로 안 것은 뒤의 세그먼트들이 도착하고 있다는 뜻이라 길이 살아 있다. 그래서 창을 절반으로만 줄이고 이어 간다. 손실을 아는 방법이 둘인 것은 그 둘이 말해 주는 길의 상태가 다르기 때문이다.

## 6. 윈도우 크기와 흐름 제어

24장에서 창은 확인 없이 보내도 되는 양이고 창 ÷ 왕복 시간이 처리량의 상한이라고 했다. 여기서는 그 창이 어디서 나오고 얼마여야 하는지를 본다.

```text
받는 쪽 버퍼 4096B (# 사용 / - 여유)
#####-----  2000B 사용 → 창 2096
#########-  4000B 사용 → 창 96
##########  가득 참    → 창 0 (멈춤)
```

창의 값은 받는 쪽 버퍼의 빈자리다. 받은 세그먼트는 응용 프로그램이 읽어 갈 때까지 버퍼에 있고, 프로그램이 느리면 버퍼가 차며, 찬 만큼 창이 줄어 보내는 쪽이 늦춰진다. 버퍼를 넘긴 세그먼트는 버려지고 재전송을 부르므로, 미리 줄이는 것이 버리고 다시 받는 것보다 싸다.

```text
처음 (창=4)
[1][2][3][4][5][6][7][8]
 ├─ 보낼 수 있음 ─┤

1~2를 보낸 뒤
[*][*][3][4][5][6][7][8]
 확인 대기│보낼 수 있음│

ACK=3을 받은 뒤
[v][v][*][*][5][6][7][8]
      확인 대기│보낼 수 있음│
```

창은 확인이 올 때마다 오른쪽으로 밀린다. 1과 2를 보내고 확인을 기다리는 동안에도 3과 4를 보낼 수 있고, ACK=3이 오면 5와 6이 새로 창 안에 들어온다. 회선에 늘 창 크기만큼의 세그먼트가 떠 있게 되어 확인을 기다리는 시간이 숨겨진다.

{{< callout type="info" >}}
하나 보내고 확인을 기다렸다 다음을 보내는 방식(Stop-and-Wait)은 왕복 시간마다 세그먼트 하나다. 이 PC에서 핀란드 서버까지라면 0.25초에 1,460바이트, 초당 6KB다. 창이 있으면 왕복 시간 동안 창 크기만큼 보내므로, 창을 회선이 왕복 시간 동안 나를 수 있는 양만큼 키우면 회선이 쉬지 않는다. 그 양을 계산하는 것이 아래의 BDP다.
{{< /callout >}}

### 창 배율

창 필드는 16비트라 65,535바이트가 한도이고, 24장에서 본 대로 SYN에서 배율(2의 몇 제곱)을 교환해 최대 2¹⁴배, 1GB까지 넓힌다. 이 PC의 "Receive Window Auto-Tuning: normal"은 운영체제가 왕복 시간을 보며 창을 최대 16MB까지 스스로 키우는 설정이다.

### BDP: 창은 얼마여야 하는가

```text
BDP = 회선 속도(bit/s) × 왕복 시간(s)
```

| 이 PC에서 | 왕복 시간 | 1Gbps 회선의 BDP | 창이 64KB일 때의 상한 |
|:----------|:----------|:-----------------|:---------------------|
| 구글 DNS | 38ms | 4.75MB | 초당 1.7MB (14Mbps) |
| 핀란드 서버 | 251ms | 31.4MB | 초당 260KB (2Mbps) |

회선이 왕복 시간 동안 나를 수 있는 비트 수가 BDP다. 확인이 돌아오는 데 왕복 시간이 걸리므로, 그동안 회선을 채우려면 창이 적어도 BDP만큼이어야 한다. 이 PC의 1Gbps 회선으로 핀란드 서버에서 받으면 창이 31MB는 되어야 회선을 다 쓰는데, 배율 없는 64KB 창이면 초당 260KB, 2Mbps에 묶인다. 회선의 0.2%다. 1981년의 회선은 느리고 가까워서 64KB로 충분했고, 회선이 빨라지고 멀어지면서 창 배율이 필요해졌다. 이 PC의 자동 조절 상한 16MB로도 핀란드까지는 초당 64MB, 510Mbps가 한계라 1Gbps를 다 쓰지는 못한다. 멀리 있는 서버에서 큰 파일이 회선 속도만큼 안 내려오는 첫 번째 이유가 이 계산이고, 그다음 이유가 23장의 혼잡 제어다. 물론 실제 병목은 대개 상대 서버와 중간 회선 쪽에 먼저 있다.

Wireshark의 필터다. 이 장의 재전송, 겹친 확인, 순서 뒤바뀜, 창 0이 캡처에서 그대로 표시된다.

```bash
# Linux: 버퍼와 창 배율
sysctl net.core.rmem_max

```

```bash
# Linux: 연결마다의 실제 값
ss -ti
# wscale:7,7  cwnd:10  rtt:15.2/7.6  rto:204

# Windows: 설정값
netsh int tcp show global
Get-NetTCPSetting -SettingName Internet
```

| 지표 | 뜻 | 이 장의 어디 |
|:-----|:---|:------------|
| wscale | 보내는 쪽과 받는 쪽의 창 배율 | 6절 |
| cwnd | 혼잡 창. 길의 사정으로 정한 창 | 23장 |
| rtt | 평균 왕복 시간과 흔들림 (ms) | 5절의 SRTT, RTTVAR |
| rto | 지금의 재전송 시간 (ms) | 5절 |

Linux의 `ss -ti`는 연결마다 5절과 6절의 값을 그대로 보여 준다. 예시의 rtt 15.2/7.6, rto 204는 SRTT 15.2ms에 흔들림 7.6ms, 그래서 RTO가 하한 200ms 근처인 연결이다. 6절의 16MB는 Windows에서 자동 조절 수준을 normal로 둘 때의 상한이고, Linux에서는 위의 sysctl 값이 그 상한이다.

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 두 카운터 | 방향마다 일련번호가 따로 | 연결은 전이중이다 |
| 얹어 보내기 | 확인은 반대 방향 세그먼트에 실린다 | 빈 확인을 따로 만들 이유가 없다 |
| 바이트 번호 | 세그먼트가 아니라 바이트 | 다시 자를 수 있어야 한다 |
| SYN, FIN은 1 | 순수 ACK는 0 | 재전송할 것만 번호가 필요하다 |
| 누적 확인 | 다음에 기대하는 번호 | 확인 하나쯤 잃어도 된다 |
| 미뤄진 확인 | 두 번째 세그먼트나 200ms까지 | 확인도 회선을 쓴다 |
| Nagle과의 정체 | 둘 다 기다려 200ms | 절약 둘이 부딪힌다. TCP_NODELAY |
| 선택 확인 | 구멍을 알린다 | 누적은 여기까지만 말한다 |
| RTO | SRTT + 4 × RTTVAR | 길마다 다르니 재어서 정한다 |
| 이 PC의 값 | 구글 70ms, 핀란드 296ms | 하나의 값으로는 두 길을 못 감당한다 |
| 하한과 초기값 | 300ms, 1초 | 미뤄진 확인보다 짧으면 안 된다 |
| 재전송은 안 잰다 | Karn의 규칙 | 어느 것의 확인인지 모른다 |
| 빠른 재전송 | 같은 확인 세 번 | 뒤가 오고 있으면 타이머를 기다릴 이유가 없다 |
| 빠른 회복 | 창을 절반으로만 | 길이 살아 있다는 증거가 있다 |
| 창 | 받는 쪽 버퍼의 빈자리 | 넘겨서 버리는 것보다 미리 줄이는 것이 싸다 |
| BDP | 회선 속도 × 왕복 시간 | 왕복 동안 회선을 채울 양 |
| 핀란드 31MB | 64KB로는 0.2% | 창 배율이 필요해진 이유 |

{{< callout type="info" >}}
**용어 정리**
- **일련번호 / 확인 응답 번호**: 이 세그먼트 첫 바이트의 번호 / 다음에 기대하는 바이트의 번호
- **얹어 보내기 (piggyback)**: 확인 응답을 데이터 세그먼트에 실어 보내는 것
- **누적 확인 / 선택 확인 (SACK)**: 여기까지 받았다 / 이 구간도 받았다
- **미뤄진 확인 (delayed ACK)**: 두 번째 세그먼트나 시간 제한까지 확인을 미루는 것
- **Nagle 알고리즘**: 확인이 안 온 동안 작은 조각을 모아 보내는 규칙. TCP_NODELAY로 끈다
- **RTT / SRTT / RTTVAR**: 왕복 시간 / 그 가중 평균 / 흔들리는 폭
- **RTO**: 재전송 시간. SRTT + 4 × RTTVAR, 하한과 초기값이 있다
- **Karn의 규칙**: 재전송한 세그먼트로는 왕복 시간을 재지 않는다
- **빠른 재전송 / 빠른 회복**: 같은 확인 세 번에 바로 재전송 / 창을 절반으로만 줄이고 계속
- **창 / 슬라이딩 윈도우**: 확인 없이 보내도 되는 양 / 확인마다 창을 밀며 연속 전송
- **BDP**: 회선 속도 × 왕복 시간. 창의 적정 크기
