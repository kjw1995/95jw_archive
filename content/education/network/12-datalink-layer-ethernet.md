[11. 리피터와 허브의 구조](../11-repeater-hub)에서 한 전선을 여럿이 쓰는 규칙(CSMA/CD)과 그 규칙이 정한 숫자(64바이트)를 봤다. 이 장은 그 규칙이 속한 층, 데이터 링크 계층과 그 대표 규칙인 이더넷을 본다. 원리는 셋이다. 첫째, **2층은 "옆 기계에게 정확히 건네기"만 책임진다.** 다른 망으로 가는 것은 3층의 일이고, 이 층은 같은 링크 안에서 비트열을 프레임으로 묶고, 주소를 붙이고, 깨졌는지 확인하고, 차례를 정한다. 둘째, **프레임의 모든 필드에는 그 자리에 있는 이유가 있다.** 프리앰블이 앞에, 목적지 주소가 출발지보다 먼저, FCS가 맨 뒤에 오는 것은 우연이 아니다. 셋째, **이더넷이 이긴 이유는 단순함과 변하지 않는 프레임이다.** 10Mbps에서 400Gbps로 오는 동안 접근 규칙은 바뀌었지만 프레임의 모양은 1982년 그대로다. 이 장의 수치는 계산과 필자 PC의 랜 카드 통계에서 나왔다.

## 1. 데이터 링크 계층: 옆 기계에게 정확히

```
  7  응용 계층
  6  표현 계층
  5  세션 계층
  4  전송 계층
  3  네트워크 계층
  2  데이터 링크 계층  ← 여기
  1  물리 계층
```

| 기능 | 하는 일 | 왜 필요한가 |
|:-----|:--------|:-----------|
| 프레이밍 | 비트열을 시작과 끝이 있는 덩어리로 | 1층의 신호는 끝없는 비트의 흐름이라 경계가 없다 |
| 주소 | MAC 주소로 보내는 쪽과 받는 쪽을 적는다 | 한 링크에 기계가 여럿이다 |
| 오류 검출 | FCS로 프레임이 깨졌는지 | 전선의 잡음은 비트를 뒤집는다 |
| 매체 접근 제어 | 누가 언제 보낼 수 있나 | 한 전선을 나눠 쓰던 시절의 규칙 |
| 흐름 제어 | 받는 쪽이 넘치면 잠시 멈추라고 | 보내는 쪽이 더 빠를 수 있다 |

[07. OSI 모델과 TCP/IP 모델](../07-osi-tcpip-model)에서 2층의 질문은 "같은 망 안의 옆 기계에게 어떻게"였다. 1층이 넘겨주는 것은 끝없는 비트의 흐름이다. 어디서 한 조각이 시작되고 끝나는지, 누구 것인지, 도중에 깨졌는지를 그 흐름 자체는 말하지 않으므로 그 셋을 정하는 것이 이 층의 일이다. 범위는 **한 링크**다. 스위치로 이어진 한 LAN 안에서만 배달하고, 라우터 너머로 가는 것은 [17. 네트워크 계층의 역할](../17-network-layer-role)의 몫이다.

| 하위 층 | 맡는 것 | 왜 나눴나 |
|:--------|:--------|:----------|
| LLC | 위층의 어느 규칙에게 줄지, 흐름과 오류 제어 | 매체가 무엇이든 같다 |
| MAC | 주소, 프레임 형식, 매체 접근 규칙 | 이더넷과 Wi-Fi가 다른 부분 |

층이 둘로 나뉜 것은 매체마다 다른 부분과 같은 부분을 가르기 위해서다. 케이블(이더넷)과 전파(Wi-Fi)는 주소 형식은 같지만 차례를 정하는 규칙이 다르고, 그 다른 부분만 MAC에 모아 두었다. 실제로는 아래의 이더넷 II 프레임이 LLC 없이 위층 번호를 직접 담아서, LLC는 거의 쓰이지 않는 이름으로 남았다.

## 2. 이더넷

| 특징 | 값 | 비고 |
|:-----|:---|:-----|
| 표준 | IEEE 802.3 | 1983년. 원형은 1982년의 DIX 규격 |
| 주소 | 48비트 MAC | [09](../09-physical-layer-nic)장에서 본 카드의 주소 |
| 단위 | 프레임 | 64 ~ 1,518바이트 |
| 접근 규칙 | 반이중은 CSMA/CD, 전이중은 없음 | 11장 |
| 속도 | 10Mbps에서 400Gbps | [16](../16-ethernet-types-features)장 |

이더넷은 1973년 제록스 PARC의 밥 메트칼프가 만들었고, 이름은 19세기에 빛을 나른다고 믿었던 가상의 매질 "에테르"에서 왔다. 모두가 공유하는 매질 위에 프레임을 띄운다는 뜻이다. 1982년 DEC, 인텔, 제록스가 낸 규격(DIX)이 지금의 프레임 모양을 정했고, 이듬해 IEEE 802.3이 됐다. [03. LAN과 WAN](../03-lan-and-wan)에서 이더넷이 LAN의 유일한 기술이 된 이유를 "규칙은 두고 매체와 속도만 바꿨다"고 했는데, 바뀌지 않은 그 규칙이 3절의 프레임이다.

## 3. 이더넷 프레임: 자리마다 이유가 있다

```
┌────┬────┬────┬───┬──────┬────┐
│PRE │DST │SRC │TYP│ DATA │FCS │
└────┴────┴────┴───┴──────┴────┘
 8B   6B   6B   2B  46-1500B 4B
```

| 필드 | 크기 | 담는 것 | 왜 그 자리인가 |
|:-----|:-----|:--------|:--------------|
| 프리앰블 + SFD | 8B | 10101010이 7바이트, 마지막에 10101011 | 받는 쪽이 시계를 맞추고 "여기부터"를 알도록. 프레임 길이에는 안 센다 |
| 목적지 MAC | 6B | 받을 카드 | 맨 앞에 두어야 카드가 남의 것을 **빨리** 버린다 |
| 출발지 MAC | 6B | 보낸 카드 | 답장과 4절의 스위치 학습에 |
| 타입 | 2B | 안의 내용이 IPv4인지 ARP인지 | 뜯은 뒤 누구에게 줄지. [06](../06-network-protocol)장의 번호 |
| 데이터 | 46 ~ 1,500B | 위층의 패킷 | 하한은 11장, 상한은 [01](../01-network-basics)장 |
| FCS | 4B | CRC-32 | 보내면서 계산해 끝에 붙인다. [08](../08-encapsulation-decapsulation)장 |

프리앰블은 1층과 2층의 경계다. [09](../09-physical-layer-nic)장에서 받는 쪽은 신호의 전환으로 시계를 맞춘다고 했는데, 프레임 사이의 조용한 시간이 지나고 갑자기 데이터가 오면 첫 비트 몇 개를 놓칠 수 있다. 그래서 1과 0이 번갈아 나오는 7바이트를 먼저 보내 시계를 맞추게 하고, 마지막 바이트의 끝을 11로 바꿔 "다음 비트부터 프레임"이라고 알린다. 목적지 주소가 출발지보다 앞에 있는 것은 9장에서 본 대로 카드가 남의 프레임을 최대한 빨리 버리기 위해서다. 6바이트만 읽으면 내 것인지 안다.

| EtherType | 안의 내용 |
|:----------|:----------|
| 0x0800 | IPv4 |
| 0x0806 | ARP |
| 0x86DD | IPv6 |
| 0x8100 | VLAN 태그가 붙어 있다(802.1Q). 실제 타입은 4바이트 뒤에 |

타입 값이 전부 0x0600(1536) 이상인 데는 이유가 있다. 1982년의 이더넷 II는 이 자리에 타입을 적었지만 1983년의 IEEE 802.3은 데이터의 **길이**를 적기로 했다. 두 형식을 같은 선에서 구별하려면 값으로 가려야 했고, 데이터가 최대 1,500바이트이니 1,536 이상은 길이일 수 없다. 그래서 1,536 이상이면 타입, 미만이면 길이로 읽는다. 오늘날 흐르는 프레임은 거의 전부 타입을 쓰는 이더넷 II다. 길이는 안의 IP 헤더가 이미 알고 있어서 굳이 적을 필요가 없었다. [05](../05-office-lan-configuration)장의 VLAN은 이 자리에 0x8100을 적고 4바이트 태그를 끼워 넣는 방식으로 프레임 모양을 깨지 않고 얹혔다.

{{< callout type="info" >}}
프레임의 최소 크기는 64바이트(헤더 14 + 데이터 46 + FCS 4)다. 데이터가 46바이트가 안 되면 0으로 채우고, 받는 쪽은 IP 헤더의 길이를 보고 채운 부분을 버린다. 이 하한이 [11](../11-repeater-hub)장에서 본 충돌 감지 시간이고, 1Gbps에서 64바이트 프레임은 512ns 만에 지나간다.
{{< /callout >}}

프레임에는 값이 있다. 1,500바이트를 실어 보내면 헤더와 FCS 18바이트, 프리앰블 8바이트, 프레임 사이의 빈 시간(12바이트 분량)이 붙어 회선의 97.5%가 데이터다. 그러나 46바이트만 실으면 54.8%로 떨어진다. 1Gbps 회선은 큰 프레임이면 초당 8만 개, 작은 프레임이면 149만 개를 나르고, 9장에서 랜 카드가 CPU 대신 일을 떠맡게 된 이유가 이 숫자다.

## 4. FCS: 깨졌는지 어떻게 아나

```
보내는 쪽  프레임 전체로 CRC-32 계산
           ─▶ 끝에 4바이트로 붙인다
받는 쪽    같은 계산 ─▶ 다르면 버린다
```

| 입력 | CRC-32 |
|:-----|:-------|
| `Hello, Ethernet` | `77C0FD37` |
| 첫 바이트의 비트 하나를 뒤집음 | `CE3B26DF` |
| 첫 두 글자의 순서를 바꿈 | `7995B926` |
| 연속 32비트를 전부 뒤집음 | `F3EAC4A7` |

FCS는 프레임의 모든 비트를 하나의 다항식으로 나눈 나머지(CRC-32)다. 표는 필자의 PC에서 자바의 `CRC32`로 계산한 것인데, 비트 하나만 바뀌어도 값이 전혀 다르고, 두 글자의 순서만 바꿔도 다르다. 단순한 합계(체크섬)는 순서 바뀜을 잡지 못하지만 CRC는 잡는다. 수학적으로 비트 하나나 둘이 뒤집힌 것, 홀수 개가 뒤집힌 것, 연속 32비트 안의 어떤 오류든 반드시 잡히고, 그보다 긴 무작위 손상도 43억분의 1 확률로만 놓친다. 전선의 잡음이 만드는 오류는 짧게 몰려 오는 성질이 있어 이 성질이 딱 맞는다.

값이 다르면 프레임은 그 자리에서 조용히 버려진다. 8장에서 본 대로 2층은 다시 보내 달라고 하지 않는다. 잃어버린 것을 알아채고 채우는 일은 위층 TCP의 몫이다. 이 PC의 랜 카드는 누적 1억 3천만 프레임을 받는 동안 오류를 0개로 기록했다. 좋은 케이블에서는 FCS가 걸러 낼 것이 거의 없고, 오류가 세기 시작하면 케이블이나 포트를 의심하라는 뜻이다.

## 5. CSMA/CD: 한 전선을 나눠 쓰던 규칙

```
 ┌──────────────┐
 │ 전송할 데이터 │
 └──────┬───────┘
        ▼
   매체가 비었는가?
    │          │
    No         Yes
    │          │
   대기      전송 시작
              │
              ▼
         충돌 감지?
          │       │
         Yes      No
          │       │
       JAM+대기  완료
```

| 단계 | 하는 일 |
|:-----|:--------|
| CS | 전선에 신호가 있으면 기다린다 |
| MA | 비었으면 보낸다. 순서표는 없다 |
| CD | 보내는 동안 부딪히면 즉시 멈추고 JAM 신호를 낸다 |
| 백오프 | n번째 충돌이면 0 ~ 2ⁿ − 1 슬롯 중 무작위로 기다렸다 다시. 16번이면 포기 |

규칙 자체는 11장에서 봤다. 여기서 볼 것은 이 규칙이 프레임에 남긴 흔적이다. 슬롯 하나가 512비트, 10Mbps에서 51.2μs이고, 그 시간 안에 충돌이 돌아와야 하므로 프레임은 최소 512비트(64바이트)여야 했다. 백오프의 대기 단위도 이 슬롯이다. 전이중 스위치 환경에서는 이 규칙이 통째로 꺼지지만 64바이트 하한은 규격에 남아 있고, 3절의 채움(패딩)이 그 흔적이다. 전파에서는 부딪힌 것을 보내면서 들을 수 없어(자기 신호가 남의 신호를 덮는다) 충돌을 **피하는** 쪽으로 바뀐 규칙(CSMA/CA)을 쓰며, 그것은 [35. 무선 랜의 구조](../35-wireless-lan-structure)에서 본다.

## 6. 듀플렉스

| 항목 | 반이중 | 전이중 | 왜 |
|:-----|:-------|:-------|:---|
| 송수신 | 번갈아 | 동시에 | 보내는 쌍과 받는 쌍이 따로인가 |
| 충돌 | 있다 | 없다 | 내 선에는 나만 보낸다 |
| CSMA/CD | 켜짐 | 꺼짐 | 다툴 상대가 없다 |
| 실효 대역폭 | 나눠 쓴다 | 양방향 각각 온전히 | 1Gbps 전이중은 합쳐 2Gbps |
| 환경 | 허브 | 스위치 | 11장 |

[10. 케이블의 종류와 구조](../10-cable-types-structure)에서 UTP는 100Mbps까지 1-2번 쌍으로 보내고 3-6번 쌍으로 받는다고 했다. 선이 따로이니 동시에 오갈 수 있고, 스위치는 그 선을 합치지 않으므로 전이중이 된다. 기가비트는 네 쌍을 모두 양방향으로 쓰는데, 한 쌍에서 내 신호와 상대 신호가 겹치니 내가 보낸 신호를 알고 있다가 받은 신호에서 빼는 에코 제거로 양쪽을 갈라낸다. 링크가 어느 쪽으로 동작할지는 케이블을 꽂을 때의 자동 협상이 정하고, 이 PC의 유선 링크는 9장에서 본 대로 1Gbps 전이중으로 잡혀 있다.

{{< callout type="warning" >}}
한쪽은 전이중, 다른 쪽은 반이중으로 잡히는 **듀플렉스 미스매치**가 있다. 한쪽을 수동으로 고정하면 상대는 협상할 상대가 없어 10/100Mbps에서는 반이중으로 떨어지기 때문에 생긴다. 반이중 쪽은 상대가 동시에 보내는 것을 충돌로 보고 멈추고, 전이중 쪽은 그 멈춘 프레임을 깨진 것으로 받는다. 링크는 살아 있는데 속도만 이상하게 느린 전형적인 증상이고, 해법은 양쪽을 모두 자동으로 두는 것이다. [15. 데이터가 케이블에서 충돌하지 않는 구조](../15-collision-free-structure)에서 다시 본다.
{{< /callout >}}

## 7. 프레임 송수신 과정

```
상위 계층 데이터
   ↓  (IP 헤더 추가 → 패킷)
   ↓  (이더넷 헤더 + FCS 추가)
  프레임
   ↓  (비트열 → 전기 신호)
  케이블
```

```
케이블 (전기 신호)
   ↓
 프레임 복원 (프리앰블로 동기)
   ↓  목적지 MAC 확인
   ↓  (내 것, 브로드캐스트, 멀티캐스트)
   ↓  FCS 검증
 상위 계층으로 전달 (타입을 보고)
```

보낼 때는 [08](../08-encapsulation-decapsulation)장의 캡슐화 마지막 단계다. IP 패킷 앞에 목적지와 출발지 MAC, 타입을 붙이고 뒤에 FCS를 계산해 붙인 뒤, 카드가 프리앰블을 앞세워 신호로 내보낸다. 받을 때 카드는 프리앰블로 시계를 맞춰 프레임을 조립하고, 목적지 MAC이 나이거나 브로드캐스트이거나 내가 신청한 멀티캐스트일 때만 남기고 나머지는 버린다. FCS가 맞으면 타입을 보고 IP나 ARP에게 올린다. 목적지 확인이 FCS 검증보다 먼저인 것은 남의 프레임에 계산을 쓰지 않으려는 것이다. 이 판단이 카드 안에서 끝나는 이유는 9장에서 봤고, 이 프레임의 주소가 어떻게 생겼는지는 [13. MAC 주소의 구조](../13-mac-address-structure)에서, 스위치가 그 주소로 무엇을 하는지는 [14. 스위치의 구조](../14-switch-structure)에서 본다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 2층의 범위 | 한 링크 안의 옆 기계 | 다른 망은 3층의 일 |
| 프레이밍 | 비트 흐름에 경계를 | 1층의 신호에는 시작과 끝이 없다 |
| LLC와 MAC | 같은 부분과 매체마다 다른 부분 | 이더넷과 Wi-Fi는 접근 규칙만 다르다 |
| 이더넷 | 1982년의 프레임이 그대로 | 규칙은 두고 매체와 속도만 바꿨다 |
| 프리앰블 | 시계 맞추기와 시작 표시 | 조용하다 갑자기 오면 첫 비트를 놓친다 |
| 목적지가 먼저 | 6바이트만 읽고 버린다 | 남의 프레임에 시간을 쓰지 않는다 |
| 타입 | 1,536 이상이면 타입 | 802.3의 길이 필드와 한 선에서 구별하려고 |
| 46 ~ 1,500 | 하한은 충돌 감지, 상한은 공평한 공유 | 11장과 1장 |
| 효율 | 큰 프레임 97.5%, 작은 프레임 54.8% | 봉투와 빈 시간은 크기와 무관하다 |
| FCS | CRC-32 | 비트 하나, 순서 바뀜, 32비트 연속 오류를 전부 잡는다 |
| 버릴 뿐 안 묻는다 | 재전송은 TCP의 일 | 층의 독립성 |
| CSMA/CD | 반이중의 규칙 | 전이중에서는 꺼지고 64바이트 하한만 남았다 |
| 듀플렉스 미스매치 | 한쪽 고정이 원인 | 협상 상대가 없으면 반이중으로 떨어진다 |

{{< callout type="info" >}}
**용어 정리**
- **이더넷 (Ethernet)**: IEEE 802.3으로 정의된 LAN의 데이터 링크 규칙. 이름은 빛의 매질이라 믿었던 에테르에서
- **프레임 (Frame)**: 2층의 데이터 단위. 헤더 14바이트, 데이터 46~1,500바이트, FCS 4바이트
- **프리앰블 / SFD**: 시계를 맞추는 7바이트 / 프레임의 시작을 알리는 1바이트
- **EtherType**: 안의 내용이 어느 상위 규칙인지 적는 2바이트. IPv4는 0x0800
- **FCS (Frame Check Sequence)**: CRC-32로 계산한 4바이트 오류 검출 코드
- **CSMA/CD**: 반이중 이더넷의 매체 접근 규칙. 듣고, 보내고, 부딪히면 물러난다
- **전이중 / 반이중**: 동시에 오가는 것 / 번갈아 쓰는 것
- **듀플렉스 미스매치**: 양 끝의 듀플렉스 설정이 어긋난 상태. 느리고 오류가 난다
{{< /callout >}}
