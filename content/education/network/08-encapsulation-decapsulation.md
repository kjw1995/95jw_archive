[07. OSI 모델과 TCP/IP 모델](../07-osi-tcpip-model)에서 세그먼트, 패킷, 프레임은 같은 데이터에 봉투가 몇 겹 붙었는지의 차이라고 했다. 이 장은 그 봉투를 붙이고 뜯는 과정과 봉투에 무엇이 적히는지를 본다. 원리는 셋이다. 첫째, **봉투는 층마다 한 겹이고, 각 층은 자기 봉투만 읽고 쓴다.** 헤더의 필드 하나하나는 그 층이 답해야 하는 질문의 답이고, 그래서 어느 필드가 왜 있는지는 7장의 질문 표에서 유도된다. 둘째, **봉투에도 값이 있다.** 헤더는 회선을 차지하고, 프레임 하나의 크기에는 한도(MTU)가 있으며, 그 한도가 TCP가 한 번에 보내는 양(MSS)과 단편화를 결정한다. 셋째, **봉투는 겹칠 수 있다.** 패킷을 통째로 다른 봉투에 넣으면 터널이 되고, 그 봉투를 암호화하면 VPN이 된다. 이 장의 실측은 필자의 PC에서 `ping`으로 TTL과 MTU를 확인한 것이다.

## 1. 캡슐화: 층마다 봉투 한 겹

| 구성 | 위치 | 담는 것 | 왜 |
|:-----|:-----|:--------|:---|
| 헤더 | 앞 | 주소, 다음 층의 상대, 순서, 길이 | 뜯는 쪽이 제일 먼저 읽어야 하는 정보라 앞에 둔다 |
| 페이로드 | 가운데 | 위층이 넘겨준 것 전부 | 이 층은 안을 보지 않는다 |
| 트레일러 | 뒤 | 오류 검출 코드(FCS) | 앞에서부터 계산하며 흘려보내고 끝에 값을 붙인다 |

```
응용     [      데이터      ]
             ▼ TCP 헤더
전송     [TCP][   데이터    ] 세그먼트
             ▼ IP 헤더
네트워크 [IP][TCP][ 데이터  ] 패킷
             ▼ 이더넷 헤더, FCS
링크 [ETH][IP][TCP][데이터][FCS] 프레임
             ▼ 신호
물리  0101 1101 ...  비트
```

보내는 쪽은 위층에서 아래층으로 내려가며 층마다 자기 헤더를 **앞에** 붙인다. 이것이 캡슐화다. 각 층은 위층이 넘겨준 것을 열어 보지 않고 통째로 페이로드로 삼는다. TCP는 HTTP 요청이 무슨 내용인지 모르고, IP는 그 안이 TCP인지 UDP인지 헤더의 번호 하나로만 안다. 그래서 층을 갈아 끼울 수 있다는 7장의 독립성이 성립한다. [01. 네트워크의 구조](../01-network-basics)에서 회선을 나눠 쓰려면 조각마다 봉투가 필요하다고 했는데, 그 봉투가 실제로는 한 겹이 아니라 세 겹이다.

트레일러가 뒤에 붙는 이유는 계산 순서 때문이다. 오류 검출 코드는 프레임의 처음부터 끝까지를 입력으로 계산하므로, 앞부분을 전선에 내보내면서 동시에 계산하고 마지막에 결과를 덧붙이는 것이 가장 빠르다. 이더넷의 FCS가 그것이고 IP와 TCP의 헤더 체크섬은 헤더 안에 있다.

## 2. 봉투에 적는 것: 계층별 헤더

헤더의 필드는 그 층이 답하는 질문의 답이다. 7장의 표를 그대로 옮기면 전송 층은 "어느 프로그램에게, 믿을 수 있게", 네트워크 층은 "어느 망의 어느 기계에게", 데이터 링크 층은 "옆 기계에게 어떻게"였다.

### TCP 헤더: 어느 프로그램에게, 믿을 수 있게

| 필드 | 크기 | 답하는 것 |
|:-----|:-----|:----------|
| 출발지 포트, 목적지 포트 | 각 16비트 | 어느 프로그램이 보내고 어느 프로그램이 받나 |
| 순서 번호 | 32비트 | 이 조각이 전체의 몇 번째 바이트부터인가 |
| 확인 응답 번호 | 32비트 | 여기까지 받았으니 다음은 이것을 달라 |
| 제어 비트 | 8개 | SYN, ACK, FIN, RST 같은 연결 상태의 신호 |
| 윈도우 크기 | 16비트 | 내가 더 받을 수 있는 양. 흐름 제어 |
| 체크섬 | 16비트 | 헤더와 데이터가 깨지지 않았나 |

20바이트가 기본이다. 순서 번호와 확인 응답 번호가 32비트나 되는 것은 바이트 단위로 세기 때문이고, 그 번호로 [01](../01-network-basics)장에서 본 순서 뒤바뀜과 손실을 되돌린다. 자세한 동작은 [24. TCP의 구조](../24-tcp-structure)와 [25. 일련번호와 확인 응답 번호의 구조](../25-sequence-ack-number)에서 본다.

### IP 헤더: 어느 망의 어느 기계에게

| 필드 | 크기 | 답하는 것 |
|:-----|:-----|:----------|
| 버전 | 4비트 | IPv4는 4, IPv6는 6 |
| 전체 길이 | 16비트 | 이 패킷이 몇 바이트인가. 그래서 IPv4 패킷은 65,535바이트가 한도 |
| 식별, 플래그, 단편 오프셋 | 16 + 3 + 13비트 | 5절의 단편화. 조각들이 어느 패킷의 몇 번째인가 |
| TTL | 8비트 | 앞으로 몇 개의 라우터를 더 지날 수 있나 |
| 프로토콜 | 8비트 | 안의 내용을 TCP(6), UDP(17), ICMP(1) 중 누구에게 줄까 |
| 헤더 체크섬 | 16비트 | 헤더가 깨지지 않았나 |
| 출발지 IP, 목적지 IP | 각 32비트 | 어느 기계에서 어느 기계로 |

TTL(Time To Live)은 이름과 달리 시간이 아니라 **남은 홉 수**다. 라우터를 지날 때마다 1씩 줄고 0이 되면 버려진다. 경로 설정이 잘못되어 패킷이 라우터 사이를 맴돌 때 영원히 돌지 않게 하려는 장치인데, 필자의 PC에서 `ping`으로 그 값을 직접 볼 수 있다.

| `ping` 대상 | 응답의 TTL | 읽는 법 |
|:------------|-----------:|:--------|
| 127.0.0.1 | 128 | Windows의 시작값 그대로. 라우터를 하나도 안 지났다 |
| 기본 게이트웨이 | 255 | 라우터의 시작값 255 그대로. 바로 옆이다 |
| 8.8.8.8 | 113 | 시작값 128에서 15개의 라우터를 지나왔다 |
| 핀란드의 서버 | 50 | 리눅스의 시작값 64에서 14개를 지나왔다 |

운영체제마다 시작값이 다르고(Windows 128, 리눅스 64, 네트워크 장비 255) 응답이 돌아오면서 라우터마다 하나씩 깎였으니, 응답의 TTL은 상대가 몇 홉 떨어져 있는지를 말해 준다. 라우터가 TTL을 줄이는 과정은 [22. 라우터의 구조와 라우팅](../22-router-structure)에서, 주소 필드는 [18. IP 주소의 구조](../18-ip-address-structure)에서 본다.

### 이더넷 헤더: 옆 기계에게

| 필드 | 크기 | 답하는 것 |
|:-----|:-----|:----------|
| 목적지 MAC | 6바이트 | 같은 망 안의 어느 랜 카드에게 |
| 출발지 MAC | 6바이트 | 어느 랜 카드가 보냈나 |
| 타입 | 2바이트 | 안의 내용을 IPv4(0x0800), ARP(0x0806), IPv6(0x86DD) 중 누구에게 |
| FCS (트레일러) | 4바이트 | 프레임이 전선에서 깨지지 않았나 |

이더넷 헤더는 14바이트, 뒤의 FCS까지 18바이트다. 목적지 MAC이 **다음 라우터의 것**이라는 점이 IP 헤더와 다르다. IP 헤더의 목적지는 최종 상대라서 끝까지 바뀌지 않지만, 이더넷 헤더의 목적지는 "이 망 안에서 다음으로 건네줄 기계"라서 라우터를 지날 때마다 새로 붙는다. 그래서 라우터는 프레임을 뜯어 IP 패킷을 꺼낸 뒤 다음 망에 맞는 새 프레임에 다시 담는다. 세 헤더가 각각 "다음 층의 누구에게"를 가리키는 번호(포트, 프로토콜 번호, 타입)를 가진 이유는 [06](../06-network-protocol)장에서 봤고, 프레임의 형식은 [12. 데이터 링크 계층의 역할과 이더넷](../12-datalink-layer-ethernet)에서 본다.

## 3. 역캡슐화: 한 겹씩 뜯으며 검사한다

```
물리     0101...       비트 → 프레임
링크  [ETH][IP][TCP][데이터][FCS]
           ├ FCS 검사, 내 MAC인가
           ▼ 뜯는다
네트워크 [IP][TCP][데이터]
           ├ 내 IP인가, 체크섬
           ▼ 뜯는다
전송     [TCP][데이터]
           ├ 어느 포트인가, 체크섬
           ▼ 뜯는다
응용     [데이터]
```

| 층 | 검사 | 실패하면 |
|:---|:-----|:---------|
| 데이터 링크 | FCS가 맞나, 목적지 MAC이 나인가 | 조용히 버린다. 재전송은 위층의 일 |
| 네트워크 | 목적지 IP가 나인가, 헤더 체크섬 | 내 것이 아니면 라우터는 다음으로 넘기고, 종단은 버린다 |
| 전송 | 그 포트에 프로그램이 있나, 체크섬 | 없으면 버리거나 "그런 포트 없음"(RST, ICMP)을 돌려준다 |

받는 쪽은 반대로 아래층부터 한 겹씩 뜯는다. 겉봉투부터 열어야 안의 봉투가 나오니 순서는 정해져 있다. 층마다 두 가지를 확인한다. **내 것인가**(주소)와 **깨지지 않았나**(검증 코드). 깨진 프레임은 데이터 링크 층이 조용히 버리고 위층에 알리지 않는다. 손실을 알아채고 다시 보내는 것은 TCP의 순서 번호가 할 일이며, 아래층이 위층을 대신해 재전송하지 않는 것도 층의 독립성이다.

7장의 장비 표가 여기서 그림이 된다. 스위치는 첫 봉투(프레임)만 읽고 넘기고, 라우터는 두 번째 봉투(IP)까지 뜯어 보고 새 첫 봉투에 담아 넘기며, 최종 상대만 세 번째 봉투까지 뜯어 프로그램에게 준다.

## 4. 웹 요청 한 번의 전체 흐름

```
[클라이언트] 192.168.1.10
[서버]       10.0.0.5

응용     HTTP GET /index.html
           ▼ 캡슐화
전송     [TCP: 50000→80]
           ▼
네트워크 [IP: 192.168.1.10→10.0.0.5]
           ▼
링크    [ETH: AA→BB][...][FCS]
           ▼
물리     101011001...

         ═══ 네트워크 전송 ═══

물리     신호 수신
           ▼ 역캡슐화
링크    MAC 확인 → 헤더 제거
           ▼
네트워크 IP 확인 → 헤더 제거
           ▼
전송     포트 80 → 웹 서버로 전달
           ▼
응용     HTTP 요청 처리
```

브라우저가 만든 HTTP 요청이 서버의 웹 서버 프로그램에 닿기까지 봉투가 세 번 붙고 세 번 뜯긴다. 그림에 보이지 않는 준비 단계가 둘 있다. IP 주소 10.0.0.5는 이름을 DNS로 풀어 얻은 것이고([30](../30-dns-server-structure)장), 이더넷 헤더의 목적지 MAC `BB`는 "이 IP 주소의 MAC은 누구?"라고 ARP로 물어 얻은 것이다([13](../13-mac-address-structure)장). 서버가 다른 망에 있다면 `BB`는 서버가 아니라 기본 게이트웨이의 MAC이고, 라우터가 3절에서 본 대로 프레임을 갈아 끼우며 넘겨준다.

## 5. 봉투의 값: MTU, MSS, 단편화

| 용어 | 뜻 | 값 |
|:-----|:---|:---|
| MTU | 한 프레임에 실을 수 있는 IP 패킷의 최대 크기 | 이더넷 1,500바이트 |
| MSS | TCP 세그먼트 하나에 실을 수 있는 데이터의 최대 크기 | 1,500 − 20(IP) − 20(TCP) = 1,460바이트 |
| 단편화 | MTU보다 큰 패킷을 여러 조각으로 나누는 것 | IP 헤더의 식별, 플래그, 오프셋 필드로 |

```
응용     [  1460 데이터  ]
전송     [20][  1460  ]        = 1480
네트워크 [20][20][ 1460 ]   = 1500 MTU
링크  [14][20][20][1460][4]    = 1518
      ETH  IP  TCP       FCS
```

봉투는 공짜가 아니다. 1장에서 처리량이 대역폭에 못 미치는 이유로 헤더를 들었는데, 이제 계산할 수 있다. 데이터 1,460바이트에 헤더 54바이트가 붙으니 회선의 3.6%는 봉투다. 데이터가 1바이트뿐인 패킷도 봉투는 그대로 54바이트라, 작은 패킷을 많이 보내는 통신은 회선의 대부분을 봉투로 쓴다. 패킷 하나의 한도가 1,500바이트인 이유는 1장에서 봤고, TCP는 그 한도에서 자기 헤더와 IP 헤더를 뺀 1,460바이트씩 잘라 보낸다. 그것이 MSS이고, 연결을 맺을 때 서로의 MSS를 알려 준다.

한도를 넘는 패킷을 만나면 IPv4의 라우터는 그것을 조각내어(단편화) 보내고 최종 상대가 다시 맞춘다. 조각마다 헤더가 다시 붙어 낭비이고 하나만 잃어도 전체를 잃으므로, 요즘은 IP 헤더의 DF(Don't Fragment) 플래그를 켜서 "자르지 말고 못 가면 알려 달라"고 한 뒤 알려 온 크기에 맞춰 보내는 경로 MTU 탐색을 쓴다. IPv6는 아예 라우터의 단편화를 없앴다. 필자의 PC에서 그 한도를 직접 확인할 수 있다.

```
> ping -f -l 1472 8.8.8.8
Reply from 8.8.8.8: bytes=1472 ...
  (1472 + ICMP 8 + IP 20 = 1500)

> ping -f -l 1473 8.8.8.8
Packet needs to be fragmented
but DF set.
```

`-f`가 DF 플래그이고 `-l`이 데이터 크기다. 1,472바이트까지는 헤더를 합쳐 정확히 1,500이라 통과하고, 1바이트를 더하면 자르지 말라는 표시 때문에 보내지 못한다. MTU 1,500이라는 숫자가 실제로 이 PC의 회선을 지키고 있다.

## 6. 봉투를 겹치기: VPN

```
원본 패킷
[IP][TCP][데이터]

터널에 넣은 뒤
[새 IP][VPN 헤더][암호화된 원본 패킷]
```

패킷을 통째로 다른 패킷의 페이로드에 넣으면 터널이 된다. 바깥 봉투의 주소는 터널의 양 끝(예를 들어 본사와 지사의 VPN 장비)이고, 안의 봉투는 원래의 주소 그대로다. 중간의 인터넷은 바깥 봉투만 보고 나르므로 안의 사설 주소가 인터넷을 건널 수 있고, 안의 봉투를 암호화하면 중간에서 열어 볼 수도 없다. 이것이 [03. LAN과 WAN](../03-lan-and-wan)에서 본 인터넷 VPN이고, [05. 회사에서의 LAN 구성](../05-office-lan-configuration)의 DMZ에 VPN 서버가 서 있던 이유다.

| 유형 | 규칙 | 쓰임 | 비고 |
|:-----|:-----|:-----|:-----|
| 거점 간 | IPsec | 본사와 지사의 망을 통째로 잇는다 | 양쪽 라우터가 터널의 끝 |
| 원격 접속 | SSL/TLS VPN, WireGuard | 재택근무자의 PC 한 대를 사내망에 | 443 포트를 써서 어디서든 뚫린다 |
| MPLS VPN | 통신사의 레이블 스위칭 | 대기업의 폐쇄망 | 암호화가 아니라 통신사 망 안에서의 **분리**다 |

| IPsec | 하는 일 |
|:------|:--------|
| AH | 위조되지 않았음을 보증한다. 암호화는 없다 |
| ESP | 암호화까지 한다. 실제로 쓰이는 쪽 |
| 전송 모드 | 페이로드만 암호화. 원래 IP 헤더는 그대로. 기계와 기계 사이 |
| 터널 모드 | 원본 패킷 전체를 암호화하고 새 IP 헤더를 붙인다. 망과 망 사이 |

거점 간 VPN이 터널 모드인 이유는 안의 주소를 숨기고 사설 주소를 그대로 쓰기 위해서다. MPLS VPN을 같은 표에 두는 것은 오해를 부르기 쉬운데, 그것은 봉투를 암호화하는 기술이 아니라 통신사가 자기 망 안에서 고객별로 경로를 분리해 주는 기술이다. 남이 못 보는 것은 통신사를 믿기 때문이지 암호 때문이 아니다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 캡슐화 | 층마다 헤더를 앞에 붙인다 | 각 층은 자기 질문의 답만 적고 안은 보지 않는다 |
| 역캡슐화 | 아래층부터 한 겹씩 뜯는다 | 겉봉투를 열어야 안이 나온다 |
| 트레일러 | FCS는 뒤에 | 보내면서 계산하고 끝에 붙인다 |
| TCP 헤더 | 포트, 순서 번호, 확인 응답, 제어 비트, 윈도우 | 어느 프로그램에게, 믿을 수 있게 |
| IP 헤더 | 주소, 프로토콜 번호, TTL, 단편화 필드 | 어느 망의 어느 기계에게 |
| TTL | 남은 홉 수. 라우터마다 1 감소 | 맴도는 패킷을 없앤다. `ping`의 TTL로 홉 수를 안다 |
| 이더넷 헤더 | 다음 기계의 MAC | 라우터마다 새로 붙는다. IP 주소는 끝까지 그대로 |
| 검사 | 내 것인가, 깨졌나 | 깨진 것은 아래층이 조용히 버리고 재전송은 TCP가 |
| MTU 1,500 | 프레임에 실을 IP 패킷의 한도 | 넘으면 단편화. DF를 켜면 못 간다고 알려 준다 |
| MSS 1,460 | MTU에서 헤더 40을 뺀 것 | TCP가 한 번에 자르는 크기 |
| 헤더의 값 | 패킷마다 54바이트 | 작은 패킷이 많으면 회선을 봉투로 쓴다 |
| VPN | 패킷을 새 봉투에 넣고 암호화 | 사설 주소가 인터넷을 건너고 중간에서 못 본다 |
| MPLS | 분리이지 암호화가 아니다 | 통신사를 믿는 것이다 |

{{< callout type="info" >}}
**용어 정리**
- **캡슐화 / 역캡슐화**: 층마다 헤더를 덧붙이는 것 / 받는 쪽이 한 겹씩 뜯는 것
- **PDU**: 각 층의 데이터 단위. 세그먼트, 패킷, 프레임, 비트
- **TTL (Time To Live)**: 패킷이 더 지날 수 있는 라우터 수. 0이 되면 버려진다
- **MTU (Maximum Transmission Unit)**: 프레임에 실을 수 있는 IP 패킷의 최대 크기. 이더넷은 1,500바이트
- **MSS (Maximum Segment Size)**: TCP 세그먼트 하나의 데이터 최대 크기. 보통 1,460바이트
- **단편화 / DF / 경로 MTU 탐색**: 큰 패킷을 조각내는 것 / 조각내지 말라는 플래그 / 경로의 MTU를 알아내 맞추는 것
- **VPN**: 공용 인터넷 위에 패킷을 다시 감싸 만든 암호화 터널
- **IPsec (AH, ESP)**: IP 층의 보안 규칙. 인증만 / 인증과 암호화
- **MPLS**: 통신사가 레이블로 경로를 분리하는 기술. VPN이라 부르지만 암호화는 아니다
{{< /callout >}}
