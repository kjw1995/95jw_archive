[23. 전송 계층의 역할](../23-transport-layer-role)에서 TCP와 UDP의 차이는 상태의 유무 하나에서 나오고, UDP는 신뢰의 값을 치르지 않기로 한 선택이지 열등한 것이 아니라고 했다. [26](../26-port-number-structure)장은 두 헤더의 맨 앞 4바이트가 같은 이유를 보고 나머지를 여기로 미뤘다. 이 장은 그 나머지, 곧 UDP에 무엇이 남고 무엇이 없는지를 본다. 원리는 셋이다. 첫째, **UDP는 IP에 포트를 더한 것이다.** 헤더 8바이트에는 포트 둘과 길이와 체크섬뿐이고, 그중 새 정보는 포트뿐이다. 상태가 없으니 적을 것도 없다. 둘째, **봉투는 봉투째 도착하거나 아예 안 온다.** TCP의 바이트 흐름과 달리 보낸 단위가 그대로 받는 단위이고, 그래서 경계는 지켜지지만 크기와 순서와 도착은 응용 프로그램의 몫이다. 셋째, **상태가 없어서 되는 것과 안 되는 것이 있다.** 한 봉투를 모두에게 뿌릴 수 있고 연결 비용이 없지만, 길이 막혀도 스스로 물러설 줄 모른다. 이 장의 실측은 이 PC에서 같은 DNS 질의를 UDP와 TCP로 보냈을 때의 시간 차이와, [자바 기초 16장](../../java/basics/16-networking)에서 데이터그램 소켓으로 본 성질들이다.

## 1. UDP의 개념

| 성질 | 뜻 | 왜 |
|:-----|:---|:---|
| 비연결 | 인사도 작별도 없다 | 기억할 상태가 없으니 시작과 끝도 없다 |
| 비신뢰 | 잃어도, 겹쳐도, 뒤바뀌어도 모른다 | 번호도 확인도 없다 |
| 헤더 8바이트 | 포트 둘, 길이, 체크섬 | 새로 더할 정보가 포트뿐이다 |
| 기다림 없음 | 확인을 기다리지 않는다 | 기다릴 것이 없다 |
| 1:N | 브로드캐스트, 멀티캐스트 | 연결은 1:1의 상태인데 그것이 없다 |

이름의 "사용자 데이터그램"은 응용 프로그램이 만든 봉투 하나를 뜻한다. 봉투는 각각 독립이라 앞뒤의 봉투와 아무 관계가 없고, 규격 문서(RFC 768)는 1980년에 세 쪽으로 끝났다. 신뢰를 위한 장치를 [24](../24-tcp-structure)장에서 봤듯 TCP가 다 갖고 있다면, UDP는 그것을 전부 뺀 것이 아니라 **처음부터 넣지 않은** 것이다. [17](../17-network-layer-role)장의 IP가 이미 "갈 수 있으면 보내고 못 가면 버린다"였고, UDP는 거기에 "어느 프로그램에게"만 붙였다.

## 2. TCP와 비교

| 항목 | TCP | UDP |
|:-----|:----|:----|
| 연결 | 세 번의 인사 | 없다 |
| 신뢰 | 확인과 재전송 | 없다 |
| 순서 | 번호로 되돌린다 | 없다 |
| 헤더 | 20~60바이트 | 8바이트 |
| 속도 조절 | 흐름 제어, 혼잡 제어 | 없다 |
| 상대 | 1:1 | 1:1, 1:모두, 1:그룹 |
| 단위 | 세그먼트. 바이트의 흐름 | 데이터그램. 봉투 하나 |
| 비유 | 등기우편 | 엽서 |

표의 오른쪽에 "없다"가 반복되는 것은 UDP가 덜 만들어졌기 때문이 아니라 23장에서 본 대로 **상태를 갖지 않기로** 했기 때문이다. 상태가 없으면 연결도 번호도 창도 있을 수 없고, 헤더는 8바이트가 되며, 대신 상대가 하나일 필요가 없어진다. 엽서는 수취 확인이 없어 잃어버려도 다시 오지 않지만, 그래서 빠르고 싸고 같은 엽서를 백 장 뿌릴 수도 있다.

## 3. UDP 헤더 구조

```text
 0        16        31
 ├─────────┼─────────┤
 │ src port│ dst port│
 ├─────────┼─────────┤
 │  length │checksum │
 ├─────────┴─────────┤
 │       data        │
 └───────────────────┘
```

| 필드 | 크기 | 뜻 | 왜 있나, 왜 이 모양인가 |
|:-----|:-----|:---|:----------------------|
| 출발지 포트 | 16비트 | 답장을 받을 프로그램 | 답이 필요 없으면 0. 답장 주소를 안 적은 엽서 |
| 목적지 포트 | 16비트 | 받을 프로그램 | 유일하게 꼭 필요한 값 |
| 길이 | 16비트 | 헤더와 데이터를 합친 바이트 수. 최소 8 | IP 헤더에서도 알 수 있어 사실상 중복. 체크섬 계산의 편의 |
| 체크섬 | 16비트 | 헤더, 데이터, 의사 헤더의 검사 | IPv4에서는 선택, IPv6에서는 필수 |

체크섬이 IPv4에서 선택인 것은 1980년의 CPU에는 바이트마다 더하는 일이 비쌌기 때문이고, 0으로 두면 "검사하지 않았다"는 뜻이다. IPv6에서 필수가 된 이유는 [17](../17-network-layer-role)장에서 봤다. IPv6는 라우터를 가볍게 하려고 IP 헤더의 체크섬을 없앴으므로, 주소가 깨진 것을 잡을 마지막 검사가 4층에만 남았다. 요즘은 이 계산을 [09](../09-physical-layer-nic)장에서 본 대로 랜 카드가 대신하므로 비용이 없고, 이 PC의 카드도 UDP 체크섬 오프로드가 켜져 있다.

### 의사 헤더

체크섬은 UDP 헤더와 데이터만이 아니라 IP 헤더의 출발지와 목적지 주소, 프로토콜 번호 17, UDP 길이를 앞에 붙인 **의사 헤더**까지 넣어 계산한다. 실제로 보내지는 않고 계산에만 쓰는 가짜 헤더다. 이유는 23장의 TCP 체크섬과 같다. 데이터가 멀쩡해도 엉뚱한 기계에 배달된 봉투를 걸러 내려면 주소까지 검사에 넣어야 하고, IP 헤더의 체크섬은 홉마다 다시 계산되어 끝에서 끝의 보증이 못 되기 때문이다.

### TCP에 있고 UDP에 없는 것

| TCP의 필드 | 하는 일 | UDP에 없는 이유 |
|:-----------|:--------|:---------------|
| 일련번호, 확인 응답 번호 | 순서와 재전송 | 봉투마다 독립이라 순서가 없다 |
| 플래그 SYN, ACK, FIN | 연결의 단계 | 연결이 없다 |
| 창 크기 | 흐름 제어 | 받는 쪽의 사정을 묻지 않는다 |
| 옵션 | MSS, 배율, 타임스탬프 | 정할 것이 없다 |

없는 것의 목록이 곧 24장에서 본 상태의 목록이다. TCP 헤더의 20바이트 중 포트 4바이트와 체크섬 2바이트를 빼면 전부 상태를 적는 칸이고, UDP는 그 칸이 없다.

## 4. UDP 데이터그램

```text
응용 데이터
   ↓ UDP 헤더 8바이트
[UDP][데이터]         데이터그램
   ↓ IP 헤더 20바이트
[IP][UDP][데이터]     패킷
```

UDP 헤더가 붙은 단위가 데이터그램이다. TCP 세그먼트는 하나의 흐름을 잘라 놓은 조각이지만 데이터그램은 각자 완결된 소포이고, 그 차이가 프로그램에서 그대로 보인다. 자바 기초 16장에서 이 PC의 JDK로 확인한 세 성질이 그것이다.

| 성질 | 실측 | 왜 |
|:-----|:-----|:---|
| 경계가 있다 | 2바이트를 두 번 보내면 두 번 받고 각각 2바이트다 | 보낸 봉투 하나가 받는 봉투 하나다. TCP는 `abcd`로 합쳐졌다 |
| 잘릴 수 있다 | 2,000바이트를 보내고 1,024바이트 버퍼로 받으면 1,024만 남고 나머지는 조용히 사라진다 | 봉투를 나눠 받을 수 없다. 버퍼가 봉투보다 작으면 넘친 부분은 버려진다 |
| 상대가 없어도 보내진다 | 아무도 듣지 않는 포트로 보내도 보내기는 성공한다 | 연결이 없으니 상대를 확인할 순간이 없다. 없다는 것은 ICMP로 뒤늦게 올 뿐이다 |

봉투의 크기에도 한계가 있다. 길이 필드가 16비트라 데이터는 최대 65,507바이트(65,535에서 IP 헤더 20과 UDP 헤더 8을 뺀 값)이지만, [08](../08-encapsulation-decapsulation)장의 MTU 1,500을 넘으면 IP가 조각을 낸다. 이더넷에서 조각 없이 가는 데이터는 1,472바이트까지이고, 17장에서 본 대로 조각은 인터넷 너머에서 자주 버려진다. 그래서 UDP를 쓰는 규칙들은 봉투를 작게 유지한다. DNS가 오랫동안 답을 512바이트로 제한했고, 요즘도 4,096바이트를 넘는 답은 "잘렸다"는 표시와 함께 보내 클라이언트가 TCP로 다시 묻게 한다. 크기를 맞추는 것도 조각을 피하는 것도 응용 프로그램의 몫이다.

## 5. UDP 통신 과정

```text
TCP  SYN → SYN+ACK → ACK   인사
     데이터 → ACK          전송
     FIN → FIN+ACK → ACK   작별
     세그먼트 여덟에 데이터 하나

UDP  데이터               끝
```

```text
PC 192.168.1.10:52341   DNS 8.8.8.8:53
    │                              │
    │── "google.com A?"  ────────→│
    │                              │
    │←── "142.250.185.78" ────────│
    │                              │
```

TCP로 요청 하나에 답 하나를 받으려면 인사 셋, 데이터와 확인, 작별 셋으로 세그먼트 여덟 개 남짓이 오가고 그중 데이터는 둘뿐이다. UDP는 봉투 둘로 끝난다. 연결이 없으니 첫 봉투가 곧 데이터이고, 걸리는 시간은 왕복 한 번이다.

| 이 PC에서 8.8.8.8에 같은 이름을 물었을 때 | 걸린 시간 |
|:----------------------------------------|:----------|
| UDP (보통의 DNS) | 42 ~ 56ms |
| TCP (연결을 맺고 묻기) | 76 ~ 89ms |

이 PC에서 구글의 DNS 서버에 같은 질의를 UDP와 TCP로 세 번씩 보내 잰 값이다. [25](../25-sequence-ack-number)장에서 잰 대로 그 서버까지의 왕복은 40ms 안팎이고, UDP는 딱 그만큼, TCP는 인사에 왕복 하나를 더 써 두 배가 걸린다. 이름 하나를 묻는 데 40ms를 더 내는 것은 데이터보다 인사가 비싼 셈이라, DNS가 UDP를 기본으로 쓰는 이유가 이 표에 있다. 답이 안 오면 어떻게 하는가. 재전송은 TCP처럼 운영체제가 하는 것이 아니라 **응용 프로그램이** 한다. DNS 클라이언트는 1초쯤 기다렸다 다시 묻고, 그래도 없으면 다른 서버에 묻는다.

## 6. 브로드캐스트와 멀티캐스트

| 방식 | 상대 | 규칙 | 왜 UDP만 되나 |
|:-----|:-----|:-----|:-------------|
| 유니캐스트 | 하나 | TCP, UDP | |
| 브로드캐스트 | 같은 링크의 모두 | UDP | 연결은 상대 하나와의 상태다. 모두와 맺을 수 없다 |
| 멀티캐스트 | 가입한 그룹 | UDP | 위와 같다. 라우터를 넘을 수 있다 |

TCP가 1:N을 못 하는 것은 기능이 빠져서가 아니다. 연결은 상대 하나와 번호와 창을 맞춘 상태이고, 받는 쪽이 백 명이면 확인 응답도 백 개가 되어 "한 번 보낸다"는 뜻이 사라진다. 상태가 없는 UDP만이 봉투 하나를 [20](../20-network-broadcast-address)장의 브로드캐스트 주소나 [19](../19-ip-address-class)장의 멀티캐스트 주소로 보낼 수 있다.

```text
New PC ──DHCP Discover──→ 모든 장비
        (255.255.255.255:67)
New PC ←──DHCP Offer──── DHCP 서버
        (192.168.1.100 제안)
```

[18](../18-ip-address-structure)장의 DHCP가 그 예다. 아직 주소도 없고 서버가 어디 있는지도 모르는 기기는 "이 링크의 모두"에게 보내는 수밖에 없고, 그래서 DHCP는 UDP다. TCP였다면 연결을 맺을 상대의 주소부터 알아야 했을 것이다.

```text
Server ─(239.1.1.1:5000)─→ Router
Router ─→ 가입자 A (수신)
Router ─→ 가입자 B (수신)
Router ─× 비가입자 (제외)
```

멀티캐스트는 같은 방송을 보는 기기만 그룹에 가입시키고, 보내는 쪽은 한 줄기만 보내며 라우터와 스위치가 가입자에게만 복제해 준다. 시청자가 만 명이어도 서버의 회선은 한 줄기 값이다. 19장에서 본 대로 이 PC의 이더넷도 224.0.0.1, 224.0.0.251, 224.0.0.252, 239.255.255.250 네 그룹에 가입해 있고, 그 봉투들은 전부 UDP다. 같은 링크의 프린터를 찾고(mDNS, SSDP) 이웃 PC의 이름을 묻는(LLMNR) 일이 연결 없이 "누구 있나"를 뿌리는 일이기 때문이다. 이 주소가 [13](../13-mac-address-structure)장의 01:00:5E MAC으로 바뀌어 카드가 걸러 내는 것까지가 한 벌이다.

## 7. UDP를 사용하는 주요 프로토콜

| 규칙 | 포트 | 왜 UDP인가 |
|:-----|:-----|:-----------|
| DNS | 53 | 질문 하나 답 하나. 인사가 데이터보다 비싸다 |
| DHCP | 67, 68 | 주소가 없는 기기의 브로드캐스트 |
| NTP | 123 | 시각을 맞추는 데 재전송된 늦은 봉투는 해롭다 |
| SNMP | 161, 162 | 장비 수천 대에 작은 질문을 던진다 |
| TFTP | 69 | 부팅 롬에 TCP를 넣기엔 크다. 재전송을 스스로 한다 |
| RTP, 음성 통화 | 가변 | 늦은 소리는 쓸모없다 |
| QUIC (HTTP/3) | 443 | 신뢰를 응용에서 다시 얹었다. 23장 |
| WireGuard 같은 VPN | 가변 | 터널 안에 이미 TCP가 있으니 밖은 가벼워야 한다 |

{{< callout type="info" >}}
재전송한 음성이나 영상의 조각은 이미 지나간 시점의 것이라 틀어도 소용이 없다. 실시간 매체는 잃은 것을 되찾기보다 다음 것을 제때 받는 편이 낫고, 그래서 TCP의 재전송이 오히려 해가 된다. 이런 규칙들은 UDP 위에 자기 순서 번호와 시각을 붙이고(RTP), 잃은 조각은 잡음을 채우거나 앞뒤로 메운다. 이 PC의 VPN 어댑터도 마지막 줄의 예다. 터널 안에 TCP 연결을 실어 나르는 터널 자체가 TCP라면 재전송이 두 겹으로 겹쳐 서로를 방해하므로, 터널은 UDP로 만든다.
{{< /callout >}}

## 8. UDP가 적합한 상황과 부적합한 상황

| 맞는 곳 | 왜 |
|:--------|:---|
| 실시간 매체. 스트리밍, 게임, 통화 | 늦은 데이터는 쓸모없다 |
| 짧은 요청과 답. DNS, DHCP, NTP | 인사가 데이터보다 비싸다 |
| 브로드캐스트와 멀티캐스트 | 상태가 없어야 여럿에게 간다 |
| 스스로 신뢰를 얹는 규칙. QUIC | 운영체제의 TCP보다 자기 방식이 낫다고 판단한 경우 |

| 안 맞는 곳 | 왜 |
|:----------|:---|
| 파일, 메일, 금융 거래 | 한 바이트도 잃으면 안 된다 |
| 순서가 뜻을 만드는 것. 웹 응답, 데이터베이스 질의 | 뒤바뀌면 다른 뜻이 된다 |
| 큰 전송. 업로드, 백업 | 조각과 손실을 응용이 다 감당해야 한다 |

기준은 [23](../23-transport-layer-role)장의 것 그대로다. 늦게 도착한 데이터가 쓸모 있으면 TCP, 없으면 UDP. 마지막 줄의 QUIC은 그 사이에 있다. 늦은 데이터가 쓸모 있지만 TCP의 방식이 마음에 안 들어 UDP 위에 자기 신뢰를 쌓은 경우이고, 그렇게 할 수 있는 것은 UDP가 아무것도 하지 않기 때문이다.

## 9. 장단점 정리

| 장점 | 왜 |
|:-----|:---|
| 지연이 없다 | 연결이 없다. 5절의 40ms |
| 오버헤드가 작다 | 8바이트. 상태를 안 적는다 |
| 1:N이 된다 | 6절 |
| 구현이 단순하다 | 세 쪽짜리 규격 |

| 단점 | 왜 |
|:-----|:---|
| 잃어도 모른다 | 확인이 없다 |
| 순서가 없다 | 번호가 없다 |
| 길이 막혀도 계속 보낸다 | 혼잡 제어가 없다 |
| 상대가 살았는지 모른다 | 연결이 없다 |

{{< callout type="warning" >}}
셋째 단점이 가장 위험하다. 23장에서 인터넷이 붕괴하지 않는 것은 모든 TCP가 손실을 보고 물러서기 때문이라고 했는데, UDP는 물러설 줄 모른다. 스트리밍 서버가 회선이 막혔는데도 같은 속도로 계속 쏘면 자기 봉투만 버려지는 것이 아니라 같은 길을 쓰는 남의 TCP까지 밀려난다. 그래서 UDP를 쓰는 응용 프로그램은 손실을 보고 화질을 낮추는 식으로 스스로 물러서야 한다는 것이 규격의 요구이고, QUIC이 TCP와 같은 혼잡 제어를 UDP 위에 다시 구현한 이유다. UDP는 혼잡 제어를 면제해 주는 것이 아니라 응용 프로그램에게 떠넘긴 것이다.
{{< /callout >}}

## 10. 소켓 프로그래밍 예시 (Python)

```python
import socket

server = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
server.bind(('0.0.0.0', 9999))

while True:
    data, addr = server.recvfrom(1024)
    print(f"from {addr}: {data.decode()}")
    server.sendto(f"echo: {data.decode()}".encode(), addr)
```

```python
import socket

client = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
client.sendto("hello UDP".encode(), ('localhost', 9999))

data, server = client.recvfrom(1024)
print(data.decode())
client.close()
```

TCP 코드와 견주면 `listen()`, `accept()`, `connect()`가 없다. 서버는 소켓 하나로 누가 보낸 것이든 받고, 봉투마다 보낸 쪽의 주소가 딸려 오므로 그 주소로 답한다. `recvfrom(1024)`의 1024가 4절에서 본 버퍼 크기이고, 이보다 큰 봉투가 오면 나머지는 잘린다. 같은 프로그램의 자바 판과 그 실측은 자바 기초 16장에 있다.

## 11. UDP 확인 명령어

```bash
# Windows
netstat -an -p UDP
Get-NetUDPEndpoint

# Linux
ss -u -a
# UNCONN  0  0  0.0.0.0:53  0.0.0.0:*
netstat -u -a
```

Linux의 `ss`가 UDP 소켓에 `UNCONN`이라고 적는 것이 이 장의 요약이다. 연결이 없으므로 TCP의 ESTABLISHED나 TIME_WAIT 같은 상태가 없고, 소켓은 그저 열려 있거나 아니거나다. [26](../26-port-number-structure)장에서 이 PC에 UDP 소켓이 75개 열려 있다고 했는데, 그 전부가 이 한 상태다.

```text
udp
udp.port == 53
udp.port == 67 || udp.port == 68
ip.dst == 255.255.255.255
ip.dst >= 224.0.0.0 &&
  ip.dst <= 239.255.255.255
```

Wireshark의 필터다. 위에서부터 UDP 전부, DNS, DHCP, 브로드캐스트, 멀티캐스트다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| UDP | IP에 포트를 더한 것 | 상태가 없으니 적을 것이 없다 |
| 8바이트 | 포트 둘, 길이, 체크섬 | 새 정보는 포트뿐. 길이는 중복 |
| 체크섬 | IPv4 선택, IPv6 필수 | IPv6는 IP 헤더 체크섬을 없앴다 |
| 의사 헤더 | 주소까지 검사에 넣는다 | 엉뚱한 기계에 온 봉투를 거른다 |
| 없는 것들 | 번호, 플래그, 창, 옵션 | 곧 TCP의 상태 목록 |
| 봉투 | 보낸 단위가 받는 단위 | 경계는 지켜지고, 크면 잘린다 |
| 크기 | 최대 65,507이지만 1,472까지가 안전 | 조각은 버려진다. DNS의 512 |
| 이 PC의 DNS | UDP 42~56ms, TCP 76~89ms | 인사가 왕복 하나를 더 쓴다 |
| 재시도 | 응용 프로그램이 한다 | 운영체제에는 상태가 없다 |
| 1:N | 브로드캐스트, 멀티캐스트 | 연결은 상대 하나와의 상태다 |
| 이 PC의 그룹 넷 | mDNS, LLMNR, SSDP | "누구 있나"는 연결 없이 뿌린다 |
| VPN이 UDP인 이유 | 안에 이미 TCP가 있다 | 재전송이 두 겹이면 서로 방해한다 |
| 혼잡 제어 없음 | 남의 TCP까지 밀어낸다 | 물러서는 일을 응용에 떠넘긴 것 |
| UNCONN | UDP 소켓의 유일한 상태 | 열려 있거나 아니거나 |

{{< callout type="info" >}}
**용어 정리**
- **UDP**: 연결도 확인도 없이 봉투에 포트만 붙여 보내는 전송 규칙
- **데이터그램**: UDP 헤더가 붙은 봉투 하나. 앞뒤와 무관하다
- **비연결형**: 인사 없이 첫 봉투가 곧 데이터인 방식
- **의사 헤더**: 체크섬 계산에만 쓰는 가짜 헤더. IP 주소와 프로토콜 번호를 담는다
- **유니캐스트 / 브로드캐스트 / 멀티캐스트**: 하나에게 / 링크의 모두에게 / 가입한 그룹에게
- **잘림 (truncation)**: 버퍼보다 큰 봉투의 나머지가 버려지는 것
- **UNCONN**: ss가 UDP 소켓에 붙이는 상태. 연결 없음
- **QUIC**: UDP 위에 신뢰, 순서, 혼잡 제어를 응용 프로그램이 다시 얹은 규칙
{{< /callout >}}
