[07. OSI 모델과 TCP/IP 모델](../07-osi-tcpip-model)에서 응용 층은 사용자의 프로그램이 네트워크를 만나는 창구이고, 이 시리즈의 마지막 아홉 장이 이 층이라고 했다. 표현과 세션의 일이 별도의 프로토콜이 아니라 응용 프로그램 안에서 처리되기 때문에 위의 세 층이 하나로 합쳐진다고도 했다. 이 장은 그 합쳐진 층의 개요이고, 웹은 [29](../29-web-server-structure)장, DNS는 [30](../30-dns-server-structure)장, 메일은 [31](../31-mail-server-structure)장이 맡는다. 원리는 셋이다. 첫째, **응용 계층의 규칙은 "무슨 글자를 어떤 순서로 주고받는가"다.** [06](../06-network-protocol)장의 구문, 의미, 타이밍이 이 층에서는 사람이 읽을 수 있는 대화로 나타난다. 그래서 손으로 쳐 볼 수 있고, 그래서 느리다. 둘째, **위의 세 층은 응용 프로그램 안에 있다.** 암호화와 인코딩(표현), 대화의 시작과 끝(세션)은 HTTP나 브라우저가 스스로 한다. 이 PC에서 curl이 TLS를 직접 맺고 그 안에서 똑같은 글자를 주고받는 것으로 확인한다. 셋째, **만남의 약속은 포트와 클라이언트-서버다.** 서버는 정해진 번호에서 기다리고 클라이언트가 말을 건다. 그 약속이 이 PC의 운영체제 안에도 표로 적혀 있다.

## 1. 응용 계층이란

| 하는 일 | 뜻 | 왜 이 층인가 |
|:--------|:---|:------------|
| 프로그램끼리의 대화 규칙 | 요청과 응답의 글자와 순서를 정한다 | 아래 층들은 바이트를 나를 뿐 뜻을 모른다 |
| 데이터의 형식 | 문자셋, 압축, 암호화 | 07장의 표현 층. 프로그램이 한다 |
| 대화의 단위 | 시작, 끝, 이어짐 | 07장의 세션 층. 프로그램이 한다 |
| 아래 층 감추기 | 소켓 하나로 세계에 닿는다 | [23](../23-transport-layer-role)장 이하의 사정을 몰라도 된다 |

```
┌────────────────────────────┐
│ 7. 응용 (Application)      │ ← 이 장
│    HTTP, DNS, SMTP ...     │
├────────────────────────────┤
│ 6. 표현 (Presentation)     │
│    SSL/TLS, 인코딩         │
├────────────────────────────┤
│ 5. 세션 (Session)          │
├────────────────────────────┤
│ 4. 전송 (Transport)        │
│    TCP, UDP                │
├────────────────────────────┤
│ 3. 네트워크 (Network)      │
│    IP                      │
├────────────────────────────┤
│ 2. 데이터링크 (Data Link)  │
│    Ethernet, MAC           │
├────────────────────────────┤
│ 1. 물리 (Physical)         │
└────────────────────────────┘
```

| 층 | 단위 | 누가 만드나 |
|:---|:-----|:-----------|
| 응용 | 메시지 | 프로그램 |
| 전송 | 세그먼트, 데이터그램 | 운영체제의 TCP, UDP |
| 네트워크 | 패킷 | 운영체제의 IP |
| 데이터 링크 | 프레임 | 카드와 드라이버 |
| 물리 | 비트 | 카드 |

아래 네 층이 답한 질문은 "어느 기계의 어느 프로그램에게, 깨지지 않게"였다. 그 질문이 끝나면 남는 것은 바이트의 흐름 또는 봉투이고, 그 안에 무엇이 어떤 순서로 적히는지는 아무도 정해 주지 않았다. 브라우저와 웹 서버가 서로 알아듣는 글자의 규칙, 메일 프로그램과 메일 서버의 규칙이 응용 계층이다.

07장에서 미뤄 둔 이야기를 여기서 거둔다. OSI의 표현 층과 세션 층이 TCP/IP 모델에서 응용 층에 합쳐진 이유는 그 일을 하는 별도의 프로토콜이 없기 때문이다. 이 PC에서 curl로 `https://example.com`을 열면 curl이 스스로 TLS 1.3을 맺고(AES-256, SHA-384, 클라우드플레어가 발급한 인증서), 그 안에서 `GET / HTTP/1.1`을 보내 `HTTP/1.1 200 OK`를 받는다. 암호화라는 표현 층의 일을 운영체제도 TCP도 아닌 응용 프로그램 curl이 했고, 그 안에서 오간 글자는 암호화 없는 HTTP와 똑같다. 세션 층의 일도 마찬가지다. 로그인 상태를 기억하는 것은 HTTP가 아니라 브라우저와 서버가 쿠키로 주고받는 응용의 약속이다. 층이 하나로 합쳐졌다는 것은 일이 사라졌다는 뜻이 아니라 프로그램 안으로 들어갔다는 뜻이다.

## 2. 클라이언트-서버 모델

| 구분 | 하는 일 | 예 | 왜 |
|:-----|:--------|:---|:---|
| 클라이언트 | 먼저 말을 건다 | 브라우저, 메일 프로그램 | 상대의 주소와 포트를 안다 |
| 서버 | 정해진 포트에서 기다린다 | Apache, Nginx, Postfix, BIND | 누가 올지 모르니 늘 열어 둔다 |

```
[클라이언트]         [서버]
    │  1. Request     │
    │ ───────────────▶│
    │                 │ 처리
    │  2. Response    │
    │ ◀─────────────── │
    │                 │
```

응용 계층의 대화는 대부분 **요청과 응답**이고, 역할은 비대칭이다. [26](../26-port-number-structure)장에서 본 대로 약속은 먼저 말을 거는 쪽의 상대에게만 필요하므로, 서버는 알려진 포트에서 기다리고(LISTEN) 클라이언트는 그때그때의 포트로 찾아간다. 이 모델이 지배적인 이유는 둘이다. 하나는 방금 본 약속의 비대칭이고, 다른 하나는 [04](../04-home-lan-configuration)장의 NAT다. 집과 회사의 기기는 NAT 뒤에 있어 밖에서 먼저 찾아올 수 없으므로 서버가 될 수 없고, 서버는 공인 주소를 가진 쪽에만 있게 된다. 기기끼리 직접 말을 거는 P2P가 어려운 이유이고, 그래서 화상 통화조차 중계 서버를 거친다.

{{< callout type="info" >}}
서버가 기다리는 포트가 "만나는 약속"이고, 그 약속은 이 PC의 운영체제 안에도 적혀 있다. Windows의 `drivers/etc/services` 파일에는 `http 80/tcp`, `https 443/tcp`, `smtp 25/tcp`, `domain 53/tcp`와 `53/udp`, `pop3 110/tcp`, `imap 143/tcp`, `ntp 123/udp`가 줄줄이 있고, 최근 파일에는 `https 443/udp`도 있다. [23](../23-transport-layer-role)장의 HTTP/3가 UDP 443을 쓰기 때문이다. 프로그램이 포트 번호 대신 서비스 이름을 쓸 때 운영체제가 이 표에서 번호를 찾는다.
{{< /callout >}}

## 3. 주요 응용 계층 프로토콜

### HTTP와 HTTPS

```http
HTTP/1.1 200 OK
Date: Fri, 11 Sep 2026 06:37:43 GMT
Content-Type: text/html
Connection: keep-alive
Server: cloudflare
Last-Modified: Thu, 10 Sep 2026 21:00:47 GMT
Allow: GET, HEAD
```

이 PC에서 `curl -I http://example.com`으로 받은 응답의 머리 부분이다. 첫 줄이 결과(구문과 의미), 그 아래가 "이름: 값" 꼴의 헤더, 빈 줄 하나가 머리의 끝이다. 전부 사람이 읽는 글자다. HTTP가 텍스트인 것은 1990년대의 규칙들이 대체로 그랬기 때문이고, 그 덕에 5절처럼 손으로 쳐 볼 수 있고 헤더 한 줄을 더하는 것만으로 기능을 늘릴 수 있었다. 대가는 크기와 파싱이다. 글자를 읽어 뜻을 알아내는 일은 고정 길이 필드를 읽는 것보다 훨씬 느려서, HTTP/2는 같은 뜻을 이진 형식으로 바꿨다.

| 성질 | 뜻 | 왜 |
|:-----|:---|:---|
| 요청과 응답 | 클라이언트가 묻고 서버가 답한다 | 웹은 문서를 달라는 대화였다 |
| 무상태 | 요청마다 남남이다 | 서버가 수백만 클라이언트의 상태를 기억할 수 없다 |
| 쿠키 | 상태를 클라이언트에게 들려 보낸다 | 무상태로는 로그인이 안 된다. 세션 층의 일을 응용이 만든 것 |
| 80과 443 | 평문과 TLS | 같은 글자를 자물쇠 안에서 주고받는다 |

HTTP의 구조와 버전은 29장에서, 메서드와 상태 코드와 헤더의 뜻은 별도 시리즈 [HTTP 기본](../http/02-http-basics)에서 본다.

### DNS

이름을 주소로 바꾼다. 질문 하나에 답 하나라 [27](../27-udp-structure)장에서 본 대로 UDP 53번을 기본으로 쓰고, 이 PC에서 UDP는 42~56ms, TCP는 76~89ms였다. 답이 512바이트를 넘거나 서버끼리 영역 전체를 옮길 때는 TCP를 쓴다. 이름의 구조와 서버의 종류, 캐시는 30장에서 본다.

### FTP

파일을 옮긴다. 명령 연결(21)과 데이터 연결(20 또는 임시 포트)을 따로 두어 전송 중에도 명령을 받게 한 1971년의 설계다. 이 두 연결 구조가 NAT와 상극이다. 데이터 연결을 서버가 클라이언트 쪽으로 새로 맺는 능동 모드는 04장에서 본 대로 NAT 뒤로 들어갈 수 없고, 그래서 클라이언트가 두 연결을 다 여는 수동 모드가 생겼다. 게다가 비밀번호와 파일이 평문으로 지나가므로, 지금은 SSH 위의 SFTP나 TLS를 얹은 FTPS를 쓴다.

### SMTP, POP3, IMAP

| 규칙 | 하는 일 | 포트 | 왜 따로인가 |
|:-----|:--------|:-----|:-----------|
| SMTP | 메일을 보내고 서버끼리 넘긴다 | 25, 587 | 보내는 일은 밀어 넣기다 |
| POP3 | 메일을 내려받는다 | 110, 995 | 받는 일은 꺼내 가기다. 한 기기에서 |
| IMAP | 서버에 둔 채 본다 | 143, 993 | 기기 여럿이 같은 편지함을 본다 |

메일이 보내기와 받기에 다른 규칙을 쓰는 이유는 방향이 다르기 때문이다. 보내는 쪽은 상대 서버에 밀어 넣고, 받는 쪽은 자기 서버에서 꺼내 간다. 25번과 587번이 따로 있는 것은 스팸 때문이다. 서버끼리 넘기는 25번을 가정용 회선에서 막는 통신사가 많아, 사용자가 자기 서버에 제출하는 문을 587번으로 나눴다. 이 PC의 사무실 망에서는 지메일의 25번과 587번이 둘 다 열려 있지만, 집에서는 25번이 안 열리는 일이 흔하다. 자세한 것은 31장에서 본다.

### 프로토콜과 포트

| 규칙 | 용도 | 포트 | 전송 계층 | 왜 |
|:-----|:-----|:-----|:----------|:---|
| HTTP, HTTPS | 웹 | 80, 443 | TCP | 한 바이트도 빠지면 페이지가 깨진다 |
| DNS | 이름 풀이 | 53 | UDP, 크면 TCP | 질문 하나 답 하나 |
| FTP | 파일 | 20, 21 | TCP | 파일은 완전해야 한다 |
| SMTP | 메일 보내기 | 25, 587 | TCP | 위와 같다 |
| POP3, IMAP | 메일 받기 | 110, 143 | TCP | 위와 같다 |
| SSH | 원격 셸 | 22 | TCP | 명령 한 글자도 잃으면 안 된다 |
| DHCP | 주소 받기 | 67, 68 | UDP | 주소가 없는 기기의 브로드캐스트 |
| NTP | 시각 맞추기 | 123 | UDP | 늦게 온 시각은 틀린 시각이다 |

| 고르는 기준 | TCP | UDP |
|:-----------|:----|:----|
| 잃어도 되나 | 안 된다 | 늦은 것은 버리는 편이 낫다 |
| 대화의 모양 | 길고 순서가 있다 | 짧은 질문과 답, 또는 여럿에게 |
| 대표 | HTTP, FTP, SMTP, SSH | DNS, DHCP, NTP, 음성 |

전송 계층을 고르는 기준은 23장의 것이다. 늦게 도착한 데이터가 쓸모 있으면 TCP, 없으면 UDP. 응용 계층의 규칙은 이 선택 위에 자기 대화를 얹는다.

## 4. 캡슐화와 역캡슐화

```
[송신]                 [수신]
응용 데이터             응용 데이터
    │                      ▲
    ▼ +TCP                 │ -TCP
 세그먼트               세그먼트
    │                      ▲
    ▼ +IP                  │ -IP
  패킷                    패킷
    │                      ▲
    ▼ +이더넷              │ -이더넷
 프레임                  프레임
    │                      ▲
    ▼ 전기 신호            │
    └──────────────────────┘
```

보내는 쪽에서 응용 데이터에 층마다 봉투가 한 겹씩 붙고, 받는 쪽에서 반대 순서로 벗겨진다. [08](../08-encapsulation-decapsulation)장에서 본 대로 아래 세 겹이 54바이트다. 응용 계층에도 봉투가 있다. 3절의 HTTP 헤더가 그것인데, 아래 층의 봉투와 달리 고정 길이의 비트가 아니라 **글자로 된 봉투**다. 08장의 원리대로 각 층은 자기 봉투만 읽고 쓰므로, TCP는 HTTP 헤더가 어디서 끝나는지 모르고 HTTP는 자기가 몇 번째 세그먼트에 실렸는지 모른다. 응용 프로그램이 받는 것은 봉투가 다 벗겨진 바이트의 흐름이고, 그 흐름을 빈 줄에서 끊어 머리와 몸으로 나누는 것부터가 응용 계층의 일이다.

## 5. 실무 도구

```bash
curl -v http://www.example.com     # 요청과 응답 전부
curl -I http://www.example.com     # 응답 머리만
curl -v https://www.example.com    # TLS 협상까지
```

```bash
nslookup www.google.com
Resolve-DnsName www.google.com     # Windows
dig www.google.com +short          # Linux
```

```bash
telnet smtp.example.com 25         # 평문 SMTP
openssl s_client -connect pop.example.com:995
Test-NetConnection smtp.gmail.com -Port 587
```

응용 계층의 규칙이 텍스트라는 것은 이 도구들이 왜 되는지를 설명한다. `telnet`으로 25번에 붙어 `HELO`와 `MAIL FROM`을 손으로 치면 메일 서버가 답하고, 06장에서 본 대로 curl이 보여 주는 요청과 응답은 규칙 문서에 적힌 글자 그대로다. TLS로 감싼 뒤에는 `openssl s_client`가 자물쇠를 대신 열어 주고 그 안에서 같은 글자를 칠 수 있다. 이 PC에서 curl로 본 대로 HTTPS 안의 대화가 HTTP와 같은 것이 그 증거다. 각 규칙을 손으로 쳐 보는 예는 29장, 30장, 31장의 실무 절에 있다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 응용 계층 | 프로그램끼리 주고받는 글자와 순서의 규칙 | 아래 층은 뜻을 모른다 |
| 세 층의 합침 | 표현과 세션의 일은 프로그램 안에 | 별도의 프로토콜이 없다 |
| 이 PC의 TLS | curl이 TLS 1.3을 직접 맺는다 | 자물쇠 안의 글자는 HTTP 그대로 |
| 클라이언트-서버 | 기다리는 쪽과 말을 거는 쪽 | 약속은 한쪽에만 필요하다 |
| P2P가 어려운 이유 | NAT 뒤는 서버가 못 된다 | 04장 |
| services 파일 | 운영체제 안의 약속 표 | https는 tcp와 udp 둘 다 |
| 텍스트 규칙 | 손으로 쳐 볼 수 있다 | 대가는 크기와 파싱. HTTP/2는 이진 |
| 무상태와 쿠키 | 상태를 클라이언트에게 들려 보낸다 | 서버가 수백만을 기억할 수 없다 |
| DNS의 UDP | 42~56ms 대 76~89ms | 질문 하나에 인사는 비싸다 |
| FTP와 NAT | 데이터 연결이 밖에서 들어온다 | 수동 모드, 그리고 SFTP |
| 25와 587 | 서버 사이와 사용자 제출 | 스팸 때문에 25를 막는 통신사 |
| 글자로 된 봉투 | HTTP 헤더도 봉투다 | 빈 줄에서 끊는 것부터 응용의 일 |

**용어 정리**
- **응용 계층**: 프로그램과 프로그램이 주고받는 메시지의 규칙을 정하는 층. HTTP, DNS, SMTP
- **클라이언트 / 서버**: 먼저 말을 거는 쪽 / 정해진 포트에서 기다리는 쪽
- **요청-응답**: 클라이언트가 묻고 서버가 답하는 대화의 모양
- **무상태 (stateless)**: 요청마다 남남으로 처리하는 것. HTTP의 기본
- **쿠키**: 서버가 클라이언트에게 들려 보내 다음 요청에 되돌려 받는 상태
- **TLS**: 응용 프로그램이 직접 맺는 암호화 층. HTTPS의 S
- **services 파일**: 서비스 이름과 포트 번호를 적은 운영체제의 표
- **텍스트 프로토콜**: 사람이 읽는 글자로 대화하는 규칙. HTTP/1.1, SMTP, FTP
