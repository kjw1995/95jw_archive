여기서부터 세 장은 앞의 서른한 장을 한 요청에 꿰어 본다. 이 장은 보내는 PC 안에서 일어나는 일, [33](../33-switch-router-data-transfer)장은 그 프레임이 스위치와 라우터를 지나는 일, [34](../34-web-server-data-processing)장은 서버가 받아서 답하는 일이다. 따라갈 요청은 이 시리즈 내내 쓴 것, 이 PC의 curl이 example.com에 보낸 `GET /`이다. [08](../08-encapsulation-decapsulation)장에서 봉투가 층마다 한 겹씩 붙는다고 했고, [09](../09-physical-layer-nic)장에서 요즘 랜 카드는 작은 컴퓨터라 검사와 자르기를 CPU 대신 한다고 했다. 원리는 셋이다. 첫째, **봉투는 운영체제가 붙이고 카드는 마지막 한 겹만 맡는다.** HTTP는 프로그램이, TCP와 IP 헤더는 운영체제의 커널이, 이더넷 헤더와 FCS와 프리앰블은 드라이버와 카드가 붙인다. 둘째, **카드는 보내기 전에 자르고 검사하고 채워 넣는 일을 대신한다.** 큰 덩어리를 세그먼트로 자르는 것도, 체크섬을 계산하는 것도 이 PC에서는 카드가 하며, 그래서 캡처 도구에는 틀린 체크섬이 보인다. 셋째, **받을 때는 층마다 "내 것인가"를 먼저 묻고 "깨졌는가"를 그다음에 묻는다.** 남의 것을 검사하는 데 시간을 쓰지 않기 위해서다. 이 장의 실측은 그 요청의 실제 바이트 수와 이 PC 카드의 설정, 그리고 부팅 뒤 보내고 받은 프레임의 평균 크기다.

## 1. 캡슐화 개요

```
[응용]    데이터 (HTTP)
   │ + TCP 헤더
   ▼
[전송]    세그먼트
   │ + IP 헤더
   ▼
[네트워크] 패킷
   │ + 이더넷 헤더/FCS
   ▼
[데이터링크] 프레임
   │ NIC
   ▼
[물리]    비트/전기 신호
```

| 층 | 단위 | 붙는 것 | 이 요청의 크기 | 누가 붙이나 |
|:---|:-----|:--------|:--------------|:-----------|
| 응용 | 데이터 | HTTP 요청 | 75바이트 | curl |
| 전송 | 세그먼트 | TCP 헤더 20 | 95바이트 | 커널 |
| 네트워크 | 패킷 | IP 헤더 20 | 115바이트 | 커널 |
| 데이터 링크 | 프레임 | 이더넷 헤더 14, FCS 4 | 133바이트 | 드라이버, 카드 |
| 물리 | 비트 | 프리앰블 8, 프레임 간격 12 | 153바이트 분량 | 카드 |

이 PC에서 curl이 example.com에 보낸 요청은 `GET / HTTP/1.1`과 헤더 세 줄, 빈 줄로 75바이트다. [29](../29-web-server-structure)장에서 본 그 요청이다. 여기에 TCP 20, IP 20, 이더넷 18이 붙어 133바이트 프레임이 되고, 회선에서는 프리앰블과 프레임 사이의 빈 시간까지 153바이트 분량을 차지한다. 데이터 75에 봉투 78이다. 08장에서 본 대로 봉투는 공짜가 아니고, 작은 요청일수록 봉투의 몫이 크다. 서버의 답은 헤더 301바이트와 본문 559바이트, 합쳐 860바이트라 세그먼트 하나에 들어가고 프레임으로는 914바이트다. 요청과 응답을 다 합쳐도 이 PC의 1Gbps 회선을 차지하는 시간은 10μs 남짓이다. [29](../29-web-server-structure)장에서 이 대화에 86ms가 걸린 것은 회선이 아니라 왕복 때문이었다.

## 2. 전송 계층: TCP 세그먼트

```
┌───────────────────────────┐
│ TCP 헤더 (20~60 바이트)   │
│  - 출발지 포트 (2B)       │
│  - 목적지 포트 (2B)       │
│  - Seq / Ack (각 4B)      │
│  - 플래그, Window, 체크섬 │
├───────────────────────────┤
│ 데이터 (HTTP)             │
└───────────────────────────┘
```

curl이 소켓에 75바이트를 쓰면 커널의 TCP가 헤더를 붙인다. 출발지 포트는 [26](../26-port-number-structure)장에서 본 대로 운영체제가 49152 이상에서 무작위로 고른 번호이고, 목적지는 80이다. 순서 번호는 [24](../24-tcp-structure)장의 세 번 인사에서 정한 무작위 시작 번호에 이어지며, 이 요청은 그 인사가 끝난 뒤 첫 데이터 세그먼트다. 플래그는 ACK와 PSH, 창은 [25](../25-sequence-ack-number)장에서 본 대로 이 PC가 받을 수 있는 양이다. 체크섬 칸은 여기서는 **비워 둔다.** 5절에서 카드가 채운다.

75바이트는 세그먼트 하나에 들어가지만, 파일을 올릴 때처럼 프로그램이 한 번에 수십 KB를 쓰면 [08](../08-encapsulation-decapsulation)장의 MSS 1,460바이트 단위로 잘라야 한다. 이 PC에서는 그 자르기도 커널이 아니라 카드가 한다. 커널은 64KB짜리 덩어리에 헤더 하나를 붙여 내려보내고, 카드가 그것을 1,460씩 잘라 세그먼트마다 헤더를 복사해 붙인다(대량 전송 오프로드, LSO). 세그먼트 40개를 만들 일을 CPU가 한 번으로 끝내는 것이고, 09장에서 본 "작은 컴퓨터"의 첫 번째 일이다.

## 3. 네트워크 계층: IP 패킷

```
┌───────────────────────────┐
│ IPv4 헤더 (20 바이트)     │
│  - 버전, IHL, TOS         │
│  - 전체 길이              │
│  - 식별자/플래그/오프셋   │
│  - TTL, 프로토콜, 체크섬  │
│  - 출발지 IP (4B)         │
│  - 목적지 IP (4B)         │
├───────────────────────────┤
│ TCP 세그먼트              │
└───────────────────────────┘
```

| 필드 | 이 요청에서의 값 | 왜 |
|:-----|:----------------|:---|
| 버전 | 4 | 18장. 이 PC에는 글로벌 IPv6 주소가 없다 |
| 전체 길이 | 115 | 헤더 20과 세그먼트 95 |
| TTL | 128 | [17](../17-network-layer-role)장. Windows의 시작값. 라우터마다 하나씩 줄어 도착한다 |
| 프로토콜 | 6 | 안에 든 것은 TCP |
| 출발지 IP | 이 PC의 공인 주소 | 18장. NAT 뒤가 아니라 그대로 간다 |
| 목적지 IP | 104.20.23.154 | [30](../30-dns-server-structure)장의 DNS가 준 두 주소 중 하나 |

IP 헤더도 커널이 붙인다. 목적지 주소는 요청을 만들기 전에 DNS로 얻어 둔 것이고, 그 주소를 [17](../17-network-layer-role)장의 라우팅 표에서 찾으면 이 PC의 망이 아니므로 기본 경로, 곧 게이트웨이로 보내야 한다는 답이 나온다. 이 판단이 다음 절의 목적지 MAC을 정한다. 헤더 체크섬 칸은 여기서도 비워 둔다.

## 4. 데이터링크 계층: 이더넷 프레임

```
┌────────┬────────┬────────┐
│ 이더넷 │  IP +  │  FCS   │
│ 헤더   │  TCP + │ (4B)   │
│ (14B)  │  HTTP  │ CRC-32 │
└────────┴────────┴────────┘
```

| 필드 | 크기 | 이 요청에서의 값 | 왜 |
|:-----|:-----|:----------------|:---|
| 목적지 MAC | 6B | 게이트웨이의 MAC | 상대는 다른 망에 있다. [13](../13-mac-address-structure)장 |
| 출발지 MAC | 6B | 이 카드의 주소. B4:2E:99로 시작 | 09장. 답장과 스위치의 학습에 쓰인다 |
| 타입 | 2B | 0x0800 | 안에 든 것은 IPv4 |

이더넷 헤더는 드라이버가 붙인다. 목적지 MAC이 example.com 서버의 MAC이 아니라 게이트웨이의 MAC인 것은 [15](../15-collision-free-structure)장에서 본 대로 다른 망의 이름은 링크 안에서 아무 뜻이 없기 때문이고, 그 MAC은 [13](../13-mac-address-structure)장에서 본 ARP 캐시에 Reachable로 늘 있다. 이 PC의 통신 거의 전부가 그 문을 지나기 때문이다. FCS는 드라이버가 아니라 **카드**가 붙인다. [12](../12-datalink-layer-ethernet)장의 CRC-32는 프레임의 모든 바이트를 훑어야 하므로 카드가 내보내는 순간에 계산하는 것이 싸다.

```
1) 같은 LAN:
   192.168.0.20의 MAC은? (브로드캐스트)
   00:1A:2B:...:5E (유니캐스트 응답)

2) 다른 LAN:
   목적지 MAC = 게이트웨이의 MAC
   (게이트웨이가 그다음 홉으로 전달)
```

캐시에 없는 상대라면 프레임을 만들기 전에 ARP가 먼저 나간다. 15장에서 본 대로 요청은 브로드캐스트, 답은 유니캐스트이고, 답이 올 때까지 이 요청의 패킷은 커널에 잠시 기다린다.

{{< callout type="info" >}}
FCS는 오류를 고치지 못하고 "깨졌다"만 안다. 12장에서 본 대로 받는 쪽 카드는 FCS가 안 맞는 프레임을 그냥 버리고 아무에게도 알리지 않는다. 다시 보내는 것은 [24](../24-tcp-structure)장의 TCP가 확인 응답이 안 오는 것을 보고 할 일이고, UDP라면 [27](../27-udp-structure)장에서 본 대로 응용 프로그램의 일이다. 2층이 복구까지 하지 않는 이유는 어차피 위층이 해야 하는 일을 두 번 하지 않으려는 것이다.
{{< /callout >}}

## 5. 물리 계층: 전기 신호

| 표준 | 속도 | 인코딩 | 왜 |
|:-----|:-----|:-------|:---|
| 10BASE-T | 10Mbps | 맨체스터 | 09장. 비트마다 전환해 시계를 싣는다 |
| 100BASE-TX | 100Mbps | 4B/5B + MLT-3 | [16](../16-ethernet-types-features)장. 100MHz 케이블에 넣으려고 |
| 1000BASE-T | 1Gbps | PAM-5, 네 쌍 | 이 PC의 링크. 전압 5단계로 한 번에 2비트 |

| 이 PC 카드의 설정 | 값 | 하는 일 |
|:-----------------|:---|:--------|
| 체크섬 오프로드 | IP, TCP, UDP 모두 Rx/Tx | 2절과 3절에서 비워 둔 칸을 카드가 채운다 |
| 대량 전송 오프로드 (LSO v2) | 켜짐 | 2절의 자르기 |
| 송신 링 | 128칸 | 보낼 프레임의 주소를 카드에 줄 세우는 자리 |
| 수신 링 | 512칸 | 받은 프레임을 놓을 메모리 자리 |
| 인터럽트 조절 | 켜짐 | 프레임마다 깨우지 않고 모아서 깨운다 |
| 수신 큐 (RSS) | 4개 | 받은 프레임을 CPU 코어 넷에 나눈다 |

보낼 때 카드가 하는 일은 이렇다.

1. 드라이버가 프레임이 놓인 메모리 주소를 송신 링의 한 칸에 적는다. 카드는 그 주소에서 프레임을 직접 읽어 온다(DMA). CPU가 바이트를 옮기지 않는다.
2. 비워 둔 체크섬 칸을 채운다. IP 헤더 체크섬과 TCP 체크섬을 카드가 계산해 넣고, LSO가 켜져 있으면 자르기도 여기서 한다.
3. 프레임 전체의 CRC-32를 계산해 FCS로 붙인다.
4. 앞에 프리앰블 8바이트를 붙이고, [09](../09-physical-layer-nic)장의 방식대로 비트를 전압으로 바꾼다. 이 PC는 PAM-5로 네 쌍에 나눠 싣는다.
5. 전이중이라 [15](../15-collision-free-structure)장에서 본 대로 듣지도 기다리지도 않고 바로 내보내며, 다음 프레임 앞에 12바이트 분량의 빈 시간을 둔다.

받을 때는 거꾸로다. 신호를 비트로 되돌리고, 프리앰블로 시계를 맞춘 뒤 프레임을 조립하고, 목적지 MAC이 나(또는 브로드캐스트, 가입한 멀티캐스트)가 아니면 그 자리에서 버린다. 내 것이면 FCS를 검사하고, 수신 링의 빈칸이 가리키는 메모리에 DMA로 놓은 뒤 CPU를 깨운다. 이 PC의 카드는 프레임마다 깨우지 않고 몇 개를 모아 한 번에 깨우며(인터럽트 조절), 깨울 코어를 넷 중 하나로 골라 준다(RSS). 09장에서 1Gbps는 초당 프레임 8만 개라고 했는데, 그것을 프레임마다 인터럽트로 받으면 CPU가 네트워크만 하다 끝난다.

{{< callout type="warning" >}}
체크섬 오프로드 때문에 생기는 착시가 있다. 캡처 도구는 커널이 카드에 넘기는 순간의 프레임을 복사하는데, 그때는 아직 체크섬 칸이 비어 있다. 그래서 Wireshark로 이 PC가 **보내는** 패킷을 보면 IP와 TCP 체크섬이 전부 "틀렸다"고 표시된다. 실제 회선에는 카드가 채운 올바른 값이 나가므로 오류가 아니고, 받는 패킷의 체크섬은 정상으로 보인다. 오프로드를 모르면 멀쩡한 카드를 고장으로 오해한다.
{{< /callout >}}

## 6. MTU와 단편화

```
이더넷 프레임 (최대):
┌────────┬────────┬────┐
│ 헤더   │ 1500B  │FCS │
│ 14B    │ 페이로드│4B │
└────────┴────────┴────┘
총 1518B (VLAN 없음 기준)
```

MTU는 [08](../08-encapsulation-decapsulation)장에서 본 대로 프레임 하나에 실을 수 있는 IP 패킷의 최대 크기이고, 이 PC의 이더넷은 1,500이다. 그보다 큰 패킷은 [17](../17-network-layer-role)장에서 본 대로 IP가 조각을 내지만, 요즘은 DF 플래그를 켜고 "너무 크다"는 ICMP를 받아 크기를 맞추는 경로 MTU 탐색을 쓰며, 08장에서 `ping -f -l 1472`로 이 PC의 한도를 직접 확인했다. 이 장의 요청은 133바이트라 한도와 거리가 멀다.

| 이 PC가 부팅 뒤 | 바이트 | 프레임 수 | 프레임당 평균 |
|:---------------|:-------|:----------|:-------------|
| 받은 것 | 9.2GB | 911만 | 1,011바이트 |
| 보낸 것 | 1.6GB | 472만 | 340바이트 |

카드의 통계가 MTU의 쓰임을 말해 준다. 받은 프레임은 평균 1,011바이트로 한도에 가깝고, 보낸 프레임은 340바이트로 작다. 이 PC는 받는 쪽이라 내려오는 데이터는 1,500씩 꽉 채운 프레임으로 오고, 올라가는 것은 이 장의 요청처럼 작은 요청과 [25](../25-sequence-ack-number)장의 빈 확인 응답이 대부분이기 때문이다. 확인 응답은 데이터 없이 헤더뿐이라 프레임의 최소 크기 64바이트로 나간다.

```bash
ip route get 104.20.23.154            # Linux. 경로와 MTU
ping -M do -s 1472 example.com        # Linux. DF를 켜고 1472
ping -f -l 1472 example.com           # Windows. 08장
#  1472 = 1500 - 20(IP) - 8(ICMP)
```

## 7. 역캡슐화 (수신)

```
[물리]    전기 신호 → 비트
    │
    ▼
[데이터링크]
  - 목적지 MAC 확인
  - FCS 검증 (CRC-32)
  - 이더넷 헤더/트레일러 제거
    │
    ▼
[네트워크]
  - 목적지 IP 확인
  - TTL, 체크섬 확인
  - IP 헤더 제거
    │
    ▼
[전송]
  - 목적지 포트 확인
  - TCP 체크섬, Seq/Ack 처리
  - TCP 헤더 제거
    │
    ▼
[응용]    HTTP 메시지 처리
```

서버의 답인 914바이트 프레임이 이 PC에 돌아오면 반대 순서로 뜯긴다. 층마다 순서가 같다. **내 것인가**를 먼저 보고, 내 것이면 **깨졌는가**를 본다. 카드는 목적지 MAC이 나인지를 보고 아니면 FCS도 계산하지 않고 버리며(12장), 커널의 IP는 목적지 주소가 나인지를 보고 체크섬을 확인하고, TCP는 목적지 포트로 소켓을 찾은 뒤 체크섬과 순서 번호를 확인한다. 남의 것에 계산을 쓰지 않으려는 순서이고, 그래서 [13](../13-mac-address-structure)장의 브로드캐스트만이 "내 것"의 문을 통과해 CPU까지 올라와 값을 치른다.

이 PC에서 그 답을 받는 데 드는 카드 쪽 시간은 다른 이야기다. 5절의 인터럽트 조절과 수신 큐 넷 덕에 커널은 프레임 여러 개를 한 번에 받아 코어 넷에서 나눠 처리하고, 체크섬은 카드가 이미 검사해 둔 표시만 본다. 서버 쪽에서 요청을 받아 답을 만드는 과정은 34장에서 본다.

**용어 정리**
- **PDU**: 층마다의 데이터 단위. 메시지, 세그먼트, 패킷, 프레임, 비트
- **NIC**: 랜 카드. 마지막 한 겹과 신호 변환, 그리고 오프로드를 맡는다
- **오프로드**: 커널이 할 일을 카드가 대신하는 것. 체크섬, 자르기(LSO), 받은 것 합치기
- **링 버퍼**: 보낼 프레임과 받을 자리의 메모리 주소를 줄 세운 칸. 이 PC는 128과 512
- **DMA**: 카드가 CPU를 거치지 않고 메모리를 직접 읽고 쓰는 것
- **인터럽트 조절 / RSS**: 모아서 깨우기 / 받은 프레임을 여러 코어에 나누기
- **FCS**: 카드가 붙이는 CRC-32. 깨졌다만 알고 고치지 않는다
- **MTU**: 프레임 하나에 실을 IP 패킷의 최대 크기. 1,500
