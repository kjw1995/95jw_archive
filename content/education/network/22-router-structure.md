[01](../01-network-basics)장에서 구글 DNS까지 가는 길에 이 PC를 나선 뒤 12개의 장비를 거친다고 했고 그 장비가 이 장의 라우터라고 했다. [17](../17-network-layer-role)장은 라우터를 "링크마다 2층을 가진 기계"라고 정의하고 라우팅 프로토콜의 동작을, [21](../21-subnet-structure)장은 마스크를 나르는 프로토콜을, [05](../05-office-lan-configuration)장은 두 대가 게이트웨이 주소 하나를 나눠 갖는 방법을 이 장으로 미뤘다. 원리는 셋이다. 첫째, **라우터는 표를 만드는 일과 표대로 보내는 일이 분리된 기계다.** 표를 만드는 일은 느려도 되고 보내는 일은 패킷마다 나노초 안에 끝나야 하므로, 앞의 일은 CPU가 프로토콜로 하고 뒤의 일은 전용 칩이 요약된 표로 한다. 둘째, **표의 한 줄에는 답이 셋 있다.** 어디로, 어느 문으로, 얼마나 좋은 길인가. 같은 목적지에 줄이 여럿이면 마스크 길이, 출처의 신뢰도, 메트릭의 순서로 고른다. 셋째, **표를 채우는 방법은 셋이고, 동적 라우팅의 차이는 "무엇을 가까움으로 보고 무엇을 주고받는가"의 차이다.** 이웃의 표를 믿는 RIP, 모두가 지도를 갖는 OSPF, 거리 대신 계약으로 고르는 BGP가 그 세 답이다. 이 장의 실측은 이 PC 라우팅 표 32줄의 출처, 기본 경로의 메트릭이 281인 이유, 그리고 VPN 어댑터가 회선 속도를 100Gbps라고 우기는 이유다.

## 1. 라우터의 역할

| 하는 일 | 뜻 | 왜 라우터가 하나 |
|:--------|:---|:----------------|
| 망 사이 전달 | 한 링크의 프레임을 벗겨 다른 링크의 프레임으로 | 17장. 링크마다 2층이 따로다 |
| 길 고르기 | 표에서 다음 라우터를 찾는다 | 망들의 망에서 방향을 정하는 유일한 장비 |
| 브로드캐스트 분리 | 옛 프레임을 버린다 | 14, 15장 |
| NAT, 방화벽 | 경계에서 주소를 바꾸고 거른다 | 04장. 경계에 서 있으니 여기서 한다 |

스위치가 있어도 다른 망끼리는 통하지 않는다. [14](../14-switch-structure)장의 스위치는 프레임의 겉봉인 MAC 주소만 읽고, 다른 망의 기계는 MAC으로 가리킬 수 없기 때문이다. 라우터는 그 안의 IP 헤더까지 읽어 192.168.1.0/24와 192.168.2.0/24 사이를 잇는다.

```
┌─ 제어면 (CPU) ────────────┐
│ 라우팅 프로토콜 → RIB     │
└─────────────┬─────────────┘
              ▼ 요약해 내려보냄
┌─ 전달면 (ASIC) ───────────┐
│ 패킷 → FIB 조회 → 포트    │
└───────────────────────────┘
```

라우터의 안은 두 층이다. 위층(제어면)은 CPU가 이웃 라우터와 프로토콜로 대화하며 길을 계산해 라우팅 표(RIB)를 만든다. 느려도 된다. 길은 초 단위로 바뀌기 때문이다. 아래층(전달면)은 패킷이 올 때마다 목적지 주소로 표를 찾아 포트로 내보낸다. [12](../12-datalink-layer-ethernet)장에서 1Gbps 회선은 초당 프레임 148만 개라고 했고, 10Gbps 포트 수십 개면 나노초마다 한 번씩 표를 찾아야 한다. 그래서 CPU가 만든 표를 조회에 맞게 요약한 전달 표(FIB)를 전용 칩에 내려보내고, 칩이 14장의 CAM과 같은 방식으로 한 번에 찾는다. 두 일을 나눈 것이 라우터 구조의 핵심이고, 14장에서 본 L3 스위치란 이 아래층을 스위치 칩에 넣은 것이다. 반대로 [04](../04-home-lan-configuration)장의 가정용 공유기는 CPU가 두 일을 다 하며, 그래서 값싸고 기가비트를 다 못 채우기도 한다.

## 2. 허브·스위치·라우터 비교

| 항목 | 허브 | 스위치 | 라우터 |
|:-----|:-----|:-------|:-------|
| 층 | 1 | 2 | 3 |
| 읽는 것 | 없음 | MAC 주소 | IP 주소 |
| 보내는 법 | 모든 포트로 | 표의 포트로 | 표의 다음 라우터로 |
| 표 | 없다 | MAC 표. 스스로 배운다 | 라우팅 표. 스스로 못 배운다 |
| 브로드캐스트 | 넘긴다 | 넘긴다 (VLAN 안에서) | 막는다 |
| 쓰이는 곳 | 사라졌다 | 망 안 | 망 사이 |

[01](../01-network-basics)장의 원리대로 세 장비의 차이는 어디까지 읽는가이고, 그 차이가 표의 성격을 가른다. 스위치의 표는 지나가는 프레임의 출발지를 엿보아 스스로 채워졌다. 라우터의 표는 그렇게 채울 수 없다. 지나가는 패킷은 "출발지 기계가 저쪽에 있다"는 것만 말해 줄 뿐, 라우터에게 필요한 것은 세상의 **망들이 어디에 어떻게 이어져 있는가**라는 지도이기 때문이다. 기계 하나의 위치는 엿볼 수 있어도 지도는 엿볼 수 없다. 그래서 라우터의 표는 사람이 적거나, 라우터끼리 일부러 주고받아 만든다. 5절과 6절의 이야기다.

## 3. 기본 게이트웨이

```
목적지 IP AND 내 마스크
      │
  같은 망인가?
  ├─ 예   → ARP로 직접
  └─ 아니오 → 게이트웨이의 MAC으로
```

기본 게이트웨이는 호스트가 자기 망 밖으로 가는 패킷을 전부 맡기는 라우터의 주소다. [03](../03-lan-and-wan)장에서 본 판단이고, 17장에서 이것이 실은 호스트 라우팅 표의 0.0.0.0/0 한 줄임을 봤다. 호스트가 게이트웨이 **하나만** 아는 이유는 호스트에게 지도를 주지 않기 때문이다. 세상의 모든 망을 PC마다 알려 줄 수는 없고 알려 줄 필요도 없다. "내 망이 아니면 저기로"만 알면 되고, 더 나은 라우터가 같은 링크에 있으면 17장의 ICMP 리다이렉트로 라우터가 알려 준다.

```bash
ipconfig               # Windows. 기본 게이트웨이 : 192.168.1.1
ip route show          # Linux. default via 192.168.1.1 dev eth0
```

```
[R1 활성]──┐
           ├─ 가상 IP .1, 가상 MAC
[R2 대기]──┘
 PC의 게이트웨이 = .1 (누가 살아 있든)
```

하나만 안다는 것은 그 하나가 죽으면 전부 끊긴다는 뜻이다. 05장에서 미룬 이중화의 답이 **가상 게이트웨이**(VRRP, Cisco는 HSRP)다. 라우터 두 대가 진짜 주소 말고 가상 IP 하나와 가상 MAC 하나를 나눠 갖고, 활성 쪽이 그 주소로 답하며 1초마다 "살아 있다"를 알린다. 세 번 끊기면 대기 쪽이 같은 가상 MAC으로 프레임을 받기 시작한다. PC는 게이트웨이가 .1이라는 것과 [15](../15-collision-free-structure)장의 ARP 캐시에 적힌 MAC이 그대로이므로 아무것도 모른 채 통신을 잇는다. 가상 MAC이 00:00:5E로 시작하는 것은 그 OUI가 [13](../13-mac-address-structure)장의 멀티캐스트 01:00:5E와 같은 인터넷 번호 기구의 것이기 때문이다.

## 4. 라우팅과 라우팅 표

| 열 | 뜻 | 왜 있나 |
|:---|:---|:--------|
| 목적지 | 망 주소와 마스크 | 20장. 기계가 아니라 망을 적는다 |
| 다음 홉 | 넘겨줄 라우터의 주소. 직접 연결이면 on-link | 링크 너머의 첫 라우터까지만 알면 된다 |
| 인터페이스 | 어느 포트로 | 다음 홉이 어느 링크에 있는가 |
| 메트릭 | 길의 비용. 작을수록 좋다 | 같은 목적지에 길이 여럿일 때 |
| 출처 | 직접 연결, 정적, 어느 프로토콜 | 출처마다 믿는 정도가 다르다 |

```bash
$ ip route show
default via 192.168.1.1 dev eth0 metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10
192.168.2.0/24 via 192.168.1.254 dev eth0 metric 20
```

Linux의 출력에 표의 열이 다 있다. `via`가 다음 홉, `dev`가 인터페이스, `metric`이 메트릭, `proto kernel`이 출처(운영체제가 인터페이스 설정에서 스스로 만든 줄)다. 이 PC의 Windows 표 32줄을 출처로 나누면 29줄이 Local, 곧 인터페이스에 주소를 준 순간 운영체제가 스스로 만든 줄이고, 3줄만 사람과 프로그램이 넣은 것이다. 기본 경로 한 줄과 VPN이 넣은 두 줄이다. 라우터도 같다. 직접 연결된 망은 저절로 표에 들어가고, 그 너머는 누군가 알려 줘야 한다.

```
같은 목적지에 줄이 여럿이면
 1) 마스크가 긴 줄        (최장 일치)
 2) 출처가 믿을 만한 줄   (관리 거리)
 3) 메트릭이 작은 줄
```

| 목적지 후보 | 프리픽스 | 순위 |
|:-----------|:---------|:-----|
| 192.168.1.50/32 | /32 | 1 |
| 192.168.1.0/24 | /24 | 2 |
| 192.168.0.0/16 | /16 | 3 |
| 0.0.0.0/0 | /0 | 4. 기본 경로 |

첫째 기준인 최장 일치는 17장에서 봤다. 가장 구체적인 정보가 가장 정확하다. 둘째 기준은 마스크 길이가 같은 줄이 출처만 다를 때다. 같은 망을 사람이 적은 줄과 RIP가 배운 줄이 함께 있으면, 라우터는 출처마다 정해 둔 **관리 거리**로 고른다. Cisco의 값은 직접 연결 0, 정적 1, OSPF 110, RIP 120이고, 작을수록 믿는다. 사람이 적은 것을 프로토콜이 배운 것보다 믿고, 지도를 계산하는 OSPF를 소문을 믿는 RIP보다 믿는다는 뜻이다. 셋째 기준이 메트릭이고, 같은 프로토콜이 같은 망에 길을 둘 알려 줄 때 비로소 쓰인다.

Windows의 메트릭은 두 값의 합이다. 이 PC의 기본 경로는 `route print`에서 281인데, 줄 자체의 값 256에 인터페이스의 값 25를 더한 것이다. 인터페이스의 값은 운영체제가 **회선 속도로 자동 계산**한다. 1Gbps인 이더넷은 25이고, 속도가 빠를수록 작다. 같은 목적지로 가는 길이 두 인터페이스에 있으면 빠른 회선이 이기게 하려는 것이다. 이 규칙에는 부작용이 있다. 이 PC의 VPN 어댑터는 자기 회선 속도를 100Gbps라고 보고하고, 그래서 메트릭이 5다. 실제 속도가 아니라 "내 줄이 이기게 해 달라"는 신호다. Hyper-V의 가상 어댑터는 반대로 5000을 손으로 박아 두어 절대 이기지 못하게 했다. 메트릭은 물리량이 아니라 우선순위의 표현이다.

## 5. 정적 라우팅 vs 동적 라우팅

| 구분 | 정적 | 동적 | 왜 |
|:-----|:-----|:-----|:---|
| 누가 적나 | 사람 | 라우터끼리 프로토콜로 | 망이 수천 개면 사람이 못 적는다 |
| 길이 끊기면 | 사람이 고칠 때까지 끊긴다 | 스스로 돌아간다 | 01장의 메시형은 자동일 때만 산다 |
| 비용 | 없다 | CPU와 회선을 조금 쓴다 | 대화에는 값이 든다 |
| 예측 | 적힌 대로 | 계산 결과에 따라 | 사고가 나면 정적이 읽기 쉽다 |
| 어울리는 곳 | 출구가 하나인 작은 망, 가정 | 여러 길이 있는 회사와 인터넷 | 길이 하나면 고를 것이 없다 |

```bash
ip route add 192.168.2.0/24 via 192.168.1.254 dev eth0     # Linux
route add 192.168.2.0 mask 255.255.255.0 192.168.1.254 -p  # Windows
Router(config)# ip route 192.168.2.0 255.255.255.0 192.168.1.254
```

가정과 작은 사무실은 출구가 통신사 하나뿐이라 기본 경로 한 줄이면 끝나고, 그것이 정적 라우팅이다. 동적 라우팅이 필요한 곳은 **길이 둘 이상인 곳**이다. 본사와 지사가 두 회선으로 이어져 있으면 한쪽이 끊겼을 때 다른 쪽으로 돌아가야 하고, 그 판단을 사람이 새벽 세 시에 할 수는 없다. 둘을 섞기도 한다. 동적으로 배운 길이 사라졌을 때만 살아나도록 관리 거리를 일부러 크게 준 정적 경로를 예비로 두는 식이고, 4절의 관리 거리가 있어서 가능한 방법이다.

## 6. 주요 동적 라우팅 프로토콜

```
RIP    이웃의 표를 믿는다   (소문)
OSPF   모두가 지도를 갖는다 (지도)
BGP    길 전체와 정책       (계약)
```

| 구분 | 무엇을 주고받나 | 무엇이 가까움인가 | 대표 |
|:-----|:---------------|:-----------------|:-----|
| 거리 벡터 | 이웃에게 "나는 어디까지 몇 홉"이라는 표 | 홉 수 | RIP |
| 링크 상태 | 모두에게 "내 링크는 이렇다"는 지도 조각 | 링크 비용의 합 | OSPF, IS-IS |
| 경로 벡터 | 이웃에게 "이 망까지의 AS 목록" | 정책 | BGP |
| 혼합 | 이웃에게 표, 그러나 계산은 정교하게 | 복합 | EIGRP (Cisco) |

라우터끼리 무엇을 주고받는가가 프로토콜을 가른다. 표를 통째로 건네면 받는 쪽은 "이웃이 B까지 3홉이라니 나는 4홉"이라고 적고 끝이다. 계산이 없어 쉽지만 이웃이 틀리면 나도 틀린다. 지도 조각을 건네면 받는 쪽이 조각을 모아 지도를 그리고 스스로 최단 경로를 계산한다. 무겁지만 소문에 속지 않는다. 그리고 인터넷처럼 주인이 다른 망 사이에서는 가까움보다 **누구를 거쳐도 되는가**가 먼저이므로, 거리가 아니라 길 전체와 정책을 주고받는다.

### RIP: 이웃을 믿는다

| 항목 | 값 | 왜 |
|:-----|:---|:---|
| 메트릭 | 홉 수 | 계산이 없는 가장 단순한 잣대 |
| 한계 | 15홉. 16은 도달 불가 | 소문이 돌며 커지는 것을 끊으려고 |
| 갱신 | 30초마다 표 전체를 이웃에게 | 변화를 알리는 방법이 이것뿐이다 |
| 마스크 | 2판부터 함께 보낸다 | 21장. 1판은 VLSM이 안 됐다 |
| 쓰임 | 작은 망. 지금은 드물다 | 수렴이 분 단위다 |

15홉이라는 이상한 한계가 거리 벡터의 약점을 그대로 보여 준다. 망 B가 사라졌을 때, 그 소식이 퍼지기 전에 이웃 라우터가 "나는 B까지 2홉"이라는 옛 표를 보내면, 나는 B가 살아 있는 줄 알고 "나는 3홉"이라고 적고, 이웃은 내 표를 받아 4홉으로 고치는 식으로 둘이 서로를 믿으며 홉 수만 끝없이 키운다(무한 세기). 이것을 어딘가에서 끊어야 해서 16을 무한으로 정했고, 그래서 RIP 망은 15홉을 넘을 수 없다. 이웃에게서 배운 길을 그 이웃에게 되돌려 알리지 않는 규칙(스플릿 호라이즌)도 같은 병의 처방이다. 30초마다 표 전체를 보내는 것과 합쳐, 링크 하나가 끊긴 뒤 모든 라우터가 새 길에 합의하기까지 몇 분이 걸린다.

### OSPF: 모두가 지도를 갖는다

| 항목 | 값 | 왜 |
|:-----|:---|:---|
| 주고받는 것 | 링크 상태 광고(LSA) | 표가 아니라 지도 조각 |
| 계산 | 다익스트라 최단 경로 | 지도가 있으니 각자 계산한다 |
| 메트릭 | 비용 = 100Mbps ÷ 링크 속도 | 빠른 링크가 싸다 |
| 이웃 확인 | 10초마다 hello, 40초 무응답이면 죽은 것 | 링크가 죽은 것을 초 단위로 안다 |
| 주소 | 224.0.0.5, 6 | 19장. 같은 링크의 라우터들에게만 |
| 구조 | 영역(Area). 0번이 뼈대 | 지도가 커지면 계산도 커진다 |

OSPF의 라우터는 자기 링크의 상태("이 링크는 저 라우터와 이어져 있고 비용은 이것")를 모든 라우터에게 그대로 퍼뜨린다. 모두가 같은 지도를 갖게 되고, 각자 자기를 출발점으로 최단 경로를 계산해 표를 만든다. 소문이 아니라 원본을 받으니 무한 세기가 없고, 링크가 죽으면 그 사실 하나만 퍼뜨리면 되므로 수렴이 초 단위다. 대가는 계산이다. 라우터가 수백 대면 지도가 커지고 링크 하나가 바뀔 때마다 모두가 다시 계산하므로, 망을 영역으로 나누어 영역 안의 지도만 갖고 영역 사이는 요약해 넘긴다. 21장의 경로 요약이 여기서 쓰인다. 메트릭의 기본 계산에는 오래된 함정이 있다. 참조 속도가 100Mbps라 100Mbps 링크가 비용 1인데, 1Gbps도 10Gbps도 1보다 작아질 수 없어 셋이 같은 비용이 된다. 그래서 요즘 망은 참조 속도를 올려 설정한다.

### BGP: 거리가 아니라 계약

| 항목 | 값 | 왜 |
|:-----|:---|:---|
| 단위 | AS. 통신사나 큰 회사 하나 | 인터넷은 주인이 다른 망 7만여 개의 연합이다 |
| 주고받는 것 | 망까지의 AS 목록 | 길 전체가 보여야 고리를 피하고 정책을 건다 |
| 연결 | TCP 179번 | 표를 잃으면 안 되니 신뢰 연결 위에서, 바뀐 것만 보낸다 |
| 고르는 기준 | 정책. 로컬 선호도, AS 경로 길이, MED | 짧은 길보다 돈이 덜 드는 길 |
| 표의 크기 | 100만 줄 안팎 | 17장. 세계의 모든 망 |
| 수렴 | 느리다. 분 단위 | 안정이 속도보다 중요한 곳 |

통신사 사이에서는 "가장 짧은 길"이 답이 아니다. 경쟁사의 망을 공짜로 지나갈 수는 없고, 고객의 트래픽은 계약한 회선으로 보내야 한다. 그래서 BGP는 홉 수도 링크 비용도 아닌 **정책**으로 고른다. 어느 AS를 거쳐 왔는지 목록을 통째로 나르므로 자기 번호가 이미 있는 길은 고리로 알고 버리고, 특정 AS를 거치는 길은 피하거나 선호하도록 규칙을 건다. 이 PC에서 구글까지 12홉 중 7번째부터 구글 망이었던 것은 [17](../17-network-layer-role)장에서 봤는데, 이 PC의 통신사와 구글이 어디서 만나는지가 그들의 BGP 정책이다. 라우팅 정보를 TCP 위에서 나르는 것은 표 한 줄을 잃는 것이 곧 망 하나를 잃는 것이기 때문이고, 그래서 주기적으로 전부 보내는 대신 연결을 유지하며 바뀐 것만 보낸다.

| 항목 | RIP | OSPF | EIGRP | BGP |
|:-----|:----|:-----|:------|:----|
| 방식 | 거리 벡터 | 링크 상태 | 혼합 | 경로 벡터 |
| 메트릭 | 홉 수 | 비용 | 대역폭, 지연 등 복합 | 정책 |
| 최대 홉 | 15 | 없음 | 255 | 없음 |
| 수렴 | 분 | 초 | 초 | 분 |
| VLSM | 2판만 | 된다 | 된다 | 된다 |
| 쓰임 | 작은 망 | 회사, 통신사 안 | Cisco 망 | AS 사이 |

| 망의 크기 | 고르는 것 | 왜 |
|:----------|:----------|:---|
| 라우터 10대 이하 | 정적, RIP 2판 | 길이 몇 개 없다 |
| 10~100대 | OSPF, EIGRP | 길이 여럿이고 초 단위 복구가 필요하다 |
| 100대 이상 | OSPF 영역 구조, IS-IS | 지도가 너무 커서 나눠야 한다 |
| 인터넷 연결 | BGP | 남의 망과는 정책으로만 대화한다 |

## 7. 트러블슈팅 절차

| 순서 | 확인 | 왜 이 순서인가 |
|:-----|:-----|:--------------|
| 1 | `ping 게이트웨이` | 내 링크와 첫 라우터가 사는지. 여기가 죽으면 나머지는 볼 것도 없다 |
| 2 | `route print`, `ip route show` | 기본 경로가 있는지, 엉뚱한 줄이 이기고 있는지 |
| 3 | `tracert`, `traceroute` | 어느 홉까지 가고 어디서 멈추는지 |
| 4 | 라우터 설정 | 인터페이스가 살아 있는지, 프로토콜 이웃이 맺어졌는지 |

```bash
tracert 192.168.3.10
  1  192.168.1.1     1 ms   기본 게이트웨이
  2  192.168.2.2     5 ms   중간 라우터
  3  *  *  *                여기서 멈춤
  4  *  *  *
```

가까운 곳부터 먼 곳으로 보는 이유는 문제가 겹치기 때문이다. 게이트웨이도 안 되는데 원격 서버를 의심하는 것은 순서가 틀렸다. `*`를 읽을 때는 조심해야 한다. 17장에서 이 PC에서 구글까지의 4번과 5번 홉이 `*`였지만 그 뒤는 멀쩡히 이어졌다. ICMP를 안 보내는 라우터일 뿐이다. 진짜 막힌 곳은 그 홉부터 **끝까지** `*`이거나, "목적지 도달 불가"가 돌아오는 곳이다. 그 라우터의 표에 목적지 망으로 가는 줄이 없거나(기본 경로도 없거나), 돌아오는 길이 없는 경우가 대부분이다. 길은 왕복이라 가는 표만 맞고 오는 표가 틀려도 같은 증상이 난다.

{{< callout type="warning" >}}
표를 볼 때는 최장 일치를 머릿속에서 같이 돌려야 한다. 기본 경로가 멀쩡한데도 특정 망만 안 될 때는 VPN이나 가상 어댑터가 넣은 더 긴 마스크의 줄이 그 망을 가로채고 있는 경우가 흔하다. 이 PC의 VPN 어댑터가 넣은 /32 줄이 그 예이고, 4절에서 본 대로 그 줄은 메트릭까지 낮다. "가까운 곳부터"는 물리적 거리만이 아니라 표의 줄에도 해당한다.
{{< /callout >}}

## 8. 자주 쓰는 명령어

```bash
# Windows
ipconfig                   # 주소, 마스크, 게이트웨이
route print -4             # 라우팅 표. 메트릭은 두 값의 합
Get-NetRoute -AddressFamily IPv4   # 출처(Protocol)까지
tracert <host>

# Linux
ip addr show
ip route show
ip route get 8.8.8.8       # 이 목적지에 어느 줄이 이기는가
traceroute <host>

# Cisco IOS
show ip interface brief    # 포트가 살아 있는가
show ip route              # 출처 코드 C, S, O, B
show ip protocols
show ip ospf neighbor      # 이웃이 맺어졌는가
```

`ip route get`과 `show ip route`의 출처 코드는 4절의 기준을 눈으로 확인하는 도구다. 목적지 하나를 주면 어느 줄이 이겼는지 알려 주고, 표의 각 줄 앞에는 직접 연결(C), 정적(S), OSPF(O), BGP(B) 같은 출처가 붙어 있다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 라우터 | 링크마다 2층을 가진 3층 장비 | 프레임을 벗기고 새로 싼다 |
| 제어면과 전달면 | 표 만들기와 표대로 보내기 | 하나는 초 단위, 하나는 나노초 단위 |
| L3 스위치, 공유기 | 전달면을 칩에 / CPU가 다 한다 | 값과 속도의 차이 |
| 스위치 표와 라우터 표 | 엿보아 배운다 / 못 배운다 | 위치는 엿볼 수 있어도 지도는 못 엿본다 |
| 기본 게이트웨이 | 호스트가 아는 유일한 라우터 | 호스트에게는 지도를 주지 않는다 |
| VRRP, HSRP | 가상 IP와 가상 MAC을 두 대가 나눔 | 하나뿐인 것을 둘로 |
| 표의 한 줄 | 목적지, 다음 홉, 인터페이스, 메트릭, 출처 | 첫 라우터까지만 알면 된다 |
| 고르는 순서 | 최장 일치 → 관리 거리 → 메트릭 | 구체성, 신뢰도, 비용의 순 |
| 이 PC의 281 | 256 + 25 | 인터페이스 값은 회선 속도에서 나온다 |
| VPN의 100Gbps | 메트릭 5를 얻으려는 신호 | 메트릭은 우선순위의 표현이다 |
| 정적 | 출구가 하나면 충분 | 고를 길이 없다 |
| RIP | 이웃의 표를 믿는다 | 무한 세기 때문에 15홉 |
| OSPF | 모두가 지도를 갖고 계산한다 | 원본을 받으니 소문에 안 속는다 |
| BGP | AS 경로와 정책 | 남의 망과는 계약으로 |
| tracert의 별표 | 끝까지 이어지면 진짜 막힘 | ICMP를 안 보내는 라우터가 있다 |

{{< callout type="info" >}}
**용어 정리**
- **라우터**: 링크를 둘 이상 갖고 IP 주소로 다음 링크를 고르는 장비
- **제어면 / 전달면**: 표를 만드는 CPU 쪽 / 표대로 보내는 칩 쪽
- **RIB / FIB**: 라우팅 표 / 조회용으로 요약한 전달 표
- **기본 게이트웨이**: 호스트 라우팅 표의 0.0.0.0/0이 가리키는 라우터
- **VRRP / HSRP**: 라우터 두 대가 가상 IP와 가상 MAC을 나눠 갖는 이중화
- **메트릭**: 길의 비용. 작을수록 좋다. Windows는 줄의 값과 인터페이스의 값을 더한다
- **관리 거리**: 출처마다 정한 신뢰도. 직접 연결 0, 정적 1, OSPF 110, RIP 120
- **거리 벡터 / 링크 상태 / 경로 벡터**: 표를 나눈다 / 지도 조각을 나눈다 / AS 목록을 나눈다
- **AS**: 한 주체가 관리하는 망의 묶음. BGP의 단위
- **IGP / EGP**: AS 안의 프로토콜(RIP, OSPF) / AS 사이의 프로토콜(BGP)
- **수렴**: 변화 뒤 모든 라우터의 표가 다시 맞아떨어지는 것
{{< /callout >}}
