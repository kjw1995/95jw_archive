이 시리즈는 HTTP를 다루고, 이 장은 그 바닥을 한 장에 깐다. 인터넷, IP, TCP와 UDP, 포트, DNS, URL, 그리고 브라우저가 주소창의 글자를 화면으로 바꾸기까지의 순서다. 네트워크 시리즈가 36장에 걸쳐 본 것을 HTTP의 눈으로 접은 것이라 자세한 근거는 그쪽 장으로 잇고, 여기서는 "HTTP가 왜 그 위에 그렇게 놓였는가"만 본다. 원리는 셋이다. 첫째, **인터넷은 주소만 보고 패킷을 던지는 망이다.** IP는 상대가 켜져 있는지 묻지 않고, 도착했는지 확인하지 않고, 도착한 컴퓨터 안의 어느 프로그램 것인지도 모른다. 이 세 구멍이 TCP와 UDP와 포트가 있는 이유다. 둘째, **TCP는 IP 위에 약속을 얹고 UDP는 이름표만 얹는다.** 웹이 TCP를 고른 이유와 HTTP/3가 UDP로 돌아간 이유가 같은 문장 안에 있다. 셋째, **이름과 주소는 층이 다르다.** 포트는 컴퓨터 안의 프로그램 주소이고, DNS는 이름을 주소로 바꾸는 사전이며, URL은 그 셋을 한 줄에 적는 표기다. 브라우저가 하는 일은 이 셋을 순서대로 푸는 것이다. 이 PC에서 example.com까지 실측한 값(네트워크 [32](../../32-network-card-data-transfer)~[34](../../34-web-server-data-processing)장)을 그대로 가져와 썼다.

## 1. 인터넷 통신

```text
┌────────┐   ┌────┐  ┌────┐   ┌────────┐
│ Client │──→│ R1 │→ │ R2 │──→│ Server │
└────────┘   └────┘  └────┘   └────────┘
             (수많은 중간 노드 = 라우터)
```

| 요소 | 하는 일 | 왜 |
|:-----|:--------|:---|
| 패킷 | 데이터를 잘라 주소를 붙인 조각 | 회선을 독점하지 않고 나눠 쓰려고. 네트워크 [01](../../01-network-basics)장 |
| 라우터 | 표를 보고 다음 홉으로 넘기고 잊는다 | 전체 경로를 아는 곳이 없다. 네트워크 [22](../../22-router-structure)장 |
| 클라이언트-서버 | 한쪽이 묻고 한쪽이 답한다 | HTTP의 모양이 이것이다. [02](../02-http-basics)장 |

인터넷은 전용선이 아니라 **패킷 교환망**이다. 보낼 것을 조각내어 조각마다 목적지 주소를 붙이고, 라우터는 조각이 올 때마다 자기 표를 보고 다음 라우터로 넘긴 뒤 잊는다. 이 PC에서 example.com까지 tracert로 세면 11홉이고, 그중 셋은 답을 하지 않는 라우터였으며, 왕복은 32ms다. 전체 길을 아는 곳은 어디에도 없고 라우터마다 "다음"만 알기 때문에, 같은 상대에게 보낸 조각이 서로 다른 길로 갈 수 있다. 첫째 원리의 뿌리가 여기다. 망은 조각을 던질 뿐이고, 순서와 도착은 끝에 있는 컴퓨터끼리 맞춰야 한다.

## 2. IP (Internet Protocol)

```text
┌───────────────────────┐
│ 출발지 IP │ 목적지 IP │
├───────────────────────┤
│        데이터         │
└───────────────────────┘
```

IP는 컴퓨터마다 주소를 하나씩 주고, 그 주소를 붙인 **패킷** 단위로 조각을 목적지까지 나르는 규칙이다. 패킷의 앞머리에는 출발지와 목적지 주소, 그리고 라우터를 하나 지날 때마다 1씩 줄어드는 TTL이 있다. 이 PC의 패킷은 128로 출발해 118로 example.com에 도착했고(네트워크 [34](../../34-web-server-data-processing)장), 답은 64로 출발해 54로 돌아온다. 양쪽 다 라우터 열 대를 지난 것이다.

| 한계 | 뜻 | 왜 그렇게 만들었나 |
|:-----|:---|:------------------|
| 비연결성 | 상대가 꺼져 있어도 일단 보낸다 | 보내기 전에 묻는 절차가 없어야 라우터가 가볍다 |
| 비신뢰성 | 잃어버리고, 순서가 바뀌고, 겹칠 수 있다 | 라우터는 넘기고 잊는다. 기억하면 느려진다 |
| 포트 부재 | 컴퓨터까지만 안다 | IP의 일은 컴퓨터 사이. 프로그램 구분은 위층의 몫 |

세 한계는 결함이 아니라 설계다. 라우터가 연결을 기억하고 도착을 확인하고 프로그램까지 구분하면, 초당 수백만 패킷을 넘기는 장비가 느려지고 라우터 하나가 죽을 때 그 기억도 함께 죽는다. 그래서 인터넷은 어려운 일을 전부 **양 끝의 컴퓨터**에 맡겼고, 그 일을 하는 것이 다음 절의 TCP와 UDP, 그리고 포트다. IP의 주소 체계 자체는 네트워크 [17](../../17-network-layer-role)·[18](../../18-ip-address-structure)장에서 봤다.

| 구분 | IPv4 | IPv6 | 왜 |
|:-----|:-----|:-----|:---|
| 주소 길이 | 32비트, 약 43억 개 | 128비트 | 43억은 사람 수보다 적다 |
| 표기 | `192.168.0.1` | `2606:4700:10::6814:179a` | 16진수 여덟 덩어리. 0은 `::`로 줄인다 |
| 주소 고갈 | 2011년 IANA 소진 | 사실상 없음 | |
| 헤더 | 가변 20~60B | 고정 40B | 라우터가 길이를 계산하지 않게 |
| IPsec | 선택 | 선택. 한때 필수, 2011년부터 권고 | 모든 기기에 강제하기엔 무거웠다 |

이 PC에서 example.com의 IPv6 주소를 물으면 `2606:4700:10::6814:179a`가 온다. 끝의 `6814:179a`를 16진수로 읽으면 104.20.23.154, 곧 같은 서버의 IPv4 주소다. 클라우드플레어가 v4 주소를 v6 주소 안에 박아 둔 것이고, IPv6가 새 세계가 아니라 같은 서버로 가는 더 긴 주소라는 것을 보여 준다.

| 사설 대역 | 범위 | 왜 |
|:----------|:-----|:---|
| 10.0.0.0/8 | 10.0.0.0 ~ 10.255.255.255 | 큰 회사용. 1,600만 개 |
| 172.16.0.0/12 | 172.16.0.0 ~ 172.31.255.255 | 중간. 도커가 즐겨 쓴다 |
| 192.168.0.0/16 | 192.168.0.0 ~ 192.168.255.255 | 집과 작은 사무실. 공유기의 기본값 |

{{< callout type="info" >}}
공인 주소가 43억 개로 모자라니 집 안에서는 누구나 같은 사설 주소를 쓰고, 밖으로 나갈 때만 공유기가 자기 공인 주소로 바꿔 내보낸다. 이것이 NAT이고, 공유기 뒷면의 `192.168.0.1`이 사설 주소다. 밖에서 안으로는 길이 없으므로 서버를 집에 두려면 포트 포워딩이나 VPN이 필요하다. 네트워크 [04](../../04-home-lan-configuration)장.
{{< /callout >}}

## 3. TCP (Transmission Control Protocol)

```text
┌──────────────────────────┐
│ IP Header                │
│  src IP / dst IP         │
├──────────────────────────┤
│ TCP Header               │
│  src port / dst port     │
│  seq / ack / flags       │
├──────────────────────────┤
│  데이터                  │
└──────────────────────────┘
```

| 특징 | 어떻게 | 왜 |
|:-----|:-------|:---|
| 연결 지향 | 세 번 인사(3-way handshake) | 상대가 있고 듣고 있는지를 먼저 확인한다. IP는 안 묻는다 |
| 신뢰성 | ACK, 재전송, 체크섬 | 잃어버린 것을 끝에서 알아채고 다시 보낸다 |
| 순서 보장 | 순서 번호로 재조립 | 패킷마다 다른 길을 오므로 |
| 흐름 제어 | 받는 쪽 버퍼 크기만큼만 | 받는 쪽이 넘치면 그것도 손실이다 |

```text
Client              Server
  │── SYN ──────────→│
  │←──── SYN+ACK ────│
  │── ACK + 요청 ───→│   1 RTT 뒤
```

TCP는 IP의 세 구멍 중 둘을 메운다. 보내기 전에 세 번 인사해 상대가 듣고 있음을 확인하고(비연결성), 바이트마다 번호를 붙여 빠진 것은 다시 보내고 뒤바뀐 것은 제자리에 놓는다(비신뢰성). 이 일을 라우터가 아니라 양 끝의 운영체제가 하는 것이 둘째 원리이고, 그 값은 **왕복 한 번**이다. 이 PC의 curl은 example.com과 연결을 맺는 데 41ms를 썼는데(네트워크 [29](../../29-web-server-structure)장) 왕복 32ms에 처리 시간이 붙은 값이다. 인사가 1.5 RTT라는 말도 있지만 클라이언트는 세 번째 인사(ACK)에 요청을 실어 보내므로, 요청이 떠나는 시점은 1 RTT 뒤다. 웹이 TCP를 고른 이유는 단순하다. HTML은 한 바이트가 빠져도 깨지고, 순서가 바뀌면 다른 문서가 된다. 헤더의 칸과 번호의 규칙은 네트워크 [24](../../24-tcp-structure)·[25](../../25-sequence-ack-number)장에서 본다.

## 4. UDP (User Datagram Protocol)

| 항목 | TCP | UDP | 왜 다른가 |
|:-----|:----|:----|:---------|
| 연결 | 세 번 인사 | 없음 | UDP는 확인할 것이 없다 |
| 신뢰성 | 보장 | 없음 | 잃어도 되는 데이터가 있다 |
| 순서 | 보장 | 없음 | 늦게 온 것은 버리면 된다 |
| 헤더 | 20B 이상 | 8B | 포트 둘, 길이, 체크섬뿐 |
| 첫 지연 | 왕복 하나가 먼저 든다 | 바로 보낸다 | |
| 용도 | 웹, 메일, SSH | DNS, 스트리밍, 게임, QUIC | 늦은 프레임은 없는 프레임과 같다 |

UDP는 IP 패킷에 포트 두 개와 길이와 체크섬, 8바이트만 얹은 것이다. 세 구멍 중 포트 하나만 메우고 나머지 둘은 그대로 둔다. 그래서 인사 없이 첫 패킷부터 데이터를 보내고, 잃어버리면 그만이다. 영상 통화의 0.1초 전 프레임을 다시 받아 봐야 쓸 곳이 없고, DNS는 질문 하나에 답 하나라 인사가 데이터보다 크다. 네트워크 [27](../../27-udp-structure)장.

```java
var socket = new DatagramSocket();
byte[] data = "hello".getBytes();
InetAddress addr =
    InetAddress.getByName("localhost");
var pkt = new DatagramPacket(
    data, data.length, addr, 9876);
socket.send(pkt);  // ACK 없이 반환
socket.close();
```

`send`가 바로 돌아오는 것이 UDP의 전부다. 상대가 받았는지, 상대가 있기는 한지 이 코드는 알 수 없다. 자바의 소켓은 자바 기초 [16장](../../../java/basics/16-networking)에서 본다.

{{< callout type="info" >}}
HTTP/3가 UDP 위의 QUIC을 쓰는 이유는 UDP가 빨라서가 아니다. TCP는 운영체제 커널 안에 있어 브라우저가 고칠 수 없고, 중간 장비들이 TCP 헤더를 뜯어보며 낯선 옵션을 막는다. 비어 있는 UDP 위에 신뢰성과 순서와 암호를 **프로그램이 직접** 얹으면 브라우저 업데이트만으로 프로토콜을 바꿀 수 있다. 둘째 원리를 응용 프로그램이 다시 쓴 것이다. [02](../02-http-basics)장 8절.
{{< /callout >}}

## 5. 포트 (Port)

| 범위 | 이름 | 용도 | 왜 |
|:-----|:-----|:-----|:---|
| 0 ~ 1023 | Well-known | 서버가 약속한 번호 | 클라이언트가 묻지 않고 찾아오게 |
| 1024 ~ 49151 | Registered | 프로그램이 등록한 번호 | MySQL 3306처럼 관례로 굳는다 |
| 49152 ~ 65535 | Dynamic | 클라이언트가 그때그때 | 묻는 쪽은 약속이 필요 없다 |

IP가 메우지 않은 세 번째 구멍이다. 주소는 컴퓨터까지만 오고, 그 안의 브라우저와 메일 프로그램과 게임을 가르는 것은 **16비트 번호** 하나다. 서버 쪽 번호는 약속이고 클라이언트 쪽 번호는 운영체제가 그때그때 준다. 이 PC의 동적 범위는 49152부터 16,384개이고, 지금 맺혀 있는 연결 다섯을 보면 이 PC 쪽은 64923~65512의 번호, 상대 쪽은 넷이 443, 하나가 5228(구글 푸시)이다. 상대는 번호를 정해 두고 기다리고, 이 PC는 매번 새 번호로 찾아간다. 네트워크 [26](../../26-port-number-structure)장.

| 포트 | 프로토콜 | 용도 | 왜 그 번호인가 |
|:-----|:---------|:-----|:-------------|
| 20 / 21 | FTP | 파일 전송 (데이터/제어) | 명령과 데이터를 따로 잇는다 |
| 22 | SSH | 보안 셸 | 23번 텔넷의 암호화 후계 |
| 25 | SMTP | 메일 보내기 | 서버끼리의 약속 |
| 53 | DNS | 이름 풀기 (UDP, 크면 TCP) | 6절 |
| 80 | HTTP | 웹 | 1991년의 선택. `http://`의 기본값 |
| 443 | HTTPS | 자물쇠 안의 웹 | `https://`의 기본값 |
| 3306 | MySQL | 데이터베이스 | 등록 포트 |
| 6379 | Redis | 캐시 | 등록 포트 |

## 6. DNS (Domain Name System)

```text
① 브라우저 → 리졸버: example.com?
② 리졸버 → 루트: "com은 gtld-servers"
③ 리졸버 → .com: "iana-servers에"
④ 리졸버 → 권한 서버: 104.20.23.154
⑤ 브라우저 ← 리졸버: 104.20.23.154
```

| 계층 | 역할 | 왜 나눴나 |
|:-----|:-----|:---------|
| 루트 | `.` 꼭대기. 13개 이름, 수백 대 | 어디서 시작할지 하나는 다 알아야 |
| TLD | `.com`, `.kr`, `.org` | 나라와 종류별로 관리 주체가 다르다 |
| 권한 서버 | 그 이름의 주인이 운영 | 주소를 바꾸는 사람이 답해야 |
| 리졸버 | 대신 뛰고 기억한다 | 브라우저마다 루트를 찾으면 루트가 죽는다 |

셋째 원리의 첫 층이다. 사람은 `example.com`을 기억하고 패킷에는 104.20.23.154가 실려야 하므로 누군가 바꿔 줘야 한다. 한 대의 서버가 세상의 이름을 다 갖는 대신, 이름을 점으로 쪼개어 층마다 "다음은 저기"만 답하게 한 것이 DNS다. 이 PC에서 손으로 따라가면 루트는 com의 서버들을, com은 example.com의 권한 서버 a.iana-servers.net을, 권한 서버가 비로소 주소를 답한다(네트워크 [30](../../30-dns-server-structure)장). 리졸버가 이 사슬을 대신 밟고 답을 TTL만큼 기억하므로 두 번째부터는 한 번에 온다.

| 타입 | 뜻 | 이 PC에서 본 예 |
|:-----|:---|:--------------|
| A | 이름 → IPv4 | example.com → 104.20.23.154, 172.66.147.243 |
| AAAA | 이름 → IPv6 | example.com → 2606:4700:10::6814:179a |
| CNAME | 별칭 → 다른 이름 | www.github.com → github.com |
| MX | 메일 받는 서버 | 네트워크 [31](../../31-mail-server-structure)장 |
| NS | 그 이름의 권한 서버 | example.com → a.iana-servers.net |
| TXT | 글자 | SPF, 도메인 소유 확인 |

| DNS를 쓰는 이유 | 왜 되는가 |
|:----------------|:---------|
| 외우기 쉽다 | 사람은 글자를, 패킷은 숫자를 |
| 주소가 바뀌어도 이름은 남는다 | 서버를 옮기면 레코드만 고친다 |
| 한 이름에 여러 주소 | 이 PC에서 www.google.com을 물으면 A 레코드가 8개 온다 |

www.google.com의 답 8개는 TTL이 300초였다. 리졸버는 5분 뒤에 다시 묻고, 구글은 그때 다른 순서나 다른 주소를 줄 수 있다. 이름 하나로 수천 대에 부하를 나누는 방법이 DNS 안에 있다.

## 7. URI / URL / URN

```text
          ┌──── URI ────┐
          │             │
       ┌──┴──┐       ┌──┴──┐
       │ URL │       │ URN │
       │위치 │       │이름 │
       └─────┘       └─────┘
```

| 용어 | 뜻 | 왜 따로 있나 |
|:-----|:---|:-----------|
| URI | 자원을 가리키는 식별자 전체 | 위치로 가리키든 이름으로 가리키든 |
| URL | 자원이 **어디** 있는가 | 옮기면 깨진다. 실무의 거의 전부 |
| URN | 자원이 **무엇**인가 (urn:isbn:...) | 영구한 이름. 찾아가는 방법이 없어 거의 안 쓴다 |

```text
https://example.com:443/search?q=x#s1

┌ scheme    https
├ host      example.com
├ port      443
├ path      /search
├ query     q=x
└ fragment  #s1
```

| 구성 | 뜻 | 왜 |
|:-----|:---|:---|
| scheme | 어떤 규칙으로 (http, https, ftp, ws) | 포트의 기본값과 대화 방식이 정해진다 |
| userinfo | `user:pass@` | 주소에 비밀번호를 적는 것이라 거의 안 쓴다 |
| host | 이름 또는 IP | 6절. 이름이면 DNS부터 |
| port | 생략하면 스킴의 기본값 (80/443) | 5절. 서버 쪽 약속 |
| path | 서버 안의 계층 경로 | 파일 경로에서 왔지만 지금은 자원의 이름 |
| query | `?key=value&...` | 같은 경로에 조건을 붙인다 |
| fragment | `#앵커` | 서버로 가지 않는다 |

셋째 원리의 셋째 층이다. URL 한 줄에 어떤 규칙으로(scheme), 어느 컴퓨터의(host), 어느 프로그램에(port), 무엇을(path, query) 달라고 할지가 다 들어 있다. 브라우저는 이 줄을 오른쪽부터가 아니라 왼쪽부터 푼다. 스킴으로 포트 기본값과 TLS 여부를 정하고, 호스트를 DNS로 풀고, 그 주소와 포트로 연결한 뒤, 경로와 쿼리를 요청 줄에 적는다.

{{< callout type="warning" >}}
`fragment`(`#` 뒷부분)는 서버로 보내지 않는다. 브라우저가 문서 안에서 위치를 찾는 데만 쓰므로, 같은 URL에 `#`만 다른 요청은 서버 로그에 한 줄로 남는다. 옛 SPA가 `#`으로 라우팅한 이유가 이것이다. `#`를 바꿔도 서버에 요청이 가지 않아 페이지가 새로 뜨지 않았다.
{{< /callout >}}

## 8. 브라우저 요청 전체 흐름

```text
① DNS: example.com → 104.20.23.154
   (캐시에 있으면 0ms, 없으면 왕복 1)
② TCP 세 번 인사        왕복 1  41ms
③ TLS 1.3 인사          왕복 1  84ms
④ GET / HTTP/1.1 (75B) 보냄
⑤ 캡슐화: TCP → IP → 이더넷
⑥ 200 OK (860B) 도착    왕복 1 124ms
⑦ 렌더링: HTML → DOM → 그리기
```

앞의 일곱 절이 순서대로 한 번씩 쓰인다. 7절의 URL을 풀어 6절의 DNS로 주소를 얻고, 5절의 포트 443으로 3절의 세 번 인사를 하고, 그 위에 자물쇠(TLS)를 맞추고, 그제야 [02](../02-http-basics)장의 요청 메시지가 떠난다. 오른쪽 숫자는 이 PC의 curl이 `https://example.com`에 요청했을 때의 누적 시각(네트워크 [29](../../29-web-server-structure)장)이다. 첫 바이트가 오기까지 124ms가 걸렸는데 그중 서버가 일한 시간은 거의 없고, 대부분이 왕복 32ms짜리 대화를 세 번 한 값이다. 요청은 75바이트, 응답은 860바이트였다. 그 75바이트가 카드를 떠나 라우터 열 대를 지나 서버의 프로그램까지 올라가는 길은 네트워크 [32](../../32-network-card-data-transfer)~[34](../../34-web-server-data-processing)장이 한 바이트씩 따라갔다.

| 단계 | 비용 | 왜 |
|:-----|:-----|:---|
| DNS | 캐시 미스면 왕복 1 이상 | 6절의 사슬. 리졸버가 대신 뛴다 |
| TCP | 왕복 1 | 세 번 인사 |
| TLS | 왕복 1 (1.3), 2 (1.2) | 자물쇠를 맞추는 대화 |
| HTTP | 왕복 1 + 서버 처리 | 요청이 가고 답이 온다 |
| 렌더링 | CSS와 JS가 막는다 | 그리기 전에 다 읽어야 한다 |

{{< callout type="info" >}}
첫 요청의 대부분은 네트워크 왕복이다. 그래서 웹 성능은 왕복 횟수 싸움이다. Keep-Alive는 인사를 한 번만 하고([02](../02-http-basics)장), HTTP/2는 한 연결에 요청을 겹쳐 보내고, DNS prefetch는 6절을 미리 해 두고, CDN은 서버를 가까이 두어 32ms 자체를 줄인다. 캐시는 아예 요청을 없앤다([05](../05-http-headers)장).
{{< /callout >}}

## 9. 실무 진단 명령어

```bash
# DNS 조회
nslookup example.com
dig example.com +short

# 경로 추적
tracert example.com     # Windows
traceroute example.com  # Linux/Mac

# 연결 상태 (동적 포트가 보인다)
netstat -ano | findstr ESTAB   # Windows
ss -tan                        # Linux

# 포트 열림 확인
telnet example.com 443
```

```powershell
Resolve-DnsName www.google.com -Type A
Resolve-DnsName example.com -Type AAAA
Test-NetConnection example.com -Port 443
netsh int ipv4 show dynamicport tcp
```

절마다 하나씩 대응한다. 6절은 nslookup과 Resolve-DnsName, 1절은 tracert(답 없는 홉은 `*`로 나온다), 5절은 netstat와 dynamicport, 3절은 Test-NetConnection이다. 이 장의 실측값은 전부 이 명령들에서 나왔다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 인터넷 | 라우터가 패킷을 넘기고 잊는 망 | 전체 경로를 아는 곳이 없다 |
| IP | 주소와 패킷. 비연결·비신뢰·포트 없음 | 어려운 일은 끝에 맡겨 라우터를 가볍게 |
| TTL | 라우터마다 1 감소 | 이 PC → example.com은 열 대 |
| IPv6 | 128비트, 고정 헤더 | 43억이 모자라서. 같은 서버로 가는 긴 주소 |
| NAT | 사설 주소를 공인 주소로 | 주소가 모자라니 집 안은 겹쳐 쓴다 |
| TCP | 세 번 인사, 번호, 재전송 | HTML은 한 바이트도 빠지면 안 된다 |
| 3-way | 왕복 1 뒤에 요청 | 상대가 듣고 있는지 먼저 |
| UDP | 8바이트 이름표만 | 잃어도 되는 데이터가 있다 |
| QUIC | UDP 위에 프로그램이 신뢰성 | 커널의 TCP는 못 고친다 |
| 포트 | 16비트, 프로그램의 주소 | 서버는 약속, 클라이언트는 그때그때 |
| DNS | 층마다 "다음은 저기" | 한 대가 다 알 수 없다. 리졸버가 기억 |
| URL | 규칙·컴퓨터·프로그램·자원을 한 줄에 | 브라우저는 왼쪽부터 푼다 |
| 요청 흐름 | DNS → TCP → TLS → HTTP → 렌더링 | 왕복 셋에 약 100ms |

{{< callout type="info" >}}
**용어 정리**
- **패킷 교환**: 데이터를 조각내어 주소를 붙여 보내고 라우터가 조각 단위로 넘기는 방식
- **IP**: 컴퓨터의 주소 체계와 패킷 전달 규칙
- **TTL**: 라우터를 지날 때마다 줄어드는 수명. 0이 되면 버려진다
- **TCP / UDP**: 전송 계층. 약속과 신뢰(TCP) 대 이름표만(UDP)
- **3-way handshake**: SYN, SYN+ACK, ACK의 세 번 인사
- **QUIC**: UDP 위에 신뢰성과 암호를 얹은 HTTP/3의 전송 계층
- **포트**: 한 컴퓨터 안의 프로그램을 가르는 16비트 번호
- **동적 포트**: 클라이언트가 연결마다 받는 임시 번호. 이 PC는 49152부터
- **DNS / 리졸버**: 이름을 주소로 바꾸는 분산 사전 / 대신 묻고 기억하는 서버
- **TTL(DNS)**: 리졸버가 답을 기억해도 되는 초
- **URI / URL / URN**: 식별자 / 위치 / 이름
- **RTT**: 왕복 시간. 이 PC에서 example.com까지 32ms
- **NAT**: 사설 주소를 공인 주소로 바꿔 내보내는 것
{{< /callout >}}
