[01. 인터넷 네트워크](../01-internet-network)에서 브라우저는 URL을 풀어 DNS로 주소를 얻고, 포트 443으로 TCP 인사를 하고, 그 위에서야 HTTP 요청을 보낸다고 했다. 이 장은 그 요청과 응답이 어떻게 생겼고 왜 그렇게 생겼는지를 본다. 원리는 셋이다. 첫째, **HTTP는 글자로 된 요청 하나와 응답 하나의 쌍이다.** 첫 줄이 무엇을 원하는지(또는 어떻게 됐는지)를 말하고, 그 아래 줄들이 부가 정보를, 빈 줄 뒤가 내용물이다. 내용물이 HTML이든 JSON이든 그림이든 상관없는 것은 헤더가 "이것은 무엇이다"를 대신 말하기 때문이다. 둘째, **서버는 기억하지 않는다.** 요청 하나에 필요한 것이 다 들어 있어야 하고, 그 대가로 서버는 몇 대든 늘릴 수 있다. 셋째, **인사는 비싸고 줄 서기는 발목을 잡는다.** 1.0에서 3까지 버전이 바뀐 역사는 왕복을 줄이고 줄 서기를 없애 온 역사다. 이 PC의 curl로 example.com과 주고받은 75바이트 요청과, 자바 25의 HttpClient로 같은 서버와 HTTP/2로 나눈 대화를 그대로 실었다.

## 1. HTTP의 개념

**HTTP(HyperText Transfer Protocol)** 는 이름과 달리 하이퍼텍스트만 나르지 않는다. HTML, JSON, 이미지, 영상, 파일, 서버끼리 주고받는 API 호출까지 오늘날 거의 모든 데이터가 HTTP 위를 지난다. 브라우저와 서버 사이만이 아니라 서버와 서버, 앱과 API 사이도 그렇다.

| 구분 | HTTP가 하는 일 | 왜 |
|:-----|:-------------|:---|
| 무엇을 나르나 | 아무것이나 | 내용물의 종류를 헤더(`Content-Type`)가 말해 준다 |
| 누가 쓰나 | 브라우저, 앱, 서버, 명령줄 | 규칙이 글자라 어떤 언어로도 만들 수 있다 |
| 어디 위에서 | TCP(1.1, 2), QUIC(3) | 순서와 도착을 아래층이 맡는다. 01장 |

네트워크 시리즈 [28](../../28-application-layer-role)장에서 응용 층의 규칙은 글자로 되어 있어 `telnet`으로 손으로 쳐 볼 수 있다고 했다. HTTP가 그 대표다. 첫째 원리가 이것이고, 이 장의 나머지는 그 글자의 모양이다.

## 2. HTTP 버전 역사

| 버전 | 연도 | 새로 생긴 것 | 아래층 | 왜 바뀌었나 |
|:-----|:-----|:-----------|:-------|:-----------|
| HTTP/0.9 | 1991 | GET 한 줄, 헤더 없음 | TCP | 문서 하나를 가져오면 됐다 |
| HTTP/1.0 | 1996 | 헤더, 상태 코드, POST/HEAD | TCP | 폼과 그림이 생겨 "이것은 무엇"이 필요했다 |
| HTTP/1.1 | 1997 | Keep-Alive, Host 필수, chunked | TCP | 파일이 수십 개가 되자 인사 비용이 커졌다 |
| HTTP/2 | 2015 | 이진 프레임, 멀티플렉싱, HPACK | TCP | 줄 서기와 헤더 반복이 병목이 됐다 |
| HTTP/3 | 2022 | QUIC, 0-RTT, 스트림 독립 | UDP(QUIC) | TCP의 순서 보장이 오히려 발목을 잡았다 |

셋째 원리의 연표다. 버전마다 글자의 뜻은 거의 그대로이고, 바뀐 것은 **그 글자를 어떻게 실어 나르는가**다. 어느 버전으로 말할지는 TLS 인사(ALPN) 중에 정한다. 이 PC의 curl은 HTTP/2를 모르는 빌드라 ALPN에 `http/1.1`만 내밀어 1.1로 말했고, 자바 25의 HttpClient는 같은 example.com과 `h2`로 말했다. 1.0으로 물으면 서버는 `HTTP/1.1 200 OK`로 답하면서 `Connection: close`를 붙였다. 옛 손님에게는 옛 방식대로 끊어 주는 것이다. 실무에서는 1.1과 2가 대부분이고, 브라우저와 CDN 사이에서는 3도 흔하다. 버전별 연결 방식의 비교는 네트워크 [29](../../29-web-server-structure)장에서 봤다.

## 3. 핵심 특징

### 클라이언트-서버 구조

```text
┌────────┐   Request    ┌────────┐
│ Client │ ───────────→ │ Server │
│        │ ←─────────── │        │
└────────┘   Response   └────────┘
```

한쪽이 묻고 한쪽이 답한다. 서버가 먼저 말을 거는 길은 없다. 역할이 갈려 있어 서버는 데이터와 규칙에, 클라이언트는 화면에 집중하며 서로 모르는 채 발전한다. 브라우저가 바뀌어도 서버를 고치지 않고, 서버를 옮겨도 브라우저는 모른다.

### 무상태 (Stateless)

```text
[Stateful]          [Stateless]
손님: 아메리카노    손님: 아메리카노 둘
점원: 몇 잔이요?    점원: (바로 준비)
손님: 둘            매번 다 말한다
점원 A가 기억한다   점원이 바뀌어도 된다
```

| 관점 | Stateful | Stateless | 왜 |
|:-----|:---------|:----------|:---|
| 확장 | 어렵다 | 쉽다 | 기억이 없으니 아무 서버가 받아도 된다 |
| 장애 | 상태를 잃는다 | 무관 | 다음 요청이 다시 다 말한다 |
| 요청 크기 | 작다 | 크다 | 매번 자기가 누구인지 들고 다닌다 |

둘째 원리다. 서버는 앞 요청을 기억하지 않으므로 요청 하나가 그 자체로 완결되어야 한다. 이 규칙이 웹을 키웠다. 점원이 기억하는 가게는 손님을 그 점원에게만 보내야 하지만, 매번 다 말하는 가게는 점원을 백 명으로 늘려도 아무나 받는다. 서버 열 대 앞에 부하 분산기를 두고 아무 서버로나 던지는 구조가 무상태 덕에 성립한다.

{{< callout type="info" >}}
로그인처럼 꼭 이어져야 하는 상태는 서버가 아니라 **클라이언트가 들고 다니게** 한다. 쿠키와 세션 ID, 토큰이 그것이다. 서버는 여전히 요청만 보고 판단하고, "내가 누구인지"는 요청 안의 헤더가 매번 말한다. 쿠키의 규칙은 [05](../05-http-headers)장 7절에서 본다.
{{< /callout >}}

### 비연결성과 지속 연결

```text
[HTTP/1.0]  인사 → 요청 → 응답 → 끊음
            인사 → 요청 → 응답 → 끊음
            인사 → 요청 → 응답 → 끊음
[HTTP/1.1]  인사 ─┬─ 요청 → 응답 (html)
                  ├─ 요청 → 응답 (css)
                  └─ 요청 → 응답 (png)
```

HTTP/1.0은 요청 하나에 답하고 TCP 연결을 끊었다. 문서 하나를 주는 대화였으니 그것으로 충분했다. 그런데 페이지 하나가 HTML에 CSS와 그림 수십 개가 되자 파일마다 01장의 세 번 인사, 곧 왕복 하나씩을 새로 치르게 됐다. HTTP/1.1은 답한 뒤에도 연결을 열어 두고 다음 요청에 다시 쓴다(Keep-Alive). 이 PC에서 curl로 example.com을 연달아 두 번 요청하면 첫 응답 뒤에 "connection left intact", 두 번째 요청 앞에 "Reusing existing connection"이 찍힌다. 인사는 한 번이었다.

```http
GET /index.html HTTP/1.1
Host: example.com
Connection: keep-alive
```

1.1에서는 이 헤더가 없어도 기본이 유지다. 반대로 끊고 싶을 때 `Connection: close`를 쓴다. 서버가 1.0 손님에게 붙인 것이 그것이었다.

### HOL Blocking과 HTTP/2 멀티플렉싱

```text
[HTTP/1.1 한 연결]     [HTTP/2 한 연결]
요청1 ─ 응답1          스트림1 ─┐
요청2 ─ 응답2          스트림3 ─┼─ 섞임
요청3 ─ 응답3          스트림5 ─┘
(순서대로 줄 서기)     (프레임을 섞는다)
```

연결을 재사용해도 문제가 하나 남았다. 1.1은 한 연결에서 요청을 연달아 보낼 수는 있어도(파이프라이닝) 응답은 보낸 순서대로 와야 한다. 앞 응답이 늦으면 뒤 응답이 다 됐어도 기다린다. 이것이 **줄 서기(Head-of-Line Blocking)** 이고, 브라우저들은 파이프라이닝을 끄고 대신 연결을 여섯 개쯤 열어 우회했다. HTTP/2는 한 연결 안에 번호 붙은 **스트림**을 여럿 두고, 각 스트림의 요청과 응답을 프레임으로 잘라 섞어 보낸다. 자바 HttpClient로 example.com에 요청 하나를 보내 연결을 연 뒤 셋을 동시에 보내면, 연결은 하나였고 스트림 1, 3, 5, 7의 HEADERS 프레임이 연달아 나간 뒤 DATA 프레임이 섞여 돌아왔다. 홀수 번호는 클라이언트가 연 스트림이라는 규칙 때문에 1, 3, 5, 7이다.

## 4. HTTP 메시지 구조

```text
┌─────────────────────┐
│ Start-line          │
├─────────────────────┤
│ Header-name: value  │
│ Header-name: value  │
├─────────────────────┤
│  (CRLF, 빈 줄)      │
├─────────────────────┤
│  Message Body       │
└─────────────────────┘
```

첫째 원리의 모양이다. 모든 HTTP 메시지는 **시작 줄, 헤더들, 빈 줄, 본문** 순서다. 줄은 CRLF(`\r\n`)로 끝나고, 헤더가 끝났음을 알리는 것은 빈 줄 하나다. 받는 쪽은 빈 줄까지 읽으면 본문이 몇 바이트인지(`Content-Length`) 또는 어떻게 잘라 오는지(`Transfer-Encoding: chunked`)를 이미 알고 있어서 어디까지가 이 메시지인지 안다. 네트워크 [34](../../34-web-server-data-processing)장에서 웹 서버 프로그램이 빈 줄에서 요청을 자르는 것을 봤다.

### 요청 메시지

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.18.0
Accept: */*

```

이 PC의 curl이 example.com에 보낸 요청 그대로이고, 줄 끝의 CRLF까지 세면 정확히 75바이트다. 네트워크 [32](../../32-network-card-data-transfer)장에서 133바이트 프레임이 되어 카드를 떠난 그 75바이트다.

| 요청 줄 | 뜻 | 왜 |
|:--------|:---|:---|
| 메서드 `GET` | 무엇을 할지 | 서버가 읽기인지 쓰기인지를 첫 단어에서 안다. [03](../03-http-methods)장 |
| 대상 `/` | 어느 자원에 | 01장의 URL에서 host와 port는 이미 연결에 썼고 남은 것이 path와 query |
| 버전 `HTTP/1.1` | 어떤 규칙으로 | 서버가 1.1의 기본값(Keep-Alive, chunked)을 써도 되는지 |

### 응답 메시지

```http
HTTP/1.1 200 OK
Date: Mon, 14 Sep 2026 04:34:51 GMT
Content-Type: text/html
Transfer-Encoding: chunked
Connection: keep-alive
Server: cloudflare
Age: 13300
cf-cache-status: HIT

22f
<!doctype html>...
0

```

같은 요청에 온 응답의 앞부분이다. 머리가 303바이트, 본문이 559바이트였다. 첫 줄은 버전과 상태 코드와 이유 문구이고, 코드가 곧 결과다([04](../04-http-status-codes)장). 그 아래 `Age: 13300`과 `cf-cache-status: HIT`는 이 응답이 서버가 아니라 클라우드플레어의 캐시에서 왔고, 3시간 40분 전에 만들어진 것이라는 뜻이다. 서버는 기억하지 않지만 중간의 캐시는 응답을 기억한다. 그 규칙은 [05](../05-http-headers)장의 절반이다.

| 상태 줄 | 뜻 | 왜 |
|:--------|:---|:---|
| 버전 | 서버가 쓰는 규칙 | 1.0으로 물어도 1.1로 답할 수 있다 |
| 코드 `200` | 결과의 종류 | 프로그램이 숫자 하나로 분기한다 |
| 이유 문구 `OK` | 사람용 | HTTP/2는 아예 없앴다 |

### 본문 (Body)

본문은 요청에도 응답에도 있을 수 있고, 실제 내용물이 담긴다. 종류는 `Content-Type`이, 길이는 `Content-Length`가 말한다. 길이를 미리 모르면 `Transfer-Encoding: chunked`로 "이번 조각은 몇 바이트"를 앞에 붙여 보낸다. 위 응답의 `22f`가 그것이다. 16진수 22f는 559, 곧 본문 전체가 조각 하나로 왔고 `0`이 끝을 알린다. 동적으로 만드는 페이지는 다 만들기 전에는 길이를 모르므로 chunked가 흔하다.

## 5. HTTP 헤더 개요

```text
field-name: field-value
```

| 규칙 | 내용 | 왜 |
|:-----|:-----|:---|
| 이름은 대소문자 구별 없음 | `Content-Type`도 `content-type`도 같다 | HTTP/2는 아예 소문자로만 보낸다 |
| 값 앞뒤 공백 무시 | `Host:example.com`도 된다 | 손으로 치는 규칙의 관용 |
| 표준에 없어도 된다 | `X-Request-Id` 같은 것 | 모르는 헤더는 무시하면 되므로 확장이 자유롭다 |
| Host는 필수(1.1) | 없으면 거절 | 한 IP에 도메인 여럿. 이 PC에서 빼고 보내니 400 Bad Request |

헤더는 첫째 원리의 "부가 정보"다. 시작 줄이 무엇을 원하는지를 말하면 헤더가 어떤 형식으로, 누구로서, 얼마나, 언제까지를 말한다. 헤더의 이름이 대소문자를 가리지 않는 것은 사람이 손으로 치던 규칙의 흔적이고, 표준에 없는 이름을 써도 되는 것은 받는 쪽이 모르는 헤더를 그냥 무시하기 때문이다. 이 관용 덕에 HTTP는 규격을 바꾸지 않고도 30년간 기능을 더해 왔다. 분류와 캐시 헤더는 [05](../05-http-headers)장에서 본다.

| 헤더 | 방향 | 용도 | 왜 |
|:-----|:-----|:-----|:---|
| Host | 요청 | 어느 도메인에 | 한 서버가 도메인 여럿을 받는다 |
| User-Agent | 요청 | 누가 보냈나 | 서버가 브라우저별로 다르게 줄 수 있게 |
| Accept | 요청 | 원하는 형식 | 같은 자원을 HTML로도 JSON으로도 |
| Authorization | 요청 | 자격 증명 | 무상태라 매번 들고 온다 |
| Content-Type | 양방향 | 본문의 종류 | 아무것이나 나르려면 이름표가 필요하다 |
| Content-Length | 양방향 | 본문의 바이트 수 | 어디까지가 이 메시지인지 |
| Cache-Control | 양방향 | 캐시 지시 | 요청을 없애는 가장 싼 방법 |
| Set-Cookie | 응답 | 쿠키 저장 지시 | 상태를 클라이언트에 맡긴다 |

## 6. HTTP 통신 예시

### Spring Boot 컨트롤러

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    @GetMapping("/{id}")
    public User get(
            @PathVariable Long id) {
        return service.findById(id);
    }

    @PostMapping
    public ResponseEntity<User> create(
            @RequestBody User user) {
        User saved = service.save(user);
        URI loc = URI.create(
            "/api/users/" + saved.id());
        return ResponseEntity
            .created(loc).body(saved);
    }
}
```

프레임워크가 하는 일은 4절의 메시지를 자바로 바꾸는 것이다. 시작 줄의 메서드와 경로가 `@GetMapping`, `@PostMapping`의 어느 메서드를 부를지를 정하고, 경로의 일부가 `@PathVariable`로, 본문이 `Content-Type`에 따라 `@RequestBody`의 객체로 바뀐다. 돌아가는 객체는 다시 상태 줄과 헤더와 본문이 된다.

### 요청

```http
GET /api/users/123 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer eyJhbGci...

```

### 응답

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 69

{
  "id": 123,
  "name": "홍길동",
  "email": "hong@example.com"
}
```

둘째 원리가 `Authorization` 줄에 있다. 서버는 이 손님이 누구인지 기억하지 않으므로 요청마다 토큰을 들고 오고, 서버는 토큰만 보고 판단한다. 그래서 이 요청은 서버 열 대 중 어느 것이 받아도 같은 답이 나온다.

## 7. HTTP/2 개선

| 기능 | 내용 | 왜 |
|:-----|:-----|:---|
| 이진 프레이밍 | 글자 대신 길이 붙은 프레임 | 어디서 끊어 읽을지 계산이 필요 없다 |
| 멀티플렉싱 | 한 연결에 스트림 여럿 | 3절의 줄 서기 |
| 헤더 압축 (HPACK) | 반복 헤더를 표의 번호로 | 요청마다 같은 헤더가 수백 바이트 |
| 스트림 우선순위 | 중요한 것 먼저 | CSS가 그림보다 급하다 |
| 서버 푸시 | 요청 없이 미리 보냄 | 실효가 적어 브라우저들이 뺐다 |

```text
┌─────────────────────────┐
│ Length (24)             │
├───────┬───────┬─────────┤
│ Type  │ Flags │Stream ID│
│ (8)   │ (8)   │  (31)   │
├───────┴───────┴─────────┤
│      Frame Payload      │
└─────────────────────────┘
```

HTTP/2는 글자의 뜻은 두고 실어 나르는 방식만 바꿨다. 메시지를 길이가 앞에 붙은 프레임으로 자르고 프레임마다 스트림 번호를 달아 한 연결에 섞는다. 이 PC의 자바 HttpClient가 보낸 요청은 1.1에서 75바이트이던 것이 HEADERS 프레임 34바이트가 됐고 두 번째부터는 33바이트였다. 응답 쪽이 더 크다. 1.1에서 303바이트이던 응답 헤더가 첫 번째는 131바이트, 두 번째부터는 26바이트로 왔다. 한 번 보낸 헤더를 양쪽이 표에 적어 두고 다음부터는 번호만 보내는 HPACK의 효과다. 첫째 원리의 글자는 그대로이되, 선 위에서는 이진이 됐다.

## 8. HTTP/3와 QUIC

| 항목 | HTTP/2 (TCP) | HTTP/3 (QUIC/UDP) | 왜 |
|:-----|:-------------|:------------------|:---|
| 연결 수립 | TCP + TLS (2 RTT) | QUIC에 TLS 내장 (1 RTT, 재접속 0-RTT) | 인사를 한 번에 합쳤다 |
| 줄 서기 | TCP 층에서 생긴다 | 스트림별로 독립 | 아래에서 본다 |
| 이동성 | IP가 바뀌면 재연결 | 연결 ID로 이어 간다 | 주소가 아니라 번호로 연결을 식별 |
| 배포 | 방화벽 친화적 | UDP 차단 환경 주의 | 낯선 것은 막힌다 |

```text
[HTTP/2]
TCP SYN/ACK → TLS Hello → HTTP 요청
  1 RTT         1~2 RTT       1 RTT

[HTTP/3]
QUIC + TLS 동시 → HTTP 요청
      1 RTT          바로
(재접속 0-RTT 가능)
```

HTTP/2가 줄 서기를 HTTP 층에서 없앴더니 TCP 층에서 다시 나타났다. 스트림을 아무리 섞어도 TCP는 바이트를 순서대로 넘기는 규칙이라, 패킷 하나가 빠지면 그 뒤의 모든 스트림이 그 재전송을 기다린다. 다른 스트림의 데이터가 이미 도착해 있어도 그렇다. TCP를 고치면 되지만 01장에서 본 대로 TCP는 운영체제 커널의 것이라 브라우저가 손댈 수 없다. 그래서 HTTP/3는 UDP 위에 QUIC을 얹고 스트림마다 따로 순서를 맞춘다. 잃어버린 패킷은 그 스트림만 기다린다. 이 PC의 curl과 자바 25는 HTTP/3를 말하지 못해 이 절은 실측 없이 규격의 값이다.

{{< callout type="warning" >}}
Wi-Fi에서 LTE로 넘어가듯 주소가 바뀌는 환경에서 HTTP/3의 **연결 이동(Connection Migration)** 이득이 크다. TCP 연결은 주소 넷(출발지·목적지 주소와 포트)으로 식별되어 주소가 바뀌면 끊기지만 QUIC은 연결 ID로 식별한다. 반대로 사내 방화벽이 UDP를 막으면 HTTP/2로 내려갈 길을 두어야 한다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| HTTP | 글자로 된 요청·응답 한 쌍 | 아무 데이터나 나른다. 이름표는 헤더 |
| 클라이언트-서버 | 한쪽이 묻고 한쪽이 답한다 | 서로 모른 채 발전한다 |
| 무상태 | 서버는 기억하지 않는다 | 아무 서버가 받아도 되니 늘릴 수 있다 |
| 상태의 행방 | 쿠키·토큰으로 클라이언트가 | 서버를 무상태로 두려고 |
| Keep-Alive | 인사 한 번에 요청 여럿 | 파일마다 왕복 하나가 아깝다 |
| 줄 서기 | 앞 응답이 뒤를 막는다 | 1.1은 순서대로만 답한다 |
| 메시지 구조 | 시작 줄, 헤더, 빈 줄, 본문 | 빈 줄까지 읽으면 나머지 길이를 안다 |
| 헤더 | 이름은 대소문자 무시, 모르면 무시 | 30년간 규격을 안 바꾸고 더해 왔다 |
| chunked | 조각마다 길이를 앞에 | 다 만들기 전엔 길이를 모른다 |
| HTTP/2 | 프레임, 스트림, HPACK | 한 연결에 섞고 헤더는 번호로 |
| HTTP/3 | UDP 위의 QUIC | TCP의 순서 규칙이 줄 서기를 되살렸다 |

{{< callout type="info" >}}
**용어 정리**
- **HTTP**: 웹의 응용 계층 규칙. 글자로 된 요청과 응답
- **Stateless**: 서버가 앞 요청을 기억하지 않는 성질
- **Keep-Alive**: 응답 뒤에도 TCP 연결을 열어 두고 다시 쓰는 것
- **Request / Response**: 클라이언트의 요청 메시지 / 서버의 응답 메시지
- **Start-line**: 메시지 첫 줄. 요청 줄 또는 상태 줄
- **Header / Body**: 부가 정보 / 내용물
- **chunked**: 길이를 모를 때 조각마다 길이를 붙여 보내는 방식
- **HOL Blocking**: 앞 응답이 늦어 뒤 응답이 기다리는 줄 서기
- **Multiplexing**: 한 연결에 스트림 여럿을 프레임 단위로 섞는 것
- **HPACK**: HTTP/2의 헤더 압축. 한 번 보낸 헤더는 번호로
- **ALPN**: TLS 인사 중에 HTTP 버전을 정하는 확장
- **QUIC**: UDP 위에 순서·재전송·TLS를 얹은 HTTP/3의 전송 계층
{{< /callout >}}
