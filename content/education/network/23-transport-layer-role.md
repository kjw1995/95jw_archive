[01. 네트워크의 기본](../01-network-basics)에서 패킷 교환의 대가는 지연, 손실, 순서 뒤바뀜이고 그것을 응용 프로그램이 못 느끼게 덮는 일을 누가 하는가가 이 장의 주제라고 했다. [17](../17-network-layer-role)장은 IP가 약속하지 않는 대신 신뢰는 양 끝에서 한다고 했고, [07](../07-osi-tcpip-model)장은 4층의 질문이 "이 기계의 어느 프로그램에게, 얼마나 믿을 만하게"라고 했다. 이 장은 그 층의 개요이고, 자세한 동작은 [24](../24-tcp-structure)장부터 [27](../27-udp-structure)장까지 넷이 나눠 맡는다. 원리는 셋이다. 첫째, **전송 계층은 기계가 아니라 프로그램에게 배달하고, 그 일은 양 끝에서만 한다.** 3층까지의 주소는 기계를 가리켰다. 한 기계에서 브라우저와 메일과 게임이 동시에 도는데 패킷이 누구 것인지를 가리는 것이 포트이고, 라우터는 이 층을 읽지 않는다. 둘째, **신뢰는 공짜가 아니라 상태와 시간으로 산다.** TCP는 연결이라는 상태, 바이트마다의 번호, 확인 응답, 재전송 타이머, 창으로 IP의 비신뢰를 덮는데, 그 값은 왕복 한 번의 지연과 양 끝의 메모리다. UDP는 그 값을 치르지 않기로 한 선택이지 열등한 것이 아니다. 셋째, **둘 중 무엇을 쓸지는 "늦은 데이터가 쓸모 있는가"로 정해진다.** 파일은 늦어도 완전해야 하고 음성은 완전해도 늦으면 쓸모없다. 이 장의 실측은 앞 장들에서 잰 값과 [자바 기초 16장](../../java/basics/16-networking)에서 소켓으로 직접 확인한 결과를 가져와 쓴다.

## 1. 전송 계층이란

| 하는 일 | 뜻 | 왜 이 층인가 |
|:--------|:---|:------------|
| 끝에서 끝으로 | 보낸 프로그램에서 받는 프로그램까지 | 17장. 중간은 단순하게, 똑똑함은 끝에 |
| 프로그램 구별 | 포트 번호로 여러 프로그램을 가른다 | 3층 주소는 기계까지만 가리킨다 |
| 오류와 손실 복구 | 번호, 확인, 재전송 (TCP) | IP는 버려도 알리지 않는다 |
| 속도 조절 | 흐름 제어와 혼잡 제어 (TCP) | 받는 쪽과 길의 사정은 보내는 쪽이 모른다 |

네트워크 계층이 "어느 기계로"를 정했다면 전송 계층은 "그 기계의 어느 프로그램에게, 얼마나 믿을 만하게"를 정한다. 17장에서 IP가 신뢰를 포기한 이유를 라우터가 아무것도 기억하지 않아야 죽어도 다른 길로 갈 수 있기 때문이라고 했다. 그렇게 버린 신뢰를 누군가는 다시 만들어야 하고, 그 자리는 라우터가 아니라 **양 끝**이다. 확인과 재전송에 필요한 기억(어디까지 받았나, 무엇을 다시 보내야 하나)을 양 끝의 프로그램 옆에 두는 것이 이 층이고, 대표 규칙이 TCP와 UDP 둘이다.

## 2. OSI 7계층에서의 위치

```text
 7  Application   │ HTTP, DNS, SMTP
 6  Presentation  │ 암호화, 인코딩
 5  Session       │ 세션 관리
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 4  Transport     │ TCP, UDP, 포트
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
 3  Network       │ IP, 라우팅
 2  Data Link     │ MAC, 스위치
 1  Physical      │ 케이블, 허브
```

4층은 경계선이다. 아래 세 층은 케이블, 스위치, 라우터가 저마다 한 겹씩 읽고 벗기지만, 4층 헤더는 보낸 기계가 붙이고 받는 기계가 벗길 뿐 그 사이의 어떤 장비도 원칙적으로 읽지 않는다. [08](../08-encapsulation-decapsulation)장의 봉투로 말하면, 라우터는 IP 봉투까지만 열고 그 안의 TCP 봉투는 뜯지 않은 채 넘긴다. 이 층의 단위를 TCP는 세그먼트, UDP는 데이터그램이라 부른다. 원칙에는 예외가 있다. [04](../04-home-lan-configuration)장의 NAT가 포트 번호까지 바꾸고 방화벽이 포트로 거르는 것은 중간 장비가 4층 헤더를 읽는 일이고, 인터넷의 설계를 어긴 대가가 04장의 "밖에서 안으로는 못 들어온다"였다.

## 3. 멀티플렉싱과 포트 번호

```
브라우저(52341) 메일(52342) SSH(52343)
       │             │          │
       └─────────────┴──────────┘
                     │
                전송 계층 (포트)
                     │
                네트워크 계층
```

한 기계에서 여러 프로그램이 동시에 네트워크를 쓴다. 나가는 패킷을 한 줄로 합치고 들어오는 패킷을 주인에게 나눠 주는 것이 멀티플렉싱이고, 그 주인을 적는 칸이 **포트 번호**다. 이 PC에서 세어 보면 열려 있는 TCP 연결이 200개가 넘는데, 그 전부가 같은 IP 주소로 드나들면서도 섞이지 않는 것은 포트가 다르기 때문이다.

| 범위 | 이름 | 누가 쓰나 | 왜 나뉘나 |
|:-----|:-----|:----------|:----------|
| 0 ~ 1023 | 잘 알려진 포트 | HTTP 80, HTTPS 443, DNS 53 | 서버는 상대가 미리 알아야 찾아온다 |
| 1024 ~ 49151 | 등록 포트 | MySQL 3306, RDP 3389 | 표준은 아니지만 겹치지 않게 등록 |
| 49152 ~ 65535 | 동적 포트 | 클라이언트가 그때그때 | 클라이언트는 상대가 찾아올 일이 없다 |

서버의 포트는 정해져 있고 클라이언트의 포트는 그때그때 운영체제가 고른다. 비대칭인 이유는 **누가 먼저 말을 거는가**다. 브라우저는 서버의 443번을 알고 찾아가지만 서버는 브라우저가 몇 번 포트인지 미리 알 수 없고 알 필요도 없다. 요청에 적혀 오기 때문이다. Windows의 기본값도 49152부터다.

```
클라이언트 192.168.1.10:52341
        ↔
서버     203.0.113.50:80
```

IP 주소와 포트 번호를 합친 것이 소켓이고, 연결 하나는 양 끝의 소켓 둘, 곧 네 값(내 주소, 내 포트, 상대 주소, 상대 포트)으로 식별된다. 서버의 80번 포트 하나에 수천 명이 붙어 있어도 섞이지 않는 것은 상대 주소와 상대 포트가 다르기 때문이다. 포트 번호의 배분과 확인 명령은 [26. 포트 번호의 구조](../26-port-number-structure)에서 본다.

## 4. TCP vs UDP

| 항목 | TCP | UDP | 왜 다른가 |
|:-----|:----|:----|:----------|
| 연결 | 맺고 시작한다 | 없다 | 상태를 기억하려면 시작과 끝이 있어야 한다 |
| 신뢰성 | 확인과 재전송 | 없다 | 재전송하려면 보낸 것을 갖고 있어야 한다 |
| 순서 | 번호로 되돌린다 | 없다 | 번호를 붙이려면 흐름이 있어야 한다 |
| 단위 | 바이트 흐름 | 봉투 하나 | 27장 |
| 헤더 | 20~60바이트 | 8바이트 | 상태가 없으면 적을 것이 없다 |
| 속도 조절 | 있다 | 없다 | 위와 같다 |
| 1:N | 안 된다 | 브로드캐스트, 멀티캐스트 | 연결은 1:1의 상태다 |

등기우편과 엽서의 비유가 정확하다. TCP는 받았다는 확인을 받고 잃어버리면 다시 보내며, UDP는 부치고 끝이다. 표의 오른쪽 열이 말하듯 두 규칙의 차이는 기능의 유무가 아니라 **상태의 유무** 하나에서 다 나온다. 잃어버린 것을 다시 보내려면 보낸 것을 갖고 있어야 하고, 갖고 있으려면 언제부터 언제까지 갖고 있을지(연결)가 있어야 하며, 그 모든 기억이 헤더의 20바이트와 양 끝의 메모리다. UDP는 그 기억을 갖지 않기로 했으므로 헤더가 8바이트이고, 상태가 없으니 한 봉투를 여럿에게 뿌릴 수도 있다.

| 규칙 | 쓰는 곳 | 왜 |
|:-----|:--------|:---|
| TCP | HTTP, HTTPS, 메일, 파일 전송, SSH, 데이터베이스 | 한 바이트라도 틀리면 안 된다 |
| UDP | DNS, DHCP, 음성 통화, 영상 스트리밍, 게임 | 늦은 것은 버리는 편이 낫다 |

{{< callout type="info" >}}
음성 통화에서 잃어버린 0.02초의 소리를 0.3초 뒤에 다시 받아 봐야 이미 지나간 시점의 소리라 쓸모가 없다. 그사이 대화는 앞으로 갔다. 이런 데이터는 잃은 것을 되찾는 것보다 다음 것을 제때 받는 것이 중요하므로 TCP의 재전송이 오히려 해가 되고, UDP 위에 응용 프로그램이 자기 방식의 복구(잡음 채우기, 앞뒤로 보간)를 얹는다.
{{< /callout >}}

두 규칙의 단위 차이는 코드로 보면 분명하다. 자바 기초 16장에서 이 PC의 JDK로 확인한 것인데, TCP 소켓에 `ab`와 `cd`를 두 번 써 보내면 상대는 `abcd`를 한 번에 읽는다. TCP에는 봉투가 없고 바이트의 흐름만 있어서 어디서 끊어 보냈는지가 남지 않는다. UDP는 반대로 보낸 봉투 하나가 받는 쪽에서도 봉투 하나이고, 받는 쪽 버퍼가 1,024바이트인데 2,000바이트짜리 봉투가 오면 나머지는 잘려 사라진다. 흐름인가 봉투인가는 프로그램을 짜는 방식까지 바꾼다.

## 5. 신뢰성 메커니즘 (TCP)

TCP가 IP의 비신뢰를 덮는 장치는 셋이고, 셋이 한 벌이다.

### 1) 순서 번호

```text
송신: [1][2][3][4][5]
수신: [1][3][2][5][4]  ← 순서가 바뀜
정렬: [1][2][3][4][5]  ← 번호로 복구
```

01장에서 같은 파일의 조각이 다른 길로 가면 순서가 바뀌어 도착한다고 했다. TCP는 세그먼트가 아니라 **바이트마다** 번호를 붙여, 받는 쪽이 원래 자리에 꽂아 넣게 한다. 08장에서 본 대로 번호 칸이 32비트나 되는 것은 바이트 단위로 세기 때문이고, 세그먼트 단위가 아닌 이유는 재전송할 때 원래와 다른 크기로 잘라 보내도 받는 쪽이 맞출 수 있게 하려는 것이다.

### 2) 확인 응답

```text
송신 ─ #2 ─→ 수신   (잃어버림)
송신 ─ #2 ─→ 수신   (재전송, ACK 옴)
```

받는 쪽은 "다음에 기대하는 번호"를 확인 응답(ACK)으로 알린다. "3까지 받았다"가 아니라 "4를 다오"라고 하는 이유는 누적이기 때문이다. 4를 달라는 말에는 3까지 전부 받았다는 뜻이 들어 있어, 확인 응답 하나가 사라져도 다음 확인 응답이 그것을 대신한다. 보내는 쪽은 확인이 올 때까지 보낸 것을 갖고 있다가 일정 시간 안에 오지 않으면 다시 보낸다. 그 시간은 정해진 값이 아니라 **왕복 시간을 재어** 정한다. 01장에서 잰 대로 구글까지는 38ms, 핀란드까지는 251ms라 같은 기다림으로는 한쪽에서는 너무 성급하고 다른 쪽에서는 너무 느리기 때문이다. 이 두 번호의 자세한 동작은 [25. 일련번호와 확인 응답 번호의 구조](../25-sequence-ack-number)에서 본다.

### 3) 체크섬

헤더와 데이터 전체의 체크섬을 붙이고, 받는 쪽이 다시 계산해 다르면 버린다. 버려진 세그먼트는 확인 응답이 안 오므로 재전송으로 이어진다. 17장에서 IP의 체크섬은 헤더만 검사한다고 했는데, 데이터의 검사를 이 층이 맡기 때문이다. TCP의 체크섬에는 IP 헤더의 출발지와 목적지 주소까지 함께 넣어 계산한다. 데이터가 멀쩡해도 엉뚱한 기계에 배달된 세그먼트를 걸러 내려는 것이다.

## 6. 흐름 제어와 혼잡 제어 (TCP)

속도 조절이 둘인 이유는 막히는 곳이 둘이기 때문이다. 받는 쪽의 프로그램이 느려 버퍼가 차는 것과, 중간의 길이 붐벼 라우터가 패킷을 버리는 것은 다른 문제이고 신호도 다르다.

### 흐름 제어: 받는 쪽의 사정

```text
버퍼 #####-----  창=5
버퍼 ##########  창=0 → 멈춤
버퍼 ##--------  창=8 → 재개
```

받는 쪽은 확인 응답에 **창 크기**, 곧 앞으로 몇 바이트를 더 받을 수 있는지를 실어 보낸다. 보내는 쪽은 그만큼만 확인 없이 보내고, 창이 0이면 멈춘다. 받는 쪽이 자기 사정을 직접 말하므로 정확하다. 창의 동작은 [24](../24-tcp-structure)장에서 본다.

### 혼잡 제어: 길의 사정

| 단계 | 동작 | 왜 |
|:-----|:-----|:---|
| 느린 시작 | 작게 시작해 확인이 올 때마다 두 배 | 길의 용량을 모르니 더듬는다 |
| 혼잡 회피 | 어느 선을 넘으면 하나씩만 늘린다 | 한계 근처에서는 조심스럽게 |
| 빠른 재전송 | 같은 확인 응답이 세 번 오면 바로 다시 보낸다 | 타이머를 기다리면 너무 늦다 |
| 빠른 회복 | 손실이 나면 절반으로 줄이고 다시 늘린다 | 붐빔의 신호는 손실뿐이다 |

길의 사정은 아무도 말해 주지 않는다. 라우터는 17장에서 본 대로 버릴 뿐 알리지 않으므로, 보내는 쪽은 **손실을 붐빔의 신호로** 읽고 스스로 속도를 낮춘다. 1986년에 인터넷이 실제로 이 조절 없이 마비된 뒤 나온 규칙이고, 그래서 모든 TCP는 처음에 작게 시작해 더듬으며 늘리고 손실이 나면 물러선다. 인터넷이 수십억 대가 되어도 붕괴하지 않는 것은 각자가 이 규칙을 지키기 때문이다. 요즘 운영체제의 기본 알고리즘(CUBIC 등)은 늘리고 줄이는 곡선이 다를 뿐 뼈대는 같다.

## 7. TCP 연결 수립과 해제 요약

```text
클라이언트 ─ SYN ─────────→ 서버
클라이언트 ←─ SYN+ACK ────── 서버
클라이언트 ─ ACK ─────────→ 서버
              연결됨
```

연결을 맺는 데 세 번이 오가는 이유는 **양쪽이 각자의 시작 번호를 알려 주고 상대의 것을 확인**해야 하기 때문이다. 두 번이면 서버가 자기 번호를 보냈다는 것만 있고 클라이언트가 그것을 받았다는 확인이 없다. 세 번째가 그 확인이다. 이 세 번이 왕복 한 번의 시간이고, 01장의 실측으로 핀란드 서버라면 첫 바이트를 보내기도 전에 0.25초가 든다. 신뢰의 첫 번째 값이다.

```text
클라이언트 ─ FIN ─────────→ 서버
클라이언트 ←─ ACK ────────── 서버
클라이언트 ←─ FIN ────────── 서버
클라이언트 ─ ACK ─────────→ 서버
```

끊을 때 네 번인 이유는 연결이 양방향이고 **방향마다 따로 닫기** 때문이다. 클라이언트가 "다 보냈다"고 해도 서버는 아직 보낼 것이 남았을 수 있으므로, 서버는 먼저 확인만 하고 자기 것을 다 보낸 뒤에 자기 쪽을 닫는다. 그 사이의 반쪽 열린 상태와, 마지막 확인이 사라졌을 때를 대비해 잠시 기다리는 상태(TIME_WAIT)의 사정은 [24. TCP의 구조](../24-tcp-structure)에서 본다.

## 8. UDP 통신 요약

```text
클라 ─ #1 ─→ 서버  받음
클라 ─ #2 ─→ 서버  손실. 재전송 없음
클라 ─ #3 ─→ 서버  받음
```

UDP는 맺는 것도 끊는 것도 없다. 봉투를 만들어 보내고 끝이며, 도착했는지 묻지 않는다. 헤더 8바이트에는 출발지 포트, 목적지 포트, 길이, 체크섬만 있다. IP가 이미 주소를 갖고 있으니 4층이 더할 것은 프로그램의 번호뿐이고, 상태가 없으니 번호도 창도 필요 없다.

DNS가 UDP를 쓰는 이유가 이 규칙의 성격을 보여 준다. 이름 하나를 묻고 답 하나를 받는 데 세 번의 인사로 연결을 맺으면 데이터보다 인사가 더 크다. 한 번 보내고 답이 없으면 다시 물으면 되고, 그 재전송은 응용 프로그램이 직접 한다. 04장의 DHCP가 UDP인 것도 같은 이유에 더해 브로드캐스트가 필요해서다. 연결이 없으므로 한 봉투를 [20](../20-network-broadcast-address)장의 브로드캐스트 주소나 [19](../19-ip-address-class)장의 멀티캐스트 주소로 보낼 수 있고, TCP는 1:1의 상태라 그럴 수 없다. UDP의 구조와 쓰임은 [27. UDP의 구조](../27-udp-structure)에서 본다.

## 9. 프로토콜 선택 기준

```text
        늦은 데이터가 쓸모 있나?
              │
        ┌─────┴─────┐
       있다         없다
        │             │
       TCP           UDP
        │             │
  HTTP, 메일, SSH   스트리밍, DNS
  파일 전송, DB     게임, 음성
```

"손실을 허용하는가"보다 정확한 질문은 "**늦게 도착한 데이터가 쓸모 있는가**"다. 파일의 조각은 1초 늦어도 쓸모가 있으니 기다려서라도 받아야 하고, 음성의 조각은 0.3초 늦으면 쓸모가 없으니 버리고 다음을 받는다. 앞의 것이 TCP, 뒤의 것이 UDP다.

{{< callout type="info" >}}
요즘 웹은 이 구분을 비튼다. HTTP/3는 UDP 위에서 돌면서 신뢰와 순서와 암호화를 응용 프로그램 안에 직접 구현한다(QUIC). TCP의 신뢰가 부족해서가 아니라, TCP가 운영체제 안에 고정되어 있어 고치기 어렵고, 요청 여럿을 한 연결에 실으면 앞의 조각 하나가 늦어질 때 뒤의 것까지 다 기다려야 하기 때문이다. 신뢰가 필요한데도 TCP 대신 UDP 위에 신뢰를 새로 쌓은 것이고, 둘째 원리의 "신뢰는 상태와 시간으로 산다"를 응용 프로그램이 자기 손으로 다시 한 예다.
{{< /callout >}}

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 전송 계층 | 프로그램에서 프로그램으로 | 3층 주소는 기계까지다 |
| 양 끝 | 라우터는 4층을 읽지 않는다 | 17장. 중간은 단순하게 |
| 포트 | 16비트 프로그램 번호 | 한 기계의 여러 프로그램을 가른다 |
| 서버와 클라이언트 포트 | 정해진 것 / 그때그때 | 먼저 말을 거는 쪽은 상대를 알아야 한다 |
| 소켓 | 주소 + 포트. 연결은 넷의 조합 | 같은 80번에 수천 명이 붙어도 다르다 |
| TCP와 UDP | 상태가 있다 / 없다 | 모든 차이가 이 하나에서 나온다 |
| 순서 번호 | 바이트마다 | 다른 길로 온 조각을 되돌린다 |
| 확인 응답 | 다음 기대 번호 | 누적이라 하나쯤 사라져도 된다 |
| 재전송 시간 | 왕복 시간에서 계산 | 38ms와 251ms에 같은 값을 쓸 수 없다 |
| 체크섬 | 데이터와 주소까지 | IP는 헤더만 본다 |
| 흐름 제어 | 받는 쪽이 창을 알린다 | 받는 쪽의 사정 |
| 혼잡 제어 | 손실을 신호로 물러선다 | 길의 사정은 아무도 안 알려 준다 |
| 3번 인사 | 서로의 시작 번호 확인 | 왕복 한 번의 값 |
| 4번 작별 | 방향마다 닫는다 | 상대는 아직 보낼 것이 있을 수 있다 |
| UDP 8바이트 | 포트, 길이, 체크섬 | 상태가 없으면 적을 것이 없다 |
| 선택 | 늦은 데이터가 쓸모 있는가 | 파일은 있고 음성은 없다 |
| HTTP/3 | UDP 위에 신뢰를 다시 | TCP는 고치기 어렵다 |

{{< callout type="info" >}}
**용어 정리**
- **전송 계층**: 프로그램과 프로그램 사이의 배달을 맡는 4층. TCP와 UDP
- **포트 번호**: 한 기계 안의 프로그램을 가리키는 16비트 번호
- **소켓**: IP 주소와 포트 번호의 짝. 연결은 양 끝 소켓의 조합
- **멀티플렉싱**: 여러 프로그램의 데이터를 포트로 가르며 한 회선에 싣는 것
- **세그먼트 / 데이터그램**: TCP의 단위 / UDP의 단위
- **확인 응답 (ACK)**: 다음에 기대하는 번호를 알리는 응답
- **흐름 제어 / 혼잡 제어**: 받는 쪽의 창에 맞추는 것 / 길의 손실에 맞추는 것
- **3-way / 4-way 핸드셰이크**: 시작 번호를 확인하는 세 번 / 방향마다 닫는 네 번
- **QUIC**: UDP 위에 신뢰와 암호화를 얹은 규칙. HTTP/3의 바탕
{{< /callout >}}
