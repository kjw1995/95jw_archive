[32](../32-network-card-data-transfer)장에서 이 PC를 떠난 133바이트 프레임이 [33](../33-switch-router-data-transfer)장의 11홉을 지나 TTL 118로 example.com의 서버 앞에 닿았다. 이 장은 그 서버가 프레임을 받아 봉투를 뜯고, 요청을 읽어 파일을 찾고, 답을 싸서 되돌려 보내는 일이다. [29](../29-web-server-structure)장은 앞단 서버가 요청을 읽고 뒤로 넘기는 과정을 여기로 미뤘다. 원리는 셋이다. 첫째, **서버의 수신은 32장의 거울이다.** 층마다 "내 것인가"를 먼저 묻고 "깨졌는가"를 그다음에 물으며 봉투를 한 겹씩 뜯고, 마지막 문인 80번 포트에서 웹 서버 프로그램이 받는다. 둘째, **웹 서버 프로그램이 하는 일은 글자를 읽어 파일 경로로 바꾸고, 있으면 주고 없으면 404를 주고, 결과에 헤더를 붙여 되돌려 보내는 것이다.** 이 PC에서 작은 웹 서버를 띄워 같은 요청을 보내고 그 서버의 눈으로 본 기록을 싣는다. 셋째, **서버는 손님 수만큼의 연결을 동시에 다뤄야 하고, 그 방법이 서버의 구조를 가른다.** 연결마다 프로세스인가, 스레드인가, 하나의 루프가 수천 연결을 돌보는가. 이 장의 실측은 이 PC에서 띄운 JDK 내장 웹 서버가 남긴 요청과 응답의 기록, 그리고 존재하지 않는 경로를 요청했을 때의 404다.

---

## 1. 개요

```
수신                      송신
[물리]      비트       ← 비트
   ▲                      │
[데이터링크] 프레임    ← 프레임
   ▲                      │
[네트워크]  패킷       ← 패킷
   ▲                      │
[전송]      세그먼트   ← 세그먼트
   ▲                      │
[응용]      HTTP 요청  → HTTP 응답
```

서버에 도착한 신호는 아래층부터 위로 올라가며 봉투를 한 겹씩 벗고, 응답은 위에서 아래로 내려오며 봉투를 다시 입는다. 33장의 마지막 구간에서 이 요청은 클라우드플레어 라우터가 새로 싼 프레임에 실려 서버의 카드에 닿는다. 프레임의 목적지 MAC은 서버의 카드, IP 헤더의 목적지는 104.20.23.154, TTL은 118, 안에는 32장에서 만든 그대로의 TCP 세그먼트와 75바이트의 `GET /`이다. [08](../08-encapsulation-decapsulation)장에서 본 대로 IP 패킷과 그 안은 이 PC를 떠날 때와 같고, 프레임만 열한 번째 것이다.

## 2. 계층별 수신 처리

| 층 | 내 것인가 | 깨졌는가 | 아니면 |
|:---|:----------|:---------|:-------|
| 물리 | | 프리앰블로 시계를 맞춰 비트를 되살린다 | 시계를 못 맞추면 프레임이 안 된다 |
| 데이터 링크 | 목적지 MAC이 내 카드인가 | FCS | 조용히 버린다. 12장 |
| 네트워크 | 목적지 IP가 나인가 | 헤더 체크섬, TTL이 0이 아닌가 | 버린다. 서버는 넘기지 않는다. 17장 |
| 전송 | 80번에 듣는 프로그램이 있나, 어느 연결인가 | TCP 체크섬, 순서 번호 | 없으면 RST. 24장 |
| 응용 | Host 헤더의 사이트가 여기 있나 | 요청 줄이 문법에 맞나 | 4xx. 29장 |

```
┌──────────┬──────┬──────┐
│ Ethernet │ IP+  │ FCS  │
│ 헤더     │ TCP+ │      │
│          │ HTTP │      │
└──────────┴──────┴──────┘
```

순서가 32장과 같은 이유도 같다. 남의 것에 검사를 쓰지 않는다. 서버의 카드도 이 PC의 카드처럼 목적지 MAC이 자기 것이 아니면 FCS도 보지 않고 버리고, 자기 것이면 체크섬을 검사해 표시만 남긴 채 메모리에 놓는다. 커널의 IP는 목적지가 자기 주소인지 보고, 17장에서 본 대로 서버는 라우터가 아니므로 자기 것이 아니면 넘기지 않고 버린다. TTL 118은 0이 아니니 통과이고, 프로토콜 번호 6이라 TCP에게 준다.

```
1) 목적지 포트로 프로그램을 찾는다
   (80 → HTTP, 443 → HTTPS)
2) TCP 체크섬을 검사한다
3) 순서 번호를 확인해 제자리에 놓는다
4) 확인 응답 번호를 정한다
5) TCP 헤더를 벗긴다
```

TCP는 두 단계로 "내 것"을 찾는다. 먼저 목적지 포트 80에 듣고 있는 소켓이 있는지 보고, 있으면 [26](../26-port-number-structure)장의 네 값(주소 둘, 포트 둘)으로 이 PC와 맺어 둔 연결을 찾는다. 인사가 끝난 연결이므로 세그먼트는 그 연결의 받는 버퍼에 [25](../25-sequence-ack-number)장의 순서 번호대로 놓이고, 75바이트를 받았으니 다음 기대 번호를 확인 응답에 적어 둔다. 이 확인은 [25](../25-sequence-ack-number)장에서 본 대로 곧 나갈 응답 세그먼트에 얹혀 간다.

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.21.0
Accept: */*
```

이제 웹 서버 프로그램의 차례다. 받은 것은 봉투가 다 벗겨진 75바이트의 글자이고, 프로그램은 [28](../28-application-layer-role)장에서 본 대로 빈 줄에서 끊어 요청 줄과 헤더로 나눈다.

1. 요청 줄에서 메서드(GET)와 경로(/)와 버전을 읽는다.
2. Host 헤더로 어느 사이트인지 고른다. 29장에서 본 대로 엉뚱한 Host면 여기서 거절된다.
3. 경로를 파일 경로로 바꾼다. `/`는 그 사이트의 문서 디렉터리, 보통 index.html이다.
4. 파일이면 읽고, 프로그램이 만들 것이면 뒤의 애플리케이션 서버로 넘긴다.
5. 상태 코드와 헤더와 본문으로 응답을 만든다.

이 과정을 서버의 눈으로 보려고 이 PC에서 JDK에 딸린 작은 웹 서버를 127.0.0.1의 8000번에 띄우고, 파일 하나(42바이트짜리 index.html)를 두고, 같은 모양의 요청을 보냈다. 서버가 남긴 기록이 이렇다.

```
127.0.0.1 - -
[14/Sep/2026:09:32:42 +0900]
"GET / HTTP/1.1" 200 -
Resource requested: ...\www
> Accept: */*
> Host: 127.0.0.1:8000
> User-agent: curl/8.21.0
```

첫 줄은 29장에서 본 서버 로그 그대로다. 그 아래 "Resource requested"가 3단계, 곧 경로 `/`를 디스크의 디렉터리로 바꾼 순간이고, `>`로 시작하는 줄들은 서버가 헤더를 한 줄씩 읽어 들인 흔적이다. 존재하지 않는 `/nothing.html`을 요청하면 기록은 `"GET /nothing.html HTTP/1.1" 404 -`와 "could not resolve request URI path"가 된다. 404는 서버가 고장 난 것이 아니라 3단계에서 경로를 파일로 바꾸지 못했다는 뜻이고, 그래서 29장의 표에서 4xx가 "네 잘못"이다.

## 3. 응답 캡슐화

```
응용      HTTP/1.1 200 OK + HTML
   │ + TCP 헤더 (src 80, dst 54321)
   ▼
전송      세그먼트
   │ + IP 헤더
   ▼
네트워크  패킷
   │ + 이더넷 헤더 + FCS
   ▼
데이터링크 프레임
   │ NIC
   ▼
물리      전기 신호
```

```http
HTTP/1.1 200 OK
Date: Mon, 14 Sep 2026 00:32:42 GMT
Last-modified: Mon, 14 Sep 2026 00:32:38 GMT
Content-type: text/html
Content-length: 42
```

이 PC의 작은 서버가 만든 응답이다. 헤더 넷이 어디서 왔는지가 서버가 하는 일의 요약이다. Date는 서버의 시계, Last-modified는 파일의 수정 시각(파일을 만든 4초 뒤에 요청했다), Content-type은 파일 확장자에서, Content-length는 파일의 크기다. 42바이트는 `<html>...</html>` 한 줄 40바이트와 줄바꿈 2바이트다. 서버는 파일의 메타데이터를 헤더로 바꿔 붙이고 본문을 뒤에 단다. example.com의 실제 서버가 32장에서 보낸 응답도 같은 모양이었다. 헤더 301바이트에 본문 559바이트, 그리고 29장의 304를 가능하게 하는 Last-Modified.

응답은 소켓에 쓰이는 순간 32장의 역순을 밟는다. 커널의 TCP가 출발지 포트 80, 목적지 포트에 이 PC의 동적 포트, 순서 번호와 함께 2절에서 정해 둔 확인 응답 번호를 헤더에 적는다. 860바이트는 MSS 안이라 세그먼트 하나이고, IP 헤더에 출발지 104.20.23.154와 목적지 이 PC의 공인 주소, TTL 64가 붙는다. 33장에서 본 답의 TTL 54가 이 64에서 출발한 것이다. 카드가 서버 쪽 게이트웨이의 MAC을 목적지로 프레임을 싸서 내보내면 914바이트 프레임이 되고, 33장의 길을 거꾸로 밟아 이 PC에 온다. 연결은 끊지 않는다. 이 PC의 작은 서버도 "Connection #0 left intact", 곧 연결을 열어 둔 채 응답을 마쳤고, 29장의 Keep-Alive가 서버 쪽에서는 이렇게 보인다. 다음 요청이 같은 연결로 오면 인사 없이 2절부터 다시 한다.

## 4. 웹 서버 소프트웨어

| 제품 | 모델 | 왜 그 모델인가 |
|:-----|:-----|:--------------|
| Apache HTTPD | 프로세스나 스레드마다 연결. 설정으로 고른다 | 1995년의 설계. 모듈과 `.htaccess`로 무엇이든 얹는다 |
| Nginx | 이벤트 루프 하나가 수천 연결 | 2004년. 연결 만 개를 프로세스 몇 개로 |
| Microsoft IIS | 스레드 풀 | Windows와 .NET에 붙어 있다 |
| Node.js | 이벤트 루프 하나 | 자바스크립트 자체가 그렇게 돈다 |
| Tomcat, Spring | 스레드 풀, 요즘은 가상 스레드 | 자바의 서블릿 컨테이너. 뒷단의 WAS |

```
Prefork (프로세스 기반)
[요청 1] → [프로세스 1]
[요청 2] → [프로세스 2]

Worker/Event (스레드·이벤트 기반)
[프로세스]
  ├ 스레드 1 ← 요청 1
  ├ 스레드 2 ← 요청 2
  └ 이벤트 루프 ← 다수 연결
```

셋째 원리가 이 표다. 2절과 3절은 연결 하나의 이야기였지만 서버에는 연결이 수천 개 동시에 있고, 그 대부분은 [25](../25-sequence-ack-number)장의 확인이나 29장의 다음 요청을 **기다리는 중**이다. 연결마다 프로세스를 두면 기다리는 연결마다 메모리를 통째로 쓰고, 스레드를 두면 스레드마다 1MB 안팎의 스택을 쓴다. [자바 기초 16장](../../java/basics/16-networking)에서 이 문제를 그대로 봤다. 연결마다 스레드를 만들면 접속 만 개에 스택만 수 GB이고 그 스레드의 대부분은 읽기에서 자고 있다. 그래서 스레드 수에 상한을 둔 풀이 나왔고, 하나의 루프가 "지금 데이터가 온 연결"만 골라 처리하는 이벤트 방식이 나왔으며, 자바는 그 문제를 가상 스레드로 풀어 이 PC에서 연결 500개를 0.3초에 받았다. Nginx가 이벤트 기반인 이유는 앞단 서버의 일이 대부분 기다리기(느린 클라이언트, Keep-Alive로 놀고 있는 연결)이기 때문이고, 그 일을 스레드 없이 처리하면 연결 만 개가 프로세스 몇 개로 된다.

{{< callout type="info" >}}
29장에서 본 앞단과 뒷단이 여기서 만난다. 앞단의 Nginx가 정적 파일을 직접 답하고, TLS를 풀고([28](../28-application-layer-role)장의 표현 층 일을 앞단이 대신한다), Keep-Alive로 놀고 있는 연결 수천 개를 이벤트 루프로 들고 있다가, 동적 요청만 뒤의 WAS(Spring, Node, Django)로 넘긴다. WAS는 연결이 아니라 **요청**을 받으므로 스레드 풀로 충분하다. 자바 쪽에서 그 WAS가 서블릿 컨테이너이고, 그 안에서 요청이 어떻게 프로그램에 닿는지는 [웹 프로그래밍 시리즈](../../java/web-programming/02-web-application)에서 본다.
{{< /callout >}}

## 5. 라우팅과의 관계

3절의 응답 프레임이 서버의 게이트웨이를 떠난 뒤의 길은 서버 쪽 망들이 정한다. 가는 길과 돌아오는 길이 같으리라는 보장은 없다. 33장에서 본 대로 이 PC에서 example.com까지 라우터가 열 개였고 답의 TTL로 센 돌아오는 길도 열 개였지만, 그것은 세어 보니 같았을 뿐이며 통신사끼리의 [22](../22-router-structure)장 BGP 정책에 따라 다른 길로 돌아오는 일이 흔하다. 서버 쪽 라우팅은 두 가지를 섞는다.

| 어디 | 방식 | 왜 |
|:-----|:-----|:---|
| 서버 랙과 데이터센터 안 | 정적 기본 경로, OSPF | 출구가 정해져 있고 안에서는 최단 경로면 된다 |
| 데이터센터와 인터넷 사이 | BGP | 통신사 여럿과 계약으로 길을 고른다 |

| 출처 | 관리 거리 | 뜻 |
|:-----|:----------|:---|
| 직접 연결 | 0 | 가장 믿는다 |
| 정적 | 1 | 사람이 적었다 |
| eBGP | 20 | 밖에서 배운 길 |
| OSPF | 110 | 안에서 계산한 길 |
| RIP | 120 | 소문 |
| iBGP | 200 | 안에서 전달된 BGP 길 |

같은 목적지의 줄이 여럿이면 [22](../22-router-structure)장에서 본 대로 최장 일치, 관리 거리, 메트릭의 순서로 고른다. 이 표는 그 둘째 기준의 값이고, 서버 쪽 라우터가 안에서 계산한 길보다 통신사에서 배운 길을 더 믿는 이유(eBGP 20)는 밖으로 나가는 길은 밖이 더 잘 알기 때문이다.

## 6. 실무 도구

```bash
# 라우팅
ip route show
ip route get 104.20.23.154
route -n
show ip route                  # Cisco. C, S, O, B가 출처
```

```bash
# 웹 서버가 살아 있나
ps aux | grep -E 'httpd|nginx'
systemctl status nginx

# 듣고 있나 (26장의 LISTEN)
ss -tlnp
netstat -tlnp | grep :80
Get-NetTCPConnection -State Listen -LocalPort 80   # Windows

# 요청마다 한 줄
tail -f /var/log/nginx/access.log
tail -f /var/log/nginx/error.log
```

```bash
# 이 장의 실험. JDK 18 이상에 들어 있다
jwebserver -b 127.0.0.1 -p 8000 -d ./www -o verbose
curl -v http://127.0.0.1:8000/
curl -o NUL -w "%{http_code}" http://127.0.0.1:8000/nothing.html
```

서버 점검의 순서는 이 장의 순서다. 프로그램이 떠 있는가, 그 포트에서 듣고 있는가, 요청이 로그에 찍히는가. 로그에 찍히는데 404면 2절의 3단계, 곧 경로가 파일로 안 바뀐 것이고, 500이면 4단계에서 뒤의 프로그램이 실패한 것이며, 로그에 아예 안 찍히면 요청이 서버 프로그램까지 오지 못한 것이라 33장의 길이나 26장의 방화벽을 본다. 마지막 블록이 2절의 실험이다. 디렉터리 하나를 서버로 띄우는 데 한 줄이면 되고, 그 로그에서 요청이 파일이 되는 순간을 볼 수 있다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 수신 | 32장의 거울 | 내 것인가, 그다음 깨졌는가 |
| 도착한 것 | TTL 118, 75바이트 그대로 | 패킷은 끝에서 끝까지의 것 |
| TCP의 두 단계 | 80번 소켓, 그다음 네 값의 연결 | 듣는 소켓과 맺은 연결은 다르다 |
| 웹 서버의 일 | 글자를 경로로, 경로를 파일로 | Resource requested가 그 순간 |
| 404 | 경로가 파일이 안 됐다 | 서버는 멀쩡하다 |
| 응답 헤더 | 시계, 수정 시각, 확장자, 크기 | 파일의 메타데이터가 헤더가 된다 |
| Content-length 42 | 파일 크기 그대로 | 40바이트와 줄바꿈 2 |
| 응답의 TTL | 64에서 출발 | 33장의 54는 이것에서 10을 뺀 것 |
| 연결을 열어 둔다 | left intact | Keep-Alive의 서버 쪽 |
| 처리 모델 | 프로세스, 스레드, 이벤트 | 연결의 대부분은 기다리는 중이다 |
| 앞단과 뒷단 | 연결은 앞단이, 요청은 뒷단이 | 정적은 싸고 동적은 비싸다 |
| 돌아오는 길 | 서버 쪽이 정한다 | BGP 정책. 가는 길과 다를 수 있다 |
| 점검 순서 | 떠 있나, 듣나, 찍히나 | 로그가 없으면 서버 밖의 문제 |

**용어 정리**
- **역캡슐화**: 받은 프레임의 봉투를 아래층부터 한 겹씩 벗기는 것. 층마다 내 것인가와 깨졌는가를 본다
- **듣는 소켓 / 연결 소켓**: 80번에서 기다리는 것 / 손님마다 맺어진 네 값의 연결
- **문서 디렉터리**: URL의 경로를 대응시키는 디스크의 폴더. `/`는 보통 index.html
- **404 / 500**: 경로를 파일로 못 바꿨다 / 뒤의 프로그램이 실패했다
- **MPM**: Apache의 처리 모델 선택. prefork, worker, event
- **이벤트 루프**: 데이터가 온 연결만 골라 처리하는 하나의 순환. Nginx, Node
- **WAS**: 요청을 받아 프로그램을 돌리는 뒷단 서버. 자바의 서블릿 컨테이너
- **관리 거리**: 라우팅 표에서 출처마다 정한 신뢰도. 22장
