[23. 전송 계층의 역할](../23-transport-layer-role)에서 포트는 프로그램의 주소이고 서버의 포트는 정해져 있지만 클라이언트의 포트는 그때그때 운영체제가 고른다고 했다. [04](../04-home-lan-configuration)장의 NAT는 이 번호를 바꿔서 기기를 구별했고, [05](../05-office-lan-configuration)장의 방화벽은 이 번호로 규칙을 적었으며, [06](../06-network-protocol)장은 이 PC에 200개가 넘는 연결이 열려 있어도 섞이지 않는 이유를 이 장으로 미뤘다. 원리는 셋이다. 첫째, **포트는 주소라기보다 약속이다.** IP 주소는 기계의 위치이지만 포트 번호는 "이 번호에서 이 서비스가 기다린다"는 약속이고, 약속이 필요한 쪽은 서버뿐이다. 그래서 번호의 범위가 세계가 합의한 것, 등록한 것, 약속이 필요 없는 것 셋으로 나뉜다. 둘째, **연결의 이름은 포트 하나가 아니라 다섯 값이다.** 프로토콜, 주소 둘, 포트 둘. 같은 80번에 수천 명이 붙어도 되고, TCP 443과 UDP 443이 다른 문이며, NAT가 포트를 바꿔도 되는 이유가 여기서 나온다. 셋째, **열린 포트는 문이고, 문의 수가 곧 공격면이다.** 그래서 확인하고, 닫고, 방화벽으로 거른다. 이 장의 실측은 이 PC의 동적 포트 범위와 지금 열려 있는 문의 수다.

## 1. 포트 번호란

| 값 | 답하는 질문 | 누가 정하나 |
|:---|:-----------|:-----------|
| IP 주소 | 어느 기계인가 | 망 관리자나 DHCP. 18장 |
| 포트 번호 | 그 기계 안의 어느 프로그램인가 | 서버는 약속으로, 클라이언트는 운영체제가 그때그때 |

```text
192.168.1.10 : 80
└─── IP ───┘  └ Port
```

포트 번호는 [02](../02-bit-and-byte)장에서 본 대로 16비트라 0부터 65,535까지다. IP가 아파트의 동이라면 포트는 호수다. 우편물이 동까지 왔어도 호수가 없으면 누구에게 줄지 모르듯, 세그먼트가 기계까지 왔어도 포트가 없으면 운영체제는 브라우저에게 줄지 메일 프로그램에게 줄지 모른다. 운영체제는 도착한 세그먼트와 데이터그램의 목적지 포트를 보고 그 번호에서 기다리는 프로그램에게 건넨다.

{{< callout type="info" >}}
포트 없이 IP만 있다면 한 서버에서 웹과 메일과 SSH가 동시에 돌 수 없다. 기계 하나에 프로그램 하나만 네트워크를 쓸 수 있었을 것이고, 서비스마다 기계를 따로 두어야 했을 것이다. 23장의 멀티플렉싱은 전부 이 16비트에 기대고 있다.
{{< /callout >}}

## 2. 포트 번호의 범위

| 범위 | 이름 | 뜻 | 왜 나뉘나 |
|:-----|:-----|:---|:----------|
| 0 ~ 1023 | 잘 알려진 포트 | 세계가 합의한 번호 | 상대가 미리 알아야 찾아온다 |
| 1024 ~ 49151 | 등록 포트 | 겹치지 말자고 명부에 올린 번호 | 표준은 아니지만 부딪히면 곤란하다 |
| 49152 ~ 65535 | 동적 포트 | 그때그때 쓰고 버리는 번호 | 클라이언트는 약속이 필요 없다 |

약속이 필요한 쪽은 먼저 말을 거는 쪽의 **상대**뿐이다. 브라우저는 서버가 443번에서 기다린다는 약속을 알고 찾아가지만, 서버는 브라우저의 포트를 미리 알 필요가 없다. 요청에 적혀 오기 때문이다. 그래서 위 두 범위는 서버의 번호이고 마지막 범위는 클라이언트의 번호다. 인터넷 번호 기구(IANA)가 앞 둘의 명부를 관리한다.

| 운영체제 | 동적 포트 범위 | 개수 |
|:---------|:--------------|:-----|
| Windows | 49152 ~ 65535 | 16,384 |
| Linux | 32768 ~ 60999 | 28,232 |
| 옛 BSD | 1024 ~ 4999 | 3,976 |

실제 동적 범위는 운영체제마다 다르다. 이 PC의 설정을 읽으면 TCP와 UDP 모두 49152부터 16,384개로, IANA의 표 그대로다. Linux가 32768부터 시작하는 것은 옛 BSD의 1024~4999가 너무 좁아 넓힌 뒤 등록 포트 영역을 일부 침범한 채 굳은 것이다. 이 개수는 한계가 되기도 한다. 한 서버로 연결을 맺었다 끊기를 반복하면 끊긴 연결이 [24](../24-tcp-structure)장의 TIME_WAIT로 2분 동안 포트를 붙들고 있으므로, Windows에서 같은 서버로는 초당 136개 남짓(16,384 ÷ 120초)이 새 연결의 상한이다. 요청마다 연결을 새로 맺는 프로그램이 바쁜 서버 앞에서 "포트가 없다"며 실패하는 이유이고, 연결을 재사용하는 HTTP의 Keep-Alive가 필요한 이유이기도 하다.

## 3. 잘 알려진 포트 (0~1023)

| 포트 | 서비스 | 왜 이 번호, 왜 이 모양인가 |
|:-----|:-------|:--------------------------|
| 20, 21 | FTP 데이터, 제어 | 명령과 파일을 다른 연결로 보내던 1971년의 설계 |
| 22 | SSH | 23번 Telnet의 암호화 대체. 바로 옆 번호를 받았다 |
| 23 | Telnet | 평문 원격 접속. 지금은 쓰면 안 된다 |
| 25 | SMTP | 서버끼리 메일을 넘기는 문 |
| 53 | DNS | UDP와 TCP 둘 다. 30장 |
| 67, 68 | DHCP 서버, 클라이언트 | 둘 다 브로드캐스트를 받으므로 번호로 갈라야 했다 |
| 80 | HTTP | 1991년에 비어 있던 번호 |
| 110, 143 | POP3, IMAP | 메일을 가져오는 두 방식. 31장 |
| 443 | HTTPS | 80에 TLS를 얹은 것에 새 번호 |
| 465, 993, 995 | SMTPS, IMAPS, POP3S | TLS 판마다 새 번호를 받은 시절의 흔적 |
| 587 | 메일 제출 | 클라이언트가 자기 서버에 보내는 문을 25번과 분리 |

번호 자체에 뜻은 없다. 먼저 신청한 순서와 그때 비어 있던 자리일 뿐이고, 그래서 표는 외우는 것이지 유도하는 것이 아니다. 다만 모양에는 이유가 있다. FTP가 포트 둘을 쓰는 것은 명령 채널과 데이터 채널을 따로 두어 전송 중에도 명령을 받으려던 설계이고, DHCP가 67과 68로 나뉜 것은 [18](../18-ip-address-structure)장에서 본 대로 서버도 클라이언트도 브로드캐스트를 받기 때문에 한 기계에서 둘을 구별할 방법이 번호뿐이었기 때문이다. 443과 465, 993, 995는 기존 서비스에 암호화를 얹으면서 새 번호를 받은 것인데, 나중에는 같은 번호에서 암호화를 켜는 방식(STARTTLS)도 나와 번호가 둘씩이다.

{{< callout type="warning" >}}
Unix와 Linux에서 1024 미만 포트를 열려면 root 권한이 필요하다. 이것은 IANA의 규칙이 아니라 1980년대 BSD의 관례다. 아무나 80번을 열 수 있으면 남의 웹 서버 행세를 할 수 있으니 관리자만 열게 한 것이고, Windows에는 이 구분이 없다. 컨테이너와 일반 사용자 환경에서 8080처럼 1024 이상을 쓰거나, 권한 하나만 따로 주는 capability로 우회하는 이유가 이 관례다. Linux는 이 경계를 설정으로 낮출 수도 있다.
{{< /callout >}}

## 4. 등록 포트 (1024~49151)

| 포트 | 서비스 | 비고 |
|:-----|:-------|:-----|
| 1433 | MS SQL Server | |
| 1521 | Oracle | |
| 3306 | MySQL | |
| 3389 | 원격 데스크톱 (RDP) | 인터넷에 열어 두면 안 되는 대표 포트 |
| 5432 | PostgreSQL | |
| 5900 | VNC | |
| 6379 | Redis | 기본은 인증 없음. 9절 |
| 8080, 8443 | HTTP, HTTPS 대체 | 80과 443을 못 열 때. 80을 두 번 쓴 이름 |
| 9200 | Elasticsearch | |
| 27017 | MongoDB | |

등록은 강제가 아니라 명부다. IANA에 "이 번호는 우리가 쓴다"고 올려 두면 다른 회사가 같은 번호를 피하고, 방화벽과 감시 도구가 번호만 보고 서비스를 짐작할 수 있다. 어기면 벌은 없지만 겹치면 서로 곤란하다. 그래서 MySQL은 3306, PostgreSQL은 5432처럼 제품마다 번호가 굳어 있고, 이 번호들이 곧 9절에서 공격자가 먼저 두드리는 문이다.

## 5. 소켓: 주소와 포트의 짝

```text
클라이언트 192.168.1.10:52341
                 ↕
서버       203.0.113.50:80
```

IP 주소와 포트 번호의 짝이 소켓이고, 소켓은 통신의 끝점이다. 연결은 그 끝점 둘로 이루어지므로 다음 값의 조합이 연결 하나를 유일하게 가리킨다.

| 값 | 예 | 왜 필요한가 |
|:---|:---|:-----------|
| 프로토콜 | TCP | TCP 443과 UDP 443은 다른 문이다 |
| 내 주소, 내 포트 | 192.168.1.10:52341 | 같은 서버에 붙은 내 연결들을 가른다 |
| 상대 주소, 상대 포트 | 203.0.113.50:80 | 어느 서버의 어느 서비스인가 |

| 연결 | 내 쪽 | 상대 쪽 |
|:-----|:------|:--------|
| 구글 탭 1 | 192.168.1.10:52341 | 142.250.185.78:443 |
| 구글 탭 2 | 192.168.1.10:52342 | 142.250.185.78:443 |
| 깃허브 탭 | 192.168.1.10:52343 | 140.82.114.4:443 |

같은 서버의 같은 443번에 탭 둘이 붙어도 내 포트가 다르니 다른 연결이고, 서버 쪽에서 보면 같은 80번 하나에 수천 명이 붙어 있어도 상대 주소와 상대 포트가 제각각이라 섞이지 않는다. 06장에서 본 이 PC의 200개 넘는 연결이 전부 같은 IP 주소로 드나드는데 구별되는 이유가 이것이고, 04장의 NAT가 포트를 마음대로 바꿔도 되는 이유도 이것이다. 안쪽 기기 둘이 같은 50000번을 써도 밖에서 40001과 40002로 바꿔 놓으면 다섯 값이 여전히 유일하다. 프로토콜이 첫 값인 것은 요즘 브라우저가 같은 서버의 443번에 TCP로도, [23](../23-transport-layer-role)장의 HTTP/3처럼 UDP로도 붙기 때문이다. 번호가 같아도 문은 둘이다.

## 6. 동적 포트 할당

클라이언트는 자기 포트를 고르지 않는다. 프로그램이 연결을 요청하면 운영체제가 2절의 동적 범위에서 비어 있는 번호 하나를 골라 붙인다.

1. 프로그램이 `connect()`를 부른다. 상대의 주소와 포트만 준다.
2. 운영체제가 동적 범위에서 쓰이지 않는 포트를 하나 고른다.
3. 그 포트를 출발지로 SYN을 보낸다.
4. 연결이 끝나면 포트를 돌려받는다. 24장의 TIME_WAIT가 지나면 다시 쓸 수 있다.

| 고르는 법 | 동작 | 문제 |
|:---------|:-----|:-----|
| 순차 | 49152, 49153, 49154, ... | 다음 번호를 누구나 맞힌다 |
| 무작위 | 범위 안에서 예측 불가능하게 | 지금의 기본 |

무작위로 바뀐 데는 사건이 있다. 순차 할당이면 내 다음 연결의 포트를 밖에서 맞힐 수 있고, 맞힌 포트로 가짜 답장을 보내면 진짜 답장보다 먼저 도착해 받아들여질 수 있다. 2008년에 DNS 서버가 이 방식으로 속아 엉뚱한 주소를 기억하게 되는 공격이 알려진 뒤, 포트를 무작위로 고르는 것이 규격의 권고가 되었다. 포트 번호는 인증이 아니지만, 맞히기 어렵게 하는 것만으로도 공격의 값을 올린다. [자바 기초 16장](../../java/basics/16-networking)에서 `new Socket(host, port)`에 내 포트를 적지 않는 것이 이 절차이고, 서버 쪽에서 `new ServerSocket(0)`처럼 0을 주면 운영체제가 빈 포트를 골라 준다.

## 7. TCP와 UDP 헤더에서의 포트

```text
 0        16        31
 ├─────────┼─────────┤
 │ src port│ dst port│
 ├─────────┴─────────┤
 │  sequence number  │
 └───────────────────┘
```

```text
 0        16        31
 ├─────────┼─────────┤
 │ src port│ dst port│
 ├─────────┼─────────┤
 │  length │checksum │
 └─────────┴─────────┘
```

TCP와 UDP 모두 헤더의 **맨 앞 4바이트**가 출발지 포트와 목적지 포트다. 두 규칙이 그 외에는 딴판인데 이 자리만 같은 것은, 포트가 두 규칙에 공통인 유일한 정보이고 받는 쪽이 가장 먼저 할 일이 "누구에게 줄지"이기 때문이다. 원칙적으로 4층을 읽지 않는 중간 장비들, 곧 NAT와 방화벽이 실제로는 이 앞 4바이트만 읽는 것도 같은 이유다. 어느 규칙이든 같은 자리에 있으니 규칙을 몰라도 읽을 수 있다. UDP는 답이 필요 없는 일방 전송이면 출발지 포트를 0으로 둘 수 있다. 상대가 답장할 곳을 알 필요가 없으므로 비워도 되는 것이고, 상태가 없는 UDP다운 규칙이다. 두 헤더의 나머지는 [24](../24-tcp-structure)장과 [27](../27-udp-structure)장에서 본다.

## 8. 포트 확인과 관리

```bash
# Windows
netstat -an                       # 전부
netstat -ano                      # 프로세스 번호까지
netstat -ano | findstr ":80"      # 특정 포트
Get-NetTCPConnection -State Listen

# Linux
ss -tuln                          # 듣고 있는 포트
ss -tulnp                         # 프로세스까지
lsof -i :80                       # 이 포트를 누가 쓰나
```

듣고 있는 포트(LISTEN)가 곧 열린 문이다. 이 PC에서 세어 보면 지금 TCP 65개, UDP 75개의 문이 열려 있다. 대부분 운영체제와 백그라운드 서비스가 연 것이고, 그 하나하나가 9절에서 점검할 대상이다.

### 포트 충돌

`Address already in use`는 같은 포트를 두 프로그램이 열려 할 때 난다. 24장에서 본 대로 TIME_WAIT 때문에 조금 전에 닫은 서버가 다시 못 열리는 경우와, 진짜로 다른 프로그램이 그 포트를 쓰고 있는 경우가 있다.

```bash
# 누가 쓰는지 찾아 끝낸다
lsof -i :80                       # Linux
kill <PID>
netstat -ano | findstr :80        # Windows
taskkill /PID <PID> /F
```

1. 점유한 프로세스를 찾아 끝낸다.
2. 다른 포트를 쓴다. 8080이 관례다.
3. TIME_WAIT라면 `SO_REUSEADDR`을 켠다. 24장.

### 방화벽

```bash
# Windows
netsh advfirewall firewall add rule name="HTTP 80" dir=in action=allow protocol=TCP localport=80

# Linux
firewall-cmd --permanent --add-port=80/tcp && firewall-cmd --reload
ufw allow 80/tcp
```

05장에서 본 방화벽 규칙의 뿌리는 "기본은 거부, 필요한 것만 허용"이었고, 그 허용의 단위가 포트다. 서버를 띄웠는데 밖에서 안 붙으면 프로그램이 듣고 있는지(위의 LISTEN)와 방화벽이 열려 있는지(위의 규칙)를 따로 봐야 한다. 둘은 다른 층의 문이다.

## 9. 포트 보안 권장 사항

| 권장 | 왜 |
|:-----|:---|
| 안 쓰는 포트는 닫는다 | 문의 수가 공격면이다. `nmap`으로 밖에서 본 내 문을 주기적으로 센다 |
| 데이터베이스는 127.0.0.1에만 연다 | 4절의 번호들은 공격자가 먼저 두드린다. 같은 기계에서만 붙게 한다 |
| 관리 포트는 특정 IP만 허용 | 22, 3389는 비밀번호 사전 공격의 단골이다 |
| 22를 2222로 바꾸는 것은 보안이 아니다 | 자동 스캔의 소음을 줄일 뿐이다. 키 인증과 함께 써야 한다 |
| 포트 노킹 | 정해진 순서로 두드려야 문이 열린다. 문이 있는지조차 안 보인다 |

열린 포트는 밖에서 보인다. 인터넷 전체를 상시로 훑는 검색 서비스가 있어 3389나 6379를 열어 둔 기계는 몇 분 안에 발견되고, 인증이 없는 Redis처럼 기본 설정이 열린 서비스는 발견되는 즉시 남의 것이 된다. 포트를 닫는 것은 이 시리즈에서 배운 것 중 가장 싸고 효과가 큰 보안이다.

## 핵심 정리

| 개념 | 핵심 | 왜 |
|:-----|:-----|:---|
| 포트 | 16비트, 기계 안의 프로그램 | 동과 호수 |
| 약속 | 서버의 번호만 정해져 있다 | 먼저 말을 거는 쪽의 상대만 알려져 있으면 된다 |
| 세 범위 | 합의, 등록, 동적 | 약속의 강도 |
| 이 PC의 동적 범위 | 49152부터 16,384개 | IANA 표 그대로. TCP와 UDP 같다 |
| 동적 포트의 한계 | 같은 서버에 초당 136개 | TIME_WAIT 2분 동안 포트가 묶인다 |
| 잘 알려진 번호 | 외우는 것이지 유도하는 것이 아니다 | 신청 순서와 빈자리 |
| 1024의 경계 | root만 연다 | BSD의 관례. Windows에는 없다 |
| 등록 | 명부이지 강제가 아니다 | 겹치면 서로 곤란하다 |
| 연결의 이름 | 프로토콜 + 주소 둘 + 포트 둘 | 같은 80에 수천 명, TCP 443과 UDP 443 |
| NAT | 포트를 바꿔도 된다 | 다섯 값이 유일하면 그만이다 |
| 무작위 할당 | 다음 포트를 못 맞히게 | 2008년의 DNS 공격 |
| 헤더 맨 앞 4바이트 | TCP와 UDP가 같다 | 누구에게 줄지가 첫 일. NAT와 방화벽도 여기만 읽는다 |
| 이 PC의 문 | TCP 65, UDP 75 | 하나하나가 점검 대상 |
| 보안 | 닫고, 묶고, 거른다 | 문의 수가 공격면이다 |

{{< callout type="info" >}}
**용어 정리**
- **포트 번호**: 기계 안의 프로그램을 가리키는 16비트 번호
- **잘 알려진 포트 / 등록 포트 / 동적 포트**: 0~1023 세계의 약속 / 1024~49151 명부 / 49152~65535 그때그때
- **동적(임시) 포트**: 클라이언트가 연결마다 운영체제에서 받는 번호
- **소켓**: 주소와 포트의 짝. 통신의 끝점
- **연결의 다섯 값**: 프로토콜, 내 주소, 내 포트, 상대 주소, 상대 포트
- **LISTEN**: 프로그램이 그 포트에서 기다리는 상태. 열린 문
- **포트 충돌**: 같은 포트를 둘이 열려는 것. Address already in use
- **포트 노킹**: 정해진 순서로 두드려야 열리는 문
